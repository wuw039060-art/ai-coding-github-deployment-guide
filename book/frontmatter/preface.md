# 前言

很多人的第一次软件开发经历，已经不再从一门编程语言或一本教材开始。它可能只从一句“帮我做一个预约网站”开始。几分钟以后，AI 已经创建了项目文件、页面、接口和数据库配置。再过一会儿，它也许会告诉你网站已经部署完成，并给出一个可以打开的地址。

这改变了过去常见的顺序。以前往往先学习，再练习，最后才尝试做产品。现在，一个人可以先把想法做出雏形，再在真实问题出现时补充知识。许多原本不会开始编程的人，第一次获得了亲手解决问题的能力。一个小工具可以替家人减少重复劳动，一个网站可以验证一项服务，一个 App 可以把只有创作者真正理解的需求交到用户手里。

新的机会也带来了新的知识断层。AI 可以把人送进软件开发，却不会自动把软件工程常识一起放进人的头脑。项目已经存在，使用者却不清楚这些文件各自负责什么。AI 已经在修改 Git 记录，使用者却不知道一个版本保存了什么。数据库结构发生变化，他看见的可能只是一段迁移脚本。部署平台显示构建成功，他也无法判断用户登录、数据写入和故障恢复是否真的可用。

这时完全照搬传统计算机专业的学习路线，通常太长，也未必符合眼前任务。一个人今天需要处理的是环境变量配置错误，先花半年学习完整的操作系统和计算机网络并不现实。另一种做法是把所有事情继续交给 AI。它在项目较小时很省力，但项目一旦涉及真实用户、付费、隐私和长期维护，黑箱里的问题就会迅速积累。AI 一次改动几十个文件，你不知道范围是否合理；它引入新的组件，你无法判断复杂度有没有必要；它说测试已经通过，你也不知道测试覆盖了哪些路径。

《AI 写代码之后》写给的正是处在这两条路之间的人。你已经愿意借助 AI 创造软件，也希望补上与当前工作真正相关的知识。你不需要先完成一套本科培养计划，也不能永远只凭一句完成说明判断结果。本书会从 AI Coding 的真实场景出发，重新筛选和排列 Git、网络、部署、服务器、数据库、Docker、App 发布、日志、安全和维护知识。每个专题都尽量讲到足以支持当前判断的深度，再把更专门的内容留到真正需要的时候。

## 视频确实能更快教会第一次操作

如果你的目标只是第一次创建 GitHub 仓库，完成一次 Commit 和 Push，或者跟着部署平台发布一个简单网页，视频、官方交互教程和亲手操作通常比连续阅读几十页文字更有效率。为了完成第一次 Push，没有必要先读完整本书。界面操作具有明显的动作顺序，先看一遍完整流程，再暂停视频逐步跟做，往往最容易建立第一印象。

操作完成以后，另一类问题才会出现。学会按下 Push，并不等于理解版本控制。成功部署一次，也不等于知道构建、运行环境、DNS 和后端分别承担什么。Docker 显示 Running，只能说明容器进程处在运行状态，用户仍可能无法访问服务。AI 回复 Done，也只能说明它认为任务已经完成，实际需求、关键路径和回退办法仍要用证据检查。

因此，视频、本书和 AI 各自承担不同工作。视频把第一次操作变得可见，让你快速看到按钮、窗口和完整流程。本书连接不同技术，解释为什么会出现某种配置，错误可能停在哪一层，以及一个成功状态究竟证明到哪里。AI 可以结合你的真实项目继续解释、执行修改和收集反馈。三者配合以后，学习会形成一个自然循环。先看见，再理解，接着动手；遇到问题以后带着证据回来理解，然后继续完成项目。

视频不承担事实裁决。平台界面、账号政策和软件行为都会变化，第三方视频也可能存在错误。书中的视频只作为视觉辅助。只要视频与当前官方文档、标准或经过验证的实际行为发生冲突，就应以后者为准。

## 本书希望留下什么

本书不会承诺让读者在短时间内获得等同于计算机专业训练的能力。专业训练包含大量理论、实践、评审和长期经验，一本书无法替代。更现实的目标是，在常见的 AI Coding 场景中，尽量缩小由基础工程认知造成的使用能力差距。

读完并实践其中的核心内容以后，你应该能大致看懂项目结构，知道 AI 正在修改哪一层，能阅读主要的 Git Diff，能提供有效的调试材料，也能识别明显的复杂度扩张。你会逐渐分清代码写完、构建成功、程序运行、用户可用和产品可靠之间的距离。遇到密钥、生产数据、支付、安全或不可逆操作时，你也会知道何时暂停，何时核对官方资料，何时请更有经验的人共同确认。

这些能力并不要求你拒绝自动化。亲手完成一次提交、部署、日志检查和恢复练习，是为了获得可以比较的参照。以后仍然可以让 AI 执行大量工作，但你能描述范围，要求验证，检查结果，并在证据不足时提出更准确的问题。就像使用导航不会取消人对目的地和道路风险的判断，使用 AI 也不应取消人对需求、数据和交付结果的责任。

AI 会继续变得更擅长执行。需求来自人，数据属于真实的人，软件最终服务的也是人。因此至少有一件事情不适合完全外包，那就是知道自己的项目正在发生什么，并保留最后的判断。
