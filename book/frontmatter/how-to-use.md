# 如何使用本书

全书有十卷、104 章，承担的是一套学习与查询体系。你不必先从头读到尾才开始做项目。最合适的方式取决于你现在有没有项目、正在卡在哪一层，以及希望建立多完整的理解。

## 第一次来到这里

先读前言和第一卷。第一卷会把本地电脑、GitHub、部署平台、服务器和用户设备放进同一张地图。读完以后，你至少能判断一个问题更接近项目文件、构建、网络、运行环境还是用户设备。随后可以进入核心路线，也可以直接选择与你当前项目对应的路线。

核心路线由十五章组成，依次是第 1、5、8、12、14、15、18、19、21、26、59、64、65、70 和 72 章。它覆盖交付链路、Git、秘密保护、网络请求、数据位置、浏览器排错、构建与环境变量、故障定位、向 AI 提供材料、最小权限、验证和完成检查。多数读者可以分几次阅读和练习，不必连续读完，也不必先掌握所有高级章节。

## 带着自己的项目学习

如果你正在制作网站，可以先读第一至第四卷，再按需要进入第五卷和第九卷。项目使用自建服务器时，继续读第六、七卷。正在制作 Flutter App 或微信小程序的读者，可以先建立第一、三、五卷的基础认识，再进入第八卷。希望长期与 AI 协作、控制项目复杂度的人，可以在掌握版本、日志和验证以后阅读第十卷。

每读完一个关键专题，都拿自己的项目做一次小检查。学习 Git 时，看一遍 AI 最近改动的文件，并确认提交范围。学习 HTTP 时，在浏览器 Network 面板里找到一个真实请求，记录方法、地址、状态码和响应。学习环境变量时，只核对变量名和生效环境，不复制真实值到聊天或公开仓库。学习 Docker 时，确认哪些数据位于 Volume，哪些内容会随着容器重建而消失。

这些练习的目的很朴素。你需要把书中的名词对应到自己的文件、界面和结果。操作成功也要注意边界。Push 成功说明提交到达远程仓库，不能证明部署已经成功。HTTP 返回 200 说明请求得到了成功状态响应，不能单独证明业务结果正确。测试通过说明已执行的测试没有发现失败，不能证明没有其他缺陷。

## 遇到问题时怎样查

先按现象寻找证据，再选择章节。页面显示异常，先看 Console。请求失败，打开 Network。部署失败，查看 Build Log。上线以后才报错，查看 Runtime Log。服务器服务异常，检查 systemd 或容器日志。数据不符合预期，先确认请求是否到达后端，再查数据库记录和权限策略。第九卷提供了跨平台的故障定位方法，适合在不知道从哪里开始时使用。

搜索时优先使用稳定术语，例如 `CORS`、`502`、`environment variable`、`volume`、`journalctl` 和 `TestFlight`。不要只搜索“为什么打不开”。把软件版本、发生位置、预期结果、实际结果和完整错误一起交给 AI，通常能显著减少猜测。

## 视频、本书和 AI 怎样配合

需要辨认界面或连续动作时，先看正文里的跟做视频提示。配套资源优先选择 B 站中文入口，YouTube 作为官方演示或备用入口。观看前准备练习仓库或测试账号，观看时暂停并亲手完成关键步骤。完成以后回到对应章节，理解每一步改变了哪里，以及结果还不能证明什么。接着让 AI 检查你的真实项目，但要限制修改范围，并要求它给出 Diff、测试、日志或实际访问结果。

所有平台行为和政策都以当前官方资料为准。视频用于帮助看懂，不能替代官方文档。涉及删除数据、改写 Git 历史、开放端口、修改 SSH、防火墙、数据库迁移、密钥轮换、应用商店提交和小程序发布时，先确认影响范围、备份、验证方法和回退办法，再执行最后一步。

如果某个专题暂时与你无关，可以跳过。等项目真正出现相应需求时再回来读，理解会更快。系统学习和问题查询并不冲突。前者让你看见技术之间的关系，后者让知识在真实任务中变得牢固。
