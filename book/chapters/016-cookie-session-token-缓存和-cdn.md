# Cookie、Session、Token、缓存和 CDN

HTTP 请求本身通常彼此独立。用户第一次打开登录页与提交密码，是两个请求。登录成功后继续认识同一用户，需要浏览器和服务器共同保存状态。Cookie、Session 与 Token 解决身份和状态传递。缓存与 CDN 解决重复内容的复用与距离。它们都可能让用户看到“同一个地址却不是同一个结果”。

## Cookie 是浏览器保存的小段数据

服务器在响应中使用 Set-Cookie，浏览器按规则保存。之后访问符合域名、路径和安全条件的请求时，浏览器自动带上 Cookie。MDN Cookie 指南说明，HTTP 是无状态协议，Cookie 能让服务器在不同请求之间识别有限状态。常见用途包括会话管理、个性化和跟踪。

Cookie 包含名称和值，还可以设置 Domain、Path、Expires 或 Max-Age、Secure、HttpOnly 与 SameSite 等属性。Cookie 容量有限，并会随请求发送，不适合保存大段业务数据。敏感会话通常只存随机会话标识，真实账户状态留在服务器。

Secure 要求 Cookie 通过 HTTPS 发送。生产会话应使用 HTTPS。开发环境的行为要按浏览器与本地规则测试。HttpOnly 阻止普通页面 JavaScript 读取 Cookie，能降低部分脚本窃取会话的风险。浏览器仍会按规则在请求中发送。

SameSite 控制跨站请求时是否带 Cookie，有助于防御 CSRF。Strict、Lax 与 None 的行为不同。跨站登录和嵌入场景需要准确配置。这些属性各自解决一部分风险，不能替代输入防护、权限检查与会话过期。错误 Domain 或 Path 也会让 Cookie 不发送。

## Session 把状态留在服务器

![Cookie 与服务端 Session 登录流程](../assets/diagrams/login-session-flow.png)

*Cookie 与服务端 Session 登录流程*

图中浏览器通过 HTTPS 提交凭据。后端验证后在服务端创建 Session，并只把随机会话标识放入安全 Cookie。后续请求自动带 Cookie，后端查会话并检查权限。注销时，服务端使会话失效并删除客户端 Cookie。

Session 译为会话。用户登录成功后，服务器生成难以猜测的会话标识，把账户、过期时间和其他状态保存在服务端存储。浏览器 Cookie 只保存标识。后续请求带标识，服务器查到对应会话并得到用户身份。注销时服务器使会话失效，并让浏览器删除 Cookie。

会话存储可以在内存、数据库或专门缓存服务中。单实例内存很简单，多实例部署时请求可能到另一台机器，需要共享存储或粘性会话。服务器重启后内存会话消失，用户被迫重新登录。是否可接受由产品决定。高风险操作还可以要求重新验证身份。

## Token 是携带证明的字符串

Token 译为令牌。它表示客户端获得了某种访问能力。API Key、访问令牌和刷新令牌都属于不同形式。有些 Token 只是随机标识，服务端查存储得到状态。有些签名 Token 自带用户、过期时间和权限声明，服务端验证签名后读取。

JWT 是常见签名 Token 格式。其 Header 与 Payload 通常只是编码，不是加密。放进其中的信息可能被客户端读取；签名防止未授权修改，不能隐藏内容；Token 泄露后，持有者可能在有效期内冒充用户。应使用 HTTPS、安全存储、短期访问令牌和可控撤销。具体设计需要安全评审。

浏览器网站常使用 HttpOnly Cookie 保存会话。移动 App 和 API 常使用 Authorization Header 携带 Token。两者也可以组合。Session 容易服务端立即撤销，存储和多实例共享需要设计。自包含 Token 可以减少每次查会话，撤销与权限变更可能更复杂。

不要根据“现代”或“无状态”选。考虑客户端类型、撤销、过期、多设备、权限变化、跨域和基础设施。初学项目可以使用成熟框架或托管认证服务的推荐流程，不自己发明加密和 Token 格式。仍要正确配置回调 URL、Cookie 和权限。

## 登录流程逐步看

1. 浏览器 GET 登录页。
2. 用户提交邮箱和密码。
3. 服务器验证凭据和账号状态。
4. 成功后创建 Session 或签发 Token。
5. 浏览器保存 Cookie，或客户端安全保存 Token。
6. 后续请求携带凭据。
7. 服务器每次验证并检查权限。
8. 注销或过期后凭据失效。

任何一步都可能失败。密码正确但 Cookie 被浏览器阻止，登录请求显示成功，下一页仍返回 401。Token 过期后刷新流程失败，也会循环登录。

用户输入正确凭据，页面短暂进入主页，又回到登录页。Network 显示 POST `/login` 返回 200，响应有 Set-Cookie。随后 GET `/account` 没带 Cookie，返回 401。检查 Cookie 的 Domain、Path、Secure、SameSite 与浏览器提示。开发环境用 HTTP，却设置仅 HTTPS 发送，可能导致本地不带。

若请求带 Cookie，服务器仍 401，查会话存储是否保存、是否过期、签名密钥是否一致。多实例使用不同会话密钥会让请求偶发失败。不要在日志打印 Cookie 值。可以记录会话内部编号的安全摘要与过期原因。

## 浏览器缓存保存可复用响应

Cache 译为缓存。浏览器保存资源后，下次可以直接使用或询问服务器内容是否变化。MDN 缓存指南说明，合理复用能减少传输和延迟。Cache-Control 响应头可以设置最大新鲜时间、是否必须重新验证、是否允许共享缓存等。ETag 与 Last-Modified 能帮助条件请求。

客户端发送 If-None-Match 或 If-Modified-Since。资源未变化时，服务器可以返回 304，没有完整正文。浏览器继续使用本地副本。缓存规则是 HTTP 行为，不等于应用内存缓存、数据库缓存或 CDN 缓存。排错先确定哪一层。

资源仍在新鲜期时，浏览器可以不联系服务器，直接用缓存。重新验证则会发条件请求，由服务器判断是否变化。HTML 频繁改变，常使用短缓存或重新验证。带内容哈希的脚本与图片，文件名随内容变化，适合长期缓存。

若 `app.js` 内容改变，文件名却不变，又设置一年缓存，老用户可能长期运行旧代码。构建工具通常生成 `app.abc123.js` 一类名称解决。Service Worker 还能用程序逻辑拦截请求和管理缓存。PWA 更新问题需要同时检查浏览器 HTTP 缓存与 Service Worker 缓存。

## CDN 把内容放到靠近用户的位置

CDN 是 Content Delivery Network 的缩写，中文常译为内容分发网络。它在多个节点缓存静态资源，用户请求由较近或合适节点响应。CDN 第一次没有内容时，会向 Origin，也就是源站，请求并缓存。之后命中缓存可以减少源站负载和网络距离。

CDN 也可终止 TLS、应用防火墙规则、压缩和优化资源。具体能力由平台产品决定，不把所有 CDN 视为相同。源站更新后，CDN 旧缓存可能仍有效。可以使用版本化 URL、等待过期或按平台规则 Purge。清除整个站点缓存会增加源站压力，应控制范围。

一次配置错误让 `/api/profile` 响应被标记为公共缓存。CDN 可能把甲用户数据返回给乙用户，形成严重泄露。立即停止共享缓存或绕过 CDN，清除受影响键，修复响应头并调查访问记录。动态个性化内容通常使用 private 或 no-store 等合适策略。

缓存键还要包含影响响应的因素，例如 Host、路径、查询和必要 Headers。配置遗漏会把本应不同的响应合并。不要用客户端参数声明“不要缓存”作为唯一保护，源站和 CDN 政策才是控制点。

## Cookie 与 CDN 的相互影响

CDN 看到 Cookie 后，可能选择不缓存，或把特定 Cookie 纳入缓存键。全部 Cookie 都参与会降低命中率，完全忽略又可能串用户。静态资源最好使用与身份无关的 URL。用户 API 明确不进入公共缓存。页面若根据登录状态在源站生成，需要准确 Vary 与 Cache-Control。

Set-Cookie 响应被 CDN 缓存尤其危险。平台通常有保护默认值，仍要测试真实配置。用两个测试账户和未登录窗口验证，确认响应没有交叉。不要用真实用户数据做缓存试验。

`no-store` 表示不存储响应，适合高度敏感内容；`no-cache` 允许存储，但使用前需重新验证；名称容易误解；`private` 表示响应只适合私有缓存，不进入共享缓存；`public` 表示可以由共享缓存保存，仍受其他指令控制；`max-age` 控制浏览器缓存新鲜期，`s-maxage` 可用于共享缓存；具体组合要查 HTTP 规范和平台行为。

不要给所有资源统一 `no-store` 来消除调试问题，会失去性能收益。按内容变化与敏感性分类。

## 缓存导致发布后旧页面

维护者部署新前端，自己看到新版，一部分用户仍旧。Network 显示 HTML 是新版本，`app.js` 来自 disk cache，文件名没有变化。临时处理可以让用户重新加载当前站点，根本修复是构建产物使用内容哈希并设置合适 HTML 缓存。新 HTML 引用新脚本 URL，浏览器自然下载。

若 Service Worker 继续提供旧缓存，更新脚本需要正确激活和清理策略。强制立即接管可能中断正在使用的旧页面，要测试升级流程。CDN 也可能缓存旧 HTML。比较响应头、Age 与节点信息，再按平台范围清除。

短期访问 Token 减少泄露窗口。Refresh Token 可以换取新访问 Token，通常更长期和敏感。刷新流程要防止重复使用、盗取和并发竞争。服务端可以轮换 Refresh Token，发现旧值再次使用时撤销会话。

客户端收到 401 时不能无限刷新循环。刷新失败应清理本地认证状态并引导重新登录。多个请求同时过期时，协调一次刷新。移动设备使用系统安全存储。浏览器避免把高价值长期 Token 放在容易被脚本读取的位置。具体方案按威胁模型选择。

## CSRF 为什么与 Cookie 有关

CSRF 是 Cross-Site Request Forgery 的缩写，中文常译为跨站请求伪造。用户已登录某网站时，恶意页面可能诱导浏览器向该网站发请求，并自动带上 Cookie。SameSite Cookie 能阻止一部分跨站发送。服务端还可使用 CSRF Token、检查 Origin 与要求自定义头等防护。具体组合按框架官方建议。

GET 不应执行转账和删除。高风险操作再次验证、显示目标和防重复。CORS 不能独自阻止浏览器表单发送某些跨站请求。攻击测试只在自己的系统和测试账号进行。不要用真实用户会话演示。

XSS 是 Cross-Site Scripting 的缩写，中文常译为跨站脚本。应用把不可信内容当 HTML 或脚本执行，攻击者就能在站点上下文操作页面。HttpOnly Cookie 不能被普通脚本读取，攻击脚本仍可能代表用户发请求。输入输出编码、可信模板、内容安全策略和依赖更新共同防护。

把 Token 放 Local Storage 后，XSS 脚本更容易读取并外传。存储选择要结合 XSS 与 CSRF 风险，不存在一个只靠位置就安全的答案。使用框架默认转义，不随意插入原始 HTML。富文本需要成熟清理库和允许列表。

## Session Fixation 与登录后换标识

Session Fixation 译为会话固定。攻击者让受害者使用一个已知会话标识，受害者登录后若服务器仍沿用，攻击者可能共享登录状态。登录成功、权限提升和密码修改后，服务器应更新会话标识。旧标识失效。

会话标识必须由安全随机源生成，不能用连续编号。Cookie 作用域限制到需要的域名和路径。框架通常提供安全会话管理，使用其推荐配置。不要自己用用户 ID 作为 Session ID。

| 内容 | 常见方向 | 主要原因 |
| --- | --- | --- |
| 带哈希静态资源 | 长期公共缓存 | 内容变化会换 URL |
| HTML 入口 | 短缓存或重新验证 | 要尽快引用新资源 |
| 公开文章 API | 可共享缓存 | 内容对所有用户相同 |
| 账户与订单 | private 或 no-store | 包含个性化敏感数据 |
| 临时签名下载 | 谨慎或不共享 | URL 在有效期内可访问 |

表格是设计起点。支付、医疗和隐私内容要按更严格要求。平台默认值需要实测。缓存命中率高不代表策略正确。串用户数据的“高命中”是事故。先保证隔离与新鲜度，再优化性能。

## 隐私窗口能排除什么

隐私窗口通常使用独立 Cookie 与临时站点数据，能帮助比较登录、缓存与扩展影响。关闭后数据清理行为由浏览器实现。它不会隐藏网络活动，也不会绕过服务器日志、公司代理和网站账号。下载文件仍留在设备。

隐私窗口正常、常用窗口失败时，检查扩展、Cookie、Service Worker 和本地存储。不要由此断定服务器永远正常。用测试账号排查，不在共享电脑登录生产管理员。

API Key 常标识调用项目或服务账号，用户 Token 表示某个用户会话。两者权限和轮换不同。浏览器可见的 Publishable Key 由平台设计为公开标识，服务端 Secret Key 具有高权限。名称以供应商文档为准。

把服务端 Key 当用户 Token，会让所有客户端共享高权限。把用户 Token 放服务器长期配置，也会让个人会话难以撤销。日志与错误监控对两者都默认遮盖。泄露后按所属平台轮换并审计。

## 设备列表与会话管理

用户安全页可以显示活跃设备、最近时间与大致位置，让用户撤销陌生会话。位置由 IP 推测，只作线索；每次登录创建独立会话，单设备注销只撤销该会话；修改密码或发现攻击时提供全部注销；设备名称来自客户端信息，可能不准确；不要用它作唯一身份；撤销后服务器拒绝旧凭据。

管理员代用户撤销要有审计与支持流程，不能查看用户明文 Token。

CDN 前面的公开域名受防护，攻击者若知道源站 IP，可能绕过 CDN 直接访问。源站限制只接受 CDN 网络、使用认证回源或私有连接。来源 IP 列表会更新，自动同步要按平台官方方式。错误规则可能阻断全部流量，变更前准备回滚。

源站证书仍要验证，CDN 到源站连接使用 HTTPS。Flexible 一类只保护用户到 CDN 的模式会留下中间明文，生产应查平台推荐。健康检查与部署需要受控入口，不能为方便把管理端口公开。

## 多层缓存的检查顺序

页面旧内容可能来自 Service Worker、浏览器 HTTP 缓存、企业代理、CDN、应用缓存或数据库读副本。先用 Network 看当前响应头与来源。比较带版本查询或新文件名。再查 CDN 缓存状态与源站响应。

应用接口仍旧时，查服务端缓存和数据库复制延迟。不要一次清空所有层，既影响性能，也失去定位证据。每层清理后重新验证并记录。根本修复是正确失效与版本化。

登录会话和购物车可能属于提供服务所必需 Cookie，分析与广告通常有不同同意要求。具体法律义务按用户地区与业务咨询。同意界面应能拒绝非必要类别，并记录选择。拒绝后第三方脚本不能先加载再假装撤回。

隐私政策列出名称、用途、期限和第三方。实际 Cookie 与文档定期比较。开发调试 Cookie 不能进入生产。过时域名 Cookie 清理并缩小 Domain 与 Path。

## 缓存清除与版本发布的选择

紧急错误内容已经缓存，可以 Purge 指定 URL。正常发布优先版本化文件名，避免每次清全站。HTML 引用新哈希资源，旧标签页仍能用旧文件。不要立即删除旧资产，给在途客户端兼容时间。API 数据更新使用事件或明确失效 Key。通配 Purge 可能影响所有租户和源站负载。

记录清除者、范围、时间与结果。平台显示完成后从外部网络验证。

手机丢失后，用户在安全页撤销该设备 Session。服务端拒绝其 Refresh Token，即使设备仍保存。访问 Token 尚在短有效期内可能继续使用。高风险操作实时检查账户状态或要求重新认证。

远程擦除由操作系统账户提供，不能替代服务端撤销。用户修改密码是否全部注销按策略。审计查看丢失时间后的访问，向用户显示关键活动。不要在通知中发送完整位置或 Token。

## 缓存与隐私的两个账户测试

甲登录查看资料，记录响应和缓存头，随后注销。乙在同一浏览器新会话登录，不能看到甲资料。再用另一台设备或未登录窗口请求相同 URL。共享 CDN 不应返回甲内容。检查 Age、Cache-Control 与 Vary。

测试数据使用专门账号。发现串数据立即停止缓存、清除受影响内容并启动事件响应。修复后重复不同地区和设备测试，查询访问日志评估影响。

## 本章验收清单

能解释 Cookie、Session 和 Token 各自存什么。知道 HttpOnly、Secure 与 SameSite 只解决部分风险。能识别浏览器缓存、Service Worker、CDN 与应用缓存。不会让账户响应进入公共缓存。

注销包含服务端撤销，Token 泄露先轮换。调试材料不包含 Cookie 与签名 URL。

Token 和 Cookie 使用时间。客户端或服务器时钟错误，可能刚登录就过期，证书也可能显示无效。服务器使用可靠时间同步。验证 Token 可允许很小合理偏差，不能无限放宽。客户端显示时间不作为最终授权。

日志统一 UTC 并保留时区信息。比较事件时先转换，不手工改生产时间掩盖问题。大量用户同时过期，检查签名密钥、服务器时钟和全局配置，不让每人清缓存。

## 过期 Session 也要清理

服务端 Session 到期后拒绝访问，存储中的旧记录还要定期清理。清理任务按索引分批，避免锁表。活跃会话延长策略会影响安全。滑动过期每次使用续期，绝对过期限制最长时长。清理失败会增加存储，通常不应让已过期会话重新有效。监控数量和最老记录。

安全事件要求立即撤销时，不等待定期清理。

客户端删除 Cookie 或 Token，服务器还应使相应会话或刷新凭据失效。只删除客户端值，泄露副本可能继续使用。单设备注销与所有设备注销是不同功能。用户修改密码后是否撤销全部会话，要按产品安全策略决定。

CDN 和浏览器缓存的公开资源无需因注销全部清除。包含用户数据的缓存必须按隐私设计处理。注销后使用浏览器后退键可能看到历史页面，敏感页面应配置不存储并在重新请求时验证身份。

## 一个跨域 Cookie 例子

前端在 `app.example.com`，API 在 `api.example.com`。浏览器请求 API 时，Cookie Domain、SameSite、CORS 和 Fetch credentials 设置共同影响。服务端允许正确 Origin 并允许凭据，客户端请求也声明带凭据。Cookie 的 Secure、Domain 与 Path 还要匹配。

任何一项错误都可能表现为登录成功后 API 401。不要把 CORS 设置为允许所有来源并同时开放凭据。浏览器会限制，安全上也不合理。用 Network 查看请求是否带 Cookie、响应是否有 CORS 头与状态。隐藏 Cookie 值，只记录属性。

网站替换 `/images/logo.png`，CDN 仍缓存旧文件。维护者清浏览器无效，因为 CDN 响应本身就是旧内容。比较源站直连与公开 CDN 响应哈希，可以定位。按平台清除单个 URL，或发布新文件名 `logo-v2.png` 并更新页面。内容哈希文件名更可靠，例如 `logo.a1b2.svg`。内容变化生成新地址，旧缓存不会覆盖新文件。

清除后从不同地区节点验证。CDN 控制台显示 Purge 成功，不代表每个用户立即完成业务验收。

## 最小缓存观察练习

打开 DevTools Network，访问一个公开静态资源。查看 Cache-Control、ETag、Age 和 Size 或 Transferred 列。刷新一次，观察是否显示 memory cache、disk cache 或 304。勾选 Disable cache 时，通常只在 DevTools 打开期间生效，具体以当前 Chrome 为准。

不要在生产网站随意清 CDN。这个练习只观察浏览器。第十九章会给出完整界面路径。

AI 可以检查 Set-Cookie、Cache-Control 和 CDN 配置，解释登录循环与旧资源，并设计两个账户的隔离测试。不要提供 Cookie 和 Token 明文。AI 建议开放 CORS、关闭 Secure 或延长 Token 时，要用安全资料复核。

认证策略、会话撤销、用户数据缓存和 CDN Purge 需要亲自确认。生产秘密与真实用户响应不能进入公开调试材料。下一章会回到页面代码，说明 HTML、CSS、JavaScript、前端与后端如何分工。
