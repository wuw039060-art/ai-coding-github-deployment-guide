# Flutter 项目、依赖、Debug、Profile 和 Release

Flutter 让一套 Dart 代码可以构建多个平台的客户端。它没有把 Android 和 iOS 变成同一个系统。项目中仍有 Android 的 Gradle 配置、iOS 的 Xcode 工程、各平台权限和签名文件。

非专业开发者不需要先学完整 Flutter 框架，仍要认得项目入口、依赖清单、平台目录和三种构建模式。否则“本地能跑”很容易被误当成“可以发布”。

## 先确认拿到的是完整项目

Flutter 项目根目录通常能看到 `pubspec.yaml`、`lib`、`test`、`android` 和 `ios`。不同目标还可能有 `web`、`windows`、`macos` 与 `linux`。`lib` 保存主要 Dart 代码，常见入口是 `lib/main.dart`。`pubspec.yaml` 声明项目名称、版本、Dart 环境、依赖、资源和字体。`pubspec.lock` 记录依赖解析出的具体版本。平台目录包含原生工程和构建设置。

只有一个 APK、AAB 或 IPA 时，你拿到的是构建产物，不能据此可靠恢复全部源代码。只有 `lib` 而没有 `pubspec.yaml` 和平台目录，也不是可直接发布的完整项目。先在项目根目录运行只读诊断。

```
flutter --version
flutter doctor -v
flutter pub get
flutter analyze
```

运行位置

> Windows PowerShell 或 macOS Terminal。后两条在含有 `pubspec.yaml` 的项目根目录运行。

四条命令分别显示 Flutter 版本、平台工具状态、解析依赖和静态分析。预期能看到版本信息，`pub get` 正常结束，`analyze` 没有阻止构建的错误。若系统提示找不到 `flutter`，先检查 Flutter SDK 是否安装并进入 PATH。若 `doctor` 报 Android toolchain 或 Xcode 缺失，按要发布的平台处理。Windows 不能安装和运行 Xcode，因此可以准备 Android，不能在这台机器完成 iOS Archive。

## pubspec.yaml 是项目总清单

下面是一段简化示例。

```
name: pocket_list
description: A small list app
version: 1.2.0+17

environment:
  sdk: ^3.8.0

dependencies:
  flutter:
    sdk: flutter
  http: ^1.4.0

flutter:
  assets:
    - assets/images/
```

`name` 是 Dart 包名，不等于商店展示名称。`version` 中的 `1.2.0` 是给用户看的版本，`17` 是构建编号。Android 和 iOS 会把它们映射到各自版本字段，但平台仍有自己的规则。`environment` 约束 Dart SDK；`dependencies` 列出运行所需包；`assets` 把图片等资源纳入构建。YAML 对缩进敏感，Tab 和空格混用可能导致解析失败。

运行 `flutter pub get` 成功，只证明依赖能解析与下载。它不证明插件拥有正确权限，也不证明应用功能可以运行。

## 依赖包也会进入你的产品

加入一个插件，可能同时加入 Dart 代码、Android 原生库、iOS Framework、权限声明和第三方网络请求。依赖会影响包体、最低系统版本、构建工具和隐私披露。选择依赖时先看维护者、最近发布、支持平台、问题记录、许可证和迁移说明。一个只有漂亮示例却多年未适配当前 Flutter 的插件，可能让升级被旧 Gradle 或旧 iOS API 卡住。

`pubspec.lock` 对应用项目通常应进入版本库。团队在相同提交上能解析到相同依赖版本。仅提交宽泛版本范围，每次构建可能得到不同组合。升级依赖不要一次全选。先保存可工作的提交和构建证据，再查看过期依赖。

```
flutter pub outdated
```

这条命令在项目根目录运行，只生成依赖版本报告。它不会自动修改项目。先理解直接依赖与间接依赖，再分批升级、分析、测试和构建。高风险操作

> 不要为了消除依赖冲突，随意删除锁文件后提交一个从未测试的新依赖集合。锁文件可以重新生成，线上行为未必可逆。

## 平台目录不是可随意重建的缓存

有人遇到原生构建问题，会删除 `android` 或 `ios` 再运行项目生成命令。这样可能丢失包名、签名配置、权限、URL Scheme、推送能力和第三方 SDK 设置。平台目录属于源代码。修改前查看 Git 差异。若确实需要用新模板比较，应在临时分支或新项目中生成，再逐项迁移，不覆盖原工程。

`build`、`.dart_tool` 等目录通常是构建产物，可以在确认没有唯一文件后重新生成。签名密钥、导出选项、服务配置和手工加入的原生文件不能凭目录名字判断为缓存。

Flutter 工具提供 Debug、Profile 和 Release。它们使用同一项目，却改变编译优化、调试能力和运行目的。

![Flutter 三种构建模式](../assets/diagrams/flutter-build-modes.png)

*Flutter 三种构建模式*

*图 52-1　Debug 用来开发，Profile 用来在真机测性能，Release 用来生成最终分发构建。等价说明见本章“三种模式回答三个问题”。* Debug 模式用于日常开发。`flutter run` 默认以 Debug 启动，支持断点、断言和热重载。热重载把代码变化注入正在运行的程序，保留部分状态，适合快速调界面。

热重载成功不代表冷启动成功。新增原生插件、修改初始化、权限或资源后，可能需要完整停止并重新运行。发布前还要测试 App 从被系统杀死状态启动。Profile 模式用于性能分析。它保留足够的跟踪能力，同时更接近 Release 的优化。官方文档要求在真实设备上评估移动端性能，因为模拟器不能代表真实设备。

Release 模式用于分发，关闭调试服务与断言并进行优化。Release 不能连接常规调试器，问题要依靠日志、崩溃报告、符号文件和可复现步骤。一句话结论

> Debug 通过说明开发入口可用，Release 通过才说明最终构建值得继续送去测试。

## 在真机上分别运行

先查看可用设备。

```
flutter devices
```

预期看到设备名称、平台和设备 ID。Android 真机需要开启开发者选项与 USB 调试，并在手机上确认电脑指纹。iPhone 开发依赖 macOS、Xcode、Apple 账号和设备信任。Debug 运行使用下面的命令。

```
flutter run
```

启动后应看到应用首页，终端保留运行日志。修改一段可见文字并热重载，界面应更新。若设备列表为空，先处理连接，不要修改业务代码。Profile 运行使用下面的命令。

```
flutter run --profile
```

在中低端目标真机上滚动列表、打开图片密集页面和执行核心流程。观察掉帧、CPU、内存和网络。Debug 中的卡顿不能直接当作发布性能，Profile 中持续发生的卡顿才值得定位。Android Release 真机试运行可以使用下面的命令。

```
flutter run --release
```

它仍是开发连接下的 Release 运行，不等于测试商店实际分发的 AAB。最终还要通过 Google Play 测试轨道安装。

## DevTools 是一组观察窗口

Flutter DevTools 包含 Widget Inspector、Performance、CPU Profiler、Memory、Network、Debugger 和 Logging 等工具。当前功能随 Flutter SDK 一起分发，升级 Flutter 也可能改变 DevTools 界面。

Widget Inspector 帮你把屏幕元素对应到 Widget tree。按钮位置错乱时，先选择该元素，查看约束与父子关系，不必从整个项目猜是哪一行。Performance 时间线显示帧的构建与绘制。滚动时出现明显卡顿，录制一小段操作，找超过帧预算的区间，再看是 UI 构建、光栅化还是其他任务。

Network 页面帮助观察 HTTP 请求。确认请求是否真正发出、耗时、状态码和响应。它不能显示所有原生 SDK 流量，也不能代替服务器日志。Memory 页面显示内存随操作变化。页面关闭后内存没有立刻下降，不一定是泄漏。需要重复相同步骤，观察对象是否持续累积，并结合快照确认。

Flutter 官方 DevTools 教程提供从 IDE 或命令行打开工具、检查 Widget tree 和布局问题的跟做路径。

## 一个列表卡顿的排查例子

一个相册 App 在 Debug 中滚动很慢。直接修改动画没有意义，因为 Debug 本身未针对性能优化。开发者改用 Profile 在真实旧手机运行，录制相同的十秒滚动。时间线显示每次新图片出现时，主线程都进行大尺寸图片解码。Network 还显示原图没有缩略版本。

修正方案可以在服务端生成合适尺寸的缩略图，客户端按显示尺寸请求，并限制同时加载数量。再次录制相同动作，比较慢帧和内存峰值。这个证据链包含设备型号、App build、操作步骤、录制区间、修改和复测。只说“优化后感觉流畅”无法判断是否换了设备或缓存已经预热。

开发、测试和生产常使用不同 API 地址。Flutter 可以通过构建参数或不同入口读取配置，但不要把生产秘密放入客户端环境变量。客户端中的 API 基础地址通常可以公开。它告诉 App 去哪里请求，并不能赋予管理员权限。真正秘密必须留在后端。

需要多套环境时，先保证名称清楚。开发包使用测试后端与测试图标，生产包只连接生产后端。测试人员应能在关于页面看到环境、版本和构建号，避免把测试结果记到错误系统。切换环境后执行一次完整冷启动。只修改常量并热重载，旧服务实例可能继续使用原地址。

## Release 构建会暴露新的问题

Debug 中的断言在 Release 关闭。依赖调试服务的代码会失效。代码压缩、资源优化、原生权限和网络安全策略也可能改变行为。Android 的 Release 签名与 Debug 签名不同。使用地图、登录或 API 限制证书指纹的服务，可能在 Debug 正常而 Release 失败。

iOS 的分发签名、能力和 Provisioning Profile 也与开发运行不同。推送和关联域等能力要在分发构建中验证。所以发布检查应使用最终签名产物，从目标测试渠道安装。不能只用 USB 运行的 Debug 包代替。

Flutter 构建输出可能同时包含 Dart、Gradle、Kotlin、Java、CocoaPods、Swift 和 Xcode 信息。最后一行“build failed”只是总结。先从前往后找第一条明确错误，记录命令、Flutter 版本、操作系统和完整上下文。依赖下载失败先查网络与仓库。Dart 编译错误回到文件和行号。Gradle 或 Xcode 签名错误再查平台工程。

不要一次删除所有缓存、升级 Flutter、升级 Gradle、改 JDK 并换插件。即使最后成功，也无法知道根因，还可能同时引入版本变化。一个安全顺序如下。

1. 保存当前提交和原始错误。
2. 运行 `flutter doctor -v` 记录工具状态。
3. 在相同提交重试一次，判断是否偶发网络错误。
4. 根据第一条有效错误只改一个层次。
5. 重新执行同一命令并保存结果。

## 发布构建的最小证据包

每次候选版本保存 Git 提交、Flutter 与 Dart 版本、依赖锁文件、构建命令、包名、版本号、构建号和产物校验值。Android 保存 AAB、上传证书指纹和构建日志。iOS 保存 Xcode Archive 和用于符号化的调试符号。Apple 的崩溃诊断文档也要求保留与发布版本匹配的 archive 和符号信息。

测试记录写设备、操作系统、安装来源和结果。发布包从测试轨道全新安装、从旧版本升级、退出后冷启动、拒绝权限、弱网与后端错误都要覆盖。AI 可以阅读 `pubspec.yaml`、锁文件和构建日志，帮助解释依赖与第一条错误。它可以提出修改，但你必须检查 Diff、重新构建并在真实设备验证。不要把签名文件或带令牌的日志上传给未知服务。

Flutter、Dart、Gradle 和 CocoaPods 会生成大量中间文件。生成文件可以重新出现，手写平台配置和签名资产却可能只有一份。判断一个文件能否删除，先查看它由哪条命令生成、是否进入 Git、项目说明是否记录恢复办法。不要仅凭目录以点开头或体积很大决定。

`build` 通常保存构建产物，`.dart_tool` 保存工具状态，iOS Pods 可由依赖配置重建。`android/app/src`、`ios/Runner` 和自定义插件代码属于项目源文件。清理前保存 Git 状态。执行官方清理命令后，再运行相同构建。若必须靠未提交文件才能恢复，先把项目交接补完整。

## Flutter clean 解决什么

`flutter clean` 会删除部分构建产物，适合怀疑旧缓存与当前配置不一致时使用。

```
flutter clean
flutter pub get
flutter analyze
```

运行位置

> Flutter 项目根目录。第一条会删除可重建输出，执行前确认没有把唯一人工文件放在 build 目录。

清理会让下一次构建更慢，也会移除部分诊断现场。依赖冲突、代码错误和签名配置错误不会因为缓存消失自动修复。把原始错误保存后再清理。若每次构建都必须 clean，说明项目存在增量构建或生成流程问题，应继续定位。

## 原生插件跨过平台边界

相机、蓝牙、通知、地图和安全存储插件会调用 Android 或 iOS 原生 API。Dart 层接口相同，平台安装与权限要求可能不同。加入插件后阅读它对 AndroidManifest、Info.plist、Gradle、CocoaPods、最低系统版本和 capability 的说明。只复制 Dart 示例，常会在点击功能时才崩溃。

检查插件的支持矩阵。有的包支持 Android 与 iOS，不支持 Web 或桌面。代码要在不支持平台隐藏入口或提供替代。插件升级可能包含原生破坏性变化。分别构建 Android 和 iOS，不能因 Android 通过就认为 iOS 也通过。

一个可工作的发布环境包含 Flutter、Dart、JDK、Android SDK、Gradle、Android Gradle Plugin、Xcode、CocoaPods 和平台 SDK。只记录 Flutter 版本不够。`flutter doctor -v` 可以提供很多环境信息，构建日志还能记录 Gradle 和 Xcode 版本。

升级工具链时一次处理一个受控范围。Flutter 升级可能带来模板、Dart 语言和插件变化。Xcode 升级可能提高 iOS SDK 或签名要求。CI 与开发电脑尽量使用相同大版本。出现“我电脑能构建”时，先比较版本和锁文件，再比较代码。

## 多环境构建避免连错后端

开发、预发布和生产应使用不同后端与数据。Flutter flavors 可以把环境、应用名称、图标和平台配置区分，简单项目也可以用明确构建参数。无论采用哪种方式，生产构建默认连接生产后端，测试构建显示醒目标识。关于页面展示环境和 build。

第三方服务配置也要匹配。例如 Android 的服务 JSON、iOS 的 plist、登录证书和 URL Scheme 不能交叉。构建脚本对未知环境值直接失败。默默回退到生产会让测试数据进入真实系统，默默回退到测试会让正式用户看不到账号。

热重载保留当前 Dart 状态，并尝试重建 Widget。修改构造函数、全局初始化、原生插件或资源后，旧状态可能遮住问题。遇到行为不一致时先 hot restart，再完全停止 App 冷启动。涉及安装配置时，卸载测试包重新安装。

开发者在已经登录的页面热重载，可能永远没走首次启动和数据库迁移。发布验收从系统杀死状态和干净安装开始。每次缺陷记录使用了热重载、重启还是全新安装。复现条件不同会给出不同结果。

## 自动化测试分成不同层次

单元测试验证独立函数和业务规则。Widget test 在测试环境构建 Widget 并模拟交互。集成测试在设备或模拟器上走多个页面和平台能力。登录、支付、推送和相机很难只靠单元测试证明。它们需要测试后端、真机权限和最终签名包。

最低发布门可以包括静态分析、单元测试、Widget 测试、Android Release 构建和真机冒烟测试。iOS 在 Mac CI 或受控 Mac 上增加 Archive。测试通过记录命令、提交和环境。界面显示一个绿色图标却找不到对应 build，不构成发布证据。

Flutter 资源要在 `pubspec.yaml` 声明，路径大小写要与文件一致。Windows 文件系统常忽略大小写，Linux 或打包环境可能区分。YAML 缩进错误可能让资源没有进入 AssetManifest。Debug 已缓存旧资源时，问题又可能被暂时遮住。

新增图片后完整重启并构建 Release。在最终包中打开每个关键页面。文件名使用稳定英文、数字和短横线，避免不可见空格。删除资源前搜索代码、配置和平台图标引用。未使用资源会增大包，误删启动资源会阻止构建或显示空白。

## 字体会影响包体与版权

Flutter 可以嵌入自定义字体。每个字重可能是独立文件，中文字体完整字库很大，会显著增加安装包。优先使用系统字体或有明确应用嵌入许可的字体。不要从网页缓存复制一个字体进项目。需要品牌字体时只加入实际字重，测试中文、数字、Emoji 和缺字回退。字体子集会减小体积，却要确保覆盖所有动态文本。

记录字体来源、版本和许可证。商店审核通过不代表字体版权没有问题。

Flutter 提供应用体积分析能力。先生成分析报告，查看 Dart 代码、原生库、资源和字体各占多少。大图片可以改用合适分辨率和压缩格式。重复资源可以合并。只在一个平台使用的原生库应核对是否被不必要打入其他构建。

混淆主要提高逆向阅读成本，不是通用体积工具，也不能保护硬编码秘密。代码压缩后保留符号文件。优化后比较安装、启动、图片质量和崩溃符号化。体积变小却导致低端设备解码更慢，不一定是改进。

## 可访问性也要在 Release 验证

文字放大后，按钮和关键金额不能被裁掉。屏幕阅读器应读出有意义标签，不能只说“按钮一”。颜色不是唯一状态提示。错误同时提供文字或图标，深色模式保持对比度。动态内容更新要让辅助技术得到提示，又不能每秒重复打断用户。自定义手势提供可发现替代。

模拟器适合初查，最终用真实设备、系统字体大小和 TalkBack 或 VoiceOver 测试。可访问性问题属于产品缺陷，不只是商店素材问题。

候选构建来自一个固定提交和干净环境。版本、后端环境、签名和构建参数经过记录。候选包上传测试轨道后，不再在本地覆盖同一版本自称还是那个包。任何代码或配置变化都提高 build number，重新走测试。

冒烟测试覆盖冷启动、登录、核心读写、权限拒绝、后台恢复和退出登录。应用特有的高风险功能另加用例。测试通过的人与构建者可以不同。第二个人从分发渠道安装，能发现只存在于构建电脑的隐含文件。

## Git 差异是构建前的最后一面镜子

构建候选包以前查看 `git status` 和 Diff。未提交的本地修改会进入构建，却无法从发布标签重现。重点检查 `pubspec.yaml`、锁文件、Android 与 iOS 配置、权限、图标和环境文件。自动格式化带来的大量差异要与功能修改分开。

构建脚本生成版本文件时，确认它是否应进入 Git。每次构建变化的时间戳不应污染源提交，版本身份仍要可追溯。发布完成后，从记录的提交在另一目录重新构建一次。校验值可能因签名和工具生成内容不同而变化，功能配置与版本必须一致。

## 静态分析警告不要一键忽略

`flutter analyze` 会根据项目的 analysis options 检查类型、空安全和代码规范。错误通常阻止可靠构建，警告也可能指向实际缺陷。新增一条全局 ignore 能让输出变绿，却可能隐藏整个项目的同类问题。若确有例外，在最小范围写注释说明原因。

更新 Flutter 后出现新 lint，先读规则和受影响代码。把规则全部关闭会失去升级带来的检查能力。分析无法发现运行权限、后端契约和设备性能问题。它是发布门的一项，不是整套验收。

Flutter 布局由父组件向子组件传递 constraints，也就是尺寸约束，子组件选择尺寸后再由父组件定位。看到黄色黑色溢出条时，先在 Widget Inspector 选择问题元素，查看父级给了什么宽高。随意套多层 `Expanded` 或固定高度可能只在当前屏幕消失。

测试小屏、横屏、文字放大、键盘弹出和长中文。网络返回的真实标题往往比示例短词长。修复后在 Profile 或 Release 再看，复杂布局和大图片可能同时带来性能问题。

## 本地化资源也参与构建

多语言项目会从 ARB 等资源生成 Dart 本地化代码。新增 key 后要让所有目标语言有明确值或受控回退。翻译文本中的占位符名称与类型保持一致。中文没有复数变化，不代表英文和其他语言可以省略规则。

构建时生成文件失败，先检查资源语法与重复 key。不要手工修改下一次会被覆盖的生成 Dart 文件。切换系统语言、地区和 24 小时制测试。日期、数字和货币不能只替换文字。

企业代理、抓包证书和本地测试 HTTPS 可能只在开发设备受信。Release 用户设备不会继承开发电脑设置。不要为了让测试接口可访问，在生产配置永久允许明文 HTTP 或忽略证书错误。使用正确测试域名和有效证书。

抓包用于排错时保护令牌与用户数据，结束后移除测试证书和代理。记录测试环境，避免把代理故障误判成应用网络错误。正式候选在一台没有开发证书和代理的干净设备验证。

## 发布模式下日志要经过筛选

Debug 中大量 `print` 方便开发，Release 中可能泄露路径、令牌和个人数据，也会制造噪声。建立日志级别和脱敏规则。生产保留版本、关联编号、状态类别和必要错误，不输出完整请求正文。崩溃报告中附加的自定义信息同样受隐私约束。用户邮箱可以换成内部随机账号标识，真实令牌完全不记录。

测试一个故意失败的请求，确认 Release 日志足以定位，又没有秘密。

本地 `flutter run --release` 使用开发连接和本机选择的配置。商店构建还经过上传、平台处理、应用签名和设备拆分。Android 要从 Play 测试轨道安装，iOS 要从 TestFlight 安装。第三方登录、推送、深层链接和购买在最终签名下重新验证。

从商店渠道安装后，断开开发电脑。重启设备，测试冷启动和后台通知，避免调试连接改变生命周期。把商店页面显示的版本与应用关于页比较。两者不一致时停止扩大测试。
