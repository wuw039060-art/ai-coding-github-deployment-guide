# Linux 文件、目录、用户、root、sudo 和权限

登录服务器以后，最先要学会看路。Linux 把系统组织成一棵从 `/` 开始的目录树。应用代码、配置文件、日志、用户文件和临时文件都在这棵树上。你不必立刻背下所有目录，但要知道自己在哪、要改什么、改完怎样退回。

## 路径和目录

绝对路径从 `/` 开始，比如 `/var/www/app`。相对路径从当前目录开始，比如 `logs/app.log`。`pwd` 能看当前位置，`ls` 能看目录内容，`cd` 能切换目录。新手最常见的错误，是在错误目录里执行删除、复制和构建命令。

练习时先创建一个无风险目录。进入自己的家目录，创建 `server-lab`，在里面练 `mkdir`、`touch`、`cp`、`mv` 和 `rm`。确认每个命令改了什么。不要在 `/etc`、`/var/lib`、数据库目录和生产项目目录里练手。

隐藏文件只是在文件名前加点，比如 `.env`。它们不会自动加密，也不会自动保密。`.env` 常放环境变量和秘密，应该靠权限、备份策略和密钥管理保护。不要因为 `ls` 默认看不见，就以为它安全。

## root 和 sudo

`root` 可以改几乎所有东西。它能安装软件、删系统目录、改服务配置，也能一条命令毁掉整台机器。普通用户权限较小，遇到需要管理操作时，用 `sudo` 临时提权。这样命令历史和系统日志更容易追踪。

`sudo` 不是免责按钮。运行前先读命令，确认目标路径和影响范围。尤其警惕递归操作、覆盖写入、批量改权限和从网络下载后直接执行的脚本。命令里出现生产目录、系统目录或通配符时，停一下再看。

服务用户也很常见。Web 服务、数据库和队列常用独立用户运行。这个用户可能没有登录 shell，也不能直接登录。这样设计是为了限制服务被攻破后的影响。不要因为服务用户登录不了，就把它改成可登录用户。

## 权限怎样读

`ls -l` 会显示权限、所有者和所属组。权限常见三类。读、写、执行。文件的执行权限表示能否当程序运行。目录的执行权限表示能否进入或穿过这个目录。目录没有执行权限时，即使能看到名字，也可能打不开里面的文件。

目录的读权限用于列出名字，写权限配合执行权限用于创建、删除或重命名目录项。因此，一个只读文件仍可能被有权修改其所在目录的人删除或替换；sticky bit、ACL 和其他安全机制还可能施加额外限制。保护代码和秘密时，既要看文件本身，也要看上层目录。

`chmod` 修改权限，`chown` 修改所有者。给脚本增加执行权限，可以用 `chmod +x script.sh`。把项目目录交给应用用户，要用 `chown` 指向正确用户和组。不要为了省事把目录改成 `777`。它会让太多人能写入，后续事故很难查。

递归参数要格外小心。`-R` 会作用到目录里的所有内容。批量改权限前先用 `ls` 或 `find` 看目标范围。更稳的做法是先在练习目录试一遍，再对真实目录执行。改完记录旧权限、新权限、原因和回滚办法。

## 配置和秘密

配置文件和秘密要分开。端口、运行模式、日志级别属于普通配置。数据库密码、API Key、私钥和 Cookie Secret 属于秘密。普通配置可以进入仓库，秘密不能进入仓库。服务器上的秘密文件只给需要的用户和服务读取。

权限问题常出现在上传和日志目录。应用用户缺少所需的写入和目录搜索权限，上传就可能失败。日志目录归 root 所有，并不自动代表服务不能写；还要看组权限、ACL，以及写入的是已有文件还是新建文件。修复时不要直接把整个项目目录放宽。先找出服务实际运行用户，再只给必要路径授权。

文件被删除后，磁盘不一定立刻释放。若某个进程仍打开这个文件，空间会等进程关闭后才释放。日志轮转和大文件清理时会遇到这种情况。看到磁盘仍满，检查是否有进程还占着已删除文件。

## 删除和回滚

Linux 没有统一回收站。`rm` 删除后通常不能轻松恢复。生产服务器上删除文件前，先确认路径，必要时先移动到临时备份目录。删除数据库文件、上传目录、证书和配置文件前，要确认备份可用。

符号链接也要看清。它像一个指向别处的入口。删除链接和删除目标文件不是一回事，但覆盖链接可能影响真实目标。部署目录常用符号链接指向当前版本。操作前用 `ls -l` 看它指向哪里。

文件名可以包含空格和特殊字符。脚本里处理路径时要加引号。手工命令也一样。很多看似奇怪的报错，原因只是路径被 shell 拆成了几段。AI 生成命令时，也要检查路径是否被正确引用。

## umask 和新文件权限

新建文件和目录的默认权限通常由程序请求的权限与 umask 共同决定。umask 会去掉权限，不会凭空增加执行权限。父目录存在默认 ACL 时，还要考虑继承规则。你看到同一个命令在两台服务器上创建出不同权限，不一定是命令错了。先看当前用户、所属组、umask 和默认 ACL。团队服务器最好约定项目目录的所有者、组和默认权限，不要靠每个人临时 chmod。

Web 项目常用一个部署用户写代码目录，再用服务用户读取和运行。上传目录、缓存目录和日志目录可能需要服务用户写入。代码目录本身不一定要给服务用户写。把所有目录都交给应用写，会扩大被攻击后的影响。

共享目录可以用组权限处理。把相关用户加入同一个组，让目录归这个组所有，并设置合适的组写入与执行权限。新文件是否继续使用这个组，还要看目录的 setgid 等继承设置；新文件是否允许组写入，还受 umask 或默认 ACL 影响。多人上传和发布前，应分别用实际账号创建文件并验证。改组后，用户通常需要建立新登录会话，已有服务进程也要重新取得组身份。

## ACL 和看不见的权限

有些系统会使用 ACL，为指定用户或组设置访问权限。在常见 Linux 环境里，`ls -l` 权限位后面的加号提示存在扩展访问控制信息，可用 `getfacl` 查看。还要看 ACL 的 mask 和实际有效权限，不能只看到某项写着 `rwx` 就认为全部生效。只看 rwx 三组字符，可能解释不了为什么某个用户能写或不能写。

ACL 有用，但会让权限变复杂。初学项目能不用就先不用。若确实用了，文档里写清目的和命令。否则后面的人只会看到文件权限看着正确，操作却一直失败。

文件所有者不存在时，系统可能显示数字 ID。这常见于从另一台机器复制文件、恢复备份或挂载容器 volume。数字 ID 对不上，应用就可能读写失败。迁移文件后，要确认用户和组在新机器上也存在，并对应相同用途。

## 命令历史和审计边界

shell 历史能帮你回忆做过什么，但它不是可靠审计。有人可以关闭历史，某些命令不会记录完整上下文，带空格开头的命令在一些配置下可能不进入历史。`sudo` 日志和系统日志更适合追踪管理操作。

不要把秘密直接写进命令行参数。很多系统会在进程列表、历史文件或日志里暴露参数。按程序支持的方式选择受限文件、秘密管理服务或安全的交互输入。环境变量也不是保险箱，可能被子进程继承，或进入诊断输出；在终端中手写带秘密的变量赋值，还可能留下历史记录。AI 生成命令时，经常为了方便把密码写在一行里，执行前要改掉。

删除历史不能撤销已经发生的操作。误删、误改权限、上传秘密到仓库，都要按事故处理。先止损，再轮换秘密或恢复备份。不要把清理命令历史当成修复。

## 一个权限练习

安全练习应使用普通用户，不加 `sudo`。创建专用目录，放一个文本文件。用 `ls -l` 看所有者和权限，去掉文件写权限后尝试直接写入，再恢复权限。有些编辑器会通过新建文件再替换原文件来保存，若父目录可写，结果可能与直接写入不同，正好用来观察目录权限。脚本练习使用有效的解释器声明和无副作用内容，先去掉执行位，通过 `./script.sh` 直接运行，再加执行位重试；`sh script.sh` 是解释器读取脚本，不能用来验证执行位。结束后核对路径，只清理自己创建的练习文件。

这个练习的目标是形成判断，不是背命令。修改权限前先看当前状态。修改后立即验证。发现不符合预期，能回到上一状态。真实服务器上的权限问题，大多也按这三步处理。

## 一个上传失败案例

假设一个图片上传功能在本地正常，上服务器后报权限错误。前端请求到达后端，后端也能创建数据库记录，但文件写不到上传目录。检查发现服务由 `app` 用户运行，上传目录归 root 所有，并且没有通过组权限或 ACL 授予 `app` 所需的写入和目录搜索权限。

修复时不要把整个项目目录改成可写。先确认应用只需要写 `uploads` 和 `cache` 两个目录。把这两个目录交给应用用户，其他代码目录保持只读。随后用测试账号上传一张小图片，再检查文件所有者、页面显示和删除流程。

事故记录还要写下服务用户。以后换服务器、迁移容器或恢复备份时，维护者知道哪些目录需要给谁写。权限问题最讨厌的地方，是修好以后很快忘记当时为什么这样改。记录能防止下一次又把权限改乱。

## 恢复备份后的权限

从备份恢复文件后，权限常会变化。打包工具、复制方式、目标系统用户和容器用户都会影响所有者。文件内容回来了，应用却读不了，这很常见。恢复验收不能只看文件数量，还要看权限和业务访问。

如果备份来自另一台机器，用户 ID 可能不同。源机器上的 `app` 是 1001，目标机器上的 1001 可能属于另一个用户。即使恢复后显示了用户名，也可能映射到错误的人，不能只在看到数字所有者时才检查。应核对 UID、GID 与用途，必要时在确认范围后重新 chown 到目标机器上的正确服务用户。

数据库备份也会遇到权限问题。恢复后数据库角色、扩展、Schema 权限和连接用户都要检查。应用连接成功，只能说明账号能进数据库。能否读写目标表，还要用实际业务动作验证。

## 权限验收清单

上线前看几类路径。代码目录谁能写。配置文件谁能读。秘密文件谁能读。上传目录谁能写。日志目录谁能写。备份目录谁能读写。每类路径只给需要的人和服务。

再看几类操作。发布用户能否更新代码。服务用户能否启动应用。应用能否写上传和缓存。日志能否轮转。普通用户能否误改生产配置。把这些动作走一遍，比只看 `ls -l` 更可靠。

## 让 AI 审权限方案

AI 可以读懂权限表，但你要给它边界。把真实路径脱敏成 `/app/current`、`/app/uploads`、`/var/log/myapp`。把用户改成 `deploy_user` 和 `app_user`。告诉它每个目录的用途，让它判断哪些需要读，哪些需要写。

让 AI 输出权限建议时，要求它分成只读检查和会修改系统的命令。只读检查包括 `ls -l`、查看当前用户、查看服务用户和查看目录所有者。修改命令包括 `chmod`、`chown` 和递归操作。两类命令不能混在一起。

递归权限命令要人工复核。AI 可能为了省事生成 `chmod -R`，但目标路径一旦错，影响很大。执行前先在练习目录验证，再对真实目录执行。执行后立即用服务用户测试业务动作。

权限方案还应说明回滚。旧所有者是谁，旧权限是什么，改坏后怎样恢复。AI 若只给一条修复命令，没有回滚说明，就让它补完整。服务器上改权限，最怕“修好了但没人知道为什么”。

## 本章练习

按前面的权限练习准备普通用户会话，在家目录创建一个专用练习目录。新建一个普通文件、一个带有效解释器声明的简单脚本和一个子目录。用 `ls -l` 记录初始权限，明确去掉脚本执行位后通过 `./script.sh` 运行，观察失败。只给所需用户加执行权限，再以相同方式运行一次。

再创建一个模拟上传目录。把它的写权限收紧，尝试用当前用户写入。恢复权限后再写入。这个练习让你看到读、写、执行的差异，也能理解服务用户写不了目录时会发生什么。

最后写一份权限变更记录。改前状态，执行命令，改后状态，验证动作，回滚命令。真正的生产权限变更，也应有这五项。

## 常见误区

第一个误区是遇到权限问题就改成 `777`。这会让服务能写，也会让不该写的人和进程能写。正确处理从服务用户、目标目录和所需动作开始。只给必要权限。

第二个误区是认为 root 运行最省事。短期看确实少了很多权限错误，长期看会扩大事故范围。应用漏洞、脚本错误和路径写错，都可能直接影响系统文件。能用普通用户运行，就不要用 root。

第三个误区是只备份文件内容，不备份权限信息。恢复后文件都在，应用却读不了或写不了。备份和恢复记录里要写所有者、组、权限和特殊 ACL。权限也是系统状态的一部分。

## 本章交付物

本章结束时，你应该能交出一张权限表。它列出代码目录、配置文件、秘密文件、上传目录、日志目录和备份目录，分别说明谁能读，谁能写，谁负责恢复。

还应留下一份权限变更记录模板。任何 chmod、chown 和 ACL 调整，都按模板记录。这样权限不再靠口头记忆，也不会被 AI 生成的一条命令随手改乱。

AI 可以帮你解释权限字符串、生成练习命令和分析错误提示。不要把真实 `.env`、私钥、生产目录列表和含用户信息的日志交给它。下一章继续看软件包、进程、端口、磁盘和内存。
