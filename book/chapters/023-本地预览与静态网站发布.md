# 本地预览与静态网站发布

发布之前先在本机看一遍，是成本最低的排错步骤。文件路径错误、构建失败和页面空白若在本机发现，只影响自己。直接推到公开地址，问题就会与平台、域名、缓存和权限混在一起。

本地预览的目的不是证明网站已经上线。它用一个本机 HTTP 服务器模拟浏览器取文件的过程，确认准备发布的那批文件基本可用。公网 DNS、TLS、平台环境变量、地区网络和真实权限，发布后仍要单独验证。

## 双击 HTML 不是完整预览

双击 `index.html` 时，浏览器打开 `file` 地址，直接从磁盘读文件。简单页面可能正常，模块导入、路由、请求和安全策略却可能与 HTTP 访问不同。本地服务器会给出类似 `http://localhost:4173/` 的地址。`localhost` 指当前电脑，其他互联网用户不能凭这个地址访问你的项目。

测试部署结果时优先使用项目提供的生产预览命令。开发服务器用于写代码，可能即时转换文件并显示详细错误；生产预览读取已经生成的产物，更接近部署平台最终提供的内容。预览时确认自己看的不是旧 `dist`，也不是开发服务器从源目录临时补出来的资源。

打开项目根目录，查看 README 和文件结构。若只有 `index.html`、CSS、JavaScript 与图片，可能可以直接发布。若存在 `package.json`、`src`、框架组件和构建配置，通常需要先安装依赖并构建。查看 `scripts`，不要仅凭目录名决定。

## 预览要看具体结果

验收单要写可观察结果。把“页面正常”改成“首页标题出现，三张图片返回 200，导航可到关于页，关于页刷新仍能打开”。视觉检查覆盖常用桌面宽度和一部手机宽度。链接检查分内部和外部。下载链接确认文件名、大小和格式。表单如果没有后端，不要做成看似提交成功。

打开 DevTools。Console 不应有未解释的红色错误。Network 中主文档、CSS、脚本、图片和字体应返回预期状态。页面能显示，不代表所有后台请求正确。把验收结果与提交编号、预览命令、产物目录和检查时间放在一起。以后页面变化时，才能知道当时预览的是哪一版。

单页应用要特别测试刷新。用户从首页点击 `/profile` 正常，直接访问 `/profile` 时，托管服务器可能寻找同名文件或目录。没有回退规则就返回 404。解决方案取决于平台和应用。可以配置应用路由回退到 `index.html`，预先生成对应 HTML，或改用哈希路由。回退规则不能把真实静态文件缺失也全部伪装成 200。

## 三条静态发布路线

第一条是发布仓库中的现成文件。GitHub Pages 可以从指定分支的根目录或 `/docs` 发布。适合无需构建或已经把产物放到发布来源的站点。

第二条是平台连接 Git 仓库，在云端安装和构建，然后发布输出目录。Cloudflare Pages、Vercel 和 Render 都支持这类流程。每次推送可以自动产生新部署，预览地址也更容易关联到分支和提交。

第三条是本地或持续集成先构建，再直接上传成品。Cloudflare Pages Direct Upload 一类能力属于这条路线。它减少平台读取源码的权限，但每次更新要手工或由 CI 重建和上传。创建项目时要确认路线，因为有些平台项目类型不能随意互换。

三条路线没有普遍优胜者。选择依据是项目是否构建、谁负责构建、是否需要预览部署、是否希望每次 Push 自动更新，以及团队能否追踪发布来源。

## 静态不等于私密

静态站中的每个文件原则上都能被下载。即使没有页面链接，知道路径的人仍可能访问。不要放真实 `.env`、数据库备份、源设计中的隐私信息、未公开名单和私钥。前端 JavaScript 中的变量也可被查看。

来源仓库是私有仓库，也不代表生成的网站私有。许多静态站托管会把站点公开给互联网。需要成员登录才能查看的内部页面，应选择带身份验证和访问控制的方案，别依赖难猜 URL。

静态托管只描述文件提供方式，不限制浏览器脚本发请求。天气页面可以托管成静态文件，再从浏览器调用天气 API。这会遇到跨域、密钥暴露、配额和第三方停机。需要秘密的 API 不应由浏览器直接持有私钥。公开 API 也要处理超时、空数据和错误状态。

## 404 不都来自同一层

整页 404 表示服务器没找到入口或路径。先看地址栏和平台请求记录，再看产物文件树。页面空白而 HTML 200，常见原因是脚本未加载或启动异常。文字存在但没有样式，检查 CSS 请求。只有图片缺失时，逐字比较文件名与路径。

项目站可能位于 `/my-site/`。源代码里以 `/` 开头的绝对路径会从域名根解析。框架通常提供 Base、Base URL 或 Public Path 设置。部署目标不同，值也可能不同。使用当前框架部署文档，不在多个文件中手工替换路径。

浏览器缓存也会干扰判断。普通刷新不一定重新获取全部资源。在 DevTools Network 中开启 Disable cache 并保持工具打开，再刷新，可用于调试当前会话。若项目有 Service Worker，它可能主动提供离线缓存。不要清完缓存后就结束分析，还要修正版本化和更新策略。

## 发布来源要能追踪

直接上传一个文件夹很方便，也容易忘记它来自哪个提交。上传前生成发布记录，写源提交、构建命令、产物时间和上传者。由 Git 自动部署时，平台通常自动关联提交，仍要保存生产部署 ID 与验收结果。

从分支发布构建产物时，说明哪个工作流生成该分支。不要让人手改源分支和生成分支中的同一内容。发现线上文件无法在仓库重建时，先保存线上副本用于调查，再修复构建链。不要只在线编辑成品，让源代码继续保持错误。

发布前最后五分钟要做几件事。确认 Git 状态只包含预期修改，最新提交已经 Push；重新执行干净构建，检查日志没有错误；打开产物预览，按验收单走一遍；查看产物目录是否含秘密、备份和超大无关文件；记录提交与产物；触发部署；等待平台明确成功后打开平台 URL。

## 公开页面还要看可访问性

静态站常被当作“只是几个文件”，但公开页面仍需要基本可访问性。内容图片应有替代文字，装饰图片使用空替代文字，避免阅读器重复无意义文件名。图表还要有等价文字说明，读者即使关闭图片也能理解关键关系。

缩放页面到百分之二百，图片和文字不能互相遮挡。手机宽度下保持比例，避免横向滚动。网络慢时，页面应保留合理空间，减少图片加载后布局跳动。为图片声明尺寸或比例。中文正文要能自然换行，长 URL、代码和连续字符不能撑破屏幕。

只用键盘 Tab 浏览导航、按钮和表单。焦点应可见，顺序应符合页面阅读顺序。链接用 Enter 激活，按钮用 Enter 或空格。自制的可点击 `div` 往往缺少这些行为。打开菜单后应能关闭，焦点不能掉到页面不可见位置。本地预览发现这些问题后再上线，修复成本远低于用户投诉后紧急修改。

一个完整静态发布包包含构建产物、源提交编号、构建命令、运行时版本、产物清单和验收记录。直接上传时还记录上传目标。这些元数据不一定全部放进公开目录，可以保存在仓库受控文档或部署系统中。只保留一个不知来源的 ZIP，无法安全维护。

## 本章验收清单

能区分双击文件、开发服务器和生产预览。能按验收单检查首页、内部链接、深层刷新、图片、窄屏、Console 和 Network。能说出三条静态发布路线，以及谁负责构建。公开目录不含秘密、备份和未公开资料。发布记录能追溯到源提交和产物。

AI 可以读取项目说明和配置，判断候选发布目录，生成不含秘密的预览清单，并根据 404 请求比较引用路径与实际文件。让 AI 明确区分开发服务器和生产预览。亲自确认预览使用本次构建产物，关键链接和窄屏页面可用。下一章会把一份合适的静态站放到 GitHub Pages 和 Cloudflare Pages，说明两者替你承担了哪些工作。
