# 本地预览与静态网站发布

发布之前先在本机看一遍，看似是很小的步骤，却能把问题留在成本最低的地方。文件路径错误、构建失败和页面空白若在本机发现，只影响自己。直接推到公开地址，问题就会与平台、域名和缓存混在一起。

本地预览的目的不是证明网站已经上线。它用一个本机 HTTP 服务器模拟浏览器取文件的过程，确认准备发布的那批文件基本可用。

## 双击 HTML 与本地服务器

双击 `index.html` 时，浏览器打开 `file` 地址，直接从磁盘读文件。简单页面可能正常，模块导入、路由、请求和安全策略却可能与 HTTP 访问不同。本地服务器会给出类似 `http://localhost:4173/` 的地址。`localhost` 指当前电脑，端口区分不同服务。其他互联网用户不能凭这个地址访问你的电脑。

测试部署结果时优先使用项目提供的预览命令。它应当服务生产构建产物，而非带热更新的开发服务器。开发服务器用于写代码，可能即时转换文件并显示详细错误。生产预览读取已经生成的产物，更接近部署平台最终提供的内容。

打开项目根目录，查看 README 和文件结构。若只有 `index.html`、CSS、JavaScript 与图片，可能可以直接发布。若存在 `package.json`、`src`、框架组件和构建配置，通常需要先安装依赖并构建。查看 `scripts`，不要仅凭目录名决定。

Vite 当前指南把开发、生产构建和本地预览分开。默认构建结果位于 `dist`。它的静态部署指南还明确要求先本地运行构建，随后预览产物。一个仓库也可能同时包含多个站点。此时要先进入正确子目录，再执行命令。

## 无构建静态站的最小预览

如果电脑已经安装 Python，可以在纯静态站目录中运行一个临时服务器。下面命令只用于本机练习。

```
python -m http.server 8000
```

运行位置是包含 `index.html` 的目录。`-m http.server` 调用 Python 自带的简单 HTTP 服务，`8000` 是本机端口。正常结果是终端保持运行并显示监听信息；在浏览器打开 `http://localhost:8000/`，应看到首页；完成后回到终端按 `Ctrl+C` 停止。这个服务器不适合生产，不提供应用所需的身份、权限、限流和运维能力。它只用于本机查看静态文件。

若终端报告端口占用，可以先确认是否已有自己的预览服务。不要盲目结束陌生进程。也可以为练习改用另一个未占用端口，例如 `8001`。

## 有构建项目的最小预览

在项目根目录确认 `package.json` 后，按项目说明安装依赖与构建。以常见 npm 项目为例。

```
npm install
npm run build
npm run preview
```

三行分别安装依赖、生成生产产物、启动产物预览。实际项目可能要求 `npm ci` 或其他包管理器，脚本名称也可能不同。每一步单独运行并看结果。安装失败时不要继续构建，构建失败时不要拿旧产物预览。终端中仍有旧 `dist`，不代表它属于当前代码。

预览地址显示后，用浏览器完成一轮小型验收。打开首页，点击内部链接，刷新非首页路径，加载图片，提交无害表单，查看窄屏布局，再检查 Console 和 Network。

## 预览要看什么

先看页面是否完整。缺字体、缺图、样式散乱通常说明资源路径或构建复制有误。再看导航；项目站点将来可能位于 `/仓库名/`，本地预览却位于 `/`；需要特别测试基础路径；然后看刷新。单页应用从首页点击到 `/settings` 正常，直接刷新却 404，说明服务器需要回退配置，或静态托管路线不适合当前路由方式。

最后打开 DevTools。Console 不应有未解释的红色错误。Network 中主要资源应返回成功状态。表面能显示，不代表所有后台请求都正确。把验收结果与提交编号放在一起。几天后页面变化时，才能知道当时预览的是哪一版。

第一条是发布仓库中的现成文件。GitHub Pages 可以从指定分支的根目录或 `/docs` 发布。适合无需构建或已经把产物放到发布来源的站点。第二条是平台连接 Git 仓库，在云端安装和构建，然后发布输出目录。Cloudflare Pages、Vercel 和 Render 都支持这类流程。每次推送可以自动产生新部署。

第三条是本地或持续集成先构建，再直接上传成品。Cloudflare Pages 的 Direct Upload 就是例子。官方文档提醒，Direct Upload 项目不能随后切换成 Git 集成，Git 集成项目也不能切换成 Direct Upload。

三条路线没有普遍优胜者。选择依据是项目是否构建、谁负责构建、是否需要预览部署、是否希望每次 Push 自动更新，以及团队能否追踪发布来源。

## 一个活动说明页

社区准备发布一页活动说明。页面包含标题、时间、地图链接和一张海报，没有登录与数据库。若负责人手写 HTML 与 CSS，仓库文件就是成品。GitHub Pages 从 `main` 根目录发布即可。若设计者用框架生成页面，仓库保存组件和源图片，构建得到压缩资源。连接 Cloudflare Pages 或 Render 后，平台运行构建并发布 `dist` 更合适。

若活动当天内容冻结，组织方也可以在受控电脑构建，把产物直接上传。这样无需授权平台读取整个仓库，但每次更新要手工重建和上传。选择时写下责任。谁修改源内容，谁运行构建，谁确认预览，谁触发正式发布。没有责任记录，网站出错时大家只会猜最后一次是谁上传。

静态站中的每个文件原则上都能被下载。即使没有页面链接，知道路径的人仍可能访问。不要放真实 `.env`、数据库备份、源设计中的隐私信息、未公开名单和私钥。前端 JavaScript 中的变量也可被查看。

GitHub Pages 官方提醒，Pages 站点公开可访问，即使作为来源的仓库是私有仓库。私有源仓库不能代替访问控制。若内容只允许特定人员查看，应使用具备身份验证和权限控制的方案，而非靠难猜 URL。

## 入口文件与目录结构

静态服务器收到目录请求时通常寻找 `index.html`。GitHub Pages 还可处理特定 Markdown 或 README 入口，具体由发布方式决定。文件路径必须与部署后的目录结构一致。MDN 的文件课程建议使用简单、统一、小写的名称，避免空格和大小写混乱。

假设 HTML 写了 `images/logo.png`，产物中就要有对应相对位置。图片实际在 `Images/Logo.png`，Linux 托管可能返回 404。内部链接尽量使用站点规则支持的相对或基础路径。把本机 `C:\project\image.png` 写进 HTML，只在自己电脑有意义。

第一项检查平台发布目录。构建产物在 `dist`，平台却发布仓库根目录时，找不到正确入口。第二项检查基础路径。GitHub 项目站常位于 `https://用户名.github.io/仓库名/`，资源若写成 `/assets/app.js`，会从域名根目录查找。第三项检查部署对应提交。平台可能构建了另一分支，或最新部署失败后仍显示上一个成功版本。

第四项检查文件名大小写。用 Network 找到具体 404 URL，再与产物文件树逐字比较。不要一看到 404 就改 DNS。平台自带地址也 404 时，问题多半仍在发布内容或路由。

## 预览是验证，不是安全承诺

本地打开成功说明当前电脑、当前数据和当前浏览器下的若干路径可用。它没有验证公网 DNS、TLS、平台环境变量、地区网络、真实权限和高并发。发布后仍要用平台地址做一次验收。绑定自定义域名后再验一次。三次验收分别隔离本机、平台和域名层问题。

对于动态项目，本章的静态预览只覆盖前端产物。后端、数据库和身份系统在后续各卷单独验证。

## 为练习站准备一张验收单

验收单要写可观察结果。把“页面正常”改成“首页标题出现，三张图片返回 200，导航可到关于页，关于页刷新仍能打开”。视觉检查至少覆盖常用桌面宽度与一部手机宽度。缩窄浏览器只能初筛，真实手机还会暴露触摸、地址栏和字体差异。

链接检查分内部和外部。内部链接应到正确页面，外部链接应使用预期 HTTPS 地址。下载链接还要确认文件名、大小和格式。表单如果没有后端，不要做成看似提交成功。可以明确标注演示，或使用真实而安全的表单服务并说明数据去向。

最后记录浏览器、预览命令、产物目录、提交和检查时间。以后修改构建工具时可以重复同一套结果。

整页 404 表示服务器没找到入口或路径。先看地址栏和终端请求记录，再看产物文件树。页面空白而 HTML 200，常见原因是脚本未加载或启动异常。打开 Console 找错误，再在 Network 查看脚本状态。

文字存在但没有样式，检查 CSS 请求。若请求 URL 指向本机绝对路径，修正构建或 HTML 引用。只有图片缺失时逐字比较文件名与路径。构建工具可能把导入的图片改名，而手写字符串没有被处理。

本地预览与部署都缺失，修源代码或构建。只有部署缺失，比较基础路径、大小写与平台目录。

## 单页应用的刷新问题

单页应用的前端路由会在浏览器中切换视图。用户从首页点击 `/profile` 时，服务器可能只提供一次 `index.html`。直接访问 `/profile` 时，托管服务器会寻找同名文件或目录。没有回退规则就返回 404。解决方案取决于平台和应用。可以配置所有应用路由回退到 `index.html`，也可以让框架预先生成对应 HTML，或改用哈希路由。

回退规则不能把真实静态文件缺失也全部伪装成 200。错误脚本如果收到 HTML，浏览器会报告 MIME 或语法错误。验收清单应包含从地址栏直接打开深层链接和刷新。只通过首页点击无法发现这一类问题。

域名根站点的首页位于 `/`，项目站可能位于 `/my-site/`。源代码里以 `/` 开头的绝对路径会从域名根解析。框架通常提供 Base、Base URL 或 Public Path 设置。部署目标不同，值也可能不同。使用当前框架部署文档，不在多个文件中手工替换路径。

在本机模拟子路径能提前发现问题。按工具支持方式以 `/my-site/` 预览，检查 HTML、脚本、CSS、图片和路由。不要仅把首页文件移动进一层目录。构建工具生成的资源引用与路由仍需一致。

## 缓存如何干扰判断

浏览器可能保存旧 HTML、脚本与图片。普通刷新不一定重新获取全部资源。在 DevTools Network 中开启 Disable cache 并保持工具打开，再刷新，可用于调试当前会话。也可以使用新隐私窗口比较。

若项目有 Service Worker，它可能主动提供离线缓存。检查 Application 面板与项目更新策略，不要把 Service Worker 当普通缓存一键清除后就结束分析。构建文件带内容哈希时，新内容通常生成新 URL。HTML 仍需及时更新，才能引用新哈希文件。

平台地址和自定义域名可能经过不同缓存层。先确认响应头与资源 URL，再决定是否清理平台缓存。

## 相对链接的纸面练习

假设产物结构如下。

```
dist/
  index.html
  pages/
    about.html
  assets/
    logo.png
```

从 `index.html` 引用 Logo 可以写 `assets/logo.png`。从 `pages/about.html` 出发，对应相对路径是 `../assets/logo.png`。以 `/assets/logo.png` 开头的路径从域名根寻找。站点部署在子路径时可能跳出项目目录。浏览器最终请求 URL 才是判断依据。Network 的 Request URL 能显示路径怎样被解析。

实际框架优先使用其资源导入与路由方法，纸面练习用于理解错误，不鼓励在大型项目手算所有路径。

## 发布来源要能追踪

直接上传一个文件夹很方便，也容易忘记它来自哪个提交。上传前生成一份发布记录，写源提交、构建命令、产物时间和上传者。由 Git 自动部署时，平台通常自动关联提交。仍要保存生产部署 ID 与验收结果。

从分支发布构建产物时，说明哪个工作流生成该分支。不要让人手改源分支和生成分支中的同一内容。发现线上文件无法在仓库重建时，先保存线上副本用于调查，再修复构建链。不要只在线编辑成品，让源代码继续保持错误。

静态托管描述文件提供方式，不限制浏览器脚本发请求。天气页面可以托管成静态文件，再从浏览器调用天气 API。这会遇到跨域、密钥暴露、配额和第三方停机。需要秘密的 API 不应由浏览器直接持有私钥。

公开 API 也要处理超时、空数据和错误状态。静态首页能加载，动态区域可能失败。预览验收要区分本地文件与外部请求。外部 API 失败时，页面应给出可理解提示，不保持永久加载动画。

## 发布前的最后五分钟

确认 Git 状态只包含预期修改，最新提交已经 Push。重新执行干净构建，检查日志没有错误；打开产物预览，按验收单走一遍；查看产物目录是否含秘密、备份和超大无关文件；记录提交与产物，触发部署；等待平台明确成功后打开平台 URL；不要在构建仍运行时开始改 DNS。

这五分钟无法替代测试，却能阻止把旧产物、错分支和敏感文件直接公开。

检查图片替代文字。内容图片应说明信息，装饰图片使用空替代文字，避免阅读器重复无意义文件名。缩放页面到百分之二百，图片和文字不能互相遮挡。手机宽度下保持比例，避免横向滚动。网络慢时，页面应保留合理空间，减少图片加载后布局跳动。为图片声明尺寸或比例。

图表还要有等价文字说明。读者即使关闭图片，仍能理解关键关系。

## 字体、中文换行和标点

本机装有某字体，页面会悄悄使用它。另一台设备没有，排版可能变化。CSS 提供常见系统中文字体回退。检查长英文 URL、代码和连续字符会不会撑破屏幕。正文允许中文正常换行，代码块则支持横向滚动或适当折行。

粗体和颜色不能成为唯一的信息提示。深色模式下检查文字、链接和提示框对比度。本书 EPUB 也使用同样原则，网页练习成为后续电子书验收的预演。

只用键盘 Tab 浏览导航、按钮和表单。焦点应可见，顺序应符合页面阅读顺序。链接用 Enter 激活，按钮用 Enter 或空格。自制的可点击 `div` 往往缺少这些行为。打开菜单后应能关闭，焦点不能掉到页面不可见位置。跳过链接可帮助键盘用户直接进入正文。

本地预览发现这些问题后再上线，修复成本远低于用户投诉后紧急修改。

## 一个完整静态站发布包

发布包包含构建产物、源提交编号、构建命令、运行时版本、产物清单和验收记录。直接上传时还记录上传目标。这些元数据不一定全部放进公开目录。发布记录可以保存在仓库受控文档或部署系统中。需要紧急恢复时，能从记录找到上一个产物来源。只保留一个不知来源的 ZIP，无法安全维护。

版本号可以显示在页面页脚或隐藏元数据中，避免泄露内部信息的前提下帮助排错。

志愿者制作了一页会议说明，包含日程、场地图、报名链接和 PDF。页面没有后端表单，报名跳转到受信任的外部系统。本地双击 HTML 时一切正常，用 HTTP 预览后 PDF 链接却 404。链接写成了志愿者电脑的绝对路径。改为发布目录中的相对路径后，另一台电脑也能打开。

手机检查又发现日程表横向溢出，场地图没有替代文字。志愿者把表格转换成窄屏可滚动容器，为地图补充文字路线，并让键盘焦点清楚可见。最后在无缓存 Network 中确认 HTML、CSS、图片和 PDF 都返回 200。外部报名链接用新标签打开，并在文字中说明会离开当前网站。

发布记录包含提交、产物清单、PDF 文件大小和检查浏览器。主办方后来替换 PDF 时，能确认站点引用的是新文件，而非浏览器旧缓存。这个例子没有复杂框架，却仍需要 HTTP 预览、移动阅读、可访问性与公开文件检查。静态不等于无需验收。

## 本地预览通过以后还缺什么

AI 可以读取项目说明和配置，判断候选发布目录，生成不含秘密的预览清单，并根据 404 请求比较引用路径与实际文件。让 AI 明确区分开发服务器和生产预览。若它只启动 `npm run dev` 就宣称部署已验证，证据不足。

亲自确认预览使用本次构建产物，公开目录没有敏感文件，关键链接和窄屏页面可用。发布账号、仓库授权与正式上线仍由你确认。下一章会把一份合适的静态站分别放到 GitHub Pages 和 Cloudflare Pages，说明两者替你承担了哪些工作。
