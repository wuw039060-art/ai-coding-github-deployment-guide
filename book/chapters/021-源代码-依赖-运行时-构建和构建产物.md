# 源代码、依赖、运行时、构建和构建产物

把网页项目上传到 GitHub，往往还不能直接得到一个网站。仓库里可能放着人读得懂的源文件，浏览器需要的却是另一批文件。中间少了一道构建工作。本章先拆开五个词。源代码是原材料，依赖是借用的现成能力，运行时让工具能够执行，构建是加工过程，构建产物是准备交付的成品。

理解这五个位置以后，“本地能开，上线失败”就能问得更准。究竟是源文件有误，依赖没装，运行时版本不同，构建过程失败，还是平台发布了错误目录。

## 源代码是准备加工的材料

源代码包括你直接编辑的 HTML、CSS、JavaScript、图片、组件、页面模板、内容数据和配置。它以方便维护为目标，不保证浏览器可以原样使用。一个只含 `index.html`、`style.css` 和图片的简单站点，源文件已经接近成品，发布平台只要把文件送给浏览器。

另一个项目使用 React、Vue、TypeScript 或静态站点生成器。仓库里可能有 `.tsx`、`.vue`、Markdown、未压缩图片和分散模块。浏览器最终收到的是普通 HTML、CSS、JavaScript 和静态资源。构建工具负责转换、组合、压缩、生成路由和复制资源。

不要根据文件扩展名猜流程。先读 README，再看 `package.json` 的 `scripts`，然后在本地执行项目提供的构建命令。源代码和成品有时长得很像，有时差别很大。

## 依赖是项目借来的能力

开发者通常不会从头编写日期处理、界面组件、图像压缩和构建工具。他们把这些能力作为依赖装入项目。可以把依赖理解成按清单采购的零件。你的房屋设计不包含门锁内部每个弹簧，但施工时需要拿到正确型号。

在常见 JavaScript 项目中，`package.json` 是依赖和脚本清单，锁文件记录更准确的依赖树，`node_modules` 是实际安装到本机的依赖目录。这三者不能互相替代。只有清单，没有实际安装文件，程序可能无法运行；只有 `node_modules`，没有清单和锁文件，别人难以可靠重建环境。

项目一般提交清单和锁文件，把 `node_modules` 写进 `.gitignore`。新电脑或部署平台根据清单重新安装。若项目说明采用 pnpm、Yarn 或其他工具，就按项目约定执行。不要为了自己电脑方便混用包管理器。

## 运行时让代码动起来

运行时可以理解成电器需要的电压和插座。源文件存在，不代表电脑知道怎样执行。JavaScript 构建工具经常需要 Node.js，Python 项目需要 Python，Flutter 工具需要 Dart 和 Flutter SDK。浏览器本身也是一种运行环境，浏览器中的 JavaScript 和 Node.js 中的 JavaScript 可用接口不同。

运行时还有版本。一个项目在 Node.js 20 下正常，不代表在更旧或更新版本中都正常。`package.json` 可以用 `engines` 声明兼容范围，部署平台也可能通过设置或配置文件选择版本。日志里出现版本号时，要把它当作证据保存。

版本不同会产生几类问题。旧运行时不认识新语法，新运行时移除了旧能力，原生依赖没有相应二进制文件，包管理器生成了不同格式锁文件。第 22 章会专门讲这些环境差异。

## 构建把源材料加工成产物

构建会根据项目不同完成若干任务。TypeScript 转换成 JavaScript，组件转换成浏览器脚本，多个文件被组合，图片和 CSS 被复制或压缩，文件名可能加入内容哈希，最终 HTML 引用这些新文件。

哈希文件名看起来像 `app.a31f9c.js`。内容改变，名称也改变，浏览器便能长期缓存旧资源，同时在新版本到来时请求新文件。静态站点生成器还可能读取 Markdown 和模板，输出许多 HTML 文件。部署平台只需提供这些成品，不必在每次访问时重新计算。

构建不等于测试。构建命令退出成功，只说明构建工具没有报告失败。页面可能仍有错链、内容缺失、环境变量错误、浏览器运行异常和权限问题。构建完成后还要预览并检查关键路径。

## 构建产物是交付目录

构建产物通常位于 `dist`、`build`、`out` 或项目自定义目录。目录名没有统一标准。平台中的 Output Directory 或 Publish Directory 必须指向实际产物位置。盲填 `dist`，平台可能发布空目录或直接报错。

判断产物目录用四项证据。README 明确写出部署目录；构建配置声明输出位置；构建日志写出生成路径；执行构建后，某个新目录出现 `index.html` 和资源文件。四项能互相校验。

不要把整个仓库当作静态产物发布。仓库可能含源代码、测试、脚本、说明、`.env` 示例、内部配置和未公开资料。静态托管只需要浏览器应当下载的文件。发布目录越精确，泄露风险越低，排错也越清楚。

## 两个菜单网站

一家面包店有两个菜单网站。第一个只有三个手写文件，分别是 `index.html`、`style.css` 和一张图。店主修改后直接发布，源文件就是成品。第二个网站从商品数据生成中文页、英文页和打印页，图片在构建时缩小，CSS 被整理，页面由模板生成。店主编辑的是数据和模板，顾客收到的是 `dist` 中的 HTML、CSS、JavaScript 与图片。

两个都叫静态网站，发布路径却不同。第一个可以发布仓库根目录，第二个必须先运行构建，再发布产物目录。当第二个把仓库根目录误当成产物，浏览器可能下载到模板源文件，却找不到真正首页。修复重点是 Build Command 和 Output Directory，不是购买服务器。

## 构建失败先看阶段

命令未开始，检查工作目录、运行时与脚本名称。安装未完成，检查网络、锁文件、权限和依赖脚本。构建未完成，检查第一段编译错误与环境变量。构建完成但没有入口，检查配置与内容生成。产物本地正常而平台失败，比较平台环境和发布目录。平台地址正常而域名失败，再进入 DNS 与 HTTPS。

日志要从底部向上找第一段明确错误。最后一行常是“构建失败”的汇总，真正原因可能在更上方。`command not found` 常指运行时或工具不可用；`Cannot find module` 常与依赖、版本或导入路径有关；`ENOENT` 表示找不到文件或目录；大小写错误常在 Linux 云构建环境暴露。

记录错误时保留执行目录、完整命令、运行时版本、包管理器版本、第一段错误和退出码。只截最后一行会丢掉原因。

## 构建成功也要留下证据包

一次可靠构建至少留下六样证据，包括源提交、运行时版本、包管理器版本、构建命令、输出目录和预览结果。若构建依赖在线获取实时数据，还要记录数据来源时间和校验方式。旧提交能重新生成“功能相同”的站点，比记住某次机器上的临时目录更重要。

产物大小也值得看。构建从五兆突然变成五十兆，可能误把源图片、视频或依赖目录复制进去；突然只剩几千字节，可能内容生成失败。检查 HTML 引用的脚本与样式是否都存在，随机抽查图片和字体，确认文件大小合理。空文件也能通过“存在”检查。

Source Map 可以把压缩后的错误位置映射回源码，方便调试和错误监控。公开 Source Map 可能暴露较多源码结构和注释。是否发布取决于项目风险、调试需要和监控平台方式。它不会修复错误，只让错误更容易读。生产日志仍要包含部署版本，才能找到对应映射。

对图片和字体也要有来源记录。构建工具可能压缩图片、生成多种尺寸，或把小图片嵌入 CSS。字体要确认授权允许网页分发，并提供系统字体回退。构建成功无法证明字体许可合规，也不能证明外链字体在目标地区可用。

## 本章验收清单

能指出项目源目录、清单、锁文件、运行时要求、构建命令和输出目录。能在全新工作副本构建，并用生产预览打开成品。验证记录中有提交、命令、产物位置和浏览器结果。失败时能说出阶段，而非只说“部署坏了”。

AI 可以阅读项目树、`package.json` 与构建配置，列出候选安装命令、构建命令和输出目录。让它引用字段和文件，不接受只凭框架名称猜出的答案。发布前亲自确认构建无错误、产物来自本次源文件、目录中没有真实密钥和内部备份。下一章继续讲包管理器、锁文件、版本号和环境差异，它们决定另一台电脑能否重现你眼前的成功。
