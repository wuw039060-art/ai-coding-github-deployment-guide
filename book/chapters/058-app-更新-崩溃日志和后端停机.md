# App 更新、崩溃日志和后端停机

网页部署后，维护者可以把服务器立即切到旧版本。App 更新已经下载到用户设备以后，商店没有一个按钮能把所有安装瞬间换回去。用户可能关闭自动更新、长期离线，或继续使用数年前的客户端。所以 App 发布要同时考虑新客户端、旧客户端、新后端和旧数据。真正的回滚能力来自兼容设计、逐步发布、监控和快速修复，不来自“先发了再说”。

## 更新前先设计兼容窗口

假设 2.0 客户端把用户姓名字段从 `name` 改成 `displayName`，后端同一天删除旧字段。仍使用 1.9 的用户会突然无法读取资料；安全做法可以分阶段进行；后端先同时接受和返回新旧字段；2.0 客户端发布并逐步覆盖；观察旧版本使用比例下降，再让后端停止写旧字段；最后经过公告和期限才删除兼容代码。

数据库变化也使用可兼容顺序。先新增可空字段或新表，让新旧程序都能运行。数据回填完成后再切读路径。直接重命名或删除旧字段，容易让旧客户端和回滚版本同时失效。兼容窗口有成本，因此要记录最低支持版本和结束时间。无限期支持所有旧版本也不现实。

App Version 用于商店和用户。API 版本用于客户端与后端约定请求格式。两者不必一一对应。一个 2.1 App 可能仍调用 `/v1` API，只增加本地界面。另一个 2.1.1 修复可能需要后端新增可选字段。

后端日志同时记录客户端平台、App Version、Build 和 API 版本。发生错误时可以判断是否集中在某次构建。不要让客户端传一个版本字段就获得更高权限。版本信息用于兼容和观察，身份与权限仍由认证系统判断。

## 逐步发布控制新增影响

Google Play 的 staged rollout 可让更新先到一部分用户，再逐步增加比例。它只适用于更新，不适用于首次发布。暂停后，已经收到新版本的用户不会自动退回旧版。

Apple phased release 会在七天内把自动更新逐步扩大。截至 2026 年 8 月 5 日，官方比例为第一天 1%、第二天 2%、第三天 5%、第四天 10%、第五天 20%、第六天 50%、第七天 100%。用户仍可手动下载新版本，因此它不是严格实验隔离。

政策可能发生变化

> 比例、暂停期限、适用状态和控制台入口都以发布当天官方页面为准。

逐步发布前定义观察指标。只看下载量没有用。至少看启动崩溃、ANR、登录成功率、核心 API 错误、同步失败和用户反馈。扩大比例要有人确认。平台不会理解你的业务指标是否异常。

## 暂停发布不等于修复

严重崩溃出现后，先暂停继续扩大，保护尚未更新的用户。已经更新的用户仍需要解决办法。若问题来自可安全关闭的新功能，可以用后端 feature flag 临时关闭。开关本身要有权限、审计和默认值，不能依赖个人电脑。

若问题在客户端启动路径，通常需要修复代码、提高版本号、重新构建、测试和提交。审核与商店传播需要时间。若后端变更导致旧客户端失败，优先恢复兼容后端可能比等待新 App 更快。不能为了强迫升级让所有旧客户端立即失效，除非存在明确安全原因和用户沟通。

崩溃表示进程异常终止。Android ANR 是 Application Not Responding，指主线程等长时间无法响应，用户可能看到系统无响应提示。业务错误则是 App 仍运行，但登录、支付或同步给出错误结果。

三者需要不同证据；崩溃看堆栈、异常和符号；ANR 看线程状态和阻塞；业务错误要连接客户端日志、请求关联编号和后端日志。Google Play 的 Android vitals 会收集允许共享数据的设备上的稳定性、性能、电量和权限问题，并在 Play Console 展示。统计口径与第三方崩溃 SDK可能不同。

Apple 分发构建需要使用崩溃报告和设备日志排查，不能像开发构建一样直接附加调试器。

## 符号文件把地址变回函数

Release 构建会优化或移除调试名称。原始崩溃报告可能只看到内存地址。符号化使用与该 build 匹配的符号文件，把地址还原为函数和行索引。iOS 要保留每个上传 build 的 Xcode Archive 与 dSYM。Android 原生压缩和 Dart 混淆也会产生对应映射或符号文件。

如果 Flutter 使用 `--obfuscate` 和 `--split-debug-info`，必须安全保留本次生成的符号目录，并和版本、build、平台架构关联。丢失后，线上堆栈可能无法还原。符号文件属于发布证据，不应在下一次构建时覆盖。它可能包含代码结构信息，要按内部资产保护。

先确认平台、App Version、Build、设备型号、系统版本和发生时间。再看异常类型、触发线程和符号化堆栈。同一签名的崩溃按顶部相关帧聚类。影响一万人一次的问题，优先级可能高于测试账号重复一百次的问题。

对比受影响与正常设备。问题是否只发生在某 Android 厂商、某 iOS 版本、低内存设备或某语言。回到对应 Git 提交和 Archive。按用户步骤复现，加入必要诊断，再在相同级别设备验证修复。

不要只复制最后一句异常。完整报告中的异常代码、线程和系统信息可能改变判断。分享给外部人员前移除个人数据和内部秘密。

## 一个升级后启动崩溃案例

记账 App 2.0 修改本地 SQLite schema。开发者只测试了卸载后的干净安装，没有从 1.9 升级。旧用户首次启动时，迁移脚本按不存在的中间版本执行，读取缺失列并崩溃。新用户数据库直接创建为最新结构，因此团队设备都正常。

逐步发布的第一批崩溃率上升。团队暂停扩大，保留后端兼容，修复迁移顺序并增加 2.0.1。测试使用 1.7、1.8、1.9 三个旧数据库副本逐级升级。这个事故说明干净安装和升级安装必须分别测试。本地数据 schema 也是发布接口。

后端不可用时，读取缓存可以显示旧内容，但要标明最后同步时间。需要服务器确认的操作不能显示永久成功。客户端请求超时，结果可能未知。后端可能已经创建订单，只是响应没有到达。重试使用幂等键，或者先查询订单状态。

错误提示给用户行动建议。“服务暂时不可用，已保存到本机，恢复网络后同步”比“未知错误 500”有用。若本地未保存，不能承诺不会丢失。维护者需要状态页、告警和关联编号。App 可以显示短编号供客服查询，不暴露内部主机名和堆栈。

## 离线队列要防止无限重试

离线写入常放入本地队列。恢复网络后按顺序发送，成功后标记完成。认证失效需要让用户重新登录，不应每秒重试。参数错误通常不会靠等待恢复，应标记失败并允许用户修正。服务器暂时不可用可以指数退避，逐步延长重试间隔。

队列要限制大小和保留期。用户离线拍摄上千张照片可能耗尽设备空间。界面应显示待同步数量与失败原因。退出登录或删除账号时处理队列。尚未同步的唯一数据要提示导出或放弃，不能静默清除。

有时旧版本存在严重安全问题，或后端无法继续兼容；App 可以查询最低支持版本并提示升级；强制升级页面要保留商店入口、支持渠道和必要说明；若商店在某地区不可访问，用户需要替代方案；后端返回最低版本时，不能只比较版本名称字符串；`1.10` 按文字可能被错误认为小于 `1.9`；使用明确的整数 build 或规范版本比较。

强制升级服务自身也可能故障。默认策略要经过风险判断，不能因为配置接口超时让所有用户被锁在首页。

## 后端接口下线要看活跃版本

在删除旧 API 前，查看最近一段时间的客户端版本分布和请求量。统计数据可能受隐私选择影响，仍可作为证据之一。通知仍在使用旧版本的用户，给出升级期限。对无法升级的旧设备，说明最低系统要求和数据导出办法。

到期后先让旧接口返回可理解的升级错误，观察影响，再删除实现。保留审计记录和恢复计划。若旧接口涉及安全漏洞，可以缩短窗口，并使用后端保护减少风险。决策要记录影响和替代路径。

客户端日志可能被用户读取或包含在崩溃报告。不要记录密码、完整令牌、支付信息和用户正文。记录请求方法、逻辑接口名、状态类别、耗时、关联编号和脱敏错误。生产日志级别避免输出完整响应。后端使用同一关联编号，支持从客户端问题追到入口、数据库和外部服务。编号本身不应包含用户身份。

日志保留时间与访问权限写入制度。排错完成后，测试导出的临时日志也要安全删除。

## 一次后端停机演练

在测试环境准备最终 Release 安装包。保持 App 已登录并有一份同步成功的数据。第一阶段阻断网络。打开 App，确认缓存可读，最后同步时间准确。新增一条允许离线的记录，确认显示待同步。

第二阶段恢复网络但让测试 API 返回 503。App 应退避重试，不把服务错误写成密码错误，也不制造重复数据。第三阶段恢复 API。待同步记录只出现一次，状态变为已同步。后端日志能用关联编号找到请求。

第四阶段让登录令牌失效。App 提示重新登录，成功后继续可恢复任务，不把队列发到错误账号。记录设备、build、开始结束时间、预期和实际结果。演练不能在生产环境随意关闭真实服务。

发布前写基线，发布后按相同口径比较。

| 指标 | 发布前基线 | 暂停条件 | 证据位置 |
| --- | --- | --- | --- |
| 启动崩溃率 | 最近稳定版本 | 显著高于基线 | Android vitals 或 App Store Connect |
| 登录成功率 | 后端统计 | 连续下降 | API 指标与日志 |
| 同步失败率 | 客户端与后端 | 集中在新 build | 关联编号与队列状态 |
| 用户反馈 | 最近七天 | 同类严重反馈增加 | 商店和客服 |
| 数据迁移错误 | 测试为零 | 任一不可恢复错误 | 崩溃与数据库日志 |

阈值要根据用户量和风险设置。用户很少时，一个严重数据丢失也不能因百分比低而忽略。

## 发布后四种动作

继续扩大适用于指标稳定、反馈可解释的版本。保持比例适用于数据不足，需要更多观察但没有严重信号。暂停适用于新增崩溃、数据错误或核心功能失败；暂停后立即处理已更新用户；发布修复适用于客户端缺陷；更高版本经过内部测试，再进入逐步发布；不能把旧二进制原地替换。

Google 和 Apple 的逐步发布控制台只是执行工具。判断来自应用和业务证据。

主分支保持可以重建。每个生产版本打标签，保存依赖锁、构建环境、签名记录、制品校验值、符号和商店提交资料。后端变更保留兼容与回滚。数据库迁移先在恢复出的副本验证。功能开关记录默认值和负责人。

每季度做一次旧版本兼容、账号权限、签名资产、隐私表单和后端恢复检查。App 没有更新，证书、SDK 和商店政策仍会变化。AI 可以聚类崩溃、比较版本日志和生成演练清单。你必须确认符号是否匹配、指标是否真实、暂停或扩大范围的影响。任何自动发布系统都要把最终生产确认留给授权人员。

## 网络协议变化要先于客户端发布

后端准备强制 TLS 新版本、换域名或更换证书链时，先确认所有仍支持的 Android 与 iOS 版本能连接。旧设备信任库可能不认识新证书链。证书固定策略若硬编码公钥，也可能在正常轮换时阻断。

在预发布域名部署新配置，让各客户端版本测试。真正切换时保留监控和快速恢复。移动网络、企业代理、IPv6 和中国大陆网络环境都可能出现差异。只在办公室 Wi-Fi 成功不够。

远程配置可以调整文案、阈值或功能开关，无需等待商店更新。它适合止损，不适合远程下载未审核的完整新功能绕过商店。每个关键开关定义安全默认值、负责人、适用版本、过期时间和审计记录。配置服务不可用时，App 仍应启动。

后端不能向旧客户端发送它不理解的新枚举值，除非协议规定未知值处理。远程开关也要考虑旧版本字段。定期删除已经永久开启的旧开关。大量无主开关会让问题难以复现。

## 数据格式使用扩展式变化

新增可选字段通常比改字段含义安全。旧客户端忽略未知字段，新客户端对缺失字段使用明确默认。枚举新增值时，客户端提供 unknown 分支。否则后端增加一个订单状态，旧 App 可能解析崩溃。

删除字段前观察旧客户端使用。后端日志可以记录 API 版本和缺失字段错误。对文件格式和本地导出也保留 schema version。新 App 能读旧格式，无法读新格式的旧 App 至少给出清楚提示。

通知 payload 进入已经安装的各种版本。新增动作按钮或页面路径时，旧客户端可能不认识。payload 包含类型与版本，客户端对未知类型安全打开通知中心或首页。不要因缺少一个字段在后台崩溃。

服务端按客户端能力发送，或使用所有支持版本都理解的最小格式。敏感数据仍不放通知正文。发布新 App 以前先部署兼容后端，发布完成以后再逐步启用新通知类型。

## Android ANR 先看主线程在等什么

ANR 常发生在主线程长时间做网络、数据库、文件或锁等待。应用没有崩溃，用户仍无法操作。Google Play 的 ANR cluster 和堆栈能显示集中位置。结合设备和系统版本，判断是应用锁、Binder 调用还是高负载。

复现时记录完整 trace，不能只在代码中到处加异步。错误并发可能引入数据竞争。修复后在低端设备和慢存储条件重复操作。平均速度改善不代表最长停顿消失。

iOS 可能在内存压力下终止 App，Jetsam 报告记录系统内存条件，却不一定有普通异常堆栈。Apple 崩溃诊断文档将 crash、Jetsam 和 device console log 分开。

图片解码、大列表、视频和缓存容易形成峰值。用对应 build、设备和操作分析。降低缓存、按尺寸加载图片和释放不再使用资源后，在相同设备复测。用户只说“闪退”时，先查系统报告类型。不能把所有退出都归因于一行空指针。

## 崩溃 SDK 不是唯一事实来源

第三方 SDK 可以快速聚类和告警，但可能在自身初始化前漏掉崩溃，也受网络和用户同意影响。Android vitals、App Store Connect、系统崩溃报告、客服反馈和后端指标从不同角度观察。数字不一致时先比较口径。

SDK 还会收集设备与使用数据，必须进入隐私事实表。为收集更多上下文而上传用户正文，风险可能高于排错收益。保留平台原始报告与符号，不把厂商 Dashboard 当永久档案。

整体崩溃率可能被大量稳定旧版本稀释。发布观察按新 build、系统、设备和国家切片。后端错误也按客户端版本分组。新版本登录失败率高，整体 API 仍可能看似正常。逐步发布每次扩大前保存快照。记录用户量、指标窗口和判断者。

数据量小时，结合严重程度与人工反馈。一次账户串数据的影响远高于十次可重试图片失败。

## 一次后端证书故障案例

团队轮换 API 证书，桌面浏览器正常。部分旧 Android 设备从当晚开始全部报网络错误。客户端日志显示 TLS 握手失败，后端没有收到 HTTP 请求。检查发现新证书链对旧设备信任库不兼容。

团队恢复兼容链，服务立即恢复。随后在预发布环境加入旧系统设备测试，并监控握手失败。这个事故不能通过重发同一个 App 立即解决。后端网络变更同样属于客户端发布风险。

新支付页面只在 3.0 支持，远程配置却把开关发给所有版本。2.9 收到未知页面路径后停在空白页。团队关闭开关，修正服务端条件为 build 大于等于指定值，并让旧客户端对未知路径回首页。之后每个开关都记录最低版本、安全默认和回滚测试。控制台修改需要双人确认。

远程控制减少了等待时间，也增加了绕过代码发布流程的风险。

## 应用事故沟通说用户需要什么

状态公告写受影响功能、开始时间、当前状态和用户建议。不能在根因未知时承诺固定恢复时间。若重复点击可能产生重复订单，明确让用户停止重试并提供查询路径。若离线数据安全，说明不要卸载 App。

恢复后说明是否需要更新、重新登录或手工同步。提供支持入口。公开信息不披露攻击细节、个人数据和内部凭据。技术复盘可以在修复后单独发布。

建立时间线，从首个异常、告警、暂停发布、修复到恢复。每个时间点写证据与决定。区分直接原因和放大因素。数据库迁移错误是直接原因，只测干净安装是流程缺口，没有逐步发布是放大因素。行动项有负责人、期限和验证。写“加强测试”太空泛，改成“增加从最近三个生产 schema 升级的自动测试”。

复盘不以追责个人为目标。系统要让下一位维护者更难犯同样错误。

## 版本下线要给数据出口

停止支持旧系统或关闭服务前，统计受影响用户和设备。提前在 App、邮件或官网通知。提供数据导出与迁移路径。用户设备无法升级时，至少能保存自己的内容。后端接口进入只读期，再按计划关闭写入。直接返回通用 500 会让用户误以为临时故障。

商店下架、账号删除与后端关闭分别执行。只下架 App 不会停止服务器费用，也不会删除用户数据。

重大版本选择团队能连续观察的时段。避开负责人旅行、节假日开始和后端大迁移同一天。发布计划写测试完成、审核状态、逐步比例、观察窗口和停止条件。值班人能访问商店、日志和功能开关。平台审核时间不可完全控制。提前提交候选 build，使用手动或分阶段发布选项协调。

紧急修复也要最低测试。越紧急越需要确认包名、签名、版本和核心流程。

## 每季度做一次旧版本演练

保留最近几个生产安装包和测试账号。在隔离设备上安装旧版本，连接当前预发布后端。检查登录、读取、升级提示和数据导出。记录哪些版本已经不兼容以及原因。从旧版升级到当前候选，验证本地数据库和登录迁移。符号资产能否找到也一起检查。

演练结果决定兼容窗口和用户公告，不能等线上旧用户报错才发现。

审核通过和点击发布后，不同地区商店页面、搜索、CDN 和设备更新检查可能在不同时间看到新版本。用户说没有更新时，先记录国家、商店账号、设备系统和当前版本。不要让用户重复卸载，这可能删除本地数据。

后端兼容窗口覆盖传播差异。不能在点击发布后五分钟就删除旧 API。状态页说明版本正在逐步提供，避免把正常传播误报成故障。

## 数据库迁移与 App 发布分开控制

服务器数据库迁移可以在 App 审核前后发生。破坏性迁移不能依赖商店在某一刻把所有客户端更新。先做兼容 schema，部署同时支持新旧客户端的后端，再发布 App。活跃旧版本下降后才收尾。

迁移使用备份恢复出的副本测时间与回滚。生产执行记录开始、结束、版本和校验。App 被审核退回时，后端仍要保持旧客户端可用。发布计划不能把两者绑成一个无法暂停的脚本。

流量突然增加时，后端可以返回 429 等明确状态并提供重试建议。客户端使用退避和随机抖动，避免所有设备同一秒重试。服务维护可返回 503。客户端保留本地队列，显示服务暂不可用，不能误报登录失败。

限流按账号、设备和业务动作设计。共享网络中的多个用户不应因单一 IP 限制全部被封。监控限流命中和重试成功率。过严规则和真正攻击需要不同处置。

## 推送不能代替应用内状态

推送可能延迟、被系统合并、被用户关闭或因令牌失效不送达。重要订单和安全事件在 App 内有可查询记录。通知点击后重新请求后端。payload 只带最小定位标识，不把完整隐私内容放锁屏。后端保存发送结果并清理无效 token。用户退出登录时解除 token 与账号绑定，防止下一位设备使用者收到旧账号消息。

故障公告同时使用状态页、应用内提示和支持渠道，不能只发推送。

可以按数据安全、数据完整性、核心可用性和局部体验分类。账号串数据、错误扣款和不可恢复丢失属于高严重度。高严重度先止损和保护证据，暂停发布、关闭功能或限制写入。普通视觉问题可以保持比例并安排修复。

严重度定义在事故前写。现场不因负责人个人偏好争论。任何等级都记录用户影响。小用户量不降低单个隐私泄露的性质。

## 客户端修复也要考虑数据补偿

错误版本可能已经写入重复订单、损坏本地字段或上传错误文件。发布不再崩溃的新版本，只解决以后行为。先查询受影响数据范围，设计可审计修复。自动合并可能误删用户真实操作，必要时让用户确认。

补偿脚本在副本和少量账号试运行，记录前后数量与可回退备份。向受影响用户说明修复内容和他们需要的动作。不能只在 Release notes 写“稳定性提升”。

后端从昨日备份恢复后，用户今天在客户端产生的写入可能消失。客户端离线队列又可能重新上传一部分，形成冲突。灾难恢复计划定义恢复点、写入冻结、客户端维护提示和重放规则。演练时使用当前与旧客户端连接恢复环境，检查登录、版本兼容和同步。只验证数据库能启动不够。

恢复完成后对关键业务数量、对象文件和权限做核对，再开放写入。

## 指标与用户反馈互相补充

崩溃率低不表示数据正确。后端指标正常也不表示按钮文案让用户理解。量化指标用于发现范围和趋势，客服与商店评价提供具体场景。两者用版本、时间和功能连接。评价数量突然下降也可能是应用打不开评价入口，不能只把减少当作改善。

每次扩大逐步发布前，同时看技术指标、业务结果和高严重度反馈。

每个版本保存兼容说明、数据库变更、最低支持版本、候选 build、测试轨道、逐步比例、监控基线和停止条件。异常时补时间线、影响、暂停动作、修复 build、数据补偿和用户沟通。恢复后加入复盘行动。

旧 API 和功能开关的删除日期进入待办，避免兼容代码永久累积。记录能让下一位维护者回答某个旧客户端为何仍被支持，也能证明一次发布为何继续或暂停。

## App 更新专题的掌握边界

读者需要理解客户端更新有传播延迟，旧客户端会长期存在，后端和数据库必须先兼容。还要能读取平台崩溃与 ANR、保留符号、设置逐步发布停止条件，并在后端停机时保持界面诚实。暂时不用建立大型可观测平台。一个小项目也应有版本日志、接口指标、状态公告和恢复演练。

商店显示最新版本只是发布状态。完整维护还要求新旧用户的数据都安全，故障能定位，修复能到达。
