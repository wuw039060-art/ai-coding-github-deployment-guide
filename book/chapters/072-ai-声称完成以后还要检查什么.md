# AI 声称完成以后还要检查什么

AI 说“已经完成”，最可靠的理解是它认为当前工作可以交付。这句话本身没有证明文件已经写入、程序能够构建、功能在真实环境可用、外部平台已经更新，也没有证明用户数据和权限安全。验收要把一句声明逐层还原成可检查事实。

检查深度与风险相称。改错别字可以看 Diff 和构建，修登录要增加权限与会话测试，数据库迁移要真实恢复与回滚，应用商店发布还需要账号后台状态。无法进入某个环境时，正确结论是“这部分尚未验证”，不能从本地成功向外推断。

## 先把“完成”拆成具体声明

“我已经修好 Bug”至少包含代码已修改、原问题不再发生、相邻行为没有回归和修改已保存。“我已经部署”还包含正确产物上传、目标环境更新、流量切换、健康检查与用户路径通过。“我已经备份”则需要文件完整、隔离存储和恢复测试。不同动词对应不同证据。

要求 AI 在结论中列出实际动作、文件、命令、结果、外部操作和未验证项。若它只说“应该可以”“通常会”“已配置好”，继续追问可观察证据。计划中提到的动作不等于已经执行，工具返回成功也不自动证明业务结果。

可以建立声明表，字段包括声明、证据、版本、环境、验证人和状态。状态使用已验证、部分验证、未验证、失败和不适用，避免用模糊绿色。每项未验证都写需要的条件，例如真实 Mac、开发者账号、生产维护窗口或用户确认。

AI 可能生成一个路径链接，却没有写入文件，或工具调用中途失败只留下半份内容。先打开目标文件，检查大小、结尾、编码、关键章节与资源引用。二进制、图片和 EPUB 不能只看文件名，使用对应查看器打开并检查结构。

代码文件要确认语法完整，配置要有正确层级，文档内部链接与附件路径要存在。生成多文件项目时，比较清单与实际目录，找缺失、重复和意外文件。不要在验收前运行批量清理，残留中间文件有时能说明失败发生在哪里。

若 AI 说“已安装 skill”或“已生成报告”，还要核对目标位置、入口文件、元数据与调用方式。安装目录存在不表示系统会发现它，报告能打开不表示引用与数据正确。每种交付物都需要自己的有效性检查。

## 检查 Diff 是否符合授权范围

Diff 展示版本控制文件的真实变化。先看文件列表、增删规模和二进制，再逐块审查。任务是改一处按钮，却出现锁文件、数据库迁移、CI、格式化数百行或删除测试，就需要解释。未跟踪文件不会总出现在普通 Diff 中，还要结合 `git status`。

每个块都应对应验收标准。检查条件、默认值、权限、错误处理、日志、数据迁移和旧版本兼容。AI 的摘要可能漏掉自己误改的部分，Diff 是更可靠入口。OpenAI 的代码审查资料和 GitHub PR Review 都支持把反馈绑定具体变化。

已有用户改动要单独识别。AI 不应回退、重写或格式化用户未提交内容。若任务开始时工作区已脏，交付报告说明哪些文件原本已变、哪些是本次变化，重叠部分如何处理。

测试报告要与当前提交或工作区匹配。AI 先运行测试，随后又修改代码，旧报告就不能证明最终状态。记录提交 SHA、构建号、命令、环境、开始结束时间和退出码。CI 页面核对 run 触发的提交，不只看分支名。

GitHub 状态检查可以把构建、测试、扫描与部署绑定提交，但官方资料也说明 skipped、neutral 等结论在依赖关系中可能按成功处理。打开每个必需作业，确认实际运行、目标矩阵和测试数量。取消、超时、排队、未匹配路径与缓存恢复都要分别理解。

测试结果包含通过、失败、跳过和警告。跳过可能是合理平台差异，也可能遗漏最关键用例。若本机没有浏览器、数据库、设备或秘密，测试框架可能自动跳过。交付报告应列出原因，不把总退出码为零写成“全部覆盖”。

## 检查测试是否能发现原问题

修 Bug 时，新测试应在未修版本失败，在修复版本通过。若从未确认失败，它可能测试了错误函数、错误环境或永远为真的断言。可以审查测试输入、预期与调用路径，再在安全分支短暂还原修复验证测试能力，具体做法不能破坏用户改动。

测试还要覆盖失败和边界。认证功能至少检查未登录、普通用户、资源所有者和越权；上传检查允许类型、超限、解析失败与存储错误；重试检查重复提交与未知结果。只验证演示数据容易让 AI 针对样例实现。

高层端到端测试通过时，也要保留低层单元与集成检查。端到端能证明一条用户路径，无法精确覆盖全部分支。低层测试全绿也不能证明路由、签名、部署和真实浏览器正常。选择组合，不迷信某一层。

源代码通过检查，构建仍可能因依赖、环境变量、平台签名与资源缺失失败。运行项目规定的生产构建，记录产物目录、大小、版本与哈希。确认部署使用的就是这份产物，没有在审批后重新构建。网页检查 HTML 引用的 JS、CSS 与图片是否存在，Source Map 与构建匹配；Docker 检查镜像摘要、入口、健康与非 root 运行；Flutter 检查 APK、AAB 或 Archive 的版本号、构建号和签名。没有对应平台条件时明确未验证。

构建警告需要分类。弃用、体积异常、签名、权限和未解析变量可能预示运行问题。不能因为退出码为零就全部忽略，也不需要为无关低风险警告扩大当前任务。记录影响与后续 Issue。

## 第一次通过以后再查两件事

第一次通过以后，先用相同版本和相同步骤再做一次，看看结果能否重复。然后根据风险选择干净环境、重启后的服务或新设备再试，检查成功是否依赖本机缓存、未提交文件、旧登录状态和临时补过的配置。很小的文案修改无需把所有测试都做一遍，数据迁移、签名和生产发布不能只保留第一次绿灯。

还要安排一次合理的失败路径。表单缺少必填项时是否给出清楚提示，令牌过期时是否回到登录，数据库暂时不可用时是否保留用户输入，部署失败时旧版本是否继续服务。失败测试不是为了证明系统永不出错，它用于确认错误能够被看见、影响受到限制、恢复入口仍然存在。

最后检查证据能否由另一人复核。测试结果绑定当前提交，截图能看见环境与版本，日志覆盖实际操作时间，外部控制台状态仍然可访问。若结论只能依赖执行者记忆，交付还没有形成可依赖的记录。

开发电脑可能残留未提交文件、全局依赖、缓存和旧构建，使当前项目“恰好能用”。在安全的新工作区或 CI 中从版本控制重新获取，按文档安装锁定依赖并构建，可以发现隐含条件。不要删除原工作区来制造干净环境。

重建前确认依赖下载和脚本的网络与执行权限。使用项目指定运行时和包管理器，核对锁文件。预期结果应同时包括命令成功、产物一致、测试数量合理和没有读取本机秘密。无法完全重建时，记录原因，例如私有依赖、已下线服务或缺少平台证书。这些条件属于项目维护风险。不要把本机缓存复制到交付物掩盖问题，应修复依赖来源或提供受控恢复方法。

## 检查真实用户路径

真实运行检查从用户入口开始，使用隔离账号与数据完成核心动作。记录页面、步骤、版本、时间、预期、实际、截图与请求编号。OpenAI 的 Computer Use QA 用例说明可以沿真实产品流程操作并记录问题。自动操作仍需人确认目标环境和数据影响。

页面显示成功后检查 Network、服务日志或测试数据，确认后端实际完成。刷新页面、退出重登或换设备验证持久化。错误路径看提示是否清楚、是否保留用户输入、能否安全重试。视觉变化在多尺寸、浅深色和键盘操作中检查。

真实路径不等于直接用生产用户。优先预览或内部测试，生产使用专用低风险账号和可清理数据。支付、发信、推送与删除设置沙箱或人工确认，避免验收本身造成真实副作用。

AI 说“保存成功”时，确认数据库记录、对象、缓存和索引是否一致。事务失败后有没有半成品，重试会不会重复。迁移后检查行数、约束、权限和旧版本读取。备份与恢复操作必须在隔离目标真实验证。

外部邮件、Webhook、对象存储、支付与推送也要查。测试环境是否误用生产凭据，消息发送次数和接收者是否正确，失败后任务怎样重试。数据库回滚不会撤回已发邮件，交付结论应列出这些副作用。

删除功能尤其要检查软删除、对象、缓存、搜索、备份和审计。AI 删除了界面入口，不代表数据已按政策删除；AI 执行了数据库删除，也不代表外部文件消失。数据负责人决定保留与恢复责任。

## 检查外部平台的真实状态

部署、DNS、云资源、GitHub、应用商店和邮件服务都在仓库之外。AI 可以生成配置或提交请求，但外部平台可能拒绝、排队、处理失败或等待审批。必须在官方控制台或 API 中核对目标账号、项目、区域、版本、状态和时间。

部署页面显示成功后，从外部网络访问域名，查看响应版本与核心功能。DNS 修改要等待传播并从权威与递归解析验证，不能只看控制台表单。商店上传成功后还要处理、测试与审核，状态与构建号缺一不可。

账号持有人保留凭据与最终按钮。若 AI 没有权限进入平台，结论写“配置草案已生成，尚未部署”。模拟截图、推断 UI 或把本地文件存在写成外部更新，都是不可接受的交付。

新增功能可能让普通用户访问管理员数据，工作流可能获得仓库写权限，容器可能改成 root，防火墙可能开放数据库。审查 Diff、部署配置和实际平台权限，比较修改前后。最小权限测试同时验证获准动作成功与未获准动作拒绝。

秘密不应进入代码、日志、构建产物、截图和 AI 对话。查看变量名、引用与平台注入，不打印完整值。发现秘密曾提交时先轮换，再处理历史；仅从当前 Diff 删除不够。依赖和第三方 Action 的权限也要查。一个小功能若新增维护不明的包、安装脚本或宽权限 GitHub App，风险可能超过收益。要求 AI 说明必要性、版本、来源、许可证与替代，再由维护者批准。

## 检查性能、容量和费用

功能正确却把页面从一秒变成十秒，或每次请求执行百次数据库查询，仍然没有完成。与修改前基线比较响应时间、CPU、内存、查询、包体、日志和网络。选择与用户目标相关的少量指标，不为小文案改动建立复杂压测。

上传、AI API、对象存储、日志和第三方服务会产生费用。验证限额、超时、重试和预算告警，避免错误循环无限调用。免费额度与价格属于高变化信息，使用官方当前页面并注明检索日期。性能测试写数据量、并发、机器、缓存与时间。单次最快结果没有代表性，生产规模无法模拟时明确限制。发现退化后决定优化、回退或接受，不用“在我电脑上很快”覆盖用户环境。

网页视觉通过后，使用键盘完成核心路径，检查焦点、标签、对比、缩放、错误提示与屏幕阅读器语义。图片有替代文字，表单错误与字段关联，不能只用颜色表达状态。移动端检查常见尺寸、方向、系统字体和权限拒绝。

Windows 路径大小写、macOS 签名、Linux 权限、Android 版本与 iOS 证书都可能造成平台差异。没有对应设备就列为未验证，安排持有设备的人复测。云模拟器与截图补充证据，无法完全代替商店构建和真实硬件。

OpenAI 的 QA 用例提供了操作路径示例，最终可访问性结论仍要使用项目标准、真实工具和人工体验。视觉 AI 可以发现明显问题，不能替代残障用户需求与语义检查。

## 检查错误和日志是否可行动

故意触发一个安全失败，确认用户看到可理解提示，日志有时间、版本、事件与请求编号。错误不能泄露调用栈、密码、内部路径和用户数据。后台失败要有告警与重试边界，不能静默吞掉。AI 常为“方便调试”增加大量日志，验收要查级别、保留、磁盘和隐私。临时日志在任务结束时删除或设置期限。生产最低需要版本、启动、关键失败与关联编号，详细用户正文不应记录。

日志本身也是外部运行证据。确认它来自当前实例与版本，时间和时区一致。找不到日志时先验证采集通道，不把空白直接解释为请求没发生。

实现者容易沿自己的成功路径验收。让另一位人或独立 AI 只读需求、Diff 与证据，寻找未覆盖输入、权限扩大、错误回退、版本错配和环境差异。OpenAI 代码审查资料可辅助定位变更风险，结论仍需绑定具体代码和可复现结果。

独立评审不能只问“有没有问题”，应给明确任务，例如“找出能让普通用户读取他人记录的路径”“检查测试是否真的运行”“验证生产产物与批准提交一致”。评审意见按严重度、证据与复现整理，误报也记录为什么排除。

GitHub PR Review 允许评论、批准和请求修改，仓库规则决定这些状态是否阻止合并。高风险修改结合代码所有者、必需检查和部署审批，不让实施者单独批准自己触发的生产发布。

## 一个“已修复上传”的验收例子

AI 报告已把上传上限从一兆改到五兆，测试通过。验收先看 Diff，发现只改了前端提示，代理仍限制一兆；所谓测试只调用前端校验，没有发送真实请求。声明在文件层成立，在运行层失败。修正计划同时处理代理与应用边界，增加五兆以内成功、超过五兆拒绝和解析失败测试。Preview 中上传两兆图片，Network 返回 201，服务日志有请求编号，对象存储出现私有对象，刷新后头像仍在；六兆请求返回安全提示且没有留下对象。

最后检查生产配置是否采用同一模板、上传凭据是否最小、日志是否含文件内容、回滚怎样恢复旧上限。账号持有人尚未批准生产，因此最终报告写“Preview 已验证，生产未部署”。这比一句“全部完成”更准确，也让下一步清楚。

开头给出结果与范围，随后列文件、外部变化、测试与真实路径，最后列未验证、风险和回滚。每项证据附版本、环境和链接。失败也应报告，不能为了显得顺利隐藏红色结果。下面模板可以用于 AI 自检和人工验收。字段使用冒号便于复制。

```
完成的需求：
实际修改文件：
外部系统变化：
提交或构建标识：
运行的检查与测试：
通过、失败和跳过：
真实用户路径结果：
数据与副作用结果：
权限与秘密检查：
性能与费用观察：
回滚状态：
未验证内容及原因：
需要用户确认的下一步：
```

NIST 的生成式 AI 风险资料建议记录模型知识边界，并用已知事实、多种评估、自动检查与人工监督验证输出。交付报告正是把这些原则落到工程工作中，避免由 AI 的自然语言流畅度替代事实。

## 不同交付物要用不同验收办法

代码库交付检查 Diff、测试、构建、依赖与运行。部署交付增加平台状态、版本、域名、监控和回滚。数据库交付增加 schema、数据校验、备份恢复与权限。文档交付检查结构、链接、事实来源、版本、可执行步骤和渲染。

EPUB、PDF 和网站要实际打开。EPUB 看导航、内部链接、图片、代码块、中文换行和阅读器兼容。PDF 看分页、字体嵌入、目录、链接和图片清晰度。网站看不同尺寸、Network、Console 和关键交互。源 Markdown 正确，不能证明最终渲染也正确。

图片交付要打开看分辨率、构图、文字和来源，SVG 还要验证 XML、标题和阅读器兼容。表格交付检查公式、数据类型、筛选和实际值。安装包要真实安装、启动、升级和卸载，不能只看文件生成。

Mock、Fake 和 Stub 能让测试快速稳定，也可能保护一个不存在的环境。记录哪些边界使用替身，定期用受控真实集成验证契约。数据库内存替身与生产 PostgreSQL 在事务、类型、锁和 SQL 上可能不同。对象存储替身也不会完全复制权限、签名链接和配额。

## 升级、清理和来源也要查

新安装验证下载、权限、首次启动和默认数据；升级验证旧数据、旧配置、缓存与登录状态；卸载验证用户知道哪些数据会保留。网页部署也有升级问题。Service Worker、CDN 与浏览器缓存可能让旧资源和新 API 混用，只用无痕新窗口会漏掉老用户状态。

任务完成后查看未跟踪文件、缓存、下载、日志、临时服务器和后台进程。可重建缓存可以按项目规则清理，用户数据、备份、当前发布、签名和不确定文件保留。先做清单，不把“清理”变成广泛删除。

证据也要能保存和复查。链接是否可访问，日志是否对应当前时间，截图是否能看清版本，报告是否遗漏失败，哈希是否匹配，都需要抽查。敏感原始材料与脱敏副本分开，访问、保留和删除都有期限。

AI 生成的代码、字体、图片、数据和依赖也要看来源和许可。无法确认来源的资产先不用，选择官方、原创或明确授权替代。新增依赖记录名称、版本、许可证、维护状态和用途。具体法律判断由合格人员负责。

最后回到用户目标。让目标用户或代表者完成一次任务，观察是否真的更快、更清楚或更可靠。技术测试全绿，流程仍可能难以理解。最终交付把用户结果放在第一段，技术证据随后。

## 本章最终检查

- 已把“完成”拆成文件、行为、外部状态和风险声明。
- 目标文件与资源真实存在、完整且可打开。
- Diff 与未跟踪文件都在授权范围。
- 测试绑定最终提交，记录失败、跳过和警告。
- 新测试在修复前能复现原问题。
- 生产构建产物有版本、构建号或摘要。
- 干净环境能按文档重建，或明确缺少条件。
- 真实用户路径验证界面、Network、日志与数据。
- 外部平台由账号持有人核对真实状态。
- 权限、秘密、依赖、性能、费用和可访问性经过检查。
- 独立评审尝试推翻关键结论。
- 报告清楚列出未验证内容与下一步。

AI 的“已完成”是一项待验收声明。文件、Diff、测试、运行、数据、外部平台和人工判断逐层增加可信度。某层缺失时坦率标注，项目和用户才不会被一句流畅的完成报告带偏。
