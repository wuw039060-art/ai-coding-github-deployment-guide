# 更新、回滚、清理与数据丢失风险

容器更新通常不是进入旧容器安装新版本。正确方向是取得新镜像，创建新容器，验证后替换旧容器。可回滚的关键在于旧镜像仍可取得、卷数据与两版兼容、配置有记录。清理的关键在于先区分镜像、容器、卷、网络、日志和构建缓存。

最危险的误解是“unused 表示没用”。Docker 只能判断当前是否被对象引用，不知道一个停止容器或未挂载卷是否承载重要数据。

## 更新前建立版本与数据清单

运行 `docker compose config` 保存脱敏最终配置。运行 `docker compose images` 或 inspect 记录当前镜像和摘要。运行 `docker compose ps --all` 记录容器状态、端口和创建时间。列出命名卷、Bind Mount 和外部数据库。确认数据库备份和上传文件备份能恢复。记录当前健康与业务测试。

没有这份起点，更新失败时只知道“旧版之前能用”，却找不到旧镜像和数据状态。

```
docker compose pull
```

它拉取配置中引用的远程镜像，不启动也不替换容器。Docker CLI 参考明确说明 pull 只取得镜像。标签指向新内容时，本地会得到新摘要。正在运行的容器继续使用创建时的旧镜像。先检查拉取结果和摘要，再执行 `up -d`。不要因为 Registry 出现新版本就认为生产已更新。

生产配置优先使用明确版本或摘要，避免 `latest` 无法说明变化。

## 构建型服务的更新

服务使用 `build` 时，先在 CI 或服务器受控目录执行构建。

```
docker compose build web
```

构建成功后运行镜像测试，再用 `up -d web` 重建。Docker 官方 Compose 生产指南给出按服务构建与重建路径。在小内存生产机构建可能影响在线容器。优先在 CI 生成镜像并推送注册表。

构建日志与产物摘要进入发布记录。

## up -d 怎样应用更新

```
docker compose up -d web
```

Compose 比较配置和镜像，必要时停止并移除旧容器，再创建新容器。命名卷会重新挂载。单容器替换通常有短暂中断。反向代理可能在此期间返回 502。高风险业务要使用并行版本和切换策略。

执行后检查容器创建时间、镜像、健康、日志和业务。命令完成不等于应用迁移完成。数据库容器更新更谨慎，先读数据库镜像的大版本升级说明，不能只改标签。

`docker compose restart web` 停止再启动同一个容器。它保留当前可写层和创建时配置。`docker compose up -d web` 可以按新镜像和配置重建容器。旧可写层会丢弃，持久卷重新挂载。改了 `.env`、端口、卷或镜像，只 restart 往往不会生效。使用 `config` 与 inspect 比较。

重建后数据消失，说明数据原先落在容器层或挂错卷，不能把重建视为故障根因。

## 回滚镜像

Compose 文件把镜像从 `1.1.0` 改回已验证 `1.0.0` 或对应摘要，先运行 `config`，再 `up -d` 重建。Registry 中旧镜像必须仍可拉取。清理本地旧镜像前确认注册表和权限。回滚后验证卷数据格式。新版本完成不可逆数据库迁移时，旧代码可能无法运行。

应用版本和数据库迁移共同进入回滚计划。不能只保留镜像。

compose.yaml、生产覆盖文件和非秘密配置进入 Git。回滚到对应提交，检查最终合并配置。秘密版本不进入 Git，但要记录变量名、轮换和兼容范围。旧代码不能要求已撤销的泄露密钥。

主机防火墙、Caddy 和系统 Docker 配置也可能随发布变化，分别保留版本与回滚。一次只恢复必要部分。全盘覆盖服务器会破坏事故后的新数据和证据。

## 数据库镜像不能跨大版本直接替换

PostgreSQL、MySQL 等数据库的数据目录格式会随大版本变化。只改镜像标签并挂同一卷，可能启动失败或损坏流程。遵循数据库官方升级方式，可能需要逻辑导出导入、专用升级工具或复制。先在卷备份的隔离副本演练。

不要让标签 `latest` 自动跨大版本。固定验证版本，并订阅维护和安全公告。回滚数据库比应用更复杂。迁移方案要先确定向后兼容和恢复点。

开发环境绑定源代码，Git 切换分支会让运行容器立即看到变化。生产不应依赖这种隐式发布。数据库使用绑定目录时，容器内删除会直接删除主机数据。备份工具和主机权限都要保护。迁移到新服务器前创建目录和正确 UID。空路径挂入可能遮住镜像内容或让应用初始化新空数据库。

更新后检查 `Mounts` 的源与目标，不能只看容器运行。

## 安全清理从 docker system df 开始

```
docker system df
```

命令只读，按镜像、容器、卷和构建缓存显示占用与可回收估计。可回收只是 Docker 当前引用判断。下一步分别列出对象、标签、创建时间和项目归属。磁盘紧急时先停止日志风暴。清理缓存和无用镜像，卷放在最后独立确认。

不要直接运行带 `--volumes` 的全局 prune。

停止容器保留可写层和元数据，便于再次启动和调查。`docker ps` 默认不显示它们，使用 `docker ps -a`。确认容器属于过期测试、数据已迁移、日志已保存后，才删除精确名称。`docker container prune` 会删除所有符合条件的停止容器。Docker 官方清理文档提供时间与标签过滤。

生产主机优先逐项删除，不使用 `--force` 跳过确认。

## 镜像清理

悬空镜像没有标签且没有容器引用，常来自重复构建。删除通常风险较低，仍要确认不是未记录回滚材料。`docker image prune -a` 会扩大到所有未被现有容器使用的镜像，包括你打算稍后回滚的版本。先确认旧镜像已推送注册表，摘要和拉取权限有效。再按时间或标签筛选。

删除后需要重新下载会增加恢复时间。磁盘与恢复目标共同决定保留数量。

## 卷清理是最高风险项

Volume 未被容器挂载时会被 Docker 判为 unused。它可能是刚停止的数据库、迁移备份或等待恢复的数据。`docker volume prune` 会删除未使用卷。Docker 文档明确说卷不会自动删除，因为可能破坏数据。

逐个 inspect 卷，查标签、项目、创建时间和备份。临时挂载到只读检查容器时也不要修改。没有可靠归属的卷先打标签、记录并等待，不在磁盘压力下猜测删除。

`docker compose down` 默认删除项目容器和网络，保留命名卷。

```
docker compose down --volumes
```

这条命令会删除项目声明的命名卷和匿名卷，数据库可能永久丢失。本书只用文本展示风险，不作为执行步骤。教程为了重置练习环境可能使用它。生产环境不能照抄。先导出数据、验证恢复，再对精确测试项目清理。

## 构建缓存清理

BuildKit 缓存能加速重建，也会占用磁盘。它不应包含业务数据，但可能包含构建秘密泄露后的残留。用 `docker buildx du` 或系统占用查看当前构建器。清理后下一次构建更慢。多个 builder 各有缓存，确认目标。不要在发布过程中同时清理，构建可能受影响。

构建秘密使用正确挂载机制，不能依靠之后清缓存保证安全。

容器日志由日志驱动管理。删除镜像或缓存不能解决仍在运行容器的无限日志。配置日志轮转，修复错误循环。修改 daemon 默认驱动只影响新容器，需要计划重建。直接删除 Docker 内部日志文件可能破坏状态。使用官方驱动配置和受控轮转。

主机磁盘监控必须覆盖 Docker 数据目录。

## 更新过程中的数据写入

单容器重建时，用户请求可能失败。数据库仍运行，旧请求和新容器启动可能重叠。反向代理进入维护模式或使用两个应用容器，按业务风险选择。新旧版本必须兼容同一数据库。后台任务可能重复启动。调度者要有唯一锁和幂等处理。

记录切换时间，出现数据问题时能找出期间写入。

Docker 服务开机启动不等于 Compose 项目全部恢复。容器要配置适当 restart 策略。安排测试重启，确认命名卷挂载、网络、代理、健康和业务。管理员手工 stop 的容器在 `unless-stopped` 下可能不自动回来。

外部数据库和对象存储也要验证连接。DNS 与证书不由容器重启策略处理。把重启恢复时间写进运行手册。

## 一次安全更新演练

测试环境运行版本 A，先创建几条带明显前缀的练习数据并导出备份。记录 A 的镜像摘要、Compose 配置、卷名和数据查询结果。版本标识使用不可变标签或摘要，不使用会移动的 `latest`。

拉取或构建版本 B，先查看磁盘空间，再让 Compose 重建 Web。检查容器创建时间、镜像摘要、健康状态、启动日志、外部请求和原有数据。随后只在隔离环境让 B 的应用配置失效，确认监控能够发现，再把配置与镜像明确恢复到 A 并重建。恢复后重复同一条数据查询，确认用户入口仍能读取原记录。

备份恢复另开新卷演练，不能覆盖刚才仍可使用的数据卷。恢复后比较记录数量、代表性内容和应用读取结果。最后列出过期容器、镜像、缓存与练习卷，只处理能准确确认的练习对象。卷删除与普通镜像清理分开审批，不把它藏在一条综合清理命令里。

Compose 字段和 Engine 行为有最低版本。开发机支持的新功能，旧服务器可能解析失败或忽略。记录 `docker version` 与 `docker compose version`。查看发行说明和弃用，不在应用发布同一窗口顺便升级 Engine。Docker Engine 更新会影响全主机容器、网络和存储。先测试、备份 daemon 配置并准备控制台。

应用镜像更新与平台更新分开，失败原因更容易定位。

## Docker Engine 升级后的验收

检查 `docker.service`、daemon 日志、容器状态、网络、卷和日志驱动。确认 restart 策略使服务恢复。从外部验证 HTTPS 和业务，测试一次新容器创建与删除。只看已有容器继续运行可能漏掉创建路径故障。

Docker 的 live restore 能在部分 daemon 升级期间保持容器运行，网络和交互仍有边界，不能等同于零影响。升级记录保存旧新版本、重启时间和异常。

拉取新镜像时，旧镜像仍被运行容器引用。主机需要同时容纳两版镜像和临时下载层。磁盘只剩很少空间时直接 pull，可能中途失败并影响其他写入。发布前用 `docker system df` 与 `df -h` 估算。先清理明确缓存或扩大磁盘，不能删除当前卷腾空间。保留旧镜像直到观察期结束。

多架构镜像通常只拉取当前平台内容，仍要看实际大小。

## 镜像拉取失败

常见原因包括 Registry 认证、网络、标签不存在、架构不支持和磁盘不足。保存完整错误。确认登录的是正确 Registry，仓库路径和标签准确。查看服务商状态和令牌权限。不要改用来源不明的同名镜像。临时从另一 Registry 复制时要核对摘要和签名。

拉取失败不会自动替换正在运行容器。保持旧版，修复分发路径再发布。

团队用 `stable` 标签指向当前版本。两周后 stable 更新，服务器执行 pull。事故时再用 stable 回滚，得到的仍是新内容。每次发布保存摘要，并给不可重复使用的版本标签。Registry 禁止覆盖发布标签更稳妥。

Compose 可以按摘要引用镜像。易读标签保留给人看，摘要用于机器确认。回滚演练从 Registry 再拉一次，证明远程材料存在。

## 迁移任务只运行一次

应用更新可能带数据库迁移。把迁移写进每个 Web 容器启动，会在重启或扩容时重复执行。使用独立一次性 Compose service 或发布步骤，记录迁移版本和退出码。操作需要幂等或明确锁。

迁移前备份与恢复测试。失败后不要让 Web 容器继续启动到未知结构。回滚代码前核对迁移是否向后兼容。

旧容器停止时可能正在发邮件、生成报告或处理队列。强制停止会留下半完成状态。应用接收停止信号后停止取新任务，完成或安全归还当前任务。设置足够停止超时。新容器启动前确认调度锁，避免两版重复处理。任务使用幂等键。

发布验收查看队列积压和最近任务，不只请求首页。

## 反向代理与容器更新

主机 Caddy 指向固定本机端口时，容器重建会产生短暂断开。代理日志可能出现 502。低风险项目安排短窗口。更高要求可同时启动新版在另一个端口，验收后切代理。切换配置先验证，reload 后检查新旧请求。旧容器保留但停止写入，观察完成再删除。

数据库兼容仍是蓝绿发布前提。

旧容器保留时，看起来可以直接 start 回滚。它的可写层可能含临时修补、过期环境或已改变状态。更可靠的方法是从旧镜像摘要重新创建，挂同一兼容卷和对应配置。保留旧容器可用于取日志和比较，不能替代可重建发布。

回滚测试删除旧容器后仍能恢复，才证明材料完整。

## 卷备份的停写窗口

数据库 Volume 备份前按数据库工具取得一致状态。普通文件若持续写入，压缩过程可能得到混合时间点。短期进入只读或暂停写入，记录开始结束。备份完成校验后再恢复业务。无法停写的项目使用支持快照和持续归档的存储与数据库方案。

备份影响用户时提前通知，不能在高峰临时冻结。

创建名字带 `restore-test` 的新卷。使用与生产兼容的工具容器或数据库镜像恢复。启动独立测试数据库和应用，不发布公网端口。检查结构、数量、权限和关键业务。记录恢复时间和错误。完成后保留报告，确认无真实用户需要访问，再删除测试资源。

任何恢复命令的目标卷都要精确确认，不能覆盖生产卷。

## 匿名资源和 orphan

Compose 文件删除某个服务后，旧容器可能成为 orphan。`up` 会提示，`--remove-orphans` 可删除。先确认它是否属于已废弃服务，是否含独有数据和日志。提示不是自动删除许可。匿名卷可能随 orphan 留下。查挂载和标签，按数据流程处理。

配置重构前记录旧服务名，新旧对应能避免误清理。

默认 system prune 处理停止容器、未使用网络、悬空镜像和构建缓存。它默认不清理卷。加入 `-a` 扩大镜像范围，加入 `--volumes` 加入未使用卷。组合后的影响很大。生产服务器不用它作为定时任务。按对象类型设置保留与标签，逐项预览。

Docker 官方清理页面会显示确认警告，不能用 `-f` 跳过审阅。

## 定时清理为什么危险

夜间脚本只根据 unused 删除，可能刚好遇到维护中停止的数据库。脚本不知道明早还要启动。安全自动化只清理明确标记、超过期限、可从 Registry 重建的对象。卷不纳入自动删除。脚本先输出候选报告，负责人审阅后执行。保留对象和释放空间日志。

磁盘阈值触发时通知，不直接扩大删除范围。

构建缓存最容易重建，代价是下次构建更慢。远程 Registry 有副本的旧镜像也可重拉。停止容器的可写层可能含调查证据，需要确认。日志受保留与隐私要求影响。Volume 和 Bind Mount 数据最难重建，最后处理并要求备份与业务确认。

排序来自恢复代价，不能只看占用大小。

## 数据删除后的验收

删除操作完成后再次运行 `docker system df` 和 `df -h`，记录释放空间。运行 `docker compose ps`、健康和业务测试，确认没有误删依赖。检查备份任务和 Registry 拉取。若空间没有释放，可能有已删除但仍打开的日志、Docker Desktop 虚拟磁盘或其他主机目录。

不要因为结果不符就继续删除。回到分层检查。

先停止外部流量和后台任务，导出数据并验证备份。记录镜像、配置和卷。执行普通 `docker compose down` 移除容器和网络，保留卷观察。撤销域名、代理、凭据和监控。观察期结束后对卷做最终备份与删除审批，再删除精确卷和旧镜像。

检查云磁盘与账单。容器删除不会删除 VPS 和外部数据库。

## 更新报告模板

写旧新镜像摘要、Compose 提交、数据库迁移、卷与备份、开始结束时间。保存 pull 或 build、config、ps、健康、日志和业务验收。内容脱敏。失败时写回滚摘要、数据处理和用户影响。清理写删除对象与恢复来源。

报告让下一次更新能复用证据，不依赖管理员终端历史。

发布前一天先在副本环境恢复最近备份，使用新镜像执行迁移。记录迁移用时、磁盘增长和是否能回退。若迁移会删除字段或重写大量数据，应准备应用与数据库共同回退方案，不能只保留旧镜像。窗口开始后暂停会冲突的后台任务，并向用户说明影响。再次生成备份，记录旧镜像摘要、Compose 提交与数据库版本。没有这些基线，失败后很难知道要回到哪里。

先拉取或构建新镜像，避免停机后才等待大文件下载。使用 `docker compose config` 检查最终配置，再运行迁移。迁移完成后更新应用容器，观察启动日志与健康。验收至少覆盖登录、读取一条旧数据、写入一条新数据、后台任务和文件访问。随后观察错误率与资源，不要在首页能打开后立即清理旧版本。

若失败，先判断新版本是否已经写入不可逆数据。可以安全回退时使用记录的旧摘要和旧配置重建。数据库已经发生不兼容变化时，按预演的恢复方案处理，不能反复启动新旧程序碰运气。观察期结束后再清理明确可重建的缓存与旧镜像。最近可回滚镜像、备份和迁移日志应按保留策略保存。

## 空间告警发生时的止损顺序

先停止产生海量日志或临时文件的故障服务，避免磁盘继续下降。读取 `df -h` 与 `docker system df`，分清主机文件系统、镜像、构建缓存、容器和卷各占多少。构建缓存和可以从可信 Registry 重新拉取的未用镜像通常最容易恢复，可以优先精确清理。停止容器是否可删，要看它的可写层是否含调查证据。

卷不因“看起来未使用”就安全。Compose 项目改名、容器暂时移除或恢复演练都可能留下没有当前引用的业务卷。清理前核对标签、创建时间、大小、备份和业务所有者；释放空间以后修复根因；若根因是无限日志，配置轮转与告警；若根因是备份堆积，调整保留和外送；只执行一次 prune，问题还会回来。
