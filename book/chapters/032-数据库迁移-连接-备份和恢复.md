# 数据库迁移、连接、备份和恢复

数据库一旦保存真实用户数据，改变结构就不能像改一份空白表格。新代码、旧代码、现有数据、备份和恢复步骤必须协调。迁移记录改变，备份保留过去，恢复验证两者在事故时真的可用。本章不提供可直接粘贴到生产的删除和恢复命令。所有示例只在本地练习数据库或一次性恢复环境使用，执行者先确认目标名称与备份。

## Schema 是数据结构

Schema 在本章指表、列、类型、约束、索引、视图和权限等结构。它回答数据库允许保存什么。代码从 `users.display_name` 读取，数据库删掉该列，运行时就会失败。数据库新增必填列，旧代码写入时也可能失败。结构与代码是同一个发布的一部分。只在控制台手工改表而不留记录，下一套环境无法重现。

迁移文件按顺序描述结构变化，让本地、测试、预览和生产执行相同步骤。

迁移通常保存结构变化和必要数据转换，不保存全部业务数据。创建表、增加列、回填字段和建立索引都可成为迁移。备份保存某个时间的数据与结构，用于恢复。两者用途不同。只有迁移，没有备份，误删用户数据无法找回。只有备份，没有迁移记录，新版本部署过程难以审查和重建。

Supabase 的迁移指南使用版本化 SQL 文件描述数据库变化，并提供本地到远程的工作流。具体 CLI 会变，原则可迁移到其他工具。

## 一次安全的增加列

假设资料表要增加 `timezone`。直接新增非空列并要求所有旧行都有值，可能失败或长时间锁表。可分阶段进行。先增加允许为空的列，部署能读写新列且能处理空值的代码。随后分批回填旧数据，再增加默认值与约束。

确认所有活跃代码已兼容后，才移除过渡逻辑。每个阶段都可观察，回退范围更清楚。表很小时步骤可以简化，仍要在测试副本验证。生产数据量与锁行为不能只凭开发库推断。

把 `name` 改成 `display_name`，直接重命名会让旧代码失效。可先增加新列，代码双写或使用兼容视图，回填后逐步切读。双写期间要定义失败处理，不能一个字段成功另一个失败却悄悄继续。尽量在同一数据库事务内完成。确认旧版本和后台任务不再读取旧列后，再做删除迁移。移动 App 可能长时间保留旧 API，后端兼容期更长。

迁移记录说明何时停止兼容和如何验证调用量。

## 删除是高风险操作

删除列、表和数据会让恢复依赖备份。命令执行前确认目标环境、影响行数、依赖和备份可恢复。先在副本运行只读查询，列出会受影响对象；搜索代码、报表、任务和外部集成是否引用；重要删除采用延迟策略；先停止写入并隐藏使用，观察一段时间，再删除结构；期间保留导出或归档。

生产操作由有权限和责任的人执行，使用变更窗口与第二人复核。本书示例不鼓励读者在生产终端练习。

结构迁移改变列和约束，数据迁移转换现有内容。将完整地址拆成省、市和详细地址，就需要解析旧数据。真实数据常有异常格式。先统计分布，设计无法解析的处理，不强行猜。数据转换写入批次、进度和错误记录，支持暂停与重跑。重跑不能重复扣减或重复创建。

完成后对比迁移前后行数、空值、唯一性和抽样业务。只看脚本退出成功不够。

## 数据库连接包含什么

应用连接数据库需要主机、端口、数据库名、用户、密码和 TLS 等信息，常组合为连接字符串。连接字符串是秘密，不进入前端、仓库和公开日志。平台环境变量只把值交给后端运行环境。数据库用户使用最小权限。应用账号不必拥有创建角色、删除数据库和读取所有 Schema 的能力。

迁移账号可能需要更高结构权限，和应用运行账号分开。迁移完成后不把高权限凭据留在普通服务。

创建数据库连接有成本。连接池维持一组连接，让请求复用。每个应用实例都开过多连接，会超过数据库上限。无服务器函数并发启动时问题更明显。设置池大小要根据数据库上限、实例数和管理连接计算，不直接照抄高数值。

连接泄漏表现为一段时间后新请求等待。日志记录池使用量与超时，代码保证请求结束归还连接。

## 超时与事务

连接超时说明无法及时建立连接，查询超时说明语句运行过久，锁等待又是另一类原因。设置超时可以阻止请求永久占用资源，也可能中断合法大任务。按业务路径区分交互请求与后台任务。事务保持越久，锁和连接占用越久。不要在事务内等待用户输入或慢外部 API。

发生超时后，先确认事务是否已提交。客户端提示失败不等于数据库没有写入，幂等检查仍重要。

备份什么，保存到哪里，多久能恢复。只有第一项，仍不足以面对事故。PostgreSQL 官方把 SQL Dump、文件系统级备份和连续归档列为三类方法，各有适用条件。个人项目可以从托管平台自动备份与定期逻辑导出开始。重要系统还要按恢复时间和恢复点目标设计。

备份存储与生产账号完全相同，账号被盗时可能一起被删。使用独立权限、保留策略和必要加密。

## RPO 与 RTO

RPO 表示可接受丢失多少时间的数据。例如 RPO 一小时，最坏可丢最后一小时写入。RTO 表示服务需要在多久内恢复。例如 RTO 四小时，团队和工具要能在四小时内完成恢复与验收。每天备份一次无法提供五分钟 RPO。一个十小时才能下载和恢复的备份也无法满足一小时 RTO。

先从业务影响制定现实目标，再选择频率、连续归档和人员安排。

`pg_dump` 导出单个 PostgreSQL 数据库，可生成 SQL 脚本或归档格式。官方说明它能在数据库并发使用时创建一致导出，并且不会阻止普通读写。它不自动覆盖整个集群角色和所有全局对象。大型生产数据库的常规备份也不应只凭一条 `pg_dump` 命令决定。

下面只展示在本地练习数据库中导出自定义格式的形状，数据库名为虚构值。

```
pg_dump --format=custom --file=practice.dump practice_db
```

运行位置是安装了匹配 PostgreSQL 客户端的本地终端，目标只能是自己创建的 `practice_db`。成功时生成 `practice.dump`，并应检查命令退出状态和警告。该文件可能包含敏感数据，按秘密备份保护。不要上传 GitHub。

## 恢复才是备份验收

文件存在、大小不为零和备份任务绿色，都不能证明可恢复。要在隔离环境实际恢复；创建与生产分开的测试数据库，使用匹配工具恢复；检查结构、关键表行数、约束、权限和应用烟雾测试；恢复工具可能执行导出中包含的 SQL。PostgreSQL 官方警告，从不可信超级用户来源恢复可能执行任意代码。不接收陌生备份直接恢复到受信环境。

记录恢复耗时、错误和人工步骤。超过 RTO 时，改进流程或调整承诺。

SQLite 数据库是文件，应用正在写入时普通文件复制可能得到不一致快照，尤其还存在 WAL 等相关文件。SQLite 提供在线备份 API，把正在使用的数据库复制到另一个数据库文件。具体应用应使用框架或工具支持的安全备份方式。

备份后在另一目录打开，运行完整性检查和应用读取。不要用原文件验证后宣称备份可用。移动 App 的本地 SQLite 还要考虑设备备份、加密和用户隐私。服务端数据库备份不能覆盖设备尚未同步的数据。

## 托管平台备份要问什么

自动备份频率、保留天数、区域、加密、时间点恢复、导出能力和恢复权限。价格与计划限制按当前官方页面确认。“每天备份”还要问时间、失败通知和最近一次成功。保留七天不等于七个可用恢复点。

恢复是覆盖现有实例、创建新实例，还是提供下载，影响风险。优先恢复到新实例后验证，再计划切换。离开供应商前测试标准导出。平台快照若只能在原账号恢复，不是完整退出方案。

使用专用测试项目和虚构数据。先创建三张表、约束和少量记录，记录预期行数与校验值。按选定方法备份，随后恢复到另一个全新数据库。不要覆盖源库。让测试应用连接恢复库，完成读取、创建、更新和约束失败检查。检查时区、序列和用户权限。

删除一条测试记录，确认是否能从目标恢复点找回。完成后保留报告，安全清理练习凭据与副本。

## 迁移失败如何处理

先停止继续部署，保存错误和迁移版本。确认事务是否自动回滚，数据库现在处于哪一步。不要立即重复运行未知是否幂等的迁移。检查已创建对象和已转换批次。若应用与数据库不兼容，限制流量或恢复旧应用，但先确认旧应用能读当前结构。

修复迁移作为新版本记录，不随意修改已经在其他环境执行过的历史文件。团队工具规则若不同，以其文档为准。

备份一直成功，恢复时报角色不存在，说明未记录全局对象或权限。补充恢复前置步骤。迁移在小测试库秒过，生产锁表很久，说明没有按真实数据量演练。考虑分阶段和并发索引能力。应用部署回滚后仍 500，检查数据库迁移没有回滚。不要连续切换应用版本。

连接偶尔耗尽，统计实例数乘每实例池大小，再看泄漏与慢事务。

## 迁移文件命名与顺序

迁移常用时间戳或递增编号排序，并附简短动作名称。名称例如增加用户时区，能帮助审查。一旦迁移在共享环境执行，不随意改写历史。新增修复迁移，让每个环境沿同一路径前进。分支各自创建迁移时可能发生顺序冲突。合并前检查最终排序，并从空数据库完整执行。

迁移表记录已执行版本。不要手工把记录标成成功来绕过失败。

控制台手工改表却没有迁移，生产结构会与仓库不一致，这叫结构漂移。定期导出或比较实际 Schema 与迁移结果。发现差异先确认来源，再生成准确迁移或恢复预期状态。不要直接让自动同步删除生产中“多余”对象。它可能是未记录但仍被使用的表。

变更权限与函数也属于 Schema 管理，不只比较列。

## 展开与收缩迁移

展开阶段增加新结构，同时保持旧代码可用。部署兼容代码并迁移数据。收缩阶段才删除旧结构。这种 Expand and Contract 方法适合零停机发布和移动客户端兼容。每阶段有独立验证与停止点。失败时能留在兼容状态，而非必须立刻反向删除。

完成收缩前监控旧字段或端点调用，确认后台任务和旧 App 已停止使用。

大表创建索引可能耗时、占磁盘并阻塞写入。PostgreSQL 提供降低阻塞的并发方式，也有失败后残留处理。具体命令需要 DBA 按当前版本确认。本书不提供可直接用于生产的大表命令。先在接近真实数据量的副本测时间和空间。生产监控锁、CPU、I/O 与复制延迟。

创建后查看查询计划，确认目标查询实际使用。无用索引仍增加写入成本。

## 备份加密与密钥

备份常包含全量用户数据，敏感度可能高于单次查询。传输和静态存储都要加密。加密密钥与备份分开管理。密钥丢失会让备份永久不可读，权限过宽又会扩大泄露。轮换密钥时确认旧备份仍可按保留期解密。恢复演练使用受控访问并留下审计。

下载到个人电脑的临时备份要有明确清理和磁盘保护，不能长期留在 Downloads。

保留策略可包含每日、每周和每月恢复点。旧备份逐步过期，避免无限增长。删除备份前确认法律、合同、调查和用户删除要求。保留更多不总是更安全。不可变或对象锁能降低勒索与误删风险，也会阻止提前删除。启用前理解费用和合规。

每次生命周期规则变更都要评审，防止把保留天数误写成小时。

## 异地与独立账号

生产和备份在同一磁盘，磁盘故障会一起丢。仅有云平台快照，账号被删除也可能一起消失。重要数据保留至少一份受独立权限保护的副本，必要时在不同区域或供应商。跨地区存储涉及数据驻留和传输费用。先确认允许位置。

独立不等于无人管理。备份账号也开启 MFA、告警和联系人恢复。

全量备份保存完整数据，恢复简单，时间与空间较大。增量保存变化，恢复依赖一条备份链。PostgreSQL 连续归档记录 WAL，可恢复到某个时间点。配置、监控和存储要求更高。

个人项目先确保基础全量或逻辑备份可恢复，再按 RPO 需要增加连续方案。任何方案都记录最后成功时间和链完整性。某一天增量缺失可能让后续恢复点无效。

## Point-in-Time Recovery

时间点恢复允许把数据库恢复到误操作之前。例如下午三点误删，可恢复到两点五十九分。恢复结果通常创建新实例或新时间线。恢复后到事故发生期间的合法写入需要另行合并。先停止相关写入，记录误操作时间和时区。日志、监控和审计帮助选择恢复点。

不要直接让恢复实例覆盖原生产。先验证，再计划流量和差异数据处理。

监控任务是否开始、完成、大小是否异常、保存位置是否可访问。零字节和突然缩小需要调查。成功率指标配合定期恢复。备份连续一百次成功却从未恢复，仍缺关键证据。失败告警要有人接收和升级。假期中无人处理，自动化没有完成责任链。

每月抽查最新恢复点，每季度做完整应用恢复，频率按业务风险调整。

## 恢复权限

备份操作可由只读导出账号执行，恢复通常需要创建对象和写数据的高权限。高权限凭据不放在日常应用。恢复时按审批临时取得，完成后撤销。恢复目标环境网络隔离，避免测试恢复实例向真实用户发送邮件和推送。

将外部服务切为沙盒或禁用后台任务，再启动应用验收。

检查表数与关键行数只是开始。还要检查外键、序列、索引、权限、扩展和时区。抽样计算业务总额、最近订单和用户登录。敏感数据只由授权人员检查。运行应用烟雾测试时使用测试账号，不改真实恢复数据。需要写入测试就先复制到独立环境。

结果与备份时间点对照，晚于时间点的记录缺失属于预期，不应误判恢复失败。

## 一个误删演练

测试库有一百条虚构任务。先备份并记录校验值，再故意在测试环境删除十条。不要在原库覆盖恢复。创建新库恢复备份，确认一百条都在，并检查约束。随后比较原库剩余九十条与恢复库，练习如何提取十条差异。真实事故中还要合并事故后的合法写入。

记录从发现到可用的总时间。清理演练库前保存报告，不保留无用途凭据。

新版本把状态文本转为枚举，发现旧数据包含未预期值。迁移中止，事务回滚，应用仍用旧结构。团队先查询异常分布，定义映射和人工处理列表，再写新迁移。没有强行把未知值归为默认。第二次在数据副本验证行数、每种状态计数与约束，之后安排生产。

这个处理保留了数据语义。脚本“成功跑完”不能优先于业务事实。

## 连接字符串轮换

数据库密码泄露或定期轮换时，先创建新凭据并授予同等最小权限。测试连接后更新应用秘密并滚动部署。确认新实例使用新账号，旧连接逐步结束，再撤销旧账号。直接改唯一密码会让运行实例同时断开。

日志和指标按数据库用户名观察，确认没有旧账号活动。连接字符串不出现在进程参数和公开错误。轮换记录写凭据版本和时间，不写明文。

先从备份或复制建立新实例，让应用在测试环境连接并完成读写。对比扩展、时区、排序规则和权限。正式切换前减少数据差距，可使用复制或短暂停写。方法由数据库和供应商决定。切换后保留旧实例只读观察，禁止两边同时接受写入。双写需要专门一致性设计。

确认新备份任务生效后，才按保留策略下线旧实例。

## 迁移发布检查单

记录迁移版本、目标数据库、预计时间、锁风险、兼容代码、数据验证和恢复点。确认执行账号、操作窗口、负责人和停止条件。大表操作在副本测量。部署前备份并验证最近一次恢复。部署中监控锁、连接、延迟和错误。

完成后记录实际耗时、行数、Schema 版本和应用验收。移除临时高权限。

确认备份包含目标数据库、必要角色、扩展和外部文件清单。保存位置独立且加密。恢复到新环境，不覆盖唯一生产。禁用真实邮件、推送和 Webhook。运行结构、行数、约束、权限和应用测试，记录 RPO 与 RTO 实际结果。

验证后安全清理恢复副本和临时凭据。失败项进入下一次演练计划。

## 综合例子　误更新整张表

运营人员准备给一名测试用户改状态，手工 UPDATE 缺少 WHERE，整张用户表都被更新。团队立即停止相关写入，保存审计时间和数据库日志。没有再次运行反向 UPDATE 猜原值。最近时间点恢复创建新实例，团队从恢复实例取得事故前状态，再与事故后的合法注册进行差异处理。

应用连接只在验证完成后切换。所有用户状态和权限抽样检查，事故窗口内的操作单独审计。后续把日常修复放进带目标预览、事务和第二人确认的工具。生产账号取消普通人员直接全表更新权限。这个例子说明，可靠恢复不只是“有昨晚备份”。时间点、审计、停写和差异合并共同决定损失。

AI 可以审阅迁移计划、生成数据验证查询和恢复演练清单，也能根据脱敏日志解释失败阶段。它不能替你确认生产目标。任何 DROP、覆盖恢复和权限提升都由人工核对数据库名、环境和备份。

亲自执行隔离恢复并记录耗时。确认备份包含数据、结构、必要角色与外部对象清单。生产迁移前确认旧代码兼容、锁风险、恢复点和负责人。删除与覆盖操作需要第二人复核。下一章会处理数据库之外的文件、邮件、推送和 AI API。这些外部状态让恢复边界继续扩大。
