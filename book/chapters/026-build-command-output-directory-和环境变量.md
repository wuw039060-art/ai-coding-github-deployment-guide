# Build Command、Output Directory 和环境变量

自动部署表单中最常见的字段，回答四个问题。在哪个目录工作，怎样安装依赖，运行哪条命令，发布哪个目录。环境变量再向构建或程序提供仓库之外的值。字段名称在平台间略有差异，但 Root Directory、Install Command、Build Command、Output Directory 和环境变量的职责相对稳定。

把输入和输出画清楚，比记住某个平台菜单更可靠。字段填错时，部署平台通常不会理解你的意图，只会按错误配置执行。

## Root Directory 是工作起点

Root Directory 指项目在仓库中的位置。仓库根目录本身就是项目时，通常留空或使用默认值。项目在 `web` 子目录时，填写 `web`。平台进入这个目录后寻找 `package.json`、锁文件和构建配置。它也是相对路径计算的常见起点。

不要把 `src` 当作 Root Directory，除非清单和构建配置确实都在 `src`。`src` 常只是源代码目录。判断方法是先在本机进入候选目录，确认从这里能按 README 执行安装和构建。

Monorepo 中一个项目只需部分文件，平台 Git App 仍可能读取整个授权仓库。Root Directory 控制构建工作位置，不等于仓库读取权限。高度敏感项目要分仓库或使用平台提供的更细授权。构建脚本也可能访问上级目录，因此陌生仓库不要注入生产秘密。

## Install 和 Build 不同

Install Command 负责取得依赖，Build Command 负责从源材料生成可发布内容。平台默认安装命令通常会根据锁文件和框架识别选择。只有项目明确要求时才覆盖。私自改成忽略锁文件，会让每次部署解析到不同依赖。

Build Command 常见值是 `npm run build`，但实际名称取决于项目清单中的 `scripts`。部署表单填写的是项目公开脚本入口，不猜构建工具内部命令。纯静态项目可能不需要构建，此时按平台当前文档设置空命令或适用默认值，不要编造一个总是成功却什么也没做的命令来绕过检查。

命令成功要看退出状态与产物。只打印“完成”却没有生成目录，平台随后仍会失败。构建脚本是可执行代码，连接陌生仓库到平台，相当于允许其中脚本在构建环境中运行。审查 `scripts`、安装脚本和工作流，尤其是来源不明项目。

## Output Directory 是交付箱

Output Directory 指构建后平台要发布的目录。Vite 默认使用 `dist`，其他工具可能使用 `build`、`out` 或自定义名称。这个目录通常相对于项目根目录解释。项目根是 `web`，产物在 `web/dist`，平台输出框通常填 `dist`，不是从仓库根写 `web/dist`。平台规则若有例外，以当前文档为准。

Root 填错，平台找不到清单。Build Command 填错，产物没有生成。Output Directory 填错，构建成功也发布不到正确文件。发布前写下四行。

```text
仓库位置    web/
构建命令    npm run build
产物位置    web/dist/
平台输出框  dist
```

第一行从仓库根观察，第三行是构建后的真实路径，第四行按平台相对规则填写。四行对不上时，先在本地复现。再记录入口 `web/dist/index.html` 是否存在。若构建产生的是服务端程序而非静态目录，不应硬填静态 Output Directory。

产物中不应包含 `.git`、`node_modules`、真实环境文件、测试截图和数据库备份。Source Map 是否公开按项目风险决定。发布前可以生成清单，记录相对路径和大小。突然多出超大文件或只剩一个空 HTML，都是检查信号。

## 环境变量进入哪个阶段

变量可能在构建阶段读取，也可能在运行阶段读取。静态前端的变量常在构建时被写入成品。修改变量以后必须重新构建才能改变页面。动态后端可在每次启动或请求时读取运行环境。平台如何注入、是否需要重启，由运行时和供应商决定。

前端需要知道公开 API 地址、站点名称和非秘密功能开关。这些值即使从环境变量注入，最终仍可能出现在可下载文件中。服务端数据库密码、支付私钥、管理令牌和小程序 AppSecret 不能进入前端构建。变量名称带 `PUBLIC`、`NEXT_PUBLIC` 或 `VITE_` 一类前缀时，通常表示框架允许暴露到客户端，具体规则查当前框架文档。

不要把秘密直接写在 Build Command 中。命令会出现在设置、日志或进程信息中。使用平台秘密管理，并限制账号权限。环境变量排错时只确认名称、作用环境、是否存在和格式类别，不把真实值放进截图、Issue 或 AI 对话。

## 预览和生产要分开

预览环境可连接测试 API，生产环境连接正式 API。两者使用同名变量、不同值，能减少代码分支。如果预览正常、生产失败，比较两边变量清单、部署分支和构建日志。不要把生产变量临时复制到预览来“验证”，这可能让测试页面操作真实数据。

反过来，生产站连接测试数据库也很危险。上线验收要创建一条可识别的测试记录，并确认它出现在预期系统中，完成后按流程清理。平台提供的预览 URL 有时会被第三方访问，测试变量也应遵循最小权限和最小数据原则。

生产分支决定哪些 Git 事件进入 Production，环境变量决定该部署得到哪些值。两项共同影响结果。把生产分支从 `main` 改成 `release` 后，原本 Push `main` 只会生成预览或不部署。先把分支策略写进 README。

## 变量值的格式也会出错

变量名存在，不代表值可用。最常见的格式错误来自 URL、换行、引号、空格和布尔值。`https://api.example.com` 与 `https://api.example.com/` 对某些拼接代码会产生不同结果。值前后多一个空格，签名验证可能失败。多行私钥在控制台中被折成一行，程序启动时才报解析错误。把 `true` 当字符串还是布尔值，也要看代码如何读取。

公开 API 地址要写完整协议。只写 `api.example.com`，浏览器可能把它当相对路径。回调地址要区分根域、`www`、预览域名和生产域名。支付、登录和小程序服务端域名往往要在第三方控制台另行登记；仅改部署平台变量不能让外部服务自动认可新地址。

Base64 编码不是加密。有人为了绕过换行问题，把证书、JSON 或私钥编码后放进变量。这样可以改善传输格式，却不改变秘密属性。谁能读取变量，谁就能还原内容。记录时写清变量保存的是明文、JSON 字符串、Base64 文本还是文件路径。排错材料只写格式类别和长度范围，不复制真实值。

变量校验应在启动或构建早期完成。缺少必需变量时，程序给出变量名和环境，别在用户点击某个按钮后才出现 `undefined` 地址。可选变量要有明确默认值。默认值若连接测试服务，生产启动时也要报警。一次好的变量错误信息能告诉维护者缺了什么，却不打印秘密内容。

## 三个常见现场

第一个现场显示 `Could not read package.json`。日志工作目录是仓库根，而清单在 `frontend`。修正 Root Directory 或按工作区命令构建。第二个现场构建成功，平台提示发布目录不存在。本地配置把输出从 `dist` 改成 `out`，控制台仍填旧值。对照构建日志里的实际路径。

第三个现场预览 API 正常，生产浏览器请求到 `undefined/users`。生产缺少公开 API 地址变量，或变量修改后没有重新部署。检查变量作用环境并创建新部署。三种错误分别属于工作起点、构建输出和环境输入。它们都不需要先改 DNS。

构建缓存也会造成误解。平台可能缓存依赖和构建结果以提高速度。缓存命中不是错误，旧缓存掩盖问题时需要受控地清理或触发无缓存构建。先确认提交、变量和配置确实改变。没有新部署时，清缓存不会让生产分支自动更新。

## 配置变更要留痕

控制台设置不总在 Git Diff 中出现。修改 Root、命令、变量和生产分支后，团队可能无法从仓库知道原因。每次配置变更至少记录旧值、新值、操作者、时间、原因、部署 ID 和回退步骤。秘密只写名称或版本。

平台支持配置文件时，可以把非秘密设置版本化。仍要理解配置文件与控制台谁覆盖谁。事故排查把代码提交与控制台变更放在同一时间线。代码未变而服务故障，配置与供应商状态就更值得查。

变量命名应明确，例如 `PUBLIC_API_URL`、`DATABASE_URL` 和 `MAIL_FROM`。不要用 `URL`、`KEY` 这类含糊名称。示例文件为每个变量写用途、是否秘密、在哪个环境必需和示例格式。启动校验一次列出所有缺少名称，减少修一个再发现一个的循环。

## 配置验收表

| 字段 | 证据 | 预期结果 |
| --- | --- | --- |
| Root Directory | 清单与锁文件位置 | 平台能开始安装 |
| Install Command | 项目包管理器说明 | 依赖树可重现 |
| Build Command | scripts 与本地日志 | 命令成功生成新产物 |
| Output Directory | 构建配置与文件树 | 顶层有入口文件 |
| Runtime Version | 项目声明与平台日志 | 两边处于支持范围 |
| Environment Variables | 名称清单与环境 | 不缺失且无秘密暴露 |

每一行都要有实际证据。自动识别值也按同样标准检查。

## 本章验收清单

能从仓库和构建日志填写 Root Directory、Install Command、Build Command、Output Directory 和变量名称。能解释它们为何不是同一目录。能区分构建变量与运行变量、公开值与秘密。生产与预览变量分开，设置变更有记录。

AI 可以把仓库树转换成配置候选，解释每个字段的证据，并检查变量名是否在代码和平台记录中一致。让它标注推断与确认。例如“根据 Vite 默认值推测 dist，尚需执行构建确认”。亲自运行构建，查看新产物目录，确认环境变量作用范围和秘密边界。下一章顺着部署记录区分 Preview、Production、部署日志和回滚。
