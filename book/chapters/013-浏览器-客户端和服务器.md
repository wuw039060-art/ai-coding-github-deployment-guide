# 浏览器、客户端和服务器

在浏览器地址栏输入一个网址，页面出现之前，至少有两种角色参与。主动发起请求的一方叫客户端，接收请求并返回内容的一方叫服务器。浏览器是一种客户端，手机 App、桌面程序、命令行工具和监控服务也可以是客户端。服务器既可以指一台远程计算机，也可以指正在某个端口等待请求的程序。

先把角色和设备分开，很多故障就不再是一团“服务器坏了”。同一台电脑可以同时运行浏览器和本地开发服务器；同一个后端接收浏览器请求时是服务器，随后调用邮件服务或 AI API 时又变成客户端。角色取决于这一段关系，不取决于机器名称。

图中浏览器先根据 URL 找到入口，再发送 HTTP 请求。入口可能是 CDN、托管平台或反向代理。静态资源可以直接返回，动态请求会继续转给后端。后端读取数据库、对象存储或第三方服务，再把响应逐层送回浏览器。

## 浏览器不是一个透明窗口

浏览器负责解析 URL、建立连接、发送请求、读取响应、解析 HTML、CSS 和 JavaScript，并把结果绘制成页面。它还管理标签页、缓存、Cookie、下载、扩展、权限和安全提示。用户看到的一次“打开网页”，在 Network 面板里常常是几十个请求。主文档、脚本、样式、图片、字体和 API 各自有状态。

所以页面显示一半时，不要立刻判断后端整体宕机。HTML 可能成功，图片路径却 404；CSS 可能加载失败，导致页面像“没排版”；JavaScript 可能执行报错，按钮没有反应；API 可能返回 401、403 或 500。浏览器把这些结果组合成一个界面，排错时要拆开看。

浏览器运行在用户设备上，用户可以查看页面代码、修改请求、安装扩展，甚至不用浏览器而改用别的工具直接调用 API。因此价格、权限、所有权、支付状态和管理员操作不能只由浏览器决定。前端可以帮助用户输入和展示结果，服务端必须重新验证关键规则。

一个常见错误是把高权限配置放进前端。只要代码进入浏览器，它就可能被用户看到。公开客户端密钥是否安全，要按平台设计判断；服务端密钥、数据库管理员密码和支付后台密钥不能进入浏览器、小程序前端或移动 App。

## 服务器先看“哪一个角色”

“服务器”这个词太宽。它可能指静态文件服务器、反向代理、API 应用、数据库、队列工作进程、实时连接服务，也可能指承载这些程序的云主机。小项目可以把多个角色放在一台机器上，但日志、风险和修复动作仍然不同。

| 角色 | 主要工作 | 典型线索 |
| --- | --- | --- |
| 静态文件服务 | 返回 HTML、CSS、脚本和图片 | 路径、状态码、传输大小 |
| CDN 或反向代理 | TLS、缓存、域名路由、转发 | 缓存命中、上游地址、502 |
| API 应用 | 认证、权限、业务规则 | Request ID、错误码、业务日志 |
| 数据库 | 查询、事务、约束 | 连接失败、慢查询、唯一冲突 |
| 工作进程 | 处理慢任务或队列 | 任务 ID、重试次数、结果 |
| 实时服务 | 管理长连接和订阅 | 连接、频道、断开原因 |

用户说“网页打不开”，先问影响范围和失败点。只有一个标签页崩溃，其他用户正常，可能是浏览器内存、扩展或特定数据；所有用户的 API 都 5xx，才更像公共服务故障。首页能打开而“我的订单”转圈，通常说明静态入口正常，动态 API 或后端依赖有问题。

本地开发服务器也是服务器程序。运行开发命令后，它可能监听 `localhost:5173`，只给当前电脑的浏览器返回页面。它不是公共生产服务。生产环境还会有 HTTPS、域名、构建产物、日志、配置和访问控制，不能把“本地能打开”当作上线完成。

## 静态请求和动态请求

浏览器请求 `/index.html`，服务器找到已经生成好的文件并返回；浏览器再请求 `/styles.css` 和图片。这类请求不依赖当前用户身份，通常属于静态资源。CDN 很适合缓存它们。图片 404 不代表后端登录系统坏了，只说明这一路资源没拿到。

动态请求会根据身份、时间或数据库内容变化。用户访问 `/account`，浏览器带上会话标识，服务端验证身份，查询账户数据，再返回 HTML 或 JSON。若数据库连接失败，服务端可能返回 500；若没有登录，常见是 401；若已登录但无权访问，常见是 403。状态码会在第十五章展开。

动态内容的缓存要更谨慎。把甲用户账户页缓存后交给乙用户，是严重事故。静态资源追求复用，账户、订单、支付和管理数据追求隔离。看到缓存配置时先问两个问题。这个响应是否对所有人都相同，是否可以被共享缓存保存。

服务端可以直接生成 HTML，也可以返回 JSON 让浏览器生成界面。服务端渲染有利于首屏内容和搜索理解，但增加运行和缓存复杂度；客户端渲染部署静态文件简单，但脚本失败时可能空白。许多现代框架混合两者。判断项目时看实际构建产物、路由和部署说明，不按框架名字猜。

## 请求和响应是一来一回

请求包含方法、URL、请求头和可选正文。响应包含状态码、响应头和可选正文。浏览器打开页面通常使用 GET，提交表单或创建记录可能使用 POST。服务器即使收到请求，也可以拒绝、重定向或报错。网络连接成功和业务操作成功不是一回事。

浏览器会按协议、主机和端口判断 Origin，也就是源。`https://example.com` 与 `https://api.example.com` 是不同源。网页脚本跨源读取响应时，浏览器会执行同源策略和 CORS 规则。CORS 配置错误时，服务器可能已经返回响应，但浏览器仍阻止页面脚本读取。

CORS 不是身份系统。允许某个来源访问，不证明请求者就是合法用户。命令行工具和手机 App 不受浏览器同源策略约束，服务端仍要认证、授权和验证输入。遇到 CORS 错误时，记录网页 Origin、请求 URL、方法、状态和 Console 提示，不要把关闭浏览器安全功能当作修复。

请求材料经常含秘密。排查时可以分享方法、路径、状态、Request ID 和脱敏后的响应结构，不分享 Cookie、Authorization、签名 URL、密码和真实用户资料。

## 客户端状态和服务端状态不同寿

刷新页面会重新加载前端，不会重启后端。清浏览器缓存不会修复数据库连接。重启后端会影响正在处理的请求，可能让用户短暂失败。重新部署前端会生成新静态资源，但旧标签页可能仍运行旧脚本，直到刷新或缓存更新。

用户关闭标签页后，已经发到后端的请求可能继续执行。重复打开页面再提交，可能产生两次操作。创建订单、付款和慢任务要有任务编号或幂等设计。客户端显示“处理中”只是界面状态，权威状态要从服务端查询。

浏览器进入后台时，系统可能限制计时器和网络。实时连接可能断开，轮询可能暂停。回到前台后，客户端应重新获取服务端状态。不要假设用户离开期间每一条事件都被页面接收。

多用户同时访问时，服务端不能把某个用户的临时数据放进所有请求共享的全局变量。最后一个名额被两个人同时预约，需要数据库约束、事务或其他并发控制。访问量很小的项目也应避免明显串用用户数据。

## 不同客户端可以共用同一个后端

同一个后端可以同时服务网页、Android App、iOS App、小程序、管理后台和自动化脚本。它们的界面、发布渠道和本地能力不同，但请求到后端后，都要经过同一套身份、权限和数据规则。若只有网页前端检查权限，App 或脚本就可能绕过。若只有 App 端限制版本，旧网页缓存也可能继续调用旧接口。

客户端差异仍要记录。浏览器有同源策略和 Cookie 行为；手机 App 有系统权限、离线缓存和商店版本；微信小程序有自己的登录、审核、域名白名单和能力边界；命令行工具通常没有浏览器 CORS 限制。服务端不能把这些客户端机制当作最终安全，但要理解它们为什么影响故障现象。

例如网页请求 API 失败并显示 CORS，小程序请求同一路径却显示域名未配置，命令行 `curl` 能得到 401。这三条证据说明后端入口存在，但不同客户端的外层规则不同。维护者应分别检查浏览器 Origin、微信小程序后台允许的服务器域名、以及 API 自身的认证结果。把它们统称为“服务器不通”会走错方向。

多端共用后端时，API 版本和兼容期变得重要。网页可以较快更新，App 和小程序可能有审核、缓存和用户不升级的问题。后端删除字段或改变错误结构前，要知道哪些客户端还在使用。日志记录客户端类型和版本只用于诊断，不能让客户端自报身份决定权限。

## 一条请求的最小追踪

用户说北京时间 14 点 32 分点击保存后失败。浏览器 Network 显示 PATCH `/api/profile` 返回 500，并带 Request ID `req-test-42`。入口日志用同一 ID 找到上游状态和耗时。应用日志显示数据库唯一约束冲突。数据库里另一个测试用户已经占用昵称。

修复方向是把后端响应改为 409 和稳定错误码，前端在昵称字段旁提示“已被使用”，不是让用户清缓存。再次测试时，Network、界面和数据库状态一致。这个例子从客户端现象进入，经请求定位到 API，再用服务端日志确认原因。

Web 前端、移动 App 和小程序都可以把构建版本或客户端版本发给后端，帮助定位“只有旧客户端失败”。版本字段只用于诊断和兼容，不能决定权限。攻击者可以伪造客户端信息，服务端授权仍以认证身份和资源规则为准。

## 本章验收清单

能说出浏览器为什么是客户端，服务器为什么既可能是设备也可能是程序。能沿图指出浏览器、入口、后端和数据库各自负责什么。能用 Network 区分主文档、静态资源和 API。知道刷新页面、重新部署前端、重启后端和重启服务器影响范围不同。

最小练习从一个无敏感信息的公开网页开始。进入 DevTools 的 Network，刷新。记录主文档的 Request URL、Method、Status 和 Content-Type，再选一张图片或脚本比较状态。不要在 Console 粘贴陌生代码，也不要修改不属于你的站点数据。完整 DevTools 操作放在第十九章。

AI 可以根据脱敏后的 URL、状态码、Network 导出和服务日志画出请求路径，判断下一处检查位置。它不能从一个浏览器错误直接证明服务器内部原因。真实账户权限、生产日志、证书警告和安全策略仍需人工确认。下一章拆开 IP、域名、DNS、端口和 URL，回答浏览器到底要去哪里。
