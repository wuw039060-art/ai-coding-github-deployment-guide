# 用 GitHub Desktop 管理本地项目

GitHub Desktop 是 GitHub 提供的桌面应用。它把仓库选择、文件变化、提交历史、分支和远程同步放进图形界面，支持 Windows 与 macOS。对第一次管理项目的人，它最大的帮助是让即将提交的文件和每一行变化可见。

图形界面没有改变 Git 的基本动作。Commit 仍发生在本地，Push 仍把提交送到远程，Pull 仍把远程变化带回本地。理解按钮作用以后，即使将来换编辑器或命令行，判断方法仍能保留。

## 安装前先确认用途与来源

GitHub Desktop 适合查看 Diff、提交、同步与常见分支操作，不覆盖复杂历史修复和服务器自动化。只从 GitHub 官方入口安装；受管理设备按组织策略申请，不关闭安全功能绕过。首次浏览器授权时读清账号，尤其不要混淆个人与工作身份。

Current repository 表示当前仓库。它决定左侧变化和历史属于哪个本地目录。Current branch 表示当前分支。Changes 展示尚未提交的文件变化。History 展示当前分支的提交历史。

操作前先读仓库名和分支名。两个项目都叫 `website` 时，仓库名仍可能一样，应再查看本地路径。GitHub Desktop 的 Repository 设置或在文件资源管理器中显示仓库，可以帮助确认绝对路径。

Changes 中每个文件有选择状态；选中的变化会进入下一次提交；文件名旁的标记会区分新增、修改与删除。点击文件后，中间区域显示 Diff，也就是修改前后的差异。绿色通常表示新增行，红色通常表示删除行；修改一句文字时，界面可能显示一行删除和一行新增；它说明内容怎样改变，不代表先执行删除再执行新增。

## 创建、添加和克隆是三个入口

Create a New Repository 在本地创建新仓库，适合新练习或尚未使用 Git 的空项目。Add an Existing Repository 把电脑上已有的本地 Git 仓库加入 GitHub Desktop 列表，不会复制一份项目。Clone a Repository 从 GitHub 或其他远程地址取得仓库，在本地创建工作副本。

项目已在电脑并含 `.git` 时用 Add；项目只在远程时用 Clone；ZIP 快照没有正常历史，按项目归属决定初始化新仓库还是重新 Clone。只选符合当前状态的一条路线。

## 用 GitHub Desktop 创建本地练习仓库

在普通空目录创建练习仓库，填写 Name、Description 与 Local path；最终路径由父目录和仓库名组成。创建前读出路径。本地创建不会自动让 GitHub 出现仓库；Publish 前还要确认 Owner、远程名称与可见性。

Publish 成功后，用浏览器打开远程 URL，比较所有者、仓库名和最新提交。若创建到了错误账户，不要继续上传正式文件，先确定应转移还是重建练习仓库。

## 把普通文件夹变成仓库前先做清单

AI 生成的项目可能已经有源码、依赖目录、构建产物与 `.env`。直接在父目录 Create repository 会让所有内容进入 Changes。先确定项目根目录。删除可重建缓存可以稍后做，当前先加入合适 `.gitignore`。列出秘密、用户数据和大文件，确认它们不会提交。保留原始目录备份，尤其是没有其他副本时。

GitHub Desktop 发现目标不是 Git 仓库时，可能提供创建仓库的入口。创建后先不要 Publish。查看 Changes 与 Diff，确保范围正确，再完成第一次提交。第一次提交常叫 Initial commit，也可以用中文写“建立项目初始版本”。它应包含能重建项目所需的源码与说明，不包含依赖缓存、真实秘密和本地用户数据。

新分支从当前提交开始，刚创建时文件看起来相同。在分支修改并提交后切回 `main`，新增内容会消失，因为 `main` 尚未包含提交。此时先看 Current branch 与 History，不要重建文件。若分支在 GitHub 上合并，本地切回 `main` 后再 Fetch 和 Pull 取得结果；若已经在本地合并到 `main`，结果就在本地历史中，推送后远程才会更新。

## 外部编辑器与 GitHub Desktop 的分工

GitHub Desktop 管理版本，文本编辑器修改内容。点击 Open in Visual Studio Code 一类入口时，应用把当前仓库交给编辑器。编辑器的集成 Git 面板也可能显示相同变化。

尽量让一次 Git 操作由一个工具完成。不要在 Desktop 正在合并时，又在另一个工具执行 Reset 或切换分支。两个界面都操作同一 `.git` 数据，状态变化会互相影响。编辑器保存后，Desktop 通常自动刷新。没有刷新时先确认文件路径和保存状态，再手动切换界面。不要复制一份文件到仓库以制造变化。

Diff 中空白变化可能来自格式化或换行。项目启用自动格式化时，先了解保存动作是否会改整份文件。大范围格式化最好独立提交。

Push 突然要求重新登录，不表示本地提交丢失。先确认 History 中提交仍在。通过 GitHub Desktop 设置退出和重新登录前，记录远程 URL 与当前账号。浏览器授权页面出现多个账号时，选择对仓库有权限的身份。组织要求额外授权时，按组织流程完成。不要把个人访问令牌粘贴到来历不明的弹窗。

认证恢复后先 Fetch，再 Push。若远程在等待期间有新提交，先整合。不要为解决认证错误删除 `.git` 或重新初始化。

## GitHub Desktop 的日志与诊断

应用发生错误时，先保留界面提示。GitHub Desktop 还提供日志位置或帮助入口，具体菜单随版本变化。日志可能含本地路径、仓库 URL 和账号信息，分享前遮盖隐私。一份有效报告包括应用版本、操作系统、仓库是否公开、正在执行的动作、错误时间和完整提示。能在无敏感练习仓库复现时，再提供最小复现步骤。

只有一个仓库出错，先查仓库状态和权限。所有仓库都无法认证，更可能是账号、网络或应用级问题。形成对照后再重装应用。

## 提交范围必须是一项完整变化

你可以在 Changes 中取消选择某些文件，让它们不进入这次提交。这样适合把文档与功能拆开，也可能制造不完整提交。例如代码开始引用新图片，却只提交代码，没有提交图片。其他电脑 Pull 后会出现 404。提交范围要围绕一项完整变化，不能只追求文件数量少。

查看 Diff 时按功能检查依赖。新增导入语句要有对应文件，配置变化要有说明，数据库迁移要与代码顺序协调。工具只能展示选中状态，完整性由人判断。GitHub Desktop 也支持逐行选择的能力时，使用前确认代码仍能编译。一个函数只提交半段修改，可能产生语法错误。初学者优先按文件拆分清楚工作。

## 不同颜色与图标要结合文字

界面颜色会受主题与无障碍设置影响。不要只记“绿色按钮”或“红色行”。同时读操作名称、文件状态和正负行标记。深色模式中 Diff 颜色可能改变，色觉差异也会影响辨认。EPUB 的截图与说明会用文字标明新增和删除，不让颜色承担唯一信息。

软件更新后按钮位置可能移动，动作关系仍是仓库、分支、变化、提交和远程。找不到按钮时从当前状态判断需要 Commit、Fetch、Pull 或 Push，再查官方文档。

添加本地仓库前确认项目含 `.git` 且没有危险历史操作。目录不是仓库时先取消，检查根目录或 ZIP 来源，不立即初始化。Add 只让应用管理该路径，不会 Push 或改变可见性；随后核对远程地址。已有重复条目时回到现有路径，不复制项目消除提示。

## 查看一次真实变化

选择一个无敏感信息的练习仓库。在编辑器中打开 README，增加一行“本仓库用于练习 GitHub Desktop”，保存文件。回到 GitHub Desktop，Changes 应出现 `README.md`。点击文件，Diff 中能看到新增文字。若没有出现，先确认编辑器保存成功，再核对 Current repository 与本地路径。

提交前阅读整个 Diff。示例只有一行，实际项目可能因为格式化工具改变许多文件。突然出现锁文件、构建产物、日志或 `.env` 时，先查明来源。不要为了让列表归零而全部勾选。GitHub 官方提交说明强调可以选择文件并在创建提交前审查变化。这是桌面工具最值得养成的习惯。

AI 大规模修改时，先观察 Diff 的形状。修正文案却同时改变部署脚本、权限配置和数据库迁移，范围就值得暂停。文件数量不能证明对错，却能提示你要求解释每组变化与需求的关系。

## 创建一个本地提交

确认只选中 README 后，在 Summary 填写“补充练习仓库说明”。Description 可以记录更多原因，小修改可以留空。点击提交到当前分支。成功后，Changes 中的这项变化消失，History 顶部出现新提交。此时提交仍可能只在电脑上。界面若出现 Push origin，说明本地有提交尚未发送到远程。

提交按钮会写出当前分支名。生产仓库中看到错误分支时，先停止。切换分支前还要处理未提交变化，避免把工作带到意外位置。提交说明应描述结果，例如“修复首页图片路径”“增加安装前提”。“update”“修改”“试试”很难在故障时帮助判断。说明不必写成长文，能够区分这次工作即可。

Push origin 会把本地提交发送到当前分支对应的远程。GitHub 官方说明中，推送前如果远程已有新提交，应用会提示先获取远程变化。第一次发布本地仓库时，界面可能显示 Publish repository。此时要选择 GitHub 所有者、仓库名和可见性。Publish 会发送提交并创建远程仓库，因此必须亲自确认账号与公开范围。

普通 Push 成功后，按钮状态会变化。打开 GitHub 仓库网页，检查同一分支的最新提交说明和 README 内容。网页证据比“按钮消失了”更能证明远程更新；网络中断时，Push 可能失败；本地提交通常仍在 History 中，不需要重新提交；恢复网络后先 Fetch，再根据界面提示重试；连续点击可能造成困惑，却不会让错误凭据变正确。

## Clone 一个练习仓库

Clone 会下载仓库文件与 Git 历史，并设置远程关联。开始前选择一个清楚的本地父目录，例如 Windows 的 `C:\Projects` 或 macOS 的 `/Users/USER/Projects`。不要把仓库克隆到另一个仓库内部。在 GitHub Desktop 中选择 Clone，找到自己的练习仓库，确认 Local path。路径末尾通常会包含仓库名。点击 Clone 后等待完成。

成功结果是应用切换到新仓库，Changes 通常为空，History 能看到远程提交，本地目录出现项目文件。若目标目录非空，应用会阻止或提示更换位置。不要把现有项目文件强行覆盖。克隆私有仓库失败时，检查应用登录账号是否具有权限。克隆公开仓库一般不代表你能 Push 回原仓库。没有写权限时，可以只读使用，或者按项目贡献说明 Fork 后提出改动。

Fetch origin 查询远程是否有新提交，通常不会直接改写当前工作文件。发现远程领先后，界面可以显示 Pull。Pull 会取得并整合远程提交，因此可能改变本地文件。Push 表示本地领先。若本地与远程各自都有新提交，应用需要先整合。简单情况可以 Pull 后自动合并，修改冲突时会进入冲突处理。

开始同步前保存编辑器文件并查看 Changes。未提交工作不一定阻止所有操作，却会增加冲突和误判。首次学习时，保持 Changes 为空再同步更容易理解结果。

## 丢弃变化是有损操作

GitHub Desktop 提供 Discard changes 一类操作。它会把未提交文件恢复到仓库记录的状态。GitHub 官方说明当前版本可能把丢弃内容放入系统回收站或废纸篓，但具体恢复能力与文件状态有关，不能把它当成稳定备份。

丢弃前打开 Diff，确认文件、行和目标仓库。新建但未提交的文件与已跟踪文件的处理可能不同。工作项目中存在用户内容时，先复制到受控备份位置，并记录恢复方法。不要把“撤销最近提交”“Revert 提交”“Reset 到某个提交”和“丢弃未提交变化”混在一起。它们影响的历史范围不同。第九章会分别解释。

> 高风险操作
>
> 看到 Discard、Delete、Force 或覆盖提示时先停。列出受影响文件，确认是否已提交、已推送或有独立备份，再决定。

## 常见错误

Changes 中出现几千个文件，常见原因是把父目录误建成仓库，或构建输出没有忽略。不要一次全部提交。确认仓库根目录和 `.gitignore`。History 中有提交，GitHub 网页没有，先看是否 Push，再比较分支。网页显示另一个分支时，文件列表会不同。

Push 提示没有权限，检查远程所有者、登录账号和协作权限。更换账户前保留本地提交，不要删除项目重来。切换仓库后看见陌生改动，先核对本地路径。不要丢弃，它们可能属于另一个项目或用户已有工作。

AI 可以解释 Diff、建议提交拆分和说明，读取非敏感错误并指出当前仓库、分支与远程可能不一致。它也可以提供 Windows 与 macOS 的界面步骤。允许 AI 点击提交、Push 或 Discard 以前，要让它先报告仓库绝对路径、分支、文件清单和预期远程。普通学习阶段可以由人亲手完成这些按钮。

登录账号、仓库路径、分支、提交文件和可见性必须亲自确认。任何丢弃、删除、覆盖、强制同步和发布到组织账户的操作，都保留人工决定。下一章会把 Commit、Push、Pull、Clone 和 Sync 放进同一条时间顺序，解释两台电脑或多人协作时怎样避免覆盖。
