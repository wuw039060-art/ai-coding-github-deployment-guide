# 模块、内聚、耦合、依赖方向与公开接口

一个项目有 `controllers`、`services`、`models` 和 `utils` 四个目录，看上去已经分层。现在要修改“订单取消后退还库存”这条规则。AI 先改订单服务，又在库存服务补一次判断，接着发现定时任务也能取消超时订单，于是把相同逻辑复制过去。目录依然整齐，规则已经有了三个版本。

模块边界在这种改动里才看得清。订单取消应该由一个地方决定，其他代码通过公开接口请求这项操作。库存模块可以拒绝非法返还，通知模块可以接收订单已取消的结果，却不应各自重新判断订单是否允许取消。

**模块的价值在于缩小理解和修改范围。目录只是它留在文件系统里的痕迹。**

## 内聚让相关变化留在一起

内聚描述一个模块内部的内容是否围绕同一类责任变化。订单状态、取消条件和退款协调常因同一项业务变化一起修改，把它们放在订单模块有实际理由。日期格式化、数据库连接和邮件发送不会因为订单规则改变而一起变化，塞进订单模块只会让名称越来越宽。

判断内聚可以看提交历史。某几个文件经常在同一项需求中一起修改，它们可能属于同一边界。一个文件每次都陪着完全不同的功能变化，它可能承担了太多责任。历史只能提供线索，还要结合代码调用和数据所有权确认。

“一个文件只做一件事”常被理解得过窄。业务操作本来就可能包含验证、状态变化、审计和事件记录。强行拆成许多只剩几行的文件，会让维护者为了读懂一个动作不断跳转。更实用的问题是，这些代码是否由同一种原因推动变化，是否能用一个清楚名称说明责任。

耦合表示一个部分对另一个部分知道多少。订单模块调用库存模块公开的 `releaseReservation`，知道的是对方提供什么能力。订单模块直接读取库存内部表、拼接对方的状态码、依赖对方私有文件路径，就知道了太多实现细节。所有协作都会产生耦合，目标是让依赖明确、方向可解释，并把经常变化的细节挡在接口后面。

微软的架构指南说明，逻辑分层可以限制哪些区域互相通信，并让基础设施实现通过接口满足应用核心的需要。读者不必照搬某一种 Clean Architecture 文件夹。应当保留的判断是，稳定的业务规则不应被某个数据库驱动、邮件 SDK 或 Web 框架的具体调用方式绑住。

## 依赖方向会改变测试难度

假设预约规则直接导入 PostgreSQL 客户端，在函数内部执行 SQL。测试“名额用尽后拒绝预约”时，就必须准备数据库、迁移和连接。若预约规则依赖一个较小的席位存储接口，单元测试可以提供受控实现，数据库适配器再用集成测试验证。

接口不该为了画架构图而到处增加。一个只有单一实现、不会阻碍测试、也没有跨越边界的内部函数，未必需要额外抽象。接口带来名称、文件、装配和维护成本。它在隔离易变细节、表达模块协议或支持独立测试时才开始偿还这些成本。

可以用三项证据检查依赖方向。

- 核心规则能否在不启动 Web 服务器和真实外部服务的情况下运行。
- 更换邮件、对象存储或数据库实现时，业务规则文件是否保持稳定。
- 框架升级引起的 Diff 是否集中在入口与基础设施区域。

第一项通过只能说明测试边界成立，不能证明真实数据库适配器正确。第二项通过说明抽象隔离了当前变化，不能保证未来所有供应商差异都被覆盖。第三项若修改扩散到业务规则，需要查看框架类型是否已经穿过公开接口。

## 公开接口要比内部代码更克制

模块的公开接口是其他部分获准依赖的表面。公开得越多，未来越难自由修改。把整个数据库对象、框架请求对象或内部状态枚举直接交出去，调用者很快会依赖其中细节。随后一次内部重构就变成跨项目迁移。

接口应当表达业务动作和必要结果。`cancelOrder(orderId, actor)` 比“拿到订单模型以后由调用者随意改状态”更容易集中权限、审计和并发处理。返回结果需要包含调用者真正要处理的信息，也要区分可重试失败、权限拒绝和业务冲突。

接口稳定不等于永远不变。变更时要判断调用者数量、部署是否同步、旧客户端会保留多久。单体内部接口可以跟随同一次发布修改。跨服务 API、移动 App API 和队列消息面对不同版本同时存在，需要兼容窗口、版本策略和迁移证据。

设想这样一个项目。订单模块原本拥有订单表，库存模块拥有库存预留表。为了赶进度，新代码在订单事务里直接更新两张表。正常取消成功，测试也很快。后来库存模块增加预留历史和并发版本号，这条旁路更新没有写历史，也没有检查版本。库存数字看似恢复，审计记录却少了一笔。

修正时先停止继续增加旁路，让库存模块提供明确的释放操作。订单取消记录业务意图，库存操作使用幂等编号，重复调用不会返还两次。若两个模块仍位于同一数据库和同一进程，可以在受控边界内使用事务协调。若已经分成独立服务，就要处理局部成功、重试与补偿。

这个例子也说明模块和微服务不能混为一谈。清楚的数据所有权在单体中同样重要。服务拆分会让边界更难绕过，也会把一次本地调用变成网络协议。边界不清时先拆进程，通常只会让含糊责任变成含糊 API。个人项目没有团队边界，仍然需要为未来的自己和 AI 保留可理解范围。
