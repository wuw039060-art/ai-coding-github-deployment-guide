# Console、Network、Build Log 和 Runtime Log

日志不是一个窗口里的同一种文字。Build Log 记录依赖、编译和打包，Console 记录网页脚本执行，Network 记录请求与响应，Runtime Log 记录程序在服务器、容器或设备上的运行。先判断失败阶段，才能打开正确证据。

例如点击登录没有反应，Console 可能显示 JavaScript 在读取空值时异常，代码还没有发送请求。Network 中若已经出现 401，请求到达后端但身份不被接受。若构建平台连产物都没生成，浏览器窗口与生产运行日志都不是当前起点。

## 四类证据回答四种问题

Build Log 回答源代码和依赖能否变成构建产物。Console 回答浏览器页面中的 JavaScript 执行发生了什么。Network 回答浏览器实际发送了什么、服务器返回了什么。Runtime Log 回答服务接到请求以后如何处理，以及运行环境发生了什么。

四者会互相连接，却不能相互替代。Network 显示 500，要用关联编号去 Runtime Log 查服务错误。Runtime Log 没有请求，要回到 Network、代理或时间范围，不要先改数据库。

构建工具经常在一个根错误后输出几十行连带失败。最后一句 `Build failed` 只说明结果，第一条包含文件、行号、依赖或权限的明确错误更接近起点。阅读时从前往后找第一个异常转折，再保留它前后的上下文。Build Log 常分为环境准备、依赖安装、编译、测试、打包和上传几个阶段。先确定失败在哪个阶段。依赖下载超时与 TypeScript 编译错误需要不同处理，打包成功后的部署上传失败又属于平台交付。

构建平台通常显示命令、退出码和耗时。退出码为零表示该进程按自己的规则成功结束，不保证产物内容正确。还要检查产物目录、文件大小和后续部署是否使用了同一目录。

## 保存完整构建上下文

一份可重现构建记录包含 Git 提交、运行命令、Node、Flutter、JDK 等工具版本、锁文件、操作系统和环境名称。只复制红色一行，接手者可能不知道它来自本地、CI 还是部署平台。日志中的环境变量要脱敏。平台可能自动遮罩已登记 Secret，却不会识别临时打印的数据库 URL 或自定义令牌。怀疑变量缺失时打印变量是否存在、长度或哈希摘要，不打印真实值。

本地构建成功、CI 失败时，优先比较大小写敏感路径、未提交文件、工具版本、环境变量与网络。不要直接把本地生成目录提交进仓库遮住差异。

Chrome DevTools 可以从浏览器菜单或快捷键打开，Console 显示脚本错误、警告、显式日志和交互表达式结果。Chrome 官方参考说明了级别过滤、调用位置和堆栈等功能。

红色错误先看错误类型、信息、文件和行号。点击来源可以跳到脚本位置，展开调用栈能看到从哪个事件和函数到达这里。经过压缩的生产文件可能只显示 bundle 行号，需要 Source Map 才能映射回源码。

黄色警告不一定阻止功能，却可能提示弃用 API、资源策略或性能问题。不要为“控制台全绿”忽略所有警告，也不要把第三方浏览器扩展产生的消息当成自己应用错误。使用无痕窗口或禁用扩展比较。

## 清空 Console 之前先保留现场

Console 日志可能随刷新清空，也可能因 Preserve log 设置跨页面保留。复现前先清理旧消息，开启必要保留，再执行一次最短步骤。这样能区分当前问题和半小时前的无关错误。记录错误发生时间和用户动作。页面加载时的错误与点击按钮后的错误意义不同。复制为文本时保留调用栈，截图用于展示界面位置，两者各有用途。

不要在 Console 粘贴来源不明的代码。网页可以诱导用户执行窃取 Cookie、令牌或账号操作的脚本。Console 拥有当前页面上下文，任何粘贴操作都应先理解。

打开 DevTools 的 Network 面板后刷新页面或重复操作，列表会显示请求。Chrome 官方练习建议从录制请求、查看 Headers、Preview、Response 和 Timing 开始。

先找到目标请求。可以按 Fetch/XHR、文档、图片等类型过滤，也可以搜索 URL。看不见请求时，可能页面代码在发送前就失败，Network 录制未开启，或者请求来自 Service Worker、原生 SDK 等另一环境。

选中请求后依次查看 URL、方法、状态码、请求头、请求内容、响应头、响应正文、发起者和耗时。每一项都能排除一类猜测。请求发到测试域名时，生产后端日志当然没有记录。

## 状态码先按类别理解

2xx 表示请求在 HTTP 层成功处理，仍要检查业务响应。204 没有响应正文，前端若强行按 JSON 解析可能报错。3xx 表示重定向，登录循环常能在请求链中看到。4xx 通常表示客户端请求、身份或权限问题。401 常与未认证有关，403 表示服务器理解身份但拒绝访问，404 可能是路径不存在，也可能被应用用来隐藏资源。MDN 的状态码参考给出标准语义，具体 API 仍要看自己的契约。

5xx 表示服务端处理失败。502 常来自网关无法得到有效上游响应，503 常用于服务暂不可用，504 常与上游超时有关。状态码指出失败层级，不能单凭一个数字断言唯一根因。

Preview 会格式化 JSON 等内容，Response 更接近原始正文。错误响应可能包含用户可读信息、错误代码和关联编号，也可能错误地泄露堆栈与 SQL。前端显示“未知错误”时，检查响应是否有更具体代码。若服务器返回 HTML 错误页，前端却按 JSON 解析，Console 可能只显示 `Unexpected token <`。这时 Network 的 Content-Type 与 Response 能指出真正输入。

分享响应前删除令牌、Cookie、邮箱、订单和用户正文。错误页面不应包含数据库密码或内部路径，发现时按秘密泄露处理。

## Headers 帮助定位身份、缓存和跨域

Request Headers 包含 Content-Type、Authorization、Cookie、Origin 等信息。浏览器可能因为 Cookie 属性、跨域策略或缓存没有发送你以为存在的身份。

Response Headers 包含缓存策略、内容类型、重定向位置和跨域许可。CORS 是浏览器对跨来源读取的限制，服务器收到请求并不代表浏览器允许脚本读取响应。不能通过浏览器扩展关闭 CORS 作为生产修复。

Cookie 与授权头属于秘密。截图前遮罩。调试环境可以查看是否存在和属性，问题报告不复制完整值。

Network Timing 可以把排队、DNS、连接、TLS、等待服务器首字节和下载分开。DNS 很慢与服务器计算很慢，用户都只感觉转圈，处理方式不同。等待首字节长，可能是应用、数据库或外部服务。下载长则看响应大小、带宽和压缩。排队时间高可能与浏览器连接限制或 Service Worker 有关。

比较同一请求的多次结果，并记录网络条件。缓存命中、首次 TLS 连接和后续复用会产生明显差异。单次最快结果不能代表用户体验。

## 缓存会让旧内容看起来像发布失败

浏览器、Service Worker、CDN 和服务器都可能缓存。HTTP 缓存由请求与响应头共同决定，MDN 对 freshness、validation 和 Cache-Control 有系统说明。

DevTools 的 Disable cache 只在工具打开时影响当前浏览器环境，不能证明所有用户缓存已更新。先在普通模式复现，再用禁用缓存比较，确认问题是否与缓存相关。带哈希的静态文件适合长期缓存，HTML 入口通常需要更谨慎策略。部署新 JS 却沿用旧文件名，用户可能继续使用旧代码。

Fetch Promise 通常只在网络层失败时 reject。服务器返回 404 或 500 时，Fetch 仍可能正常得到 Response，需要代码检查 `response.ok` 或状态码。因此 Console 中没有异常，不表示业务请求成功。页面也可能把 500 响应当普通数据继续处理。Network 与应用代码要一起看。

网络错误、超时、用户取消和 HTTP 错误在 UI 中给不同提示。后端未知结果的写入不能盲目重复。

## Runtime Log 记录服务实际处理

Runtime Log 可以来自平台实例、systemd Journal、Docker 容器、移动设备或应用自己的日志系统。它应包含时间、级别、服务、版本、事件、结果和关联编号。日志要写事实，例如请求 `7F3A` 调用对象存储 30 秒后超时。只写“出错了”缺少位置，写完整用户正文又违反最小化。结构化 JSON 日志便于按字段筛选，但可读文本也能用于小项目。

Build Log 属于一次构建，Runtime Log 属于某个运行实例。构建通过后的空指针、磁盘满和数据库断连只会在运行阶段出现。

客户端为请求生成关联编号，代理和应用沿途保留。Network 响应可以返回编号，用户反馈时提供它。维护者用编号和时间在代理、应用、数据库与外部服务日志中查同一次请求。编号随机生成，不包含用户邮箱或业务秘密。重试可以使用新的 request ID，同时保留同一个业务幂等键。两者用途不同，一个连接日志，一个防止重复操作。

各服务器时钟使用时间同步并记录时区。没有统一时间和编号，并发请求会让日志拼接依赖猜测。

## 日志级别不是严重度装饰

Debug 用于开发细节，Info 记录正常关键事件，Warning 表示可继续但需要注意，Error 表示操作失败，Fatal 表示进程或核心能力无法继续。具体名称按日志库调整。把每次 404 都记 Error 会淹没真实服务故障。把数据库连接失败记 Debug 又可能错过告警。级别与可行动影响对应。

生产可以降低详细度，但不能完全没有版本、启动、关键失败和关联编号。临时提高日志级别要限定时间，结束后恢复，避免磁盘与隐私风险。

无限增长的日志会占满磁盘，让应用和数据库一起失败；设置大小或时间轮转、总保留上限和磁盘告警；轮转前后都要能按时间查找。安全和故障调查需要一定保留期，隐私与成本又要求不过度保留。按日志类型制定期限，访问只给需要的人。OWASP Logging Cheat Sheet 还强调日志完整性、来源、时间和敏感信息排除。

删除日志不能用于掩盖事故。正常到期清理由策略执行，安全事件需要依法和按组织制度保留证据。

## 一个“保存按钮没反应”的完整例子

用户点击保存，页面无提示。Console 显示 `Cannot read properties of undefined`，文件指向表单提交函数。Network 没有新请求，说明错误发生在发送前。开发者用相同空白可选字段复现，发现代码假定字段对象一定存在。修复空值处理后，Console 不再报错，Network 出现 POST 并返回 201，页面显示新记录。

随后检查 Runtime Log，关联编号对应一次成功写入。再测试字段有值、无值、超长和服务器失败。四类证据组成完整验证，而不是只看到按钮弹出“成功”。

部署日志显示新构建成功，服务器 Runtime Log 也报告新提交。某些用户页面仍显示旧功能，Network 中 HTML 来自 CDN cache，引用旧 JS 文件名。临时禁用浏览器缓存后页面变新，说明代码和服务器不是主要问题。团队修正入口缓存策略，并让构建产物使用内容哈希文件名。

验证在普通浏览器、无痕窗口和两个地区网络进行。直接让所有用户清缓存只能当临时说明，不能替代发布设计。

## HAR 文件保存了什么

DevTools 可以把 Network 记录导出为 HTTP Archive，也就是 HAR 文件。它适合让另一位维护者查看请求顺序、地址、方法、状态、请求头、响应头、Timing 和部分正文，比一组零散截图更容易还原现场。导出前先完成一次最短复现，并限制在必要页面与时间，避免把整个浏览会话都收进去。

HAR 可能包含 Cookie、Authorization、查询参数、表单、邮箱、订单和响应正文，风险接近一份会话与业务数据包。发送前使用文本工具或受信任查看器检查全部条目，删除秘密后再确认文件仍能说明问题。若不能可靠脱敏，就在受控会话中共享屏幕或只导出必要字段，不把原始 HAR 上传公开 Issue 或通用 AI 服务。

导入别人提供的 HAR 时，也应把它当作不可信诊断文件。使用隔离的分析环境，不点击未知响应中的链接，不将其中令牌拿去重放。报告中记录导出浏览器版本、发生时间、目标环境和脱敏范围，接收者才能判断缓存与界面差异。

生产 JavaScript 常经过压缩与打包，Console 调用栈可能只显示一行巨大文件和难读函数名。Source Map 保存生成代码到源文件的映射，开发者工具或错误平台可以将位置还原到项目源码。它必须与准确构建匹配，拿新版本 Source Map 解释旧版本错误会得到错误行号。

公开 Source Map 可能暴露源码结构、注释与内部路径，是否部署给浏览器取决于项目安全与调试策略。另一种做法是把映射文件保存在受控错误平台，只上传构建标识。无论方式如何，Release 都应记录提交、构建号和资产哈希，使错误、脚本与映射属于同一版本。

找不到映射时仍可保留压缩调用栈、错误时间、浏览器、脚本 URL 和版本标识，再在相同提交的本地构建复现。不要为了得到漂亮栈而临时把生产改成未压缩调试模式，详细错误与源码可能扩大泄露范围。

## 多实例运行时要先确认是哪一台

生产服务可能同时运行多个容器或平台实例。一个实例配置错误时，用户请求会时好时坏，查看另一台正常实例的 Runtime Log 容易得出“没有异常”。代理或应用日志应记录实例 ID、区域、版本与请求编号，维护者先用 Network 响应头或入口日志确定请求落到哪里。

滚动发布期间，新旧版本会短暂共存。检查 Build Log 只能证明某个构建成功，部署状态也未必证明所有实例已经替换。按版本统计错误率和流量，确认旧实例退出、新实例健康，再结束观察。发现单实例异常时先隔离该实例并保留日志，避免重建后丢失证据。

DevTools 可以模拟较慢网络或离线，适合观察加载提示、超时、重试和缓存行为。它改变浏览器侧的请求条件，不能完整模拟移动基站切换、真实丢包、DNS 故障和服务器拥塞。测试记录应写使用的预设、是否禁用缓存和操作时间，不能把一次本地模拟当成所有地区网络的结论。

写操作在超时后可能已经到达服务器。界面提供重试前，应使用请求编号或幂等键确认结果，避免重复订单、邮件或文件。离线队列恢复时还要测试顺序、冲突和用户退出后的权限，Network 中看到请求重新发送只是第一步，Runtime Log 与数据库结果仍需核对。

## 控制台过滤可能隐藏真正错误

Console 和 Network 都支持按文字、级别、类型与域名过滤。排错开始时先记录当前过滤条件，必要时恢复默认，再进行一次最短复现。页面只显示 Warning 而 Error 被过滤，或 Network 只显示 Fetch 而文档请求失败，都可能造成错误边界判断。

清空界面前保存原始记录，修复后再用同一过滤与步骤比较。第三方扩展和浏览器自身消息可以通过无痕窗口或干净配置区分，但无痕模式会改变 Cookie、缓存和扩展状态，结果差异本身也要记录，不能直接说“浏览器坏了”。

[第 19 章的 DevTools 视频跟做卡](019-浏览器开发者工具-状态码和网络请求.md#ch019-h020)已经给出 Chrome 官方视频、准确观看区间、前置准备与跟做任务。本章不重复推荐另一段内容相近的视频。请在同一练习页复现错误，把注意力从按钮位置转到 Build Log、Console、Network 与 Runtime Log 之间的证据关系。

- 已判断失败发生在构建、页面执行、网络还是运行阶段
- Build Log 保留第一条有效错误和环境版本
- Console 错误包含文件、行号和调用栈
- Network 核对 URL、方法、状态、响应与耗时
- Runtime Log 使用时间、版本和关联编号
- 日志与截图已移除秘密和个人数据
- 缓存测试在普通模式和禁用缓存模式分别验证
- 修复后四类证据与用户功能一致

工具界面会改变，四类日志的阶段边界不会轻易改变。掌握边界后，面对 Vercel、Docker、Flutter 或服务器平台都能找到相应入口。
