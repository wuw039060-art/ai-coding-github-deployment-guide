# 运行环境问题与 Docker 的基本模型

开发者把项目发给你，附上一句“在我电脑上能运行”。你在自己的电脑安装相同语言，仍收到缺少库、版本不对或端口占用。把项目搬到服务器后，问题又出现一次。应用运行依赖代码以外的环境。它需要操作系统提供文件和网络，需要某个运行时版本，需要系统库、依赖包、环境变量和启动命令。任何一项不同，结果都可能不同。

Docker 让开发者把应用所需文件、依赖和启动约定打包成镜像，再从镜像创建隔离进程。这样能减少环境差异，也能让部署步骤更可重复。它不会自动理解应用，不会自动备份数据库，也不会让有漏洞的程序变安全。Docker 解决的是运行环境打包和容器生命周期问题。

## 先分清四个对象

Dockerfile 是构建说明，像一张可执行的装箱单。它写基础镜像、工作目录、复制哪些文件、安装什么依赖以及默认启动什么程序。镜像是构建后的只读模板。它包含分层文件系统和运行元数据。

容器是镜像的一次运行实例。一个镜像可以创建多个容器，每个容器有自己的进程、可写层和网络视角。Docker Engine 是接受命令、管理镜像、容器、网络和卷的服务。`docker` 命令行是与它通信的客户端。

这四个对象不能混用。修改 Dockerfile 不会自动改变已有镜像。构建新镜像也不会自动替换正在运行的容器。删除容器通常不会删除镜像，数据是否保留还要看存储位置。

某个 Python 程序在作者电脑使用 Python 3.13 和一个系统图像库。另一台电脑只有 Python 3.11，安装依赖时找不到对应编译工具。作者可以编写 Dockerfile，选择明确的 Python 基础镜像，安装系统库和项目依赖，再写启动命令。团队在支持相同架构的 Docker 环境构建和运行，步骤更接近。

如果项目忘记把某个依赖写入清单，Docker 构建仍会失败。容器只是让遗漏更早、更加重复地暴露，不会猜出缺失内容。

## 容器首先是隔离进程

Docker 官方工作坊把容器描述为主机上的沙箱化进程，并说明它拥有隔离的文件系统、网络和进程空间。容器不是一台缩小的完整电脑。常见容器只运行一个主要服务进程，不需要在里面启动 SSH、桌面和完整系统服务。

容器中的进程仍使用主机内核。Linux 容器依赖 Linux 内核能力。Windows 和 macOS 上的 Docker Desktop 通常通过一个 Linux 虚拟机运行 Linux 容器。这解释了为什么容器启动快、镜像通常小，也解释了它与虚拟机的隔离边界不同。

安装 Docker Desktop 后，界面看起来像本机直接运行容器。Linux 容器实际由 Docker Desktop 管理的 Linux 虚拟机承载。本地文件绑定挂载时，Docker Desktop 负责在本机文件系统和虚拟机之间共享。路径、性能和权限表现可能与原生 Linux 服务器不同。

本地容器运行成功，不证明服务器部署必然成功。还要确认处理器架构、环境变量、文件名大小写、网络和持久存储。生产服务器通常直接安装 Docker Engine，不需要桌面图形界面。安装方式要跟随 Docker 针对当前 Ubuntu 版本的官方说明。

## 一条命令背后发生什么

运行 `docker run` 时，客户端向 Docker Engine 发送请求。Engine 查找指定镜像，本地没有时可能从注册表下载。随后创建容器文件系统、网络和可写层，应用环境变量与挂载，再启动镜像定义的程序。

主程序退出，容器就停止。容器中另一个后台进程仍存在，也不能替代主程序的生命周期。Docker 官方运行文档说明容器拥有隔离文件系统、网络和进程树，并必须从镜像引用创建。

在已经安装 Docker 的本地终端或远程服务器运行。

```
docker version
docker info
```

`docker version` 显示客户端和服务端版本。只有客户端信息、服务端报连接错误时，Docker Engine 可能没有运行，或者当前用户无权访问。`docker info` 显示容器、镜像、存储、日志驱动和安全选项等主机信息。输出可能包含主机名和内部配置，分享前脱敏。

不要通过把 Docker API 无保护地开放到公网来解决连接问题。Docker 官方把守护进程访问列为高权限安全边界。

## 运行一个最小测试容器

下面命令会下载公开测试镜像并创建一个短期容器，需要网络和 Docker Engine 写入空间。

```
docker run --rm hello-world
```

`run` 从镜像创建并启动容器。`--rm` 让容器正常退出后删除这个容器实例。`hello-world` 是镜像名称。成功时会看到 Docker 客户端、Engine、镜像下载和容器输出的说明。它证明最小运行路径工作，不证明端口、卷或 Compose 已配置。

失败时先区分找不到 Engine、下载失败、权限拒绝和架构错误。不要用管理员权限掩盖所有问题。

## Docker 权限接近主机管理员权限

能控制 Docker Engine 的用户通常能启动高权限容器、挂载主机目录并改变主机文件。把用户加入 `docker` 组不是普通便利授权。Docker 安全文档提醒只有可信用户才能控制守护进程，因为绑定挂载可以让容器修改主机文件系统。

服务器上限制谁能运行 Docker 命令。CI 使用专用凭据和明确部署范围。不要把 Docker socket 挂进普通 Web 应用容器。Rootless 模式能降低部分守护进程风险，也有前置条件和行为差异。本书先建立权限边界，不把它当作一键安全开关。

镜像默认用户可能是 root。容器隔离和能力限制会缩小它相对主机 root 的权限，仍不应给应用多余能力。Dockerfile 可以用 `USER` 指定非特权用户。运行时还可移除能力、使用只读文件系统并限制挂载。

使用 `--privileged` 会显著扩大权限，不能为了让权限错误消失就添加。先找出应用真正需要的设备、文件或能力。容器逃逸不是唯一风险。应用仍可能读取挂载的秘密、删除卷中数据或攻击同一网络的数据库。

## 容器可写层不是持久数据库位置

容器运行时写入的文件默认落在它的可写层。删除容器后，这层数据也消失。重新创建容器是正常更新方式，所以需要保留的数据必须放到 Volume、Bind Mount 或外部服务。Docker 存储文档明确区分容器可写层与独立持久存储。

一个 SQLite 应用把数据库写在镜像中的 `/app/data.db`，第一次运行正常。更新时 Compose 重建容器，记录全部消失。故障不在 SQLite，而在数据位置没有声明持久化。第 46 章会把 Volume 与 Bind Mount 分开说明。

应用在容器内监听 3000，只对容器网络可见。要从主机或公网访问，需要发布端口或由同一容器网络的反向代理访问。端口发布把主机某地址和端口转发到容器端口。例如主机 8080 可以映射到容器 3000。

未指定主机地址时，Docker 可能绑定所有接口，造成意外公网暴露。数据库和应用上游端口要优先绑定本机或只留在内部网络。容器网络不会替代云防火墙与 UFW。第 46 章会画出完整路径。

## 镜像能重复，不代表运行结果完全相同

同一个镜像在不同机器上运行，环境变量、挂载数据、CPU 架构、内核、网络和外部服务仍可能不同。镜像标签 `latest` 还能在不同时间指向不同内容。需要可追踪部署时记录不可变摘要或明确版本标签。时间、随机数、第三方 API 和数据库状态也影响结果。Docker 提高环境一致性，不消除所有外部差异。

验证仍要包含实际配置、数据和请求，不能只说两台机器使用同一镜像。

应用依赖较多、需要在多台机器重复运行、由多个服务组成，Docker 能明显减少安装差异。一个简单静态网站使用 Pages 托管，不需要为了“专业”加入容器。一个单文件脚本只在自己的电脑运行，也可能直接使用语言环境更简单。

服务器上需要 Node.js、数据库、Redis 和代理时，Compose 能把服务、网络、卷和配置写在一处。它适合本书的个人项目部署范围。是否使用 Docker 要看它减少的环境工作，是否大于新增的镜像、存储、网络和更新责任。

## Docker 没有解决什么

它没有替你修复代码错误，没有决定数据备份，没有自动管理域名证书，也没有理解业务权限。容器重启策略能重新启动退出进程，无法修复数据库密码错误。健康检查能报告不健康，无法决定数据是否一致。

多容器运行在同一台 VPS，仍共享主机故障。Docker Compose 也不会自动提供跨服务器高可用。把边界写清楚，才能正确选择下一层工具。

第一次练习优先使用 Docker Desktop 或没有真实数据的测试 VPS。不要在已经运行生产数据库的主机执行清理命令。为练习创建独立目录和 Compose 项目名。记录镜像、容器、网络和卷。练习结束逐项确认再清理。

命令中的 `--rm` 只删除短期容器，不删除镜像。涉及 `down --volumes`、`volume prune` 和 `system prune` 时必须等第 49 章后再使用。现在只需要能解释 Dockerfile、镜像、容器和 Engine，能运行最小测试，知道容器数据和主机权限是两条高风险边界。

## 客户端与服务端可以不在同一台机器

`docker` 命令是客户端，Docker Engine 是服务端。默认情况下，两者在同一台主机，通过本地 socket 通信。Docker Context 可以让客户端连接远程 Engine。命令看起来相同，创建和删除却发生在远程主机。执行前运行 `docker context show`，确认当前目标。

不要把远程 Engine 的 TCP 端口无认证暴露。通过 SSH 或双向 TLS 按官方方式保护，并限制账号。终端提示符只能说明 shell 在哪里，Docker Context 还可能指向另一处。高风险命令前两者都要核对。

Engine 要创建命名空间、网络、挂载和控制组，还要管理主机存储。传统 rootful 模式的 daemon 因此拥有主机 root 权限。本地 socket 文件通常只允许 root 和 docker 组访问。把 Web 应用容器挂载这个 socket，相当于给它控制主机容器的能力。

监控工具确实可能需要读取 Docker API。使用只读代理、最小权限和受信镜像，仍要评估接口是否允许创建容器。Rootless 模式把 daemon 与容器放进用户命名空间，能降低部分风险，但端口、存储驱动和资源控制可能受限。采用前在测试机核对当前文档。

## 容器启动的是一个主进程

镜像的 `ENTRYPOINT` 与 `CMD` 共同确定主进程。它在容器中通常是 PID 1。Docker stop 会先向主进程发送停止信号，等待超时，再强制终止。应用应接收信号、停止新请求并完成必要清理。启动脚本若产生子进程却不转发信号，容器停止可能拖延或丢失任务。使用 exec 形式启动真实程序，或加入轻量 init。

数据库和队列写入必须测试正常停止。直接 kill 只是最后手段。

常用建议是一个容器承担一个主要职责，而不是机械限制只能有一个进程。Web 服务器可能创建多个工作进程，仍属于一个服务。把数据库、Web 和定时任务全塞进同一容器，会让更新、日志、资源和故障边界混乱。Compose 将它们拆成服务更清楚。

辅助进程确有同生共死需求时，可以同容器运行，但要有正确进程管理与信号处理。判断单位是生命周期和责任，不是进程数量。

## 镜像层与容器层的关系

镜像由多个只读层组成，容器在顶部增加可写层。多个容器可以共享同一镜像层，各自的修改互不相同。这让创建容器高效，也让现场修改只属于单个实例。第二个容器不会自动看到第一个容器安装的软件。

删除镜像前，Docker 会检查容器引用。强制删除或全局清理可能破坏回滚材料。镜像大小显示层的逻辑总量，主机实际新增占用受共享与缓存影响。

容器有长 ID，也可有易读名称。名称只在当前 Docker daemon 中唯一。容器内 `hostname` 默认可能显示短 ID，可以通过配置覆盖。它不是公网 DNS，也不会自动加入外部网络。Compose 服务名用于项目网络发现，容器名称还可能包含项目和序号。脚本优先使用服务名或标签，不依赖自动生成完整名称。

日志记录服务和容器 ID，重建后 ID 会变化。业务请求标识才能跨容器对应。

## 环境变量不是镜像内容的一部分时

Dockerfile 的 `ENV` 会进入镜像默认元数据，任何使用镜像的人都可能查看。运行时 `-e` 或 Compose environment 在创建容器时覆盖。真实秘密不写 Dockerfile。运行时环境也能从 inspect 或高权限接口看到，必须限制 Docker 控制权。

应用从文件读取秘密时，文件通过受控挂载提供。轮换后重建或通知应用重新读取。只在 shell 中 export 变量，Compose 变量替换与容器环境还受配置优先级影响。用脱敏 `config` 和应用检查验证。

容器内 `127.0.0.1` 指向这个容器自身，不是 Docker 主机，也不是另一个数据库容器。Web 容器连接 Compose 数据库应使用服务名 `db`。连接主机服务需要 Docker 平台提供的受控地址或网络方案，Windows、macOS 与 Linux 表现不同。

把数据库地址写成 localhost，是多容器初学故障之一。日志会显示连接拒绝，却不说明目标写错。先画请求起点，再决定名称。主机、容器和浏览器各有自己的 localhost。

## 时间与时区

容器共享主机内核时钟，用户空间时区和应用配置可能不同。日志显示 UTC 不表示时钟错误。不要在容器中手工改系统时间。校准 Docker 主机的时间同步，应用存储 UTC，界面按用户时区显示。

定时任务要明确时区。镜像更新可能改变时区数据库，发布后验证夏令时与业务计划。事故记录写带时区时间，才能与主机、代理和数据库日志比较。

Linux 镜像必须支持主机处理器架构。多架构标签会选择对应内容，镜像内下载的额外二进制仍可能只支持一种架构。容器共享主机内核，应用需要特定内核模块或系统调用时，镜像打包无法补上。主机内核和安全策略必须支持。

GPU、USB 和特殊设备需要显式授权与运行时支持。为了访问设备加入 `--privileged` 会扩大到远超所需。列出真正设备和能力，使用最小映射。在目标服务器实测。

## Docker Desktop 的资源上限

Windows 与 macOS 的 Linux 虚拟机有 CPU、内存和磁盘分配。主机还有大量内存，Docker 虚拟机也可能先达到上限。构建突然退出或容器 OOM 时，查看 Docker Desktop 资源与容器限制。增加后重启 Desktop 可能中断所有本地容器。

虚拟磁盘会随镜像、卷和缓存增长，删除对象后宿主机文件不一定立即缩小。按当前 Desktop 文档管理，不直接改内部虚拟磁盘。本地设置不进入 Compose，团队成员要记录最低资源需求。

容器应用先要监听正确地址，Docker 再发布主机端口，主机防火墙最后决定外部能否访问。应用只监听容器内 `127.0.0.1` 时，端口发布也可能无法从容器外到达。容器中通常需要监听 `0.0.0.0`，再由主机绑定限制公网。

不要把两处 `0.0.0.0` 混为一谈。容器监听全部容器接口，与主机端口发布到全部主机接口是两个层次。从容器内、本机端口和外部 HTTPS 分别验证。

## 容器不是恶意代码沙箱

运行陌生镜像会执行其中程序。它可能联网、消耗资源，并读取你授予的挂载与秘密。只从可信来源取得镜像，查看 Dockerfile、签名和摘要。不要挂载主机根目录、Docker socket、SSH 目录和个人文档。

限制 CPU、内存、网络和文件系统，仍不能保证完全隔离。处理不可信代码需要更专业的沙箱或虚拟机边界。镜像名像官方项目也可能是仿冒仓库，核对发布组织与文档链接。

静态站点托管、平台原生函数和已经由 PaaS 管理的运行时，额外容器层可能没有收益。开发者完全不理解镜像与卷，却把唯一数据库放进容器层，风险会高于直接 systemd 部署。先把应用在本地稳定运行，写清依赖和启动。Dockerfile不能替代缺失的项目说明。

工具选择可逆。项目成熟后再容器化，仍可从锁文件和运行文档出发。

## 第一次判断故障发生在哪一层

容器启动失败时，先不要连续改 Dockerfile。把问题分成四层，每层只做一个能够得到明确结果的检查。第一层是主机。确认 Docker Desktop 或 Docker Engine 正在运行，磁盘还有空间。连 `docker version` 都无法返回服务端信息时，应用配置还没有进入排查范围。

第二层是镜像。运行 `docker image inspect 镜像名`，确认镜像存在、架构正确。拉取失败时检查镜像名称、Registry 登录、网络与标签，不要用关闭证书校验来绕过错误。第三层是容器进程；用 `docker ps -a` 看退出状态，再读日志和退出码；容器显示 `Exited (1)`，说明主进程已经运行过并以错误结束；显示 `Created`，则可能连启动阶段都没有完成。

第四层是外部访问。容器为 `Up` 只说明进程尚未退出。还要检查应用监听地址、端口发布、主机防火墙和反向代理。浏览器打不开不能直接推断 Docker 坏了；例如一个笔记服务显示 `Up`，本机访问发布端口却被拒绝；进入容器后发现程序只监听 `127.0.0.1`；修正应用监听为容器内 `0.0.0.0`，重建后本机端口恢复；这个例子说明状态、进程和网络是三种证据。

把每次检查的命令与结果写下来。这样即使最后需要请开发者帮助，也能说明故障停在哪一层，而不是只说“Docker 跑不起来”。
