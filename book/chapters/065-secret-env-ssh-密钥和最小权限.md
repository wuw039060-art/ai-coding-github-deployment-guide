# Secret、.env、SSH 密钥和最小权限

Secret 可以译为秘密值，指一旦泄露就可能让别人冒充程序、访问数据或控制基础设施的凭据。API Key、数据库密码、会话签名密钥、云平台令牌、SSH 私钥、应用商店签名材料都属于这一类。它们不是普通配置，也不能因为只用于个人项目就写进代码或截图。

保护秘密要覆盖完整生命周期，包括生成、保存、授权、使用、轮换、撤销和审计。`.env` 只是一种本地载入配置的文件形式，GitHub Actions Secrets 只是一种托管机制，SSH 密钥只解决一类身份认证。真正的目标是让每个主体只在需要的时间获得最低必要权限，并能在泄露或离职时迅速撤销。

## 先分清秘密、标识和普通配置

用户名、项目 ID、公开 API 地址通常是标识或配置，不一定需要保密；密码、私钥、访问令牌和 Cookie 会赋予访问能力，必须保护。客户端应用里的任何固定值最终都可能被提取，因此 Flutter、网页 JavaScript 和桌面安装包中不能长期保存能够控制后端的主密钥。客户端只应得到面向当前用户、权限受限且可以过期的凭据。

“环境变量”也不自动等于秘密。变量可能被子进程继承、出现在错误报告、调试界面或部署平台导出中。环境变量适合在进程启动时注入秘密，但存储位置、访问权限、日志屏蔽和轮换仍要另外设计。对高价值凭据，专用秘密管理服务通常能提供版本、审计和短期凭据，个人项目至少也要使用平台的受控秘密功能。

会话 Cookie 是浏览器保存的认证材料。使用 HTTPS、`Secure`、`HttpOnly` 和合适的 `SameSite` 属性可以降低部分风险，但后端仍要验证会话、设置过期和支持撤销。把 Cookie 复制给他人等同于把当前会话交出去，排错截图只说明属性和是否存在，不展示完整值。

很多框架从 `.env` 读取本地变量，例如数据库地址与开发用 API Key。文件通常是明文，能读取电脑或备份的人也能读取内容。它适合个人开发机的受控目录，不适合通过聊天、邮件或公开仓库传递。团队可提交 `.env.example`，只保留变量名与安全示例，不放真实值。

```
DATABASE_URL=postgresql://app_user:[REPLACE_ME]@localhost/app
MAIL_API_KEY=[REPLACE_ME]
SESSION_SECRET=[GENERATE_A_RANDOM_VALUE]
```

示例文件告诉读者需要哪些键，真实 `.env` 由每个环境单独创建。变量名本身也可能暴露架构，但通常比真实值风险低；若项目高度敏感，应按实际威胁模型处理。生产秘密不应从开发电脑复制一份长期共用，开发、预览和生产应使用不同凭据与权限。

`.gitignore` 可以阻止尚未跟踪的 `.env` 被新提交，却不会自动移除已经提交的文件。GitHub 官方忽略文件文档与模板仓库可作为起点，项目仍要检查框架生成文件和本地工具。常用规则可以写成下面形式，随后用 `git status` 验证真实文件不在待提交列表。

```
.env
.env.*
!.env.example
```

运行位置为本地仓库根目录。保存规则后执行 `git status --short`，预期真实 `.env` 不出现，而 `.env.example` 可以正常跟踪。若 `.env` 仍显示为已跟踪，说明它早已进入 Git 索引，不能仅靠新增忽略规则解决。此时先停止推送并进入泄露处置流程。

## 秘密一旦提交，第一步是撤销

删除最新文件或追加一个撤销提交，无法让已经克隆、缓存或记录的秘密失效。发现泄露后先判断它能访问什么，立即在提供方轮换或撤销，再检查使用日志与异常操作。新的秘密必须与旧值不同，并更新所有合法使用者，避免服务因轮换同时中断。

GitHub 的敏感数据移除文档说明了历史重写的复杂性，包括分支、标签、协作者克隆和缓存。历史清理只减少旧值继续传播，不能替代轮换。公共仓库重写历史还会改变提交 ID，影响现有分支与拉取请求，应由仓库负责人规划，并通知协作者重新同步。

GitHub Push Protection 可能在命令行推送前阻止已识别秘密。这是一道补充防线，无法识别每种私有格式，也不能证明仓库完全安全。项目还应在提交前检查 Diff、限制令牌权限、设置过期、审查依赖与 CI 输出。Dependabot 提醒的是已知依赖风险，也不能替代秘密扫描和权限审计。

高风险操作

> 不要为了“让 GitHub 不再报警”选择绕过秘密保护，也不要先公开一段真实值询问它是不是密钥。把旧值视为已泄露，先撤销，再用占位符讨论格式与配置。

## GitHub Actions Secrets 只在工作流需要时注入

仓库、环境和组织级秘密适用于不同作用范围。生产部署应优先放在受保护 Environment 中，配合分支、审批与权限策略，让普通测试工作流拿不到生产凭据。工作流使用 `${{ secrets.NAME }}` 引用值，日志遮罩提供辅助保护，但拼接、编码、转换或第三方 Action 仍可能泄露内容。

```
jobs:
  deploy:
    environment: production
    permissions:
      contents: read
    steps:
      - name: Deploy
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
        run: ./scripts/deploy.sh
```

这里把令牌只注入需要它的步骤，并把默认仓库权限收窄为只读。真实项目还要固定第三方 Action 版本、审查脚本是否回显环境、限制哪些分支能进入 production。不要运行 `env`、`set` 或调试跟踪来输出全部变量，也不要把秘密写入构建产物供网页或 App 下载。

更安全的云部署可以使用短期身份联合，让 CI 在运行时换取短期令牌，减少长期静态秘密。是否可用取决于平台。个人项目暂时使用长期令牌时，应限制资源、操作和有效期，建立轮换日期，并保留一个不依赖同一令牌的撤销入口。

## SSH 密钥包含公钥和私钥

SSH 公钥可以放到服务器授权列表，私钥留在用户控制的设备。服务器用公钥验证客户端确实持有对应私钥，私钥不应上传服务器、发送给运维或提交仓库。多人管理一台服务器时，每人使用自己的密钥，离开项目时删除该人的公钥，避免共用一份无法追责的私钥。

Windows 11、现代 macOS 与多数 Linux 发行版通常提供 OpenSSH 客户端。运行位置为自己的电脑终端，下面命令生成一对 Ed25519 密钥。文件名使用项目专用名称，避免覆盖已有默认密钥。

```
ssh-keygen \
  -t ed25519 \
  -f ~/.ssh/project_notes_ed25519 \
  -C "notes-server-admin"
```

命令会询问 passphrase，建议设置并保存在受控密码管理器中。预期得到私钥 `project_notes_ed25519` 和可分享的公钥 `project_notes_ed25519.pub`。若提示文件已存在，应停止并确认，不要直接覆盖。Windows PowerShell 中 `~` 通常指当前用户目录，实际路径可通过命令输出确认，书中不假设每台电脑目录完全相同。

查看并复制公钥时，只读取带 `.pub` 的文件。Ubuntu 官方 OpenSSH 文档介绍密钥认证与服务器配置。将公钥添加到服务器账号的 `~/.ssh/authorized_keys` 后，先保持现有 SSH 会话不要关闭，再从第二个终端测试新密钥。

```
ssh \
  -i ~/.ssh/project_notes_ed25519 \
  admin@server.example.com
```

预期进入正确的普通管理账号。若失败，先看用户名、主机、文件路径、服务器授权文件所有者与权限，再用服务器日志定位。不要因为一次失败就关闭密码策略、允许 root 远程登录或给私钥设置宽泛权限。新会话成功并确认 `sudo` 能按策略工作后，才考虑收紧旧认证方式。

## 私钥的保存、备份和代理

私钥应保存在只有当前用户可读的位置，并用 passphrase 保护。设备丢失、人员离开或怀疑复制时，要从所有服务器与平台撤销对应公钥，再生成新密钥。仅修改私钥文件名没有任何安全作用。公钥注释用于识别用途，不提供认证保证，资产清单应另外记录指纹、持有人、用途、创建和撤销日期。

SSH agent 可以在解锁后暂存私钥，减少重复输入 passphrase。便利也扩大了当前登录会话可用权限，离开电脑要锁屏，高风险服务器可设置更短会话与额外审批。不要启用不理解的 agent forwarding，远端主机若被攻破，可能借用转发的身份访问其他系统。

备份私钥要加密并限制副本数量。更理想的恢复方式是在新设备生成新密钥，再由已有管理员添加公钥，而不是到处复制同一私钥。若项目只有一个管理员，应预先准备受控恢复流程，避免电脑损坏后只能通过云平台紧急控制台重置服务器。

最小权限指主体只拥有完成当前任务所需的资源与动作，并限制在必要时间。一个部署工作流可能只需读取仓库、上传某个服务版本和读取部署状态，不需要删除整个云账号；一个 Web 应用数据库用户可能只需访问自己的 schema，不需要创建超级用户或读取其他项目。

权限设计可以从三张清单开始。第一张列主体，包括人、CI、应用、备份任务和第三方服务。第二张列资源，包括仓库、服务器、数据库、对象存储和商店应用。第三张列动作，包括读取、写入、部署、删除、授权和查看日志。将必要交叉点授予角色，默认未列出的动作不开放。

OWASP 授权指南强调默认拒绝、每次请求检查权限和避免只依赖客户端。网页隐藏“删除”按钮只改善界面，攻击者仍可直接调用 API。后端必须根据当前身份、目标资源与动作重新判断，例如用户只能修改属于自己的笔记，管理员权限也要限制到确有需要的人员。

临时维护权限应设置到期时间并在任务结束后撤销。紧急授予 root 或组织管理员后，如果没有记录和回收，就会永久扩大风险。季度检查账号、部署令牌、SSH 公钥和商店成员，删除确认不再使用的权限；不确定时先联系持有人或禁用，再按可恢复流程处理。

## 根账号与日常账号分开

云平台、域名注册商和商店的所有者账号负责计费、成员与恢复，日常开发尽量使用权限较低的成员账号。根账号使用强密码、多因素认证和受控恢复码，不用于普通 API 调试。共享团队不要共用一个邮箱和密码，否则无法知道谁做了修改，也难以在人员变化时单独撤销。

服务器日常 SSH 进入普通账号，需要管理动作时通过 `sudo` 按策略提升。应用进程使用独立系统用户，不能以 root 运行只为绕过文件权限。日志目录、上传目录和配置文件分别授予最小读写权限。遇到 `Permission denied`，先确认哪个进程需要访问哪个路径，再修改所有者或组，不使用 `chmod 777` 当通用答案。

数据库也应区分迁移账号、运行账号、只读分析账号和备份账号。迁移需要改变结构，不代表长期运行进程也需要这些权限。备份账号与备份存储权限还要配合恢复测试，避免“能读取所有数据”的凭据在普通应用容器中长期存在。

应用不得打印完整环境变量、Authorization 头、Cookie、连接串和私钥内容。CI 失败时也不要用 `printenv` 寻找变量名。日志可以记录秘密的稳定内部编号、提供方、权限范围和最后四位等低风险信息，具体做法需评估是否仍可识别或被利用。OWASP 日志指南要求排除访问令牌、密码和高敏感个人信息。

异常页面面向用户时只显示安全的错误编号与下一步，详细调用栈留在受控服务端。数据库错误可能包含表名、查询片段和内部地址，反向代理错误也可能暴露上游。调试模式只在隔离环境短期开启，不能把生产详细错误公开给浏览器。

发生泄露后，日志与下载记录用于判断影响范围。审计应记录谁在何时读取或修改了秘密、工作流使用了哪个版本、轮换是否成功，但审计系统本身不能保存秘密明文。OWASP 的秘密管理资料强调集中管理、访问控制、轮换与审计。

## 短期令牌和刷新机制也要能撤销

用户登录后常得到短期访问令牌，过期后再用刷新令牌换取新令牌。短有效期可以缩小访问令牌泄露后的时间窗口，刷新令牌价值更高，应放在平台提供的安全存储并支持服务端撤销。浏览器通常优先使用受保护 Cookie，移动端使用系统安全存储，具体选择要结合威胁模型。

退出登录应撤销或失效相关会话，改密码、账号被盗和管理员封禁也要有批量撤销机制。仅删除客户端本地值，无法阻止已经复制的令牌继续使用。后端保存会话或令牌版本、设备和最后活动等必要信息，日志记录内部会话编号，不记录完整值。

服务到服务令牌也应短期、限定受众与权限。一个对象存储上传令牌不应同时拥有删除所有备份的能力，预览环境凭据不能访问生产数据库。第三方 API 不支持细粒度权限时，使用独立项目或账号隔离，并在风险清单中记录限制。

## 建立秘密清单和轮换演练

秘密清单记录名称、提供方、环境、持有人、用途、权限范围、创建时间、到期、轮换方法、使用者和撤销入口，不记录真实值。每个秘密都应能回答“谁会因轮换中断”和“旧值怎样确认失效”。无人能回答的长期令牌应优先审查。

轮换先创建新版本，在一个低风险使用者上验证，再逐步更新其他使用者，最后撤销旧值并查看失败日志。直接先删旧值可能造成停机，永久保留新旧两值又失去轮换意义。对于支持双密钥的服务，可以设置短重叠窗口；不支持时需要维护窗口或代理机制。

每季度选择一类高价值秘密做演练，例如部署令牌或数据库应用密码。记录从生成、注入、验证到撤销的耗时，确认不需要在群聊传播值，也不依赖某个离线人员。发现工作流、旧服务器或备份脚本仍使用旧值时，修正文档与资产清单。

安装 GitHub App、OAuth 应用、CI Action 或部署集成时，应阅读它请求的仓库、组织和账号权限。一个只做代码格式检查的工具不应获得仓库管理与秘密读取。试用结束后撤销授权，检查它创建的 Webhook、部署密钥和令牌是否一并删除。

第三方 Action 运行在工作流环境，可能读取注入的秘密和修改仓库。固定可信版本、限制 `permissions`、把生产秘密放入需要审批的环境，并避免让来自不可信分支的代码接触秘密。工具维护者被攻破时，最小权限可以限制影响范围。

供应商发生安全事件时，先确认受影响产品、时间和凭据类型，再轮换相关秘密、审查访问日志与依赖版本。不要把所有系统的主密钥放在同一服务中，也不要因为尚未发现异常就跳过撤销一个已经明确暴露的令牌。

## 设备丢失和人员离开要按身份撤销

管理员电脑丢失时，先从另一受控设备撤销该人的 SSH 公钥、平台会话、个人访问令牌与设备授权，再检查异常登录。远程擦除可以作为补充，不能代替服务端撤销，因为设备可能离线或数据已被复制。新设备生成新密钥，不从不可信备份直接恢复旧私钥。

人员离开项目时，按身份清单处理仓库、云平台、域名、服务器、数据库、商店、密码管理器和第三方工具。共用账号会使单人撤销困难，因此要尽早改成独立成员。交接只转移资源所有权和文档，不要求离开人员发送个人私钥或恢复码。

撤销完成后验证旧身份确实无法访问，并检查自动任务是否错误依赖个人令牌。需要保留的 CI 与部署任务迁移到专用服务身份，权限保持最低并设负责人。整个过程记录时间与回执，不在离职清单中复制真实凭据。

维护者发现公开仓库两小时前提交了生产数据库连接串。正确的第一步是立即在数据库或平台撤销旧密码，创建权限相同或更小的新凭据，并更新生产秘密存储。随后查看连接与审计日志，确认旧凭据是否从异常来源使用，必要时隔离数据库和通知相关负责人。

服务恢复后，再从仓库当前文件和历史中移除秘密，检查 Fork、构建日志、Release 资产、Issue 和聊天附件。历史重写由仓库负责人统一执行，协作者按说明重新同步。最后增加 `.gitignore`、提交前检查、Push Protection 和更短有效期，行动项要有负责人和验收。

只删除 `.env` 并提交一次会留下可用旧密码，只重写 Git 历史也不能让已复制值失效。处置顺序必须围绕访问能力，先撤销，再调查、清理和预防。报告中始终使用 `[REDACTED_SECRET]`，不为证明泄露而再次传播真实值。

## AI 可以审查配置结构，不能接收真实秘密

AI 可以检查 `.gitignore`、工作流权限、环境变量名称、SSH 配置结构和权限矩阵，也可以生成轮换清单。提供占位符、脱敏 Diff 与目标权限，不要粘贴真实 `.env`、私钥、恢复码、Cookie 或令牌。让 AI 明确哪些建议会改变外部权限，并要求在执行前停下确认。

AI 声称秘密“已安全保存”时，仍要亲自检查目标平台、访问成员、工作流日志和实际部署。生成新令牌、撤销旧令牌、添加 SSH 公钥、改变组织角色都会影响外部系统，必须由账号持有人确认。任何测试都使用专用低权限凭据，不拿生产主密钥验证一段未知脚本。

- 已区分公开标识、普通配置与真正秘密
- 客户端包中没有长期主密钥
- `.env.example` 只有变量名和安全占位符
- `.gitignore` 已用 `git status` 验证
- 泄露处置先撤销和轮换，再清理历史
- CI 只向必要步骤注入最低权限秘密
- SSH 私钥不离开持有人设备，公钥按人分配
- 新 SSH 认证在第二个会话验证后才收紧旧方式
- 人、CI、应用和备份任务使用独立角色
- 临时权限有到期和撤销记录
- 日志、截图与 AI 输入不含秘密明文
- 根账号、多因素认证和恢复材料得到独立保护

秘密安全取决于访问能力能否被限制和撤销。文件名、环境变量和日志遮罩只是手段，生命周期、最小权限、独立身份与可验证轮换才组成完整控制。个人项目规模较小，更应从第一天避免共用账号和永久主密钥，因为事后拆分往往更困难。
