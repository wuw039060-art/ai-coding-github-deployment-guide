# Secret、.env、SSH 密钥和最小权限

排错时人最容易把秘密贴出来。截图里有数据库连接串，日志里有 Authorization，`.env` 里有 API key，服务器命令里有私钥路径。AI 可以帮你看配置结构，不能接收真实秘密。秘密一旦泄露，重点动作是撤销和轮换，删除截图只能减少继续传播。

## 先分清秘密、标识和普通配置

秘密是拿到后能直接访问资源或冒充身份的东西。数据库密码、API key、服务账号 JSON、JWT 签名密钥、SSH 私钥、支付密钥、对象存储访问密钥都属于秘密。它们不能进入 Git、截图、公开 Issue 和普通聊天。

标识用于说明对象是谁。项目 ID、包名、Bundle ID、公开域名、证书指纹、公钥、客户端 ID，有些可以公开，有些要看场景。它们通常不能单独访问资源，但能帮助攻击者定位目标。分享时只给排错需要的部分。

普通配置包括端口、环境名称、功能开关、超时时间、日志级别和公开 API 地址。普通配置也可能带来风险。把管理后台开到公网，把 Debug 日志留在生产，把测试支付切到正式支付，都会造成事故。

## .env 不应进入 Git

`.env` 常保存本地环境变量。它方便开发，也很容易泄露。项目应把 `.env` 放进 `.gitignore`，同时提供 `.env.example`。示例文件只写变量名和安全占位符，不写真实值。

```text
DATABASE_URL=请在部署平台中配置
PAYMENT_SECRET=不要写入仓库
LOG_LEVEL=info
```

前端项目要特别小心。构建时进入浏览器包的变量，会交到用户设备上。名称里带 public 或客户端前缀的变量，通常只能放公开配置。真正服务端密钥应留在后端。小程序 AppSecret、支付密钥和云服务服务端凭据也不能写进前端包。

环境变量名称也会泄露结构。公开一个变量名通常问题不大，但成组变量能暴露服务商、数据库类型和内部系统。文档中保留必要名称，隐藏真实值和敏感路径。截图部署平台时，注意页面可能同时显示变量值、上次修改人和项目 ID。

本地 `.env` 与部署平台 Secret 要分开管理。本地值用于开发，生产值由平台或秘密管理系统注入。不要把生产 `.env` 下载到每个人电脑上。需要临时排查生产配置时，优先查看变量是否存在、版本是否一致和最后更新时间，不直接展示值。

## 秘密泄露后先撤销

秘密一旦提交到 Git 或发到不可信环境，第一步是撤销或轮换。删除当前文件不够。Git 历史、构建日志、缓存、截图、聊天记录和第三方工具都可能保留副本。先让旧密钥失效，再更新依赖它的服务。

处理顺序可以这样写。

1. 判断泄露了哪个秘密，能访问哪些资源。
2. 在服务商控制台撤销或轮换。
3. 更新部署平台、CI 和本地安全存储。
4. 检查异常访问和费用。
5. 清理仓库历史或限制访问。
6. 记录影响、时间和负责人。

若泄露的是生产数据库、支付或用户数据相关密钥，要按组织安全流程处理。不要把“我已经删了”当成结束。

泄露范围要具体判断。一个只读测试 key 和生产支付密钥的风险完全不同。一个已经过期的短期 token 与长期服务账号也不同。先确认它能访问哪些资源、权限范围、是否有异常使用、是否需要通知用户或客户。不要把所有泄露都轻描淡写，也不要在没有判断时制造恐慌。

清理 Git 历史要谨慎。重写公开仓库历史会影响协作者，也不能保证别人本地副本消失。密钥轮换始终排在前面。历史清理、访问限制和通知协作者属于后续控制。若仓库已经公开过，默认按泄露处理。

## GitHub Actions Secrets

CI 里的秘密应只在需要的工作流注入。部署生产的密钥，不应给所有分支、所有 Pull Request 和所有人可见。第三方贡献者的 PR 更要小心，不能让未信任代码读取生产密钥。

工作流日志要避免打印秘密。很多平台会自动遮蔽已登记的 Secret 值，但遮蔽不是安全边界。拼接、编码、截断或写入文件后再打印，可能绕过遮蔽。排错时不要加 `env` 全量输出。

服务账号使用最小权限。只需要上传对象，就不要给删除桶和管理账号权限。只需要部署某个项目，就不要给整个组织管理员权限。定期检查哪些 Secret 已不再使用。

工作流权限也要看。仓库默认 token 可能拥有读取代码、写入包、创建 Release 或部署页面的权限。能设只读就设只读，需要写权限的 job 单独声明。把测试、构建和部署拆开，能减少普通 PR 接触生产秘密的机会。

环境保护规则很有用。生产部署可以要求人工批准，只允许主分支触发，并限制谁能查看或修改生产 Secret。批准人看到的应是提交、差异、测试结果和将要部署的环境，而不是一串没人读的命令。

## SSH 密钥和服务器账号

SSH 密钥包含公钥和私钥。公钥可以放到服务器或平台账号里，私钥留在自己设备或受控密钥库。私钥文件不要发给别人，不要贴给 AI，不要放进项目仓库。若必须临时授权，给对方自己的账号和公钥，事后撤销。

服务器日常操作不要共享 root 密码。每个人使用独立账号，必要时通过 sudo 执行授权命令。这样出了问题能知道谁在什么时候做了什么。共享账号会让审计失明。

密钥要有口令和备份策略。电脑丢失后，先撤销相关公钥、令牌和会话，再检查服务器登录记录。离职时撤销账号、SSH key、云平台 token、GitHub 权限、部署平台权限和商店账号角色。

SSH agent 会把解锁后的私钥临时提供给命令使用，能减少反复输入口令。它也带来边界问题。不要把 agent 转发到不信任服务器。被控制的跳板机可能借用转发能力访问其他机器。需要跳板时，使用受控配置和最小目标范围。

服务器上的 `authorized_keys` 要定期看。里面的注释应能说明这把公钥属于谁、什么用途、何时加入。发现无法识别的 key，不要立刻删除生产唯一入口。先确认是否有替代登录方式，再撤销并记录。

## 短期令牌也要能撤销

现代系统常用短期访问令牌和刷新令牌。短期令牌泄露后的影响时间较短，刷新令牌泄露后可能不断换新令牌。登录、退出、改密码、账号冻结和设备丢失，都要有让旧令牌失效的机制。

客户端只删除本地令牌，不能阻止已经复制出去的令牌继续使用。后端需要维护失效策略、签名密钥轮换和会话列表。高风险动作可以要求重新认证。

日志不要记录完整令牌。需要定位时，记录不可逆短指纹、请求编号和用户脱敏标识。崩溃报告、客服系统和 AI 分析服务也算数据接收方。

服务间令牌也需要撤销路径。后端调用对象存储、支付、邮件、AI API、地图和推送时，常使用长期密钥。能使用短期凭据或限定作用域时，优先缩小权限。不同环境使用不同密钥，测试环境泄露时不应能访问生产资源。

密钥轮换会影响运行中的服务。旧密钥撤销前，新密钥要已经部署并验证。对支持双密钥的服务，可以先增加新密钥，切流量，再撤销旧密钥。对只支持单密钥的服务，要安排维护窗口和回退计划。

## 第三方平台 token

部署平台、云服务、GitHub、支付、短信、邮件、地图、AI API 和商店后台，都可能提供 token 或 API key。它们常被复制到本地脚本、CI、临时测试工具和外包交付文档中。每复制一次，撤销难度就增加一次。

为第三方 token 单独记录作用域和到期时间。能设置只读就不要给写权限。能限制项目就不要给组织权限。能设置 IP、环境或回调域名限制，就写进配置。不能限制的高权限 token，要减少使用场景，并加密保存。

供应商账号也要能交接。个人邮箱注册的 API key，离职后可能没人能轮换。公司或团队项目使用组织账号，并开启二步验证和备份联系人。支付、商店和云平台这类高风险账号，不要依赖单个人的手机验证码。

## 建立秘密清单

秘密清单不写秘密值，只写名称、用途、保存位置、权限、负责人、轮换周期、最后验证时间和撤销办法。

| 名称 | 用途 | 保存位置 | 权限 | 负责人 | 撤销办法 |
| --- | --- | --- | --- | --- | --- |
| 数据库连接 | 后端访问数据库 | 部署平台 Secret | 读写业务库 | 后端负责人 | 控制台轮换 |
| 对象存储 key | 上传图片 | 云平台 IAM | 指定桶读写 | 运维 | 禁用 key |
| SSH key | 服务器登录 | 个人密钥库 | 指定主机 | 本人 | 删除公钥 |

每季度做一次轮换演练。演练不要求每次都把所有秘密换掉，重点是确认你知道在哪里换、换完哪些服务要重启、旧密钥是否失效。没有演练，事故时很容易只改了一半。

AI 可以审查配置结构、指出可能泄露的位置、生成 `.env.example` 和权限清单。不要给它真实值。让它看占位符已经够了。

秘密清单还应标出环境。开发、测试、预发布和生产使用不同值。测试密钥不应访问生产数据，生产密钥不应出现在本地教程里。小程序、移动 App、Web 后端和 CI 若共享某个高权限密钥，要重新评估是否拆分。共享越多，撤销越痛。

最小权限不是一次性工作。新功能上线时常会先给宽权限，赶时间时没人收回。每月或每季度检查一次。某个服务只读数据库，却拥有写权限。某个部署 token 只部署一个项目，却能管理整个组织。这些都是事故前就能改的小洞。

排错时也遵守最小权限。给临时人员看日志，不等于给他服务器登录。给供应商看错误，不等于给生产控制台。给 AI 看配置结构，不等于给真实密钥。每次协作只给完成当前任务所需的最小材料。
