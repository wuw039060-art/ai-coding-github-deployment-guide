# 让 AI 先理解项目结构

让 AI 修改一个现有项目之前，最重要的准备是让它建立一张有证据的项目地图，单纯把“帮我改”写得更长仍然不够。地图要说明用户从哪里进入、请求经过哪些模块、数据存在哪里、配置怎样进入运行环境、测试保护什么，以及哪些文件绝对不能随意改变。只有文件列表，没有执行关系，AI 仍然可能在错误位置做一个看似合理的修改。

AI 可以快速搜索、归纳和追踪引用，却不知道你的项目目标、生产状态和未写进仓库的约定。它也可能把过期 README 当成当前事实，把生成文件当成源码，把示例 `.env` 当成生产配置。理解阶段要求它区分已确认事实、合理推断和仍需核对的空白，追求的是足以安全修改的具体认识，无需假装已经熟悉所有代码。

## 你能提出的问题受项目地图影响

面对陌生项目时，人通常会从自己已经知道的对象提问。只看到页面，就会问颜色、按钮和文案；知道 Network 后，会追问请求是否发出；继续发现后端、队列和对象存储，才会想到保存成功以后还有哪些异步工作。提问者看见了更多真实部件和关系，问题才会变得更好。花哨的提示词无法代替这张地图。

因此，让 AI 理解项目的第一轮任务不应急着给修复结论。先让它指出入口、数据流、外部服务、权限检查、后台任务和部署路径，并为每项结论引用文件或配置。读者再抽查其中一条用户路径，把看不见或无权访问的部分列为未知。项目地图越完整，后续问题越能指向具体边界。

地图也不能制造虚假的全知。仓库里可能没有生产环境变量，代码无法证明控制台当前选中的分支，README 也可能落后于实际部署。报告应把事实、推断和未知分开。一个写得清楚的未知项会告诉你下一步需要谁、哪份日志或哪个控制台，而一个被猜测填满的空白会让后面的计划建立在错误前提上。

第一轮只要求 AI 阅读和解释，不授权编辑、安装依赖、启动生产服务或访问外部账号。给出目标功能、允许查看的目录、明确禁区和希望得到的产物。例如“请只读分析笔记保存流程，允许查看仓库文件与现有测试，不读取真实 `.env`，不安装依赖，不修改文件；输出用户动作到数据库的流程、关键文件、已知风险和待确认问题”。

只读并不代表所有读取都没有风险。仓库中可能存在秘密、用户导出、生产日志与商业材料，运行测试也可能连接外部服务。开始前清点敏感目录，使用脱敏副本或隔离工作区，并明确哪些命令只能查看文件、哪些会执行代码。NIST 的生成式 AI 风险资料建议记录任务、知识限制、上游信息来源和输出将怎样被人使用。

如果项目很大，不要让 AI 一次解释“全部”。先选择一个真实目标，例如登录、上传头像、保存笔记或生成订单，从用户动作向后追踪。完成一条路径后，再补后台任务、错误处理和相邻功能。范围越具体，地图越容易用文件与测试验证。

## 从项目根目录识别入口

项目根目录通常有 README、依赖清单、锁文件、构建配置、容器配置、CI 工作流、测试目录和源码目录。它们分别回答项目自称做什么、依赖什么、怎样运行、怎样部署和怎样验证。先读这些高信息文件，再进入具体模块，比按字母顺序打开几百个文件有效。

常见依赖清单包括 `package.json`、`pyproject.toml`、`pubspec.yaml`、`Cargo.toml` 和平台构建文件，锁文件记录实际解析版本。看到清单不能直接安装，先确认项目规定的包管理器、运行时版本和网络权限。README 的命令也要与当前脚本、CI 和锁文件交叉核对，文档可能尚未更新。

入口文件是程序开始接收输入的位置。网页可能从路由、页面组件或 API handler 进入，服务器可能从主程序、命令行或消息队列进入，Flutter 应用从 `main()` 启动并通过路由进入界面。AI 应指出具体文件和函数，不用“前端层”“后端层”这类抽象词代替位置。

一个目录名叫 `services`，里面可能放业务逻辑，也可能只是第三方 API 包装。要理解责任，需要看谁调用它、输入输出是什么、错误怎样传播和测试在哪里。让 AI 为每个关键模块写“拥有的行为”“不负责的行为”“上游”“下游”和“副作用”，比生成整棵文件树更有用。

生成文件、依赖目录、构建产物和缓存通常不应作为主要源码阅读。典型例子有 `node_modules`、`build`、`dist`、Flutter 的生成目录和覆盖率输出。真正规则以项目配置和版本控制状态为准，不要仅凭名称删除。AI 应先确认哪些文件被 Git 跟踪、哪些可重建、哪些是用户数据。

同名文件也可能属于不同环境。`config.dev`、`config.production`、Compose override 和平台环境变量会改变实际行为。项目地图要标出“源码默认值”“部署时注入值”和“运行时读取位置”，真实秘密只记录变量名，不读取或输出值。

## 沿一个用户动作追踪请求

假设用户在网页点击“保存笔记”。第一步找按钮或表单事件，确认它如何收集数据和展示加载状态。第二步找客户端请求，记录 URL、方法、请求体、认证与错误处理。第三步找服务器路由和参数验证，再进入授权、业务逻辑、数据库事务和外部副作用。最后找响应怎样回到界面，以及失败后是否允许重试。

每一步都应附文件路径、函数或类、输入与输出。AI 若说“数据会存入数据库”，继续追问哪个模型、哪张表、哪次迁移、是否在事务中、失败怎样回滚。若它找不到，应明确写“未在已读文件中确认”，不能凭框架惯例补出一个不存在的实现。

OpenAI 的 Codex 大型代码库用例建议先追踪请求流、模块所有权、验证、副作用和状态变化，再指出下一批应读文件。这套方法适用于任何代码助手，因为它把概括转换成可以回到仓库核对的声明。

读项目时最容易遗漏的部分，是函数返回以后仍发生的事情。保存数据库后可能发送邮件、上传对象、刷新缓存、推送消息或投递后台任务。回滚代码不会自动撤销已经发出的邮件，测试环境也可能误连真实第三方服务。地图必须把这些副作用单独列出。

对每个副作用记录触发条件、凭据来源、失败处理、重试、幂等和日志。一个后台任务若能重复执行，应说明怎样防止重复扣款或重复邮件。找不到幂等设计时，不代表一定有缺陷，但要列为待核风险，在授权修改前由项目负责人判断。

状态也可能留在浏览器 Cookie、移动端数据库、Redis、文件系统和对象存储。只追踪主数据库会错过升级迁移、缓存失效与离线同步。询问“用户关闭应用再打开后，状态从哪里恢复”，往往能找到真正的持久化边界。

## 依赖和版本决定代码实际怎样运行

同一段源码在不同运行时与依赖版本上可能表现不同。项目地图应记录语言和运行时版本、包管理器、锁文件、操作系统差异、数据库版本与基础镜像。版本来自配置、CI 和实际命令输出，不写“最新版”。

依赖关系分为直接与间接。直接依赖由项目声明，间接依赖由锁文件解析。AI 可以解释某个库承担什么工作，但不能未经授权升级它。升级会改变大量间接版本和生成文件，必须单独规划、审查 Diff 并运行回归测试。

遇到来源不明的脚本，先读内容与调用位置，再决定是否运行。`postinstall`、迁移、种子数据和部署脚本都可能访问网络或修改数据。理解项目不需要执行每条脚本；静态阅读、CI 配置和现有日志通常能先建立大部分地图。

文档描述作者希望系统怎样工作，测试展示某些输入下程序被要求产生什么结果。先查看测试目录、命名、测试框架和 CI 命令，再把测试关联到用户路径。登录流程若只有组件渲染测试，没有服务端授权测试，地图应标出保护缺口。

测试也可能过期、被跳过或只在特定环境运行。AI 应区分“存在测试文件”“命令实际运行”“测试通过”和“覆盖当前改动”。GitHub 状态绿色并不自动证明所有工作都执行，因为跳过的工作流在某些情况下也可能呈现成功状态，后续章节会专门处理验证证据。

没有测试的项目仍能理解，但风险更高。可以先从现有行为、接口、日志与用户可见结果建立基线，随后在获准修改时添加最小回归测试。不要让 AI 为了证明自己理解项目，先大规模补测试或重构。

## 日志和部署配置说明生产实际路径

本地代码路径可能与生产不同。反向代理重写 URL，平台注入环境变量，Docker 改变工作目录，数据库通过私有网络连接。部署配置、构建日志、运行版本和健康检查能说明实际路径。理解报告应明确哪些结论只来自本地仓库，哪些已有生产证据。

生产日志只使用脱敏故障窗口，不把完整用户数据交给 AI。请求编号、版本、实例、状态码和错误类别通常足以验证流向。若仓库说服务监听 3000，运行日志和容器配置显示 8080，应列出矛盾并请求确认，不擅自决定哪一个“正确”。

OpenAI 的 Computer Use QA 用例强调按真实用户路径操作并记录可见结果。视觉和交互检查可以补充代码地图，却不能证明数据库与权限内部正确。页面显示成功后，还要使用 Network、运行日志或测试数据确认实际写入。

项目中可使用 `AGENTS.md` 给 Codex 提供持续指令，例如构建命令、测试要求、目录责任、禁止读取的材料和需要确认的操作。OpenAI 官方资料说明 Codex 会按目录层级读取并合并项目指导，靠近当前目录的说明可以覆盖更上层约定。具体发现顺序和大小限制属于产品行为，封版前应按当前官方文档再核对。

一份有用项目约定应短而可执行。可以写“修改 JavaScript 后运行 `npm test`”“生产部署需要账号持有人批准”“不要读取 `data/private`”“数据库迁移必须附回滚与备份验证”。不要把整本架构文档塞进去，也不要写“保证代码完美”这类无法验收的要求。

约定文件本身进入版本控制，修改经过 Diff 审查。过期命令会让每次 AI 工作都从错误前提出发，因此新依赖、目录迁移和发布流程变化后要同步更新。敏感凭据不放在指令中，只写安全存储的名称和访问审批。

## 要求 AI 给证据，不只给总结

理解报告中的关键声明应引用具体文件、函数、配置或测试。可以要求表格字段包含“结论”“证据位置”“置信度”“待核问题”和“修改风险”。文件链接帮助人快速打开，但不能把几十个路径堆成没有解释的清单。

让 AI 主动列出冲突与空白。例如 README 写 Node 20，CI 使用 Node 22；示例环境变量名与代码读取名不同；接口有路由却没有授权测试。冲突不等于立刻修改，先问哪个来源代表当前生产事实。保留这些问题能防止后续计划建立在隐藏假设上。

抽查报告中的三类结论。第一类是入口和调用关系，打开文件看引用是否存在；第二类是命令与测试，核对脚本和 CI；第三类是生产推断，要求运行证据或明确未验证。若抽查频繁出错，缩小范围并重新建立地图，不继续扩大授权。

多应用仓库可能同时包含网页、API、移动端、基础设施和共享包。先识别工作区与构建边界，再为每个子项目建立入口、依赖、测试和部署。共享包的修改会影响多个消费者，需要列出反向依赖，不只验证当前页面。

可以分四轮。第一轮只读根目录与项目约定，第二轮追踪目标用户路径，第三轮检查测试、配置和部署，第四轮由人抽查并补充业务语义。每轮都生成简短增量，不反复输出整份报告。这样既控制上下文，也让错误在早期被发现。

项目含 Git 子模块、生成代码、外部 API 或未纳入仓库的基础设施时，明确地图边界。AI 不能读取的部分写成外部依赖，记录负责人和当前接口，不用猜测内部实现。需要新的访问权限时停下说明用途，由用户决定是否扩大范围。

## 接口契约比函数名字更稳定

模块之间通过接口交换数据。Web API 的方法、路径、状态码和 JSON，消息队列的事件名与字段，数据库 schema，Flutter 平台通道，都是契约。AI 理解项目时应找出契约定义、消费者、生产者、版本和错误行为，不能只追踪某个实现函数。

契约可能写在 OpenAPI、类型文件、schema、迁移、测试或文档中，也可能只有实际代码。多处定义不一致时，先记录哪一处由构建生成、哪一处被运行时使用。生成的客户端通常不直接手改，应修改源 schema 后按项目命令重新生成，并审查所有消费者。

增加字段一般比删除或改义容易兼容，仍要检查旧客户端。网页可以随服务器同时发布，商店 App 却可能几个月不更新。项目地图应标出版本兼容与弃用窗口，使 AI 不会把当前后端唯一消费者误认为全部用户。

用户请求结束后，队列 worker、定时任务和 Webhook 可能继续处理。它们常在独立进程、容器或平台函数中运行，入口不在网页路由。搜索任务注册、调度配置、队列名称和部署清单，确认谁启动、怎样重试、失败在哪里告警。

一个“删除账号”功能可能立即标记数据库，随后后台删除文件、搜索索引和邮件订阅。AI 只改同步路由会留下残余数据。地图为每个后台动作写触发事件、幂等键、最大重试、死信或失败记录，以及用户何时看到最终状态。

定时任务还可能产生费用和外部副作用。确认它使用哪个时区、如何防止重复运行、错过一次后是否补跑。多个实例都启动同一 scheduler 时，锁或平台调度必须避免重复。找不到机制就列为风险，不直接在生产启动第二份 worker。

## 通过 CI 找到项目的标准命令

本地文档可能过期，CI 往往更接近团队真正运行的构建与测试。查看工作流的触发、工作目录、运行时、依赖安装、缓存、环境变量名和命令。它也可能只运行部分路径，因此要解释条件和矩阵，不能把 CI 文件当完整产品说明。

项目脚本与 CI 不一致时，记录差异。例如本地 `npm test` 运行全部测试，CI 只执行 changed packages；或 CI 先生成代码，本地 README 没写。理解报告应给推荐的最低验证序列，并注明哪些步骤需要网络、数据库或平台账号。

不要为了“确认命令”立即触发远端工作流。先静态阅读，确实需要运行时获得仓库权限和费用授权。自托管 runner 可能接触生产网络，理解阶段不执行未知工作流。

数据模型说明对象字段与关系，迁移说明结构如何随版本变化，种子数据说明测试或初始内容。AI 应把当前 schema 与迁移历史区分。旧迁移通常已经在生产执行，随意改写它会让新旧环境产生不同结果；常见做法是新增迁移，具体遵守项目规则。

对每类数据记录创建、读取、更新、删除、归档、导出与备份。用户界面删除可能只是软删除，真正清理由后台完成；日志和备份还有独立保留。项目所有者根据隐私与业务决定生命周期，AI 只根据代码无法推断合法期限。

数据库之外还可能有对象存储、搜索索引、缓存和分析事件。地图标明哪一个是权威来源，哪些可以重建。缓存丢失与主数据库丢失风险不同，恢复顺序也不同。

## 识别构建时与运行时边界

前端环境变量有些在构建时写入 JavaScript，部署后改平台变量却不会改变旧产物。服务器变量通常在进程启动时读取，远端功能开关可能运行中变化。理解报告要写每个关键配置何时读取、在哪个进程生效和怎样验证。

构建产物可能经过多步。TypeScript 编译成 JavaScript，前端再打包与哈希，Docker 把产物放进镜像，平台从镜像启动。AI 修改源码后若只启动旧产物，会误以为改动无效。反过来，未提交构建文件也可能让本机显示新效果，CI 却无法重现。

移动端把配置和资源打进 APK、AAB 或 iOS Archive，商店处理后才到用户设备。项目地图记录包名、版本、构建号和后端兼容，不能把“代码仓库已改”写成“用户 App 已更新”。

前端隐藏按钮、路由守卫和界面角色用于体验，服务端 API 与数据库策略才决定攻击者能否执行。沿请求追踪身份从 Cookie 或 Token 进入，怎样解析，在哪检查资源所有权，拒绝返回什么。一个 `isAdmin` 名字不能证明所有路径都调用它。

列出未登录、普通用户、资源所有者、管理员和服务账号的关键动作。对应测试是否存在，后台任务是否绕过用户权限，内部接口是否仍有身份。AI 若建议在前端增加检查，继续问直接调用 API 会怎样。

第三方服务权限也要进入地图。部署令牌、数据库用户、对象存储角色与 GitHub App 各自拥有什么能力。理解阶段只记录名称与范围，不读取真实值。权限过宽列为后续任务，不在当前功能分析中顺手轮换。

## 检查错误从哪里被转换

底层数据库错误可能在服务层转换为业务错误，再由 API 变成状态码，客户端最后显示文字。追踪转换能说明日志和用户提示为什么不同，也能发现错误被吞掉。地图记录内部错误类别、对外状态与关联编号。

重试必须在明确边界。浏览器、代理、应用和队列若同时重试，一次失败可能被放大。写操作使用幂等键，未知结果先查询状态。AI 只看到某层超时配置时，不能单独增加重试而不检查其他层。错误处理也是契约。调用方是否区分 401、403、409 与 500，会影响登录、权限、冲突和重试。测试只断言“不是 200”不足以保护具体行为。

同一信息可能同时出现在 README、代码注释、Wiki、CI、部署平台和运行日志。项目负责人应指定权威来源，例如依赖版本以锁文件为准，生产环境变量以平台为准，接口以 schema 和契约测试为准。AI 报告写清选择依据。

权威来源也可能过期。生产实际版本与声明不一致时，先记录漂移，不让 AI 直接覆盖任何一边。通过只读状态、部署记录与负责人确认，决定更新文档还是恢复生产。时间敏感事实写最后核对日期。平台界面、商店政策和 AI 产品功能尤其容易变化。源码内部稳定关系与外部政策分开记录，后者在每次操作前刷新。

## 常见的五种理解错误

第一种是根据目录名猜责任，没有追踪调用。第二种是直接修改生成文件，下一次构建被覆盖。第三种是只读 README，忽略 CI、锁文件与生产差异。第四种是只看成功路径，漏掉后台任务和副作用。第五种是一次读取太多文件，最后给出抽象总结却没有证据。

修正方法都是缩小范围并回到用户动作。要求具体文件、输入输出、错误和下一步；抽查关键引用；对冲突写待确认。AI 能说出“我不知道哪些部分”是良好结果，不需要用完整感掩盖空白。理解报告也可能过细，逐行解释工具函数却没有系统位置。每段说明应回答它为什么影响当前目标。无关高级细节放到以后学习，不让信息量压过决策。

AI 的上下文容量有限，长任务还可能跨越多次对话或摘要。把已确认地图、决策、未验证项和当前提交保存到项目内的受控工作记录，不依赖模型“记得”。每次继续前重新读取当前文件与 `git status`，确认仓库没有被其他人改变。

摘要会压缩细节，因此关键规则放 `AGENTS.md`、测试、schema 和正式文档，临时推断放任务记录。秘密不写入任何上下文文件。记录引用具体版本，代码变化后过期结论要更新或删除。AI 若在长任务后开始使用旧文件名、旧计划或已排除假设，应停止实施并重新建立当前状态。重复确认不是浪费，它防止一份正确的早期地图在项目变化后变成错误依据。

## 多人或多个 AI 同时工作要划分所有权

并行可以加快独立研究与测试，却会制造共享文件、锁文件和迁移冲突。开始前按目录或交付物划分所有者，约定集成顺序和禁止同时修改的文件。数据库迁移编号、依赖锁与发布配置通常需要单一协调者。

使用分支或工作树隔离代码变化，每个任务报告基线提交与 Diff。合并后重新运行集成测试，不能把两个分支各自通过相加为整体通过。冲突解决改变了代码，也需要重新评审。共享同一外部测试环境时，数据和部署也会互相覆盖。为每个任务使用独立账号、命名空间或预览环境；做不到就串行执行。AI 不应因为文件没有 Git 冲突，就假定运行状态互不影响。

选择不会修改数据的用户路径，例如打开公开页面或读取测试记录。根据地图预测浏览器请求、代理记录、应用日志和数据读取，再在隔离环境观察。预测与实际不符时更新地图，不能为了保留原图忽略证据。

第二次演练选择安全失败，例如未登录访问受保护测试资源。预期界面、状态码、服务端授权和日志都明确。若前端阻止但 API 直接请求成功，地图会暴露真实权限边界。演练记录版本、环境和时间，使用测试账号与数据。理解阶段不需要压力测试、迁移或生产写入。两条路径已经能检验入口、错误和证据连接。

## 一份项目理解报告应包含什么

报告开头写目标与已读范围，随后给出系统入口、请求流、数据与副作用、配置与环境、依赖版本、测试与部署、风险与待核问题。结尾给出“若要修改，最小可能涉及哪些文件”“哪些文件不应动”“验证需要什么环境”。它是修改计划的输入，不是架构永久真相。

下面是一份机器可读的简化模板。字段使用冒号便于复制，真实报告中的每个结论仍要附证据。

```
目标功能：
只读范围：
未读取或无权访问：
用户入口：
请求与状态流：
数据存储：
外部副作用：
运行时与依赖：
配置来源：
现有测试：
部署路径：
已确认事实：
待验证假设：
高风险文件和操作：
建议下一批阅读文件：
```

假设 AI 起初报告“保存按钮直接调用数据库”。抽查发现网页只发出 `POST /api/notes`，数据库访问发生在服务器仓库层。进一步追踪显示路由先验证正文长度，服务层检查所有权，事务写入笔记与版本表，提交后投递搜索索引任务。用户界面收到 201 才显示成功。

项目配置显示本地使用 SQLite，生产使用 PostgreSQL；测试只覆盖路由成功，没有覆盖所有权拒绝和索引任务失败。这个理解报告已经能支持一个小修改计划，同时保留两项待核风险。它没有因为看到 `saveNote()` 函数名，就把整个行为压缩成一句“保存到数据库”。

若需求是增加标签，AI 下一步应确认标签表、迁移兼容、旧客户端、事务与搜索索引，而不是只在页面加输入框。地图让非专业读者也能问出关键问题，例如“标签失败时笔记会不会已经保存”“旧版本能不能读新数据”。

## 理解完成的最低标准

- 能从一个用户动作追到入口、业务逻辑、数据与响应
- 每个关键结论有文件、函数、配置、测试或日志证据
- 已区分源码、生成文件、依赖、缓存和用户数据
- 已记录运行时、锁文件、构建与部署环境
- 已列出数据库之外的副作用与后台任务
- 已说明现有测试真正覆盖和没有覆盖的内容
- 已标记 README、CI、配置与生产证据的冲突
- 已说明没有读取或无法验证的部分
- 已列出可能修改文件、明确禁区和验证环境
- 人已经抽查关键路径，确认没有明显虚构

AI 理解项目的价值，是把陌生系统压缩成一组可核对关系。它可以加快搜索和解释，最终地图仍要由代码、配置、测试、日志与项目负责人共同校正。完成这一步后，修改计划才有可信的范围，后面的 Diff 与测试也才知道要保护什么。
