# 让 AI 先理解项目结构

让 AI 修改现有项目之前，先让它建立一张有证据的项目地图，单纯把“帮我改”写得更长仍然不够。地图要说明用户从哪里进入、请求经过哪些模块、数据存在哪里、配置怎样进入运行环境、测试保护什么，以及哪些文件不能随意改变。只有文件列表，没有执行关系，AI 仍然可能在错误位置做一个貌似合理的修改。

AI 可以快速搜索、归纳和追踪引用，却不知道你的项目目标、生产状态和未写进仓库的约定。它也可能把过期 README 当成当前事实，把生成文件当成源码，把示例 `.env` 当成生产配置。理解阶段要求它区分已确认事实、合理推断和仍需核对的空白。

## 你能提出的问题受项目地图影响

面对陌生项目时，人会按自己看见的东西提问。只看到页面，就会问颜色和文案；看到 Network 后，会追问请求有没有发出；继续看到后端、队列和对象存储，才会想到保存成功后还有异步任务。项目地图让问题指向边界。

第一轮只要求 AI 阅读和解释，不授权编辑、安装依赖、启动生产服务或访问外部账号。让它指出入口、数据流、外部服务、权限检查、后台任务和部署路径，并为每项结论引用文件或配置。看不见或无权访问的部分写成未知。

只读也要有边界。仓库里可能有秘密、用户导出、生产日志和商业材料，运行测试也可能连接外部服务。开始前清点敏感目录，使用脱敏副本或隔离工作区。

## 从项目根目录识别入口

项目根目录通常有 README、依赖清单、锁文件、构建配置、容器配置、CI 工作流、测试目录和源码目录。它们分别回答项目自称做什么、依赖什么、怎样运行、怎样部署和怎样验证。先读这些文件，再进入具体模块。

常见依赖清单包括 `package.json`、`pyproject.toml`、`pubspec.yaml`、`Cargo.toml` 和平台构建文件，锁文件记录实际解析版本。看到清单不能直接安装，先确认包管理器、运行时版本和网络权限。README 的命令也要与当前脚本、CI 和锁文件交叉核对。

入口文件是程序开始接收输入的位置。网页可能从路由、页面组件或 API handler 进入，服务器可能从主程序、命令行或消息队列进入，Flutter 应用从 `main()` 启动并通过路由进入界面。AI 应指出具体文件和函数，不用“前端层”“后端层”这类抽象词代替位置。

生成文件、依赖目录、构建产物和缓存通常不应作为主要源码阅读。典型例子有 `node_modules`、`build`、`dist`、Flutter 的生成目录和覆盖率输出。规则以项目配置和版本控制状态为准，不能仅凭名称删除。

同名文件也可能属于不同环境。`config.dev`、`config.production`、Compose override 和平台环境变量会改变实际行为。项目地图要标出“源码默认值”“部署时注入值”和“运行时读取位置”，真实秘密只记录变量名，不读取或输出值。

## 沿一个用户动作追踪请求

假设用户在网页点击“保存笔记”。第一步找按钮或表单事件，确认它如何收集数据和展示加载状态。第二步找客户端请求，记录 URL、方法、请求体、认证与错误处理。第三步找服务器路由和参数验证，再进入授权、业务逻辑、数据库事务和外部副作用。再找响应怎样回到界面。

每一步都应附文件路径、函数或类、输入与输出。AI 若说“数据会存入数据库”，继续追问哪个模型、哪张表、哪次迁移、是否在事务中、失败怎样回滚。若它找不到，应写“未在已读文件中确认”。

读项目时容易遗漏函数返回以后仍发生的事情。保存数据库后可能发送邮件、上传对象、刷新缓存、推送消息或投递后台任务。回滚代码不会自动撤销已经发出的邮件，测试环境也可能误连第三方服务。地图必须把这些副作用单独列出。

对每个副作用记录触发条件、凭据来源、失败处理、重试、幂等和日志。一个后台任务若能重复执行，应说明怎样防止重复扣款或重复邮件。找不到幂等设计时，不代表一定有缺陷，但要列为待核风险，在授权修改前由项目负责人判断。

状态也可能留在浏览器 Cookie、移动端数据库、Redis、文件系统和对象存储。只追踪主数据库会错过升级迁移、缓存失效与离线同步。询问“用户关闭应用再打开后，状态从哪里恢复”，往往能找到持久化边界。

## 依赖和版本决定代码实际怎样运行

同一段源码在不同运行时与依赖版本上可能表现不同。项目地图应记录语言和运行时版本、包管理器、锁文件、操作系统差异、数据库版本与基础镜像。版本来自配置、CI 和实际命令输出，不写“最新版”。

依赖关系分为直接与间接。直接依赖由项目声明，间接依赖由锁文件解析。AI 可以解释某个库承担什么工作，但不能未经授权升级它。升级要单独规划、审查 Diff 并运行回归测试。

遇到来源不明的脚本，先读内容与调用位置，再决定是否运行。`postinstall`、迁移、种子数据和部署脚本都可能访问网络或修改数据。理解项目不需要执行每条脚本；静态阅读、CI 配置和现有日志通常能先建立大部分地图。

文档描述作者希望系统怎样工作，测试展示某些输入下程序被要求产生什么结果。先查看测试目录、命名、测试框架和 CI 命令，再把测试关联到用户路径。登录流程若只有组件渲染测试，没有服务端授权测试，地图应标出保护缺口。

没有测试的项目仍能理解，但风险更高。可以先从现有行为、接口、日志与用户可见结果建立基线，随后在获准修改时添加最小回归测试。

## 日志和部署配置说明生产实际路径

本地代码路径可能与生产不同。反向代理重写 URL，平台注入环境变量，Docker 改变工作目录，数据库通过私有网络连接。部署配置、构建日志、运行版本和健康检查能说明实际路径。理解报告应区分本地仓库结论与生产证据。

生产日志只使用脱敏故障窗口，不把完整用户数据交给 AI。请求编号、版本、实例、状态码和错误类别通常足以验证流向。若仓库说服务监听 3000，运行日志和容器配置显示 8080，应列出矛盾并请求确认，不擅自决定哪一个“正确”。

项目中可使用 `AGENTS.md` 给 Codex 提供持续指令，例如构建命令、测试要求、目录责任、禁止读取的材料和需要确认的操作。OpenAI 官方资料说明 Codex 会按目录层级读取并合并项目指导，靠近当前目录的说明可以覆盖更上层约定。具体产品行为在封版前应按当前官方文档再核对。

一份有用项目约定应短而可执行。可以写“修改 JavaScript 后运行 `npm test`”“生产部署需要账号持有人批准”“不要读取 `data/private`”“数据库迁移必须附回滚与备份验证”。不要把整本架构文档塞进去。

约定文件本身进入版本控制，修改经过 Diff 审查。过期命令会让每次 AI 工作都从错误前提出发，新依赖、目录迁移和发布流程变化后要同步更新。敏感凭据不放在指令中。

## 要求 AI 给证据，不只给总结

理解报告中的关键声明应引用具体文件、函数、配置或测试。可以要求表格字段包含“结论”“证据位置”“置信度”“待核问题”和“修改风险”。文件链接帮助人快速打开，但不能堆成没有解释的清单。

让 AI 主动列出冲突与空白。例如 README 写 Node 20，CI 使用 Node 22；示例环境变量名与代码读取名不同；接口有路由却没有授权测试。冲突不等于立刻修改，先问哪个来源代表当前生产事实。保留这些问题能防止后续计划建立在隐藏假设上。

抽查报告中的三类结论。入口和调用关系要打开文件看引用是否存在；命令与测试要核对脚本和 CI；生产推断要有运行证据或明确未验证。若抽查频繁出错，缩小范围并重新建立地图。

多应用仓库可能同时包含网页、API、移动端、基础设施和共享包。先识别工作区与构建边界，再为每个子项目建立入口、依赖、测试和部署。共享包的修改会影响多个消费者，需要列出反向依赖，不只验证当前页面。

项目含 Git 子模块、生成代码、外部 API 或未纳入仓库的基础设施时，明确地图边界。AI 不能读取的部分写成外部依赖，记录负责人和当前接口，不猜测内部实现。

## 契约、CI 和运行边界

模块之间通过契约交换数据。Web API 的方法、路径、状态码和 JSON，消息队列的事件名与字段，数据库 schema，Flutter 平台通道，都是契约。AI 要找出契约定义、消费者、生产者、版本和错误行为，不能只追踪某个函数名。生成客户端通常不直接手改，要修改源 schema，再按项目命令重新生成。

本地文档可能过期，CI 往往更接近团队实际使用的构建与测试。查看工作流触发、工作目录、运行时、依赖安装、缓存、环境变量名和命令。项目脚本与 CI 不一致时，记录差异，并给出最低验证序列。

前端环境变量有些在构建时写入 JavaScript，部署后改平台变量不会改变旧产物。服务器变量通常在进程启动时读取，远端功能开关可能运行中变化。移动端把配置和资源打进 APK、AAB 或 iOS Archive，商店处理后才到用户设备。地图记录包名、版本、构建号和后端兼容。

权限也要落到运行边界。前端隐藏按钮和界面角色只改善体验，服务端 API 与数据库策略才决定攻击者能否执行。部署令牌、数据库用户、对象存储角色与 GitHub App 各自拥有什么能力，也要进入地图。

## 错误、权威来源和协作边界

底层数据库错误可能在服务层转换为业务错误，再由 API 变成状态码，客户端显示文字。追踪转换能说明日志和用户提示为什么不同，也能发现错误被吞掉。重试也要看全路径。浏览器、代理、应用和队列若同时重试，一次失败可能被放大。

同一信息可能同时出现在 README、代码注释、Wiki、CI、部署平台和运行日志。项目负责人应指定权威来源。依赖版本以锁文件为准，生产环境变量以平台为准，接口以 schema 和契约测试为准。生产实际版本与声明不一致时，先记录差异。

常见理解错误有五类。按目录名猜责任，修改生成文件，只读 README，只看成功路径，一次读取太多文件后给出抽象总结。修正办法是缩小范围并回到用户动作。

长任务会跨越多次对话或摘要。把已确认地图、决策、未验证项和当前提交保存到受控工作记录。多人或多个 AI 同时工作时，按目录或交付物划分所有者，合并后重新运行集成测试。共享外部测试环境时，能隔离就隔离，做不到就串行执行。

## 一份项目理解报告应包含什么

报告开头写目标与已读范围，随后给出系统入口、请求流、数据与副作用、配置与环境、依赖版本、测试与部署、风险与待核问题。结尾给出若要修改，最小可能涉及哪些文件，哪些文件不应动，验证需要什么环境。

假设 AI 起初报告“保存按钮直接调用数据库”。抽查发现网页只发出 `POST /api/notes`，数据库访问发生在服务器仓库层。进一步追踪显示路由先验证正文长度，服务层检查所有权，事务写入笔记与版本表，提交后投递搜索索引任务。用户界面收到 201 才显示成功。

项目配置显示本地使用 SQLite，生产使用 PostgreSQL；测试只覆盖路由成功，没有覆盖所有权拒绝和索引任务失败。这个理解报告已经能支持一个小修改计划，同时保留两项待核风险。

若需求是增加标签，AI 下一步应确认标签表、迁移兼容、旧客户端、事务与搜索索引，不只在页面加输入框。地图让非专业读者也能问出关键问题，例如标签失败时笔记会不会已经保存，旧版本能不能读新数据。

## 理解完成的最低标准

- 能从一个用户动作追到入口、业务逻辑、数据与响应
- 每个关键结论有文件、函数、配置、测试或日志证据
- 已区分源码、生成文件、依赖、缓存和用户数据
- 已记录运行时、锁文件、构建与部署环境
- 已列出数据库之外的副作用与后台任务
- 已说明现有测试实际覆盖和没有覆盖的内容
- 已标记 README、CI、配置与生产证据的冲突
- 已说明没有读取或无法验证的部分
- 已列出可能修改文件、明确禁区和验证环境
- 人已经抽查关键路径，确认没有明显虚构

AI 理解项目的价值，是把陌生系统压缩成一组可核对关系。它可以加快搜索和解释，这张地图仍要由代码、配置、测试、日志与项目负责人共同校正。完成这一步后，修改计划才有可信范围。
