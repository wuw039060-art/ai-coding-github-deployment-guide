# systemd、systemctl、journalctl 和服务日志

服务器上的应用不能靠手工开一个终端长期运行。终端断了，进程可能也断。systemd 是许多 Linux 发行版上的服务管理系统。它负责启动服务、停止服务、开机自启、记录状态和管理日志。初学者先学会读状态和看日志，就能解决一半的部署问题。

## 先分清对象

systemd 是管理系统。service unit 是服务描述文件。`systemctl` 是操作服务的命令。`journalctl` 是查看 systemd 日志的命令。不要把它们混成一个词。排错时，你在操作的是某个服务，比如 `myapp.service`。

`systemctl status myapp` 给概况。它会显示服务是否运行、最近退出码、主进程 ID 和几行最近日志。它适合第一眼判断。详细时间线要用 `journalctl -u myapp`。若只看 status，常常漏掉真正出错的第一行。

日志按时间读。先找到你执行启动、重启或访问请求的时间点。再往前看配置加载、环境变量、端口绑定、数据库连接和权限错误。不要只复制最后一行。最后一行经常只是程序退出，原因在前面。

## start、restart、reload 和 enable

`start` 启动服务。`stop` 停止服务。`restart` 先停再启。`reload` 通常让服务重新读取配置，但不一定所有服务都支持。`enable` 设置开机自启。它不会立刻启动服务。`disable` 取消开机自启，也不一定立刻停止服务。

改配置后先验证。Nginx、Caddy、PostgreSQL 和许多应用都有自己的配置检查方式。验证通过，再 reload 或 restart。直接重启会把语法错误带到生产入口。若服务启动失败，先看日志，不要连续重启。

服务存活不等于业务可用。进程可能在，但连不上数据库。HTTP 端口可能在，但登录失败。健康检查要覆盖用户真正依赖的路径。至少确认应用能响应、关键依赖能访问、版本符合预期。

## 一份最小 service 文件

最小 service 文件通常写明工作目录、启动命令、运行用户、重启策略和环境变量来源。工作目录决定相对路径。运行用户决定文件权限和安全边界。启动命令要用绝对路径或清楚的运行时。环境变量可以从文件加载，但秘密文件权限要收紧。

不要让服务以 root 运行，除非你能说明原因。Web 应用通常用独立用户。日志写到标准输出或固定日志目录。若写文件，目录所有者要和服务用户匹配。权限错误是服务启动失败的常见原因。

重启策略要适度。`on-failure` 可以在异常退出时重启。若配置错了，服务会反复失败。systemd 会限制过快重启，但你仍要看日志处理原因。重启不是修复，它只是争取恢复时间。

## 一次启动失败怎样定位

服务启动失败时，按顺序看。第一，unit 文件是否被 systemd 读到。第二，启动命令路径是否存在。第三，运行用户是否存在。第四，工作目录是否存在。第五，环境变量是否加载。第六，端口是否被占用。第七，应用日志说了什么。

修改 service 文件后运行 `systemctl daemon-reload`，让 systemd 重新读取描述。只改应用配置时通常不需要这个命令。很多人改了 unit 文件却忘了 reload，于是 systemd 仍按旧配置启动。

端口占用也常见。旧进程没停，另一个服务已经监听，或同一台机器上跑了测试实例。用 `ss -lntp` 查端口。不要看到占用就杀进程。先确认它是谁、为什么在运行、是否属于生产服务。

## 日志和安全边界

journal 日志会保存标准输出、标准错误和 systemd 自身信息。它适合排错，但也可能包含用户邮箱、请求参数和错误堆栈。复制给 AI 或发到群里前要脱敏。密钥、Cookie、Token 和个人数据不能原样外传。

日志量要有限制。高频错误会快速占满磁盘。配置日志轮转或 journal 保存上限。应用也要避免在循环里反复打印同一错误。磁盘满了以后，日志系统本身也可能失效，排错会更难。

定时任务可以用 systemd timer，也可以用 cron 或队列系统。任务要有日志、失败告警和重试规则。备份、证书续期、清理和报表生成都不应无声失败。

## 环境变量怎样交给服务

手工 SSH 里能读到的环境变量，systemd 服务未必能读到。服务启动环境由 unit 文件和 systemd 管理。开发者在终端里 `export` 过变量，服务重启后通常看不到。正式项目要把变量放到受控文件或平台配置中，再由 service 文件加载。

环境变量文件也要有权限。普通配置可以多人读取，秘密文件只给服务用户和维护者读取。文件名可以写进 unit，文件内容不要写进公开仓库。修改环境变量后，要重启服务或按应用要求 reload，并验证新值生效。

排查环境变量时，不要直接把全部变量打印到日志。它们可能包含数据库密码、Cookie Secret 和 API Key。可以打印变量名是否存在、配置版本或脱敏后的前后几位。排错需要信息，安全也要守住。

## 资源限制和工作目录

systemd 可以给服务设置资源边界，比如最大内存、最大打开文件数和重启频率。边界太低会让服务频繁失败，边界太高又可能拖垮同机其他服务。初学阶段先知道有这件事，遇到 OOM、连接耗尽和重启风暴时再查对应配置。

工作目录影响相对路径。应用读取 `./config`、写 `./logs`、加载静态文件，都依赖当前工作目录。手工运行成功，服务运行失败，常常是工作目录不同。unit 文件里写清 WorkingDirectory，可以减少这种差异。

启动命令也要稳定。不要依赖某个用户 shell 里的别名、nvm 初始化或临时 PATH。使用绝对路径或在 service 文件中明确环境。Node、Python 和 Java 项目尤其容易被运行时路径影响。

## reload 的边界

reload 通常用于重新读取配置，适合反向代理和部分服务。应用是否支持 reload，要看它自己的实现。若应用无法安全 reload，就用滚动重启、短维护窗口或进程管理工具处理。不能因为命令存在，就假设业务无感。

restart 会中断进程。对无状态 Web 服务影响较小，对长任务、上传、WebSocket 和后台队列影响更大。重启前看是否有任务正在运行，是否需要停写，是否需要通知用户。把 restart 当刷新按钮，是服务器上很危险的习惯。

失败后的第一件事是保留现场。看 status、读日志、记录时间和刚改过的内容。随后再回滚配置或启动旧版本。连续尝试不同修改，会把最初线索冲淡。

## 服务文件的交接

service 文件要进项目文档或仓库模板。服务器上最终路径可以由发布脚本安装，但源头应可追溯。否则某个人在 `/etc/systemd/system` 里手改过什么，离开以后没人知道。

交接时至少说明服务名、运行用户、工作目录、启动命令、环境变量文件、日志查看命令、重启方式和健康检查。另一个人能根据这些信息重建服务，才算文档合格。只写“用 systemd 跑”，帮助很有限。

若一台机器上有多个服务，命名要统一。`myapp-web.service`、`myapp-worker.service`、`myapp-scheduler.service` 比 `app1`、`test2` 清楚。服务名会出现在日志、告警和脚本里，命名越随意，排错越费力。

## 后台任务和长任务

Web 请求适合短时间返回，长任务适合放到后台。导出报表、处理图片、批量同步、AI 生成和发送大量邮件，都不应依赖一个 SSH 会话。可以用 systemd service 管 Worker，也可以用 timer 或队列触发。

长任务要有状态记录。开始时间、输入范围、处理进度、失败原因和重试次数都要能查。任务失败后，用户界面或后台管理要能看到状态。只把错误写进日志，会让业务人员不知道任务到底有没有完成。

重启服务器前，要知道有哪些长任务正在跑。若任务可中断，重启后能继续。若任务不可中断，就要等待完成或进入维护窗口。把服务器当普通电脑随手重启，会让后台任务留下半成品。

## 日志时间线怎样读

读日志时先统一时间。服务器时区、容器时区、数据库时区和浏览器本地时间可能不同。事故记录里写明时区。北京时间晚上八点和 UTC 晚上八点相差八小时，查错时间会浪费很多力气。

再把几类日志按时间排起来。systemd 日志、应用日志、反向代理日志、数据库日志和云平台事件。很多故障只有拼起来才清楚。应用报数据库断开，数据库日志显示重启，云平台事件显示实例迁移，这就是一条完整线索。

## 让 AI 读 service 文件

service 文件适合交给 AI 审查，前提是先脱敏。环境变量文件路径可以保留形状，秘密值不能给。启动命令、工作目录、运行用户、重启策略和日志方式可以让 AI 看。它能帮你发现工作目录缺失、用户权限不合理、启动命令依赖 shell 初始化等问题。

让 AI 审查时，不要只问有没有问题。要求它按启动失败、权限风险、日志风险、重启风险和交接风险分类。这样输出更像检查表，方便你逐项验证。

AI 可能建议加自动重启、提高限制或改为 root 运行。不要直接接受。自动重启会掩盖失败，提高限制会影响同机服务，root 运行会扩大事故影响。每个建议都要能说出适用条件。

service 文件改完后，走人工验收。daemon-reload，启动或 reload，查看 status，读取日志，访问健康接口，重启服务器后确认开机自启。AI 可以帮你写验收清单，不能替你证明服务真的恢复。

## 本章练习

在测试机上找一个无风险服务，先查看 status，再用 journalctl 看最近日志。记录服务名、状态、最近启动时间和最近一条错误或正常日志。不要对生产服务练 restart。

如果你有自己的示例应用，可以写一个最小 service。运行用户使用普通用户，工作目录指向练习目录，启动命令只输出一行文本或启动简单 HTTP 服务。启动后查看状态和日志，再停止它。

练习结束后删除这个测试服务，并执行 daemon-reload。记录创建、启动、查看、停止、删除的完整路径。systemd 的学习重点在生命周期，不在背参数。

## 常见误区

第一个误区是看到 active 就认为业务正常。systemd 只知道进程还在。登录、上传、队列和数据库连接是否正常，要靠健康检查和业务验收。

第二个误区是频繁 restart。重启能短暂恢复一些问题，也会冲掉现场线索。每次重启前先记录状态和日志。若同一个服务反复需要重启，说明根因没有处理。

第三个误区是把环境变量放在个人 shell 里。服务由 systemd 启动，不会自动继承你手工 export 的内容。正式配置要写到受控文件或 unit 配置里，并通过服务重启验证。

## 本章交付物

本章结束时，你应该留下一个最小 service 模板。模板里写工作目录、运行用户、启动命令、环境变量来源、重启策略和日志查看方式。真实项目可以从模板改，不用每次重新摸索。

还应有一条服务验收命令序列。重新读取 unit，启动服务，查看 status，读取 journal，访问健康接口，确认开机自启。以后 AI 写了 service 文件，也按这条序列验收。

## 安全边界

systemd service 可以设置一些安全边界。比如限制服务能访问的路径，给服务独立临时目录，再控制新权限和可写位置。这些配置不能代替应用安全，但能减少服务出错后的影响。初学阶段不用一次全开，先知道它们存在。

最常见的边界仍然是运行用户。Web 应用用普通用户，数据库用数据库用户，队列 Worker 用对应服务用户。服务不需要写代码目录，就不要给写权限。服务只需要读配置，就不要把配置目录交给它改。

私有临时目录也有用。有些服务会写临时文件。给服务独立临时目录，可以减少不同服务互相影响。上传中转、图片处理和导出任务都可能用到临时空间。临时目录满了或权限错了，服务也会失败。

资源限制要配合业务。最大打开文件数太低，WebSocket 或高并发连接会失败。内存限制太低，构建、图片处理和报表任务会被杀掉。限制要根据监控、测试和同机服务来定。

## timer 和计划任务

systemd timer 可以替代一部分 cron。它把计划时间和执行服务分开。好处是日志统一，状态可查，失败能和 service 一样排查。备份、证书检查、缓存清理和定时报表，都可以用 timer 管。

timer 也要有幂等设计。任务可能因为服务器重启、时间调整或手工触发而重复执行。备份任务重复跑，最多浪费空间。扣款、发邮件、迁移数据这类任务重复跑，就可能出事故。任务自己要能判断是否已经处理过。

计划任务不能无声失败。每次执行要有日志，失败要告警。若任务生成文件，还要检查文件大小和时间。只看到 timer active，不代表任务产物正确。和 service 一样，状态只是入口，结果要验收。

## 发布流程里的 systemd

发布时，systemd 通常负责让新版本进程接管服务。若应用是无状态 Web 服务，可以更新文件或切换目录后 restart。若服务支持 reload，也可以先 reload。若应用有长连接、上传和后台任务，就要更谨慎。

发布脚本里不要只写 restart。先确认新产物存在，配置文件可读，环境变量文件可读，端口没有被其他进程占用。重启后看 status 和日志，再访问健康接口。最后记录版本和服务启动时间。

回滚也要接入 systemd。旧版本目录、旧环境变量和旧 service 配置在哪里，要能说清。若只回滚代码，不重启服务，旧进程仍在跑新代码或旧配置，结果会很混乱。发布记录里写清 systemd 做了什么。

## 一次 unit 写错案例

一个 Node 服务手工运行正常，放进 systemd 后一直启动失败。status 只显示退出，journal 里有一行说找不到 `node`。原因是开发者在 shell 里用 nvm 管 Node，systemd 启动时没有加载这个 shell 初始化。

修复有几种。可以在 service 文件里使用 Node 的绝对路径。也可以把运行时安装到系统路径。还可以用容器或构建产物减少服务器运行时差异。无论哪种，service 文件都要写清启动命令依赖什么。

这个案例提醒我们，手工运行成功只能证明当前 shell 环境可用。systemd 服务有自己的环境、工作目录和用户。排查时把二者对照起来看，通常能很快找到差异。

## 重启风暴和日志保留

服务配置错误时，重启策略可能让它反复启动又反复失败。CPU 和磁盘被日志拖高，真正错误反而淹没在重复输出里。看到服务不断重启，先停止继续尝试，读取最早几次失败日志。第一轮失败常常比第一百轮更有价值。

systemd 会限制过快重启，但不要把这个限制当成修复。它只是防止服务把机器拖死。修复仍要回到启动命令、环境变量、端口、权限和依赖。若重启次数已经很高，发布记录里要写清恢复前后的次数变化。

日志保留也要配置。journal 可以按大小和时间保存日志。个人项目可以保留较短时间，生产项目要结合事故排查和隐私要求。日志太少，事故时缺线索。日志太多，会占磁盘，也可能保存过量用户信息。

导出日志时只截取相关时间段。把整台机器的 journal 全量发给别人，会带出太多无关信息。更好的做法是按服务、时间和请求 ID 取片段，再脱敏。这样 AI 和协作者都能聚焦在问题上。

这部分也要进入交接材料。别人接手服务时，应该知道日志保留多久、重启异常怎么看、告警在哪里触发。systemd 管的是进程，团队要管的是服务能不能被理解和恢复。

这也是本章的最后验收点，写进记录后再继续，不要只凭个人临场记忆处理。

AI 可以帮你解释 service 文件、梳理启动失败路径和总结脱敏日志。不要把真实环境变量、密钥、用户请求和完整生产日志交给它。下一章看防火墙、Caddy、Nginx、域名和 HTTPS。
