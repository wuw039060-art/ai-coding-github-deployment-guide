# systemd、systemctl、journalctl 和服务日志

手工运行应用时，关闭 SSH 窗口后进程可能退出。服务器重启后，它也不会自动回来。生产应用需要一个可靠的管理者负责启动、停止、监视和记录运行状态。Ubuntu 常用 systemd 完成这件事。systemd 是 Linux 系统的一组基础组件，其中的系统与服务管理器以 PID 1 运行，并启动和管理其他服务。

`systemctl` 是查看和控制 systemd 单元的命令。`journalctl` 用来读取 systemd 日志系统保存的记录。三个名称相似，职责不同。

## 先理解四个对象

程序文件是磁盘上的可执行内容，例如 `/usr/bin/caddy` 或项目中的应用运行时。服务单元文件描述怎样启动程序、使用哪个用户、在哪个目录运行、失败后是否重启，以及依赖哪些系统能力。文件名通常以 `.service` 结尾。进程是程序实际运行后的实例。一个服务可以产生一个或多个进程。

日志是服务和管理器在运行期间留下的事件。状态只告诉你当前和最近概况，日志提供时间顺序中的详细证据。修改单元文件不会自动改变已经运行的进程。重新加载 systemd 配置也不会自动重启所有服务。这些动作要分开执行。

下面命令在远程 Ubuntu 服务器运行，只读取 SSH 服务状态。

```
sudo systemctl status ssh
```

`systemctl` 与 systemd 管理器通信。`status` 请求状态。`ssh` 是服务单元名称，省略的 `.service` 通常会被补全。输出中常见几项内容。

- `Loaded` 表示单元文件是否被找到，以及是否设置开机启动
- `Active` 表示当前运行状态
- `Main PID` 表示主要进程编号
- 最近几行日志提供启动或失败线索

`active (running)` 表示服务当前正在运行，不证明外部一定能连接。防火墙、端口、账号和应用内部错误仍需单独验证。`failed` 表示启动或运行失败。不要只执行重启。先保存状态输出和最近日志。

## status 可能进入翻页器

输出较长时，终端会进入分页查看程序。屏幕底部可能出现 `(END)`，键盘输入看起来不像普通命令行。按方向键或空格滚动，按 `q` 退出。很多初学者以为终端卡住，反复按 `Ctrl+C`。认识分页器能避免误判。需要一次性输出并返回提示符时，可以使用。

```
sudo systemctl --no-pager status ssh
```

在自动记录或复制短结果时更方便。输出仍可能包含主机名、路径和错误内容，分享前要检查秘密。

`start` 启动当前未运行的服务。

```
sudo systemctl start notes-api
```

`stop` 请求服务停止。

```
sudo systemctl stop notes-api
```

`restart` 先停止再启动，通常会造成短暂中断。

```
sudo systemctl restart notes-api
```

`reload` 请求服务在不完全重启的情况下重读配置，但只有服务实现了这项能力时才有效。

```
sudo systemctl reload caddy
```

不要把 `reload` 和 `restart` 当作同义词。配置错误时，两者失败表现也可能不同。操作前先使用软件自己的配置验证命令。

## enable 与 start 也不是一回事

`enable` 设置服务在适当的系统启动目标中自动启动。它不一定立即启动服务。

```
sudo systemctl enable notes-api
```

`start` 只影响当前运行状态，不保证服务器重启后自动启动。需要两项都完成时，可以显式运行两条命令，便于读者看清作用。某些教程使用 `enable --now` 合并操作，初学阶段分开更易审查。检查是否启用可以运行。

```
systemctl is-enabled notes-api
systemctl is-active notes-api
```

第一条回答是否启用，第二条回答当前是否活动。返回文字和命令退出码都能用于自动检查。

## 单元文件的最小结构

下面是教学示例，不应原样用于未知项目。

```
[Unit]
Description=Notes API
After=network.target

[Service]
Type=simple
User=notesapp
WorkingDirectory=/srv/notes-api/current
ExecStart=/usr/bin/node server.js
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

`[Unit]` 描述名称和依赖关系；`After` 只规定启动顺序，不证明数据库或互联网已经可用；`[Service]` 描述进程。`User` 指定运行用户，`WorkingDirectory` 指定工作目录，`ExecStart` 指定启动命令，`Restart` 指定失败后的处理。`[Install]` 描述启用时与哪个启动目标关联。路径要用绝对路径。systemd 的环境与交互终端不同，终端里能找到的 `node` 不一定在服务的搜索路径里。使用 `command -v node` 找到真实路径，并确认服务用户有权限执行。

## 单元文件放在哪里

管理员自己创建的系统级服务常放在 `/etc/systemd/system`。发行版软件包提供的单元通常位于 `/usr/lib/systemd/system` 或 `/lib/systemd/system`，具体路径随发行版布局变化。不要直接修改软件包管理的原始单元。升级可能覆盖它。使用 `systemctl edit 服务名` 创建覆盖配置，或者按软件官方方式管理。

查看 systemd 实际加载的单元内容可以运行。

```
systemctl cat notes-api
```

它会显示来源路径和合并后的片段。排错时比只查看你以为存在的某个文件更可靠。

## 修改单元后的顺序

编辑或新增单元文件后，先让 systemd 重读单元定义。

```
sudo systemctl daemon-reload
```

这条命令不会自动重启 `notes-api`。接着检查单元，再明确重启目标服务。

```
sudo systemctl restart notes-api
sudo systemctl status notes-api
```

预期状态为 `active (running)`。随后还要对本机健康检查地址发请求。服务运行和业务可用是两项验收。若新配置失败，立即查看日志。不要在没有理解失败原因时连续执行 `daemon-reload` 和 `restart`。

## journalctl 从哪里取日志

systemd-journald 收集内核、服务和其他来源的日志。`journalctl` 提供查询入口。日志是否持久保存、保留多久，取决于系统配置和磁盘策略。查看某个服务的日志。

```
sudo journalctl -u notes-api
```

`-u` 按单元筛选。输出可能进入分页器，按 `q` 退出。只看最近五十行。

```
sudo journalctl -u notes-api -n 50 --no-pager
```

`-n 50` 限定最近五十行，`--no-pager` 直接返回提示符。systemd 的官方 `journalctl` 手册记录了按单元、实时跟随和启动范围等筛选方式。

## 实时跟随日志

复现故障时，可以在一个 SSH 窗口运行。

```
sudo journalctl -u notes-api -f
```

`-f` 表示持续等待新日志。它不会自动结束，按 `Ctrl+C` 停止跟随。在另一个窗口执行测试请求。这样能把一个操作与紧接着出现的日志对应起来。测试完成后停止跟随，避免忘记窗口正在持续输出。SSH 服务也能用同一方法查看。

```
sudo journalctl -fu ssh.service
```

Ubuntu OpenSSH 文档给出了这个实时日志入口。

## 按时间和启动次数缩小范围

服务昨天失败，今天已经恢复时，只看最新日志会漏掉原因。可以使用明确时间。

```
sudo journalctl -u notes-api --since "2026-08-05 09:00"
```

时间字符串由 journalctl 解析。服务器时区与本地时区不同会造成偏差，先运行 `timedatectl` 查看服务器时区。查看本次启动以来的日志。

```
sudo journalctl -b -u notes-api
```

查看上一次系统启动的同一服务日志。

```
sudo journalctl -b -1 -u notes-api
```

如果日志没有持久保存，上次启动记录可能不存在。这个结果本身就是日志配置线索。

## 从一次启动失败读日志

假设状态显示 `failed`，日志出现 `No such file or directory`；先看消息中的完整路径；若 `WorkingDirectory` 不存在，服务在执行程序前就会失败；若 `ExecStart` 的二进制不存在，说明路径或安装有误；若出现 `Permission denied`，检查服务用户对程序、工作目录和配置的权限。看到数据库连接拒绝时，systemd 可能已经正确启动应用，故障位于依赖服务或网络。不要因为日志来自 systemd 就认为 systemd 是根因。

维护者的 systemd 管理文章展示了 `systemctl status` 把服务元数据和最近日志放在同一处的排错价值。

`Restart=on-failure` 能让意外退出的服务自动恢复。若配置永久错误，服务会不断启动、失败、再启动。循环会快速增加日志，也可能持续请求数据库或第三方 API。`systemctl status` 中的重启次数和短时间重复日志是明显线索；先停止服务，修正原因，再启动验证；不要把重启间隔调得极短来“提高可用性”；真正的配置错误不会被频繁重试治好。

你在 SSH 终端中运行 `export API_KEY=...`，变量只存在于当前 shell 和它启动的子进程。systemd 从自己的管理环境启动服务，不会自动继承这个终端变量。单元可以通过 `Environment` 或 `EnvironmentFile` 指定变量。真实秘密不应直接写在公开仓库的单元文件中。

若使用环境文件，限制读取权限，记录路径但不记录秘密内容。修改后要重启服务才能让新进程读取。日志和错误输出也不能打印秘密。更复杂的生产系统可使用专门秘密管理服务。本书先要求做到来源明确、权限受限、不会进入 Git、能安全轮换。

## 日志里也可能有秘密

应用为了排错打印完整请求头，可能把访问令牌写入日志。数据库连接错误也可能包含用户名和地址。分享日志前删去令牌、密码、会话标识、个人数据和内部地址。保留时间、错误类型、调用位置和必要上下文。

不要通过删除整个日志来处理泄露。先停止继续写入，轮换已经暴露的秘密，再按保留和合规要求处理历史日志。

journal 有自己的保留机制，应用还可能同时写普通文件。若错误循环每秒写很多行，磁盘仍会快速增长。查看 journal 占用。

```
sudo journalctl --disk-usage
```

这是只读查询。清理日志属于删除操作，执行前要确认事故证据已经保存、保留要求允许，并先修复持续写入原因。磁盘空间不足时，优先停止日志风暴或故障服务。盲目扩盘只会把同一问题推迟。

## 一次安全的服务变更

先记录当前版本、单元内容、状态和健康检查结果。保存配置备份，确认回滚版本仍在服务器。修改配置后使用程序自带验证器。修改单元后运行 `daemon-reload`。重启目标服务，再依次检查状态、最近日志、本机健康地址和外部地址。

任何一步失败，就停止后续流量切换。恢复旧配置或旧发布，重新加载并再次完成四项检查。服务状态截图不是全部验收证据。至少保存命令、时间、预期、实际和修正结果。

通过 Ubuntu 软件包安装的 Caddy、Nginx、PostgreSQL 等软件通常已经提供经过维护的单元。优先使用并通过覆盖配置做小调整。容器由 Docker Compose 管理时，主机上通常只需管理 Docker 服务和 Compose 项目，不要再为每个容器重复写 systemd 单元。

托管平台已经管理进程时，也不需要 systemd。先判断谁负责进程生命周期，避免两套管理器互相重启和争抢端口。

## 查看单元是否有语法与引用问题

systemd 提供单元验证工具。下面命令在远程服务器运行，只检查指定文件。

```
systemd-analyze verify /etc/systemd/system/notes-api.service
```

它可能报告未知指令、缺失程序和依赖问题。部分警告来自系统中其他单元，阅读时要看文件名和行号。验证通过不证明应用能连接数据库，也不证明权限正确。它只缩小到单元结构和静态引用。修改系统单元前先复制原文件，并使用 `systemctl cat` 保存当前实际配置。验证失败时不要重启正在正常运行的旧进程。

单元可能由原始文件和多个覆盖片段合并。`systemctl show` 能读取 systemd 当前理解的属性。

```
systemctl show notes-api \
  --property=User,Group,WorkingDirectory,ExecStart,Restart
```

反斜杠用于终端换行，复制时可以合成一行。命令只读，输出展示最终用户、组、目录、启动命令和重启策略。你修改了某个片段，`show` 仍显示旧值时，检查文件位置和 `daemon-reload`。不要反复编辑另一个未被加载的文件。

## 服务失败后为什么 start 仍可能不工作

服务在短时间内连续失败，systemd 可能触发启动频率限制。此时修好配置后直接 `start`，仍会收到启动过于频繁的提示。先查看状态和日志，确认根因已经修复。再运行。

```
sudo systemctl reset-failed notes-api
sudo systemctl start notes-api
```

`reset-failed` 清除失败状态和部分计数，不会修复应用。若根因仍在，服务会再次失败。不要把频率限制关闭来掩盖循环。它在保护 CPU、日志和上游服务。

`.service` 管理服务进程。`.socket` 可以先监听端口，在连接到来时激活服务。`.timer` 按时间触发另一个单元。初学者日常部署主要接触 service。定时备份、报告或清理任务可以使用 timer，它比把任务绑在某个 SSH 会话中可靠。

查看定时器。

```
systemctl list-timers --all
```

命令只读，会显示上次和下次触发时间。时间受服务器时区影响，任务是否成功还要查看被触发服务的状态和日志。定时器显示已触发，不代表备份文件有效。业务结果仍需单独验证。

## 定时任务失败怎样查

假设 `notes-backup.timer` 触发 `notes-backup.service`。先查看两者状态，再按服务名查日志。

```
systemctl status notes-backup.timer
systemctl status notes-backup.service
sudo journalctl -u notes-backup.service -n 100 --no-pager
```

timer 负责时间，service 负责实际命令。只看 timer 为 active，可能漏掉最近一次 service 失败。日志中确认输出路径、退出状态和完成时间。备份任务成功退出后还要验证文件大小、校验和与恢复。

应用使用相对路径读取 `./config.json` 时，结果取决于当前工作目录。SSH 中从项目目录启动正常，systemd 默认目录不同，服务就找不到文件。单元中的 `WorkingDirectory` 应使用存在的绝对路径，并让服务用户能够进入。应用更稳妥的做法是对关键资源使用明确配置路径。

日志显示找不到相对文件时，先查最终 `WorkingDirectory`，不要把配置复制到多个未知目录。发布使用 `current` 符号链接时，服务重启后会进入新目标。回滚要确认链接、目录权限和依赖都恢复。

## ExecStart 不是交互式 shell

systemd 默认不会像终端那样解释管道、重定向、通配符和 shell 内建命令。把一长串 shell 命令直接写进 `ExecStart` 容易失败。优先让 `ExecStart` 指向一个明确程序和参数。需要复杂准备时，把逻辑放入受版本控制、可单独测试的脚本，并明确解释器。

环境变量替换和引号规则也与 shell 不完全相同。终端中能运行的一行不能保证原样放入单元。使用绝对程序路径，执行前以服务用户在相同工作目录测试。仍要避免把秘密放到命令行，因为进程列表可能显示参数。

`Type=simple` 常用于以前台方式运行、不会自行派生后台进程的应用。systemd 在进程启动后就认为服务已开始。`Type=notify` 让支持通知协议的程序在真正准备好后告知 systemd。`Type=oneshot` 适合执行一次并退出的任务。类型选错会出现状态看似成功却尚未就绪，或程序已经后台化而 systemd 跟错进程。使用软件包提供的单元时不要随意改变。

自建应用优先遵循运行时或框架的官方 systemd 示例，并用真实健康检查补充状态。

## Restart 策略要配合退出原因

`on-failure` 在非正常退出时重启，正常停止通常不重启。`always` 连正常退出也会再启动。批处理任务正常完成后应退出，使用 `always` 会让它无限重复。长期 API 服务异常退出则可能需要自动恢复。设置 `RestartSec` 留出重试间隔，避免每毫秒循环。上游数据库故障时，过快重试也会增加压力。

自动恢复必须有次数或持续失败告警。用户看见服务短暂恢复，不代表根因消失。

systemd 先向服务发送正常终止信号，等待一段时间。程序应停止接收新请求、完成必要清理并退出。超过超时时间后，管理器可能发送强制信号。数据库写入和长任务可能因此中断。应用要实现优雅关闭，反向代理或负载均衡器也要先停止向旧实例发送新流量。维护窗口中测试一次有活动请求时的停止行为。

不要把停止超时设为零来追求速度。要根据最长安全事务和用户可接受中断确定。

## reload 能否生效由程序决定

Caddy、Nginx 等服务支持在保持现有连接的同时加载新配置。应用若没有 reload 处理，`systemctl reload` 可能报告不支持。先用 `systemctl show` 查看 `CanReload`，再查软件官方文档。配置验证通过后才加载。加载后检查进程、日志和请求。某些设置只有完整重启才能生效，不能凭命令返回成功猜测。

如果 reload 失败，旧进程可能仍在运行。先确认当前服务状态，再决定回滚配置或安排重启。

journal 记录时间、主机、单元、进程和优先级等结构化字段。`journalctl -o verbose` 可以查看详细字段，输出很长，适合针对单条记录调查。按优先级筛选错误。

```
sudo journalctl -u notes-api -p err --since today
```

`-p err` 只选错误及更严重级别，`--since today` 限定今天。应用若把所有消息都写成普通信息，筛选会漏掉业务错误。日志级别需要在应用中正确使用。严重级别也不能替代监控，错误可能没有日志或被错误捕获。

## 日志时间为什么与本地不一致

服务器常使用 UTC，读者电脑使用中国标准时间。复制日志时若不写时区，事件顺序会混乱。下面命令只读查看时间设置。

```
timedatectl
```

输出包含本地时间、UTC、时区和同步状态。不要为了让日志看起来熟悉就随意更改生产服务器时区。事故记录统一使用带时区的时间，例如 `2026-08-05 14:20 +08:00`。比较不同系统记录时更可靠。

部分系统把 journal 放在易失位置，重启后旧日志不存在。持久日志通常位于 `/var/log/journal`，具体行为由配置决定。生产环境需要根据磁盘、隐私和调查要求设置保留。长期无限保存会占满磁盘，保留过短又无法调查低频问题。

更改 journald 配置属于系统级变更，先查当前 Ubuntu 和 systemd 文档，验证配置，再重启相应服务。不要只创建目录就假定策略完成。关键应用还可以把日志发送到独立平台，服务器故障时仍可查看。远程日志也要限制秘密和个人数据。

## 服务资源限制

systemd 能限制服务的内存、CPU、文件数和其他资源。限制可以防止一个应用拖垮整机，也可能让配置过小的服务频繁失败。看到进程被终止或无法打开更多文件时，查看单元限制和内核日志。不能只调大上限。

先测真实峰值，保留余量，设置告警。限制命中应产生可观察事件，并有清楚恢复步骤。初学项目可以先监控，不急着配置复杂沙箱。安全加固要逐项验证应用需要的文件、网络和系统调用。

`is-enabled` 返回 enabled 只是配置状态。要证明服务器重启后服务可用，需要一次受控重启验收。安排维护窗口，保存状态和备份，确认云控制台入口。重启后记录恢复时间，检查 SSH、网络、磁盘挂载、目标服务、代理和业务请求。

如果服务依赖数据库或挂载，可能因启动顺序过早失败。`After` 只控制顺序，应用仍应对依赖暂时不可用进行有限重试。不要在没有回滚和通知的生产高峰做第一次重启测试。

## 服务依赖不要写得过度严格

单元可以声明顺序和强依赖。强依赖会在目标失败时连带停止服务，错误使用可能扩大故障。应用依赖数据库，不表示数据库短暂重启时应用必须永久失败。应用可以有限重试并在恢复后继续工作。网络目标达到也不保证外部互联网、DNS 或第三方 API 已可用。启动代码仍要处理暂时失败。

先用最少依赖表达真实关系，再通过健康检查证明就绪。不要复制一个包含大量 `After` 和 `Requires` 的单元模板。

名称带 `@` 的单元可以按实例参数运行多份，例如 `worker@1.service` 和 `worker@2.service`。它适合多个结构相同的工作进程。每个实例仍有独立状态和日志筛选。个人项目只有一个进程时，不需要为灵活性提前使用模板。普通 service 更容易理解和维护。

看到系统自带的 `getty@` 等名称时，知道它是实例化单元即可，不要随意停止。

## drop-in 覆盖比复制整份单元更稳

软件包升级会更新原始单元。把完整文件复制到 `/etc` 后，你可能长期错过上游改进。`systemctl edit caddy` 等命令会创建只包含差异的覆盖片段。执行前仍要了解软件包支持方式。查看 `systemctl cat` 时会按顺序显示原始文件和覆盖。记录每个片段的目的。

不再需要覆盖时，先保存内容、移除精确片段、`daemon-reload` 并验证服务。不要删除整个 systemd 配置目录。

单元引用不存在的环境文件，服务可能直接启动失败。路径前加特定前缀可表示文件可选，但秘密配置通常不应可选。部署前检查文件存在、所有者正确、服务用户可读、其他用户无权读取。文件内容使用程序期望的语法。

更新环境文件后重启应用，确认新进程读取。旧进程不会因磁盘文件变化自动得到新值。回滚代码时同时检查环境变量兼容。新版本新增必需变量，旧版本可能不认识或仍依赖旧名。

## 标准输出与文件日志不要重复无限保存

应用同时把日志写入文件和标准输出，journald 又保存标准输出，会产生两份内容。明确主要日志路径和保留策略。容器与 systemd 环境常优先标准输出，由平台收集。传统软件可能使用自己的文件与轮转。

重复日志增加磁盘与隐私风险，也让排错看到两套时间格式。删除一套前确认监控和审计没有依赖。应用应在日志中写结构化错误和请求标识，不需要每次成功都打印巨大对象。

同时查看测试和生产日志时，终端内容很相似。窗口标题、提示符和命令记录要标明环境。执行 `journalctl -f` 前先运行 `hostname`，把结果与开始时间记在故障记录。输出复制后仍知道来源。测试完成按 `Ctrl+C` 结束。它只停止查看，不会停止服务。

不要在日志窗口误输入服务控制命令。使用独立窗口能减少混淆。

## 一个状态为运行但业务失败的案例

`systemctl status notes-api` 显示 active，浏览器却持续 500。最近日志显示数据库认证失败。systemd 已完成启动程序的职责，进程也没有退出。故障位于应用配置或数据库身份。如果只不断重启，错误会重复并可能锁定账号。正确步骤是核对秘密来源、数据库可达和最近配置变更。

修复后重启，检查日志、本机健康地址和真实业务。状态始终为 active，不影响故障定位结论。

修改服务配置并重启以后，先在服务器查看 `systemctl status` 和本次启动日志，确认进程没有继续退出，也没有读取旧配置。接着从服务器本机访问健康地址，确认程序正在预期端口响应。最后从用户入口完成一个关键操作，例如登录测试账号并读取一条练习数据。三个位置都通过，才能说明这次服务故障已经恢复到用户可用状态。

若本机健康地址成功，公开地址仍失败，继续检查反向代理、防火墙、域名和证书。若公开首页成功，保存操作仍返回 500，回到应用与数据库日志。检查顺序由实际结果决定，不用重复重启碰碰运气。每一步记录时间，方便在 journal 和代理日志中找到同一次请求。

## 一个服务循环退出的案例

新发布把工作目录写错。systemd 启动应用失败，按重启策略连续尝试，日志每秒增加。先保存状态和几行代表日志，停止服务，修正目录。用服务用户检查路径，再验证单元。执行 `daemon-reload`、清除失败计数、启动并验收。确认日志增长恢复正常。

事故改进包括发布前静态验证、目录存在检查和重启次数告警，而不是永久关闭自动重启。

为每个自建服务记录单元名、运行用户、工作目录、启动命令、配置、环境文件、监听端口和健康地址。写出查看状态、最近日志、实时日志、重启、重新加载和回滚命令。每条说明执行位置与预期结果。

标出重启会中断多久、是否有后台任务、怎样确认数据库兼容。秘密只写存放系统和变量名。新成员按手册在测试环境完成一次启停，发现缺失就修订。手册能运行才有价值。

## 系统服务与用户服务

systemd 既能管理系统级服务，也能管理登录用户范围的服务。生产 Web 应用通常使用系统级单元和专用服务用户。用户服务命令带 `--user`，状态与系统服务分开。把两者混用会出现一个位置显示找不到，另一个位置实际运行。

查看进程的父级、运行用户和单元归属，确认谁在管理。不要为了找到服务而在两层同时创建同名单元。桌面程序适合用户服务，长期服务器应用按项目官方部署建议选择。

管理员为排错在终端运行一份应用，systemd 管理的旧进程仍在。两者可能争抢端口或同时处理后台任务。测试前先看 `ss`、`pgrep` 和服务状态。需要前台调试时停止目标服务，并在维护窗口使用测试端口。调试完成终止手工进程，再由 systemd 启动。确认只有预期 PID 和端口。

不能把手工进程留在 `tmux` 中当作正式服务。重启、日志和权限都不再由统一入口管理。

## 状态中的 exited 不一定失败

`active (exited)` 常见于一次性服务。它执行成功后进程退出，systemd 仍认为单元活动。长期 API 服务若显示 exited，就要检查单元类型和启动程序是否自行后台化。阅读 `Type`、`RemainAfterExit` 和日志，再判断。不能只把所有 active 都解释为正在处理请求。

用端口和健康请求验证业务，服务状态只是其中一项。服务名也可能带别名。`ssh.service` 与 `sshd.service` 在不同发行版和兼容配置中可能指向同一实现。先用 `systemctl status` 和 `systemctl cat` 查看实际单元，不要因教程名称不同就创建重复服务。本书以 Ubuntu 当前名称为示例，其他发行版要查自己的包文档。命令对象正确，才谈状态含义。
