# 文件上传、对象存储、邮件、推送和 AI API

现代应用的数据不只在数据库。用户上传图片，对象存储保存文件；邮件服务发送确认信；推送服务把通知送到设备；AI API 接收任务并返回生成结果。每增加一个外部服务，就增加权限、费用、失败和恢复边界。

本章把这些能力放回系统位置。读者不需要同时注册所有服务。只有产品确实需要时，才选择一项并完成最小、安全的接入。

## 文件通常不直接放进数据库

图片、音频、视频和 PDF 体积大，传输方式与结构化记录不同。对象存储为文件数据提供 Bucket、Object、Key 和元数据模型。数据库保存文件记录，例如所有者、对象 Key、原始文件名、类型、大小、状态和创建时间。文件字节保存在对象存储。

页面需要文件时，后端先检查权限，再返回受控下载或短时签名 URL。公开资源可以通过明确策略和 CDN 提供。把文件直接写进应用服务器本地目录，在多实例和重新部署时很容易丢失或不一致。临时目录只能放可重建内容，不能放用户唯一副本。

Key 看起来可以包含斜杠，例如 `users/17/avatar/abc.jpg`，但对象存储内部模型未必等同普通文件夹。不要直接使用用户原始文件名作为唯一 Key。重名、特殊字符、路径欺骗和隐私信息都会造成问题。生成随机标识，原始名称单独保存用于显示。

## 一次受控上传流程

客户端先向后端请求上传。后端验证登录、用途、大小上限和配额，生成对象 Key 与临时上传授权。客户端把文件直接上传对象存储，减少后端转发大文件的负担。上传完成后通知后端。后端确认对象存在、大小和类型，必要时进入病毒扫描、图片解码和转码队列。验证完成前状态为待处理，不对其他用户公开。

扩展名可以改，浏览器提交的 `Content-Type` 可伪造，文件头也不能单独证明安全。文件名由用户控制。安全上传通常组合使用允许扩展名、类型检查、文件签名、随机文件名、大小限制、授权、存储隔离和恶意内容扫描。

上传失败要有清理办法。数据库记录创建了，文件没上传，会留下待处理记录。文件上传了，数据库写入失败，会留下孤立对象。可以给对象 Key 加任务 ID，定期清理过期待处理对象。删除用户内容时，也要协调数据库、对象存储、缓存、搜索索引和备份保留。

压缩包和文档预览要额外小心。压缩包可能包含大量文件、超深目录和路径穿越。文档预览可能触发解析漏洞或泄露内部链接。高风险文件先放隔离区，后台任务完成安全检查后再开放。

## 邮件和推送是外部投递

邮件常分事务邮件和营销邮件。事务邮件包括注册验证、预约确认、密码重置和账单通知，用户通常期待它们立即到达。营销邮件需要订阅、退订、频率控制和合规记录。两类邮件不要混用同一套默认策略。

邮件发送成功只表示服务商接受或投递到下一站，不证明收件人看见。退信、投诉、退订和限流都要记录。密码重置链接要短期有效，只能使用一次，并绑定用户与场景。链接进入日志、客服截图或转发后，都可能带来风险。

推送通知要经过平台通道。Web Push、iOS、Android 和小程序各有权限、Token、审核和展示规则。用户关闭通知、设备换机、Token 过期、平台限流都会影响结果。推送适合提醒，不适合承载唯一业务状态。关键状态仍应能在应用内查询。

通知偏好要尊重用户选择。用户关闭营销消息后，不应继续通过另一渠道发送同类内容。安全提醒、账单和法律通知可能有不同规则，先在产品和合规层面定义，再落到技术实现。

## AI API 是外部计算服务

AI API 和邮件、支付一样，是外部服务调用。请求会消耗费用，响应可能慢，结果需要验证。不要把服务端密钥放进浏览器、App 或小程序前端。客户端请求自己的后端，后端检查身份、配额、内容范围和费用，再调用 AI 服务。

输入要最小化。能传摘要就不传完整用户资料，能传当前文件片段就不传整个文件库。涉及个人数据、商业秘密、医疗、法律和客户资料时，要按组织批准的工具与位置处理。日志中不要保存完整提示、原始文件和模型响应，除非业务明确需要并有保留策略。

AI 输出要当作外部数据。它可能格式不合、引用不存在、内容违规或与业务状态冲突。后端应验证 JSON 结构、字段范围、引用 ID 和权限。需要展示给用户时，界面应说明生成结果的状态，关键业务动作仍由规则和人工确认。

长任务不要压在一次请求里。用户提交文件总结，后端创建任务并返回 ID。工作进程调用 AI API，记录状态、费用、模型名称和错误。前端轮询或订阅任务状态。超时、重试和取消都要有规则。重复调用可能重复扣费，所以任务 ID 和幂等键很重要。

缓存 AI 结果可以省钱，但要看数据权限。公共帮助文档的摘要可以复用。用户私有文件、订单和病历的结果不能跨用户共享。缓存键应包含数据版本、用户权限范围和生成参数。数据删除后，相关缓存也要进入删除流程。

## 外部服务要有状态表

每个外部服务至少记录服务名、用途、密钥位置、调用方、费用指标、日志入口、失败提示、重试规则和负责人。表中不写明文密钥。供应商状态页只能说明供应商自报状态，不能替代自己的请求日志。

Webhook 要按供应商协议验证签名、防重放信息和事件标识。支付、邮件退信、对象存储回调和 AI 任务回调都可能重复发送。后端验证后先将事件可靠保存到任务表或持久队列，再快速确认接收，由工作进程幂等处理。签名失败时，只记录必要且经过清理的诊断信息；请求自报的来源和事件类型尚不可信，不应当作已确认事实，更不保存完整秘密。

费用也要进入设计。上传文件按容量和流量收费，邮件按发送量和信誉影响成本，推送可能有平台限制，AI API 按输入输出和工具调用计费。上线前设置预算或用量告警。账单突然增长时，按用户、接口、任务和供应商拆分，不先删除生产资源。

## 一个活动报名系统

用户报名后，后端写数据库，发送确认邮件，并允许上传凭证图片。图片先进对象存储待处理区，后台检查大小和格式，再把记录标为可用。邮件发送失败时，报名仍成立，系统记录待重发。管理员页面显示邮件状态和文件状态。

活动临近时，系统向已报名用户发送提醒。用户关闭提醒后，只保留必要事务通知。若 AI 用来生成活动摘要，后端只把公开活动内容和必要上下文发给 AI 服务，不发送报名者名单。摘要生成失败时，页面显示人工编辑版本或暂不展示。

这个例子里，数据库保存权威报名，存储保存文件，邮件和推送负责投递，AI 负责辅助生成。任何一个外部服务失败，都不应让维护者猜它是不是数据库问题。

## 隐私和保留期限

外部服务会扩大数据流动范围。邮件服务会看到收件人地址和邮件内容，推送平台会看到设备 Token 和消息摘要，对象存储保存文件内容，AI 服务可能看到输入文本。接入前先写清每项数据去了哪里、保留多久、谁能访问、怎样删除。

文件保留期限要和业务一致。用户删除头像后，公开 URL 应失效，数据库记录应更新，对象存储和缩略图应进入删除流程。备份中的残留要按政策处理。临时上传失败的文件可以更快清理，审计材料可能需要保留更久。不要让所有对象都永久保存。

邮件退订和推送偏好也属于数据状态。用户关闭通知后，新任务不应继续创建同类投递。已经排队的消息如何处理，要有规则。营销邮件、事务邮件和安全通知分开配置，别让用户退订营销后收不到密码重置。

AI 结果同样要有保留策略。草稿、摘要、标签和审核记录是否保存，保存多久，是否可由用户删除，都要写清。若结果参与重要决策，还要保留生成版本、输入范围和人工确认记录。

## 外部服务凭据轮换

外部服务通常靠密钥接入。邮件 API Key、对象存储访问密钥、推送证书和 AI 服务 Key 都应放在服务端环境变量里。前端、小程序端和移动端只能拿到临时令牌或受限配置。把主密钥打进客户端，就等于把项目交给所有能反编译安装包的人。

密钥要能轮换。文档里记录密钥创建位置、使用服务、权限范围和轮换周期。计划轮换且供应商允许新旧并存时，先创建新密钥，把服务切过去，确认调用正常，再停用旧密钥。不允许并存时，要按供应商流程安排切换和失败处置；已经泄露的凭据应优先止损。若供应商支持权限范围，上传、读取、删除、发信和推理调用分开授权。

泄露响应也要提前写好。发现密钥进入日志、截图、仓库或聊天记录后，先撤销密钥，再查最近调用记录。随后替换环境变量，重新发布服务，检查是否有异常账单和陌生资源。很多事故扩大，原因常常是没人知道撤销入口在哪里。

## 小程序上传和临时凭证

小程序上传文件时，常见做法有两种。一种是先传给自己的后端，再由后端写入对象存储。另一种是后端生成临时凭证或预签名地址，小程序直接上传到对象存储。前一种控制简单，但后端要承受文件流量。后一种效率更高，但临时凭证必须严格限制路径、大小、类型和有效期。

临时凭证不能让客户端随便写任意路径。后端可以为每次上传生成独立对象 Key，将其与用户和业务记录绑定，并保存到数据库。小程序上传成功后，再通知后端确认。后端检查归属、对象大小和实际内容，完成必要扫描后才把状态改为可用。短期授权不一定只能使用一次，还要防止客户端在验证后用仍有效的授权覆盖同一对象。可按存储服务能力限制覆盖、绑定对象版本，或将已验证文件转入客户端无写权限的最终位置。

删除也要从业务出发。用户撤销报名、删除头像或取消材料时，数据库状态先改变，后台任务再清理对象存储。若清理失败，记录待删除对象并重试。不要只删数据库记录。只删数据库会留下没人知道的文件，也会留下继续计费的存储。

微信生态里的图片、视频和订阅消息都有平台规则。上传前要看体积限制，发送订阅消息前要确认用户授权和模板用途。后端保存授权状态和发送结果，小程序端负责提示用户。把所有失败都显示成上传失败，会让用户不知道下一步该做什么。
