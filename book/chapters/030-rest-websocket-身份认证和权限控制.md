# REST、WebSocket、身份认证和权限控制

API 至少要回答三件事。客户端怎样表达操作，服务器怎样持续发送更新，服务器怎样知道请求者是谁并判断他能做什么。REST、WebSocket、身份认证和授权分别处理其中一部分。它们可以同时存在。一个应用用 REST 读取资料，用 WebSocket 接收新消息，用 Cookie 保持登录，再用授权规则限制每条消息。

## REST 用资源组织 HTTP

REST 常把业务对象视为资源，用 URL 表示位置，用 HTTP 方法表达动作。`GET /articles/42` 读取文章，`POST /articles` 创建文章，`PATCH /articles/42` 修改一部分，`DELETE /articles/42` 请求删除。团队不必追求教科书式纯粹，但方法语义要稳定。

GET 正常用于读取。浏览器、缓存和爬虫可能自动访问 GET，所以删除、扣款和发送邮件不应放在 GET 上。POST 常用于创建资源或触发动作。重复 POST 可能创建多份结果，需要幂等设计。PATCH 表示部分更新，DELETE 表达删除意图，业务上也可以先软删除。

路径中的 ID 不能代替权限。`/users/17/orders` 表示用户 17 的订单集合，可当前登录者是否能看，要由后端决定。不可猜 ID 能减少误撞，不能算授权。ID 可能从日志、链接、截图和分享里泄露。

## 实时连接处理持续更新

轮询、SSE 和 WebSocket 都能让客户端获得更新。轮询最简单，客户端每隔一段时间请求一次。SSE 适合服务端向浏览器推送事件。WebSocket 建立双向连接，适合聊天、协作编辑和游戏状态。

实时连接不替代数据库。客户端需要按协议衔接当前状态与后续事件，不能简单地先读取、再订阅，否则两步之间的变化可能漏掉。可以先订阅并暂存事件，再读取带版本的状态并合并后续变化，或使用服务支持的游标重放。断线后重新连接，也要补取遗漏状态。消息可能重复、乱序或丢失，业务消息应有 ID，并按版本或序号去重与排序；时间戳本身未必能确定唯一顺序。

WebSocket 建立连接时要认证，订阅频道时还要授权。用户不能只靠知道房间 ID 就加入别人聊天室。权限在连接期间变化时，服务端要停止推送或断开订阅。客户端发来的“我是管理员”没有安全意义。

## 认证回答你是谁

身份认证确认请求者是谁。常见方式有 Cookie 会话、Bearer Token、OAuth 登录、短信或邮件验证码、Passkey 和平台登录能力。浏览器站点常用 HttpOnly Cookie 保存会话标识。移动 App、小程序和服务端调用常用 Authorization Header 或平台推荐机制。

服务端会话通常较容易集中撤销，浏览器可以用 Cookie 保存对应标识。Token 是令牌的统称，随机会话标识也可以属于 Token；Cookie 则是浏览器存储与发送数据的机制，两者不互斥。自包含的签名 Token 可以减少部分会话查询，但撤销、权限变化和泄露处理更复杂。选择时看客户端类型、跨域需求、多设备、撤销速度和基础设施，不按“现代”或“无状态”决定。

密码不能明文保存。后端保存经过专用密码哈希算法处理后的结果，并使用合适参数。登录失败提示要谨慎，别让攻击者轻易枚举账号是否存在。重置密码、绑定手机、改邮箱和关闭账号都要有审计记录。

OAuth 2.0 主要处理委托授权，OpenID Connect 在其上提供身份认证。做第三方登录时，要按身份提供商的登录协议验证身份结果，不能把拿到任意访问令牌当作已经证明用户身份。业务资料仍要在本系统里建模。第三方返回的邮箱、头像和昵称不能自动变成业务权限。账号合并、重复邮箱和撤销授权都要有流程。

## 授权回答你能做什么

授权发生在认证之后。知道用户是谁，不代表他能读取任意资源。常见规则包括角色权限、资源归属、组织成员关系、套餐限制和当前状态。管理员、商家、普通用户和访客看到的入口不同，后端仍要逐次检查。

RBAC 按角色授予能力，适合后台管理。资源归属按对象判断，适合订单、文件、项目和租户。多租户系统要特别小心。甲租户不能通过改 URL、请求体、对象 Key 或实时频道访问乙租户。

权限缓存能提升速度，也会带来延迟。用户被移出组织后，旧 Token 或缓存权限可能还在短时间内有效。高风险操作应重新读取最新权限，或缩短缓存期。权限变化要有生效边界和撤销办法。

## 浏览器安全机制别用错

CORS 控制浏览器页面能否读取跨源响应。它不是身份认证。命令行工具、App 和小程序不受浏览器 CORS 规则约束，后端仍要认证和授权。把 CORS 设置成任意来源并允许凭据，容易扩大风险。

CSRF 与 Cookie 自动携带有关。用户已登录时，恶意页面可能诱导浏览器向目标站发请求。SameSite、CSRF Token、Origin 检查和高风险操作再次确认都能降低风险。GET 不应改变业务状态。

XSS 是不可信内容被当成脚本执行。HttpOnly Cookie 不易被脚本直接读取，但攻击脚本仍可能代表用户发请求。把长期 Token 放在 Local Storage 后，XSS 更容易读取并外传。存储位置要结合 XSS、CSRF、撤销和客户端类型设计。

## 用两个账号做权限测试

最小测试不要只用管理员。准备甲用户、乙用户、管理员和未登录状态。甲创建一条记录，乙尝试读取、修改和删除。管理员执行允许动作，再执行一个不该允许的跨组织动作。每一步记录请求、状态码、响应和后端日志。

实时功能也要同样测试。甲加入自己的频道，乙不能订阅。甲权限被移除后，已有连接应停止接收。聊天室、协作编辑、订单状态和推送通知都要测这一点。

一个常见事故是前端隐藏了按钮，API 却没有权限检查。攻击者复制请求后仍能删除别人资源。修复要在后端补资源归属与角色判断，再让前端显示更友好的错误。

## 账号枚举和会话细节

登录和找回密码很容易泄露账号是否存在。提示“邮箱不存在”和“密码错误”虽然友好，也给攻击者枚举名单的机会。面向公众的系统通常使用更模糊的提示，再通过邮件给真实用户下一步。后台日志可以记录具体原因，前端不必全部展示。

登录成功后要轮换会话标识，防止会话固定。用户改密码、退出所有设备、被管理员禁用或权限降低时，旧会话怎样失效要写清楚。只删除浏览器本地 Cookie，不代表服务端会话已经失效。移动 App 和小程序还可能保存本地登录态，也要有撤销和重新登录流程。

Passkey 能减少密码泄露风险，适合支持条件成熟的产品。它仍需要账号恢复、设备丢失、组织交接和备用登录方式。不要把 Passkey 当成省掉权限系统的办法。身份确认之后，后端仍要判断资源归属和角色。

## 第三方登录的重复账号

用户先用邮箱注册，后来用微信、Apple 或 GitHub 登录。两个身份可能对应同一个邮箱，也可能没有邮箱。系统要决定是绑定到原账号，还是创建新账号。自动合并很危险，尤其当邮箱未验证或第三方不提供稳定邮箱时。

比较稳妥的做法是让已登录用户主动绑定第三方身份。未登录状态下发现可能重复时，引导用户用原方式登录后确认。账号合并要记录时间、来源、操作者和可恢复办法。后台客服也不能只凭用户报一个邮箱就合并资产。

实时聊天室可以作为综合测试。甲和乙同在一个房间时能互相收消息。乙退出组织后，REST 读取被拒绝，WebSocket 订阅也停止。甲发送消息时，服务端按已验证身份写入作者 ID，不接受客户端传来的作者字段。这个测试能同时覆盖 REST、实时连接、认证和授权。

## 小程序登录和后端会话

微信小程序常见流程是客户端调用 `wx.login` 拿到临时 code，再把 code 发给自己的后端。后端拿 code 向微信服务端换取当前小程序的 openid 和会话密钥；满足相应条件时，响应中也可能有 unionid。后端再创建项目自己的会话，不把微信会话密钥当作前端登录令牌。AppSecret 和会话密钥都留在服务端，不能放进小程序包里。

openid 只能说明用户在某个小程序里的身份。若项目还有网页、App 或公众号，就要考虑 unionid、手机号绑定和账号合并。不要只凭昵称、头像或前端传来的 openid 认定用户。昵称和头像会变，前端字段也能伪造。

小程序的登录态也会过期。微信登录凭证与项目自己的后端会话要分别管理，不能假设两者同时失效。后端接口要能返回清楚的未登录状态。小程序端重新登录后，可以恢复草稿和页面位置；原操作若是付款、创建订单或其他写入，先查询结果或使用原幂等编号重试，不能不加判断地自动重发。直接把用户踢回首页，也会让很多问题看起来像功能坏了。

权限仍由后端判断。商家小程序、社区小程序和内部工具常有多角色。小程序端可以隐藏管理入口，但接口必须检查当前用户是否属于对应商家、组织或班级。审核版、体验版和正式版也要连到对应环境，避免测试用户改到生产数据。

## 验证码和风险控制

验证码、短信登录和邮件链接解决的是身份确认的一部分。它们也会带来成本和滥用风险。短信接口需要频率限制、图形验证或行为验证，还要记录发送原因和结果。找回密码邮件要有过期时间和单次使用限制。

公开接口要限制频率。登录、注册、发送验证码、上传文件、搜索和 AI 调用都可能被刷。限制可以按 IP、账号、设备、业务编号和组织维度组合。命中限制时给用户清楚提示，后台保留足够日志，别让真实用户和攻击流量混在一起。

风控规则要留人工入口。用户换手机、出差、公司网络出口变化，都可能触发异常。系统可以要求重新验证，也可以让客服审核。规则越严格，误伤越多。项目要知道自己保护的是什么，用户愿意为这道保护多付出几步。
