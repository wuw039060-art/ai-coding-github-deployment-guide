# REST、WebSocket、身份认证和权限控制

API 需要回答三组问题。客户端怎样表达操作，服务器怎样持续发送更新，服务器怎样知道请求者是谁并判断权限。REST、WebSocket、身份认证和授权分别处理这些问题的一部分。它们不是互相替代的四种框架。一个应用可以用 REST 读取资料，用 WebSocket 接收新消息，用 Cookie 保持登录，再用授权规则限制每条消息。

## REST 是面向资源的 HTTP 约定

REST 常把业务对象视为资源，用 URL 表示位置，用 HTTP 方法表达读取、创建、更新和删除。`GET /articles/42` 读取文章，`POST /articles` 创建文章，`PATCH /articles/42` 修改一部分，`DELETE /articles/42` 请求删除。这是一种常见设计方式，不要求所有系统使用完全相同路径。关键是团队约定稳定、方法语义合理、错误清楚。

URL 使用名词比动作堆叠更容易组织。复杂业务动作仍可建成子资源或明确命令端点，例如订单退款不是普通字段改写。

GET 用于读取，正常设计下不改变业务状态。浏览器、缓存和爬虫可能自动访问 GET，不能把删除放进链接。POST 常用于创建资源或触发无法简单表达的动作。重复 POST 可能创建多份，需要幂等机制。

PUT 通常表示用完整表示替换指定资源，重复同一请求应得到相同结果。PATCH 表示部分更新，具体补丁格式要约定。DELETE 表达删除意图，业务上可能先软删除。响应要说明资源已删除、已进入处理或不存在。

## 资源路径与嵌套

`/users/17/orders` 表示用户 17 的订单集合，`/orders/203` 表示具体订单。嵌套层级不宜过深。路径中的用户 ID 不能代替权限。当前登录用户请求 `/users/18/orders` 时，后端仍要确认是否有权查看。外部 API 使用不可猜 ID 只能减少误撞，不能当授权。攻击者可从日志、链接和分享获得 ID。

内部数据库主键是否直接暴露由架构决定。公开标识应稳定，不泄露敏感顺序信息。

普通 HTTP 请求由客户端发起，服务器返回后结束。聊天、协作编辑和实时仪表盘需要服务器主动送来更新。WebSocket 在建立连接后允许双方持续发送消息。MDN 把它定义为创建和管理 WebSocket 连接并收发数据的浏览器接口。

建立连接仍从网络握手开始。服务器要验证来源和身份，连接存活期间处理心跳、重连、权限变化与消息顺序。WebSocket 不是“更快的 REST”。它增加长期连接状态和运维复杂度。普通表单提交和资料读取继续使用 HTTP 往往更简单。

## 轮询、SSE 与 WebSocket

轮询是客户端每隔一段时间请求新数据。实现容易，更新不够即时，空请求也会消耗资源。Server-Sent Events 允许服务器通过一个 HTTP 连接持续向浏览器发送事件，方向主要是服务端到客户端。适合通知和进度。

WebSocket 双向通信，适合双方频繁交换消息。选择依据是数据方向、更新频率、基础设施和断线行为。一分钟更新一次的任务进度不必立即上 WebSocket。先用简单轮询验证产品，再按性能证据演进。

手机切换网络、电脑睡眠和代理超时都会断线。客户端要显示连接状态，并按退避策略重连。重连后可能漏掉事件。可靠设计使用序号、最后事件 ID 或从 REST 重新取得权威状态。不要把内存中收到的每条消息当永久事实。服务器持久化成功后才确认，客户端本地显示可以标记“发送中”。

MDN 的 WebSocket 客户端练习也处理页面隐藏、关闭和连接生命周期。

## 身份认证回答“你是谁”

用户提供密码、一次性验证码、第三方登录或设备凭据。系统验证后建立身份。密码应通过安全哈希保存，不能明文或可逆加密。登录还要有速率限制、多因素认证和异常检测。第三方登录把部分验证交给身份提供商，应用仍要验证回调、绑定本地用户并处理账号合并。

Firebase Authentication 提供密码、联合身份与其他认证方式的托管实现。它减少自建协议工作，应用仍负责权限和账号生命周期。

身份认证成功，只证明知道用户是谁。授权根据角色、资源归属、组织和当前状态决定是否允许。普通用户能编辑自己的资料，客服能查看必要订单，财务能退款，管理员能管理账号。角色不应无限扩大。

每个后端端点都检查授权。前端隐藏按钮只能改善界面，不构成安全控制。数据库也可使用行级安全或受限账号加强边界。策略与后端规则保持一致并测试。

## Cookie 会话怎样工作

登录成功后，服务器生成随机会话标识，把会话状态保存在服务端或受控存储。浏览器通过 Cookie 保存标识；后续同站请求按 Cookie 规则自动携带；服务器查会话，得到用户与到期时间。认证 Cookie 通常设置 Secure，只通过 HTTPS 发送；HttpOnly，阻止普通 JavaScript 读取；SameSite，限制部分跨站发送。MDN 提供这些属性的当前说明。

Cookie 还要设置合理 Path、Domain 和过期。登出时服务端使会话失效，不能只删除页面显示。

Token 是凭据载体，不会自动更安全。放在可被恶意脚本读取的存储中，发生 XSS 时容易被窃取。自包含 Token 可以减少每次查会话，撤销与权限立即变化更复杂。短期访问 Token 常配合受保护刷新机制。

浏览器应用选择 Cookie 或 Header Token，要考虑跨站、XSS、CSRF、移动客户端和服务端能力。不要把 JWT 当加密盒。常见 JWT 内容只编码并签名，持有者能读取 Payload，不能放密码和秘密。

## CSRF 与 XSS 位于不同方向

CSRF 诱导已登录浏览器向目标站发送请求，利用 Cookie 自动携带。SameSite、CSRF Token、来源检查与重新认证可降低风险。XSS 让攻击脚本在站点上下文运行，可能读取页面数据、替用户操作或窃取可访问 Token。输出编码、内容安全策略和安全 DOM 操作是重要防护。

HttpOnly Cookie 能阻止脚本直接读取凭据，却不能阻止脚本在当前页面发出已认证请求。安全措施需要组合，不能用一个属性宣称登录绝对安全。

会话有创建、使用、刷新、撤销和过期。修改密码、账号被禁用和安全事件后，应能撤销现有会话。长期登录提高便利，也扩大丢失设备风险。敏感操作可要求重新认证。多设备会话页面让用户查看和退出陌生设备。日志记录创建时间、最近活动和撤销原因。

服务端时间作为到期依据，客户端倒计时只用于显示。

## 一个两账号权限测试

创建测试用户甲和乙，各自创建一条私人笔记。记下资源 ID。甲登录后读取自己的笔记应成功。把 URL 中 ID 换成乙的笔记，应得到 403 或不泄露存在性的 404。甲尝试修改乙的笔记也应失败。管理员测试账号按明确权限可访问，操作进入审计日志。

退出甲后重复请求，应得到未认证结果。仅从界面看不见乙的笔记不算通过，必须直接调用端点测试。

连接建立时验证会话，订阅房间时再检查成员身份。不能让任意已登录用户订阅任意房间 ID。用户被移出房间或会话撤销后，现有连接需要停止接收。只在握手时检查一次会留下窗口。客户端发送消息时再次检查权限与内容。服务器不能信任客户端声明的发送者 ID。

重连时重新认证，旧连接令牌过期要有明确处理。

## CORS 不是身份认证

跨源资源共享由服务器告诉浏览器哪些源可读取响应。它主要约束浏览器，不阻止服务器、脚本工具和攻击者直接调用 API。允许某个 Origin 不能证明请求者身份。API 仍需认证和授权。带凭据跨源请求需要精确 Origin 和相应配置，不能与通配符随意组合。

开发时把所有源都允许，生产忘记收紧，会扩大攻击面。使用当前实际前端域名清单。

登录成功但所有 API 401，检查 Cookie Domain、Path、Secure、SameSite 和前后端域名。只有跨域失败，Network 若显示预检错误，检查 CORS 方法、Headers 与 Origin。不要关闭浏览器安全功能。

用户能改别人资源，说明后端只验证登录，没有验证归属。立即限制接口并检查访问日志。WebSocket 频繁断开，记录关闭码、代理超时、心跳和网络切换。不要无限快速重连。

## 密码怎样存

服务端使用专门密码哈希算法和随机 Salt，不保存明文，也不使用普通快速哈希直接处理密码。算法参数随硬件和安全建议调整。登录成功时可逐步升级旧哈希。数据库泄露后，哈希仍可能被离线猜测，所以要求合理密码、阻止常见泄露密码并提供 MFA。

管理员也看不到用户密码。客服流程不能要求用户把密码发来。

MFA 在密码之外要求另一个因素，例如认证器、硬件安全密钥或设备确认。短信验证码有覆盖面，也面临号码接管和网络问题。高权限账号优先使用抗钓鱼更强的方法。启用时生成恢复码，安全保存并测试恢复。丢失第二因素的人工恢复是重要攻击入口。

敏感操作可以要求最近完成 MFA，即使会话仍登录。

## OAuth 与 OpenID Connect 的最低认识

OAuth 主要处理委托授权，OpenID Connect 在其上提供身份信息。应用把用户引导到身份提供商，再接收授权结果。应用不应直接收集第三方账号密码。回调验证 State、Nonce、授权码和预先登记的 Redirect URI。

访问 Token 授予特定资源范围，不是用户所有权限。Refresh Token 更敏感，放在受保护服务端。“使用某平台登录”仍要创建或关联本地用户，并处理邮箱变化、撤销和账号删除。

第三方 API 通过 Scope 限定读取资料、发送邮件或管理文件等能力。只请求功能需要的范围。用户拒绝某个可选 Scope 时，应用应降级，不能强迫授予无关权限。扩大 Scope 可能要求用户重新同意。变更前解释用途并更新隐私说明。

撤销第三方授权后，本地应用要停止调用并清理不再需要的 Token。

## RBAC 与资源归属

基于角色的访问控制常叫 RBAC。角色如访客、编辑和管理员，对应一组能力。仅靠角色仍不足以区分“自己的订单”和“别人的订单”。资源归属条件与角色一起判断。组织应用还要检查用户是否属于当前组织。URL 中组织 ID 不能决定归属。

管理员能力拆分为客服、财务和账号管理，减少一个账号拥有所有权限。

更复杂系统会根据部门、地区、时间、设备和资源状态授权，常称属性策略。规则变复杂后，需要集中策略、测试和审计。散落在每个路由中的条件容易不一致。拒绝作为默认结果。规则无法判断时不应自动放行。

给权限变化设置生效时间和撤销流程，避免长期临时授权。

## 会话固定与登录后轮换

攻击者若能预先给用户一个会话 ID，再等待用户登录，可能劫持已认证会话。登录成功和权限提升后生成新的会话标识，旧标识失效。登出与密码变更也按策略撤销。会话 ID 使用高强度随机值，不能由用户 ID 和时间推算。

Cookie 属性保护传输与脚本访问，服务端轮换保护生命周期，两者都需要。

长期登录应使用可撤销、限时和设备绑定适度的 Token，不把普通会话无限延长。用户能查看长期登录设备并逐个撤销。高风险操作重新验证密码或 MFA。公共电脑不默认开启。登录页清楚说明持续时间。

Token 泄露后服务端可查找和撤销，日志不保存完整值。

## 账号枚举

登录和找回页面若分别提示“邮箱不存在”和“密码错误”，攻击者能收集注册用户。公开响应使用统一提示，例如凭据无效或若账号存在将发送邮件。内部日志保留准确原因。响应时间也尽量接近，避免从明显时间差推断。

客服和管理员需要查账号时使用受权限保护的内部工具。

攻击者会尝试泄露名单中的邮箱密码组合。单纯按账号永久锁定会被用来拒绝服务。组合限流、风险检测、MFA、泄露密码检查和用户通知。异常成功登录触发会话审查。验证码接口限制发送与验证次数，防止短信费用攻击。

日志记录结果和风险信号，不记录提交密码。

## WebSocket 消息权限

连接认证后，每种消息仍要校验 Schema、大小、频率和权限。客户端不能指定任意发送者。订阅主题使用服务端计算的允许列表。离开组织后立即停止对应订阅。广播消息前完成持久化，再返回服务器分配的消息 ID。客户端临时 ID 用于匹配发送状态。

大文件不通过 WebSocket 直接传，使用对象存储上传并在消息中引用受控对象。

管理后台使用 Cookie 登录，删除用户接口接受 POST，却没有 SameSite、CSRF Token 或来源检查。管理员打开恶意网页后，浏览器向后台自动带 Cookie 发请求。攻击者看不到响应，也可能完成操作。

修复包括严格 Cookie 属性、CSRF 防护、检查 Origin、敏感操作再次确认与审计。GET 不执行删除。同时检查已发生的管理操作，撤销陌生会话。只修前端按钮不能处理攻击请求。

## 一个越权现场

App 请求 `/api/invoices/204`，后端只验证已登录，然后按 ID 返回。用户把 204 改为 205，看到他人发票。修复查询同时限定发票 ID 与当前用户或组织，并为不同角色明确规则。测试遍历相邻与随机 ID，确保不存在性也不泄露。访问日志用于确定影响范围。

这种漏洞常叫对象级授权缺失。难猜 UUID 能降低猜测，不能代替查询约束。

验证码短期有效，限制尝试次数和发送频率。数据库保存安全表示，不记录明文到日志。同一账号重新发送时决定旧码是否失效。多个有效码会让用户困惑，也扩大攻击面。一次性链接绑定用途和账号，使用后失效。不能把注册验证 Token 用于重置密码。

响应统一，避免暴露邮箱是否注册。邮件送达失败给出重新尝试与支持路径。

## Passkey 的位置

Passkey 使用公钥凭据，让用户通过设备解锁登录，能降低钓鱼和密码重复风险。应用保存公钥相关凭据，不保存设备生物信息。注册与登录依赖正确域名和安全上下文。用户可能有多台设备，提供多个凭据与恢复方式。删除最后一个凭据前确认仍可登录。

是否采用取决于目标设备、身份服务和恢复设计，本书不展开协议实现。

邀请链接不能只包含可猜组织 ID。使用随机、短期、单次邀请 Token，并绑定受邀邮箱或明确接收流程。接受邀请时用户登录并确认组织。已撤销、过期和已使用邀请给出清楚结果。邀请者需要相应管理权限，不能邀请比自己权限更高角色。

审计记录邀请、接受、撤销和角色变化。

## 权限缓存

后端可能缓存用户角色提升性能。管理员撤销权限后，缓存未失效会继续允许操作。高风险权限使用短缓存或每次查权威来源。角色变化发布事件让各实例清理。Token 中包含角色时，到期前可能保留旧权限。敏感操作再查询服务端状态。

设计时明确权限变化最长生效时间，并在测试中验证。

用户触发后，服务端撤销所有刷新凭据和会话，当前设备也重新登录。仅清浏览器 Cookie无法影响其他设备。身份服务若使用 Token 版本，可增加账号会话版本，使旧 Token 校验失败。撤销动作进入安全日志并发送通知。攻击者控制邮箱时，通知渠道要有额外考虑。

管理员强制退出需要权限与理由，不提供读取用户 Token 的能力。

## 实时聊天室综合测试

用户甲和乙属于房间一，丙不属于。甲乙能连接、订阅和发送，丙的订阅被服务器拒绝。管理员把乙移出，现有连接立即停止收到新消息。乙重连仍失败。甲断网后发送中的消息保持待处理，重连按客户端 ID 去重。服务器返回最终消息 ID 和顺序。

消息正文验证长度，附件使用对象存储。日志包含连接 ID、用户 ID 和关闭原因，不含完整私聊内容。

检查 Cookie 或 Token 存储、HTTPS、登录限流、找回、MFA、登出、撤销和会话过期。检查账号枚举、开放重定向、第三方回调和 Scope。所有 Redirect URI 使用实际允许列表。

使用四种角色做授权矩阵，直接调用端点与 WebSocket 订阅。隐藏按钮不计安全证据。备份恢复流程不能让客服绕过 MFA 随意接管账号。

## 综合例子　第三方登录账号重复

用户先用邮箱密码注册，后来使用同邮箱的第三方登录。系统直接创建第二个本地用户，订单分散到两个账号。修复不能仅按相同邮箱自动合并，因为第三方邮箱验证状态和账号控制权可能不同。要求用户先登录原账号，再主动绑定新方式。

绑定流程验证当前会话、第三方回调与一次性 State，成功后把身份记录关联到同一用户 ID。已产生的重复账号由受权限支持人员按审计流程处理，涉及订单和文件时先确认归属。任何合并都有回退记录。

以后注册流程检测候选冲突并给出安全提示，不透露某邮箱具体登录方式。

应用能区分认证与授权，Cookie 或 Token 生命周期有创建、轮换、撤销和过期。密码、MFA 与恢复路径经过测试。REST 与 WebSocket 都使用同一资源权限原则，移除成员后现有连接也失效。CORS 没被当成身份控制。

四角色权限矩阵、CSRF、账号枚举、重复登录与退出所有设备均有验收记录。

## 认证方案要用多个账号直接验证

AI 可以把资源操作整理成 REST 草案，生成两账号权限测试表，解释 Cookie 属性与 WebSocket 关闭日志。它不能从前端按钮推断后端已授权。让它引用实际路由、中间件、策略和测试结果。

亲自使用多个账号和直接请求验证权限。检查登出、改密码、禁用账号和 Token 过期后的行为。实时功能要测试断网、重连、移除成员和会话撤销。生产 CORS 要按资源用途配置。公开且不带凭据的资源可以允许任意来源读取，带 Cookie 等凭据的请求必须返回明确来源，不能使用通配符。服务器若按请求来源动态返回允许值，还应发送 `Vary: Origin`，避免缓存把一个来源的结果交给另一个来源。

CORS 管的是浏览器脚本能否读取跨来源响应，不能代替身份认证、资源授权或 CSRF 防护。命令行客户端和另一台服务器不会因此自动被挡住。每个受保护接口仍要验证会话或 Token，再检查当前账号是否有权操作这份资源。使用 Cookie 的写操作还要采用合适的 SameSite、CSRF Token 或来源校验，并根据应用场景测试。秘密继续留在受控后端，不进入浏览器代码。
