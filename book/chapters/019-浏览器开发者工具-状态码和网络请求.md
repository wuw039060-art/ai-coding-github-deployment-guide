# 浏览器开发者工具、状态码和网络请求

用户点击“保存”，页面没有变化。有人说是前端，有人说后端挂了，AI 建议清缓存。此时先别继续猜。打开浏览器开发者工具，找到这次点击在浏览器里留下的第一条错误和第一个失败请求。

DevTools 能观察当前浏览器、当前页面、当前时间收到或发出的信息。它不会因此获得服务器权限，也不会显示打开面板之前已经错过的活动。对大多数网页故障，先学会 Console 与 Network 的分工，已经足以判断下一步该去哪里。

## 代码消息与请求证据

**Console** 主要回答浏览器代码发生了什么。JavaScript 异常、浏览器安全策略、应用主动日志和扩展消息会出现在这里。第一条与本次操作相关的错误通常比后续连锁报错更接近根因。`TypeError: Cannot read properties of null` 说明代码取得了空对象，不等于服务器已经失败；点开来源和调用栈，才能继续判断选择器、加载顺序或条件渲染。

**Network** 主要回答浏览器与其他系统怎样交换请求。每一行是一份边界记录。请求发往哪里、使用什么方法、有没有得到 HTTP 状态、发送了什么最小数据、收到什么响应、由谁发起、时间花在哪里。页面主文档成功而某个 API 失败，与主文档本身 404 是两条不同路径。

两个面板要一起读。按钮代码根本没执行时，Network 可能没有新请求，Console 会有异常；请求已经出现并返回 4xx，先查输入、身份和权限；返回 5xx，再带着 Request ID、时间和路径去查服务端日志。只看红色颜色或一串错误文字，容易把表现当原因。

> **证据边界**
>
> Console 证明浏览器在这个页面上下文中记录了某条消息；Network 证明这个浏览器观察到某次请求及响应。状态码 200 不证明返回了正确业务结果，500 不证明写操作完全没有副作用，没有请求也不证明服务器正常。它们用于决定下一层检查，不替代服务端日志、数据库状态和真实用户验收。

## 捕获一次干净复现

以“保存资料”失败为例。先确认自己有权调试该页面，并使用测试账号和非敏感数据。打开 DevTools 后执行以下最小流程。

1. 打开 Console 与 Network，清空旧记录。
2. 需要观察跳转或登录重定向时启用 Preserve log；普通单页操作不必一直保留历史。
3. 刷新页面，让主文档、脚本和 API 都在面板打开后发生。
4. 只做一次“保存”，记录操作时间及时区。
5. 找 Console 第一条与操作相关的错误，再找 Network 第一个失败或异常请求。
6. 保持页面、账号、网络和输入不变，不要同时清缓存、换浏览器和修改代码。

面板空白可能只是仍有筛选条件，或请求发生在打开之前。扩展程序也可能注入消息；需要对照时，可用无痕窗口或受控的无扩展配置复现，但不要为了排错永久关闭安全扩展。

Console 不是聊天框。陌生网站要求粘贴的代码会在当前登录权限内执行，可能读取页面数据或发起真实操作。不要绕过浏览器的 Self-XSS 提示。自己的只读表达式也要先看懂，输出中的 URL 查询参数和账号信息仍需脱敏。

## 读一个请求只需七个字段

选择目标请求，先记录以下字段。

| 字段 | 要回答的问题 |
|---|---|
| Request URL | 实际发往哪个域名和路径，是否误指 `localhost`、测试域名或旧 API |
| Method | GET、POST、PATCH、DELETE 等是否符合操作 |
| Status | 浏览器有没有得到普通 HTTP 响应，类别是什么 |
| Payload | 表单、JSON、查询或文件元数据是否包含预期最小字段 |
| Response | 服务端返回的是业务错误、Request ID、HTML 登录页还是预期数据 |
| Initiator | HTML、哪段脚本、第三方资源、扩展或 Service Worker 发起 |
| Timing | 时间主要在 DNS、连接、TLS、等待服务器还是下载 |

Headers 里的 `Content-Type` 能解释前端为何解析失败；缓存头能说明是否可能读到旧结果；Payload 为空时先查前端收集，字段正确却返回校验错误时再查 API 规则。请求和响应可能包含 Authorization、Cookie、Token、密码、个人资料和用户文件，不能原样贴进 Issue 或 AI 对话。

一次 Timing 会受缓存、网络和负载影响。等待服务器时间长只是线索，需与后端日志和重复测量对照。请求长期 Pending 也可能是正常流式连接或 WebSocket，先看请求类型，不能直接判定卡死。

## 状态码是路标，不是结论

状态码把排查带到更接近的责任层。

- **404**。先看完整 URL、方法、部署路由与文件大小写。主文档 404 和 API 404 的负责人可能不同。
- **401**。认证凭据缺失、过期或未被接受；检查测试账号和请求上下文。
- **403**。身份可能已确认，但权限、组织策略或防火墙拒绝。
- **429**。查看限流说明与重试策略，不让客户端无限重发。
- **500**。保存响应中的错误代码或 Request ID，转向应用日志。
- **502**。代理没有从上游得到有效响应，检查服务地址、端口和代理日志。
- **503**。服务维护、容量不足或健康检查失败。
- **504**。某一层等待超时，需要比较代理、应用和上游各自的时间。

`(blocked)`、`(canceled)` 或 `ERR_NAME_NOT_RESOLVED` 没有普通 HTTP 状态。它们分别可能来自浏览器策略/扩展、导航或代码取消、DNS 等更早阶段。若浏览器根本没连到应用，服务端访问日志可能没有记录。

CORS 错误要记录前端 Origin、API URL、方法、请求头、预检 OPTIONS 状态和响应头。上游先返回 500，却没在错误响应上附 CORS 头时，浏览器也可能表现为 CORS。扩大为允许任意来源、安装“关闭 CORS”扩展，只改变安全边界或自己的浏览器，不是产品修复。

缓存也会改变观察结果。主文档或资源来自 memory cache、disk cache、Service Worker，说明浏览器可能没有重新取得服务器内容。需要对照时才在 DevTools 打开期间禁用缓存并刷新，记录这个条件；不要把“所有用户清缓存”当发布机制。若无痕窗口显示新版本、普通窗口仍旧，再检查缓存规则和 Service Worker，别继续重复部署同一提交。

## 用成功请求校准失败请求

第一次只看失败请求，很难知道“正常”应该长什么样。更可靠的方法是保留一条成功样本，再只改变一个条件。

在练习站点中，把一张图片的正确路径改错一个字符。刷新后用 Network 找到图片 404，确认 Request URL 与 Initiator；恢复路径并重新部署，同一资源应变为 200，Preview 能显示图片。两次操作只有路径变化，因此能建立清楚因果。

保存功能也可用测试账号做对照。先提交完整的无敏感表单，记录方法、地址、必要 Header、Payload 结构、Response 和 Timing；再缺少一个必填字段。若失败响应为 400 且给出明确字段错误，传输链可能正常，问题位于输入校验。若点击后没有任何请求而 Console 报错，先修前端执行路径。

每次只改变一个条件。若同时换账号、清缓存、切网络和修改代码，即使问题消失，也不知道是哪一步起作用。修复后不仅要看原红色请求消失，还要确认正确版本已经发布，并从用户入口完成同一操作。

### 一次从浏览器走到服务端的判断

假设用户上传头像后看到“保存失败”。Console 没有 JavaScript 异常；Network 中出现 `POST /api/avatar`，状态为 502。Payload 显示文件名、类型和大小都符合测试要求，Response 是代理生成的短错误页，Timing 主要耗在等待服务器。到这里可以排除“按钮根本没发请求”，但不能断言后端完全没有处理文件。

维护者用请求时间、路径和代理生成的 Request ID 查日志。代理日志说明连接上游被拒绝，服务状态显示应用进程刚退出；应用日志里的第一条根因是启动时读取了不存在的存储目录。于是修复对象是服务配置，不是前端表单，也不是把 502 改写为 200。

恢复旧目录配置并重启后，先查服务状态与本机健康请求，再用同一个公开小图片重复上传。Network 这次返回 201，Response 有新的头像 ID；重新读取资料确认头像真的存在，数据库和存储日志没有重复记录。201 只证明这次接口声称创建成功，后续读取才补上业务结果。整个推理每一步都由上一份证据决定，没有靠“常见原因”跳层。

如果最初看到的是 413，下一步会比较代理和应用的上传上限；如果是 401，会先确认测试账号和凭据；如果没有请求而 Console 报错，则停在前端。相同的“保存失败”可以有完全不同的责任位置，所以问题描述必须包含请求事实。

## 证据包要小而可复查

交给维护者或 AI 的材料可以包括这些字段。

```text
页面地址（脱敏）与页面版本
浏览器、设备、时间及时区
最短复现步骤
Console 第一条相关错误
请求方法与地址（脱敏）
Status / Content-Type / Request ID
Payload 与 Response 的最小非敏感字段
Timing 的主要阶段
成功对照
已经尝试及结果
仍未验证
```

截图只保留需要的面板、目标请求和关键列，同时保留时间与面板名。HAR 会包含大量 URL、Headers、Cookie、Payload 和 Response，风险远高于普通截图。确需导出时使用测试账号，导出后再次检查文本内容，通过受控渠道限时分享，并按数据政策删除。

Copy as cURL、Copy as fetch 或 Replay XHR 会重发真实请求。一个返回 500 的写操作可能已经部分写入数据库，重放可能创建重复订单或再次扣额度。生产重放需要授权、幂等设计和事前状态查询；默认只在练习环境和无害 GET 上使用。

## DevTools 的临时状态不能冒充修复

Elements 中改文字和 CSS 通常只改变当前页面内存；Console 给变量赋值也只影响当前运行状态。Local Overrides 甚至可能让本机刷新后继续显示修改，却仍没有更新 GitHub、部署平台或其他用户。排错结束时检查 Overrides、断点、请求阻止和限速是否仍启用。

Application 面板能查看 Cookie、Local Storage、IndexedDB、Cache Storage 和 Service Worker。删除站点数据会退出登录并可能清掉草稿；先在测试账号和可恢复数据上操作。Device Toolbar 与网络限速适合模拟视口和条件，但桌面 Chrome 不能替代真实 iOS Safari、Android WebView 和目标手机。

Lighthouse 分数、瀑布图和单次耗时都是线索。它们不能代替关键流程验收，也不应为了分数删除必要功能和无障碍文字。

时间是浏览器证据与服务器证据的连接点。浏览器常显示本地时间，服务器可能使用 UTC；记录时写明时区，不要为对齐日志随意改生产服务器时钟。并发请求的显示顺序也不一定等于业务顺序，能使用 Request ID、操作 ID 或服务端事件序号时，它们比“下午两点左右”更可靠。

## 现在可以跳过什么，继续查哪里

当前只需掌握 Console/Network 分工、七个请求字段、状态码入口和一次成功/失败对照。复杂断点、WebSocket Frames、Waterfall、Throttling、Request blocking、Application、HAR 与截图步骤可以遇到相应问题再查。

当故障只发生在浏览器页面、点击、资源或 API 交互时，这套方法值得优先使用。若 DNS 根本解析失败、服务器服务已明确停止、数据库维护告警已经给出，DevTools 只用于确认用户侧表现，应直接转向对应系统。反过来，后端日志没有记录而浏览器显示请求被策略阻止，也不应靠反复重启服务器碰运气。

目标是让一次模糊抱怨变成可以交给下一位维护者复现、对照和继续验证的事实，不要求把每个面板都学完。

证据越小、越准确、越接近故障发生处，排错就会更少走回头路。

先抓事实，再谈修复。

这一步会省掉许多猜测。

完整操作、安全提醒和证据模板见[《Web 部署与浏览器排错参考》](../../references/web-deployment.md)。下一次再遇到“按钮没反应”，不要先让 AI 猜修复；先交付一组脱敏、带版本、可以比较的浏览器事实。
