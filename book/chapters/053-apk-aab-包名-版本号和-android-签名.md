# APK、AAB、包名、版本号和 Android 签名

Android 发布失败时，最容易混在一起的词是 APK、AAB、包名、版本号和签名。它们分别回答安装文件是什么、商店收到什么、系统如何识别应用、怎样判断新旧以及谁有权发布更新。先把五者分开，再执行构建。这样遇到“版本已存在”“签名不匹配”或“找不到应用”时，能直接检查对应层。

## APK 是设备安装包

APK 是 Android Package 的常见文件格式。手机最终安装和运行的是针对设备准备的 APK。直接在网站分发时，可以给用户下载签名后的 APK。用户需要允许从该来源安装未知应用，并自行判断来源、更新和安全风险。Android 官方发布概览把网站分发与应用商店分发分开说明。

Google Play 接收 AAB 后，也会为具体设备生成适合的 APK。用户通常不会看到这个生成过程。开发时 Flutter 生成的 Debug APK 使用调试签名，适合连接开发工具。它不能作为正式更新的身份依据。

AAB 全称 Android App Bundle，中文可理解为 Android 应用捆绑包。它包含应用代码和资源，Google Play 根据设备架构、语言和屏幕等条件生成并交付 APK。新应用在 Google Play 发布时通常使用 AAB。Android 官方发布页说明，从 2021 年 8 月起，新应用需要使用 Android App Bundle。

AAB 不能像普通 APK 那样直接点开安装。要验证它，可以上传测试轨道，或使用官方 bundletool 生成设备 APK 集合。Android App Bundle 测试指南把本地 bundletool 与 Play 测试列为两种路径。

一句话结论

> AAB 是提交给分发平台的材料，APK 是设备实际安装的包。

## 包名是应用的稳定身份

Android 中常说的包名，在发布配置中主要指 Application ID，例如 `com.example.pocketlist`。它连接设备上的应用、Google Play 记录、深层链接和部分第三方服务配置。商店首次创建应用时要慎重确定。发布后若改成另一个 Application ID，Android 会把它当成另一个应用，原用户不能通过正常更新继承安装身份。

包名不必与商店展示名称相同。展示名称可以本地化和修改，Application ID 应稳定。不要把 `com.example` 带到正式产品。使用自己控制的反向域名形式，并核对是否与现有应用冲突。即使没有网站，也要选一个长期可维护、不会冒用别人组织的标识。

Flutter 项目的 Android Application ID 位于原生构建配置中，具体文件结构会随 Flutter 模板和 Gradle DSL 变化。以当前 Flutter Android 发布文档与项目实际配置为准，不从旧博客复制固定路径。

版本名称可以是 `1.2.0`，用于商店和应用关于页面。版本代码是递增整数，用来判断更新顺序。Flutter 常在 `pubspec.yaml` 写成下面形式。

```
version: 1.2.0+17
```

`1.2.0` 映射为用户可见版本，`17` 映射为 Android 版本代码。每次向同一轨道上传新包，版本代码必须大于已使用值。已经上传过 `17`，即使删除草稿，也不要假定可以再次使用。版本名称没有强制使用语义化版本，但稳定规则能帮助用户和维护者。修复可以从 `1.2.0` 到 `1.2.1`，新功能可以到 `1.3.0`。真正决定 Play 接受更新顺序的是递增版本代码。

关于页面最好显示两者，例如 `1.2.0 (17)`。收到故障报告时，可以准确对应商店制品与代码提交。

## 签名证明谁有权更新

Android 要求 APK 在安装前经过数字签名。设备更新已有应用时，会检查新旧版本签名是否匹配。版本号更高却使用另一签名，系统也会拒绝覆盖安装。签名不证明代码没有漏洞。它证明构建由持有对应私钥的一方签署，并保持更新链身份连续。

Google Play 的当前常见流程包含应用签名密钥和上传密钥。开发者用上传密钥签署 AAB。Play 验证上传者，再用受管理的应用签名密钥签署交付给用户的 APK。

如果同一应用还要在其他商店分发，并希望安装包保持同一签名，需要在第一次配置 Play App Signing 前研究密钥选择。Android 签名文档提醒，多商店使用同一签名时应提供自己的应用签名密钥。

## Keystore 是私钥容器

Android 上传密钥常保存在 Keystore 文件中。文件、别名和密码共同参与签名配置。Keystore 文件不能提交到公开 Git。密码也不能与文件保存在同一个公开配置。应制作加密备份，至少放在两个受控位置，并记录谁有访问权限。

证书的公开指纹可以用于配置 Google 登录、地图或 Firebase 等服务。指纹可以记录和分享给需要配置的平台，私钥不可以。高风险操作

> 不要在不理解现有签名状态时重新生成“一个新的 release key”。新密钥不能给已发布应用续上原来的更新身份。

开始前确认这是不是全新应用，是否已在任何商店发布，是否需要多个商店使用同一签名，以及账号属于个人还是组织。全新 Google Play 应用可以按 Flutter 和 Android 当前文档生成上传密钥，并配置 Play App Signing。已有应用必须先找到现有签名资料和 Play Console 中的证书信息。

Flutter Android 发布指南给出 `keytool` 的当前示例。命令会创建长期敏感文件。这里不提供一条让读者直接粘贴的固定密码命令，因为路径、有效期、算法要求和密钥管理方式需要依据当前文档与组织制度确定。

执行后至少记录以下信息。

- Keystore 文件的安全位置和加密备份位置
- Key alias 的准确拼写
- 上传证书 SHA-256 指纹
- 创建日期和负责人
- 对应应用包名与 Play Console 账号
- 恢复或轮换流程的官方链接

密码管理器保存密码，备份系统保存加密文件。不要在聊天记录里发送两者。

## 配置签名时使用秘密引用

Gradle 构建需要知道 Keystore 路径、别名和密码。常见做法是通过未提交的本地属性或受控 CI Secret 提供。`.gitignore` 要覆盖真实密钥文件和本地秘密配置，但忽略规则不是唯一保护。提交前检查 Git 差异和历史。若密钥已经进入 Git，再加忽略规则不会从历史中删除。

配置完成后，执行一次 Release AAB 构建。

```
flutter build appbundle
```

运行位置

> Windows PowerShell 或 macOS Terminal，在 Flutter 项目根目录运行。需要 Android SDK、兼容 JDK、可解析的 Gradle 依赖和有效签名配置。

Flutter 当前文档给出的默认产物位置如下。

```
build/app/outputs/bundle/release/app.aab
```

成功时终端显示构建完成，文件存在且修改时间对应本次构建。若报找不到 Keystore，检查路径是相对哪个配置文件解析。若报密码或 alias 不正确，不要反复修改密钥文件，先用安全记录核对配置。

## APK 构建用于什么

不通过支持 AAB 的商店分发，或者需要本地安装检查时，可以构建 APK。

```
flutter build apk --split-per-abi
```

`--split-per-abi` 按应用二进制接口生成多个 APK，减少单个设备下载无关架构代码。用户必须拿到匹配设备架构的文件。省略该选项会生成包含多个架构的较大 APK。用 APK 测试能验证很多 Release 行为，但不能完整模拟 Play 从 AAB 生成、签名和交付的过程。最终 Google Play 发布仍应从内部测试轨道安装一次。

最可靠的测试对象是用户将收到的那个签名链和分发路径。上传 AAB 到内部测试，让测试账号通过 Google Play 安装。测试以下两种路径。第一种是干净安装。卸载旧测试包后从测试链接安装，检查首次启动、权限、登录和资源。

第二种是升级安装。保留上一版本和本地数据，通过测试轨道升级，检查数据库迁移、登录状态和缓存。Debug 包与正式包签名不同，可能无法直接覆盖。不要为了方便卸载后只做干净安装，升级问题会被漏掉。

## 构建出来、装得上和能够升级分别检查

`flutter build appbundle` 成功，说明这次构建生成了 AAB 文件。它还没有经过 Play 处理，也没有证明目标手机能够安装。先记录文件路径、大小、版本名称、版本代码、包名和签名指纹，确认这些信息属于准备发布的应用。

安装检查要使用接近最终渠道的包。直接运行 Debug 版本只能验证开发环境。内部测试版本从 Play 安装以后，检查首次启动、权限、登录、网络和关键功能。升级检查则保留一台装有旧正式版或旧测试版的设备，从测试轨道更新到新版本，确认旧数据、登录状态和本地文件仍然可用。

三项检查若有一项失败，先停在相应位置。AAB 没生成就查构建日志，Play 拒绝上传就查版本代码、包名、签名与政策字段，设备安装或升级失败就保存 Play 提示、设备信息和应用日志。不要为了让安装通过临时改包名，包名变化会让系统把它当成另一个应用。

一个登录 App 在 USB Debug 运行时 Google 登录正常，内部测试安装后却报认证失败。后端控制台只登记了 Debug 证书指纹，没有登记 Play 交付签名证书指纹。排查时先确认失败包来自哪里，读取 Play Console 中应用签名证书，核对第三方服务配置。修正后增加版本代码、重新构建并上传测试。

另一种情况是地图显示空白。原因同样可能是 API 限制只允许 Debug 签名。关闭限制会暂时“恢复”，却扩大密钥滥用风险。正确做法是增加正式包名与证书指纹组合。

## 目标 API 是商店政策，不是手机系统版本

`minSdk` 决定应用支持的最低 Android 版本，`targetSdk` 表示应用已针对某个 Android 行为级别适配，`compileSdk` 决定编译时可使用哪些 API。三者职责不同。Google Play 会逐年提高目标 API 要求。截至 2026 年 8 月 5 日，官方页面说明，从 2026 年 8 月 31 日起，手机和平板的新应用和更新需要面向 Android 16，也就是 API 36 或更高。其他设备类型有不同要求。

成本可能发生变化

> 目标 API 与截止日期属于高频变化政策。准备上传时打开官方页面重新核对，不把本章数字当作永久要求。

提升 `targetSdk` 可能改变通知、后台任务、存储和权限行为。不能只把数字改大到构建通过。查看各版本行为变化，在目标设备测试。

## 构建产物的交接包

交给负责上传的人时，不要只发一个叫 `app-release.aab` 的文件。附上包名、版本名称、版本代码、Git 提交、Flutter 版本、构建时间、SHA-256 校验值和上传证书指纹。说明它要进入哪个 Play 应用和哪个测试轨道。测试包、预发布包与生产包使用清楚的发布记录，不靠下载目录猜。

Keystore 与密码不要放在同一个压缩包。若上传者通过 CI 获取签名产物，保留构建日志和制品来源。AI 可以解释 Gradle 签名错误，帮助核对包名和版本字段。你必须亲自确认密钥来源、Play Console 证书和最终 AAB。任何要求你把 Keystore 和密码一起上传的服务，都要先停下来审查。

`AndroidManifest.xml` 声明应用组件、权限、深层链接和部分设备要求。Flutter 插件也可能通过 manifest merge 把自己的声明合入最终应用。不能只检查源文件中的一份 Manifest。构建变体、依赖库和占位变量会共同生成最终清单。使用 Android Studio 或构建工具查看 merged manifest，确认 Release 实际包含哪些权限和组件。

删除一个插件后，检查它加入的权限是否仍被其他配置保留。商店表单要依据最终构建，不依据开发者记忆。组件是否导出、URL Scheme 和网络安全设置也可能影响安全。复制旧教程中的宽泛 `exported` 或明文流量配置，会扩大应用暴露范围。

## 最低、编译和目标 SDK 各自控制什么

`minSdk` 决定最低可安装 Android 版本。提高它会让旧设备无法安装新版本。`compileSdk` 决定构建时可以引用的 Android API。它高于 `minSdk` 很常见，代码在旧系统运行时仍要判断 API 可用性。`targetSdk` 告诉系统应用已经针对哪个行为版本适配，也受 Google Play 提交要求约束。提高后，系统可能启用新的权限、后台或安全行为。

三者一起升级时，先读对应 Android 行为变化。构建成功以后，在最低支持、主流和最新系统各测试一台代表设备。

`INSTALL_FAILED_UPDATE_INCOMPATIBLE` 常表示设备已有同包名应用，但签名不同。确认那是 Debug、其他商店还是正式版。`VERSION_DOWNGRADE` 表示要安装的 versionCode 低于已安装版本。测试降级需要单独数据方案，不能把生产用户当普通覆盖。

设备显示解析包错误，可能是 APK 损坏、架构或系统版本不支持。核对文件校验值、ABI、`minSdk` 和签名。不要用卸载应用作为所有安装错误的第一反应。卸载会删除本地数据，也会掩盖正式升级路径问题。先记录已有包的版本与来源。

## 检查签名证书指纹

Release 构建完成后，使用 Android 官方工具查看签名证书。公开指纹与 Play Console、Firebase、Google Cloud 或其他 API 控制台比较。验证时分别写清上传证书和应用签名证书。上传 AAB 使用前者，Google Play 交付给设备的 APK 使用后者。

第三方登录通常需要设备实际安装包的签名指纹。测试轨道失败时，优先检查 Play App Signing 页面提供的应用签名证书。指纹可以放进发布记录。Keystore 私钥与密码不进入记录正文。

上传密钥丢失时，无法签署新的 AAB。使用 Play App Signing 的应用可以按官方流程申请上传密钥重置。重置需要账号权限和身份验证，不应临近紧急发布才发现没有负责人。上传密钥疑似泄露时，也要尽快重置并审计 Play Console 访问。攻击者只有上传密钥，仍需通过账号权限上传，但两层都应处理。

应用签名密钥承担设备更新身份。由 Play 管理时，升级和灾难流程按当前官方政策处理。自行管理的其他商店签名密钥丢失，可能导致无法更新既有安装。每半年做一次恢复演练。确认备份可读取、密码可找到、证书指纹匹配，并且至少两名授权负责人知道流程。

## CI 签名要限制秘密暴露

持续集成可以在固定环境构建 AAB。Keystore 通过受保护的 Secret 或专门签名服务提供，任务结束后清理临时副本。构建日志不能打印密码、Base64 密钥全文或完整环境变量。Pull Request 来自不受信分支时，不能自动获得生产签名 Secret。

发布任务限制在受保护分支和授权审批。输出 AAB 记录提交、依赖、工具版本、校验值与执行者。CI 成功仍要把 AAB 上传测试轨道安装。自动签名没有验证第三方服务指纹、权限弹窗和升级数据。

一个 AAB 可能包含 ARM 32 位、ARM 64 位与 x86-64 等代码。Play 根据设备生成 APK 组合。在一台开发手机安装成功，不能证明其他 ABI、语言和屏幕密度的拆分都完整。Play Console 的内部测试和 pre-launch report 能提供更多设备信号。

包含按语言分发资源时，切换系统语言后检查文本与图片。按需功能模块要测试未安装、下载中、失败和更新。重要设备仍由人工完成核心流程。自动截图能发现崩溃和布局，不能判断业务结果正确。

## 应用备份与换机恢复

Android 系统可能备份部分应用数据，具体取决于系统、配置、用户账号和设备厂商。不要把它当成唯一业务备份。登录型 App 应从服务器恢复权威数据。本地草稿、离线队列和设备偏好要明确是否随系统备份迁移。

敏感令牌不应在换机后无条件恢复。新设备通常需要重新认证。测试从旧设备备份恢复到新设备，检查数据库 schema、文件路径和账号状态。若产品不支持恢复，在帮助文档中说明可导出内容。

Android App Links 让 HTTPS 地址直接打开经过验证的应用。网站上的关联文件会声明允许的包名和证书指纹。Debug、侧载 Release 和 Google Play 交付包可能有不同指纹。测试环境和生产环境要配置对应值。

验证失败时，链接通常退回浏览器或弹出选择，而不是显示明确签名错误。检查网站文件可访问性、Content-Type、包名和应用签名证书。应用接到链接后仍要检查登录与业务权限。域名关联只证明某 App 可以处理该网站地址。

## 一次完整升级矩阵

发布 2.0 前，至少准备当前生产 1.9 和一个更旧的仍活跃版本。分别创建包含中文、Emoji、附件和未同步任务的数据。从 Play 内部测试把它们升级到 2.0。检查安装没有签名错误，本地迁移完成，登录仍有效，后台任务没有重复，通知入口可用。

再做 2.0 干净安装，确认首次启动和默认数据。最后在最低支持 Android、主流版本和最新版本重复核心冒烟。把组合写成表格。某一格没有设备条件时标为未验证，不能用另一版本结果填充。

- 包名与 Play 应用记录相同
- versionCode 高于所有已上传制品
- versionName 与发布说明一致
- 上传签名配置来自受控密钥
- 目标 API 满足上传日要求
- Merged Manifest 权限与披露一致
- AAB 校验值和 Git 提交已记录
- 从 Play 测试轨道完成干净安装与升级
- 正式签名下登录、地图、推送和深层链接通过
- 符号和混淆映射得到保存

检查单全部完成，才把 AAB 称为发布候选。文件存在只表示构建命令产生了输出。

## Release 包不能保持 debuggable

正式构建应关闭 Android 调试能力。若 Release 仍是 debuggable，攻击者更容易附加调试器，商店检查也可能警告。Flutter 和 Android 默认 Release 配置会处理很多设置，自定义 flavor 或复制 build type 时仍要检查最终 Manifest 和构建变体。

测试人员需要诊断时使用日志、崩溃报告和专门测试构建，不能让生产包永久开启调试。在测试轨道安装后，用平台工具查看应用是否可调试。结果记录到候选构建证据。

Android Release 可以使用 R8 等工具缩减、优化和混淆 Java 或 Kotlin 代码。Flutter 当前 Android 发布文档说明 Release 构建会进行代码缩减。

反射、序列化或某些 SDK 可能需要 keep rule。压缩后只在 Release 崩溃，先检查映射与库的官方配置，不能直接永久关闭所有优化。每个上传版本保存 mapping 文件。没有映射，混淆后的原生堆栈很难还原。

Dart 混淆使用另一套符号信息。两种映射按版本和 build 分开保存。

## Native library 也有位数与页面要求

Flutter 插件可能打入 `.so` 原生库。它们要支持目标 ABI，也要满足 Android 平台和 Google Play 当前技术要求。旧库只有 32 位、缺少 ARM64 或使用过时工具链时，AAB 可能上传失败，或者部分设备无法运行。

App Bundle Explorer 能帮助查看各设备 APK 与原生库。构建日志和插件发布说明用于定位来源。不要从未知网站下载同名 `.so` 替换。升级官方依赖或由有源码的维护者重新构建，才能追溯安全和许可证。

应用查询设备上其他应用、接收外部 Intent 或提供 Service 时，会涉及包可见性和组件导出。只声明核心功能需要的查询与 Intent filter。广泛查看安装列表可能触发隐私和 Play 政策问题。

导出组件必须验证调用者和输入。一个 Activity 能被外部打开，不代表外部可以绕过登录执行内部管理动作。查看 merged manifest，列出所有 exported 组件。第三方插件加入的组件也要审查。

## 侧载 APK 增加了发布者责任

从自己网站提供 APK 时，开发者负责托管、TLS、文件校验、更新通知、旧版本撤回和用户说明。用户允许浏览器安装未知应用会扩大设备风险。指导完成后应建议恢复系统默认限制，不要求长期关闭安全保护。

网站明确展示包名、版本、签名证书指纹和 SHA-256。下载页被劫持或文件损坏时，用户有核对依据。不同商店与侧载包若使用不同签名，不能相互覆盖。发布前决定渠道关系，不在用户设备上试错。

确实需要换包名时，要把它当成新应用迁移。旧 App 无法直接被新包覆盖，登录状态和本地数据也不会自动共享。可以让旧 App 提示迁移、导出数据或使用后端账号恢复。敏感本地数据不能由两个包随意互读。

商店评价、安装量、订阅与购买迁移有各自平台规则，先查官方支持，不作自动继承假设。旧包保持维护多久、何时下架和用户怎样求助，要有公告与数据出口。

## 版本代码建立统一分配机制

多人和 CI 同时打包时，手工把 versionCode 加一容易冲突。建立一个受控来源，例如 CI build number 或发布登记表。测试 build 也会占用已上传代码。不能把生产版本预留成一个很小间隔，然后让每日构建耗尽计划。

versionCode 只需严格递增，不必从数字反推出所有业务含义。版本名称和发布记录承担人类解释。分支合并时先查询 Play Console 已使用的最大值，再生成候选。构建完成后把编号写回发布记录。

接手者从受控仓库检出发布提交，安装记录中的 Flutter 与 JDK，取得最小签名权限。他运行分析和测试，构建 AAB，比较包名、版本和上传证书指纹。校验值与原构建不同也要解释工具或签名差异。

然后上传内部测试，在不连接开发电脑的真机完成干净安装和升级。第三方登录与深层链接通过。只有原作者电脑能生成 AAB，说明项目仍缺工具版本、秘密入口或原生配置。交接失败是工程证据，不是接手者不熟练。

## Android 签名专题的掌握边界

初学者需要能区分上传密钥与应用签名密钥，知道包名保持更新身份，能备份上传 Keystore，并从测试轨道验证正式签名。暂时不用学习证书 ASN.1 结构、密码算法数学或 Android 包管理器源码。遇到多商店、密钥升级和组织 CI 时，再阅读对应官方章节。

任何教程让你关闭签名校验、共享私钥或通过改包工具修改别人的 APK，都不属于正规发布流程。本章结束时，你应能根据错误把问题放到包格式、包名、版本、签名、SDK 或设备兼容中的一层。
