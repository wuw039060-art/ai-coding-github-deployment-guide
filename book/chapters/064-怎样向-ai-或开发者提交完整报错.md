# 怎样向 AI 或开发者提交完整报错

一份完整报错的目标，是让没有坐在你电脑前的人也能理解问题、判断优先级并开始验证。它不要求贴出所有文件，也不要求使用专业术语。最重要的是把现象、环境、步骤、证据、影响和已经尝试的动作组织成一个可执行的问题包。

AI 与开发者需要的核心材料相同，权限边界却不同。项目开发者可以在受控渠道查看内部仓库与诊断文件，公开 Issue 的任何人都可能看到内容，第三方 AI 服务还涉及数据处理范围。提交前先决定接收者、公开程度和允许分享的材料，再进行脱敏与裁剪。

## 第一屏先让人知道发生了什么

标题应包含对象、动作和可观察结果，例如“Windows 11 上 GitHub Desktop Push 后提示认证失败”，比“救命，GitHub 又坏了”更容易搜索和分派。正文开头用三到五句说明谁受影响、从何时开始、哪个版本、核心现象、影响范围和当前是否仍在发生。紧急事故还要说明数据、安全与临时替代。

一个清楚摘要可以这样写。“从 `2026-08-06T14:00:00+08:00` 起，生产站点所有登录请求返回 502，公开首页仍为 200。版本为 `web-2.8.4`，故障在部署 `abc1234` 后两分钟开始。已暂停继续发布并关闭登录写入，没有发现数据删除，旧会话仍可读取内容。”读者无需先翻日志，就能判断范围、时间关系与止损状态。

不要在摘要中提前宣布未经验证的根因。“部署后发生”是事实，“这次部署导致”需要实验支持。可以写“当前假设为上游应用未监听，待用服务状态和代理错误日志确认”。这种表达把观察与推断分开，也给接手者一个明确的下一步。

环境信息至少包括操作系统与版本、硬件或设备、应用或服务版本、构建模式、浏览器、运行时和关键依赖。网页问题还要写目标 URL、浏览器扩展或隐私模式是否相关；服务器问题写部署方式、镜像摘要或提交；Flutter 问题写 Flutter、Dart、Android 或 iOS 版本、设备和 Debug 或 Release。

版本不要写“最新”。今天的最新与接手者明天安装的版本可能不同，平台也会分批更新。优先复制工具实际输出或关于页面中的完整版本，并注明获取时间。路径与用户名可以脱敏，包名、服务名和版本若不敏感则应保留，因为它们决定日志与构建是否属于同一对象。

运行环境存在多个层级时要分别写。例如代码在 Windows 编辑，CI 使用 Ubuntu 构建，最终容器运行在 Debian 基础镜像，用户通过 Android App 访问。只写“Windows 电脑”无法解释大小写路径、Linux 权限和移动网络差异。无法确认的字段可以写“尚未确认”，不要猜一个看似合理的版本。

## 复现步骤要让动作和结果一一对应

步骤从可重复的前置状态开始，例如已登录测试账号、打开某仓库、使用一条脱敏测试记录。每一步只写一个主要动作，并在关键位置说明应看到什么。若必须使用命令，注明运行位置、权限、前置条件、预期输出与失败检查。开发者照做后应能判断自己是否已经到达同一状态。

```
标题：

最后正常时间：
应用或服务版本：

构建或运行模式：

前置条件：
1.

复现步骤：
1.
2.
3.

预期结果：
实际结果：
发生频率：

请求编号或崩溃编号：
最近相关改动：
已经尝试及结果：
附件清单：
脱敏说明：
```

步骤不能省略看似普通的动作。拖入文件、刷新页面、从旧版本升级、拒绝权限、切换网络和第二次点击，往往正是触发条件。也不要把自己的解释塞进步骤，例如“点击坏掉的保存按钮”，应写“点击保存，按钮转圈约十秒，随后显示 504”。动作与观察分开后，别人更容易发现差异。

若只能偶尔复现，应写尝试次数与失败次数，并保留成功和失败的比较。“十次中三次失败，均发生在恢复网络后的第一次同步”比“偶尔不行”更有价值。无法复现时，给出原始时间、受影响用户范围和监控证据，说明还缺哪些信息。

## 预期与实际都要有可观察结果

预期不能只写“正常工作”。更具体的写法是“提交后五秒内返回 201，页面出现新笔记且刷新后仍存在”。实际结果则写状态码、界面文字、耗时、数据是否变化和能否继续操作。这样开发者能判断错误发生在界面、网络、服务还是数据持久化。

预期来源也要合理。它可以来自产品说明、上一稳定版本、自动测试或明确业务规则，不能只是个人偏好。若文档没有承诺某行为，可以写“我原本预期”，并请维护者确认设计。GitHub Issues 用于跟踪想法、反馈、任务与缺陷，项目模板通常会要求预期、实际、步骤和环境。

数据变化必须单独说明。页面报错后记录究竟有没有保存，付款超时后订单究竟有没有生成，上传失败后服务器是否留下半成品。未知结果的写操作不能盲目重试，否则可能创建重复数据。报错中写“结果未知，尚未第二次提交”，能提醒接手者先查请求编号与幂等状态。

复制从第一条有效错误到相关调用栈与结尾摘要，保留原始大小写、代码、路径结构和时间。构建日志末尾的 `BUILD FAILED`、网页上的“发生错误”和服务器返回的 500 都只是结果。真正有行动价值的内容通常在更早位置，例如缺失文件、权限拒绝、上游连接失败或数据库认证错误。

日志要裁剪到故障窗口，又不能剪掉上下文。服务器可提供测试请求前后几十秒、应用版本和请求编号；Docker 日志注明容器与创建时间；Logcat 写设备、应用与缓冲区；Xcode 崩溃报告匹配构建与符号；商店错误保留 build number、处理状态和通知原文。相关官方资料分别规定了这些工具的字段与边界。

截图适合界面布局、控制台状态和无法复制的提示，文本适合搜索、引用和差异比较。最好同时提供一张包含上下文的截图和可复制错误。截图不要只留红框，也不要把浏览器地址、版本、时间和当前选择裁掉。视频只在交互顺序难以文字表达时补充，仍要写复现步骤，不能让接收者在十分钟录像中寻找一次闪烁。

## 最近改动要附差异，不要附猜测

写明最后正常版本、首次异常版本和两者之间的已知变化。代码改动附小范围 Diff 或提交链接，配置只列键名与是否变化，依赖附锁文件差异，数据库写迁移编号，平台写控制台设置变化与时间。秘密值一律不复制。

如果你认为某项改动相关，说明理由和能验证它的实验。例如“错误只出现在使用新 API 地址的 Preview 部署；旧地址同一请求为 200；建议核对环境变量来源”。这种材料比“肯定是环境变量”更容易检验。Git bisect 只在有稳定好坏测试时使用，结果应附首次坏提交与测试方法。

没有主动改代码也要写清。证书到期、密钥轮换、DNS、商店策略、外部 API、数据量和系统升级都可能改变结果。将“最近没有部署”误写成“最近没有变化”，会遗漏系统外部条件。

列出动作、时间、目的和结果，不要只写“试过很多办法”。例如“重新启动应用进程后五分钟恢复，随后再次 502；磁盘使用率 42%；旧镜像部署后问题仍在”。没有变化的实验同样有价值，它排除了部分假设。

不要为了让列表显得丰富，执行来源不明的清缓存、重装、关闭防火墙或提高所有权限。若某动作已经做过且可能改变现场，应如实记录，例如“曾执行 `flutter clean`，原始构建日志已保存，清理后错误相同”。隐瞒现场变化会让接手者用错误基线判断。

重启、回滚与数据恢复属于有影响动作。报告中应写审批、备份、执行版本、开始结束时间、验证和回退结果。重大事故使用公共时间线，避免多人重复修改。Google SRE 的事故管理材料强调角色、状态与交接。

## 最小复现和附件要能独立使用

如果问题依赖代码，优先准备最小复现仓库或补丁。README 写准确启动命令、已测试环境、预期、实际和复现频率。删除无关功能与资产，使用模拟服务和测试数据，确认新克隆后仍能复现。Flutter 官方 Bug report 资料也强调最小示例与环境。

附件使用稳定名称，例如 `build-log-web-2.8.4.txt`、`logcat-app-241-android15.txt` 和 `network-login-20260806.har`。HAR、崩溃报告、数据库日志和配置文件可能包含令牌与个人数据，不能因为扩展名普通就直接公开。压缩包内也要逐个检查，不能只给压缩包改名。给出附件清单和用途。接收者应知道哪个文件是原始日志，哪个是脱敏副本，哪个是最小复现。若文件过大，只提供故障窗口和获取完整文件的受控方式，不要把数百兆日志直接贴进聊天。附件到期后按项目保留规则删除，尤其是包含用户数据的诊断材料。

必须删除或替换的常见信息包括密码、API Key、访问令牌、Cookie、私钥、SSH 私钥、数据库连接串、真实邮箱、电话、订单、设备标识和用户正文。公开仓库还要检查 Git 历史、Issue 附件和构建日志，因为从最新文件删除不代表旧版本消失。秘密一旦公开，应先轮换或撤销，再处理历史。

替换时使用稳定占位符，例如同一个用户在整份日志中都替换为 `[USER_A]`，同一请求编号若不敏感则保留。随意把每个值都改成 `xxx` 会破坏事件关联。时间、错误类别、状态码、版本和调用关系通常应保留，除非它们本身能识别个人或暴露敏感内部结构。

OWASP 的秘密与日志资料要求控制秘密生命周期、日志内容与访问。GitHub Actions 的秘密机制也提醒维护者使用受控变量，不把值写入仓库和普通输出。向 AI 提交前再做一轮独立检查，因为聊天内容可能超出项目仓库原有的访问范围。

## 为诊断包建立清单和校验

复杂问题可能包含截图、HAR、调用栈、服务器日志、配置 Diff 与最小复现。把它们放入一个诊断目录时，增加 `README` 或清单，说明文件名、来源、时间、用途、是否脱敏和敏感等级。接收者先看清单，就能知道哪些文件可以公开、哪些只能在受控渠道使用。

原始材料与脱敏副本分开保存，文件名明确标记。对传输后的文件计算校验值，可以确认接收者看到的内容与发送时相同，但校验值不能证明材料安全，也不能代替加密。含用户数据的原始包应使用项目批准的加密与访问方式，设置下载到期和删除日期。

诊断包只保留故障窗口。整台服务器的环境、全部数据库日志和个人主目录通常远超所需范围，也会增加泄露风险。若后续确实需要更多证据，接收者应说明要验证哪个假设、需要什么时间和字段，再由数据负责人提供最小增量。

公开 Issue 适合可复现的产品缺陷、脱敏错误、环境和最小项目。安全漏洞、未修复的鉴权绕过、真实用户数据、生产内部地址与有效秘密不应先公开，应按项目安全政策或私有渠道报告。找不到安全入口时，可以先联系维护者询问受控方式，不在正文中披露可直接利用细节。

内部事故报告可以包含更多架构和时间线，访问仍按最小权限控制。开发、客服、供应商和管理者需要的视角不同，外部状态更新说明影响与恢复，技术附件保留详细证据。不要为了省事把同一个含秘密的大包同时发送到群聊、工单、邮件和 AI。

供应商支持要求诊断文件时，先核对官方支持域名、工单权限、数据处理和保存期限。令牌、私钥和完整数据库通常不属于合理的第一轮材料。无法确认身份或用途时停止发送，由账号负责人从官方控制台重新进入支持渠道。

## 接收追问后怎样更新报告

维护者询问新信息时，不要覆盖原始描述。按时间追加“补充证据”，写获取方式与结果；原假设被推翻时标记已排除，保留为什么排除。这样后来的读者能重建判断过程，也不会把修复后的日志误当成最初现场。

对方无法复现时，先比较环境、版本、数据和步骤，不重复发送相同截图。若发现说明遗漏了升级安装或权限拒绝，修订步骤并再次由另一台设备验证。报告版本可以使用日期或编号，附件也保持对应，防止聊天中出现三个同名 `log.txt`。

问题修复后补充修复版本、Diff 或发行链接、原步骤结果、相邻测试和观察窗口。若仍有未验证平台，例如没有真实 Mac 完成 iOS 复测，应明确写在结论里，不能用 Android 成功推断 iOS 也完成。

报告末尾给出一个明确请求，例如“请确认这是否为已知缺陷”“请帮助判断 502 首次出现在哪一层”或“请审查最小复现中的事务边界”。一次只提出当前最关键的问题，避免同时要求诊断、重构、发布和长期架构设计。接收者可以据此选择需要的权限与证据。

若任务允许修改，要写可接受范围和禁止项。例如可以在测试分支改代码并运行测试，不得访问生产数据、轮换密钥或发布商店。AI 与外部开发者都不应从“帮我看看报错”推断出删除、部署或账号变更授权。

交接时还要说明完成标准。它可以是最小复现不再失败、测试新增并通过、生产错误率回到基线或提供一份原因报告。没有完成标准，接收者可能只解释错误文字，提交者却期待完整修复，双方都会误判进度。

## 针对 AI 的提问要限定任务和证据

不要只发送错误后问“怎么修”。先说明希望 AI 做什么，例如“先判断失败阶段，列出三个以内可证伪假设，不执行修改”。提供摘要、环境、步骤、预期、实际、完整错误、最近 Diff 和已尝试动作，再要求它引用具体证据，标明哪些信息缺失。

下面模板适合第一次分析。命令执行、文件编辑和外部发布应在后续获得明确授权后进行。

```
任务：先诊断，不修改文件，不执行外部操作。

请输出：
1. 已确认事实。
2. 最多三个假设及各自依据。
3. 每个假设的最低风险验证方法。
4. 预期看到的结果和会推翻假设的结果。
5. 仍缺少的信息。

环境：
复现步骤：
预期结果：
实际结果：
错误全文：
最近改动：
已尝试动作及结果：
```

AI 回答后，先检查它引用的文件、版本和错误是否真实存在。若它建议删除数据、开放端口、关闭安全机制、重写 Git 历史或上传凭据，应停止并重新评估。让 AI 把命令分成只读检查和状态修改两类，每条说明运行位置、权限、预期、风险与回退。

## 针对开发者要尊重项目规则

提交公开 Issue 前先搜索现有问题、发行说明和项目贡献指南。找到相同错误时，补充新的环境与复现条件，比重复创建标题相同的问题更有用。不要在无关 Issue 下催促，也不要同时在多个渠道复制包含个人数据的材料。

维护者要求最小复现或版本信息时，应回答具体缺口。若无法公开商业代码，可以提供脱敏调用栈、最小替代项目和受控复现会话，并明确限制。无法提供任何复现证据时，也应诚实说明，只提交时间、频率、环境和诊断编号，避免把猜测写成项目缺陷。

修复发布后，使用原步骤和相邻场景复测，并在 Issue 中回报实际版本与结果。若问题消失但无法证明是某个修改导致，可以写“在版本 2.8.5 中连续验证 50 次未复现，原版本频率约为十次三次，继续观察”，不要把有限观察扩大成绝对结论。

一条信息只有“登录坏了，重启也没用”，接收者不知道平台、版本、范围和错误。整理后可以写成以下事实。Windows 11 的 Chrome 生产网页从 14 时 05 分起，三个测试账号均在提交登录后收到 502，首页正常；应用版本 `web-2.8.4`，部署提交 `abc1234`；Network 显示 `POST /api/login` 等待十秒后 502，请求编号为脱敏后的 `[REQ_A]`；NGINX 有同编号，应用日志没有；回滚旧镜像后仍失败。

这份材料提示问题位于代理与应用入口附近，且单纯代码回滚没有恢复。下一步可检查应用是否监听、上游地址和共享配置。它仍没有宣布根因，也没有附数据库密码。开发者收到后可以从明确边界继续，而无需先追问十个基础问题。

如果随后发现服务因环境文件权限退出，应补充 `systemctl status`、对应 Journal 区间、权限配置的脱敏 Diff、修正动作和验证。报告会随证据更新，原始观察保留，错误假设明确标记为已排除。这样的记录也能直接成为事后复盘的时间线基础。

## 本章最终检查

- 标题包含对象、动作和可观察结果
- 摘要写影响、时间、版本、范围和止损状态
- 环境精确到操作系统、设备、模式与关键工具版本
- 复现步骤从明确前置状态开始并写可见结果
- 预期与实际使用状态码、耗时、界面或数据变化表达
- 错误全文保留第一条有效错误和必要上下文
- 最近改动与已尝试动作都附结果
- 附件名称、用途、测试环境和获取方式清楚
- 发送前检查秘密、个人数据、内部地址和历史附件
- 事实、假设、待验证项与已排除项分开
- AI 请求限定权限，开发者 Issue 遵守项目规则
- 修复后使用原步骤、相邻功能和足够观察窗口复测

完整报错是一份可以继续工作的交接材料。它让接收者看见同一环境、同一动作和同一证据，也保护秘密与用户数据。信息越接近可验证事实，AI 与开发者越能把时间用在真正的定位和修复上。
