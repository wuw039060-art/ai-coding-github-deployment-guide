# SLI、SLO、SLA 与 Error Budget

课程网站首页能打开，视频却一直转圈。服务器监控显示 CPU 只有百分之二十，数据库也没有宕机。维护者如果只问“网站在线吗”，答案可能是在线；学生如果问“我能按时上课吗”，答案显然不同。

可靠性需要围绕用户想完成的事情来衡量。SLI 负责测量，SLO 规定目标，SLA 对外约定服务责任，Error Budget 把允许范围内的坏结果换算成可用于决策的预算。四个名词经常一起出现，所处位置并不相同。

个人项目也能使用这套方法，不需要先建立 SRE 团队。它最实用的价值，是把“稳定一点”“尽量别挂”改成可以测量、可以复查、会影响工程安排的目标。

图中先从用户行为选出可测量的良好结果，形成 SLI。项目为一段时间设定 SLO，并由目标减去实际坏结果得到剩余误差预算。SLA 位于对外承诺一侧，可能引用相关指标，也会包含责任、排除条件与补偿。内部 SLO 应当比对外承诺留有安全余量。

## SLI 先回答用户有没有得到好结果

SLI 是 Service Level Indicator 的缩写，中文常译为服务水平指标。它测量某项对用户有意义的服务结果。Google SRE 建议把许多 SLI 表达成良好事件除以全部有效事件。

课程视频开始播放可以这样定义。

```
良好事件
用户点击播放后两秒内开始连续播放

有效事件
用户对可观看课程发起的播放请求

SLI
良好事件数 ÷ 有效事件数
```

这个定义比“视频接口返回 200”更接近用户。接口可能成功返回播放地址，CDN 拉取首段失败，播放器仍然无法开始。测量放在 API 日志里很便宜，却会漏掉服务器以前和服务器以后的故障。测量放在客户端更接近体验，也要处理离线日志、拦截器、隐私与版本差异。

一个服务通常有多项重要结果。可用性关心能否完成，延迟关心多快完成，正确性关心结果是否正确，新鲜度关心数据是否按时更新，持久性关心已经确认保存的数据是否仍在。把这些全部压成一个“在线率”，会隐藏彼此不同的失败。

SLI 的分母尤其重要。机器人探测、内部压测、未授权请求、用户取消和无效参数是否计入，需要预先定义。把所有 `4xx` 都计为服务失败，攻击流量会耗尽预算；把所有 `4xx` 都排除，服务端错误地拒绝合法用户又可能被掩盖。分类要根据用户结果与服务责任决定。

Google Cloud 的服务监控文档区分请求型 SLI 和窗口型 SLI。请求型指标统计良好请求占比，窗口型指标统计满足条件的时间窗口占比。两种方法会给出不同答案，不能只看最终百分比。

## SLO 给测量结果设定目标和期限

SLO 是 Service Level Objective 的缩写，中文常译为服务水平目标。完整目标包含 SLI 定义、目标比例和计算周期。

```
在连续 28 天窗口内
至少 99.5% 的有效播放操作
应在点击后两秒内开始播放
```

百分之九十九点五并非越高越好。更高目标需要更强基础设施、更多冗余、更慢发布或更严格值班，仍可能测不到用户关心的错误。目标应来自用户能接受的体验、业务后果、当前数据和团队能力。

百分之百通常不是合适的默认目标。任何一次依赖故障、发布错误或测量噪声都会让目标永久失败，团队也没有办法利用数据区分普通改进与紧急工作。业务后果极高的步骤，应通过事务、人工复核和多重保护降低单次错误后果，不能只在仪表盘写一个百分之百。

## “几个九”要先说明怎样计数

时间型可用性按分钟统计时，百分之九十九点九在三十天内大约允许四十三点二分钟不符合标准。这个换算只能解释时间型口径。请求型 SLO 按事件统计，流量高峰的一分钟可能包含几万次请求，深夜的一分钟可能只有几次，两段时间消耗的预算差别很大。

允许时间也不等于一次连续停机的许可。四十三分钟可以来自一次长事故，也可以来自许多短故障。后者可能让用户每次打开页面都遇到偶发错误，排查难度也更高。报告要同时保留事故次数、最长持续时间和影响用户范围。

统计规则还要说明计划维护是否计入、测量数据中断怎样处理，以及服务在用户所在地区不可达时由谁记录。把维护时段从分母删除会让数字更好看，也会偏离用户实际感受。对外协议若有排除条款，内部 SLO 仍可以把这些时间计入，用来指导体验改进。

计算周期也会改变行为。日目标对短时故障敏感，年度目标可能让近期恶化被过去好成绩稀释。滚动二十八天窗口能持续反映最近状态，日历月便于财务和合同结算。项目要说明使用哪一种，不能在报告时临时挑更好看的窗口。

新项目没有历史数据，可以先设暂定 SLO。运行几周后检查用户投诉、延迟分布、故障类型与测量缺口，再调整定义。目标每次修改都要记录原因和生效日期，不能为了掩盖一次事故向下调整。

## Error Budget 把坏结果换成有限额度

Error Budget 常译为误差预算或错误预算。本书使用“误差预算”，强调它覆盖超时、错误和不符合良好标准的结果。它等于目标允许的坏事件比例。

```
SLO            99.5%
允许坏事件比例  0.5%
28 天有效操作   10,000 次
误差预算        50 次坏事件
```

如果一次发布造成二十次播放失败，它消耗了这段窗口内百分之四十的预算。这个数字能把事故影响与其他故障放到同一尺度。它不会证明二十位用户的损失完全相同，也不能替客服处理具体用户问题。

预算不是鼓励团队主动制造五十次失败。它承认现实系统无法无限接近百分之百，也为发布速度与可靠性投入建立讨论依据。预算充足时，团队可以按计划发布和试验；消耗过快时，应减少高风险变更，优先修复反复发生的故障。

误差预算必须配套政策。Google SRE 的示例政策会预先约定预算耗尽以后暂停哪些发布、优先处理哪些可靠性工作，以及分歧怎样升级。示例里的比例与组织角色不适合直接复制，个人项目可以写得很短。

```
预算剩余超过 50%
按正常节奏发布

预算剩余 20% 到 50%
只做小范围发布并加强观察

预算低于 20%
暂停非必要高风险变更
先处理主要失败来源

预算耗尽
只发布安全修复和明确的恢复改动
完成复盘后再恢复普通发布
```

这组阈值只是示例。项目应按发布频率、用户规模和故障后果调整。政策的价值来自提前同意行动，事故发生后才争论是否停止发布，数据很难改变各方原有立场。

## 烧蚀速度比剩余百分比更早发出信号

预算剩余百分之八十看起来安全。如果它在一个小时内从百分之百降到百分之八十，当前故障按同样速度继续，很快就会耗尽。Burn Rate 常译为预算消耗速率，它比较当前坏事件速度与整个周期允许的平均速度。

消耗速率为一，表示按刚好会在周期末用完预算的速度运行。消耗速率为十，表示坏结果出现得快十倍。告警可以同时看短窗口与长窗口。短窗口发现突然事故，长窗口避免一次小波动造成频繁报警。

低流量服务要谨慎。一天只有十次请求，一次失败就让当天成功率变成百分之九十。单个百分比会剧烈跳动，可以延长窗口、结合人工探测、合并具有相同用户承诺的事件，或同时使用最小事件数条件。不能因为样本少就假装没有可靠性问题。

长任务也不适合只按请求计数。每日备份可以用“在规定时间前完成且恢复验证通过的天数”作为窗口型 SLI。消息处理可以用“在十分钟内完成的任务比例”或“最老待处理消息不超过十五分钟的时间比例”。指标形式要跟用户等待方式一致。

## SLA 是面向客户的服务约定

SLA 是 Service Level Agreement 的缩写，中文常译为服务水平协议。它位于提供方与客户之间，会说明服务水平、双方责任、统计方式、排除条件、申诉或信用补偿。它可能使用与 SLO 类似的可用性数字，法律与商业作用不同。

内部 SLO 可以随学习结果迭代，SLA 变更会涉及合同和客户承诺。云服务的 SLA 还可能按产品、地区、套餐和架构分别适用。多可用区部署与单实例部署的承诺可能不同，维护窗口、不可控事件和客户错误可能被排除。采用前必须查看当前官方条款，不能只记宣传页上的一个百分比。

赔偿也不等于损失全额。许多云 SLA 使用服务信用额度，并要求客户在规定期限内提交申请。具体条件会变化，本书不写成永久结论。读者购买服务时，应保存当时适用的条款、架构条件和账单证据。

项目自己的 SLO 通常应比依赖 SLA 留出余量。产品承诺百分之九十九点九，唯一数据库依赖也只承诺同样数字，应用、网络和发布已经没有任何故障空间。多个依赖的可用性也不能简单取最高值，串行依赖会共同影响成功率。

供应商违反 SLA，不会让你的用户自动恢复。项目仍需降级、切换、恢复与沟通。SLA 解决责任与补偿的一部分，SLO 继续指导系统怎样保护用户。

## 指标选错会得到漂亮但无用的结果

最常见的错误是只测容易取得的数据。服务器每分钟探测首页一次，全年全绿，却没有执行登录、播放和付款。这个 SLI 只能证明探测位置能够访问首页，不能证明核心用户流程正常。

平均延迟也会隐藏少数极慢请求。一百个请求中，九十九个用一百毫秒，一个用二十秒，平均值仍可能显得尚可。用“低于目标阈值的请求比例”或延迟分位数，更容易看见尾部体验。阈值要对应用户能感受到的等待差异。

只在应用服务器计数还会漏掉没有到达服务器的请求。DNS、CDN、负载均衡与客户端网络故障不会进入应用日志。测量越靠近用户，覆盖越完整，噪声与采集成本也越高。项目可以同时保留边缘 SLI 与应用 SLI，用于区分用户结果和内部归因。

成功状态码也可能说谎。API 返回 200，响应里却是空课程列表；备份任务退出码为零，产物无法解压；部署平台显示成功，登录回调配置仍错误。SLI 要测到用户需要的结果，必要时使用合成操作或数据正确性检查。

不要把所有图表都变成 SLO。CPU、内存、磁盘、队列长度和数据库连接很重要，它们更适合用于诊断与容量告警。SLO 应保持少而稳定，围绕少数重要用户行为。内部指标帮助解释预算为什么消耗。

## 从一个小项目开始建立目标

第一步列出三项最重要的用户行为，例如登录、播放课程和保存学习进度。每项只写用户认为成功的条件，不先看当前监控系统有什么数据。

第二步选择一个最重要行为，定义良好事件、有效事件、测量位置、统计窗口和已知遗漏。不要第一天就建立二十个 SLO。

第三步用现有数据跑一段观察期。检查客户端、边缘和服务器计数是否接近，随机抽取失败样本，确认分类与真实体验一致。数据缺失要单独显示，不能默认当作成功。

第四步设定暂定目标，并写出依据。它可以来自历史表现、用户容忍度、业务时限和改进成本。目标高于当前能力时，要同时给出达到目标的计划，不能让团队长期处于预算耗尽状态。

第五步写一页误差预算政策。规定预算充足、快速消耗、接近耗尽和已经耗尽时分别采取什么行动。个人项目可以把“团队暂停发布”改成“本周不合并非必要大改动”。

第六步按月复查。查看哪些事故消耗最多预算，哪些用户投诉没有反映在 SLI，哪些指标产生误报。修改目标或实现时保留旧定义与日期，历史报告才有解释基础。

## 用受控样本检查 SLI 是否诚实

先完成一轮正常登录与播放，确认客户端事件、边缘请求和服务器日志都能关联到同一测试操作。这个结果证明测量路径能看到一次良好事件。

随后让播放器地址返回错误，检查它是否计入坏事件。再让请求在到达应用前被测试代理阻断，确认用户侧测量能够看到，而只读服务器日志的指标会漏掉。两项结果能明确不同测量位置的覆盖范围。

把 API 响应延迟到阈值之外，但仍返回成功。延迟 SLI 应计为坏事件，可用性 SLI可能仍计为良好。这个测试证明两项指标没有被状态码混成一个。

最后制造少量无效登录、主动取消和测试流量，核对分母排除规则。排除条件要使用稳定字段，不能在故障以后人工删除不喜欢的数据。

测试只验证统计实现与当前定义一致。它不能证明目标比例适合用户，也不能证明未来流量下仍准确。用户反馈、事故与业务变化会继续修正定义。

## 让 AI 交付公式、样本和决策规则

AI 可以根据事件表生成 SLI 查询、仪表盘和预算计算。提交前要求它写清分子、分母、阈值、窗口、时区、去重方法和缺失数据处理。只给一条百分比曲线，没有说明统计口径，不能用于发布决策。

再要求 AI 提供五条真实或脱敏样本，逐条判断是否进入分母、是否算良好，以及理由。维护者很容易从边界样本发现分类错误，例如把用户取消算成系统失败，或把 CDN 超时完全漏掉。

AI 建议百分之九十九点九九时，要让它计算对应坏事件数量、允许中断时间、冗余成本和当前依赖限制。多写两个九会把成本和操作要求显著提高，不能当作专业感装饰。

误差预算政策由维护者最终确认。预算耗尽后暂停哪些变更、是否允许安全修复、谁能解除限制，都涉及项目风险偏好。AI 可以整理证据，不能替负责人向用户作出服务承诺。
