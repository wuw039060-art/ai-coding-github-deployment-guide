# SQL、NoSQL、PostgreSQL 与 SQLite

数据库让应用长期保存、查找和修改结构化数据。选择数据库时，产品名称排在问题之后。先看数据之间的关系、查询方式、并发写入、离线需求和维护条件。SQL 是查询和操作关系数据库的语言。NoSQL 是一组不以传统关系表为核心的数据库类型，文档、键值、图和宽列都可能被归入。它们没有共同的单一优缺点。

## 表、行与列

关系数据库把数据组织成表。用户表的一行代表一个用户，列代表 ID、姓名、邮箱和创建时间。订单表保存订单，订单项表保存每个商品。它们通过用户 ID、订单 ID 和商品 ID 建立关系。表结构规定字段类型、是否必填和约束。数据库可拒绝缺少必要值、重复唯一值和不存在的关联。

结构不是为了限制未来变化。它把当前业务规则变成可检查的边界，变化通过迁移记录。

主键唯一识别一行。显示名称会改变，邮箱也可能更换，专用 ID 更稳定。外键确认引用对象存在。订单项引用订单，数据库可以阻止孤立记录。唯一约束保证某个范围不重复。例如账号邮箱唯一，或同一用户对同一活动只能预约一次。

约束位于所有写入路径之后。即使两个请求同时通过后端检查，数据库仍可阻止重复。

## SQL 的最小范围

PostgreSQL 官方教程从建表、插入行、查询、连接、聚合、更新和删除展开。初学者先掌握这些用途，不必立即学习复杂优化。下面只展示可读示例，不要求读者在生产数据库直接执行。

```
SELECT id, title, status
FROM tasks
WHERE owner_id = 17
ORDER BY created_at DESC;
```

`SELECT` 读取字段，`FROM` 指定表，`WHERE` 限定当前用户，`ORDER BY` 规定顺序。缺少 `WHERE` 的更新或删除可能影响整张表。任何写命令先在测试数据库验证，并使用事务、备份和变更审查。

订单表不必重复保存用户全部资料，只保存 `user_id`。查询时通过 JOIN 取得需要的用户字段。这样用户改名字不需要更新每一张订单。历史订单若依法或业务上必须保留购买时名称，则应单独保存快照字段。规范化减少重复与更新矛盾，过度拆分也会增加查询复杂度。以业务事实是否独立变化为判断。

连接很慢时先看查询、索引和数据量，不要立即把所有数据复制进一个大 JSON。

## 事务保护一组变化

转账包含账户甲扣款和账户乙加款，两步要一起成功或一起失败。事务把它们作为一个单元。预约最后一个名额时，读取容量、创建预约和减少余量要处理并发。数据库锁、隔离和约束共同参与。事务不能包住所有外部世界。数据库提交后发送邮件失败，不能指望事务撤回已经发出的消息。

外部副作用使用任务表、Outbox 或幂等机制协调。初学项目至少记录邮件状态并允许安全重试。

没有索引，数据库可能逐行查找。索引按某些字段组织额外结构，加快对应查询。每个索引占空间，写入时也要更新。给所有列建索引会拖慢写入和维护。从真实慢查询出发，查看过滤、连接和排序字段。组合索引的列顺序会影响用途。

数据很少时全表扫描完全正常。不要根据一条通用清单盲目建索引。

## PostgreSQL 是客户端服务器数据库

PostgreSQL 作为独立数据库服务运行，应用通过网络连接。它支持多用户并发、事务、丰富 SQL、扩展和运维工具。应用服务器持有受限数据库凭据，连接池复用连接。浏览器通常不直接拿管理员密码。

托管 PostgreSQL 由供应商处理部分安装、补丁和备份，自建则由你承担。两种方式都要设计权限、监控和恢复。截至 2026 年 8 月 11 日，PostgreSQL 官方 `current` 文档指向 18，书中命令仍要绑定实际测试的具体小版本。

SQLite 通常作为库嵌入应用，数据库存于单个文件，不需要独立服务器进程。它适合手机本地数据、桌面应用、缓存、测试和许多网站。读者不应只拿访问人数判断。先确认数据库进程是否都在同一台主机，再看写事务会不会频繁重叠、每次事务持续多久，以及业务是否需要独立扩展数据库。SQLite 官方把设备本地存储、应用文件格式、网站数据库和数据分析列为适用场景，同时说明多台服务器直接访问同一数据库、高写入并发和网络文件系统等边界。

“单个文件”带来部署方便，也容易被误解。数据库正在写入时随意复制文件，不一定得到可靠备份。并发、锁和备份方式仍要遵循 SQLite 文档。把 SQLite 文件放在临时云文件系统，新部署会丢失。需要持久磁盘、单实例约束或迁移到网络数据库。

## SQLite 不等于玩具

SQLite 支持事务、索引、约束和完整 SQL 子集，被大量设备和应用使用。项目小并不自动要求换成 PostgreSQL。选择它时要确认写入模式。很多用户同时写一个云端文件、需要多台应用实例或远程直接访问，客户端服务器数据库更合适。

离线优先 App 常在设备使用 SQLite，再通过 API 同步服务端。同步冲突是另一项系统设计，数据库文件本身不会自动解决。备份与升级仍要测试。一个文件易复制，也易成为单点。

文档数据库把相关字段保存在一份文档中，常用类似 JSON 的结构。用户资料可以包含一组地址与偏好。读取一个用户时一次得到所需聚合，开发体验直接。跨许多文档的关系、约束和事务则取决于具体产品。

文档可以有不同字段，也不代表无需结构。应用仍需验证版本、类型和必需值。Firestore 是 Firebase 的文档数据库实例，提供客户端 SDK、实时更新、离线支持与 Security Rules。这些是具体产品能力，不能泛化到所有 NoSQL。

## 数据重复是一项选择

文档模型常为了读取方便复制显示名称、统计和摘要。源数据改变后，要同步所有副本。订单保存购买时商品名称与价格是有意快照。用户主页复制实时粉丝数则要处理更新延迟。为每份重复数据指定权威来源和更新机制。没有这两项，重复会变成矛盾。

关系数据库也会反规范化，NoSQL 也可用引用。区别不是绝对二选一。

数据关系清楚、需要跨实体事务、复杂筛选和报表时，关系数据库是稳妥起点。数据天然按独立文档读取、结构变化频繁、需要产品提供的实时与离线 SDK 时，可以评估文档数据库。团队经验和运维能力很重要。一个熟悉 PostgreSQL 的小团队，可能比使用陌生分布式数据库更可靠。

规模预测要基于真实读写与增长。个人项目不应仅因“以后可能上亿用户”采用复杂方案。

## 一个库存模型

商品表保存 SKU 和名称，仓库表保存地点，库存表用商品 ID 与仓库 ID 组成唯一关系并保存数量。下单时后端在事务中锁定或原子更新库存，条件是余量足够。更新影响零行时返回缺货。订单项保存成交时名称和价格快照，避免商品后来改名影响历史凭证。

这个模型适合关系数据库，因为实体关系、唯一约束和事务明确。把所有库存塞进一份全局文档，会增加并发冲突。

个人笔记 App 每条笔记独立，包含标题、正文、标签和更新时间。设备离线时仍要编辑，联网后同步。本地 SQLite 很适合保存设备副本。云端可用关系或文档数据库，选择取决于同步服务和查询。

两台设备同时改同一笔记，需要冲突策略。最后写入获胜简单但会丢修改，字段合并或版本历史更安全但复杂。数据库类型不能替产品决定冲突。把策略写进同步协议并让用户能恢复历史。

## 数据类型与时间

金额不要用容易产生浮点误差的普通浮点数。使用数据库定点数或以最小货币单位存整数，并记录币种。时间保存明确时区或 UTC，展示时转换到用户时区。只存“下午三点”无法处理跨地区。枚举状态要限制允许值，状态变化由后端规则控制。自由文本会产生 `paid`、`Paid` 和 `已支付` 等混乱。

JSON 字段适合变化结构，不应成为逃避建模的垃圾袋。经常筛选和约束的字段考虑正式列。

管理控制台很方便，也会绕过应用验证。手工修数据前记录原因、范围、查询和恢复方法。先用只读 SELECT 确认目标行数。写入放在事务中，重要操作由第二人复核。大批更新分批执行并监控锁与负载。不要在高峰期运行未经解释的脚本。

修复后把必要规则加入应用或迁移，避免下次继续手改。

## NULL 表示未知或缺失

SQL 中 NULL 不等于空字符串和零。比较 NULL 通常使用 `IS NULL`，普通等号不会得到预期结果。允许为空要有业务含义。用户尚未填写昵称可以为空，订单金额通常不能为空。聚合与排序对 NULL 有具体规则，报表前确认。应用序列化为 JSON 时也要区分字段缺失和 `null`。

迁移新增列先允许空时，后续回填与约束要明确完成条件。

CHECK 可限制数量非负、状态位于允许集合，UNIQUE 防止重复，FOREIGN KEY 维护引用。约束错误返回给后端时，转换成稳定业务错误。例如重复预约提示已预约，不把数据库语句暴露给用户。

约束名称清楚，日志更容易定位。迁移中建立约束前先找出现有违规数据。应用验证提供友好反馈，数据库约束处理并发和所有写入入口。

## 事务隔离的直观理解

两个事务同时读取和写入时，数据库需要决定彼此能看到什么。隔离等级在一致性和并发间取舍。读取后在应用里计算再写入，可能产生丢失更新。使用条件更新、行锁、版本列或更高隔离处理。事务重试可能发生，业务代码要能安全重跑。外部邮件和支付不放在可自动重试事务内部。

具体锁语法和隔离行为按 PostgreSQL 当前文档与项目测试，不用一个数据库经验套另一个。

资料表增加 `version`。客户端读取版本 7，提交修改时要求当前仍为 7，并更新到 8。若另一人已经更新为 8，影响行数为零，后端返回冲突。用户可以刷新并合并。这适合冲突较少且不想长时间锁定的编辑场景。版本号由服务器管理。

最后写入获胜更简单，可能覆盖别人内容。产品要明确选择。

## PostgreSQL 连接不是无限资源

每个连接占内存和服务资源。应用通过连接池复用，后台任务和管理工具也占连接。多实例总池大小不能超过数据库承受范围。无服务器并发尤其要使用平台推荐连接方式。查询结束归还连接，事务异常也要回滚。连接泄漏会在运行一段时间后爆发。

监控活跃、空闲和等待连接，结合慢查询判断，不仅提高上限。

SQLite 允许多个读事务同时存在，同一时刻只有一个写事务。WAL 模式让读取与写入可以并行，却没有把单写者变成多写者。长事务会拖住后续写入。把外部网络请求和用户等待放进写事务，会显著拉长占用时间。先准备数据，再开启短事务写入。备份还要考虑数据库与 WAL 状态，并使用框架或 SQLite 官方支持的方法。

WAL 依赖同一主机上的共享内存，不能把数据库文件放到普通网络文件系统上，供多台云主机共同写入。这个拓扑更适合客户端服务器数据库或经过专门设计的 SQLite 服务。

## 数据库文件权限

SQLite 文件包含全部业务数据，操作系统账号只授予应用所需访问。不要放在公开 Web 目录。文件备份、临时副本和崩溃日志也按敏感数据保护。开发副本使用脱敏或虚构数据。磁盘加密保护设备丢失，应用权限和数据库加密处理运行中访问。两者解决不同问题。

删除文件前确认同步、备份和恢复需求，不把清缓存命令指向数据库目录。

把所有用户订单嵌入一份用户文档，读取资料会下载大量历史，更新也发生在同一文档。文档产品通常有单文档大小、写入频率和索引限制。按具体供应商当前文档设计集合与子集合。一起显示和一起更新的数据适合聚合，独立增长的大列表拆开。权限边界也参与拆分。

过深嵌套让查询和迁移困难。先从页面和业务事务画访问模式。

## NoSQL 查询从访问模式出发

文档数据库常要求为具体筛选和排序建立索引。临时任意报表可能没有 SQL 数据库灵活。列出首页、搜索、后台和导出需要的查询。每项估算返回文档数与读取次数。为了查询复制字段时，记录更新机制。安全规则不能依赖客户端诚实维护复制权限字段。

数据分析可以导出到专用仓库，不让线上查询承担所有报表。

PostgreSQL 可使用标准 SQL 与导出工具，扩展和专有平台服务仍需处理。SQLite 文件可直接随 App 分发，Schema 升级要在每台设备运行，并兼容用户跨多个版本升级。Firestore 导出保留文档数据，迁到 SQL 需要设计表、关系和约束。客户端查询也要重写。

选择时估计未来改变成本，不要求今天就实现第二套数据库。

## 一个评论树例子

评论有作者、文章、正文和可选父评论。关系数据库可用外键连接用户、文章与父评论。读取一层回复容易，任意深树要递归查询或额外路径字段。删除用户时决定匿名化还是删除内容。文档数据库可把少量回复嵌入评论，回复很多时拆成子集合。计数可能单独维护。

两种模型都要处理权限、分页和删除。没有一种能靠“树形数据”三个字自动胜出。

传感器 App 每秒记录读数，先写设备 SQLite。网络恢复后批量上传服务器。本地表按时间索引，设置保留期，上传成功后标记而非立即无审计删除。磁盘接近上限时按明确策略清理最旧已同步数据。

服务器使用 PostgreSQL 或时序服务汇总多设备。设备 SQLite 与云数据库承担不同位置。同步使用设备 ID、记录 ID 和幂等上传，避免断网重试产生重复。

## 数据库命名

表和列使用稳定、明确名称。避免 `data`、`info` 和 `value1`，后来无人知道含义。选择单数或复数、时间后缀和主键约定并保持一致。命名不必追求完美，迁移改名有成本。布尔列用能读出真假含义的名称，例如 `is_archived`。状态复杂时使用枚举或状态表。

数据库备注或 Schema 文档说明业务含义、单位和隐私级别。

软删除增加 `deleted_at`，查询默认排除，便于恢复和审计。数据仍存在并继续受隐私与备份规则约束。所有查询忘记过滤会让已删除内容重现。唯一约束也要决定删除后能否复用名称。后台按保留期硬删除，协调对象存储与搜索索引。高风险业务保留审计但最小化个人内容。

不需要恢复的临时数据可以直接删除。软删除不是所有表的默认答案。

## 审计字段

`created_at`、`updated_at` 和操作者 ID 能说明变化时间。时间由服务端或数据库生成。业务状态历史需要独立事件表，单个 `updated_at` 不能解释改了什么。审计日志限制修改和删除权限，避免普通管理员覆盖痕迹。记录必要字段，避免把完整敏感前后值永久复制。

多个组织共享表时，每行有 `tenant_id`，所有查询与约束都包含租户边界。唯一邮箱可能是全局唯一，也可能组织内唯一，业务先决定。数据库行级安全可加强隔离，应用连接也设置当前租户上下文。用两个组织测试相同资源 ID 和搜索，确认没有跨租户计数与导出泄露。

读副本可分担查询，复制有延迟。用户刚写入后从副本读取，可能暂时看不到。需要读己之写的流程继续访问主库或使用一致性机制。报表可以接受短延迟。副本不是备份，错误删除也会复制过去。独立恢复点仍必需。

故障转移到副本后确认写能力、连接地址和数据位置。

## 数据库与搜索引擎

全文搜索、模糊匹配和复杂排名可能使用专门搜索服务。数据库仍是权威来源。写入数据库后通过任务更新索引。索引延迟时用户可能暂时搜不到，界面可说明。删除隐私数据要同步删除索引。索引可从数据库重建，也要保存配置和映射。

小项目先用 PostgreSQL 内置搜索能力，真实需求超出再增加服务。

线上事务数据库处理用户请求，复杂全表报表会与业务争资源。数据量大时复制到分析系统。导出过程去除或限制个人信息，控制分析账号权限。指标定义版本化。分析延迟不适合决定实时库存。报表写“截至时间”。

个人项目数据少时可以在低峰只读查询，不必立即建数据仓库。

## 数据库选择检查单

列出实体、关系、唯一规则、跨实体事务、主要查询、写入并发、离线和数据增长。列出运行位置、连接方式、备份、恢复、地区、费用和团队经验。用最小模型实现两个最难查询与一个并发写入。在接近真实数据量的测试库测量。

选择结果写理由与重新评估条件，不宣称永久最佳。

每笔交易属于账户与分类，转账同时影响两个账户，月度报表按时间和分类聚合。关系和事务清楚。云端多人版适合 PostgreSQL。本地单人桌面版可以使用 SQLite，同一业务模型运行位置不同。

票据图片放对象存储或受控本地目录，数据库只保存 Key 与元数据。若未来需要多人实时协作，可通过 API 同步。无需一开始改成文档数据库来预留所有可能性。

## 常见错误

重复邮箱出现，检查唯一约束，不只检查前端。删除用户留下孤立订单，检查外键与删除策略。SQLite 在云端偶尔锁住，查看并发写入、事务时长和多实例。不要直接关闭锁保护。文档数据库费用突然增长，检查查询扫描、实时监听和客户端循环。费用模型按供应商当前文档核对。

查询变慢，保存查询计划、数据量和索引。仅加机器可能暂时掩盖低效查询。

AI 可以从业务故事草拟表、字段、关系与约束，生成测试数据和只读查询，也能比较 SQLite 与 PostgreSQL 的条件。让它说明每个约束支持哪条业务规则。任何删除、迁移和生产 SQL 都要人工审查并先在副本验证。

亲自确认数据权威来源、唯一约束、删除策略、备份和并发路径。用两个同时请求测试最后名额或库存。选择数据库前写出部署位置、写入并发、离线需求和恢复责任。不要因流行度替换可工作的简单方案。

下一章会讲数据库迁移、连接、备份和恢复，重点是如何改变结构又保留回退能力。

## 一个错误的 NoSQL 迁移

团队遇到一条复杂 SQL 很慢，决定把全部订单复制到文档数据库。新系统无法方便生成跨月财务报表，库存事务也被拆散。原问题其实是缺少合适索引和查询返回过多字段。优化后 PostgreSQL 查询从数秒降到可接受范围。

文档数据库试验仍保留给通知阅读模型，但不承担订单权威数据。团队根据访问模式使用两种工具，而非全量替换。这个案例提醒，性能问题先测量。数据库类型更换会改变一致性、查询、备份和团队工具，代价远高于一条查询优化。

读者能画出主要表或文档、唯一规则、事务和查询。能说明 PostgreSQL、SQLite 或文档数据库为何适合当前运行位置。并发写入、软删除、备份、权限和迁移成本都有答案。选择记录包含重新评估条件，不把数据库品牌当产品架构。
