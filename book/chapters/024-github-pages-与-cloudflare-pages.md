# GitHub Pages 与 Cloudflare Pages

GitHub Pages 和 Cloudflare Pages 都能把静态文件放到公开网址。前者贴近 GitHub 仓库与 Actions，后者提供独立的构建、预览与边缘发布流程。对初学者而言，先要弄清平台接收什么、何时更新、失败去哪里看。功能表可以用到时再查。

这一章使用一份无后端的练习站。它只有公开内容，不含账号登录、数据库写入和服务端秘密。动态后端不适合硬塞进纯静态发布路线。

图中第一条路线从分支或目录直接发布，第二条由平台从源码构建，第三条由本地先构建再上传。三条路线都能得到公开站点，构建责任和更新方式不同。

## GitHub Pages 承担什么

GitHub Pages 从仓库取得静态内容，构建或部署后提供 `github.io` 地址，也可以连接自定义域名。GitHub 官方列出的用途包括项目展示、博客和简历。它可以从分支发布，也可以通过 GitHub Actions 工作流发布。分支发布适合无须控制构建过程的内容，来源可选某个分支根目录或 `/docs`。需要自定义构建时使用 Actions。

Pages 不运行 PHP、Ruby 或 Python 等服务端程序。浏览器端 JavaScript 可以调用外部 API，但密钥和权限不能因此放进前端。Pages 站点是公开网站。来源仓库是否私有，不决定访问者能否打开站点。需要成员登录才能查看的内部页面，应选择带访问控制的服务。

前置条件是拥有一个 GitHub 仓库的管理或维护权限，仓库中有可公开的 `index.html`，并且发布分支已经存在。先在本地预览并提交改动。Push 后，在 GitHub 打开仓库，进入 Settings，再在侧栏 Code and automation 区域选择 Pages。

在 Build and deployment 的 Source 中选择 Deploy from a branch。选择发布分支，再选根目录或 `/docs`，保存。以上英文标签按 2026 年 8 月 5 日的官方说明核对。界面可能调整，若找不到同名入口，优先搜索当前 GitHub Pages 官方文档，不依靠旧截图猜。

保存后，GitHub 通过 Actions 完成部署。回到 Pages 设置可点击 Visit site。官方说明 Push 后发布可能需要最多约十分钟。成功结果包括 Actions 中部署运行成功，Pages 设置显示公开地址，浏览器能打开首页。若超过合理时间仍未更新，查看仓库 Actions，而非连续修改文件制造更多部署。

## 从分支发布时最容易错的地方

发布来源选了 `/docs`，仓库却没有该目录，构建会失败。官方文档明确把缺少 `/docs` 列为错误情形。入口文件不在发布来源顶层，也会找不到首页。例如来源是 `main/docs`，入口就应在 `docs/index.html`，不能只放在仓库根目录。

项目站的路径带仓库名，资源若假设位于域名根目录，样式和脚本会 404。使用框架时按其 GitHub Pages 部署指南配置基础路径。仓库包含符号链接时，GitHub 要求使用 Actions 发布。不要为了坚持分支模式而复制或改乱项目结构。

当仓库保存的是框架源代码，Pages 可以用 Actions 安装依赖、构建并上传产物。GitHub 在 Pages 设置中提供常见工作流模板。工作流一般在默认分支 Push 或手动触发时运行，检出仓库，按需构建，上传 Pages 产物，再部署。官方说明使用 `actions/upload-pages-artifact` 和 `actions/deploy-pages` 完成后两步。

初学阶段优先使用官方或框架维护者的当前模板。复制旧博客中的工作流时，Action 版本、权限和 Pages 机制可能已经改变。Actions 失败时点击失败运行，展开红色步骤，从底部向上找第一段明确错误。记录工作流名称、提交编号、失败步骤与日志。修复后产生新提交或重新运行，不要把失败状态当作网站故障。

## Cloudflare Pages 承担什么

Cloudflare Pages 可连接 GitHub 或 GitLab 仓库。选定生产分支后，推送到该分支产生生产部署，其他分支可产生预览部署。平台在自己的构建环境中运行命令并发布输出目录。

平台提供 `pages.dev` 地址、部署记录、构建日志和自定义域名配置。对框架项目而言，它把“GitHub 保存源代码”和“平台构建成品”清楚分开。Cloudflare 也支持 Direct Upload，把已经构建好的目录直接上传。这种项目类型与 Git 集成项目不能直接互换，创建时要先决定构建责任。

前置条件是 GitHub 中已有可公开部署的练习仓库，项目构建命令和输出目录已经在本地验证。不要把真实密钥写进仓库。在 Cloudflare 控制台进入 Workers & Pages，创建 Pages 项目并选择连接 Git。授权 GitHub App 时只授予需要的仓库，不要无理由开放所有仓库。Cloudflare 当前官方练习也提供按仓库限制授权的路径。

选择仓库与生产分支。无构建静态站可以使用平台当前文档要求的空命令或适用预设，框架站填写已经验证的 Build command 和 Build output directory。子目录项目还要设置 Root directory。

触发首次部署后，先看构建日志。成功结果是部署状态成功，出现唯一预览或生产网址，打开后与本地预览一致。如果日志显示找不到 `package.json`，检查根目录。构建成功却发布空白，检查输出目录。脚本与图片 404，检查基础路径和产物内容。

## 生产部署与预览部署

生产部署面向正式站点，通常来自指定生产分支。预览部署为其他分支或合并请求提供独立地址。预览地址适合让他人检查修改。它仍是互联网地址，不能放真实用户数据或未授权秘密。若页面尚未公开，也要核对平台的访问控制能力。

一个稳妥流程是创建修改分支，Push 后打开预览地址，完成检查，再合并到生产分支。生产部署成功后，再用正式地址验收。预览成功不保证生产成功。生产环境变量、域名、缓存和分支内容可能不同。保留两次部署编号便于比较。

纯 HTML 项目已经放在 GitHub，想用最短路径公开，GitHub Pages 的分支发布很合适。需要每个分支有预览地址、希望平台管理框架构建，或准备使用 Cloudflare 的其他服务，可以考虑 Cloudflare Pages。

若项目依赖服务端长进程、私有网络或本地磁盘，这两个静态发布入口都不是完整答案。先画清后端需求，再选择动态托管或服务器。选择还要考虑账号权限、地区网络、域名管理、构建限制与费用。所有额度和价格都可能变化，本书不把当前免费层写成永久承诺。

## 一个更新没有出现的案例

维护者把新海报 Push 到 `feature-poster` 分支，Pages 正式站仍显示旧图。他以为缓存坏了，反复刷新；部署记录显示生产来源是 `main`，新提交只生成了预览部署；预览地址已经显示新图；合并到 `main` 后才触发生产部署。这个问题发生在分支与环境对应关系，不在图片文件和浏览器缓存。先核对部署来源，可以避免无关修改。

另一种情况是生产分支已更新，部署却失败。此时正式站继续显示上一个成功版本很正常。打开失败日志，解决本次构建，不能用“网站还能开”判断发布成功。

域名、项目和 DNS 已经连接时，删除项目可能造成访问中断和域名残留。Cloudflare 文档还提醒，删除 Pages 项目前应先移除相应 CNAME 记录，避免域名问题。出错时先保存部署日志、设置截图与当前 DNS 记录。确定新方案后按可恢复顺序切换。单纯为了界面清爽删除旧项目，可能把唯一可用版本一起移除。

默认分支常叫 `main`，但名称没有决定性。发布设置中选择的分支才是生产来源。把日常未完成修改直接放在生产分支，每次 Push 都可能上线。个人项目也可以使用短分支预览，确认后再合并。分支保护能要求评审或检查通过后合并。是否启用取决于项目规模，但生产发布来源应限制给可信维护者。

更改生产分支属于发布流程变更。记录修改前后值，确认新分支已有完整内容，再触发部署。

## GitHub Pages 的两类站点地址

用户或组织站点常使用 `用户名.github.io` 仓库，对应域名根地址。项目站来自普通仓库，地址通常还包含仓库名。两类地址影响基础路径。一个在用户站根路径正常的应用，复制为项目站后可能丢失资源。GitHub 快速入门以用户站为例，仓库名必须匹配账号名加 `.github.io`。普通项目无需为每个仓库创建新的账号。

选择前考虑账号主页是否已有站点。一个账号的用户站入口只有一个，多个项目适合项目站或自定义域名。

GitHub Pages 从分支发布时默认使用 Jekyll 处理内容。纯静态产物若包含以下划线开头的目录，处理过程可能影响文件。GitHub 官方建议，使用其他静态生成器并从分支发布本地成品时，可在发布来源根目录放置空的 `.nojekyll`，关闭 Jekyll 构建。

使用 GitHub Actions 自定义工作流时，按官方模板上传产物。不要在不了解发布方式时随意添加或删除 `.nojekyll`。看到文件在产物中存在而线上缺失，检查 Actions 日志和实际部署产物，再判断是否与 Jekyll 处理有关。

## Actions 权限与环境

Pages 工作流需要读取仓库、上传产物和部署 Pages 的权限。官方模板会声明相应权限，并使用 `github-pages` 环境。复制工作流后不要无理由扩大权限。第三方 Action 也应选择可信维护者与明确版本。

生产环境可以配置部署保护，让只有默认分支或经过批准的运行进入。个人练习可能不需要复杂审批，正式团队应明确规则。Actions 日志是公开还是受限取决于仓库可见性和权限。不要让构建脚本输出秘密。

Cloudflare 通过 GitHub App 访问仓库。授权时可选择所有仓库或仅选定仓库。练习项目应只给目标仓库。后续新增仓库看不到时，先检查 GitHub App 安装范围，不要重复创建项目或改仓库公开性。

组织仓库可能要求管理员批准 App。个人有仓库权限，不代表有权给组织安装第三方应用。撤销 App 权限会使后续部署无法拉取代码，已发布站点是否继续可用取决于平台当前行为。权限变更前准备影响清单。

## 预览分支控制

每个分支都自动部署很方便，也可能消耗构建额度，暴露大量预览地址。Cloudflare Pages 提供分支部署控制，允许限定包含或排除的分支。仓库有自动生成分支、依赖更新分支或敏感演示时，应制定预览规则。规则修改后用一个无害分支验证。

Pull Request 关闭以后，旧预览地址可能仍存在一段时间。不要把访问地址难猜当作清理机制。记录哪些预览应长期保留，哪些应在合并后下线。平台有访问限制功能时，按项目隐私需要启用。

GitHub Pages 从分支发布也会显示 Actions 部署运行。站点没有更新时，从仓库 Actions 查最新 Pages 工作流，再对照 Pages 设置。Cloudflare Pages 在项目 Deployments 中显示每次构建。点击失败项查看阶段、提交与日志。

浏览器 404 只说明请求结果，不说明构建是否成功。平台日志证明发布过程，Network 证明用户实际请求，两份证据要配对。若平台状态页报告事故，保存事件链接和时间。仍要确认自己的故障窗口一致，不能把所有错误都归因于供应商。

## 一个双平台对照实验

把同一份无构建静态站分别发布到 GitHub Pages 和 Cloudflare Pages。只使用平台自带地址，不绑定域名。记录首次设置字段、部署提交、生成时间和地址。修改首页一句话并 Push，观察两个平台的触发时间和日志位置。

再创建一个分支。Cloudflare 若启用预览，应出现分支地址。GitHub Pages 的生产站仍按选定来源更新，除非工作流另有设计。实验用来把“Push 后谁做了什么”画出来，部署速度只作观察记录。完成后保留一个站点即可，清理另一个前先确认没有域名与外部链接。

Pages 可以提供前端文件、重定向和部分边缘函数能力，具体平台能力不同。需要数据库连接与长期后台任务时，要另外设计后端。把管理员密钥放进前端以绕过后端，会让每个访问者获得同等能力。静态站公开本质不会被平台品牌改变。

用户上传也不能仅靠把文件写到站点目录。部署产物通常只读或会在新部署被替换，应使用对象存储和授权 API。下一卷会把这些动态服务放进完整架构。本章只完成文件发布，不提前承诺业务系统已经上线。

## 一张选择表

| 情况 | GitHub Pages | Cloudflare Pages |
| --- | --- | --- |
| 仓库已有现成静态文件 | 分支发布路径短 | 可用 Git 集成或直接上传 |
| 需要自定义云端构建 | 使用 GitHub Actions | 项目设置中直接配置 |
| 每个功能分支要独立预览 | 需自行设计工作流 | Git 集成提供预览部署 |
| 不希望第三方读取仓库 | 仍在 GitHub 内 | 可选择 Direct Upload |
| 需要长期后端进程 | 不适合 | Pages 本身也不提供长期进程 |

表格按 2026 年 8 月 5 日的文档能力整理。平台限制和产品边界会变化，正式选择再看官方页面。

仓库转移到组织、改名或改变可见性，可能影响 Git App 授权、Pages 地址与构建触发。变更前记录当前 URL、发布分支、域名和平台项目。先查两边官方迁移说明。变更后触发一个无害部署，确认平台仍能读取仓库。自定义域名也要检查，不因旧平台地址自动可用就跳过。

外部文档中的旧项目地址设置重定向或更新。不要立即删除旧仓库占位，防止链接失效或名称被占用。

## 用状态徽章要谨慎

README 可以显示构建或部署状态徽章，帮助维护者快速看到失败。徽章只反映对应工作流，不能证明网站业务正常。公开仓库的徽章 URL 与状态信息也是公开的。私有项目不要把含令牌的徽章链接放进网页。

部署故障时点击进入原始运行记录，不能只看红绿颜色。过期徽章可能仍指向旧工作流。

读者能用平台自带地址发布一个无秘密静态站，指出生产来源与最新部署提交。能找到构建日志，解释预览和生产的区别。仓库授权限制在所需范围，发布目录只含公开文件。出现 404 时能区分入口、基础路径和发布分支。

自定义域名尚未开始也没关系。先让平台地址稳定，下一步才有清楚的域名排错基准。

## 综合例子　课程资料站

教师把课程讲义放进公开仓库。第一版只有 Markdown 与图片，GitHub Pages 从 `main` 根目录发布，操作路径很短。后来项目增加搜索和主题构建，仓库保存源码，产物位于 `dist`。继续从分支根目录发布会暴露源码结构，也得不到正确首页。

团队有两种可靠选择。使用 GitHub Actions 按当前模板构建并部署 Pages，或连接 Cloudflare Pages 让平台构建 `dist`。两种方案都先在本地验证命令。他们选择 Cloudflare，限定 GitHub App 只读该仓库，生产分支为 `main`，功能分支生成预览。合并前教师用预览检查链接和中文搜索。

一次新讲义没有上线，部署记录显示提交只在 `draft-week6` 分支。预览已经更新，生产没有错误。合并后才出现正式部署。团队把分支与环境关系写入 README，保留部署 ID。以后“没更新”会先查提交与分支，不再直接清浏览器缓存。

部署平台控制台属于本书允许重点推荐视频的六类动态操作。最终视频卡会演示连接 GitHub、设置构建命令、输出目录和环境变量，并查看部署日志。候选视频必须实际播放，记录准确时间段、作者、发布日期、总时长和当前界面一致性。若视频界面已明显过时，只能作为历史线索，不进入主推荐。

正文不会依赖视频才能完成操作。界面变化后，读者仍能根据输入、输出与日志理解每一步。

## 静态托管的完成证据

AI 可以根据仓库结构填写候选 Build Command、Root Directory 和 Output Directory，解释失败日志，并整理 Pages 与 Cloudflare 的差异。它不能替你批准第三方读取全部仓库。授权页面要亲自查看范围，正式部署也要打开真实网址验收。

确认仓库内容可公开、生产分支正确、授权范围最小、部署对应预期提交。打开平台地址检查页面，再查看 Console 和 Network。下一章会讨论 Vercel、Render 等自动部署平台，并说明静态站托管与可运行后端服务的差别。
