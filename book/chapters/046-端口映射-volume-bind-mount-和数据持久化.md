# 端口映射、Volume、Bind Mount 和数据持久化

容器运行以后有两条最容易出事故的边界。网络决定谁能连接，挂载决定容器能读写哪些数据。端口映射写反，用户访问不到应用。主机地址省略，数据库可能暴露公网。数据只写容器层，更新后会消失。Bind Mount 指错路径，容器可能遮住自己的文件或改坏主机内容。

这一章把网络与存储放在同一张图中，因为它们都在连接容器和外部世界。

![容器的网络与数据边界](../assets/diagrams/docker-network-storage.png)

*图 46-1　外部请求通过主机端口进入容器，持久数据通过 Volume 或 Bind Mount 离开容器可写层。等价说明见本章“容器有内外两套地址”。*

## 容器有内外两套地址

应用在容器内监听 3000，这个端口属于容器网络。主机没有发布时，从公网不能直接访问。端口发布形如 `主机地址:主机端口:容器端口`。例如 `127.0.0.1:8080:3000` 让主机本地 8080 转到容器 3000。反向代理运行在主机时，可以访问 `127.0.0.1:8080`。用户只访问 Caddy 的 443，应用端口不直接暴露。

主机端口与容器端口可以不同。先写请求从哪里来，再读数字，避免靠记忆猜方向。

## 最小端口映射练习

下面命令在安装 Docker 的测试机运行，会下载 Nginx 镜像、创建容器并发布本机端口。

```
docker run -d --name web-test \
  -p 127.0.0.1:8080:80 \
  nginx:alpine
```

`-d` 在后台运行。`--name` 设置容器名。`-p` 把主机本机地址 8080 映射到容器 80。在同一主机运行。

```
curl -I http://127.0.0.1:8080
```

应看到 HTTP 响应头。其他电脑不能直接通过服务器公网地址访问这个绑定。若被拒绝，运行 `docker ps` 和 `docker logs web-test` 检查。

## 省略主机地址的风险

下面写法很常见。

```
-p 8080:80
```

Docker 当前文档说明，未指定主机地址时，发布端口默认可能绑定所有主机 IPv4 和 IPv6 地址。若云防火墙允许，互联网就能连接。公开 Web 入口可以计划开放，数据库、Redis、管理面板和调试端口通常不应这样发布。

每次启动后用 `docker ps` 和主机 `ss -lntp` 检查实际地址。不能只看 Compose 文件猜测。

## EXPOSE 不等于发布端口

Dockerfile 中 `EXPOSE 3000` 表达镜像预期监听的端口，像文档元数据。它不会自动让主机或公网能访问。真正发布由 `docker run -p` 或 Compose 的 `ports` 决定。同一网络中的容器还可通过服务名和容器端口连接，不需要发布到主机。

看到镜像写了 EXPOSE，不要因此在防火墙开放。先画出谁需要访问它。数据库只供 API 容器使用时，放在内部 Compose 网络，不写 `ports`。

容器重建后内部 IP 可能变化。Compose 网络会为服务名提供名称解析，例如应用使用 `db:5432` 连接数据库。服务名在对应 Docker 网络内有效，主机浏览器不能把 `db` 当作公网域名。不要把容器 IP 写进应用配置。使用服务名、主机发布地址或正式域名，按通信位置选择。

网络不存在或服务不在同一网络时，名称解析会失败。用 `docker network inspect` 查看成员，输出可能含内部地址，分享前脱敏。

## 容器可写层的生命周期

镜像层只读，容器在上面增加自己的可写层。应用创建的临时文件、日志和数据库若没有挂载，都落在这里。停止再启动同一个容器，可写层仍在。删除并重建容器，可写层消失。这个差异让“我重启过数据还在”产生误导。

生产更新通常重建容器，所以持久数据必须脱离可写层。Docker 存储文档明确说明可写层属于单个容器，容器销毁后数据不持久。把容器当成可替换实例，数据位置才会设计正确。

Volume 中文常称数据卷。Docker 在主机管理它的位置，容器把卷挂到某个路径。命名卷有稳定名称，容器删除后仍保留，除非明确删除卷。多个新容器可以重新挂载。查看卷。

```
docker volume ls
docker volume inspect notes-data
```

命令只读。第二条需要卷存在，会显示名称、驱动、挂载点和标签。不要直接进入 Docker 内部目录编辑数据，官方文档说明直接操作可能破坏卷。

## 创建并挂载 Volume

下面练习会创建命名卷并让容器写一个文件。

```
docker volume create notes-data
docker run --rm \
  --mount source=notes-data,target=/data \
  alpine sh -c 'echo hello > /data/example.txt'
```

第一条创建卷。第二条创建短期容器，把卷挂到 `/data`，写入文件后删除容器。卷继续存在。再用另一个短期容器只读查看。

```
docker run --rm \
  --mount source=notes-data,target=/data,readonly \
  alpine cat /data/example.txt
```

预期输出 `hello`。这证明数据独立于前一个容器，不证明已经有备份。

## Bind Mount 直接使用主机路径

Bind Mount 中文可称绑定挂载。它把主机的精确文件或目录映射进容器。开发时把源代码目录挂进去，保存本地文件后容器立即看到，很方便。生产时可以只读挂载配置或把明确数据目录交给容器。

它依赖主机目录结构，迁到另一台机器前必须创建相同路径与权限。容器进程默认还能写主机文件，风险更直接。Docker 绑定挂载文档建议使用语义更明确的 `--mount`，并说明绑定挂载默认可写。

下面命令在测试机运行，把当前目录下的 `public` 只读挂到 Nginx 网页目录。

```
docker run --rm -d --name static-test \
  --mount type=bind,src="$(pwd)/public",dst=/usr/share/nginx/html,readonly \
  -p 127.0.0.1:8081:80 \
  nginx:alpine
```

命令会读取主机 `public`。在 PowerShell 中 `$(pwd)` 的路径传递表现可能不同，优先使用完整绝对路径和 Docker Desktop 当前文档。源目录不存在时，`--mount` 会报错，能防止悄悄创建错误空目录。检查路径后再启动。

## 挂载会遮住镜像原内容

把主机空目录挂到容器已有文件的路径，镜像中的原文件会在运行容器中被遮住。它们没有被删除，只是挂载覆盖了视图。一个常见故障是把空配置目录挂到 `/app`，容器启动时报找不到程序。移除错误挂载并重建容器后，镜像内容重新出现。

不要在运行容器中试图“卸载”来找回。Docker 官方建议重新创建不带错误挂载的容器。配置挂载到精确文件路径，比覆盖整个应用目录更容易审查。

数据库数据希望由 Docker 管理路径，使用命名卷通常更合适。主机与容器都需要直接编辑的开发源码，使用 Bind Mount 更自然。需要知道主机上明确备份目录时，绑定挂载也可以用于生产，但要管理目录所有者、权限和迁移。

Volume 不是自动备份。Bind Mount 也不是天然更透明。两者都要使用应用一致性工具备份，并实际恢复。选择后写数据所有者、容器目标路径、主机或卷来源、备份和删除方式。

## 权限编号跨过容器边界

Linux 容器内外使用用户编号。容器中的 UID 1000 写入 Bind Mount，主机上文件所有者也可能显示对应编号。镜像更换用户后，新容器可能无法写旧数据。不要用 `chmod 777` 解决。查看镜像运行用户、卷中文件所有者和宿主机映射。通过固定服务 UID、初始化权限或受控入口脚本处理。

Docker Desktop 的文件共享经过虚拟机转换，表现与 Linux 主机不同。生产权限要在真实服务器验证。

tmpfs 挂载把文件保存在主机内存，不写持久磁盘。容器停止、重启或主机重启后数据会消失。它适合可丢失缓存和短期敏感中间文件。内容占用内存，必须限制大小。不要把数据库、上传或唯一会话状态放进 tmpfs。名字里含“文件系统”也不代表持久。

Docker 存储概览明确把 tmpfs 定义为易失存储。

## 数据库备份要使用数据库工具

数据库写入 Volume，不等于可以直接压缩卷目录。运行中复制底层文件可能不一致。PostgreSQL 使用 `pg_dump`、物理备份或托管方法。SQLite 使用在线备份接口或安全停写。先遵循数据库官方文档，再决定卷如何传输。

Docker Volume 文档提供通用文件备份示例，只适合能安全按文件复制的数据。恢复测试要创建新卷和新容器，不覆盖生产卷。验证数据库版本、权限和业务数据。

`docker rm` 删除容器，命名卷通常保留。Compose `down` 默认也不删除命名卷。加入 `-v` 或 `--volumes` 可能删除关联数据。卷清理命令会处理未被容器使用的卷，而“未使用”不等于“没有重要数据”。删除前列出卷、容器引用、标签、大小和备份。没有确认所有者的卷先隔离，不执行全局清理。

第 49 章会给出安全清理顺序。本章练习卷在确认无用后才能删除。

## 完整验收

先用 `docker ps` 确认容器和端口地址。主机本地发请求，外部网络确认只开放计划入口。创建测试数据，删除并重建容器，重新挂载同一卷，确认数据仍在。再从备份恢复到不同卷。检查主机目录与卷权限，确认容器不能写只读配置，不能访问未挂载路径。

最后记录网络、卷、备份和删除方法。持久化验收必须包含重建，不是只重启。

`ports` 把容器端口发布到主机。`expose` 只描述向关联网络开放的容器端口，不创建主机入口。同一默认网络服务通常不需要 expose 也能通过容器端口通信，具体字段更多用于说明和兼容。数据库只给 Web 服务使用时，不写 ports。需要主机临时维护时，使用受控 exec 或临时本机绑定，完成后删除。

运行 `docker compose config` 和 `ps` 验证，不能只看 YAML 一行。

## 随机主机端口适合测试

只写容器端口或让 Docker选择空闲主机端口，能避免并行测试冲突。实际端口通过 `docker compose port` 查询。生产反向代理需要稳定上游时，使用明确本机端口或同一 Docker 网络服务名。随机端口不能写进防火墙永久规则。测试框架应从 Docker API 读取结果，不猜范围。

测试结束清理容器，避免占用大量随机端口。

Compose 默认创建一个项目网络。服务可以声明多个网络，把前端代理、应用和数据库分层。只有需要通信的服务加入同一网络。数据库不加入公开代理网络，能减少横向访问。Docker 网络隔离不是业务授权。被攻破的 Web 容器仍可能访问同网数据库，应使用数据库账号和最小权限。

网络配置复杂后画出每个服务成员。错误加入网络会让名称可达或不可达。

## internal 网络的含义

Compose 网络可以标记 internal，限制外部连通。它适合只需内部通信的组件。服务仍可能通过其他网络出站。要检查所有网络，而不是看到一个 internal 就认为完全离线。依赖外部软件源、邮件或 API 的服务需要出站路径。安全目标与功能要一起测试。

不同平台和网络驱动行为可能不同，按当前 Compose 和 Engine 文档验证。

同一网络可以为服务设置别名。两个服务使用相同别名时，解析可能返回多个地址，造成不稳定连接。名称只在网络范围内有效，跨项目外部网络可能让原本隔离的同名服务相遇。生产外部网络使用明确项目命名，记录创建者和成员。删除 Compose 项目时外部网络不会自动删除。

应用配置使用服务名，不使用自动容器名和动态 IP。

## 命名卷的实际名称

Compose 顶层写 `db-data`，Docker 实际卷名常带项目名前缀，例如 `notes_db-data`。目录改名或项目名变化，会创建另一只空卷。数据库看起来像数据消失，旧卷可能仍在主机。运行 `docker compose volumes`、`docker volume ls` 和 inspect 确认。不要立即初始化并覆盖。

需要跨项目共享时可声明外部卷和固定名称，但它的创建、备份与删除不再由单个项目负责。

匿名卷没有易读名称，Docker 生成随机标识。容器重建时，可能创建新匿名卷，旧数据留在主机但不再挂载。需要持久的数据库使用命名卷或明确 Bind Mount。匿名卷适合镜像声明的临时可写位置，仍要注意积累。

`down` 默认不删除匿名卷，也不会在下一次 `up` 自动重挂同一只。Docker `down` 参考明确提醒这一点。看到很多随机卷时先查原容器和挂载，不直接 prune。

## 卷标签帮助归属

Compose 创建的卷通常带项目与配置标签。自建卷也可以添加用途、环境和保留标签。清理脚本按标签筛选，比按模糊名称安全。标签仍可能缺失或错误，不能替代备份确认。资产清单记录卷名、服务、数据类型、最近备份和恢复测试。停止项目后保留数据时，明确标记保留期限。

卷跨主机迁移后更新清单，旧副本按隐私要求删除。

配置、证书公钥和静态文件只需要读取时，加入 `readonly`。容器尝试修改会收到只读错误。只读挂载不会保护主机上其他未挂载路径，因为容器本来就看不到它们。它只限制这次映射。应用要写临时文件时，提供独立 Volume 或 tmpfs，不把整个配置目录改为可写。

验证拒绝路径，进入容器尝试创建测试文件应失败。不要对真实证书文件做破坏测试。

## 只读根文件系统

运行容器可以把根文件系统设为只读，减少应用修改镜像内容。需要写入的 `/tmp`、缓存和数据通过明确挂载提供。应用或依赖可能意外写日志、PID 文件和缓存，第一次启用会暴露这些路径。在测试环境逐项找出真实写入需求。不能为了启动把整个根设回可写并结束调查。

只读根不能保护可写 Volume 数据，也不能替代非 root 和最小能力。

部分 Linux 发行版用 SELinux 标签控制绑定挂载，Ubuntu 常使用 AppArmor。权限字符串允许时，安全模块仍可能拒绝。Docker 的 `:z`、`:Z` 选项会修改主机 SELinux 标签，官方文档警告对宽泛系统目录使用可能让主机无法正常工作。

不要把这些选项复制到 Ubuntu 或未知环境。读取审计日志，按发行版与 Docker 官方文档处理。关闭安全模块不是长期修复。

## Docker Desktop 文件共享

Windows 与 macOS 的 Bind Mount 会经过 Docker Desktop 虚拟机文件共享。主机路径必须允许共享，性能和文件通知与 Linux 不同。数据库放在宿主机共享目录可能性能差，也可能不受镜像支持。开发数据库优先使用 Docker Volume。

源代码挂载适合开发。生产 Linux 服务器不使用 Desktop，应在原生文件权限下重新验收。路径中的盘符、反斜杠和空格需要按 PowerShell 与 Compose 当前规则引用。

第一步让应用进入一致状态。数据库使用自身备份工具，普通文件可以暂停写入或创建快照。第二步把备份写到容器外和主机外。只写另一只同盘 Volume 不能抵御主机故障。第三步恢复到新卷。创建独立容器连接，检查版本、权限、数据数量和业务。

把步骤、时间、校验和与结果记录。自动任务成功退出仍要定期恢复。

## 迁移命名卷

跨主机迁移时，先停止或协调写入，按应用方式生成一致备份。把备份通过加密通道传到新主机。在新主机创建新卷并恢复。使用相同数据库镜像大版本，确认 UID 和目录权限。启动测试容器验证，再切换正式应用。旧卷保持只读观察，不能立刻删除。

通用 tar 只适合可按文件复制的数据。数据库底层目录要遵循数据库文档。

管理员复制项目目录到新名称并运行 `docker compose up -d`。Compose 项目名变化，创建了新的空 `db-data` 卷。数据库初始化成功，应用显示没有记录。旧卷仍在主机，数据没有真正删除。正确处理是停止新项目，盘点卷标签与大小，确认旧卷，使用明确项目名或外部卷重新挂载。

不能在恐慌中运行 volume prune，也不能继续向新库大量写入后再混合数据。

## 一个挂错主机目录事故

生产配置把 `/srv/notes/data` 拼成 `/srv/note/data`。短语法自动创建空目录，应用初始化新数据。改用 `--mount` 能在源路径不存在时报错。部署前还可以检查绝对路径、所有者和预期文件。发现后停止写入，确认两个目录时间和内容，按数据恢复计划合并或回退。

路径错误应在自动化中成为硬失败，不能由程序默默创建生产数据库。

假设留言板包含四类内容。前端静态文件来自镜像，每次发布都能重新构建，不需要 Volume。用户上传的图片需要跨容器重建保留，可以放对象存储，也可以在小型单机方案中放受备份的命名卷。PostgreSQL 数据属于数据库自身管理的持久数据，需要数据库卷和数据库级备份。临时缩略图可以重新生成，适合临时目录。

分类时问两个问题；容器删除后，这份数据是否必须存在；若丢失，能否从代码、远程存储或备份重新得到；答案决定它是镜像内容、持久数据还是缓存；不要只按文件扩展名分类。同一个 JSON 文件可能是可重建配置，也可能是用户唯一数据。真正的判断依据是数据来源与恢复办法。

## 挂载上线前的最小检查

在 Linux 主机上先确认源路径和目标路径。Bind Mount 的源路径属于主机，目标路径属于容器。两边写反可能遮住镜像目录，也可能把文件挂到应用从不读取的位置。使用测试文件验证方向。主机写入一个没有业务含义的标记文件，在容器中确认能看到。再从容器写入临时文件，确认主机位置正确。生产数据库目录不能随意做这种写入测试，应使用应用提供的健康和备份命令。

然后重建容器，而不是只重启。查看 `docker inspect` 的 Mounts，核对类型、源、目标和读写属性。应用能启动以后再确认业务数据数量，不能只看目录存在。最后做一次停止与重建测试。删除测试容器，重新用相同配置创建，确认数据仍在。这个步骤能在上线前发现数据其实写在容器可写层的问题。

把备份写到同一块磁盘，只能应对误改部分文件。主机磁盘损坏、账号被入侵或整台 VPS 被删除时，原数据和备份会一起消失。至少保留一份位于另一故障域的加密备份。它可以是另一台主机、受控对象存储或离线介质。访问凭据不能只保存在被备份的服务器上。

定期选择一个新卷做恢复，记录恢复时长和数据核对结果。只有恢复成功的备份才具有可用证据。
