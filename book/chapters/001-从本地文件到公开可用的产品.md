# 从本地文件到公开可用的产品

你让 AI 做出一个网页，本地预览里按钮、图片和文字都正常，于是把 `http://localhost:5173` 发给朋友。朋友打不开。你又把 GitHub 仓库地址发过去，对方这次看见一排文件，仍然没有网站。直到部署平台完成构建并给出公开地址，朋友才真正看到页面。

这不是三个互相无关的工具故障，而是一条交付链还没走完。`localhost` 只指向访问者自己的设备；GitHub 仓库保存可追溯的项目版本；部署平台才把一个版本变成用户能取得的结果。发布的第一项能力不是记住按钮，而是知道当前结果停在哪一段。

## 一条交付链，而不是一个“发布”按钮

可以把过程压成六个对象：

1. **本地项目**：人和 AI 正在修改的源码、资源、配置、测试与说明。
2. **可追溯版本**：一批相关修改被 Commit 记录，并在需要时 Push 到远程仓库。
3. **构建结果**：工具按指定版本、目录、依赖和命令生成网页文件、服务程序或 App 包。
4. **运行或分发环境**：静态文件由托管平台交付，后端由平台或服务器持续运行，App 由测试通道或商店分发。
5. **公开入口**：用户通过域名和 HTTPS、商店页面或安装链接找到产品。
6. **用户验证**：目标设备上的真实用户动作得到预期结果。

这些对象经常同时存在，却不是同一件事。文件保存不等于 Commit，Commit 不等于 Push，Push 不等于构建，构建不等于部署，部署也不等于用户可用。AI 说“完成了”时，先问它完成的是哪一个对象，并要求给出相应证据。

小林的部署第一次失败，日志说找不到 `package.json`。文件明明在电脑里，问题却不是依赖本身，而是仓库最外层多了一层同名目录，平台从错误的 Root Directory 开始构建。改正目录后产生了公开地址。这个例子说明，错误通常发生在两个对象的连接处：平台有没有取得正确版本，构建有没有从正确目录读取，入口有没有指向正在运行的结果。

遇到陌生控制台时，先问三件事：用户最后打开哪个地址或安装哪个 build；这个结果由谁从哪个版本生成；失败位置留下了什么日志、状态或请求记录。答案能把“发布坏了”缩成一个可以检查的边界。

## 源码、产物与运行中的程序

电脑里的项目文件是原料。简单静态网站的 HTML、CSS、JavaScript 和图片可能已经接近最终结果；React、Vue 等项目通常还要把源码转换到 `dist`、`build` 或配置指定的目录。目录名不是规则，README、项目脚本和构建配置才是依据。直接双击 HTML 能打开，也不能证明部署平台知道怎样构建；本地开发命令能运行，也不能证明生产环境拥有相同版本、依赖和变量。

构建发生在准备版本时。它失败，通常意味着新产物还没有生成。运行发生在用户访问时：后端可能已经成功部署，后来却因数据库断开、内存不足或第三方服务异常而返回错误。因此构建日志与运行日志不能混用。前者回答“这个版本为何没生成”，后者回答“已经运行的版本为何没完成请求”。

手机 App 的链路更长。Dart、Swift 或 Kotlin 源码要经过平台构建、签名和测试分发，包名、Bundle ID、版本号、构建号与证书还要保持更新连续性。商店处理客户端分发，不负责远程后端。App 能安装，只证明客户端制品与分发通道走通；登录、同步、支付或 AI 调用仍可能因后端失败。

> **证据边界**
>
> 源码存在，只证明文件在某处；构建成功，只证明产物生成；平台显示部署成功，只证明平台接受并放置了版本；首页能打开，也只证明这一条请求成功。只有目标用户通过预定入口完成关键流程，才能在该流程范围内说“可用”。

## GitHub 是版本坐标，不是自动运行环境

Git 记录文件怎样变化，GitHub 保存远程仓库并提供协作与自动化入口。远程版本让部署系统知道该取哪一批文件，也让维护者能把故障与最近修改对照。仓库页面本身不会把任意项目自动运行成网站；静态站点需要 Pages 或其他托管，动态应用还需要能执行服务端代码的环境。

Commit 与 Push 的区别在这里很实际。Commit 把本地改动记录成一个版本，Push 才把已有提交送到远程。部署平台监听远程分支时，本地已保存但未 Push 的修改对它不存在。交接记录至少要有仓库、分支和提交标识；“代码已经改了”不足以定位实际发布对象。

配置和秘密也属于交付关系，但不能混为公开源码。项目需要知道变量名称、使用位置和设置责任，真实密码、Token、签名口令则应进入受控秘密存储。把 `.env` 发给 AI 或提交到公开仓库，不会让发布更完整，只会扩大泄露范围。

## 选择路线，就是选择长期责任

静态托管、托管后端、容器平台和 VPS 都能成为链路中的运行环境。选择时先看产品需要，不从工具名开始。

- 只有文字、图片和浏览器代码，优先评估静态托管。
- 请求到来时需要少量服务端逻辑，可评估平台函数或托管后端。
- 需要常驻进程、后台任务或特殊二进制，再评估容器服务。
- 确实需要操作系统级控制，且有人负责补丁、服务、网络、备份和磁盘时，再选择 VPS。

“减少责任”不是追求功能最少，而是把与产品目标无关、却必须长期完成的系统工作交给可靠服务。一个餐厅菜单站用静态托管即可完成目标；为了显得专业而租 VPS，会额外承担 Linux 更新、Web 服务器、证书和监控。图片转码服务需要特殊程序和较长任务，短时函数可能不适合，常驻容器才可能更符合工作负载。

数据位置要单独决定。网页在静态托管，不妨碍账号与数据库由另一服务承担；后端在 VPS，也不要求数据库必须同机。拆分可以降低单机故障，也会增加账户、网络、权限和费用关系。选择的标准不是组件越多越好，而是每个组件的负责人、入口和恢复方式都能说清楚。

两个产品能看出这项选择为什么重要。

第一个是静态知识页。内容来自仓库中的 Markdown，构建工具把它转成 HTML，托管平台发布到默认域名，再绑定自定义域名。它没有业务数据库和常驻应用进程。一次更新失败时，旧部署可以继续服务；维护重点是源码版本、构建、域名、证书和外部链接。为它增加 VPS 和数据库，不会让知识页更可用，只会增加补丁、账号和备份责任。

第二个是预约 App。手机端显示时段，后端在收到请求时重新确认空闲，数据库以避免重复预约的方式写入，邮件服务随后发确认。客户端要分别构建、签名和分发；后端必须持续运行；数据库需要恢复方案；邮件失败还要能重试。这里至少有四种不同的“成功”：App 能安装、后端健康检查响应、预约确实写入、邮件最终到达。第一项通过不能代表后三项。

这两个项目都可以用 GitHub，也都可能显示“部署成功”，但它们的完成定义不同。先画组件与数据流，再决定平台和验收，比复制某份“一键发布”教程更可靠。AI 可以帮助识别项目类型和候选配置，人仍要确认真实账户、付费资源、生产数据和公开入口。

## 一张发布责任表

发布前为每项写出负责人、对象和最小证据。写“平台负责”时，也要知道去哪个页面看结果。

| 对象 | 要回答的问题 | 最小证据 |
|---|---|---|
| 源码与版本 | 正式版本在哪里 | 仓库、分支、提交 |
| 构建 | 谁从什么目录执行什么命令 | 构建记录、产物目录 |
| 运行或分发 | 产物现在由谁提供 | 部署 ID、服务状态或测试轨道 |
| 入口 | 用户从哪里进入 | 公开地址、DNS/HTTPS 或安装链接 |
| 数据 | 数据库和上传文件在哪里 | 存储配置、备份与一次恢复记录 |
| 秘密 | 谁能读取，怎样轮换 | 变量名、受控位置和权限，不保存值 |
| 日志 | 构建与运行错误分别在哪里 | 日志入口、时间与版本 |
| 费用 | 哪些资源会持续收费 | 账单入口、预算与告警 |
| 回退/下线 | 新版本失败或产品停止时怎么办 | 稳定版本、恢复步骤和资源清单 |

域名、HTTPS 与备份很容易被“平台已配置”四个字掩盖。DNS 正常不表示应用进程正常，安全连接不表示网站业务安全，平台显示有备份也不表示能恢复。证书续期、域名账户、数据库恢复和账单告警都需要可观察入口。

这张表也能指导排错顺序。域名查不到时，先看 DNS 和账户状态；能建立 HTTPS 但得到 502 时，转向代理与上游服务；首页返回 200 而登录失败，继续看浏览器请求、应用日志和数据库。不要因为所有现象都出现在同一个浏览器窗口，就假定错误都在前端。

App 同理。商店拒绝上传时查包名、版本、签名和政策；安装后立即崩溃时查客户端构建；只有登录或同步失败时再追踪网络与后端。先定位对象，能避免为数据库故障反复重装 App，或为构建失败修改 DNS。

## 用一个最小变化验收整条链

找一个已上线的练习项目，只改首页一句无风险文字：

1. 记录修改前公开页面和当前版本。
2. 在正确项目中改文字，查看 Diff，确认没有秘密和任务外文件。
3. Commit 并 Push，记录远程提交。
4. 观察构建记录是否读取同一提交，确认产物与部署状态。
5. 用公开地址、普通测试账号或无痕窗口查看新文字，同时检查一个原有关键入口没有被破坏。
6. 记下版本、环境、时间及时区、实际结果和未验证项。

一次打开可能命中旧缓存或拥有特殊权限。正式交付要使用目标地址和接近真实用户的设备、账号与操作。涉及后端数据时，再验证一次写入和读取；涉及重要数据时，备份必须用受控恢复证明。

如果还没有上线项目，可以先做只读位置清单。找到根目录和 README，辨认依赖清单、源码目录、构建脚本与可能的输出目录；确认是否存在 Git 仓库、远程地址和部署配置；只记录 `.env` 是否存在，不读取或分享内容。找不到的项写“未知”，不要让 AI 根据常见目录名假装确定。

让 AI 做这类检查时，要求它引用具体文件和脚本来源，并区分“文件中明确写着”“根据框架惯例推测”“需要登录平台确认”。项目同时出现多个部署配置时，先查哪一个仍连接真实环境，不直接删除看不懂的旧文件。只读地图本身不会完成发布，却能给后面的每个命令一个坐标。

准确的状态应像这样写：“提交 `a1b2c3d` 已于 2026-08-05 14:20 +08:00 部署到生产；公开首页与测试账号登录已验证；邮件通知和 iOS 实机尚未验证。”允许写未知，远比一句“应该上线了”可靠。

平台词语也要翻译成对象。Deploy 通常表示把某个版本放进预览或生产环境；Publish 可能表示让预览成为生产，也可能表示把 App 送进测试轨道或商店审核；Healthy 可能只检查一个进程或一个路径。按钮叫同一个名字，不代表平台承担同一责任。交接时不用复制绿色标签，而要写清目标环境、版本、入口与实际用户动作。

命令退出码为零、测试通过、构建成功、部署成功、健康检查成功和用户可用，是范围逐渐不同的证据。测试只覆盖已有用例；健康检查可能不访问数据库；公开首页可能不经过登录服务。把它们串成证据链，才能知道下一项尚未证明什么，也能在失败时回到最近一个成立的边界。

这也是本书反复使用“证据边界”的原因：不是否定工具给出的成功，而是给成功加上对象、时间和范围。范围写得越准确，AI 越不容易把局部绿色扩大成全局结论，维护者也越容易补完尚未验证的一步。

没有版本和入口的“成功截图”，后来很难复查。

## 现在可以跳过什么，继续看哪里

现在不需要背 Git 分支命令、DNS 记录类型、systemd、Docker 或商店按钮。先能指出六个对象，并为当前项目写一张责任表。某个项目根本没有后端，就可以跳过服务器部分；没有 App，就不需要学习签名与商店分发。

下一章会继续区分代码究竟运行在哪里。后续各卷会分别展开 GitHub、Web 部署、服务器、容器和 App 发布。届时遇到任何工具，都把它放回这条链：它读取哪个版本，产生什么对象，谁向用户提供，以及成功证据能覆盖到哪里。
