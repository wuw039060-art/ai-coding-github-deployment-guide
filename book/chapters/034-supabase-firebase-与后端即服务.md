# Supabase、Firebase 与后端即服务

后端即服务常缩写为 BaaS。供应商把数据库、身份认证、文件存储、实时通信和函数等能力组合起来，通过控制台、SDK 和 API 提供。个人项目可以更快得到可用后端，仍要设计数据、权限、费用和恢复。

Supabase 与 Firebase 都属于常见选择。Supabase 以 PostgreSQL 为核心，提供 Auth、REST、Realtime、Storage 和 Edge Functions 等能力。Firebase 包含 Firestore、Realtime Database、Authentication、Cloud Storage、Cloud Functions 和 Messaging 等产品。能力名称相似，数据模型和安全边界并不相同。

## BaaS 替你完成什么

供应商运行数据库或存储基础设施，提供账号、网络入口、SDK、监控与部分备份。开发者不用先安装数据库服务器。身份服务处理登录流程和 Token，存储服务处理对象上传，实时服务推送变化，函数运行短后端代码。

控制台让初学者直观看表、用户和文件。生产维护仍需要迁移文件、权限规则、备份验证和变更记录。BaaS 缩短起步时间，也把更多组件放到同一供应商。账号、区域、规则和费用配置出错时，影响会集中。

选择 BaaS 前，先写产品真正需要哪些能力。只是公开静态页，不需要后端即服务。需要登录、用户资料、文件上传和实时状态时，BaaS 很适合做第一版。需要复杂后台任务、特殊网络、强合规隔离或跨多个系统的事务时，要更谨慎。

## Supabase 的核心边界

Supabase 的核心是 PostgreSQL。表、SQL、约束、事务和索引都在数据库里。PostgREST 可以根据数据库 Schema 提供 REST API。Auth 管理用户身份，并与数据库中的行级安全策略配合。Storage 保存对象，元数据和权限规则连接到数据库模型。Realtime 监听数据变化或广播事件。Edge Functions 处理自定义服务端逻辑。

Supabase 的强处在于标准 PostgreSQL。你可以使用关系表、约束、事务和 SQL 工具。表暴露成 API 后，还要检查访问授权与 Row Level Security（RLS）策略。客户端使用的 publishable Key 或旧版 anon Key 不代表用户身份，也不等于管理员权限。secret Key 和旧版 service_role Key 可以绕过 RLS，不能进入浏览器、App 或小程序前端。使用这类高权限 Key 的后端，必须自行验证调用者和资源归属。

RLS 策略要用多个账号测试。甲用户只能读自己的记录，商家只能读自己的店铺，管理员能读管理范围。新增表、视图、存储过程和 Storage Bucket 时，都要问权限是否随之改变。只在前端过滤数据，是典型事故入口。

## Firebase 的核心边界

Firebase Authentication 管理密码、联合身份和其他登录方式。Cloud Firestore 是文档数据库，数据按 Collection 与 Document 组织，提供客户端 SDK、实时监听和离线支持。Cloud Storage for Firebase 保存用户文件，通过 Security Rules 与 Authentication 控制客户端访问。Cloud Messaging 处理跨平台消息。Cloud Functions 或其他 Google Cloud 计算服务运行可信后端代码。

Firestore 的文档模型很适合按页面读取聚合数据，也适合客户端实时监听。它不按关系表思考。跨集合查询、复杂聚合、全局唯一约束和报表可能需要额外设计。规则写得宽，客户端 SDK 就能直接读写不该访问的数据。规则写得窄，功能又可能悄悄失败。

Firebase Security Rules 要和数据结构一起设计。规则不是注释。它决定客户端能读写哪些路径。每次改变文档结构和集合路径，都要回到规则测试。小程序、App 和 Web 客户端使用同一后端时，还要检查各端登录状态和 SDK 行为差异。

Firestore 规则不会替查询过滤掉无权查看的记录。查询本身要满足规则，否则整个请求可能被拒绝。另一个容易漏掉的边界是服务端：Firestore 服务端客户端库会绕过 Security Rules，改用 IAM 等机制控制访问。因此，移动端和 Web 规则测试通过后，还要单独检查使用 Admin SDK 的后端接口，确认它验证了用户身份与资源权限。

## 认证不等于数据权限

BaaS 的登录很方便，但登录只证明用户身份。用户能不能读某条记录、上传某个文件、订阅某个频道，还要看权限规则。许多事故发生在“能登录”之后。用户 A 登录后，通过改 ID 读取用户 B 的资料，说明数据权限缺失。

Auth 用户表也不等于业务用户资料。登录系统保存邮箱、手机号、Provider 和用户 ID。业务资料还可能包含昵称、组织、角色、套餐、商家身份和同意记录。两者要有同步和删除流程。第三方登录返回的邮箱不能自动变成业务管理员。

服务端函数可以承担高权限动作。支付回调、管理员导出、批量修改、AI 调用和数据库维护，不应直接暴露给客户端 SDK。函数中使用服务端秘密，外部入口则要验证身份、签名、来源和幂等。

## 费用和生命周期

BaaS 的免费额度适合试验，不适合当作长期承诺。数据库读写、实时监听、函数调用、存储容量、下载流量、认证短信、推送和日志都可能计费。价格和额度会变化，正式项目按当前官方控制台确认。

实时监听尤其容易失控。一个列表页面若给每个卡片都开监听，用户一多就会产生大量连接和读取。页面离开后要取消订阅。后台标签页、移动端重连和小程序生命周期也会影响连接数量。费用排查时，按页面、用户动作、监听数量和读取次数拆分。

函数重试也要设计。外部服务超时、Webhook 重复、AI 调用失败和邮件发送失败都可能触发多次执行。没有幂等记录，重复函数会创建重复订单、重复邮件或重复扣费。

## 迁移和备份要分组件看

“能导出数据”不等于完整迁移。Supabase 的表、RLS、函数、Storage 对象、Auth 用户、Realtime 配置和扩展都要分别看。Firebase 的 Firestore 文档、Security Rules、Storage 文件、Auth 用户、Functions、Messaging 和索引也要分别看。

备份也一样。数据库备份未必包含对象存储。对象存储备份未必包含权限规则。Auth 用户导出可能缺少第三方 Provider 状态。正式项目要列出每个组件的备份、恢复和删除方式，并做至少一次演练。

退出计划不用一开始就写成迁移工程，但要知道最低出口。数据能否导出成通用格式，文件能否批量复制，用户身份如何重新绑定，客户端 SDK 调用是否被封装，域名和 Webhook 是否掌握在自己账号里。越早写清，平台依赖越可控。

## 一个规则回归案例

假设团队新增一个 `teams` 集合，用于保存组织成员。开发时为了方便，把读规则写得很宽。前端只显示当前用户所在组织，测试账号看起来正常。有人手工请求另一个组织 ID，却拿到了成员名单。这时应检查权限规则是否按资源归属限制访问，不能只检查登录和前端页面。

修复时先收紧规则，补多个账号的规则测试，再检查历史访问日志。随后把“新增集合必须新增规则测试”写进发布清单。BaaS 让项目少写许多后端代码，但不会自动理解你的租户边界。

## 索引、环境和发布

BaaS 控制台很方便，也容易让配置散落在网页里。索引、规则、函数、存储 Bucket、环境变量和计划任务都应进入发布记录。能版本化的配置尽量放进仓库。必须在控制台改的内容，记录旧值、新值、操作者、时间和回退办法。

Firestore 查询常会提示需要索引。Supabase 中 PostgreSQL 查询也可能需要索引。索引不是越多越好。它会占存储，拖慢写入，也需要迁移管理。先看真实查询和慢查询，再添加。添加后记录它服务哪个页面或接口，避免以后无人敢删。

项目、组织和环境要分开。个人练习项目、团队预览项目和生产项目不要混在同一个默认账号里。预览环境使用测试数据库、测试存储和测试密钥。生产环境的服务角色 Key、Firebase Admin 凭据和支付密钥不进入预览。小程序体验版、Web 预览版和 App 测试版也要对应测试后端。

发布时至少走一条端到端路径。新用户注册，创建一条业务记录，上传一个测试文件，触发一次函数或实时更新，再删除测试数据。只看控制台绿色，不足以说明规则、客户端 SDK 和函数都匹配。

## 本地开发与种子数据

本地开发不要直接连生产项目。Supabase 可以用本地容器或独立测试项目，Firebase 也有本地模拟器。能在本地跑的登录、规则、函数和数据库变更，先在本地跑。小程序开发工具里的测试账号，也应连测试环境。逐项确认各组件的连接地址，移除生产凭据，邮件、短信和推送改用测试入口或禁止真实发送。仅仅启动模拟器，不能保证函数里的外部调用不会触达生产服务。

种子数据要可重复。准备几类用户，普通账号、管理员、被冻结账号、没有资料的账号。准备几类业务记录，空状态、待审核、已完成、已删除。每次重建测试环境都能得到同样的数据，AI 写测试和人手验收才有共同参照。

跨环境复制数据时要脱敏。生产用户的手机号、邮箱、头像、聊天内容和上传文件不应直接进入开发环境。需要复现问题时，复制最小字段，遮掉个人信息，并记录谁申请、谁批准、何时删除。方便调试不能压过用户隐私。

## 什么时候不用 BaaS

如果核心业务需要复杂事务、跨系统一致性、私有网络、长时间后台任务或精细合规控制，要逐项确认所选服务的能力。Supabase 底层 PostgreSQL 本身支持事务，不能仅凭“BaaS”这个分类判断是否够用。需要集中控制核心写入时，可以放到自己的后端 API 后面，减少客户端与供应商 SDK 的直接耦合。后端仍可能依赖专有规则和接口，这些依赖也要列入迁移与审计清单。

反过来，若团队只有一两个人，功能是登录、资料、少量文件和实时状态，BaaS 可能比自建后端安全。前提是权限规则认真写，备份和费用认真看。工具替你省掉机器维护，省不掉权限设计。

## 小程序直连 BaaS 的边界

小程序可以调用云开发、Firebase、Supabase 或自己的 API。选择直连 BaaS 时，要先确认小程序运行环境是否支持对应 SDK，网络域名是否能配置，文件上传和实时监听是否稳定。很多 Web 示例直接复制到小程序里会失败，因为小程序没有完整浏览器环境。

更稳的方式是把关键写入放在自己的后端或云函数后面。小程序请求后端，后端再调用数据库、存储和第三方服务。这样可以集中处理权限、审计、密钥和兼容。读取公开配置或低风险数据时，可以让小程序直接读受限接口，但规则必须能独立挡住越权请求。

小程序审核也会影响发布节奏。后端字段改变后，线上小程序可能还停在旧版本。体验版、审核版和正式版同时存在时，后端要能识别客户端版本并保持兼容。测试环境的 BaaS 项目不要和正式环境混用，否则审核测试可能写入真实用户数据。

若使用微信云开发，也要分清云函数、数据库、存储和调用权限。云函数里可以放服务端逻辑，数据库权限仍要按集合和用户检查。开发者工具里能跑通，只说明本地调试通过。上线后还要用体验版账号和真实网络走一遍登录、写入、上传和删除。

## 本章验收清单

能说清 BaaS 替你运行了哪些组件，哪些责任仍在项目方。能区分 Supabase 的 PostgreSQL 与 RLS、Firebase 的文档模型与 Security Rules。认证和数据权限分别测试。实时监听、函数重试、存储、短信和 AI 调用都有费用边界。备份、恢复、导出和退出计划按组件列出。

AI 可以帮你整理数据模型、规则测试矩阵和费用风险表。不要把服务角色 Key、Firebase Admin 凭据、真实用户导出和生产规则控制权交给它。上线前用多个测试账号、目标客户端和真实规则跑权限测试。下一章比较托管方案、自建方案和平台依赖。
