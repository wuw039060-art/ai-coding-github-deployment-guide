# GitHub 账号、公开仓库、私有仓库和网页上传

GitHub 网页可以直接创建仓库、编辑文本和上传少量文件。它适合第一次认识仓库，也适合在没有本地工具时修改说明。项目进入日常开发后，GitHub Desktop 或 Git 命令更容易检查大量变化。

这一章只走最短网页路线。界面名称依据 2026 年 8 月 5 日检索的 GitHub 官方说明。GitHub 可能调整菜单，封版时还会复核。遇到文字略有不同，应根据对象名称和预期结果判断，不要只认按钮颜色。

## 账号是所有权与操作身份

个人账号代表一个登录身份。你可以在自己的账号下创建仓库，也可以加入 Organization，也就是组织。组织用于让多人和团队共同管理项目。仓库所有者会出现在 URL 中。`github.com/owner/repository` 里的 `owner` 可以是个人账号，也可以是组织。创建仓库前先确认 Owner 下拉项，避免把工作项目放进个人账号，或把练习仓库放进正式组织。

账号应开启强密码和两步验证。恢复码要保存在安全位置。不要把个人访问令牌写进 README、`.env.example` 的真实值或教程截图。浏览器登录状态也不能证明仓库一定属于当前人，要读页面中的所有者名称。GitHub 的显示名称可以与登录用户名不同。别人添加协作者或查看仓库地址时，通常使用用户名或组织名。交接资料应记录稳定的仓库 URL，不只写昵称。

Public repository 译为公开仓库。互联网上的人通常可以查看其代码、提交历史和公开协作内容。Private repository 译为私有仓库，只有获得权限的账户可以访问。可见性选择会影响代码和历史，不等于给内容加上适合公开使用的许可证。公开可读不自动允许他人随意复制、修改和分发。第十章会说明许可证的作用。

私有仓库也不能保存真实秘密。协作者、自动化工具和授权应用可能读取内容，仓库还可能在以后被误设为公开。密钥应放在专门的秘密或环境变量系统中。若密钥曾经提交，即使很快删除，历史中仍可能保留。第十二章会处理这种事故。

仓库可见性与部署可见性分开。私有仓库可以构建出公开网站。公开仓库也可以部署到需要登录的内部系统。改变仓库可见性前，要查看 Pages、Actions、Fork、规则和组织政策可能受到的影响，以当日官方提示为准。

## 创建一个练习仓库

前置条件是一台能访问 GitHub 的浏览器和已登录账号。练习不要包含工作资料、个人信息或密钥。打开 GitHub，新建 Repository。选择正确 Owner，仓库名称可以写 `github-practice`。说明字段可写一句用途，例如“GitHub 网页操作练习”。

选择 Public 或 Private。只想自己练习时，Private 可以减少意外公开，但它仍不是秘密存储。随后勾选添加 README。暂时不需要添加 `.gitignore` 与许可证，后面会分别练习。确认页面中的所有者、名称和可见性，再创建仓库。成功后，浏览器进入仓库首页，文件列表能看到 `README.md`，提交列表至少有一条初始化记录。

如果仓库名已存在，GitHub 会要求换名。同一所有者下不能用同一个仓库名重复创建。若页面提示组织策略阻止某种可见性，说明当前组织有额外规则，应联系组织管理员，不要改放到个人账号绕过政策。

GitHub 官方创建仓库文档会随当前界面更新，并说明初始化选项。Hello World 练习提供一条无需命令行的完整路径。

## 在网页中编辑 README

README 使用 Markdown，一种轻量标记格式。`#` 加空格可以形成标题，空行分隔段落，短横线可以形成列表。GitHub 页面能预览渲染结果。打开 `README.md`，进入编辑模式。在原说明下增加三项内容，例如项目用途、当前状态和下一步。切换到 Preview 查看格式。预览只显示将要提交的文本效果，还没有保存到仓库历史。

提交区域需要一条简短说明，例如“补充练习仓库说明”。如果界面提供直接提交到当前分支与创建新分支两种选择，单人练习可以直接提交。工作仓库应根据分支保护和审查流程选择。成功以后，README 页面出现新内容，提交历史增加一条记录。点击提交可以看到具体 Diff。若发现内容有误，再创建一个修正提交，不要为了追求“历史干净”在初学阶段重写远程历史。

网页编辑适合 README、文档和很小的配置修正。大量文件或需要本地测试的代码改动，应在本地完成。网页预览无法替你运行项目测试。

GitHub 官方的 Adding a file to a repository 说明了网页上传路径，也提醒不要提交密码和 API 密钥。页面、文件数量和大小限制可能调整，本书不把某个数值写成永久规则。超过当前限制时，GitHub 页面会提示，具体值以当日官方文档为准。

准备一个只含两份文本的文件夹，例如 `about.md` 和 `notes.txt`；进入练习仓库，选择添加文件并上传；把文件拖入指定区域，等待列表显示文件名；提交前逐个核对文件；操作系统隐藏扩展名时，`notes.txt.exe` 可能伪装成文本文件；压缩包也可能包含无关数据。网页只显示将要上传的内容，不会替你判断文件是否安全公开。

填写提交说明，例如“加入两份练习文档”。完成提交后，文件列表应出现对应文件，提交历史增加记录。打开文件，确认中文没有乱码、内容完整。若文件传错，先判断是否含秘密。普通无敏感文件可以通过后续提交删除。包含真实密钥时，单纯删除不够，应立即撤销或轮换密钥，再评估历史清理。

## 上传文件夹时要确认层级

网页拖入文件夹后，仓库中会保留相应目录层级。项目常见的“多套一层”问题也会在这里发生。假设电脑目录是 `my-site/my-site/index.html`，你把最外层拖入仓库，GitHub 顶层就可能出现名为 `my-site` 的目录，真正页面在下一层。部署工具若预期顶层有 `index.html`，就会找不到。

上传前先打开本地文件夹，找到 README 或主要配置所在层。仓库首页期望显示哪些顶层文件，就从那一层选择。已经上传错层时，少量文件可以在清楚历史的前提下重新整理。完整项目更适合本地移动后用 GitHub Desktop提交，以便一次查看全部 Diff。

文件名大小写也要统一。Windows 可能把 `Logo.png` 与 `logo.png` 当作同一名称，GitHub 和 Linux 部署环境会区分。网页链接中的路径必须与仓库文件名完全一致。

新仓库准备设为公开，至少搜索以下内容。

- `.env` 与其他环境配置文件
- 名称含 key、secret、token、password 或 credential 的文件
- SSH 私钥和签名文件
- 数据库导出、用户列表与日志
- 身份证件、合同、内部地址和个人照片
- 第三方素材与字体的授权状态

搜索文件名只是第一步。密钥也可能写在源码或提交历史中。GitHub 的秘密扫描与 Push protection 能帮助发现支持类型的秘密，不能覆盖所有自定义凭据。人工 Diff 仍然必要；把真实值换成示例时，要确保示例无法使用；可以写 `YOUR_API_KEY` 或 `[REDACTED_SECRET]`。不要保留真实值的开头和结尾来展示格式，因为部分凭据本身较短，组合其他信息仍可能被滥用。

公开还涉及版权。自己写的代码与说明可以选择许可证。第三方代码、图片、图标和字体要遵守原授权。没有来源的信息不能因为上传到自己的公开仓库就获得新许可。

## 添加协作者前确认权限需要

私有仓库要让他人访问，需要通过仓库或组织权限系统授权。邀请前确认对方的 GitHub 用户名，并通过其他渠道核对身份。显示头像和相似用户名不能替代确认。只需要查看代码的人，不应获得管理仓库和删除资源的权限。组织仓库可以使用团队集中管理。个人项目也要定期移除不再参与的人和不再使用的授权应用。

协作者接受邀请后，应从自己的账户打开准确仓库 URL。若收到 404，可能没有接受邀请、登录了错误账户，或组织要求额外身份验证。不要用把仓库改为公开的方法解决权限问题。

个人练习、作品集和单人开源项目可以放在个人账号。多人长期维护、由公司或社团拥有的项目，更适合组织。组织能够用团队分配权限，并保留资源归属。判断时问谁在成员离开后继续拥有项目，谁支付服务费用，谁负责安全事件。若答案是某个组织，仓库、域名、部署和商店资源最好使用相符的组织账户体系。

把个人仓库转移到组织会改变所有者路径，并可能影响权限、Pages、Actions、Secrets、应用授权和部署连接。GitHub 通常为旧 URL 提供重定向，不能据此假定所有外部集成都自动更新。转移前按当前官方说明列出影响，完成后逐项验证。

组织还可能要求单点登录、两步验证和仓库规则。个人能够创建公开仓库，不说明组织策略也允许。不要把正式代码复制到个人账户来避开规则。

## 可见性改变前做一次影响审查

Private 改为 Public 会让代码和历史进入公开范围。先检查所有分支、Tag、Issue、Pull Request、Actions 日志与 Release 资产。只看默认分支当前文件不够。

Public 改为 Private 会改变外部访问和部分协作能力。已有 Fork、Pages 和集成怎样处理，取决于账户类型与 GitHub 当前规则。看到确认对话框时，阅读完整提示并保存审查记录。

两种方向都要检查依赖仓库的自动部署与机器人；集成失去权限后，构建可能停止；重新授权时只给所需仓库和权限；仓库可见性无法代替应用访问控制；一个私有源码构建出的公开网页仍能被访问；一个公开前端调用的后端可以要求登录；分别验证代码、部署和数据三种边界。

练习目录包含 `index.html`、`styles.css` 和 `images/logo.png`。上传前打开 HTML，确认图片引用是 `images/logo.png`，文件名大小写一致。目录中没有 `.env`、日志或私人照片。进入正确仓库和分支，选择上传。把三个项目项连同 `images` 层级加入。待文件列表稳定后，检查顶层有 `index.html` 和 `styles.css`，子目录有图片。

提交说明写“加入静态站点初始文件”。提交后从 GitHub 文件列表逐个打开，确认中文正常、图片文件大小合理。再查看提交 Diff，确认没有额外文件。若准备使用 GitHub Pages，上传完成仍需在仓库设置中选择发布来源。本章只验证仓库内容，Pages 会在第二十四章操作。这样能避免把上传成功与网站上线混成一步。

## 网页删除与重命名也会创建提交

在 GitHub 网页删除文件会生成一次远程提交。重命名文本文件通常也会形成提交。操作前确认分支，提交后本地协作者需要 Pull。删除 README 可能让仓库首页失去说明。删除 Actions 工作流可能停止自动化。网页提示只显示当前文件，业务影响要由维护者判断。

误删普通文件时，可以从历史找到旧内容并创建恢复提交。含秘密的文件则遵循密钥事故流程，不能仅靠恢复或删除解决。

两步验证设备丢失时，需要恢复码、备用验证方式或 GitHub 官方账户恢复流程。恢复材料不要放进同一个 GitHub 仓库。组织应有至少两位经过控制的 Owner，避免一个账号失效导致管理中断。Owner 权限很高，人数和日常使用要受限制。普通协作者不需要 Owner。

个人项目也可以记录域名、部署平台和仓库的账号恢复入口。记录不含密码，只说明由谁保管恢复材料、最近验证日期和替代联系人。

## 一个公开作品仓库的发布前检查

小吴准备公开个人网站源码。仓库当前为私有，包含前端源码、README、构建配置和几张本人拍摄的图片。历史中曾出现 `.env`，后来已经删除。他先轮换 `.env` 中的旧密钥，并检查历史影响。接着确认照片版权属于自己，删除照片元数据中的不必要位置信息。README 使用无效示例地址，不展示个人手机号。

他查看全部分支和 Release，确认没有测试数据库与日志。Actions 日志没有输出秘密。许可证只覆盖自己的代码，第三方图标继续保留原许可声明。改为 Public 后，他用未登录窗口打开仓库，检查所有可见标签。网站部署仍使用自己的公开域名。最后记录公开日期和审查范围。

这个流程说明，公开前检查覆盖历史和旁边功能。只读当前文件列表，会漏掉旧提交、资产与自动化日志。

设计师只需要读取前端目录与上传图片，却被授予组织 Owner。权限远大于工作需要，账号失陷后影响整个组织。更合适的做法是通过团队授予所需仓库角色，并在项目结束后移除。客户资料放在批准的数据系统，不用仓库 Issue 传输身份证或合同。

外部部署平台只授权目标仓库。若平台应用默认请求全部仓库访问，检查是否能改为 Selected repositories。撤销集成前确认它是否仍承担部署。权限审查可以每季度列出成员、机器人、部署应用和过期邀请。仓库私有只是入口条件，谁已经获得访问仍需管理。

## 网页操作的可恢复性

网页编辑和上传会立即创建远程提交，通常可以通过后续提交恢复文件。删除仓库、转移所有权和改写安全设置的影响更大。操作前看确认对话框是否要求输入仓库名。GitHub 用这种方式降低误删，仍需要操作者核对 Owner。名字相同的个人仓库与组织仓库不能靠仓库名区分。

练习网页删除时使用专门测试仓库。正式仓库的保护规则、分支与 Release 要先备份和记录。恢复演练不应在唯一生产仓库上进行。

公开仓库首页先让读者看见用途、截图、当前状态与最短运行路径。项目仍在试验，就明确写 Experimental。需要付费服务或外部账号，也在运行前提中说明。About 区域可以添加网站与主题标签。链接要指向项目真正官网，避免让读者从同名网站下载错误文件。社交媒体账号若停止维护，应更新或移除。

README 的徽章和截图应有可访问文字。截图中不要包含令牌、真实用户和内部域名。图片较大时压缩资源，又保留能看清关键界面的分辨率。贡献入口链接 `CONTRIBUTING.md`，安全问题链接 `SECURITY.md`。普通问题去 Issue 或 Discussion。不同入口能让错误信息到达合适的人。

## 公开仓库也要限制写入

Public 允许读取，不表示任何人都能直接修改默认分支。外部贡献者通常通过 Fork 和 Pull Request 提议变化，维护者审查后合并。默认分支规则可以要求审查与检查。管理员是否能绕过、哪些账户适用，以当前 GitHub 设置为准。配置后用测试分支验证规则真的生效。

机器人令牌同样要最小权限。自动更新只需要创建 Pull Request 时，不授予删除仓库或管理组织权限。定期撤销长期未使用授权。

Fork 会在自己的账户下建立与原仓库有关联的副本，常用于没有原仓库写权限时提出改动。Template repository 用于从模板开始一个新项目，新仓库通常不保留与模板相同的提交历史关系。

下载 ZIP 又是第三种动作。它只取得某个版本的文件快照，本地没有正常 Git 历史和远程关联。想持续跟随项目更新，应 Clone。只想查看当时文件，ZIP 更简单。网页上看到相似的复制功能时，先问未来是否要向原项目贡献，是否要保留提交历史关系，是否只需一次快照。第八章和第十一章会把 Clone、Fork 与 ZIP 放在同一张表中比较。

## 仓库创建后的最小验收

创建或上传完成后，不以“页面没报错”作为唯一结果。逐项确认。

1. URL 中的所有者和仓库名正确。
2. 可见性与原计划一致。
3. 默认分支存在，最近提交说明可辨认。
4. 文件层级与本地项目根目录一致。
5. README 能说明项目用途和运行前提。
6. 没有秘密、用户数据和无授权资源。
7. 用未登录窗口检查公开仓库的真实可见范围，私有仓库则不应泄露内容。

未登录检查时，不要退出当前工作页面造成未保存内容丢失。可以使用另一个隐私窗口。私有仓库返回登录或不可访问页面属于预期结果。

GitHub 的网络可达性可能因地区、网络运营商和时间而变化。页面加载慢或下载中断时，先保留本地项目与提交，不要连续重复创建仓库。确认远程页面是否真的出现新提交，再决定重试。第三方镜像或加速服务会接触你请求的仓库内容。私有仓库、令牌和发布资产不要交给来源不明的中转服务。组织项目还要遵守所在机构的网络与数据政策。

## 常见错误

创建到错误 Owner 时，先停止上传。仓库转移会影响 URL、权限和集成，是否转移要根据归属决定。练习空仓库可以在确认无引用后重新创建，正式项目不要随意删除。仓库误设公开时，立即改回私有只能阻止后续访问，不能确认此前无人复制。若含秘密，先撤销或轮换。若含个人数据，还要按适用规则评估后续处理。

网页上传后构建不触发，先看提交进入哪个分支，以及部署平台监听哪个分支。文件已在 GitHub 不代表生产环境已经发布。

AI 可以列出创建前检查项，检查准备上传的文件名和 Git Diff，草拟 README，也能识别常见秘密文件模式。它不能保证扫描覆盖所有凭据和个人信息。让 AI 保持只读，直到你确认所有者、可见性和文件范围。不要把登录 Cookie、两步验证码、令牌或私有仓库完整内容发送给无权接触的服务。

亲自选择 Owner 与可见性，检查上传列表，确认公开范围和版权。邀请协作者、改变仓库可见性、转移或删除仓库时，核对目标账户与影响提示。下一章会安装并使用 GitHub Desktop。它把本地项目、文件变化、提交和远程同步放进同一个图形界面。
