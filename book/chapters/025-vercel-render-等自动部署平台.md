# Vercel、Render 等自动部署平台

自动部署平台把一条重复流程接到 Git 仓库。代码 Push 后，平台取得指定提交，准备环境，安装依赖，执行构建或启动命令，再把结果放到公开地址。Vercel、Render 和 Cloudflare Pages 都提供这种能力，擅长的工作负载并不完全相同。

平台减少了手工上传，却没有替你理解项目。命令填错、端口没有监听、数据写在临时磁盘或环境变量缺失，自动化只会稳定地重复错误。

## 自动部署到底自动了什么

一次部署通常包含触发、取代码、准备环境、安装、构建、发布和健康检查。每个阶段都有状态和日志。触发来源可能是生产分支 Push、合并请求、手动部署或 Deploy Hook。取代码阶段锁定提交编号；准备环境选择运行时与系统镜像；安装阶段读取清单和锁文件；构建阶段生成静态文件或编译应用；发布阶段把新版本接到网址。

静态站发布后只需要提供文件。动态服务还要启动进程、监听平台要求的端口，并持续健康运行。平台自带地址先于自定义域名验收。自带地址失败时，问题在项目或平台部署范围。自带地址成功而域名失败，才转向 DNS 和域名配置。

Vercel 与 Git 仓库集成后，生产分支提交形成生产部署，其他分支和拉取请求可形成预览部署。官方文档还允许设置根目录、框架预设、构建命令、输出目录和环境变量。导入项目时先选择仓库，再核对框架识别结果。自动识别是候选配置，不是事实。与本地成功构建对照，尤其检查 Root Directory 和 Output Directory。

首次部署完成后，部署详情页应显示提交、环境、状态和日志。打开生成的网址，检查关键页面与请求。保存部署 URL，便于后来比较。预览部署适合评审修改。合并到生产分支以后产生新的生产版本。不要把某个预览 URL 当永久正式地址，它可能与分支生命周期绑定。

## Render 的静态站与 Web Service

Render 可以创建 Static Site，也可以创建持续运行的 Web Service。静态站执行构建后发布目录，Web Service 还要执行启动命令并运行服务器。选择类型要看产物。只有 HTML、CSS、JavaScript 和图片，用 Static Site。需要 Node.js、Python 等后端进程处理请求，用 Web Service。

Render 的静态站练习要求选择仓库、分支、构建命令和发布目录，随后每次 Push 自动更新。Web Service 必须监听平台提供的端口，并绑定可接受外部连接的地址。启动日志显示服务在运行，却监听错误端口时，平台仍无法把请求送进去。

Render 当前文档说明服务默认使用临时文件系统。部署重启后，本地写入的文件可能丢失。用户上传、SQLite 数据库和业务文件不能在没有持久化设计时放进临时目录。

有些框架可以输出纯静态站，也可以使用服务端渲染。项目使用了服务端 API、动态认证回调或每次请求计算内容时，单纯静态托管可能不够。判断时不要只看框架名称。查看构建输出和启动方式。构建完成后得到一批可直接提供的文件，是静态路线。部署后还必须运行 `npm start` 一类长期进程，是服务路线。

无服务器函数位于两者之间。平台在请求到来时运行短任务，适合某些 API，不等同于任意长期服务器。执行时长、连接、区域和文件系统均受平台规则限制。

## 平台替你承担的责任

托管平台通常承担构建机器、发布入口、TLS 证书、部署历史和基础运行设施。动态服务还可能提供健康检查、日志和伸缩选项。你仍负责源代码、依赖、配置、数据、权限、秘密、业务监控和费用。平台显示绿色，只说明它的部署检查通过，不代表注册、支付和数据恢复可用。

供应商故障也可能影响网站。准备状态页、用户通知和恢复办法。重要数据要有独立备份，不能把部署历史当数据库备份。

## 一次最小导入练习

使用不含秘密的练习仓库，先在本地完成构建与预览。记录提交编号、构建命令和输出目录。在所选平台创建新项目，只授权目标仓库。选择生产分支，填写已经验证的设置。不要同时修改框架版本和配置，这会让失败原因变多。

触发部署后依次检查取代码、安装、构建和发布。成功时记录部署编号、自带 URL、实际提交和检索日期。打开自带 URL，完成首页、内部链接、刷新、窄屏、Console 和 Network 验收。修改一处无害文字，Push 到非生产分支，确认是否出现预览部署。再按项目流程合并并检查生产。

删除练习项目会使地址失效，可能影响域名。若需要清理，先确认没有绑定域名和依赖者，再按平台当前步骤操作。

取代码失败，检查仓库授权、分支和子模块。安装失败，检查包管理器、锁文件、私有包凭据与运行时版本。构建失败，查看第一段错误、工作目录和环境变量。发布失败，检查输出目录是否存在以及是否包含入口文件。

服务启动失败，检查 Start Command、监听地址、端口和运行时异常。部署成功但功能失败，转到 Runtime Log、浏览器 Network、数据库与外部 API。错误发生在哪一阶段，决定看哪份日志。连续重试相同配置不会产生新证据。

## 平台选择不靠“最流行”

静态展示页优先看构建支持、预览、域名和地区可达性。动态服务还要看运行时、长连接、后台任务、持久磁盘、数据库网络和休眠策略。个人项目也要考虑退出难度。能否导出数据，域名能否快速切换，构建是否依赖专有功能，回滚是否覆盖配置。

价格、免费额度和休眠规则变化频繁。正式决策时打开官方定价与限制页，写明查询日期和预计用量，不沿用本书截稿时数字。中国大陆访问还可能受到网络、备案、支付和节点差异影响。面向大陆公众提供服务时，应根据实际服务器位置、域名接入商和现行规定咨询官方渠道。本书不会把全球平台的默认流程写成大陆上线的完整合规答案。

开发者把一个使用 SQLite 的小应用部署成 Web Service。页面能打开，新增记录也成功。平台重新部署后，记录全部消失。构建和启动都没有错。数据写在服务的临时文件系统，新实例没有旧文件。解决方向是使用平台持久磁盘或外部数据库，并建立备份恢复，而非关闭自动部署。

这类问题说明验收要跨过重启。对有状态应用，写入测试数据后执行受控重启，再确认数据存在。只验证一次 HTTP 200 不够。

## 供应商示例怎样使用

Vite 的官方部署指南同时列出多种平台，适合核对框架产物和基础路径。平台自己的快速入门适合当前界面和字段。供应商文档对自家能力最准确，也会突出自家方案。跨平台比较要把相同需求放在一张表中，避免照搬营销描述。

社区故障案例适合发现边角问题，事实结论仍要回到当前官方文档与可复现实验。

Build Command 生成可运行内容，结束后应退出。Start Command 启动长期服务，正常情况下会持续运行。把开发命令当 Start Command，可能带热更新、详细调试和不适合生产的性能设置。使用项目提供的生产启动脚本。

静态站通常没有长期 Start Command。平台完成构建后由自己的静态服务器提供文件。动态服务的构建成功后，平台再运行 Start Command。错误日志位于不同阶段，先看命令名称与时间。

## 端口与监听地址

云平台会通过环境变量提供端口。后端应读取该值，不能固定只监听本机开发端口。监听 `127.0.0.1` 只接受容器内部本机连接，平台代理可能无法访问。许多平台要求绑定 `0.0.0.0`，具体按运行时示例配置。不要为了测试在云服务器防火墙随意开放端口。托管服务的公网入口通常由平台代理提供。

启动日志应写监听端口但不要打印秘密。平台健康检查成功后，再从自带域名访问。

健康检查用于判断新实例能否接收流量。最小端点可以验证进程存活，较深检查还可能验证关键依赖。检查过浅时，进程活着但数据库完全断开仍显示健康。检查过深时，一个非关键外部服务抖动会让所有实例反复重启。

个人项目先提供快速、无副作用的端点，返回明确状态。关键依赖另用监控检查。健康端点不能泄露版本、配置、堆栈和数据库详情。公开响应保持最少信息，详细原因进入受限日志。

## 服务休眠与冷启动

某些计划会在空闲时暂停服务，下一次请求需要等待启动。是否存在、等待多久和适用计划会变化。访问慢不一定是代码性能问题。对照部署平台事件和实例启动日志，判断是否冷启动。需要稳定响应的业务应按当前官方计划评估资源和费用，不把免费层当生产保证。

定时向服务发请求来规避平台规则可能违反条款，也掩盖真正需求。选择符合使用模式的计划或架构。

应用把上传图片写到 `uploads`，同一实例马上能读。新部署创建另一个实例，目录为空。多实例时，用户随后请求甚至可能落到没有该文件的实例。生成缩略图、临时报表和缓存可以使用临时目录，前提是内容可重建且有空间清理。业务唯一副本不行。

SQLite 是单个文件数据库，放在临时盘会随实例消失。放在持久盘又涉及单实例、备份与并发限制。适合项目的数据服务应根据一致性、备份和地区选择。第五卷会细讲托管数据库与对象存储。

## 后台任务和定时任务

Web 请求应在平台时限内完成。发大量邮件、视频转码和长时间 AI 任务可能需要后台 Worker 或队列。把长任务直接放在请求处理里，用户断开后任务可能继续、被中止或重复。平台重启也会丢失内存队列。

选平台前列出是否需要 Worker、Cron、队列与长连接。静态部署页面看不到这些要求。任务服务必须记录任务 ID、状态、重试和结果。升级部署时确认在途任务怎样处理。

平台需要读取仓库，可能还会向提交或拉取请求写部署状态。只授权目标组织与仓库。构建过程能读取注入的环境变量。陌生分支和未审查 Pull Request 不应获得生产秘密。团队离职或账号被盗时，要能撤销仓库 App、平台成员和部署令牌。只改 GitHub 密码不能覆盖所有平台会话。

每季度查看平台成员、GitHub App 和 Deploy Hook。删除不再使用的入口前记录用途和最后调用。

## Deploy Hook 的风险

Deploy Hook 是一个特殊 URL，请求它即可触发部署。适合内容系统通知平台重建，也可能被泄露后反复调用。把 Hook 当作秘密，不放进前端和公开仓库。平台日志应能看到触发时间与结果。

泄露时生成新 Hook 或按平台方式撤销旧值。仅隐藏网页上的链接不能撤回已经复制的 URL。频繁异常部署时，检查 Hook 调用方、Git 推送和自动更新工具，找出真实触发源。

| 需求 | 静态站 | 动态 Web Service |
| --- | --- | --- |
| 提供 HTML、CSS、图片 | 适合 | 可以但通常多余 |
| 每次请求运行服务端代码 | 不适合纯静态 | 适合 |
| 保存用户上传到本地目录 | 不应 | 仍需持久化设计 |
| 后台长任务 | 不适合 | 可能还需 Worker |
| 数据库 | 调用外部 API | 服务端安全连接 |
| 平台管理进程与端口 | 无长期进程 | 需要 |

表格只做第一轮筛选。框架的无服务器函数、边缘运行时和混合渲染还要查平台当前能力。

## 一次跨平台迁移预演

迁移前列出 Git 仓库、构建命令、启动命令、变量名称、域名、数据与后台任务。先在新平台使用测试变量部署。用新平台自带地址验证，不急着切 DNS。动态服务要测试重启、写入、上传和外部回调。

记录新旧平台不等价能力。例如旧平台有持久磁盘，新平台默认没有。迁移计划要补上外部存储。最终切域名时保留旧服务观察期。确认日志、错误率和数据一致后，再按清单下线。

出现大面积失败时查看供应商官方状态页。状态正常不表示单个账号或区域没有问题，仍要保存自己的日志。状态页报告事故时，记录开始、更新和恢复时间。对照自己的第一条错误，判断是否相关。不要在事故期间反复改配置。若供应商明确故障，额外变化会增加恢复后的排错难度。

业务需要更高可用时，再评估多区域或多供应商。个人项目先把备份、域名切换和恢复文档做好。

## 区域与外部服务距离

动态服务所在区域会影响用户延迟，也影响它连接数据库和对象存储的距离。应用与数据库跨洲，每次查询都会增加等待。优先让频繁通信的服务靠近，再考虑用户入口的 CDN。不要只按自己家里测速选择区域。

迁移区域可能涉及新实例、数据复制、IP 和停机。上线前确定默认区域，后续变化按迁移处理。数据驻留还有合规与合同要求。涉及个人信息时不能仅凭延迟做决定。

日志应包含时间、等级、服务版本、请求 ID 和简洁事件。错误记录异常类型与堆栈，避免只写“失败”。不要打印密码、Cookie、完整 Token、银行卡和用户上传正文。需要关联用户时使用内部 ID，并控制访问。

部署后用版本字段确认流量进入新实例。多个实例日志混在一起时，实例 ID 可以帮助发现只在一台发生的问题。平台日志保留期可能有限。关键审计和业务事件需要单独的合规存储方案。

## 费用告警从第一天开始

自动部署会消耗构建资源，爬虫和异常请求会消耗流量与函数执行。个人小站也可能因误配置产生费用。创建项目时查看官方计费维度，设置预算或用量告警。测试 Webhook 时避免循环触发部署。账单突然增长，先按服务、日期和用量类型拆分。不要立即删除生产资源，先限制异常入口并保存证据。

价格数字只在决策记录写查询日期。项目每季度重新估算真实用量。

交接文档列仓库、生产分支、平台项目、服务类型、区域、构建与启动命令、环境变量名称、域名和数据位置。再列部署、回滚、备份、费用告警和状态页入口。秘密只说明存放位置和负责人。让另一位维护者按文档找到最新日志并完成一次预览部署。只有作者自己会操作，说明文档还不够。

离开平台时用同一清单导出数据、撤销权限和移除域名，减少遗留资源。

## 什么算本章完成

能根据产物选择 Static Site 或 Web Service，正确区分 Build 与 Start Command。动态服务读取平台端口并通过健康检查。用户数据不写入无保障临时盘，后台任务和定时任务有明确去处。部署平台的仓库权限与秘密范围经过确认。

最后用平台地址走完关键路径，受控重启后再次验证。绿灯和首页 200 只能算其中两项证据。

开发者有一个前端页面和一个 Node.js API。前端构建成静态文件，API 根据编号查询数据库。把整个仓库建成 Static Site 后，页面能开，`/api/query` 永远 404。正确拆分是一项静态站和一项 Web Service。前端环境变量指向 API 自带地址，API 使用服务端数据库连接。两项都从同一仓库的不同根目录构建。

API 首次部署显示进程启动，平台健康检查仍失败。日志显示它固定监听 `localhost:3000`，没有读取平台提供端口。按当前 Render 运行时说明修改后，健康检查通过。开发者又把查询缓存写到本地文件。受控重启后缓存消失，但数据仍可从数据库重建，这符合设计。用户预约本身从未放进临时盘。

最后记录前端与 API 的部署 ID、区域、变量名称、健康端点和重启结果。前端成功与 API 成功分别验收，避免一个绿灯覆盖另一项故障。这个小系统已经有两个可独立失败的服务。下一卷加入数据库后，日志与备份责任会继续增加。

## 自动部署建议要核对平台责任

AI 可以从项目结构推断候选服务类型，比较三家平台需要的字段，解释部署日志，并生成上线验收表。它不能根据“这是 React 项目”就确定静态或服务端路线。让它引用构建配置、脚本和产物证据。

亲自检查仓库授权、生产分支、环境变量、持久数据位置和费用告警。动态服务部署后完成一次受控重启和数据验证。下一章会逐项解释 Build Command、Output Directory 和环境变量。它们是自动部署中最常填错的三个位置。
