# 软件包、进程、端口、磁盘和内存

服务器排错时，先别急着改代码。网站打不开，可能是软件没装好，进程没启动，端口没监听，防火墙没放行，磁盘满了，内存被耗尽，或外部网络出问题。把现象放回这些层级，排错会安静很多。

## 软件包和来源

软件包是系统安装和更新软件的单位。Debian 和 Ubuntu 常用 `apt`。安装前先确认软件来源。官方源、发行版仓库、供应商仓库和陌生脚本的可信度不同。生产服务器上尽量少用来历不明的一键安装。

安装软件会带来依赖。卸载软件也可能影响依赖。执行安装、卸载和升级前，读一眼工具提示。它会列出将新增、删除或升级哪些包。看到数据库、反向代理、系统运行时和安全组件时，不要随手确认。

系统更新后可能需要重启。内核、安全库和底层服务更新后，旧进程仍可能加载旧版本。用平台建议、系统提示和维护窗口来安排重启。重启前确认服务会自动启动，备份和告警正常。

## 进程和端口

进程是正在运行的程序实例。`ps`、`top`、`htop` 可以看进程。一个应用有文件，不代表它正在运行。一个进程存在，也不代表网站可用。它可能监听错地址，连不上数据库，或内部已经报错。

端口是服务等待连接的位置。在常见 Linux 系统上，`ss -lntp` 可以看 TCP 监听，部分进程信息需要相应权限才能显示。监听 `127.0.0.1` 表示只接受本机 IPv4 连接。监听 `0.0.0.0` 表示所有 IPv4 网卡都有可能接入，最终能否从公网到达还取决于安全组、系统防火墙和路由。应用只给同机反向代理访问时，通常监听本机地址即可。若开发端口可从公网直连，用户可能绕过代理配置的 HTTPS、限流或访问控制；应用本身仍须独立做好鉴权。

在服务器内部测试应用，先用 `curl` 请求应用实际监听的本机地址。若应用本机可访问，外部不可访问，再分别验证反向代理本机入口、主机防火墙、云防火墙和域名解析。若本机也不可访问，再看进程、端口、日志和配置。不要一上来就改 DNS。

## 防火墙是两道门

云平台安全组和主机防火墙是两道门。安全组在平台层，主机防火墙在系统里。两边都要允许，请求才可能进来。只改一边，经常看不到效果。SSH、HTTP 和 HTTPS 是最常见入口，其他端口要按业务逐项说明。

端口扫描只能在授权范围内进行。扫描自己的练习机可以帮助确认暴露面。扫描别人的机器或公司网络可能违反规则。生产环境更推荐从资产清单和防火墙规则开始，而不是拿扫描结果猜业务。

连接数也会耗尽资源。数据库连接池过大、爬虫大量访问、WebSocket 不关闭，都可能让服务看起来随机失败。排查时看进程数量、连接状态和日志时间线。只盯 CPU，容易漏掉连接耗尽。

## 磁盘和内存

磁盘满会让很多事情失败。写日志失败，上传失败，数据库无法写入，容器无法启动。`df -h` 看空间，`du` 看目录占用。还有一种情况是 inode 用完。空间看起来没满，但小文件太多，也会写不进去。用 `df -i` 检查。

删除日志后空间不释放，可能是进程仍打开旧文件。确认哪个进程持有文件，再按服务支持的方式重新打开日志，必要时安排重启，等最后一个引用关闭后空间才会释放。不要为了腾空间随手重启数据库或清空仍在使用的日志。还要问它为什么变大，是否缺少日志轮转，是否有异常请求。

内存不足时，系统可能触发 OOM，把某个进程杀掉。日志里会留下线索。应用突然消失、容器重启、数据库断连，都可能与内存有关。先看系统日志、进程内存和容器限制，再决定是否扩容或修代码。

## 一个排错顺序

用户说网站打不开。先从外部请求拿到状态。超时、连接拒绝、502、404 和证书错误，对应方向不同。然后登录服务器，确认进程是否在，端口是否监听，本机请求是否正常。再看反向代理日志、应用日志和系统日志。

若磁盘满，先止损。找出增长最快的目录，判断能否安全清理。日志可以轮转和压缩，构建缓存可以清理，上传文件和数据库文件不能随意删。清理后补告警和保留策略。只把空间腾出来，不处理增长原因，事故会回来。

资源指标也有测量成本。监控越细，采集、保存和查询的开销越大。个人项目可以先看 CPU、内存、磁盘、网络、进程状态和 HTTP 可用性。等业务变复杂，再加更细的指标。

## 进程用户和监听地址

进程是谁启动的，决定它能读写哪些文件，也决定事故影响范围。Web 应用用普通用户运行，数据库用数据库用户运行，反向代理用自己的服务用户运行。若所有进程都由 root 启动，权限问题少了，安全边界也薄了。

监听地址要和入口设计一致。开发框架常默认监听 `localhost`。这适合被反向代理转发。若你希望局域网或公网直接访问，才需要监听其他地址。生产项目通常让应用监听本机，再由 Caddy 或 Nginx 对公网提供 HTTPS。

端口冲突时，不要马上换随机端口。先查占用者。它可能是旧版本服务，也可能是数据库、测试服务或系统组件。随手换端口会让反向代理、健康检查和文档一起失效。确认旧进程可以停，再清理。

## CPU、内存和带宽

CPU 高时先找进程，再看它在做什么。构建、压缩、图片处理、AI 调用转发、数据库查询和爬虫访问都可能拉高 CPU。短暂高峰未必是事故，持续高并伴随响应变慢才需要处理。只看平均值会漏掉尖峰。

内存高要看进程占用和系统缓存。Linux 会把空闲内存用于缓存，这不一定是坏事。应用内存不断上涨、容器频繁 OOM、数据库连接过多，才是更明确的信号。扩内存前，先确认是否存在泄漏或配置过大。

带宽满时，用户会觉得页面慢、上传失败、SSH 卡顿。查看流量方向也很重要。出站流量可能来自文件下载、备份、镜像拉取或异常请求。入站流量可能来自上传、攻击或爬虫。费用按流量计费的平台，还要把带宽和账单一起看。

## 文件描述符和临时目录

每个进程能打开的文件和连接数量有限。连接很多时，文件描述符可能耗尽。表现为无法接受新连接、无法打开文件或日志里出现 too many open files。提高限制之前，先查连接为什么没释放，文件为什么一直打开。

`/tmp` 适合临时文件，不适合长期数据。系统重启、清理任务或容器重建都可能清掉临时目录。上传中转、图片处理和导出报表可以用临时目录，但最终结果要移动到持久位置。把用户文件长期放在 `/tmp`，迟早会丢。

排查资源问题时，先采样，不要只看单点。记录时间、命令、输出摘要和用户影响。十分钟后再看一次。资源问题往往是趋势。一次截图只能说明那一刻。

## 一个端口到代理的案例

假设用户访问域名看到 502。维护者登录服务器，发现应用进程在，日志也没有明显错误。继续查端口，应用监听在 `127.0.0.1:3001`。Nginx 配置却转发到 `127.0.0.1:3000`。代理连接不到预期后端，于是返回 502。

修复很简单，把代理配置改到正确端口，测试配置后 reload。但记录不能只写“改端口”。还要写清应用实际监听地址、代理转发地址、健康检查地址和谁负责同步。以后应用端口变更时，发布清单要提醒修改代理。

这个案例说明，进程存在、端口监听、代理配置和外部访问是四件事。每一件都要验证。AI 生成部署说明时，常会把端口写在多个地方。人要检查这些地方是否一致。

## 磁盘增长怎样查

磁盘告警发生后，先看哪个分区满。根分区、数据盘、Docker 目录和日志目录，处理方式不同。再看哪个目录增长最快。`du` 可以从大目录往小目录追。追到文件以后，判断它是日志、缓存、上传、数据库还是备份。

日志增长要找原因。某个接口反复报错，日志轮转没配置，调试级别忘了关闭，爬虫造成大量访问，都可能写爆磁盘。简单删除日志只能暂时恢复空间。修复要包含日志级别、轮转、告警和异常请求处理。

数据库增长更要谨慎。不要直接删除数据库目录里的文件。先用数据库工具查看表、索引、WAL 或 binlog 的增长。数据库空间问题常需要专门方案，比如归档、清理历史、重建索引或扩容。手工删文件可能让数据库无法启动。

## 内存事故后的复盘

OOM 发生后，先记录被杀的是哪个进程，发生时间和当时负载。若是 Web 应用，查请求量、后台任务、图片处理和内存泄漏。若是数据库，查连接数、查询、缓存配置和同机其他服务。若是容器，查容器限制和宿主机总内存。

复盘要给出一个后续动作。加监控、限制上传大小、优化查询、调低并发、拆出后台任务或扩容。只写“内存不足，已重启”，下次还是会重启。服务器会原谅一次偶发，但不会原谅同一个问题长期没人管。

## 给 AI 的资源排错材料

资源排错适合让 AI 帮你整理，但输入要有限。给它脱敏后的命令输出摘要。CPU 前几名进程，内存前几名进程，磁盘分区占用，大目录占用，监听端口，最近错误日志的几行。不要把完整访问日志和用户请求发出去。

提问时写清用户看到什么。打不开，变慢，上传失败，还是后台任务堆积。再写你已经检查过什么。AI 看到现象、指标和检查历史，才能帮你排出下一步。只说“服务器很卡”，它只能猜。

让 AI 给出排错步骤时，要求它先列只读命令，再列可能影响服务的动作。重启服务、清理文件、扩容、改连接池都属于有影响动作。每个动作应说明预期效果和风险。没有风险说明的建议，先不要执行。

资源问题处理后，把结果回填给 AI，让它帮你写复盘。复盘包括影响、原因、止损、修复和预防。这个过程能把一次故障变成后续自动化和监控的材料。


## 常见误区

第一个误区是看到 CPU 高就扩容。CPU 高可能来自正常构建，也可能来自死循环、慢查询、爬虫、压缩任务或攻击。扩容前先确认谁在用，持续多久，用户是否受影响。

第二个误区是只清理最大文件。最大文件可能是数据库文件、上传文件或仍被进程打开的日志。删错文件会造成更大事故。先判断文件性质，再决定压缩、轮转、迁移、扩容或删除。

第三个误区是把端口开放当成连通。端口开着，不代表应用处理正常。应用可能返回 500，可能连不上数据库，也可能权限失败。端口检查只是入口检查，不是业务验收。
