# 第一次使用 SSH 登录服务器

你买到一台 VPS 后，第一件事通常是确认自己真的能安全登录。部署网站可以稍后再做。SSH 是远程进入服务器的常用方式。它把你的电脑和服务器连起来，让你在本地终端里执行服务器上的命令。第一次连通以后，先记录清楚登录方式、主机信息和失败线索。后面很多排错都从这张记录开始。

## 连接需要哪些信息

SSH 连接至少需要四样信息。服务器地址，登录用户，端口，认证方式。地址可能是公网 IP，也可能是域名。用户常见为 `root`、`ubuntu`、`debian` 或云平台创建的普通用户。端口默认是 `22`。认证方式可能是密码，也可能是私钥。

命令通常长这样。`ssh user@server_ip`。若端口不是默认值，就加 `-p 端口号`。若使用私钥，就加 `-i 私钥路径`。这些参数不要凭记忆乱试。云控制台、购买邮件和实例详情页会写明登录用户、地址和密钥说明。

Windows 可以用 PowerShell 或 Windows Terminal。macOS 和 Linux 可以用 Terminal。路径里有空格时，把私钥路径放进引号里。第一次练习时，最好把命令写进项目的运维记录。以后换电脑或交接给别人，不必重新翻购买邮件。

## 第一次连接的主机确认

第一次连接一台新服务器时，SSH 会提示你确认主机指纹。这一步是在问你，是否信任这台远端机器。练习服务器可以对照云控制台提供的指纹。若平台没有直接展示，至少确认 IP 来自你刚创建的实例，不要在来源不明的地址上输入密码。

确认后，SSH 会把主机信息写入本机的 `known_hosts`。以后同一个地址的指纹变化，客户端会警告。这可能是服务器重装，也可能是你连错机器，也可能是中间人攻击。不要看到警告就删记录。先回到云控制台确认实例是否重建、IP 是否换绑、DNS 是否指向正确。

成功登录后，先看提示符。它会告诉你当前用户和主机名。再运行 `pwd`、`whoami`、`hostname` 和 `uname -a`。这些命令不会改变系统状态，只是确认你在哪里。很多新手事故都来自把生产服务器当练习机，把本地终端当远程终端。

## 密码、私钥和权限

密码登录简单，但容易被暴力尝试。私钥登录更常见。私钥保存在你的电脑上，公钥放在服务器的 `authorized_keys` 里。私钥文件要保护好，不要发进聊天记录、提交到仓库或交给 AI。丢失私钥时，用云控制台的救援入口或重置密钥功能处理。

私钥权限过宽时，SSH 可能拒绝使用它。macOS 和 Linux 上常用 `chmod 600 私钥文件`。Windows 上则要检查文件属性和用户访问权限。不要为了省事把私钥复制到多个陌生目录。钥匙越散，泄露时越难收回来。

`root` 用户权力最大。第一次能用 `root` 登录，不代表以后都应该用它。正式服务器建议创建普通用户，把必要管理操作交给 `sudo`。这样命令历史、权限范围和误操作影响都更清楚。创建用户前先确认云平台是否已经提供默认普通用户，有的平台默认就不让 root 直接登录。

## 三类连接失败

连接失败先分三类。第一类是网络到不了。表现为超时。检查 IP、端口、云防火墙、主机防火墙和本地网络。第二类是认证失败。表现为密码错误、密钥不接受或用户不存在。检查用户名、私钥、公钥和文件权限。第三类是主机确认失败。表现为指纹警告。检查实例是否重装、DNS 是否改变。

不要反复重试同一个错误。连续错误登录可能触发安全策略，把你的 IP 临时封掉。把每次失败记录成一行。时间、命令、服务器地址、端口、用户名、错误原文和你已经检查过的地方。排错时，错误原文比“连不上”有用得多。

云平台控制台是兜底工具。SSH 断了，不等于服务器彻底没救。控制台通常能看电源状态、CPU、内存、磁盘、网络、安全组和重装记录。有的平台提供网页终端或救援模式。它们适合恢复 SSH 配置、查看防火墙和修复磁盘占满，不适合长期当主要登录方式。

## SSH 配置减少重复输入

经常登录同一台机器时，可以写本机的 SSH 配置。配置里保存别名、地址、用户、端口和私钥路径。以后运行 `ssh my-server` 即可。配置文件只放连接信息，不放密码和秘密。多人协作时，可以共享一份脱敏模板，让每个人填自己的私钥路径。

修改服务器 SSH 端口能减少低级扫描噪声，但不能代替密钥、强密码、防火墙和日志监控。若要改端口，先在云防火墙放行新端口，保持旧连接不断开，另开一个终端测试新端口能登录，再关闭旧端口。先断开再改，容易把自己锁在门外。

端口转发是 SSH 的高级用法。它可以把远端内部服务临时映射到本机，方便调试数据库、后台页面或内网接口。只在授权范围内使用。不要把内部管理端口随手转发给公网，也不要长期依赖个人电脑上的转发支撑生产功能。

## Windows 上的几个细节

Windows 用户常在两处卡住。第一处是私钥路径。下载到桌面或下载目录后，路径里可能有空格和中文。命令行里要用引号包住路径。第二处是终端差异。PowerShell、Windows Terminal 和旧命令提示符对引号、换行和复制粘贴的处理不完全一样。遇到奇怪报错，先换到 PowerShell 或 Windows Terminal。

Windows 的 OpenSSH 已经能完成大多数任务。若你使用 PuTTY，也可以，但密钥格式和配置位置会不同。团队文档里要写清使用哪种工具。不要一半人用 OpenSSH，一半人用 PuTTY，却共享同一条不兼容的命令。

复制命令时注意隐藏字符。网页和聊天软件可能把普通短横线变成别的符号，也可能把空格变成不可见字符。命令报参数错误时，手打一遍关键部分常常比继续复制更快。

## ssh-copy-id 和授权文件

`ssh-copy-id` 可以把本机公钥追加到服务器的授权文件。它适合已经能用密码登录或已有临时入口的场景。若服务器只允许密钥登录，而你还没有任何可用密钥，就需要通过云控制台、镜像初始化或救援模式放入公钥。

授权文件通常在用户家目录的 `.ssh/authorized_keys`。每一行是一把公钥。删除公钥前，先确认它属于谁、是否还有人在用、是否有替代登录方式。误删唯一公钥后，SSH 会被锁住，只能回到云平台救援入口。

多人协作时，不要共用一把私钥。每个人使用自己的公钥，离开项目时删除对应公钥。这样既能减少泄露影响，也能在日志里更容易判断是谁登录。共享私钥看似简单，后面会把责任和风险搅在一起。

## 连接慢和会话中断

SSH 能连上但很慢，可能是网络线路、DNS 反查、服务器负载或本地代理造成的。先记录从哪里连、连到哪个区域、延迟大约多少。若云平台有监控，看看 CPU、内存和网络是否异常。只因为慢就改 SSH 配置，可能掩盖真实的服务器负载问题。

会话中断也要分清原因。你的电脑睡眠、本地网络切换、服务器重启、云平台网络抖动和防火墙策略改变，表现都可能是断开。长时间任务不要直接挂在 SSH 会话里运行。可以用 systemd、任务队列、CI 或终端复用工具管理。即便使用终端复用，也要知道任务日志在哪里。

若登录后要执行危险操作，先确认机器身份。看主机名、内网 IP、当前目录和 Git 分支。生产、预览和练习机最好有明显不同的提示符或登录欢迎信息。人在深夜复制命令时，机器名字比意志力更可靠。

## 第一次登录后的记录卡

第一次登录完成后，写一张记录卡。实例名称、云平台、区域、公网 IP、登录用户、端口、认证方式、主机名、系统版本、创建时间和负责人。再补一行救援入口在哪里。记录不要包含私钥、密码和完整 Token。

随后做三件小事。确认普通用户和 `sudo` 是否可用。确认系统版本和更新状态。确认云防火墙和主机防火墙没有放开多余端口。不要刚登录就复制网上的一键脚本。脚本会改用户、服务、端口、软件源和防火墙。你还没认识这台机器时，最好别让陌生脚本替你做决定。

## 一次锁门事故

某个项目把 SSH 端口从 22 改到 2222。维护者先改了服务器配置，又重启了 SSH 服务，随后才想起来云安全组没有放行 2222。旧连接断开后，新端口进不去，22 也被配置关闭。最后只能通过云平台救援控制台进入系统，改回配置。

这类事故的教训很直接。改远程入口时，当前连接保持不断开。先放行新规则，再让服务监听新端口。另开终端测试新端口。测试成功后，再关闭旧端口。每一步只改一个条件，失败时知道退回哪里。

还要把救援入口提前找出来。不同云平台叫法不同，常见名称包括网页控制台、串行控制台和救援模式。第一次购买服务器时，就应该知道它在哪里。事故当天再找入口，会把简单问题拖成长时间中断。

## 多台服务器的命名

服务器多起来后，命名会救命。`prod-web-01`、`staging-web-01`、`lab-docker-01` 这类名字，比随机主机名清楚。登录提示符里也可以显示环境。生产机器使用醒目的主机名，练习机使用另一套命名，能减少误操作。

SSH 配置里的别名也要清楚。不要把生产服务器叫 `test`，也不要把临时服务器叫 `prod2`。别名会进入肌肉记忆。一次命名偷懒，后面每次登录都可能埋一个小坑。

团队记录里写明机器用途。它负责 Web，还是数据库，还是练习。能否重装，是否有用户数据，谁可以操作。服务器是资源，也是责任对象。没有用途说明的机器，很容易变成没人敢删、也没人维护的灰色资产。

## 登录后的安全验收

第一次登录后的验收可以列成固定动作。确认系统时间正常。确认包管理器能更新索引。确认默认开放端口。确认 root 登录策略。确认普通管理员账号可用。确认 SSH 密钥归属。确认云平台安全组和主机防火墙一致。

这些动作大多是只读检查，不会改变业务。它们适合交给新成员练习，也适合作为 AI 生成服务器初始化脚本前的人工清单。脚本可以帮你执行，验收仍要由人看结果。

## 让 AI 帮你排 SSH 问题

问 AI 前先整理脱敏材料。操作系统，终端类型，SSH 命令去掉真实 IP 和用户名后的形状，错误原文，云平台安全组是否放行，主机是否刚重装。材料越具体，AI 越可能给出有用判断。

不要把私钥内容、密码、完整公网 IP、云账号截图和安全组全量规则发给 AI。你可以把 IP 改成 `server_ip`，把用户名改成 `user`，把路径改成 `key_path`。错误信息中的指纹也可以只保留开头几位和变化描述。

AI 给出命令后，先判断命令会读什么、改什么。只读命令可以先执行，改配置和删文件的命令要谨慎。涉及 SSH 配置、防火墙和云安全组时，一次只改一处，并保持现有连接不断开。

排查结束后，把脱敏过程写成项目知识。下次出现同类错误，可以直接复用这份记录。AI 很适合帮你整理错误分类，但最终服务器能不能继续登录，要靠你自己验证。

## 本章练习

准备一台可以随时重建的测试服务器。先用云平台提供的默认方式登录。登录后记录用户名、主机名、系统版本和公网 IP。退出后再登录一次，确认记录可用。

随后创建 SSH 配置别名。用别名登录成功后，把原始长命令和别名命令都写进练习记录。再故意使用错误用户名登录一次，保存错误原文。最后回到正确配置，确认仍能登录。

练习结束前，找到云平台救援入口。只记录入口位置，不做危险操作。这样以后 SSH 配置出问题时，你知道还有哪条路能回到机器上。

## 常见误区

第一个误区是把 SSH 当成网站是否正常的证明。SSH 能登录，只说明远程管理入口可用。网站是否可用，还要看进程、端口、代理、域名和 HTTPS。很多服务器能登录，用户仍然打不开页面。

第二个误区是把云控制台当成日常终端。控制台适合救援和确认状态，日常操作仍应使用 SSH、受控脚本和发布流程。长期在网页终端里临时改配置，记录会散，交接也困难。

第三个误区是把第一次能连上当作以后都没问题。IP 可能换，密钥可能丢，安全组可能改，DNS 可能指错。登录记录和救援入口要随项目维护，不是一开始写一次就结束。

## 本章交付物

本章结束时，你应该留下三份东西。第一份是脱敏登录记录，包含地址形状、用户、端口、认证方式和救援入口。第二份是 SSH 配置别名。第三份是一次失败登录的错误记录。

这三份东西能让你以后排错有起点。它们不包含秘密，却能说明怎样进入机器、怎样确认机器身份、怎样处理连接失败。服务器管理从这里开始。

AI 可以帮你解释 SSH 错误、整理登录记录和生成排错清单。不要把私钥、密码、完整 IP 白名单、云控制台登录信息和生产日志原文交给它。下一章继续看 Linux 文件、目录、用户和权限。
