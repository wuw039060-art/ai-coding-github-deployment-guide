# Preview、Production、部署日志和回滚

部署平台通常保留一串版本。每个版本对应一次提交、一次构建和一个可访问结果。理解这条时间线，才能在新版本故障时停止扩大影响，并知道回滚能恢复什么。Preview 用于检查候选改动，Production 面向正式流量。部署日志记录平台做了什么，运行日志记录程序启动后发生什么。回滚把流量重新指向旧版本，但不会让所有外部数据回到过去。

## 部署是带身份的一次结果

每次部署至少记录提交编号、分支、触发者、开始时间、环境、构建状态和部署 URL。动态服务还记录启动与健康状态。不要只说“最新版本”。多人连续 Push 后，最新会不断改变。提交编号和部署 ID 才能明确指向一个结果。

同一提交也可能因环境变量、构建镜像、缓存或手动设置不同而产生不同结果。保留平台配置版本和构建日志，才能解释差异。发布记录应回答四个问题。发布了什么，谁触发，部署到哪里，验收证据是什么。

代码提交说明准备改变什么，持续集成说明测试与构建是否通过，部署记录说明哪个产物进入环境，验收记录说明用户路径是否可用。四项缺一，事故时都会出现猜测。只有 Git 提交，不知道是否部署；只有平台绿灯，不知道业务是否通过。

## Preview 是候选环境

预览部署通常来自非生产分支或拉取请求，拥有独立 URL。它适合检查页面、文案、构建和接口兼容。评审者可以直接打开，不必在本地搭环境。

预览不等于私密。若没有访问控制，知道 URL 的人可能打开。不要把未公开资料、真实用户数据或生产管理能力暴露在预览环境。预览应使用测试服务或最小权限凭据。若必须连接生产只读接口，也要明确限制和审计。

预览成功不保证生产成功。生产变量、域名、分支、缓存、第三方回调和访问权限都可能不同。预览验收结论要写清环境和部署 ID，不把预览 URL 当长期正式地址。

## Production 是正式环境

生产部署通常由指定分支触发，也可以手动提升经过验证的部署。正式域名指向当前生产版本。上线前核对提交、环境变量和迁移计划。上线后从真实域名完成烟雾测试，检查首页、登录、核心写入、关键外部服务和日志。

烟雾测试只验证最关键路径，不能代替完整测试，但能尽早发现域名、权限和生产配置差异。生产故障时先控制影响。暂停继续自动部署，记录当前状态，评估回滚或修复前滚。多人同时 Push 会使时间线更乱。

Queued、Building、Deploying、Ready、Failed、Canceled 等状态在平台中的含义可能略有不同。Ready 不代表所有业务依赖正常，Failed 也不一定影响仍在运行的上一版本。读取当前帮助说明，并把状态与真实请求结果配对。

## 构建日志和运行日志

构建日志覆盖取代码、安装依赖、编译和产物上传。构建失败时程序通常尚未启动。运行日志来自已启动的服务，包含请求错误、数据库连接、后台任务和崩溃。静态站大多没有应用运行日志，浏览器错误要看 Console 和 Network。

部署成功、打开页面 500，重点看运行日志。部署状态失败，重点看构建与启动阶段。DNS 无法解析时，两类日志都可能没有请求。日志中记录时间、部署 ID、请求 ID 和错误栈。提交公开问题前脱敏 Cookie、Token、个人数据和连接串。

读失败部署时，先确认失败属于哪个环境和提交。再看最后一个成功阶段，以及紧随其后的第一段失败。安装阶段出现锁文件错误，回到依赖与包管理器；构建阶段变量缺失，检查当前环境配置；发布阶段找不到目录，比较真实产物与 Output Directory；动态服务反复重启，检查 Start Command、端口、健康检查与运行时异常。

## 回滚恢复的是应用流量

典型回滚把生产流量重新指向某个旧的成功部署。它比重新构建旧提交更快，也减少依赖仓库此刻状态的变化。不同平台细节不同。有的平台使用目标部署已构建产物，有的平台回滚后会暂停自动部署或保留特殊状态。执行前看当前确认页面，记录目标部署与预期流量切换。

回滚后必须验收。打开正式域名，核对页面版本和核心功能，再查看错误率与日志。不要因为控制台显示完成就宣布恢复。还要确认自动部署开关是否符合预期，避免新提交立刻覆盖回滚，或事故后忘记恢复正常发布。

回滚适合旧版本与当前外部状态兼容，且能快速降低影响。修复前滚适合问题清楚、改动小、数据结构无法安全回退。评估因素包括影响范围、修复时间、旧版兼容、数据迁移和团队熟练程度。没有永远正确的单一选择。

## 回滚不会恢复外部状态

数据库迁移、用户写入、发送的邮件、支付事件、对象存储文件、DNS 修改和第三方配置通常不随应用版本回滚。假设新版本把数据库列改名，旧代码回滚后仍面对新结构，可能继续故障。用户在故障期间创建的订单不能简单用旧备份覆盖，否则会丢失真实写入。

因此回滚计划至少分成应用、数据库、文件、外部服务和域名五部分。能一键切流量的只有其中一部分。数据恢复需要业务判断、时间点和审计。涉及真实订单、支付、个人资料和删除请求时，必须由负责人确认。

数据库迁移分为兼容添加、数据转换和破坏性删除。新增可空列通常与旧代码兼容；把整列数据转换成新格式后，旧代码能否读取要实测；删除列或合并数据可能无法自动恢复。应用回滚前查看本次部署是否执行迁移、迁移成功到哪一步、是否已有新写入。没有这些证据时，不要直接运行所谓 down migration。

## 故障等级和决策时间

生产故障发生后，团队容易在“马上回滚”和“再等我修一下”之间拉扯。先给故障分级，比争论情绪更有用。仅影响后台样式、没有数据风险，可以给修复前滚一点时间。影响登录、支付、创建订单或数据写入，先控制入口和保护数据。涉及权限越界、个人数据泄露、重复扣款和删除错误，要立即进入事件流程。

每一级都要有决策时间。比如五分钟内确认影响范围，十分钟内决定暂停自动部署，十五分钟内选择回滚、前滚或关闭功能入口。时间用来防止团队无限等待“再看一眼日志”，不当成僵硬规则。超过时间仍无法判断，就按更保守级别处理，并把未知项写出来。

功能开关能减少回滚压力。新功能通过开关逐步开放，故障时可切回已保留并验证过的旧代码路径，不一定需要回滚整个部署。涉及写入或费用的功能，要在后端停用相应操作；只隐藏前端入口，不能阻止旧客户端或直接 API 请求。开关本身也是生产配置，要记录默认值、作用环境、负责人和清理日期。临时开关长期遗留，会让代码路径越来越难测试。发布记录中写明本次依赖哪些开关，故障时才能知道是否可以先关功能。

灰度发布和分阶段流量切换也需要证据。百分之一用户正常，不代表所有地区、账号和设备都正常。观察指标要覆盖错误率、延迟、业务转化和投诉入口。移动 App、小程序和网页混合发布时，旧客户端可能继续调用旧接口。生产发布成功后，仍要保留兼容窗口，不用新版本短暂正常来证明旧端安全。

## 发布证据链

一个最小发布记录可以这样写。提交短编号、完整部署 ID、环境、开始与完成时间、操作者、验收人和结论。截图只作为辅助，可复制的编号、URL 和日志文本更便于搜索。涉及秘密与个人数据的部分先脱敏。

故障原因未知且连续提交不断进入生产时，暂停自动部署可以固定现场。暂停后在团队渠道说明，避免有人误以为 Push 会上线。修复版经过预览与审核后再明确部署。恢复自动部署之前确认生产分支没有积压的未评审提交。事故结束忘记恢复，会造成未来修改不更新。

监控要同时看技术指标和业务指标。HTTP 错误率、延迟和实例健康是技术指标；注册完成率、订单成功率和任务积压是业务指标。回滚后技术指标恢复，业务数据仍可能卡住。观察窗口要覆盖缓存更新和后台任务，不在首页打开一次后立即宣布结束。

## 一个迁移回滚例子

假设团队发布版本 B，迁移把 `full_name` 拆成 `first_name` 与 `last_name`，随后删除旧列。新版注册流程出现严重错误，负责人准备回滚到 A。A 仍读取 `full_name`，直接切回旧应用会让所有资料页失败。应用回滚按钮可用，数据结构却已不兼容。这里用姓名字段演示结构变化，并不建议按空格自动拆分真实姓名；实际姓名形式未必符合这两个字段的假设。

团队先在后端暂停新注册写入，保留可用的只读页面。数据库负责人确认迁移备份与新写入，再决定修复前滚。后续迁移改成分阶段。先增加新列并让 B 同时写新旧字段，完成回填；确认旧版本退出、字段一致且回滚策略可行后，再发布读取新字段的 C。若回滚到只写旧列的 A，新字段会逐渐过时，因此还要准备同步或重新回填办法。观察期结束且不再需要旧列后，才安排删除。回填、双写和删除都要有独立验证，不能只按部署次数推断兼容。

他们在发布清单增加“旧应用能否读取当前数据库”，并把迁移 ID 放进部署记录。以后回滚决策不再只看应用页面。这个案例说明，回滚速度由最难恢复的外部状态决定。平台按钮只处理应用流量的一段。
