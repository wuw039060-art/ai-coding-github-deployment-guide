# Preview、Production、部署日志和回滚

部署平台通常保留一串版本。每个版本对应一次提交、一次构建和一个可访问结果。理解这条时间线，才能在新版本故障时停止扩大影响，并知道回滚能恢复什么。Preview 用于检查候选改动，Production 面向正式流量。部署日志记录平台做了什么，运行日志记录程序启动后发生什么。回滚把流量重新指向旧版本，但不会让所有外部数据回到过去。

## 部署是带身份的一次结果

每次部署至少记录提交编号、分支、触发者、开始时间、环境、构建状态和部署 URL。动态服务还记录启动与健康状态。不要只说“最新版本”。多人连续 Push 后，最新会不断改变。提交编号和部署 ID 才能明确指向一个结果。

同一提交也可能因环境变量、构建镜像或手动设置不同而产生不同结果。保留平台配置版本和构建日志，才能解释差异。发布记录应回答四个问题。发布了什么，谁触发，部署到哪里，验收证据是什么。

预览部署通常来自非生产分支或拉取请求，拥有独立 URL。Vercel Git 集成和 Cloudflare Pages Git 集成都支持这类流程。预览适合检查页面、文案、构建和接口兼容。评审者可以直接打开，不必在本地搭环境。

预览不等于私密。若没有访问控制，知道 URL 的人可能打开。不要把未公开资料、真实用户数据或生产管理能力暴露在预览环境。预览应使用测试服务或最小权限凭据。若必须连接生产只读接口，也要明确限制和审计。

## Production 是正式环境

生产部署通常由指定分支触发，也可以手动提升经过验证的部署。正式域名指向当前生产版本。上线前核对提交、环境变量和迁移计划。上线后从真实域名完成烟雾测试，检查首页、登录、核心写入、关键外部服务和日志。

烟雾测试只验证最关键路径。它不能代替完整测试，但能尽早发现域名、权限和生产配置差异。生产故障时先控制影响。暂停继续自动部署，记录当前状态，评估回滚或修复。多人同时 Push 会使时间线更乱。

构建日志覆盖取代码、安装依赖、编译和产物上传。构建失败时程序通常尚未启动。运行日志来自已启动的服务，包含请求错误、数据库连接、后台任务和崩溃。静态站大多没有应用运行日志，浏览器错误要看 Console 和 Network。

部署成功、打开页面 500，重点看运行日志。部署状态失败，重点看构建与启动阶段。DNS 无法解析时，两类日志都可能没有请求。日志中记录时间、部署 ID、请求 ID 和错误栈。提交公开问题前脱敏 Cookie、Token、个人数据和连接串。

## 怎样读一段失败部署

先确认失败属于哪个环境和提交。再看最后一个成功阶段，以及紧随其后的第一段失败。安装阶段出现锁文件错误时，回到依赖与包管理器。构建阶段出现变量缺失时，检查当前环境配置。发布阶段找不到目录时，比较真实产物与 Output Directory。

动态服务构建成功后反复重启，检查 Start Command、端口、健康检查与运行时异常。不要因为构建绿灯就忽略启动日志。把错误复制到记录中时保留上下文。单独一句 `exit code 1` 只有结果，没有原因。

典型回滚把生产流量重新指向某个旧的成功部署。它比重新构建旧提交更快，也减少依赖仓库此刻状态的变化。Render 当前回滚文档说明，它会使用目标部署已构建的产物，不重新构建。通过控制台回滚还会关闭自动部署，防止新提交立刻覆盖回滚结果。

不同平台细节不同。执行前看当前确认页面，记录目标部署与预期流量切换。回滚后必须验收。打开正式域名，核对页面版本和核心功能，再查看错误率与日志。

## 回滚不会恢复什么

数据库迁移、用户写入、发送的邮件、支付事件、对象存储文件、DNS 修改和第三方配置通常不随应用版本回滚。Render 官方也明确指出磁盘、自定义域名和重定向规则等变化不会随回滚恢复。

假设新版本把数据库列改名，旧代码回滚后仍面对新结构，可能继续故障。迁移要设计向后兼容步骤或准备单独恢复方案。用户在故障期间创建的订单不能简单用旧备份覆盖，否则会丢失真实写入。数据恢复需要业务判断、时间点和审计。

因此回滚计划至少分成应用、数据库、文件、外部服务和域名五部分。能一键切流量的只有其中一部分。

只在无真实用户的练习项目进行。先保留两个成功部署，版本页面分别显示 `A` 和 `B`。确认生产当前为 B，记录部署 ID 与网址。在平台中选择 A 作为回滚目标，阅读确认信息后执行。成功结果是正式地址显示 A，部署记录标出流量变化，错误日志没有新增异常。再检查自动部署状态是否改变。

随后按正常流程把 B 或修复版重新部署。演练记录包括操作路径、耗时、验证结果与恢复步骤。不要在生产首次学习回滚按钮。平台账号权限、确认语义和自动部署行为都应提前熟悉。

## 修复前滚还是回滚

回滚适合旧版本与当前外部状态兼容，且能快速降低影响。修复前滚适合问题清楚、改动小、数据结构无法安全回退。评估因素包括影响范围、修复时间、旧版兼容、数据迁移和团队熟练程度。没有永远正确的单一选择。

若无法确认旧版本会不会破坏新数据，先限制有风险功能或切换维护状态，再由了解数据结构的人判断。决策记录要写原因和风险，不能只写“回滚更保险”。

部署历史能回答某个错误从何时出现，与哪个提交相关。把外部监控时间线、Git 提交和平台部署对上，可以缩小范围。部署历史不是长期备份。平台可能有保留期限、账号风险和删除行为。源代码、配置文档和数据备份需要独立保存。

锁文件帮助重现依赖树。仍要保存运行时版本、平台设置和必要构建镜像信息，才能提高重建概率。

## 一个变量变更事故

维护者只修改了生产 API 地址，没有改代码。旧部署仍使用旧值，新部署使用新值。发布失败后，他回滚到旧部署，页面恢复。若平台选择的是旧构建产物，变量也可能恢复为旧构建时的值。另一些运行时变量可能仍取当前配置。不能从“回滚”二字推断环境值。

Vercel 当前文档说明变量改动只用于新部署。具体回滚与提升行为仍要按平台当前说明测试。处理时记录变量版本但不记录秘密值，可保存变更时间、操作者、作用环境和引用的秘密版本号。

部署控制台出现绿色状态时，先看这个状态具体指什么。构建成功说明源码已经生成目标产物。程序启动以后，还要确认公开域名能把请求送到这个版本。地址可以打开以后，再使用普通测试账号完成登录、读取、保存或上传。涉及数据的系统还要确认写入能够保留，权限没有放宽。

这些检查使用的材料各不相同。构建日志记录命令和产物，运行日志记录程序怎样启动，公开地址与 Network 记录说明请求是否到达，真实操作和数据库查询说明核心流程是否工作。一张首页截图只能证明当时看见了首页，无法代替登录、保存和权限检查。

第一次发布后，可以在 Preview 中做一次可控重部署。记录提交编号、构建日志、预览地址和关键功能结果，然后在不改变代码的情况下重新部署，确认结果仍然一致。若第二次依赖某个临时文件、人工操作或旧缓存才能成功，这条发布路径还不能算稳定。生产环境不用于随意实验，验证成熟以后再由账号持有人批准切换。

## 建立一条发布证据链

代码提交说明准备改变什么，持续集成说明测试与构建是否通过，部署记录说明哪个产物进入环境，验收记录说明用户路径是否可用。四项缺一，事故时都会出现猜测。只有 Git 提交，不知道是否部署。只有平台绿灯，不知道业务是否通过。

一个最小发布记录可以写成提交短编号、完整部署 ID、环境、开始与完成时间、操作者、验收人和结论。截图只作为辅助。可复制的编号、URL 和日志文本更便于搜索。涉及秘密与个人数据的部分先脱敏。

Queued 表示等待资源，Building 表示安装或构建，Deploying 表示发布或启动，Ready 表示平台检查通过，Failed 表示某阶段失败，Canceled 表示被取消。平台用词不同，读取当前帮助说明。Ready 不代表所有业务依赖正常，Failed 也不一定影响仍在运行的上一版本。

长时间排队时查看平台状态和账号配额。长时间构建时查看日志是否仍增长，避免同时触发多个重复部署。取消部署前确认它不会承担数据库迁移或其他一次性任务。发布流程不应把不可逆迁移隐藏在无人知晓的构建脚本里。

## 零停机部署的条件

平台常先启动新实例，通过健康检查后再切流量，旧实例随后停止。这可以减少连接中断。新旧版本会短暂并存，所以数据库与 API 需要兼容两个版本。先删除旧代码仍读取的列，会让旧实例在切流期间报错。

较安全的数据库变化常分阶段。先增加兼容字段，发布同时支持新旧结构的代码，完成数据迁移，再在后续版本删除旧字段。长连接、后台任务和本地会话还需要额外处理。平台宣称零停机不代表每个 WebSocket 和上传请求都不会中断。

故障原因未知且连续提交不断进入生产时，暂停自动部署可以固定现场。Render 控制台回滚会自动关闭自动部署的行为就是一项保护。暂停后在团队渠道说明，避免有人误以为 Push 会上线。记录暂停时间和恢复负责人。

修复版经过预览与审核后再明确部署。恢复自动部署之前确认生产分支没有积压的未评审提交。事故结束忘记恢复，会造成未来修改不更新。把开关状态加入收尾清单。

## 数据库迁移的回滚判断

迁移分为兼容添加、数据转换和破坏性删除；三类恢复难度不同；新增可空列通常与旧代码兼容；把整列数据转换成新格式后，旧代码能否读取要实测；删除列或合并数据可能无法自动恢复。应用回滚前查看本次部署是否执行迁移、迁移成功到哪一步、是否已有新写入。没有这些证据时，不要直接运行所谓 down migration。

数据库恢复需要备份、恢复点和业务停写策略。第五卷与第九卷会分别讲迁移和恢复演练。

纯静态站没有数据库迁移时，回滚相对简单。仍要考虑 API 版本、外部内容、缓存和域名配置。旧前端可能调用已经删除的新 API，回滚后反而无法使用。前后端分开部署时，要记录兼容矩阵。CDN 可能继续缓存新 HTML 或资源。文件使用内容哈希能降低混用，回滚后仍应从无缓存会话和不同网络检查。

如果新版本修改了搜索索引或发送了通知，这些外部动作不会因静态文件回滚而撤销。

## 故障等级与决策时间

首页完全不可用、支付错误和数据破坏需要快速控制影响。轻微排版错字可以按正常修复流程处理。提前定义等级和负责人，避免小问题仓促回滚，也避免严重故障长时间争论。决策时间不是要求忽略证据。至少确认影响、当前部署、上一个已验证版本和数据兼容。

个人项目也可以写一张短卡。发现严重故障，停止发布，保存现场，选择回滚或维护页，验收并通知用户。

1. 确认故障与当前部署时间相关。
2. 记录当前提交、部署 ID、日志和用户现象。
3. 选定明确的旧部署，确认当时验收通过。
4. 检查数据库迁移、文件写入和外部事件。
5. 确认旧版能连接当前依赖。
6. 决定是否暂停自动部署和写入。
7. 执行平台确认页面中的目标操作。
8. 从正式域名验收并观察监控。

任何一项未知都要标记。严重故障可以先限制功能，同时继续查证。

## 一份事故后的收尾单

恢复服务后保存最终时间线，说明影响用户与数据范围。撤销临时权限和维护开关。确认自动部署、环境变量和 DNS 回到预期状态。把临时修复转成可维护提交，删除只属于事故的调试输出。补充测试或监控，让同类问题更早被发现。验证回滚文档与实际按钮一致。

对用户的说明写可确认事实、影响窗口和已采取措施。不把未经证实的猜测写成原因。

演练使用测试环境和虚构数据，可以暂停复盘每一步。真实事故要先控制影响，随后补齐记录。演练应包含失败注入、回滚、再发布和数据检查。只点开回滚页面不算完成。每次平台界面重大变化后重新演练。权限不足、按钮改名和确认语义都可能在关键时刻阻塞。

演练结果写明实际耗时。恢复目标若要求十分钟，演练花了一小时，就需要改进流程或期望。

## 灰度与金丝雀发布

规模较大的系统可以先让少量流量进入新版本，观察错误后再扩大。这类方式常称灰度或金丝雀发布。它需要稳定的流量分配、版本监控和用户一致性。个人项目没有这些条件时，不要用手工 DNS 轮换模拟。

平台提供流量拆分时，先在练习环境了解会话、缓存和回滚。指标要按版本区分，否则新版本少量错误会被总量掩盖。数据库变化仍要兼容同时运行的新旧代码。灰度不能绕过数据迁移设计。

功能开关允许代码先上线，功能稍后对部分用户开启。出现问题可关闭开关，速度通常快于重新部署。开关也会增加分支组合。每个开关要有负责人、默认值、到期清理时间和监控。安全检查不能只靠前端开关隐藏按钮。后端仍要验证权限。

关闭功能只阻止新操作，已经写入的数据和外部事件仍需处理。

## 监控什么才知道恢复

HTTP 错误率、延迟和实例健康是技术指标。注册完成率、订单成功率和任务积压是业务指标。回滚后技术指标恢复，业务数据仍可能卡住。检查队列、数据库写入和第三方回调。选择少量与核心路径直接相关的指标，给出正常范围。只有服务器 CPU 图无法证明用户能付款。

观察窗口要覆盖缓存更新和后台任务，不在首页打开一次后立即宣布结束。

说明影响的功能、开始与恢复时间、用户需要采取的动作和下一次更新时间。没有确认的根因不要提前写。若数据可能受影响，告诉用户暂缓重复操作，避免重复支付或提交。后续核实后单独通知处理结果。

状态更新与内部技术日志分开，不能把堆栈和用户数据公开。事故复盘关注机制和证据，避免把复杂流程归咎于一个人按错按钮。

## 什么算本章完成

读者能从部署 ID 找到对应提交、构建日志和正式地址。能区分 Preview、Production、构建日志与运行日志。有一份经过练习的回滚清单，明确应用回滚不覆盖数据、文件、DNS 和外部事件。自动部署开关在演练后恢复到预期状态。

正式发布记录含验收结论。发生故障时先固定现场和控制影响，再选择回滚或修复前滚。

团队发布版本 B，迁移把 `full_name` 拆成 `first_name` 与 `last_name`，随后删除旧列；新版注册流程出现严重错误，负责人准备回滚到 A；A 仍读取 `full_name`；直接切回旧应用会让所有资料页失败；应用回滚按钮可用，数据结构却已不兼容；团队先关闭新注册入口，保留只读页面。数据库负责人确认迁移备份与新写入，再决定修复前滚，比盲目回滚更快。

后续迁移改成分阶段。先增加新列并让 B 同时写新旧字段，完成回填，再发布只读新字段的 C。观察期结束后才删除旧列。他们在发布清单增加“旧应用能否读取当前数据库”，并把迁移 ID放进部署记录。以后回滚决策不再只看应用页面。

这个案例说明，回滚速度由最难恢复的外部状态决定。平台按钮只处理应用流量的一段。

## 发布、回滚与版本必须指向同一提交

AI 可以把部署、提交和日志排成时间线，找出故障首次出现的版本，生成回滚前检查表，并比较旧版与数据库变更。它不能替你判断真实订单是否可以丢弃，也不能仅凭应用代码保证数据库兼容。数据恢复要由负责人确认。

亲自选择回滚目标，确认正式域名实际指向，检查核心流程和外部数据。执行前保存当前状态，执行后确认自动部署开关。下一章会把平台自带网址连接到自己的域名，并说明 DNS、HTTPS、费用和地区差异为什么需要单独核对。
