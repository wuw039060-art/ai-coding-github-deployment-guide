# 容器状态、日志、健康检查和重启策略

容器项目出问题时，先看状态，再看日志，再看健康检查和重启记录。不要第一反应就重建。重建可能暂时恢复，也可能擦掉现场线索。Docker 给了很多观察入口，关键是按顺序读。

## 先看状态

`docker ps` 看正在运行的容器。`docker ps -a` 看包括已退出在内的全部容器。状态里会显示运行时间、退出状态、端口和名称。容器反复退出，通常说明启动命令、配置、权限、端口或依赖有问题。

`docker inspect` 可以看更详细的容器信息。镜像、启动命令、环境变量、挂载、网络、重启次数和健康状态都在里面。不要把完整 inspect 结果直接发给别人。里面可能有环境变量和内部地址。

`docker events` 能观察容器生命周期。启动、停止、死亡、OOM、健康状态变化都会出现。偶发问题很难复现时，events 可以帮你把时间线接起来。它适合短时间观察，不适合替代正式监控。

## 日志能看到什么

`docker logs` 看到的是容器主进程写到标准输出和标准错误的内容。应用若把日志写进容器内部文件，docker logs 可能看不到。生产应用最好把关键日志输出到标准输出，再由平台收集。

日志会占满主机。Docker 支持设置日志大小和保留数量。Compose 里也可以声明日志限制。没有限制时，一个高频错误可能把磁盘写满。磁盘满后，应用、数据库和 Docker 自身都会开始出错。

日志内容也有安全边界。请求体、用户邮箱、手机号、Token、Cookie、数据库错误和堆栈都可能出现在日志里。给 AI 或协作者看日志前，先截取相关时间段并脱敏。日志越完整，越要谨慎。

## 健康检查

健康检查回答一个问题。这个容器是否还能提供预期服务。最简单的健康检查是访问本地 HTTP 健康接口，或执行一个轻量命令。它不应依赖昂贵外部服务，也不应改变业务数据。

健康接口不要暴露秘密。它可以返回状态、版本和必要依赖结果，不要返回环境变量、连接串、内部配置和用户数量。公开访问的健康接口更要克制。内部监控需要的细节，可以放到受保护入口。

健康检查太深也会带来问题。每几秒访问数据库、第三方 API 和 AI 服务，会制造额外负载。依赖短暂抖动时，容器可能被误判为不健康，重启反而扩大故障。检查要轻，告警要能说明原因。

## 重启策略

常见重启策略有 no、on-failure、always 和 unless-stopped。练习容器可以不用自动重启。生产 Web 服务常用 on-failure 或 unless-stopped。数据库和队列要更谨慎，先确认数据目录、恢复策略和停止流程。

自动重启能缩短中断，也能掩盖故障。应用启动后立刻崩溃，重启策略会让它反复失败。用户看到的是服务不稳定，维护者若不看重启次数和日志，可能以为只是偶发网络问题。

启动顺序也不能全靠重启。应用连不上数据库时，可以在应用层做重试，也可以用健康依赖辅助。可靠的应用要能处理依赖暂时不可用。只靠固定 sleep，机器慢一点就失败，机器快一点又浪费时间。

## 一次 502 排查

浏览器看到 502。先看反向代理日志，确认它连的是哪个容器和端口。再看容器是否运行，端口是否映射，应用是否监听正确地址。随后看 docker logs。若应用日志显示数据库连接失败，就继续查数据库容器和网络。

不要只重启所有容器。重启可能让服务暂时恢复，但你会失去原来的失败顺序。先记录状态、日志时间、容器重启次数和最近配置变化。处理后再补健康检查、日志限额和告警。

## paused、stopped 和 exited

容器状态的词要看清。running 表示主进程仍在。exited 表示进程退出。paused 表示进程被暂停，通常不是正常业务状态。restarting 表示重启策略正在反复尝试。不同状态对应不同处理。

看到 exited，先看退出码和日志。看到 restarting，先看最近几次日志，不要再手动 restart。看到 paused，确认是否有人执行了暂停操作，或平台是否有资源管理动作。只凭容器名称判断，会错过状态本身给出的线索。

容器 healthy 也不代表业务完全正常。健康检查可能只覆盖本地端口。登录、上传、支付、队列和外部 API 仍可能失败。健康状态适合自动化判断，人工验收还要走关键业务路径。

## OOM 和资源限制

容器被 OOM 杀掉时，Docker 和系统日志都会留下线索。表现可能是容器突然 exited，随后被重启策略拉起。应用日志里未必有完整错误，因为进程被系统直接终止。排查时看 inspect 里的 OOMKilled，也看宿主机日志。

内存限制太低，应用会频繁死亡。限制太高，单个容器可能挤压同机其他服务。数据库、浏览器渲染、图片处理、AI 辅助任务和大型构建都可能吃内存。限制值要根据负载测试和监控调整。

CPU 限制也会影响健康检查。容器在高负载下响应变慢，健康检查超时，平台又重启容器，故障可能加剧。健康检查超时要给业务留余地，不要设置得像本地空闲机器一样紧。

## 日志采集和保留

小项目可以先靠 docker logs 和主机日志文件。项目变大后，需要集中日志。集中日志要控制采集范围、保留时间和访问权限。日志里出现个人信息时，还要考虑脱敏和删除请求。

日志格式最好稳定。时间、级别、请求 ID、用户匿名标识、接口名、状态码和耗时，足够处理许多问题。不要把整段请求体默认写进日志。排查需要时，可以临时提高某个模块日志级别，并在结束后恢复。

容器日志和应用日志要能接上。反向代理看到 502，应用容器同时重启，数据库日志出现连接拒绝，这三者按时间连起来，事故就清楚很多。没有统一时间和请求 ID，排错会慢。

## 健康检查怎样写

HTTP 服务可以提供 `/health` 或类似接口。这个接口应该快速返回，说明进程能处理请求。若要检查数据库，可以做轻量查询。若数据库短暂慢，健康检查是否立刻失败，要按业务决定。频繁误杀容器会让服务更不稳定。

Worker 服务没有 HTTP 端口，也可以用命令检查。比如检查进程是否能连接队列，或检查最近一次心跳时间。健康检查要反映服务职责。只要主进程活着就健康，可能漏掉队列断开。检查太深，又可能制造额外压力。

健康检查失败后的动作也要设计。只是标记 unhealthy，还是由编排系统重启，还是发告警给人。小项目可以先告警和记录，不急着自动重启所有东西。自动化越强，误判的后果也越大。

## 日常巡检

日常巡检可以很短。看容器状态，重启次数，健康状态，磁盘占用，日志增长，最近错误，镜像版本和备份结果。每次只要几分钟。长期坚持，比事故当天翻命令有效。

巡检结果要留痕。可以写一行日期和异常摘要。看到重启次数增加、日志变大、磁盘持续上涨，就提前处理。容器平台给了状态，不代表有人看。没人看的状态等于没有状态。

巡检还要覆盖依赖。数据库容器、缓存容器、反向代理容器和后台任务容器都要看。只看 Web 容器绿色，后台任务可能已经停了三天。用户发现报表不更新时，事故其实早就开始了。

## 重启前的三问

重启容器前问三件事。当前状态是否已经记录。容器里是否有未持久化数据。重启会不会中断长连接、上传或后台任务。三问都能回答，再执行重启。

重启后也要验收。容器是否进入 running，健康检查是否恢复，日志是否还有同样错误，用户路径是否正常。若几分钟后又重启，说明根因仍在。不要把重启当成结案。

## 让 AI 分析容器日志

容器日志给 AI 前要截取时间段。比如故障前五分钟到恢复后五分钟。再删掉 Token、Cookie、邮箱、手机号、IP 和请求体。保留时间、级别、错误类型、请求 ID 和服务名。这样既能分析，又不把用户数据带出去。

提问时告诉 AI 你的目标。你可能想知道容器为什么退出，也可能想查健康检查失败，或者确认 502 是否和容器重启相关。目标不同，分析重点不同。让 AI 输出时间线，比让它直接给结论更稳。

AI 给出原因后，要回到系统验证。它说内存不足，就看 OOM 记录。它说端口冲突，就查监听端口。它说数据库不可用，就看数据库日志。日志分析只是线索，系统状态才是证据。

分析完成后，让 AI 帮你写告警建议。哪些日志关键词要告警，哪些重启次数异常，健康检查失败多久通知人。告警要少而准。太多噪声会让人不再看。

## 本章练习

启动一个会正常运行的测试容器，记录 `docker ps`、inspect 摘要和日志。再启动一个会立即退出的容器，观察 exited 状态、退出码和日志差异。

给测试服务加一个轻量健康检查。先让它返回正常，再让服务故意返回失败。观察健康状态变化。不要让健康检查做复杂业务，只看它怎样影响状态。

最后设置一个重启策略，让容器失败后自动重启。观察重启次数。练习结束后关闭策略或删除容器。自动重启很有用，但你要亲眼看过它怎样掩盖反复失败。

## 常见误区

第一个误区是用重启替代排错。重启可能恢复服务，也会擦掉时间线。重启前先保存状态和日志。

第二个误区是 healthy 等于业务正常。健康检查可能只测本地端口。登录、上传、支付、后台任务仍要单独验收。

第三个误区是日志无限保存。容器日志会占磁盘。没有限额和轮转时，一个循环错误就能拖垮主机。

## 本章交付物

本章结束时，你应该有一份容器巡检卡。状态、重启次数、健康状态、日志大小、最近错误、镜像版本、磁盘占用和备份结果，都有检查位置。

还应有一份日志脱敏规则。写清哪些字段可以给 AI，必须删除哪些内容，并说明哪些信息只能做摘要。日志是排错材料，也是用户数据可能泄露的地方。

## 第六卷收束验收

走到这里，第六卷的最低验收可以收成一条线。你能 SSH 登录测试机，知道当前用户和系统版本。你能看文件权限，知道服务用户是否能读写目标目录。你能看进程、端口、磁盘、内存和日志，判断网站打不开大概卡在哪一层。

你还能把一个服务交给 systemd，知道 status 和 journalctl 分别回答什么。你能用 Caddy 或 Nginx 把本机应用暴露成 HTTPS 域名，并在 502、证书错误和超时时找到对应日志。你能写一份发布记录，知道备份和恢复演练比口头承诺更可靠。

Docker 部分的验收也很具体。你能解释镜像、容器、Dockerfile 和 Registry 的关系。你知道端口映射不等于 EXPOSE，volume 不等于备份，Compose 的最终配置要用 config 看。你能看容器状态、日志、健康检查和重启次数，不把 restart 当成万能修复。

这些能力放在一起，是为了让你读懂 AI 写出的部署方案。AI 可以生成命令，能补配置，也能整理日志。你负责判断命令会改哪里，数据在哪里，失败怎样恢复，秘密有没有泄露。到了这个程度，第六卷才算真正结束。

AI 可以帮你解释容器状态、重启策略和脱敏日志。不要把完整 inspect、环境变量、用户请求和生产日志原文交给它。下一章讲 Docker 更新、回滚、清理与数据丢失风险。
