# 从现象到故障层级的统一判断方法

用户说“打不开”，开发者脑子里可能同时跳出 DNS、服务器、数据库、缓存、浏览器、手机系统和商店审核。新手最容易在这里被吓住，随后随机试。重启一下、清缓存、改配置、重新部署。运气好时问题暂时消失，运气差时现场被破坏，根因也不见了。

排错的第一步不是猜根因。先把现象放回系统里，判断它发生在哪一层，有没有正在扩大，有没有需要立刻止损的动作。

## 先判断是否需要止损

有些故障可以慢慢查。页面布局错位、文案没更新、单个测试账号登录失败，通常先保存证据再复现。有些故障要先限制影响。重复扣款、公开泄露私密数据、删除生产文件、数据库写坏、所有用户无法登录，这些问题先停下扩大范围。

止损不等于盲目回滚。先问四件事。新版本是否正在继续分发。后端是否仍在写入错误数据。外部用户是否还在触发危险动作。当前操作会不会删除证据。若答案指向风险扩大，先暂停发布、关闭功能开关、限制入口或切回兼容后端。每一步都记录时间和操作者。

AI 可以帮你列止损选项，却不能替授权人决定删除、回滚、停服和公开公告。涉及钱、隐私和生产数据时，保守一点更稳。

## 把问题报告变成事实

“坏了”不是事实。可用的事实至少包含时间、用户动作、入口、设备或浏览器、账号类型、版本、预期结果、实际结果和错误文字。没有这些，任何判断都像在雾里摸门。

把第一条报告改写成这样。

```text
时间　2026 年 8 月 29 日 14 点 12 分
入口　https://example.com/orders
账号　普通用户测试账号
动作　点击保存订单
预期　订单保存并回到列表
实际　页面停留，右上角提示保存失败
版本　前端 commit abc123，后端 release 42
证据　浏览器 Network 中 POST /api/orders 返回 500
```

这段还没有根因，已经比“保存不了”强很多。它能告诉你下一步该看 API、后端日志和数据库，而不是去改按钮颜色。

事实还要分清来源。用户截图说明他看到了什么，浏览器 Network 说明请求返回什么，服务器日志说明后端做了什么，数据库日志说明存储层发生什么。四种证据不能互相代替。用户说“我点了两次”，只能证明他的记忆和操作描述；后端收到两个同请求编号，才说明系统真的处理了两次。

记录事实时也要保留不知道的地方。影响范围未知，就写未知。生产是否受影响还没查，就不要写“只影响测试”。承认缺口不会削弱报告，反而能避免别人把空白当成结论。

## 把系统画成输入和输出

故障层级可以按一次用户动作画。用户点击按钮，浏览器或 App 先通过 DNS 找到入口，再可能经过 CDN、代理、应用进程、数据库和第三方服务，最后返回结果。不是每个请求都经过全部组件；先按项目实际路径画出输入、输出和证据位置。

静态网站打不开，先看域名、DNS、CDN 和构建产物。按钮点击无反应，先看浏览器 Console 和前端状态。请求发出但 401，先看登录态和权限。请求 500，先看后端日志。后端说数据库连接失败，再看数据库和网络边界。App 商店上传失败，先看包名、版本号、签名和政策任务。

同一个现象可能由不同层造成。用户看到“白屏”，可能是 JavaScript 报错，也可能是接口 500，也可能是缓存拿到旧文件。不要让用户界面上的一句话支配全部排查。界面只是症状，不是诊断报告。

画图时不用追求架构图漂亮。先用文字列也行。

```text
用户浏览器
CDN
反向代理
后端 API
数据库
对象存储
第三方支付
```

随后在每一行旁边写证据位置。浏览器看 Console 和 Network，CDN 看命中和回源，代理看 access log，后端看请求编号，数据库看连接和查询，第三方看状态页和回调日志。排错时先定位哪一行没有把输入变成预期输出。

## 范围缩小比猜根因可靠

排错像缩小地图。先问多少人受影响。全站失败、单个地区异常、某类账号失败，方向完全不同。全部用户打不开公开页面，优先看入口层。只有管理员保存失败，优先看权限、表单和后端规则。只有新版本 App 崩溃，优先看构建、迁移和版本差异。

再问是否稳定复现。每次都失败，适合按步骤拆。偶尔失败，要记录频率、时间、数据量和外部依赖。只在晚上失败，可能和定时任务、配额、备份或网络有关。只在移动网络失败，可能和证书、DNS、IPv6 或运营商链路有关。

缩小范围时不要同时改三处。清缓存、重启服务、改环境变量和回滚代码一起做，问题消失后也不知道哪一步有效。一次只改变一个条件，并写下结果。慢一点，反而更快。

## 假设必须能被证伪

“可能是缓存”只能算猜测。可执行的假设应带验证办法。若是浏览器缓存，换无痕窗口或加版本参数后应恢复。若是后端 500，服务器日志应在同一时间出现对应请求。若是数据库连接池耗尽，应用日志和数据库连接数应同时异常。

一个好假设可以被证据推翻。验证结果不符合预期，就放下它。不要为了保住猜测继续解释所有反例。很多排错时间都耗在这里，人已经爱上了第一个猜想，证据只好陪着绕圈。

最近改动是重要线索，也只是线索。代码提交、依赖升级、环境变量、证书、DNS、数据库迁移、云平台策略、流量突增和外部 API 都可能改变系统。没有部署代码，证书到期也能让应用失效。

## 一个 502 故障的判断

假设用户访问网站得到 502。先确认影响范围。所有用户访问公开域名都失败，本地开发环境正常。再看代理日志，发现请求已到 NGINX，但连接上游失败。应用进程在运行，却监听 `127.0.0.1:3001`；NGINX 配置仍转发到 `127.0.0.1:3000`。

这时根因不在数据库，也不在前端。修复上游端口配置，重载代理，再用公开域名验证。随后把发布记录补上。谁改了启动端口，为什么代理没有一起改，健康检查为什么没提前发现。

如果一开始就改数据库连接，问题不会好。若同时重启服务器、清缓存和改端口，虽然可能恢复，也会失去判断依据。排错记录让下一次 502 少走一圈。

## 建立可交接的排错记录

排错记录不必长，但要能交给另一个人接着查。

```text
现象：
影响范围：
开始时间：
相关版本：
已看证据：
当前假设：
已尝试动作：
结果：
下一步：
风险：
```

每次动作后补一行。不要只写“试过了”。写清试了什么、在哪台机器、得到什么结果。截图要包含时间、地址、版本和完整错误。日志要保留前后几分钟，避免只截最后一行。

问题消失以后先别急着结案。确认监控恢复，用户路径可用，错误不再增长，临时开关是否要撤销，日志级别是否要降回去，测试数据是否要清理。否则“修好了”只是当时那一秒没再出错。

## 复盘把事故变成维护能力

一次复盘回答五件事。用户看到什么。系统哪一层失败。为什么没有提前发现。止损是否及时。以后怎样减少同类问题。复盘不追求写得好看，追求下次有人能用。

避免把结论写成“加强测试”“提高意识”。要写成具体动作，例如给代理增加健康检查，发布前核对端口，数据库迁移先在恢复副本跑，商店发布后观察启动崩溃和登录成功率。责任要落到流程和证据，不只落到某个人的粗心。

AI 在排错中适合做三件事。整理现象，列假设和证据，生成下一步实验。它不适合接收真实秘密、生产数据库导出和用户隐私。它也不能在没有证据时宣告根因。你要把它当作会问好问题的同事，不要当作事故现场的唯一负责人。

复盘还要关注发现机制。用户先报错，监控后响，说明监控晚于用户。客服发现退款异常，支付告警没响，说明业务指标缺口。开发者手工看日志才知道磁盘满，说明容量告警缺口。每次事故至少补一个能提前发现的信号。

最后把复盘转成下一次的检查项。端口核对、旧版本升级测试、审核账号检查和备份恢复演练，可以分别进入发布清单、商店清单和季度维护清单。复盘写完没人执行，就只是一篇事故作文。

## 什么时候可以停止排查

停止排查也要有条件。用户路径已经恢复，错误指标回到基线，监控持续稳定，临时止损动作已经处理，受影响数据已经检查，相关人员知道结果。满足这些条件，才适合把事故从紧急状态转入后续改进。

如果根因还没有完全确认，可以写成“当前证据支持的解释”。例如公开域名 502 已恢复，证据指向代理上游端口配置错误，尚未确认为什么配置没有随应用端口一起更新。这样不会假装已经知道所有事，也不会让团队继续无序试错。

停止排查前再问一次有没有残留风险。缓存里是否还有旧前端。队列里是否还有失败任务。旧 App 是否仍在调用坏接口。测试账号是否还保留管理员权限。临时开放的防火墙是否已经关闭。事故最讨厌的尾巴，常常藏在“已经好了”的那一刻之后。
