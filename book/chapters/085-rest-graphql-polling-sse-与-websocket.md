# REST、GraphQL、Polling、SSE 与 WebSocket

一个订单页面要显示付款进度。最朴素的做法，是用户打开页面时请求一次，之后每隔几秒再问服务器。有人嫌它不够实时，建议换 WebSocket。另一个人嫌接口字段太多，又建议引入 GraphQL。三种建议放在一起吵，很容易吵偏，因为它们处理的是两组问题。

REST 与 GraphQL 处理客户端怎样表达数据需求。Polling、SSE 与 WebSocket 处理页面怎样得到后续变化。系统可以用 REST 创建订单，再用 SSE 接收状态更新；也可以用 GraphQL 查询页面数据，同时用普通轮询刷新。两组问题分开以后，很多方案会自己退场。

## 先分清接口和更新

用户打开课程详情页，需要读取标题、作者和章节。这是一次数据请求。课程发布者修改内容以后，已打开页面能否收到变化，这是更新传播问题。

数据接口要回答客户端怎样表达读取和修改，资源或 Schema 怎样设计，权限、错误、缓存和版本怎样处理。更新通道要回答谁先开口，连接保持多久，变化怎样送达，断线怎样恢复。

某个 REST 接口返回字段太多，引入 WebSocket 不会减少字段。聊天消息需要双向低延迟传输，换成 GraphQL 查询也不会解决长期连接。先写清眼前的问题，再比较候选方案。

## REST 说的是资源与 HTTP 行为

REST 来自 Roy Fielding 对网络软件架构风格的研究，包含客户端与服务器分离、无状态交互、可缓存、统一接口和分层系统等约束。日常开发里，人们常把使用 HTTP 方法、资源 URL 和 JSON 的接口统称为 REST API，其中许多项目只采用了部分思想。

先掌握资源与动作的关系。`GET /orders/123` 读取订单，`POST /orders` 创建订单，`PATCH /orders/123` 修改允许改变的部分。这种接口容易被浏览器、代理、日志、缓存与测试工具理解。页面需要多类关联数据时，服务端可以增加聚合接口，也可以让客户端发多次请求。

REST 不等于把数据库表暴露出去。订单资源可以组合多个内部模型，写入接口必须执行业务规则。URL 命名再漂亮，客户端若能随意修改付款状态，系统仍然不安全。

## GraphQL 让客户端声明字段

GraphQL 使用类型系统描述服务端能力，客户端通过查询选择需要的字段。一个课程页面可以一次请求课程标题、作者姓名和前三章，另一个页面只取标题与封面。它适合多个客户端对数据形状有不同需求的情况。

灵活性会把更多责任交给服务端。一条查询可能沿作者、课程、章节和评论展开，产生大量数据库访问。服务端需要批量加载、分页、深度或复杂度限制、超时和监控。GitHub 的 GraphQL API 公开 Schema 和查询指南，同时设置查询成本、节点、超时和速率限制。

权限要落到字段与业务动作。用户能读取订单，不代表能读取内部风控备注。客户端请求字段时，服务器仍要检查身份和权限。缓存方式也会改变。GraphQL 常把不同查询发送到同一入口，HTTP 层难以只凭 URL 区分数据需求。

项目已有稳定 REST API，不必为了一个复杂页面全部重写。可以为内部管理端增加有限的 GraphQL 层，也可以先建立聚合 REST 端点。相同业务规则必须落在共同应用层。

## Polling 用普通请求换简单恢复

Polling 通常译为轮询。页面每隔固定时间发出一次 HTTP 请求，询问状态是否改变。它沿用普通请求、鉴权、状态码和日志，反向代理与托管平台也熟悉。订单状态十几秒变化一次，用户允许晚五秒看到，轮询可能已经足够。

间隔决定延迟和请求量。每秒轮询更新更快，也会在没有变化时持续消耗网络、服务器和数据库。不要抄教程默认值，要根据变化频率、在线人数和可接受延迟计算。页面隐藏、网络离线和连续错误时，要降低频率或暂停。

轮询恢复很直观。网络回来后重新请求当前权威状态，不需要补齐每一次中间变化。若审计页面必须看到每条事件，接口要支持按游标或时间获取遗漏记录。Long Polling 常译为长轮询，服务器收到请求后暂时不返回，直到有新数据或等待超时。

## SSE 和 WebSocket

SSE 是 Server-Sent Events 的缩写，可以译为服务器发送事件。浏览器通过 `EventSource` 打开 HTTP 事件流，服务器保持响应并持续发送文本事件。WHATWG HTML 标准定义了 EventSource、事件流格式、事件 ID 与 `Last-Event-ID` 等行为。

它的方向主要是服务器到浏览器。构建日志、后台导出进度、通知提示和行情摘要都可能适合。用户提交命令时，仍可使用普通 HTTP 请求，服务器再通过 SSE 推送结果。应用若分配稳定事件 ID，断线后可以继续发送遗漏内容。

连接会经过浏览器、反向代理、CDN 和应用服务器。某一层若缓存响应、缓冲输出或设置较短空闲超时，页面可能迟迟收不到事件，也可能频繁断线。上线前要用真实部署路径测试，鉴权也要提前设计。

WebSocket 让客户端和服务器在长期连接上双向发送消息。协议从 HTTP 握手开始，随后使用 WebSocket 帧通信。RFC 6455 定义了握手、数据帧、Ping、Pong 和关闭等行为。聊天室、多人协作、在线游戏和远程控制常需要双方频繁低延迟发送。

双向通道只提供运输能力。消息类型、版本、权限、确认、顺序、重复、房间成员和断线恢复都由应用设计。客户端发出修改文档消息时，服务器仍要验证用户是否有编辑权限，不能因为连接在登录后建立就长期信任。

连接断开是正常情况。手机切换网络、电脑休眠、代理超时和服务发布都会中断。客户端需要识别关闭原因、逐步重连并重新认证。慢客户端还会造成发送积压，高频进度和光标可以合并或丢弃旧值，付款状态和用户消息则不能随便丢。

## 五种技术放在一起看

REST 适合资源读取与修改，GraphQL 适合多个客户端声明不同字段组合，Polling 适合低频状态，SSE 适合服务器连续推送文本事件，WebSocket 适合双向频繁消息。通知中心可以用 REST 拉历史列表，用 SSE 接收新通知；内部订单列表只关心最新状态，带退避的轮询通常合理；在线客服需要双方频繁发送消息，WebSocket 更合适。

手机 App 进入后台后，长期连接可能暂停或断开。需要系统级通知时，应评估 Apple Push Notification service 或 Firebase Cloud Messaging 等推送体系，不能期待网页 SSE 或 WebSocket 在后台长期保持。商店和系统政策会变化，采用前要查当前官方资料。

## 权限、恢复和观察

REST 端点、GraphQL 字段、SSE 订阅和 WebSocket 消息都要验证身份与权限。身份在连接建立时有效，不代表几小时后仍有效。订阅目标不能只相信客户端提交的用户 ID，服务器要从已验证身份推导可访问的订单、房间和项目。

失败练习比本地演示重要。创建订单，付款状态改变，页面在目标时间内显示新状态。随后断开网络，检查轮询能否重新请求，SSE 和 WebSocket 能否按策略重连。让同一事件重复到达，检查界面是否重复插入。让旧事件晚于新事件到达，检查版本号或时间判断是否阻止状态倒退。

普通 HTTP API 关注请求量、状态码、延迟和响应大小。GraphQL 还要记录操作名称、查询成本、解析与数据加载耗时。轮询要看每用户频率、未修改比例和错误退避。SSE 与 WebSocket 要看连接数、持续时间、重连率、异常关闭和发送积压。

## 让 AI 先回答方向、频率和恢复

要求 AI 推荐通信方式以前，给它当前用户动作、在线人数、变化频率、允许延迟、部署平台和权限边界。让它先回答数据由谁主动发送，客户端只要最新状态还是完整事件，断线后怎样恢复。

候选方案至少保留一个简单基线。比较 WebSocket 时，把轮询也实现成可测方案。比较 GraphQL 时，把一个 REST 聚合端点放进候选。AI 生成 WebSocket 或 SSE 示例时，要写清重连、认证过期、代理超时、重复消息、顺序、连接清理、限流和多实例分发。

最后把选择写成带条件的结论。订单状态页面先用五秒轮询，因为变化低频、用户量小且只关心最新状态。在线用户与无变化请求达到既定水平，或产品要求一秒内更新时，再测试 SSE。这样的决定能够复查，也允许项目以后改变。
