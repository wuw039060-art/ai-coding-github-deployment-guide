# VPS、云服务器及购买时需要看的参数

打开云服务商的购买页，读者往往先看到一排数字。两个虚拟 CPU、四吉字节内存、八十吉字节磁盘、每月若干流量。它们看起来像电脑配置，却还不能直接回答一个更重要的问题。这个规格能不能稳定运行你的项目。

虚拟专用服务器的英文是 Virtual Private Server，常缩写为 VPS。它是从一台或一组物理服务器中划分出的虚拟计算机。你通常能获得一个操作系统、可登录的管理员账号、一定数量的处理器时间、内存、磁盘和网络资源。云服务器是更宽泛的商业名称，本书把可自行管理操作系统的云主机都放在这一类讨论。

买下 VPS 以后，你得到的是一间空房，里面已经接好水电。应用、数据库、门锁、消防检查和日常清洁仍要由你安排。这个比喻有一个边界。云服务商仍负责物理机器、机房和虚拟化平台，你负责虚拟机中的操作系统、账号、软件、数据和大部分网络规则。

## 先确认你是否真的需要一台服务器

静态网页只包含 HTML、CSS、JavaScript 和图片时，GitHub Pages、Cloudflare Pages 等静态托管通常更省事。平台替你处理操作系统、Web 服务和证书。前面几卷已经介绍过这条路线。

当项目必须长期运行一个后端进程、使用特定系统软件、保持长连接、执行定时任务，或者需要自行控制反向代理时，VPS 才开始有明显价值。例如，一个作品集网站只是展示页面和图片，不需要 VPS。一个每晚抓取公开数据并生成报告的小程序，需要在固定时间运行任务，VPS 就可能合适。另一个聊天应用使用托管数据库和无服务器函数，也未必需要自己的服务器。

先写出项目离线时仍要运行的东西。若清单为空，优先考虑托管平台。若清单包含 API 进程、任务队列、定时任务或特殊二进制程序，再继续比较 VPS。

云服务商一般负责机房供电、物理网络、物理磁盘和虚拟化平台。具体范围受产品条款影响，购买前仍要核对。用户通常负责以下内容。

- 选择和更新操作系统
- 管理登录账号与 SSH 密钥
- 安装并更新应用和依赖
- 配置防火墙、端口和反向代理
- 管理域名、证书和应用秘密
- 监控进程、磁盘、内存和费用
- 备份数据并实际测试恢复
- 在服务故障或安全事件中响应

平台提供快照按钮，不会自动替你决定何时拍快照，也不会验证快照能否恢复。平台提供防火墙，不会知道你的数据库是否应该对全世界开放。VPS 给你的是操作权限，稳定性仍来自持续管理。

## 处理器数字为什么不能单独比较

虚拟 CPU 常写成 vCPU。它表示分配给虚拟机的计算执行资源，不等于一颗独占的物理 CPU。两家平台都写两个 vCPU，实际处理器型号、共享程度和持续性能可能不同。共享 CPU 方案允许多个虚拟机使用同一组物理计算资源，适合访问量不稳定、计算不重的个人网站和测试环境。专用 CPU 方案把更确定的处理器资源留给实例，适合持续编译、视频处理、繁忙数据库等负载。DigitalOcean 的当前选型资料也明确区分共享和专用 CPU，并建议以真实负载测试为依据。

个人博客偶尔被访问，大部分时间处于等待状态，一个共享 vCPU 可能足够。持续把图片转换为多种尺寸的服务会长时间占用计算资源，相同的 vCPU 数量可能很快变慢。购买页的数字只能用于初筛。真正上线前要测一次构建时间、接口响应和高峰 CPU 使用率。资源长期接近满载时，用户会先看到页面变慢，随后可能出现超时和进程被系统终止。

内存可以理解为服务器正在使用的工作台。操作系统、Web 服务、应用运行时、数据库和缓存都要占用这张工作台。一个小型 Node.js 接口本身可能只占几百兆字节，但构建前端时会临时使用更多内存。数据库导入、图片处理和多个容器同时启动也会制造峰值。只看应用空闲时的占用，容易低估需要的容量。

内存不足时，Linux 可能使用交换空间，把部分内容暂时写到磁盘。这样能缓解短时峰值，却比真实内存慢得多；压力继续上升时，系统可能选择终止进程；日志里常能找到内存不足的线索。一个常见小案例是，网站平时运行正常，每次自动部署都会短暂离线。原因可能来自构建任务和旧应用同时占用内存，与网络无关。新进程启动时达到峰值，应用被终止。解决方向包括在别处构建、减少并行任务、增加内存，或者采用能保留旧版本的部署方式。

## 磁盘要看容量、性能和持久性

磁盘容量决定能保存多少文件。应用代码通常不大，数据库、上传文件、日志、容器镜像和备份更容易持续增长。八十吉字节并不代表应用能自由使用八十吉字节。操作系统和软件会占一部分，文件系统也需要保留空间。磁盘接近占满时，数据库可能无法写入，日志无法落盘，软件更新也会失败。

磁盘性能还包括读写延迟、吞吐量和随机操作能力。一个只读静态站点对磁盘要求很低，频繁写入的小数据库更敏感。部分低价实例的磁盘性能会受共享资源影响，不能只看容量。还要区分系统盘、附加块存储和对象存储；系统盘随虚拟机存在，适合操作系统和应用文件；块存储像额外硬盘，适合需要文件系统的持久数据；对象存储通过接口保存文件，适合图片和备份；三者的备份、网络和费用模型不同。

第一件是公网地址。服务器要被互联网访问，通常需要公网 IPv4、IPv6，或者由平台负载均衡器提供入口。静态 IP 能避免实例重建后地址变化，是否额外收费要查当前产品说明。第二件是流量；购买页可能写每月包含流量，还可能区分入站与出站；用户下载图片和安装包通常消耗出站流量。超过额度后的计费规则会变化，必须以购买当日的官方页面为准。

第三件是端口。网站常用 80 和 443，SSH 常用 22。端口能否访问同时受云平台防火墙和服务器内防火墙影响。只修改其中一层，连接仍可能失败；第四件是区域；服务器离主要用户越远，网络往返通常越慢；区域还影响产品可用性、数据驻留、价格和备案要求。中国大陆用户要另外核对跨境网络、域名备案、支付方式和当地法规。

## 地区不能只选地图上最近的点

用户主要在新加坡，选择欧洲区域往往会增加延迟。应用数据库却已在欧洲时，把 API 放到新加坡可能让每次数据库查询跨越更远距离。浏览器到 API 很快，API 到数据库很慢，整体仍慢。把会频繁通信的组件尽量放在接近的区域。前端静态资源可以通过 CDN 分发，后端和数据库更需要考虑彼此距离。对象存储、备份和日志可能有各自区域，也要分别确认。

区域选择还包含故障与迁移成本。部分平台不能直接把实例搬到另一区域，只能从快照重建。购买前查看快照、备份和 IP 的迁移方式，能减少以后被迫停机的时间。

初学者优先选择仍在支持期内的 Ubuntu 长期支持版，英文写作 Long Term Support，常缩写为 LTS。它的教程和软件包资料较多。本书服务器命令以当前 Ubuntu LTS 为主要验证环境。Ubuntu Server 官方文档也把最新 LTS 作为主要目标。

不要因为某个教程写着旧版本，就主动购买已经停止安全更新的镜像。也不要在第一次部署时选择带有大量预装面板的陌生镜像。预装软件缩短安装时间，也增加需要理解的账号、端口和更新来源。若项目明确要求其他发行版，应跟随项目官方支持范围。选择镜像后记录发行版、版本、架构和创建日期。以后排错时，“Linux 服务器”这个说法太宽，无法判断命令和配置是否适用。

## 架构会影响软件能否运行

常见处理器架构包括 x86_64 和 ARM64。许多开源软件同时提供两种版本，但某些二进制工具、旧插件或容器镜像只支持其中一种。ARM 实例有时价格更合适。若依赖没有 ARM 构建，节省的主机费用可能变成兼容工作。购买前检查应用运行时、数据库、容器镜像和监控代理的支持列表。

容器镜像标注多架构，也要确认其中确实包含目标架构。只在开发电脑的 x86_64 环境测试，然后把镜像放到 ARM 服务器，可能收到无法执行文件的错误。

“基础”“高级”“通用”是营销分类，不是可跨平台比较的标准。把关键参数抄到一张自己的表中。建议至少记录以下内容。

1. vCPU 数量和共享方式
2. 内存与是否允许增加交换空间
3. 系统盘容量、类型和扩容方式
4. 包含流量、带宽上限和超额价格
5. 公网 IPv4 与静态地址政策
6. 可选区域和网络限制
7. 快照、自动备份和恢复方式
8. 防火墙、监控和控制台救援能力
9. 计费周期、关机是否收费和删除结算方式
10. 支持渠道、账号验证和支付要求

AWS Lightsail 的实例资料同样把 vCPU、内存、SSD 和传输量作为套餐组成。数字与价格会变化。本书截至 2026 年 8 月 5 日只保留比较方法，不把任何套餐写成永久推荐。

## 先用最小可行规格，再用证据调整

无法准确预测时，可以从满足最低内存的较小实例开始，但必须确认它能否无损扩容。较小不等于越便宜越好。内存不足导致反复事故，会比主机差价更昂贵。上线后记录 CPU、内存、磁盘、网络和响应时间。关注趋势，不只看某一分钟的峰值。磁盘每天增长一吉字节，即使今天仍有一半空间，一个月后也会成为事故。

扩容前先判断瓶颈。CPU 高可能来自死循环、爬虫或编译任务，直接加内存无效。内存高可能来自泄漏，升级规格只会延迟故障。磁盘满可能是日志没有轮转，扩盘会让问题以后再次出现。

准备一个专用于服务器登录的 SSH 密钥。不要把私钥上传到项目仓库或聊天记录。平台若支持创建时写入公钥，优先使用这条路径。准备清楚的名称，例如 `notes-api-prod-sg`。名称至少表达项目、环境和区域，避免半年后看到三台都叫 `ubuntu` 的实例。

决定实例属于测试还是生产。测试实例可以删除重建，生产实例必须先有备份和变更记录。两者不要共用同一套数据库凭据。记录购买时看到的区域、镜像、规格、磁盘、网络和备份选项。DigitalOcean 与 Lightsail 的官方创建指南都把这些选择放在实例创建阶段。

## 创建后先做验收，不急着部署

实例显示 Running 只说明虚拟机已经启动。先完成四项只读验收。

1. 能用预期账号和密钥登录
2. 系统版本与购买时选择一致
3. 磁盘、内存和 CPU 与套餐大致一致
4. 云防火墙只开放计划使用的入口

再记录公网地址、实例 ID、区域和创建时间。若平台提供串行控制台或恢复控制台，确认入口在哪里。SSH 配错时，它可能是唯一救援通道。不要立即把域名指过去。先在临时地址上部署并测试健康检查，准备回滚后再切换 DNS。域名生效并不证明应用正确，只会让更多用户抵达服务器。

创建实例时常会看到自动备份、快照或删除保护之类的开关。它们解决的问题不同。自动备份通常按平台设定的周期生成副本，并保留有限时间。快照通常由用户主动创建，适合重大变更前保存整机状态。删除保护只防止误点删除，不会保存任何数据。

购买时要查四件事。副本包含哪些磁盘，保留多久，恢复会创建新实例还是覆盖旧实例，费用怎样计算。数据库正在写入时，整机快照也可能需要数据库恢复步骤。例如，一个图片站把应用放在系统盘，把上传文件放在附加磁盘。若自动备份只覆盖系统盘，恢复后页面程序存在，用户图片却全部缺失。创建前画出数据位置，逐项对应到备份范围。

## 临时磁盘与持久磁盘不能混淆

有些云产品提供本地临时盘。它速度可能很快，实例停止、迁移或硬件故障时内容可能消失。它适合缓存和可重建的中间文件，不适合唯一数据库副本。购买页如果写着 local、ephemeral 或 temporary，要打开产品说明核对持久性。不能仅凭控制台里显示一个盘符或挂载点，就认为平台会长期保存。

把数据按后果分类。代码可从 Git 重建，缓存可重新生成，上传文件和数据库记录通常不可替代。不可替代内容放在明确持久的存储中，并有独立备份。

很多平台按实例分配资源计费。操作系统内执行关机，虚拟机资源仍被保留，费用可能继续产生。控制台停止实例后，磁盘、快照、静态 IP 和备份也可能继续收费。删除通常会释放计算实例，关联磁盘是否一同删除取决于选项。误勾删除磁盘可能造成不可恢复的数据损失，漏删磁盘则会继续收费。

开始使用前做一次费用实验。创建明确标记为测试的最小实例，记录一小时或一天后的费用明细，再按平台流程停止和删除。确认账单中每项资源的状态。实验不能使用真实生产数据。

## 免费权益只适合当期判断

平台可能提供新用户抵扣、固定期限试用或有限免费额度。资格、地区、验证方式和到期行为会变化。不要围绕“永久免费”设计无法迁移的系统。购买当日保存官方条款和检索日期，设置预算告警，并准备权益结束后的月成本。

学生计划、创业计划和促销额度也可能要求重新验证。项目要能在补贴结束时缩容、迁移或停止，避免突然账单迫使团队仓促处理数据。

IPv4 地址稀缺，部分平台会对公网 IPv4 收费或限制数量。IPv6 地址空间更大，但用户网络、第三方回调和旧客户端并非全部支持纯 IPv6。购买前确认实例是否默认带公网 IPv4，静态地址怎样绑定，实例停止时地址是否保留。域名若同时配置 A 与 AAAA 记录，两条路径都要测试。

不需要公网入口的数据库或后台工作节点，可以放在私有网络，通过应用服务器访问。减少公网地址也减少直接暴露面。

## 带宽和流量不是同一个数字

带宽常表示某一时刻能传多快，例如每秒多少兆比特。流量表示一段时间传输了多少总数据，例如每月多少吉字节。一条带宽很高的线路，仍可能有较小月流量额度。一个下载站平时请求少，每个文件却很大，月出站流量可能先成为成本瓶颈。

估算时用文件平均大小乘下载次数，再加网页资源、API 响应和备份传输。不要忽略机器人访问和失败重试。上线后从平台账单与服务器日志交叉核对。

把应用和数据库放在一台小服务器上，部署最简单，也共享 CPU、内存、磁盘和故障范围。应用构建占满内存时，数据库也会受到影响。使用托管数据库能把数据服务移出主机，增加网络费用和平台依赖，却减少数据库进程的日常管理。数据量小不代表恢复不重要，个人日记的几百兆数据也可能无法重建。

第一次自建可以把 SQLite 与单个应用实例放在同一台机器。是否合适取决于写入形态和运行拓扑，访问人数只是其中一项。写事务短、读取较多、应用与数据库位于同一主机时，SQLite 可以承担真实网站。多个应用实例需要共同写入、数据库需要远程独立扩展，或长写事务经常重叠时，PostgreSQL 和独立数据服务更稳妥。SQLite 方案仍要使用一致性备份方法，并把上传文件与数据库一起纳入恢复。

## 一个报名系统的选型

假设你要发布一个社团报名系统。每天几十人查看，报名开放的两个小时会有几百次提交。应用使用 Node.js，数据存 PostgreSQL，上传文件很少。先排除纯静态托管，因为提交需要后端和数据库。再比较托管后端与 VPS。团队没有服务器维护经验，报名数据又不能丢，托管数据库加托管应用可能更合适。

若因预算和学习目的选择 VPS，内存要同时容纳系统、应用和数据库，真实需求通过测试确定。构建尽量放到 CI，数据库每日备份到异地对象存储，报名窗口前做一次恢复演练。规格数字不是案例的核心。核心是从高峰、数据后果和团队能力推出资源与责任，不能从最低价格反推系统。

另一个项目每晚运行十分钟图片整理脚本，不提供公网网页。让一台 VPS 全天开机可能浪费资源。计划任务型云函数、CI 定时任务或按需启动实例可能更合适。若脚本依赖特殊二进制工具，每次还要处理大量本地文件，VPS 会更直接。此时可以关闭不需要的公网 Web 端口，只保留受限 SSH，任务完成后把结果备份到对象存储。

同样叫后端任务，持续服务与短时批处理的最佳计费方式可能完全不同。先画出运行时间，再选资源。

## 性能测试要模拟真实峰值

在测试环境准备接近真实的数据量和关键操作。测量应用启动、首页请求、写入、文件上传和后台任务。记录 CPU、可用内存、磁盘等待和响应时间。逐步增加并发，不要一开始就发起可能压垮生产环境的压力测试。测试账号与真实用户数据分开，限制外部 API 调用，避免产生费用或垃圾邮件。

观察故障如何出现。是响应逐渐变慢，还是进程突然退出。日志是否能指出内存、连接池或磁盘问题。测试结果写进选型记录，下一次扩容就有基线。

云控制台、串行控制台和恢复镜像的使用条件不同。有的平台要求提前设置账号权限，有的平台只有实例停止后才能挂载救援盘。在测试实例中体验一次控制台登录，确认键盘布局和粘贴限制。不要等 SSH 配置损坏后第一次寻找入口。

救援控制台权限高，应启用多因素认证并限制成员。它能绕过部分网络限制，不能成为共享账号的便利入口。

## 采购记录怎样保存

在项目文档建立一页服务器卡片。写实例名称、平台、区域、创建日、操作系统、架构、规格、磁盘、IP、备份开关和预算告警。再写选择理由和拒绝的替代方案。例如“选择两吉字节内存，因为测试构建峰值为一点二吉字节，并保留系统余量”。半年后看到资源紧张时，能知道原判断依据。

价格使用“截至某日”的格式并链接官方定价页。不要把付款卡号、账号密码、私钥或恢复码放进项目文档。

生产环境承载真实用户和数据，测试环境用于验证新版本。两者放在同一台主机，测试任务可能占满资源，也可能误连生产数据库。预算允许时，测试使用独立小实例或可随时重建的临时环境。预算很紧时，至少使用不同用户、目录、端口、数据库和秘密，并设置明显名称。

开发环境不应依赖生产服务器才能启动。开发者误删一个测试表，不应影响用户数据。环境隔离程度由风险决定。支付和健康数据不能只靠文件夹名称区分，个人展示站可以采用较轻方案。

## 服务商托管镜像的便利与风险

控制台可能提供一键 WordPress、Docker 或应用面板镜像。它会预装软件并生成初始账号，能缩短第一次启动。购买前查看镜像维护者、操作系统版本、更新方式和预装端口。社区镜像没有清楚来源时，不要用于生产。

一键镜像也需要立即处理初始密码、后台入口、自动更新和备份。预装成功只说明软件启动，不能证明站点已加固。学习本书路线时，干净 Ubuntu LTS 更便于理解每一层。目标是快速试用特定产品时，官方维护镜像可能更省时。

服务器控制面板用网页管理站点、数据库、证书和文件。它降低命令行门槛，也增加一个高权限 Web 服务和独立更新责任。选择前确认项目维护状态、安全公告、备份方式和卸载路径。面板生成的配置可能覆盖手工修改，两套方法不能随意混用。

面板管理端口不要无限制暴露公网。使用多因素认证、来源限制和当前支持版本。本书使用原生服务说明系统关系，不要求安装控制面板。读懂底层位置以后，即使使用面板，也能判断它修改了什么。

## 购买后第一小时的顺序

第一步保存订单和实例非秘密信息，找到控制台救援入口。第二步从本地终端核对 SSH 指纹并登录。第三步确认系统、用户、磁盘和内存。第四步检查云防火墙和监听端口。第五步安装可用安全更新并记录是否需要重启。

接着创建项目专用用户与目录，配置备份和费用告警。应用部署、域名切换和公网开放放在这些基础之后。这套顺序让每次修改都有已知起点。直接运行一键部署脚本，会在还没理解实例时同时改变账号、软件和网络。

增加 CPU 或内存时，平台可能允许直接调整规格，通常需要关机。跨架构、跨区域或缩小磁盘时，常要新建实例迁移。原地升级保留地址和磁盘，步骤少，回滚选择也少。新建迁移能并行测试和快速切回旧地址，成本是暂时运行两台机器。

生产服务重大操作系统升级更适合新建当前 LTS 实例，重新部署和恢复数据。验证完成后切换 DNS，再安全下线旧机。能从文档和备份重建服务器，本身就是对部署能力的验收。

## 最低规格说明不等于推荐规格

软件官网写的最低内存常只保证程序能启动，没有包含操作系统、代理、数据库、日志和高峰。把所有组件最低值简单相加也不准确，因为它们的峰值时间不同。真实负载测试才能得到工作集和余量。保留安全余量给更新、备份和故障诊断。服务器平时已占满，任何维护动作都会成为事故。

记录扩容触发条件，例如内存可用量持续低于阈值、响应时间恶化或磁盘按趋势将在一个月内到线。用条件替代临时感觉。

确认这是测试还是生产，区域与数据库是否接近，架构是否受依赖支持。再看备份、救援控制台和删除后的计费。把选择截图或抄入服务器卡片，隐藏订单与付款信息。创建完成后逐项对照实际资源，发现选错镜像或区域时，在还没有数据之前重建最省风险。

主机账单只是总成本的一部分。还要计算域名、备份存储、流量、监控、邮件、维护时间和事故风险。一个每月少花几十元的方案，如果没有自动快照，也没有可靠恢复控制台，发生磁盘错误时可能损失数天数据。另一个方案单价较高，却包含适用的备份和监控，实际更便宜。

反过来，平台提供的功能只有真正配置并验证才有价值。自动备份开关没有打开，页面上存在这个功能也不会保护数据。

## 购买决策的最后检查

先问项目是否需要长期运行的服务器进程。再确认区域、架构和最低内存。随后检查网络、磁盘、备份和救援入口。最后才比较价格。购买以后，把责任清单放进项目文档。至少写明谁更新系统、谁收费用告警、备份在哪里、怎样恢复、实例到期或关闭前怎样导出数据。

VPS 的优势是可控制。它的代价也是可控制。下一章会从第一次 SSH 登录开始，把这份控制权变成可以看见、检查和撤销的操作。
