# Docker Compose 与多容器应用

一个真实应用通常不只有一个容器。Web、数据库、缓存、后台任务、反向代理和开发工具可能一起工作。Docker Compose 用一份 `compose.yaml` 描述这些服务、网络、卷和环境变量。它适合单机部署、开发环境和小团队项目。

## Compose 文件看什么

Compose 文件里最重要的是 services。每个 service 描述一个容器怎样来。它可以从 image 启动，也可以从 Dockerfile build。ports 决定主机端口映射。volumes 决定数据和文件挂载。environment 和 env_file 提供环境变量。depends_on 说明启动顺序。

YAML 对缩进敏感。一个空格错了，含义可能完全变。修改后先运行 `docker compose config` 看解析结果。它能展开默认值、合并配置并暴露许多格式错误。不要等启动失败才发现缩进错在前面。

环境变量要分清来源。Compose 文件里的普通配置可以进入仓库。`.env` 和 `env_file` 可能含秘密，不应公开。变量名要稳定，值按环境填写。开发、预览和生产不要共用同一份秘密文件。

## up、logs、exec 和 down

`docker compose up -d` 会创建网络、卷和容器，并在后台启动服务。若镜像不存在，它可能构建或拉取。改了镜像、端口、挂载、环境变量或启动命令后，通常需要重新 up，让配置应用到新容器。

`docker compose logs` 看服务输出。排错时可以指定服务名，也可以加跟随参数。服务名还承担内部 DNS。Web 容器连接数据库时，通常用数据库服务名，不用容器 IP。容器 IP 会变，服务名更稳定。

`docker compose exec` 进入正在运行的服务执行命令，适合看文件、跑迁移检查和读环境。`docker compose run` 创建一次性容器，适合临时任务。二者不同。一次性任务可能不使用同一个端口、启动流程和依赖状态，执行前要确认。

`stop` 停容器但保留资源。`start` 重新启动已存在容器。`down` 会删除 Compose 创建的容器和默认网络，默认不删除命名卷。带删除卷参数时风险很高。包含数据库的项目，执行 down 前先确认卷和备份。

## build、image 和配置合并

开发时常用 build，让 Compose 从本地 Dockerfile 构建镜像。生产中更常用 image，拉取已经构建好的镜像。这样服务器不需要完整构建环境，也能明确发布版本。小项目可以从 build 起步，稳定后再引入镜像仓库。

Compose 支持多个文件合并。它方便区分开发和生产配置，也容易出错。列表字段可能追加，映射字段可能覆盖。合并后一定看 `docker compose config` 的最终结果。不要只盯你刚改的那份文件。

profiles 适合可选服务，比如调试工具、一次性任务和本地模拟器。不要用 profiles 掩盖生产必需服务。别人拿到配置时，应该能从默认命令启动核心应用。

## 健康和依赖

depends_on 只说明启动顺序，不自动说明业务可用。数据库容器启动了，不代表数据库已经接受连接。应用启动太快，可能连库失败后退出。可以用 healthcheck、重试连接和启动脚本处理。

healthcheck 要轻。检查服务能否处理最基本请求即可。不要在健康检查里做昂贵查询、外部支付调用或 AI 推理。健康检查太重，会在系统压力大时进一步扩大故障。

资源限制也要了解。Compose 可以声明内存和 CPU 相关限制，但本地 Docker Desktop、Linux Docker Engine 和不同运行方式支持细节可能不同。设置后要验证实际生效。限制太小会导致 OOM，限制太大又会影响同机其他服务。

## 一次配置未生效

团队改了环境变量，却只执行 restart。容器重启了，但仍使用旧配置，因为环境变量写在容器创建时。正确做法是重新创建容器。先看 `docker compose config`，再 `up -d`。随后通过日志、接口或容器内环境确认新值生效。

目录改名也会影响 Compose。项目名、目录名和 `COMPOSE_PROJECT_NAME` 会影响默认网络和卷名称。把目录复制一份启动，可能创建全新的卷，看起来像数据丢了。排查时先看卷名和项目名，不要立刻恢复备份覆盖。

## 外部网络和外部卷

Compose 可以使用外部网络和外部卷。外部的意思是 Compose 不负责创建和删除。它适合多个项目共享反向代理网络，或让数据库卷独立于当前 Compose 项目。使用外部资源时，文档里要写清谁创建、谁备份、谁能删除。

外部卷能减少误删，但也会增加交接难度。新同事拿到 compose 文件后，启动前必须先创建或挂载这些资源。若文档缺失，启动失败会变成猜谜。生产项目中，外部卷名称、用途和恢复方式要写进发布记录。

外部网络也要谨慎。加入同一网络的容器可以互相访问。不要把无关项目都放进一个大网络。Web 入口网络、数据库网络、内部任务网络可以按用途拆分。隔离能减少误连和误暴露。

## 一次性任务和迁移

很多项目用 Compose 执行数据库迁移、创建管理员、导入种子数据和清理缓存。一次性任务要和长期服务分开。它需要明确命令、环境变量、网络和退出码。执行成功后记录版本，失败后保留日志。

迁移任务不要跟 Web 服务一起反复启动。若迁移写在 Web 容器启动命令里，每次扩容、重启和回滚都可能重新执行。更稳的做法是发布流程单独执行迁移，通过状态表或工具记录已经执行的版本。

种子数据也要区分环境。开发环境可以反复重建。生产环境不能随便导入示例用户和测试订单。Compose 文件里若包含 seed 服务，要用 profile 或独立命令保护，避免生产误执行。

## 配置交付给别人

把 Compose 配置交给别人时，不要只给一个 yaml 文件。还要给 `.env.example`、启动顺序、需要的外部资源、端口说明、备份位置、常见命令和停止办法。别人能启动，只是第一步。别人能安全停止和恢复，才算交付完整。

配置里的注释要解释意图，不要重复字段名。比如说明某个端口只给反向代理访问，某个卷保存数据库，某个 healthcheck 只检查本地接口。以后 AI 或同事修改配置时，能知道哪些地方不能乱动。

Compose 适合一台机器上的多容器项目。需要多台机器、高可用、自动扩缩容和复杂发布时，它可能不够。不要急着上更复杂的平台。先确认 Compose 的边界碰到了什么，再决定是否迁移。

## 多环境配置

开发、预览和生产可以共用一部分 Compose 配置，但不能共用同一份数据和秘密。开发环境可以映射源码目录，生产环境更适合使用固定镜像。开发环境可以开放调试端口，生产环境只开放入口代理。

多环境配置有两种常见办法。第一种是多个 Compose 文件叠加。第二种是同一文件配合不同 `.env`。无论哪种，都要看最终配置。执行前运行 `docker compose config`，确认端口、镜像、挂载和环境变量符合目标环境。

不要让生产命令默认读取开发 `.env`。文件命名要清楚，权限要分开。生产秘密最好由部署系统或服务器受控文件提供。开发者本地的示例配置不能混进生产。

## 服务间通信

Compose 内部服务用服务名通信。Web 连接数据库写 `db`，连接缓存写 `redis`。不要写容器 IP。容器重建后 IP 会变，服务名会由 Docker 网络解析。

服务间通信还要看端口。数据库容器内部监听 5432，Web 容器连接的就是服务名加容器端口。ports 映射的是宿主机入口，给外部或宿主机访问用。很多人把这两套端口混在一起，导致本机能连，容器互相连不上。

若一个服务需要等待另一个服务可用，不能只靠启动顺序。应用要有重试，数据库要有健康检查，迁移任务要确认数据库接受连接。Compose 能帮你组织服务，业务可用仍要由应用和发布流程保证。

## Compose 项目备份

备份 Compose 项目时，不只备份 yaml。还要备份或记录 `.env`、外部卷、数据库导出、上传文件、反向代理配置和镜像版本。只有 compose 文件，无法恢复完整服务。

恢复时先在隔离环境验证。创建网络和卷，导入数据，拉取指定镜像，启动服务，走业务路径。确认无误后，再决定是否切换正式域名。直接在原环境覆盖，风险太高。

## 让 AI 审 Compose

Compose 文件很适合 AI 审查，因为结构清楚。输入前先去掉 `.env` 里的真实值，把域名、IP 和密钥改成占位符。Compose 文件本身若包含秘密，也要先替换。

让 AI 按服务逐个解释。每个服务用什么镜像，开放什么端口，挂载什么卷，使用哪些环境变量，依赖哪些服务，健康检查怎样做。解释完以后，再让它找风险。这样比直接问“有没有问题”更可靠。

AI 容易忽略环境差异。你要告诉它这是开发、预览还是生产。开发可以挂源码，生产不应挂本地源码。开发可以开放调试端口，生产要收紧。环境不同，同一份配置的评价会变。

AI 修改 Compose 后，先运行 `docker compose config`。再看最终配置和 diff。随后在测试环境 up。确认容器、网络、卷、日志和健康状态都符合预期，再考虑生产。

## 本章练习

写一份只有 Web 和数据库的练习 Compose。Web 不需要真实业务，可以只是一个测试服务。数据库使用命名卷。启动后查看服务状态、日志、网络和卷。

修改一个环境变量后，只执行 restart，观察是否生效。再用 up 重新创建容器，比较结果。这个练习能让你记住，很多配置在容器创建时固定，普通重启不会改变。

最后运行 `docker compose config`，把最终配置保存到练习记录。关闭项目时先用 stop，再用 down。不要带删除卷参数。确认数据库卷仍在。

## 常见误区

第一个误区是把 depends_on 当成服务可用保证。它主要处理启动顺序。数据库是否准备好，应用是否能连接，还要靠健康检查和重试。

第二个误区是只 restart 配置。很多环境变量、端口和挂载在容器创建时确定。改配置后要重新创建容器，并验证新配置已经生效。

第三个误区是目录改名后找不到数据。Compose 项目名会影响默认资源名称。看到数据消失，先查旧卷和项目名，别急着恢复覆盖。

## 本章交付物

本章结束时，你应该有一份可交接 Compose 包。它包含 compose 文件、示例环境变量、外部资源说明、启动命令、停止命令、备份位置和恢复说明。

还应保存一次 `docker compose config` 的结果。它代表最终生效配置。以后排查端口、环境变量和挂载问题时，先看最终配置，不只看源文件。

保存结果时标明环境。开发、预览和生产的最终配置可能不同。没有环境标签的配置截图，过几周就很难判断它当时代表哪台机器。

AI 可以帮你阅读 Compose 文件、解释配置合并和整理多服务排错路径。不要把 `.env`、Registry 凭据、生产数据库地址和用户数据交给它。下一章看容器状态、日志、健康检查和重启策略。
