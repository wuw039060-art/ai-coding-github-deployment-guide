# `.gitignore`、秘密泄露和历史中的敏感信息

项目需要配置才能运行，其中一部分配置可以公开，另一部分必须保密。API 密钥、数据库密码、SSH 私钥和签名口令一旦进入 Git 提交，就可能随着 Push 进入远程历史。`.gitignore` 能减少误提交，无法保护已经被 Git 跟踪的文件。秘密事故发生后，第一项工作是让凭据失效，再处理仓库历史。删除文件或把仓库改成私有都不能让已暴露的凭据重新安全。

## 哪些内容通常不进入仓库

项目源码、依赖清单、锁文件、公开配置样例和文档通常需要版本管理。下面内容常需排除，实际仍以项目技术栈为准。

- 依赖安装目录与可重建缓存
- 构建输出和临时文件
- 编辑器与操作系统产生的本地文件
- 含真实秘密的 `.env` 和凭据文件
- 本地数据库、用户上传和日志
- 私钥、签名文件与恢复码

“不进入 Git”与“可以删除”是两件事。本地数据库和签名密钥可能非常重要，只是需要放在受控存储和备份中。清理仓库时不要顺手删除原文件。锁文件是否提交由项目工具与协作方式决定。许多应用项目需要提交锁文件以固定依赖。不要使用一份泛化 `.gitignore` 把所有 `lock` 文件排除。

`.gitignore` 是普通文本文件，通常放在仓库根目录。每一行可以描述忽略模式。GitHub 官方文档说明，可以使用文件名、目录和通配模式，注释行以 `#` 开始。下面是一个示例，具体项目要按工具调整。

```
# 本地秘密
.env
.env.local

# 依赖与缓存
node_modules/
.cache/

# 本地日志
*.log
```

`.env` 只匹配相应位置规则下的文件，`.env.local` 单独列出。目录末尾斜杠帮助表达目录意图。`*.log` 会忽略匹配的日志文件。规则过宽会隐藏重要文件。例如忽略整个 `config/`，可能让公开配置模板也不再提交。新增规则后查看 Git 状态，确认只消失了预期文件。

GitHub 维护的模板仓库包含多种语言、工具和操作系统示例。选择相关模板，再根据项目修改。不要把整个模板仓库内容合并进一个 `.gitignore`。

## 已跟踪文件不会自动停止跟踪

一个文件已经 Commit 后，再把名称写进 `.gitignore`，Git 仍会追踪它。官方 Ignoring files 文档明确说明，需要先从跟踪范围中移除，同时根据需要保留本地文件。这里有两种完全不同的情况。普通生成文件误提交，但不含秘密，可以在确认影响后停止跟踪并提交删除。真实密钥已经提交，必须先撤销或轮换密钥，历史中还可能保留旧值。

停止跟踪的命令会改变索引。不同路径、模式和递归范围可能影响大量文件。本书不提供一条让读者直接粘贴到任意项目的命令。先用只读状态与文件列表确认目标，再按 Git 官方文档和实际备份执行。

团队需要知道项目要求哪些变量，可以提交 `.env.example`。其中写变量名、用途注释与无效示例值。

```
API_BASE_URL=https://api.example.invalid
AI_API_KEY=YOUR_API_KEY
DATABASE_URL=postgresql://USER:PASSWORD@HOST/DB
```

`.invalid` 是为无效域名用途保留的顶级域，适合文档示例；真实数据库地址、用户名和密码不能保留；示例值要让读者一眼看出需要替换；前端项目中，一些变量会在构建时写入浏览器代码；变量名带有框架规定前缀时，往往意味着公开；不要把供应商密钥放进去。部署平台的变量控制台也不能改变最终发送到浏览器这一事实。

## 什么算秘密

秘密是获得后可以冒充身份、访问数据、消费资源或解密内容的值。包括 API Key、Access Token、数据库凭据、私钥、会话 Cookie、签名密钥、Webhook Secret 和恢复码。

邮箱、域名和公开项目 ID 可能不是秘密，仍可能属于个人信息或内部配置。不要因为某个值无法直接登录，就全部公开。密码经过哈希后通常用于验证，哈希数据仍需要保护。加密数据的密钥与密文不能放在同一公开位置。签名公钥可以公开，私钥必须保密。

截图也会泄露秘密。终端提示、浏览器地址栏、二维码、环境变量页面和日志都可能包含令牌。提交 Issue 或询问 AI 前逐项遮盖。

## 建立秘密清单，但不记录秘密值

项目至少要知道自己使用哪些凭据。清单记录变量名、所属服务、用途、权限范围、使用环境、负责人、创建和到期日期、轮换入口。值本身放在密码管理器或平台秘密系统。例如 `SUPABASE_SERVICE_ROLE_KEY` 具有高权限，只应在受控后端使用。前端可用的公开项目标识与高权限服务密钥要明确区分。具体变量名和能力以平台当前文档为准。

清单还应记录哪些构建和部署能够读取秘密。预览环境不一定需要生产数据库权限。Fork 发起的自动化通常不应直接得到生产秘密。凭据长期无人负责时，轮换容易中断服务。负责人离开项目前要转移管理与恢复方式，随后撤销其个人访问。

记录首次提交时间、首次 Push 时间、仓库当时可见性、发现时间、旧凭据撤销时间、新凭据生效时间和历史清理时间。所有时间写明时区。这条时间线帮助检查暴露窗口内的审计日志。若凭据在公开仓库停留十分钟，不能只检查发现后的访问。缓存、Fork 和自动化也可能在窗口内取得内容。

记录每项动作的操作者与证据。撤销成功要有平台状态或旧凭据调用失败的验证。新部署成功要检查真实功能。改为私有要保存设置变化，但不能把它当作撤销证据。事故记录本身可能含敏感信息，应放在受控位置。公开复盘可以删除凭据标识、用户数据和内部安全细节，同时保留原因与预防措施。

## 前端密钥泄露的例子

一个网页项目在 `.env` 中写入 AI API 密钥。构建工具把特定前缀变量替换进 JavaScript。`.env` 已被 `.gitignore` 排除，开发者因此认为安全。部署后，浏览器下载的 JavaScript 包含真实值。任何访问者都可以通过源文件或 Network 取得。问题发生在构建产物，不在 Git 历史。

处置仍从撤销旧密钥开始。随后把供应商调用移到后端，前端只请求自己的受控 API。后端验证用户、限制用量并保存秘密。重新部署后检查前端产物与网络请求，确认密钥不再发送给浏览器。这个例子说明 `.gitignore` 只能管 Git；它无法决定应用运行时把值发送到哪里；安全审查要覆盖源码、构建配置和最终产物。

调试时打印完整请求头，可能把 Authorization Token 写进本地、部署或第三方日志。删除代码中的日志语句后，旧日志仍可能保留。先轮换已暴露凭据，再按日志平台能力限制访问与保留。不要直接删除所有日志，安全调查可能需要证据。组织环境应按事件响应和保留政策处理。

今后的日志只记录必要字段。令牌可以完全省略，或记录不可逆的短识别值用于关联。请求正文含密码、身份证或支付信息时，不应默认记录。错误监控与 AI 分析服务也是外部接收者。发送日志前使用过滤器，并确认服务的数据政策和地区要求。

## 历史清理完成后验证什么

验证默认分支、其他分支、Tag 和 Pull Request 引用中不再含目标内容。仓库搜索、Clone 出的新副本和秘密扫描结果可以提供证据。检查 Actions、Pages 与部署集成是否因提交标识变化而中断。Release 若指向旧标签，也要评估。协作者旧 Clone 不能直接 Push 回被清理历史。

保留清理前加密备份的期限与访问权限。备份本身仍含敏感内容，不能长期放在普通共享盘。达到事件与合规需要后，按批准流程销毁。再次确认旧凭据失效。历史清理成功不改变凭据服务状态，两条验证都要完成。

编辑器插件、Git Hook 和秘密扫描工具可以在 Commit 或 Push 前检查高风险模式。团队还可以在 GitHub 启用可用的秘密保护。自动检查要固定配置并记录更新。误报太多时，成员可能习惯绕过。处理误报应加入明确的无效样例规则，不能把整个目录关闭扫描。

Hook 位于本地时，新电脑未必自动安装。服务器端或平台保护提供更统一的最后防线。两者结合仍需要人工 Diff。自定义秘密格式可以用组织规则识别。规则测试使用无效样例，不使用真实凭据。更改规则后在测试仓库验证，不要先在生产仓库制造泄露。

## 数据文件误提交与密钥事故不同

数据库导出可能含个人数据，却没有可撤销的“密钥”。先限制访问、停止扩散并通知数据负责人。历史清理与缓存处理仍需要，影响评估要看数据类型、人数、地区与适用义务。误提交公司内部文档也不能通过轮换解决。确认谁已经访问、外部 Fork 与下载情况，并按组织流程处置。

不要把所有敏感内容事故都简化成“删 Git 历史”。凭据需要撤销，个人数据需要影响评估，版权内容需要停止分发，三种后续不同。

一些平台允许新旧密钥短时同时有效。可以先创建新值，更新服务，验证成功，再撤销旧值。另一些凭据一经重置，旧值立即失效。选择顺序前查官方文档。高风险泄露时，安全团队可能要求立即撤销，即使产生短暂停机。记录决策与影响。

多个服务共享同一凭据会让轮换范围扩大。逐步改成每个应用和环境使用独立凭据，权限与审计更清楚。轮换后搜索配置、CI、服务器和文档，确保没有组件继续使用旧值。失败日志不要打印新值。

## 二维码也可能包含秘密

一些服务用二维码传递登录会话、配置、Wi-Fi 密码或二步验证种子。把二维码截图放进 Issue、README 或视频，等于可能公开其内容。文档需要示意图时使用专门无效样例，不对真实二维码简单打模糊。图像压缩和缩放后，部分内容仍可能恢复。

手机扫码前确认来源和预期动作。二维码只是编码形式，不能证明链接安全。涉及登录授权时读清域名与权限。EPUB 中用于外部资料的视频二维码只编码公开 URL，不含账户令牌、跟踪参数和私人分享密钥。

部署平台通常会隐藏已经保存的秘密值，仍可能显示变量名、项目、环境和最近修改者。截图前检查这些信息是否可以公开。新增秘密时浏览器、剪贴板管理器和屏幕录制工具可能接触明文。使用受控设备，粘贴后清理不安全剪贴板历史。不要通过聊天软件传递。

平台允许查看旧值时，访问权限要更严格。审计谁读取、修改和用于部署。删除秘密前确认服务的替代值已生效。环境复制功能可能把生产秘密带到预览项目。复制后逐项减少权限，不把生产数据库写权限给不可信分支。

## 秘密事故后的复盘问题

事故来自哪个动作，为什么现有检查没有阻止，凭据权限是否过大，多久发现，怎样确认旧值失效，哪些日志与外部副本可能保留。改进应落到动作。例如添加 `.env` 规则、启用 Push protection、让预览使用独立只读凭据、提交前强制 Diff 审查。只写“提高安全意识”无法验证。

复盘不应惩罚报告者。快速报告能缩短暴露时间。团队需要清楚的私密上报入口和轮换权限。改进完成后用无效测试凭据演练。扫描应阻止 Push，轮换文档应能找到控制台，服务应在替换后恢复。

秘密事故后删除仓库可能破坏调查信息。先按组织流程保留提交、审计、Actions 记录和访问证据。备份要加密并限制人员。确认外部部署、Fork、缓存和本地 Clone。删除中心仓库不会删除这些副本。逐项处理并记录无法控制的范围。

若最终删除，核对准确 Owner 与仓库名。删除操作不可逆风险高，不用通配符或脚本批量处理不清楚的目标。

## 备份文件与配置导出也要进入忽略规则

编辑器和数据库工具常生成 `.bak`、`.sql`、`.zip` 或日期命名导出。它们可能含完整数据，文件名却不像秘密。先决定备份的受控位置，再为项目添加精确忽略规则。不要用 `*.sql` 一律忽略，因为仓库可能需要提交数据库迁移和公开种子数据。

提交前检查新出现的大文件和压缩包。Git Diff 无法展示压缩包内部，大小异常就是暂停信号。解压到隔离目录审查，确认来源后再决定。云同步文件夹也不是秘密存储。共享权限、版本历史和回收站可能保留旧副本。生产备份需要加密、访问控制和恢复验证。

旧令牌已经失效，仍可能暴露服务名称、账号结构和内部环境。仓库历史保留它还会反复触发扫描。文档展示凭据格式时使用供应商官方无效样例或明显占位符。不要取真实旧值做演示。截图也重新制作，不靠遮盖一小段。

安全审计报告需要引用旧值时，使用内部事件编号和受控证据位置。普通 Issue 与提交说明不包含明文。过期凭据的清理优先级可以低于有效泄露，仍应进入事件任务并验证删除范围。

## 发现秘密进入提交后的第一分钟

先停止继续 Push、构建和分享仓库。确认泄露的是哪一种凭据、属于哪个服务、具有什么权限。立即到凭据所属平台撤销或轮换。Rotate 译为轮换，表示生成新凭据并让旧凭据失效。高权限数据库密码可能还要检查活跃连接、审计日志和异常操作。

新凭据放入安全的秘密存储，并更新需要它的服务。不要先把新凭据写进同一文件再提交。验证服务使用新值后，确认旧值确实不可用。若凭据涉及客户数据、支付、组织账户或法律义务，按组织事件响应流程通知负责人。不要为了隐藏错误私自删除审计证据。

凭据轮换完成后，先回到凭据所属平台，确认旧值已经失效，新值只拥有业务需要的权限。随后检查仓库当前分支和历史，确认秘密不再出现在最新文件、提交 Diff、Release 附件和自动生成产物中。历史清理是否必要，要按仓库公开范围、凭据敏感程度和组织流程决定，不能因为文件从首页消失就结束处置。

第三个位置是部署环境。查看构建日志、缓存、镜像和平台变量，确认旧值没有被复制进产物，也没有在错误输出中继续出现。第四个位置是事件记录。写下发现时间、撤销时间、影响权限、查询过的审计日志、已通知的人和仍待核项目。公开记录只保留脱敏信息，原始证据放在受控位置。

四处都检查完，服务还要使用新凭据完成一次真实但低风险的请求。请求成功说明新配置能够工作，旧凭据拒绝访问说明撤销生效。若无法确认旧凭据是否被使用过，应保持事件状态为待调查，并按平台日志与组织要求继续处理。

## 为什么删除最新文件还不够

Git 提交保存历史。你在下一次提交删除 `.env`，旧提交仍可能包含它。别人可以查看历史、Fork、Clone 或缓存内容。把公开仓库改成私有可以减少后续访问范围，不能收回已经复制的值。删除仓库也无法证明外部副本消失。安全恢复依靠旧凭据失效，而非假设没人看见。

GitHub Push protection 可以在命令行 Push 时阻止部分受支持秘密，并给出处理入口。它是一道防线，不能覆盖所有自定义格式，也不能替代提交前检查。

旧凭据失效后，可以评估是否需要从历史中移除敏感内容。GitHub 官方说明建议使用专门历史重写工具，并强调重写会改变提交标识，影响分支、Tag、Pull Request、Fork 与其他协作者。

这是需要协调的维护操作。先做仓库完整备份，列出受影响引用，暂停协作者 Push。清理后要验证远程历史、分支、Tag 和自动化，再让协作者重新同步或重新 Clone。历史清理也不能删除外部 Clone 和缓存。旧凭据已失效仍是第一道保证。若敏感内容属于个人数据或受监管信息，应按适用流程处理平台缓存和通知。

本书不会给无条件复制的历史重写命令。仓库结构、保护规则和协作状态不同，一条命令可能删除无关历史。

> 高风险操作
>
> 不要在唯一仓库副本中试验历史重写。不要在协作者仍 Push 时改写共享历史。不要把轮换后的新秘密再次放进提交。

## 一个完整事故例子

小陈把邮件服务密钥写进 `.env`，Commit 后 Push 到公开仓库。五分钟后，他删除文件并再次 Push，以为问题结束。正确处置从邮件服务控制台开始。他撤销旧密钥，创建权限更小的新密钥，把它保存到部署平台秘密变量。重新部署后，用测试邮件验证新值，并确认旧值调用失败。

接着检查服务审计记录，看五分钟内是否有异常发送。仓库改为私有以减少访问，但记录中明确写出这不能撤回泄露。随后备份仓库并按 GitHub 官方指导协调历史清理。最后在 `.gitignore` 中加入 `.env`，提交无效值的 `.env.example`，启用可用的 Push protection，并在交接文档中写出轮换位置。这个过程同时处理当前风险和下一次预防。

扫描器可能发现看起来像令牌的字符串。先确认文件、提交和匹配类型。测试数据也可能误报，真实秘密也可能因自定义格式漏报。对可能有效的值，按真实泄露处理，先撤销或验证其状态。不要把完整值粘贴到搜索引擎或公开验证网站。

标记误报前要说明依据，例如值来自官方无效示例域、凭据已撤销或格式只是随机测试字符串。关闭提醒不能改变凭据状态。

## 本地配置怎样安全交接

仓库提交 `.env.example` 与配置说明。真实值通过组织批准的密码管理器或平台秘密系统分享。接收者按最小权限创建自己的凭据，避免多人长期共用同一高权限令牌。交接记录变量名、所属服务、用途、权限、创建者、到期时间和轮换入口，不记录明文值。人员离开项目时撤销其个人凭据，更新共享秘密。

服务器上的 `.env` 文件要限制读取权限，备份也要加密和控制访问。命令历史与进程列表可能暴露直接写在命令参数中的秘密，优先使用安全输入和秘密注入方式。

它不能加密文件，不能阻止其他程序读取本地内容，不能清除历史，也不能控制部署平台日志。它只告诉 Git 哪些未跟踪路径通常不进入版本管理。团队成员可以使用强制方式添加被忽略文件，因此仍需审查与仓库保护。构建脚本也可能主动读取被忽略文件并打包到产物，前端秘密就会泄露给浏览器。

数据备份也不能依赖忽略规则。被忽略文件往往恰好包含本地配置和用户数据，需要单独备份或可重复生成。

## 提交前的秘密检查

先查看所有新增与修改文件，展开 Diff。搜索常见变量名与私钥头部，确认没有 `.env`、数据库导出和日志。检查二进制压缩包来源，因为 Diff 不能展示其内部文字。随后看将要 Push 的所有本地提交，不只看工作区。秘密可能在前一个 Commit 中已经删除，却仍会随历史首次 Push。

最后确认仓库可见性、远程所有者和分支。公开仓库的检查标准更严格，私有仓库仍使用同一秘密规则。

`.gitignore` 没生效，先看文件是否已经跟踪、规则文件是否在正确仓库，以及模式是否被后续规则覆盖。不要删除 `.git` 重来。Push protection 阻止提交时，阅读匹配文件和秘密类型。真实凭据先轮换并从提交中移除。不要为了通过检查就选择绕过理由。

历史清理后协作者 Push 又带回旧提交，说明同步协调没有完成。暂停 Push，确认每个 Clone 的处理方式，再恢复协作。

## 秘密进入历史以后该查哪些证据

AI 可以只读扫描文件名和 Diff 中的高风险模式，检查 `.gitignore`，生成无效示例配置，并制定轮换与验证清单。不要把真实秘密发给 AI 来问它是否有效。让 AI 执行历史重写前，必须有人核对备份、引用、协作者和恢复方案。

撤销凭据、查看审计日志、判断数据影响、通知相关人员和批准历史重写必须亲自完成。新密钥的最终权限与生产部署也要人工确认。第二卷到这里结束。下一卷从浏览器、客户端和服务器开始，解释 GitHub 之外的请求怎样在网络中移动。
