# 计划、权限、Diff、测试和验证证据

AI 已经理解项目以后，下一步仍不是立刻修改。一个受控工程任务需要把需求转成验收标准，限定文件与外部权限，做最小改动，审查 Diff，运行与风险相称的测试，再把结果绑定到准确版本与环境。任何一环缺失，“已经完成”都可能只代表 AI 停止输出。

计划的作用是暴露假设，权限的作用是限制最坏影响，Diff 让人看见实际修改，测试寻找行为错误，验证证据说明哪些检查真的运行过。它们共同组成一个可以中途拒绝、失败后回退、完成后复查的过程。非专业读者无需读懂每行代码，也能通过范围、证据和可见结果保留控制权。

## 把需求写成可失败的验收标准

“优化登录”“修好上传”“让页面更专业”都缺少可判断结果。验收标准应包含前置状态、动作、成功结果、失败结果与不应改变的行为。例如“未登录用户上传头像时返回 401，已登录用户上传两兆 PNG 时生成头像并在刷新后保留，超过五兆时返回明确提示，原文件不公开，旧头像可正常显示”。

标准要覆盖异常和边界。只写成功路径，AI 容易为演示样例做出看似有效的实现。至少问空值、最大长度、权限拒绝、网络超时、重复提交、旧版本与数据失败会怎样。风险越高，边界越具体；纯文字修改不需要数据库恢复计划，支付与删除功能则需要。

把“不做什么”也写进标准。修一个按钮不允许升级全部依赖，不改变数据库结构，不重排无关文件，不增加生产服务。范围之外发现的问题进入单独 Issue，不能借当前任务顺手重构。这样 Diff 的每一行都能追溯到需求。

AI 很容易把一个信息不全的需求补成完整故事。它看到静态配置，就可能假定生产也使用同一值；看到一个测试通过，就可能假定真实数据库与测试替身行为一致。计划开始前，先列出会改变方案的未知条件，例如生产分支、数据规模、账号权限、现有备份、旧客户端兼容和外部服务限制。能够通过只读检查确认的先确认，需要账号持有人或真实设备回答的保留为门槛。

每个未知条件都应对应一个动作。生产分支未知，就去控制台核对；备份是否可用未知，就查看最近恢复记录；iOS 真机行为未知，就把真实设备验收留给有条件的人。无法确认且影响较小的条件，可以写出保守假设并限制修改范围。涉及删除、迁移、付费、公开发布和真实凭据时，不能靠假设继续。

停止点也要提前写进计划。第一条基线测试失败，目标文件与报告不符，Diff 超出授权范围，备份不存在，生产日志显示正在发生事故，任何一项都可能要求暂停。提前约定停止点以后，暂停就不再意味着执行者能力不足，它是计划本身的一部分，保护项目不在未知条件上继续扩大变化。

## 计划要连接文件、动作和验证

一份有效计划通常有三到七步，每步写将修改什么、为什么、怎样验证。例如先补一个会失败的权限测试，再修改服务端授权，随后运行目标测试与相邻测试，最后检查网页实际响应。计划不是对结果的保证，它只是把假设和检查顺序提前公开。

开始前要求 AI 列出预计涉及文件、可能生成的文件、需要的命令、外部服务和风险。若它无法解释为什么要改某个目录，就先回到项目理解。OpenAI 的大型代码库用例强调在编辑前追踪模块责任、验证与副作用。

计划也要写停止点。发现真实秘密、需要生产账号、数据库迁移不可逆、工作区已有冲突改动或测试基线失败时，停止并报告。没有停止点的自动化会把意外情况当成继续猜测的理由。

读取项目文件通常风险最低，但敏感目录、日志与用户数据仍要排除。写入文件会改变工作区，执行命令可能安装依赖、生成文件、启动服务或访问网络。外部状态包括推送仓库、部署、发邮件、修改 DNS、操作数据库、发布商店和产生费用，需要更明确授权。

不要用“可以操作项目”覆盖所有类别。可以授权“读取仓库并修改测试分支，允许运行现有测试，不允许安装新依赖、联网、推送或访问生产”。任务后续确实需要扩大权限时，AI 应说明目的、准确命令、目标、预期结果与风险，再由用户决定。

OpenAI 的沙箱与审批文档说明可以限制文件系统、网络和高影响操作。沙箱降低越界概率，却不能判断某个获准目录中的数据库备份能否删除，也不能知道一次合法 API 调用是否会向真实用户发信。技术限制与业务判断要同时存在。

## 最小权限还包括凭据范围

测试应使用专用测试账号和数据，预览部署使用预览环境秘密，生产秘密只在批准后的受保护环境注入。给 AI 一个云平台主令牌，随后要求它“只部署测试站”，依赖的是自律，不是权限控制。令牌本身应只能访问目标项目和必要动作。

GitHub Environments 可以把部署分支、环境秘密与人工审批组合起来。官方资料说明，启用审批时，作业在通过要求前不能访问环境秘密，也可以限制部署分支和防止自审。具体功能与套餐限制可能变化，截至 2026 年 8 月 6 日的规则应在封版前再次核对。

自托管 runner 可以接触主机资源，受保护 Environment 不会自动把它变成隔离容器。工作流脚本与第三方 Action 仍需审查。生产凭据不要出现在 AI 对话、Diff、日志和测试快照中。

先运行 `git status` 或平台等价检查，记录当前分支、提交与已有改动。现有未提交文件可能属于用户，AI 不能覆盖或回退。若基线测试已经失败，把错误保存并说明与当前任务是否相关，不能在修改后把同一个旧失败算作新回归。

基线还包括可见行为。网页截图、API 状态、数据库测试记录、性能数字和版本输出能帮助比较。视觉任务尤其需要修改前图片，否则“更好看”只能依赖记忆。OpenAI 的 Computer Use QA 用例强调沿真实用户路径操作并记录结果。

有破坏风险的任务先确认备份与回退。备份是否可用由恢复测试证明，Git 提交也不能替代数据库与用户上传备份。只改本地文案通常不需要额外快照，应按风险控制成本。

## 最小修改让因果更清楚

AI 应只修改实现验收标准所需的行，并删除自己造成的无用代码。不要顺手格式化整个文件、更新全部依赖、改命名或重写相邻模块。Diff 越小，人越容易审查，失败时也更容易回滚。“最小”不等于故意留下半套实现。若新增字段需要验证、数据库迁移、API、界面和测试，这些都属于必要范围。计划应提前说明跨层变化，避免只改前端制造暂时演示。最小修改衡量的是与需求的直接关系，不是文件数量越少越好。

生成配置与锁文件时，要区分预期变更和工具噪声。一个依赖升级可能改动数百个间接版本，若任务不需要就停止。必须升级时单独审查版本、发布说明、安全与回滚，不能把巨大锁文件藏在功能 Diff 里。

计划写“只改登录提示”没有证明任何事情，Diff 才显示 AI 实际触碰了什么。审查先看文件列表与增删规模，再逐块看行为。发现任务外文件、二进制、秘密、生成产物或大范围格式变化时暂停，要求解释或拆分。

逐块审查可以问五件事。这段变化对应哪条验收标准，正常路径怎样，失败路径怎样，权限与数据有什么影响，测试在哪里。非专业读者可以让 AI 用自然语言解释每个块，同时要求指向具体行；随后抽查文件，不能只读 AI 自己的摘要。

删除往往比新增更危险。删掉验证、错误处理、迁移兼容、日志和回退代码时，要求说明替代机制。配置中的一个字符可能改变公网暴露与生产资源，行数少不代表风险低。OpenAI 的代码审查资料支持用 Codex 检查变更，GitHub 的 PR Review 允许评论、批准或请求修改。AI 审查可以发现线索，仓库所有者仍要核对业务规则与实际环境。需要阻止合并时，还必须配置对应仓库规则，仅在评论中选择“请求修改”未必自动形成技术门禁。

## 先看测试是否真的覆盖改动

静态检查发现语法、类型、格式和部分安全问题，单元测试验证小函数，集成测试验证数据库或 API，端到端测试验证真实用户路径。没有一种测试自动覆盖全部。选择组合时从改动风险出发，先运行最相关的快速测试，再扩大到相邻模块和完整套件。

修 Bug 时最好先添加能复现问题的测试，确认它在修复前失败、修复后通过。若测试从未失败，可能测错了路径。无法自动化的界面或平台流程，记录人工步骤、环境、预期和实际，并解释为什么没有自动测试。

测试命令必须来自项目脚本、CI 或官方文档，不让 AI猜一个看似常见的命令。运行位置、依赖、环境变量和数据目标要明确。测试可能创建文件、迁移数据库或发网络请求，执行前先读配置。

“已运行测试”至少要回答运行了什么、在哪个提交和环境、退出码、通过多少、跳过多少、耗时、失败和产物。只贴最后一行绿色文字，会丢失跳过、警告和版本信息。证据可以压缩，但必须能让另一人复查。

下面是一个验证记录模板。字段使用冒号便于机器生成，真实值不含秘密。

```
提交或工作区状态：
操作系统与运行时：
命令：
开始与结束时间：
退出码：
通过：
失败：
跳过：
警告：
报告或截图：
测试数据与环境：
仍未验证：
```

命令退出码为零通常表示工具认为成功，不代表测试设计足够。测试只运行空目录、错误筛选没有匹配用例、网络用例被跳过，都可能得到绿色。检查测试数量、目标文件、报告和 CI 配置，确认真正覆盖当前变更。

## GitHub 状态检查需要解释状态

GitHub 状态检查可以呈现构建、测试、代码扫描与部署结果，并绑定到具体提交。受保护分支可要求检查通过后才允许合并。GitHub Actions 快速入门展示了工作流由提交触发并在 Actions 页面留下运行记录。

绿色仍需看结论类型。GitHub 官方文档指出，被跳过的工作流在某些条件下会报告 Success，neutral 与 skipped 对依赖检查也可能按成功处理。取消、超时、未启动和运行旧提交都不能当作当前改动已验证。检查 run 对应的 SHA、触发事件、矩阵任务与每个必需作业。

状态检查也可能被具有权限的集成写入，因此它是证据机制的一部分，不是数学证明。关键仓库结合必需检查、评审、代码所有者和部署保护，减少单点误判。规则变更本身也应经过审查与审计。

本地通过、CI 失败时，比较操作系统、大小写路径、运行时、依赖锁、环境变量、时区和外部服务。CI 通过、生产失败时，再比较构建产物、部署配置、数据库版本、网络和真实数据规模。验证记录必须写环境，不能用“电脑上没问题”覆盖全部。

预览环境适合真实构建和交互检查，仍应使用隔离数据与权限。若预览共享生产数据库，一个自动端到端测试就可能修改用户记录。环境名称相似不代表资源隔离，查看实际连接、项目 ID 和权限。移动 App 还要区分模拟器、测试设备、内部测试与商店构建。签名、优化、权限和平台处理会改变行为。没有真实 Mac 和开发者账号时，明确 iOS 发布未实机验证，不用 Android 结果代替。

## 先按风险决定流程强度

低风险变更包括错别字、无行为变化的说明和隔离测试数据，通常用 Diff、构建与页面检查即可。中风险变更涉及业务逻辑、依赖、缓存和普通 API，需要相关测试、预览与代码评审。高风险变更涉及认证、权限、生产数据、支付、秘密、网络入口、迁移和不可逆删除，需要独立评审、备份恢复、受保护部署与人工批准。

风险等级来自最坏后果、影响范围、可恢复性和不确定性，不只看代码行数。一行防火墙规则可能高风险，新增一百行测试通常风险较低。计划中写等级与理由，发现范围扩大时重新分级。流程也不能机械过重。为一处文案要求数据库灾难演练会浪费注意力，让人更容易忽略真正高风险批准。建立最低门槛，再按数据和外部状态增加检查。

计划可以设一个变更预算，例如预计修改三到五个文件、不新增生产依赖、不改变 schema。预算不是硬性数字，超过时必须停下解释。这样能早期发现 AI 从修 Bug 逐渐滑向重构。新增依赖、迁移、权限与公共接口自动触发重新计划，即使文件数量仍少。重新计划说明为什么原方案不足、增加什么验证和回滚。用户可以接受、拆分或拒绝，不让扩大范围成为默认。

任务完成后对比实际与预算。差异合理就更新记录，不合理就删除任务外修改或拆分提交。这个过程也帮助非专业读者用形状判断复杂度。

## 不稳定测试不能靠重复到绿

同一提交在相同环境中时过时不过，称为不稳定测试。连续重跑直到绿色会隐藏竞态、时间、共享数据或网络问题。记录每次结果、随机种子、并发、机器和发生频率，单独创建修复任务。当前变更若明显导致不稳定，不能以“一次通过”合并。既有不稳定测试与任务无关时，报告基线与本次结果，评估它是否覆盖当前风险。关键门禁长期不稳定会削弱整个检查体系，应优先修复或替换。

允许重试的 CI 要展示首次失败与重试次数。最终绿色旁保留不稳定标记，不能只保存最后一轮。时间依赖测试使用可控时钟，网络依赖使用可控替身并保留少量真实集成验证。

代码覆盖率说明执行到哪些行或分支，不说明断言是否正确、需求是否完整。百分之九十覆盖仍可能漏掉越权和数据回滚，低覆盖也不能直接证明当前改动错误。用覆盖报告寻找未执行区域，再回到风险与验收设计测试。

测试应包含会失败的断言。只调用函数而不检查结果，能够提高覆盖率却没有保护行为。Mock 过多可能让测试验证自己设定的回答，真实数据库、文件或 HTTP 边界仍然失败。分层组合比追求一个数字更可靠。

覆盖率阈值若作为门禁，配置变化也要评审。为了通过而排除新目录或降低阈值，应有明确理由和后续计划。AI 不得自行修改阈值隐藏失败。

## 缓存会制造虚假成功和虚假失败

依赖缓存、构建缓存、测试结果缓存和浏览器缓存可以加速流程，也可能让旧产物混入。CI 记录缓存键与命中，关键发布至少有一次从锁文件干净构建。发现本地与 CI 不一致时，先比较缓存与生成步骤，不立即删除所有环境。

清缓存属于状态修改。执行前保存原始错误与构建信息，限定可重建目录，不能删除用户数据、签名和唯一产物。清理后按文档重新生成，并比较是否真正改变结果。缓存命中后也要确认产物绑定当前提交。构建系统若没有把配置或锁文件纳入缓存键，会复用错误结果。修复缓存键后增加回归检查，不把每次禁用缓存当长期方案。

普通代码评审关注正确性，安全审查问不可信输入从哪里进入、经过什么验证、获得什么权限、能访问什么资源和错误会泄露什么。新增上传、Webhook、URL 抓取、认证与管理接口时，画一条攻击路径，比搜索几个危险字符串更有效。

OpenAI 代码审查与安全变更用例可以帮助扫描 Diff，输出仍要绑定具体行和可复现实验。误报由人说明排除理由，漏报则通过授权测试、依赖扫描和项目威胁模型补充。AI 不应在未授权仓库或系统进行主动攻击测试。

安全测试既验证拒绝，也验证合法用户仍能使用。防护把全部请求都阻止不算成功。生产扫描限制时间、速率与范围，优先在隔离环境执行。

## 保存证据也要控制隐私和期限

CI 日志、截图、HAR、崩溃报告和数据库测试结果可能包含秘密与个人数据。证据包只保留必要窗口，脱敏后共享，原始材料限制访问并设置删除日期。通过测试不能成为无限期保存用户数据的理由。

证据索引记录文件、提交、环境、生成时间、用途和保留期限。哈希可以验证文件未变，不能证明内容正确。关键发布保留与组织政策相称的证据，普通开发日志按较短期限删除。NIST 关于来源与评估记录的建议支持可追溯性，仍需结合隐私与安全规则。项目手册说明证据在哪里、谁能看和何时清理，不把敏感附件散落在多个聊天。

AI 或命令可能因超时、网络、权限和应用关闭中断。失败返回不等于什么都没改变，配置文件可能写了一半，依赖可能安装部分，外部平台也可能已经收到请求。恢复前先查看工作区、进程、临时文件、平台活动与实际资源。

能够原子写入的工具应先写临时文件、验证后替换；数据库使用事务；部署使用不可变产物与平台状态。并非每种外部操作都支持原子性，因此文档写幂等键、查询状态和补偿。不要在未知状态下连续重试。

重新运行前确认上一轮副作用。邮件是否已发、迁移是否已执行、资源是否已创建、DNS 是否已更新，都要用外部证据回答。AI 若只看本地错误就建议重跑，人工门禁应要求状态查询。

## 并行验证的结果最终要汇合

静态检查、单元测试、界面 QA 和安全评审可以并行，各自绑定同一基线提交。任何一个过程修改文件后，原有结果就可能过期。设一位集成人确认最终提交，重新运行受影响检查并汇总冲突。不同评审结论冲突时，回到证据与实验。一个 AI 说安全、另一个说越权，不能按多数表决；用普通用户测试目标 API、检查服务端授权和日志。无法消除的高风险冲突阻止生产发布。

最终证据包只有一个版本，旧报告标记 superseded 或归档，避免批准者打开错误链接。合并与部署页面直接指向当前 SHA 和产物摘要。

每份证据都应能回答“验证了哪一个版本”。代码提交 SHA、构建号、镜像摘要、部署 ID 和应用版本是常见标识。修改测试后重新构建，旧截图与旧报告不能继续证明新版本。发布前核对审批看到的 Diff 与实际待部署产物属于同一提交。

构建产物最好有校验或平台生成的不可变标识。使用会变化的 `latest` 标签，会让“测试过这个镜像”失去准确对象。记录依赖锁与构建环境，必要时保存软件物料清单，具体深度按项目风险决定。NIST 的生成式 AI 风险资料建议用已知事实、多种评估方式、自动评估与人工监督检查生成式 AI 输出。在代码任务中，这意味着 Diff、测试、静态分析、真实路径和人审彼此补充，不能让 AI 自己写代码、自己总结、再用同一总结证明完成。

## 人工评审关注业务与不可逆影响

AI 很擅长识别模式，却可能不了解“这个旧字段必须保留两年”“这个按钮需要财务批准”或“这个地区不能启用该服务”。代码所有者和业务负责人应检查权限、数据、费用、用户沟通与政策。高风险变更至少由未实施的人复核。

评审不只是点 Approve。审查者要确认验收标准、Diff、测试、未验证项、回滚和发布观察。新提交改变代码后，重要评审应重新请求，避免旧批准覆盖新内容。GitHub PR Review 提供重新请求与未解决讨论跟踪，是否强制仍取决于仓库规则。

一个人维护的项目也可以把实现和评审分时进行。先让 AI 实施并保存证据，隔一段时间后从用户目标重新检查，或让另一个独立审查过程只读 Diff。独立性来自重新验证假设，不是换一个相同提示让 AI再说一次“没有问题”。

测试失败后先保存第一条有效错误、退出码与环境。对比基线失败，判断当前修改是否新增。不要立即清缓存、升级依赖和改配置，多个动作会破坏因果。提出一个可证伪假设，再做最低风险检查。若失败来自无网络、缺少平台账号或本机没有 Mac，标记为环境门槛，不伪造通过。可以完成静态检查和其他平台测试，但交付结论必须列出未验证部分与需要谁来完成。阻塞证据越具体，用户越容易决定下一步。

发现测试本身错误时，修测试也要单独审查。不能为了让 CI 变绿删除失败断言、扩大允许范围或标记跳过。若产品要求确实改变，更新验收标准、测试与文档，说明为什么旧行为不再适用。

## 回滚计划在修改前写

代码回滚要知道稳定提交和重新部署方法，配置回滚要保存旧值与来源，数据库迁移要考虑旧程序能否读取新结构。外部邮件、支付和用户数据无法通过 Git 回滚，需幂等与补偿。风险越高，发布前验证回滚越重要。

小改动也应有最低回退，例如恢复原文件并重新构建。不要使用会覆盖用户未提交改动的命令。共享历史使用新提交撤销通常比强制重写更安全，具体流程遵守项目规则。回滚后仍要运行核心测试和生产观察，确认流量、版本与数据实际恢复。回滚只是另一项变更，也可能失败。发布记录保留实施、回滚与最终状态，不能用“已经回滚”结束证据链。

假设 Preview 环境上传返回 413，生产正常。项目地图显示代理和应用都有限制。计划先复现两兆成功、六兆失败，读取当前 Preview 配置，不接触生产；验收标准要求五兆以内通过、超过五兆得到明确提示，应用内存不异常增长。

AI 发现 Preview 代理上限为一兆，应用上限为五兆。最小修改把代理上限调整到略高于业务上限，让应用负责一致提示，并增加配置测试。Diff 只有配置、测试和说明，没有改生产环境、上传代码或依赖。

验证记录包含配置语法检查、自动测试、Preview 两兆与六兆实际请求、代理和应用日志、内存观察及提交 SHA。维护者审查后批准 Preview 部署，再由账号持有人决定生产是否需要同类变更。这个过程的可信度来自范围和证据，不来自 AI 对配置语法的自信。

## 交付前做一次反向审查

完成后从失败角度重新问。哪个输入没测，哪个权限可能扩大，哪个环境与生产不同，哪个日志会泄露秘密，哪个回滚假设未经验证。尝试最小权限账号、重复提交、网络中断、旧数据与最大输入，修正发现的问题。

反向审查还看任务外影响。共享组件有多少消费者，配置是否改变缓存或代理，新增依赖是否执行安装脚本，删除字段是否影响旧客户端。每项风险要么有测试，要么明确由负责人接受，不用“应该没问题”结案。

最终报告只写实际完成内容、测试证据、未验证项与下一步。不要把计划中的动作当成已经执行，也不要把无权限环境推断成已验证。用户应能从报告回到 Diff、测试和运行结果，而不是相信一段漂亮总结。

- 需求已经写成包含成功、失败与不变项的验收标准
- 计划列出文件、命令、外部系统、风险和停止点
- 读取、写入、执行、网络和外部状态分别授权
- 修改前记录分支、提交、已有改动和测试基线
- Diff 只包含能追溯到需求的必要变化
- 删除、配置、锁文件和生成产物经过专门审查
- 测试覆盖原问题、异常路径与相邻功能
- 证据记录命令、环境、退出码、通过、失败和跳过
- 状态检查对应当前提交，未把 skipped 当成完整通过
- 真实用户路径使用隔离账号与数据验证
- 人工评审检查业务、权限、数据、费用和回滚
- 最终报告明确实际完成与仍未验证内容

计划、权限、Diff、测试和证据形成一条可追溯控制线。AI 可以快速执行其中许多动作，人保留范围、授权、验收与发布判断。只要每一步都能回到准确文件、版本和可见结果，非专业开发者也能知道项目究竟改变了什么，以及为什么可以继续。
