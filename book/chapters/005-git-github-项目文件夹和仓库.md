# Git、GitHub、项目文件夹和仓库

一个网页项目最初可以只是普通文件夹。你可以复制它、压缩它、用微信发送它，也可以把它改坏后再从备份找回来。文件夹变成 Git 仓库后，项目多了一套版本记录。Git 知道哪些文件发生变化，也能把一组变化保存成一个提交。

GitHub 是提供远程 Git 仓库和协作功能的网站。Git 与 GitHub 经常一起使用，仍是两个对象。电脑断网时，Git 仍能在本地查看变化和创建提交。需要把提交传到 GitHub，或者取得别人的远程更新时，才需要网络与账户权限。

## 先认识一个普通项目文件夹

假设文件夹中有下面内容。

```
my-site/
  index.html
  styles.css
  images/
    logo.png
  README.md
```

你在 `styles.css` 中把背景色改了，操作系统只知道文件内容与修改时间变化。它不知道这次改色的目的，也不知道应该和 `index.html` 的哪项修改放在一起。复制整个文件夹可以保留一个版本。有人会得到 `my-site-final`、`my-site-final-2` 和 `my-site-really-final`。这种方法在文件很少时能救急，版本一多就难以回答几个问题。哪一份已经上线，哪一份包含昨天修复，两个副本之间改了什么，哪些文件应合并。

Git 把这些变化保存在项目内部的版本历史中。你仍然使用原来的文件夹编辑文件，不需要为每次修改复制一份完整目录。

## 仓库是在文件夹上增加版本管理

Repository 通常译为仓库。本书提到 Git 仓库时，指由 Git 管理的一组项目文件及其版本历史。Git 仓库常简称 Repo。在现有项目中初始化 Git 后，根目录会出现隐藏的 `.git` 目录。它保存提交、分支和其他内部信息。普通源码仍在原来的位置。删除 `.git` 不会立刻删除工作文件，却会移除这份本地版本历史与仓库关系。不要手动编辑或清理其中内容。

仓库根目录是 `.git` 所属项目的最外层。你可以在它的子目录中运行许多 Git 查询命令，Git 会向上找到仓库。一个大文件夹中也可能放着几个彼此独立的仓库。看到某个父目录叫 Projects，不能推断它本身就是一个仓库。

GitHub 仓库是远程副本。它有所有者、名称、可见性、默认分支和提交历史，还可以带 Issue、Actions 与 Release。一个本地仓库可以暂时没有 GitHub 远程仓库。GitHub 上也可以先创建空仓库，后来再把本地提交推上去。

![一次文件变化从本地到 GitHub 的流转](../assets/diagrams/git-change-flow.png)

*一次文件变化从本地到 GitHub 的流转*

图中的实线从左到右。文件保存后先进入本地工作区，选择后成为本次提交范围，Commit 后进入本地历史，Push 后才进入 GitHub 远程分支。下方虚线表示远程变化回到本地时，先 Fetch 取得状态，再由 Pull 整合提交。

初学阶段可以先把一次改动看成三个阶段；工作区是你正在编辑的文件；保存以后，Git 能看到内容变化；暂存区保存准备放进下一次提交的变化；提交把选中的变化记录进本地历史。GitHub Desktop 用复选框表现“哪些变化进入这次提交”。勾选文件后填写 Summary，再创建 Commit。没有勾选的变化会留在工作区，等以后处理。

例如，你同时修改首页文字和一个测试配置；首页已经准备上线，测试配置仍在试验；可以只选择首页文件创建提交。提交主题写“更新首页活动时间”，比“改一下”更能帮助后来的人判断版本内容。一次提交应围绕一项可以说明的工作。修复图片路径与重写全部页面样式若没有依赖关系，分成两个提交更容易审查和撤销。这里没有要求每改一行就提交。提交范围应让人能解释为什么这些文件一起变化。

## 提交是记录，保存文件只是写入磁盘

编辑器按下保存后，文件内容进入磁盘。Git 状态会显示它被修改。此时关闭编辑器再打开，变化仍在，但提交历史没有新记录。创建 Commit 后，Git 为这组内容生成标识，并保存作者、时间和提交说明等信息。之后继续修改同一文件，Git 能比较当前内容与最近提交。

提交没有把内容自动发送到 GitHub。Push 才会把本地提交送到远程。反过来，GitHub 网页上的新提交也不会自动写入已打开的本地文件夹。Fetch 会查询远程状态，Pull 会在取得远程提交后把变化整合到当前本地分支。第八章会分别演示这些动作。

下面这个例子能看出四个状态。

1. 保存 `README.md`，GitHub Desktop 的 Changes 出现一项。
2. 创建 Commit，Changes 归零，本地 History 出现新记录。
3. 尚未 Push 时，GitHub 网站仍看不到该提交。
4. Push 成功后，远程分支出现相同提交。

任何一步的成功都只证明当前动作完成。Changes 归零也可能因为文件被忽略，或者打开了错误仓库，所以还要看当前路径与提交内容。

## 分支让同一仓库保留多条工作线

Branch 译为分支。创建仓库时会有默认分支，GitHub 新仓库通常使用 `main`。分支指向一系列提交，让新工作可以先与稳定版本分开；假设生产部署监听 `main`；你创建 `new-home` 分支修改首页，推送后可以在预览环境检查；确认无误再通过 Pull Request 合并到 `main`；这能减少半成品直接影响生产的机会。

分支没有复制出另一套 GitHub 账户，也没有自动创建备份。两个分支可以修改同一个文件，合并时 Git 会尝试组合变化。改到同一位置且无法自动判断时，就会产生冲突。个人项目不必为每个标点建立分支。修复很小、没有协作、又能立即验证时，可以直接在默认分支完成。涉及较大改动、试验或生产部署时，独立分支更容易审查。选择依据是风险和协作需要。

README 是仓库的入口说明。GitHub 会在常见位置自动展示 README。一个对初学者友好的 README 至少说明项目用途、运行条件、最小启动步骤、构建方式和许可证。

Issue 可以记录缺陷、需求和任务。Pull Request 展示一个分支准备合并的变化，并容纳审查讨论。Actions 可以根据提交运行测试或部署任务。Release 可以围绕一个版本提供说明和下载文件。

这些功能共享仓库的版本信息。Issue 可以引用提交，Pull Request 能显示文件 Diff，Actions 运行记录对应某个提交。它们让“为什么改”和“改后发生什么”留在同一项目附近。

## GitHub 不是自动备份系统

远程仓库能保护已经提交并推送的文件，仍有明确边界。未保存、未提交、未推送的内容不会出现在远程。`.gitignore` 排除的文件也不会进入正常提交。数据库、上传文件和部署平台里的环境变量通常不在代码仓库中。

账户被锁定、仓库误删、历史被强制改写时，远程版本也可能受影响。重要项目应有独立、可恢复的备份，尤其要覆盖仓库之外的数据和密钥恢复材料。Git 的主要职责是版本控制。它能找回历史文件，不能代替数据库备份策略，也不能保证所有误操作都容易恢复。把“已经放 GitHub”写进备份清单时，还要注明覆盖哪些内容、怎样恢复、多久验证一次。

提交记录通常包含作者、时间、说明和父提交关系。查看某个文件的历史，可以知道哪次提交改了它。逐行归属工具还能显示某一行最后由哪个提交改变。这些记录是调查线索，不直接证明责任。一次自动格式化可能让同一个人显示为整份文件的最后修改者，真正业务内容来自更早提交。共享账号也会让作者信息失去区分度。

排查时先看引入变化的提交 Diff，再读相邻提交与 Pull Request 讨论。例如价格计算突然错误，某次提交改了公式。提交说明写“重构计算”，Issue 又说明要支持新折扣。只有把代码变化与需求放在一起，才能判断修复方向。

Git 的作者姓名和邮箱来自本地配置。新电脑第一次提交前应核对身份，避免用错误邮箱进入公开历史。提交公开后，邮箱隐私设置与显示规则以 GitHub 当前文档为准。

## 未跟踪、已修改和已删除表示什么

Untracked 表示文件存在于工作目录，尚未进入 Git 跟踪。新建 `notes.txt` 后常看到这个状态。Modified 表示已跟踪文件内容改变。Deleted 表示 Git 记录过的文件在工作目录中被删除。

看到 Deleted 不要立即提交。文件可能被用户误移动，也可能由构建清理删除。打开文件资源管理器和 Diff，确认删除意图。若只是改名，Git 最终可能根据内容识别重命名，提交前仍要核对新旧路径。

Untracked 也不能一律加入。它可能是新源码，也可能是日志、数据库或密钥。先打开内容和来源，再决定提交或加入 `.gitignore`。Git 状态显示 Clean，表示当前仓库没有 Git 可见的未提交变化。被忽略文件、仓库外文件和未保存的编辑器缓冲区不在其中。Clean 不能证明项目目录没有其他数据。

在 `C:\Projects` 误初始化 Git，里面的多个项目可能一起出现在 Changes。GitHub Desktop 会列出成千上万文件，`.gitignore` 也难以正确配置。遇到这种情况先查 `.git` 位于哪一层，不要立刻提交或删除。确认错误仓库没有需要保留的提交，再设计移除方式。若下层项目本身有独立 `.git`，还会形成嵌套仓库，需要逐个核对。

正确边界通常让一个可独立版本、构建和交付的项目成为仓库。Monorepo 译为单一仓库多项目，它有意把多个相关项目放在一个仓库，必须有清楚的子目录和统一协作规则。初学者不要因为听到这个词就把所有 Projects 目录合成一个仓库。

## 提交前后的最小验证

提交前检查当前路径、分支、文件列表和 Diff。源码修改还要运行与变化相称的测试。只改 README，可以预览 Markdown 和点击链接。改构建配置，应运行构建。改登录逻辑，应验证成功、失败与无权限情况。

提交后打开 History，确认说明与文件范围。Push 后打开远程分支核对提交编号。部署由 Push 触发时，再查看部署记录。这套验证把动作分开。某一步失败后，从该步修复，不需要删除仓库重新开始。

仓库名应稳定、可辨认，避免只写 `test`、`new` 或 `final`。名称进入 URL、自动化和部署配置后，随意改名会影响集成。需要改名时先列出引用位置。Description 是仓库页面的一句短说明，可以写产品用途和维护状态。Topics 可以帮助分类。它们面向发现与管理，不代替 README。

公开仓库名称、分支名、提交说明和 Issue 都可能被搜索引擎收录。不要写客户秘密、内部漏洞细节或个人信息。

## 一个仓库从创建到归档的过程

练习仓库创建后，先有 README 和初始提交。项目开始开发，加入源码、依赖清单和 `.gitignore`。每项功能通过分支或提交进入默认分支，Actions 运行检查，部署平台读取稳定版本。第一个可供别人使用的版本出现后，维护者创建 Release，并在 README 记录安装和支持范围。后续 Issue 记录故障，修复提交链接到 Issue。这个阶段仓库仍在积极维护。

项目不再开发时，可以进入维护模式；维护者只处理严重缺陷，不再加入功能；README 应写清状态和支持期限。完全停止时，可以归档仓库，让页面保持只读，并给出替代项目或迁移说明。整个过程中，仓库可见性、所有权和许可证可能改变。每次变化都要评估外部链接、部署、Fork 与使用者。仓库没有因为代码写完就结束，它还承担版本来源与维护声明。

接手旧电脑项目时，先确认目录能打开、Git 状态可读取、当前分支和远程地址正确。再 Fetch 获取远程状态，不立刻 Pull 或 Push。列出本地未提交文件、本地独有提交和远程新提交。确认 `.gitignore` 没有隐藏重要源码。用 README 中的环境要求尝试只读检查，再决定是否安装依赖。

项目可以构建后，记录操作系统、工具版本和结果。若无法构建，不要为了“清理”删除锁文件或历史。保留原状态，创建独立副本调查。健康检查结果可以写成“本地 `main` 比远程领先两条提交，有一个未跟踪数据库文件，尚未运行构建”。这种描述比“仓库有点乱”更能指导下一步。

## 仓库与项目也可能不是一对一

一个仓库可以只保存文档，也可以包含前端、后端和 App 三个目录。一个产品也可能拆成多个仓库，每个仓库独立发布。看到产品名称时，先确定当前仓库负责哪一部分。前端仓库 README 可能链接后端仓库，部署平台也分别连接。修复登录问题前要知道接口与客户端分别位于哪里。

拆分会让权限与发布独立，也会增加版本协调。合并在一个仓库便于统一改动，也会让历史与权限范围变大。没有固定答案，关键是交接资料能说明关系。

同一电脑里出现 `site`、`site-old` 和 `site-backup` 时，先不要按名称挑。分别记录绝对路径、Git 远程、当前分支、最近提交与未提交变化。能够 Push 到正式仓库的目录也未必就是当前生产来源，部署平台可能监听另一个分支。比较生产部署提交编号，才能确定线上来自哪份历史。

旧目录含独有文件时，先复制到安全检查区并比较。不要把整个旧目录覆盖新仓库。逐项决定哪些变化仍有价值，再在正式仓库创建新提交。确认后给目录使用清楚名称，并更新编辑器最近项目和脚本路径。旧副本进入备份或批准清理流程。只删除已确认没有独有内容的副本。

## Git 信息也需要备份验证

普通文件备份若漏掉隐藏 `.git`，能恢复当前源码，不能恢复本地独有提交和分支。远程仓库若已有全部提交，重新 Clone 可以恢复大部分版本关系。重要本地分支要及时推送到受控远程，或者进入完整仓库备份。备份后在隔离目录测试能否读取 History、分支与 Tag。

备份中可能含已删除秘密的旧历史，访问权限要按敏感数据处理。版本丰富并不意味着适合公开保存。

读完这一章，你不需要记住 Git 内部对象，也不用学习复杂命令。能够区分普通文件夹、本地仓库和 GitHub 远程仓库，已经有了正确起点。你还需要能读出当前路径、分支和 Changes，知道保存、Commit 与 Push 分别发生在哪里。看到陌生状态时先观察，不使用强制或删除操作。

后续章节会在真实任务中重复这些动作。遇到高级教程中的 Rebase、Submodule、Cherry-pick 与复杂 Reset，可以先跳过。等项目确实需要，再根据备份和团队规则学习。

这一阶段的验收很简单。你能打开一个练习仓库，指出本地目录和远程 URL，修改 README，检查 Diff，创建 Commit，并说明为什么 GitHub 网页暂时还没变化。

## 先检查一个陌生仓库

打开一个 GitHub 仓库，先看页面顶部的所有者与仓库名。然后查看默认分支、最近提交时间和 README。不要立刻下载和运行。继续查看仓库是否有 Release，许可证是什么，Issue 是否显示大量未解决故障，Actions 最近是否通过。最后判断 README 中的安装步骤是否适合自己的系统。

例如，一个项目两年前停止更新，依赖老版本运行时，仍可能具有学习价值。它不一定适合直接接入生产。一个 README 写得完整的仓库，也不能仅凭文字证明代码安全。第十一章会给出下载和运行第三方项目的检查顺序。

第一种方向是先在 GitHub 创建仓库，再 Clone 到本地。它适合还没有本地项目的情况。GitHub 官方创建页面可以设置所有者、仓库名、说明、可见性，并选择是否初始化 README、`.gitignore` 和许可证。

第二种方向是本地已有项目，先在本地初始化仓库，再发布到 GitHub。此时要避免让远程仓库提前生成与本地无关的初始提交，否则首次同步可能需要合并两段历史。GitHub Desktop 可以用 Publish repository 完成这条路线。

两个方向都能得到正常仓库。关键是先认清哪边已有内容，再按一条路径完成。不要在 GitHub 网页、本地 Git 和另一个复制目录中同时各自初始化，然后试图猜哪份是正式版本。

## 最小观察练习

选择一个没有秘密的练习仓库，或者使用 GitHub 官方 Hello World 练习。官方练习通过网页完成仓库、分支、提交、Pull Request 和合并，不要求先学命令行。GitHub Skills 的 Introduction to GitHub 也提供自动引导。

完成时只记录以下信息。

- 仓库所有者和名称
- 默认分支名称
- 最近一条提交说明
- README 所在位置
- 本地是否有对应目录
- 本地是否存在尚未推送的提交

不要用工作项目练习删除、强制推送或重写历史。基础观察不需要这些操作。

## 常见误解

文件夹名字带 `.git` 字样，不说明它是仓库。应确认隐藏目录和 Git 状态。把 ZIP 下载下来也不会保留完整 Git 历史。复制仓库文件夹可能连 `.git` 一起复制，产生两个具有相同历史的本地仓库，后续 Push 时容易认错。

GitHub 仓库设为 Private 只限制仓库访问。已经发布到公网的密钥不会因为改成私有而恢复安全。公开网站也不会因为源仓库改为私有就自动需要登录。Commit message 是提交说明，不会执行命令。写得清楚能帮助审查，不能替代测试和验证。

AI 可以只读列出项目结构、Git 状态、当前分支和远程地址，解释哪些文件被修改或忽略。它也可以根据 Diff 建议提交拆分与说明。要求 AI 不创建提交、不 Push、不清理文件，直到你确认范围。项目含未提交的用户修改时，任何恢复或丢弃操作都要先展示将受影响的文件。

创建仓库时亲自确认所有者、可见性和项目内容。提交前查看 Diff，Push 前确认远程仓库与分支。涉及公开代码、许可证、历史重写和删除仓库时，保留最终决定。下一章会从 GitHub 账号和网页界面开始，完成新仓库与文件上传，同时解释公开与私有的真实边界。
