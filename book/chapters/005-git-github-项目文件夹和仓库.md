# Git、GitHub、项目文件夹和仓库

网页项目最初可以只是普通文件夹。文件夹加入 Git 后，多了一套版本历史；提交推送到 GitHub 后，又多了远程副本与协作入口。三者经常位于同一条工作链，却不是同一个对象。

电脑断网时，Git 仍能比较文件、创建提交和查看本地历史。只有把提交发送到 GitHub、取得远程更新或使用在线协作功能时，才需要网络与账号权限。

## 文件夹、仓库与远程

普通项目可能长这样。

```text
my-site/
  index.html
  styles.css
  images/
    logo.png
  README.md
```

复制它能得到快照，却很快出现 `final`、`final-2` 和 `really-final`。哪份上线、哪份含修复、两个副本差什么，都需要人工猜。Git 在原目录中记录变化，不要求每次复制完整项目。

Git 仓库通常在根目录含隐藏的 `.git`。它保存提交、分支和内部关系；普通源码仍在原位置。删除或手改 `.git` 可能破坏本地历史，不是清理缓存的方法。一个父目录可以包含多个独立仓库，也可以有意用一个仓库管理多个相关项目。边界应由可独立版本、构建和交付的关系决定，不由文件夹名称猜测。

GitHub 仓库是远程仓库，有所有者、名称、可见性、默认分支和提交历史，还可能有 Issue、Pull Request、Actions 与 Release。本地仓库可以暂时没有远程，GitHub 也可以先创建空仓库再与本地连接。

## 保存、选择、提交与推送

工作区是正在编辑的文件。保存以后，内容进入本机磁盘，Git 能看到变化。暂存或图形界面的文件勾选表示“这部分进入下一次提交”。Commit 把选中变化写入本地历史；Push 才把提交送到远程分支。

例如同时修改首页文字和仍在试验的测试配置，可以只选择首页创建提交。说明“更新首页活动时间”比“改一下”更能解释范围。一个提交围绕一项可说明的工作；修复图片路径与重写页面样式没有依赖时，拆开更容易审查和撤销，但也不必每改一行就提交。

四个状态不要混淆。

1. 保存 README 后，Changes 出现修改。
2. Commit 后，修改进入本地 History。
3. 尚未 Push 时，GitHub 网页没有该提交。
4. Push 后，远程分支出现同一提交 SHA。

Changes 为空只说明 Git 当前没有可见未提交变化。编辑器未保存内容、被忽略文件和仓库外数据不在其中；打开错误仓库时也可能“很干净”。

## 文件状态先解释，再处理

- **Untracked**。文件存在，但 Git 尚未跟踪。可能是新源码，也可能是日志、数据库或秘密。
- **Modified**。已跟踪文件的内容改变。
- **Deleted**。历史中的文件在工作区消失，可能是有意删除，也可能被误移或构建清理。
- **Clean**。没有 Git 可见的未提交变化，不证明项目没有本地数据。

看到状态先打开 Diff 和来源，不一律加入或删除。若在 `C:\Projects` 误初始化仓库，多个无关项目可能同时出现。先定位 `.git` 所在层，确认是否已有需保留提交，再设计修复；不要用提交全部文件或直接删隐藏目录掩盖边界错误。

`.gitignore` 只告诉 Git 哪些未跟踪路径通常不进入仓库。数据库、上传文件、环境变量和签名材料需要自己的备份或秘密系统。规则与事故处理见[《Git 与 GitHub 操作参考》](../../references/git-github.md)和第 12 章。

## 分支是工作线，不是备份

分支指向一条提交历史。生产可能监听 `main`，新首页在 `new-home` 分支开发并先进入预览；确认后再通过 Pull Request 合并。它减少半成品直接影响用户的机会。

分支不会创建另一账号，也不自动形成独立备份。两条分支修改同一位置时，Git 可能无法自动选择，形成冲突。个人小修复可以直接在默认分支完成；较大改动、实验、协作或生产发布更适合独立分支。选择取决于风险和审查需要，不是分支越多越专业。

README 是入口说明，Issue 记录问题或任务，Pull Request 展示准备合并的 Diff 与讨论，Actions 针对某个提交运行自动化，Release 面向使用者说明一个版本。它们共享版本身份，却不能彼此代替。测试通过不是部署完成，Release 存在也不是生产已切换。

## GitHub 不等于完整备份

远程仓库只覆盖已经提交并推送、且没有被忽略的内容。未保存、未提交、本地独有分支、数据库、用户上传和平台秘密都可能缺失。账户锁定、仓库误删或共享历史被强制改写，也会影响远程副本。

重要项目应列出仓库覆盖什么、仓库外还有什么、怎样恢复、多久演练。远程已经包含所有提交时，重新 Clone 能恢复大部分版本关系；本地独有提交要推到受控远程或进入完整仓库备份。备份可能含历史秘密，访问权限仍按敏感数据处理。

提交作者、时间和逐行归属是调查线索，不是责任判决。自动格式化会让一个人看似改过整文件，共享账号又会模糊身份。排错要同时看 Diff、相邻提交、需求与 Pull Request 讨论。

## 提交前后各验证一次

提交前检查当前绝对路径、仓库、分支、文件列表和 Diff，并运行与变化相称的验证。文档要预览和点链接，构建配置要实际构建，登录变化要测成功、失败与无权限。

提交后在 History 核对说明和文件范围；Push 后到远程目标分支比较 SHA；部署由 Push 触发时，再查看部署记录。某一步失败就从该步修复，不需删除仓库重来。

公开仓库的名称、分支、提交说明和 Issue 可能被搜索。不要写客户秘密、内部漏洞细节或个人信息。作者邮箱也可能进入公开历史，新设备首次提交前先核对身份与隐私设置。

## 先检查陌生仓库

接手本地旧项目时先只读观察。目录能否打开、Git 状态、当前分支、远程地址、本地未提交文件、本地独有提交和远程新提交。Fetch 可以取得远程状态，先不要立即 Pull 或 Push。无法构建时保留锁文件和原状态，在独立副本调查，不以“清理”为名删除历史。

打开陌生 GitHub 仓库则先看所有者、默认分支、最近提交、README、Release、许可证、Issue 与 Actions。README 完整不证明代码安全；两年未更新的项目也可能适合学习，却未必适合生产。第 11 章会继续检查下载与运行风险。

同一产品可以拆成前端、后端和 App 多仓库，一个仓库也可以包含多个子项目。修复前要知道当前仓库负责哪一部分、部署平台监听哪一分支。看到 `site`、`site-old` 和 `site-backup` 时，分别比较绝对路径、远程、分支、最近提交与未提交变化，不按名字挑“最新版”，也不整目录互相覆盖。

## 从哪边开始

新项目可以先在 GitHub 创建仓库再 Clone；已有本地项目可以先初始化 Git，再发布远程。两条路线都正确。关键是认清哪边已有内容，不要让本地、网页和复制目录分别产生无关初始历史，再靠覆盖解决。

具体命令、GitHub Desktop 按钮和恢复动作见[《Git 与 GitHub 操作参考》](../../references/git-github.md)。本章掌握边界是能区分文件夹、本地仓库和远程仓库，能读出路径、分支和状态，知道保存、Commit 与 Push 发生在哪里。Rebase、Submodule、Cherry-pick 和复杂 Reset 暂时可以跳过。

AI 适合只读列结构、Git 状态、当前分支和远程地址，或根据 Diff 建议提交拆分。让它先不 Commit、不 Push、不清理文件。创建仓库时由人确认所有者与可见性；提交前看 Diff，推送前核对远程与分支；历史重写和删除必须先说明会失去什么以及如何恢复。
