# 沿用户动作阅读测试、历史、Issue 与 PR

仓库导航图给出方向，下一步要选一件用户真的会做的事，沿着它走进代码。注册、上传、搜索、付款或导出都可以。一次只选一件，因为成熟系统里的一个按钮已经可能跨过前端、接口、权限、数据库和后台任务。

代码告诉你现在怎样实现，测试告诉你维护者准备守住什么行为，提交历史提供变化顺序，Issue 记录问题和需求，Pull Request 记录一项具体改动怎样被讨论和合入。五类材料放在一起，才能看清“它为什么写成这样”。

## 从可观察结果往回找

先写清用户做了什么以及看见什么。不要从目录名猜功能。以“用户上传照片后能在列表看到缩略图”为例，可观察结果至少包括上传请求完成、资源出现在列表、缩略图稍后出现。若只盯着 HTTP 成功，后台任务失败会被漏掉。

打开浏览器 Network，记录请求方法、路径、状态码和响应字段。移动应用可结合客户端日志和接口定义。随后在仓库中搜索稳定标识，例如路由路径、响应字段、按钮文字对应的翻译键。随机生成的类名和编译产物通常不适合作为入口。

找到接口后逐步向内走。每次只回答当前函数接收什么、检查什么、调用谁、返回什么。遇到抽象接口时再找实现和依赖注入位置。若一次跳过五层让 AI 总结，最容易把同名类型、旧实现和测试替身混在一起。

测试最有价值的部分是准备条件、执行动作和断言。它可能准备一个无权限用户，调用上传接口，断言返回拒绝并确认没有创建记录。这个测试能证明维护者在该提交里检查了这条路径。它不能证明所有权限组合都安全，也不能证明部署环境运行过测试。

先看最接近用户边界的测试。端到端或集成测试覆盖范围较大，失败时定位较慢。单元测试便于确认一个函数的分支，却可能把数据库、队列和网络都替换掉。契约测试核对调用双方对消息的共同理解，仍然不能代替完整运行路径。

阅读测试时把四件事抄下来。

```
前置状态  普通用户已登录，配额仍有空间
用户动作  上传一个受支持格式的文件
主要断言  创建资源记录并返回资源标识
没有覆盖  缩略图任务、存储写满、重复请求
```

“没有覆盖”不是批评，它告诉你还需要运行哪项实验。性质测试、模糊测试和变异测试能扩大输入或检查测试敏感度，也要先有明确性质和测试目标。工具自动生成很多样本，不会自动生成正确的业务判断。

## 用提交历史回答什么时候变了

当一行代码很奇怪，先看它最近一次有意义的变化。GitHub 的文件历史和 Blame 可以把行连接到提交。Blame 显示最后修改者与提交，不能直接说明谁最初设计、谁批准或谁应对故障负责。格式化、搬文件和批量重命名还会遮住更早的原因。

打开提交后查看完整差异和消息。一个提交可能同时修改代码、测试、迁移和文档。只看当前文件会漏掉约束。记录父提交与提交 SHA，然后检查这个提交是否属于 Pull Request。GitHub 的提交页面还能显示它所在的分支或标签，帮助判断改动是否已进入默认分支和发布版。

本地可以用以下只读命令查看路径历史。

```
git log --follow -- path/to/file
git show COMMIT_SHA
git blame -L 40,80 path/to/file
```

第一行沿重命名查看文件历史，第二行显示指定提交，第三行查看文件第 40 到 80 行的归属。它们不修改仓库。若仓库是浅克隆或只下载了部分历史，结果可能不完整，应先检查克隆方式。

## Issue 说明问题，不能自动证明结论

Issue 适合记录可复现缺陷、明确任务和功能需求。一个 Issue 的标题写“上传会损坏文件”，正文也许只涉及某个旧版本、特定文件系统和断电场景。阅读时记录软件版本、操作系统、部署方式、复现步骤、日志、维护者回复和最终状态。

关闭 Issue 有多种原因。问题已经修复、无法复现、重复、超出范围或转到其他地方，都可能显示 Closed。标签也由项目自行定义。没有查看关闭说明和关联改动，就不能把关闭当成修复证据。

若评论里出现临时命令，先判断它是诊断、缓解还是正式修复。删除缓存、重建索引和回滚数据库都可能带来数据风险。社区里多人说“对我有效”，只能说明办法值得检查，不能替代版本匹配、备份和测试。

Pull Request 是合并代码变化的提议。GitHub 把描述与讨论、提交、检查和文件差异放在同一个入口。阅读顺序可以从目的开始，再看最终差异、关键评论、测试结果和合并提交。

讨论中的早期方案可能已被后续提交推翻。评论引用某一行时，要确认自己查看的是当时差异还是最终文件。PR 显示所有检查通过，也要打开工作流确认检查覆盖什么、是否允许跳过、运行的是否为合并候选状态。

审查评论通常分三类。第一类指出确定缺陷，后续提交已修正。第二类讨论取舍，维护者接受了某种代价。第三类只是建议，可能延后或拒绝。把三类混成“维护者说过”，会让历史经验失去边界。

一份有用的 PR 阅读笔记可以这样写。

```
改动目标  上传后立即返回，缩略图交给后台任务
接受的代价  列表会短暂显示处理中
验证证据  接口测试、任务测试、迁移检查
未解决事项  大量积压时的等待时间
进入版本  由合并提交和发布标签确认
```

## 沿一次失败再走一遍

成功路径只能证明主要连接成立。再选择一个受控失败，例如上传不支持的格式、让测试存储返回容量不足，或让后台任务在测试环境报错。不要在生产环境制造故障，也不要通过删除真实数据验证恢复。

受控失败要写明预期。无效格式应在进入持久化前被拒绝，容量不足应返回可识别错误，后台任务失败应保留可重试状态。运行后收集状态码、界面提示、日志关联标识、数据库变化和队列状态。每项结果分别证明一个边界，不能用“系统成功报错”概括。

若行为和测试不同，先确认提交、配置与数据条件是否一致。随后检查测试替身是否绕过了真实存储或队列。性能问题还需区分本地剖析、压测结果和真实用户数据。本地录制能指出主线程或函数耗时，不代表所有设备和网络都相同。

可以让 AI 从请求路径寻找控制器、服务、数据访问和测试，也可以让它概括一个 PR。要求输出文件路径、符号、提交和它没有确认的部分。若仓库很大，先把范围限制在一个用户动作，避免模型用同名文件拼出不存在的调用链。

拿到结果后做三次反向检查。接口注册是否指向那个处理器，测试是否真的执行那条路径，PR 的最终差异是否支持概括。再运行一个成功样本和一个安全失败样本。AI 可以节省搜索时间，证据是否属于当前版本仍由你确认。

沿用户动作读仓库的好处很实际。你会知道一个按钮经过哪些组件，某项怪异限制来自哪次取舍，哪条测试能阻止回归。以后让 AI 修改功能时，你也能明确要求它改哪里、补什么测试，以及哪些历史约束不能顺手删掉。

## 遇到重命名与分层搬迁怎样继续追

功能移动后，当前路径的历史可能只到一次大搬迁。`git log --follow` 对单个文件的重命名有帮助，对拆分、合并和大规模改写并不总能完整追踪。此时从稳定符号、测试名称、接口路径和提交消息继续搜索。

先缩小时间范围。找到搬迁提交，查看父提交中的旧目录，再比较新旧测试和调用者。若提交同时做了格式化，使用忽略空白的差异辅助阅读，但最终仍要看真实内容。自动生成文件和锁文件可以暂时折叠，不能从最终评审中删除。

代码搜索结果也要固定版本。GitHub 默认搜索可能显示默认分支当前内容，Issue 里引用的路径却属于旧提交。打开永久链接或在本地切换到目标提交，才能保证行号和讨论一致。

用户动作涉及数据结构时，当前模型只说明现在希望怎样存。迁移文件会告诉你字段何时加入、旧数据如何转换、索引怎样建立和约束怎样收紧。按照编号或时间读取相关迁移，再看部署说明是否要求先升级数据库或先发布兼容代码。

一次安全的字段演进常要允许新旧版本短暂共存。先增加可空字段并发布兼容读取，完成数据填充，再收紧约束。若 AI 一次迁移就改名、改类型并删除旧列，代码回滚可能已经无法读取数据。

研究迁移时准备一份包含旧版本边界值的测试数据库。在副本上运行升级，检查记录数量、空值、唯一约束、时间和权限。随后用新版本读取，也要根据回滚策略检查旧版本。迁移命令退出成功只证明数据库接受了语句，不能证明业务含义没有变化。

## 把历史判断写成一页变更档案

完成一次代码考古后，不必保存所有浏览记录。保留用户动作、目标提交、当前调用链、关键测试、决定性 Issue 与 PR、仍在生效的取舍和未解决问题。每个链接说明它支持什么。

```
用户动作  请求导出数据
当前路径  页面到导出接口，再到后台任务
历史约束  大数据量改为异步，避免请求超时
保护测试  权限、任务创建、重复请求
仍待验证  对象存储失败后的恢复
最后核对  提交与检索日期
```

以后 AI 要把异步导出改回同步时，这页档案会提醒审查者先查看当初的超时证据。历史不禁止改变方案，它要求新方案处理旧问题，并提供新的验证结果。
