# 后端为什么存在以及 API 怎样工作

静态网站把准备好的文件交给浏览器。用户若要注册、留言、查询自己的订单或预约时间，网站就要根据每次请求读取和修改数据。负责这部分工作的程序通常叫后端。后端运行在用户不能直接控制的环境中。它接收请求，验证身份和输入，执行业务规则，访问数据库或外部服务，再返回结果。API 是客户端与这些能力交谈的约定。

图中浏览器或 App 通过 HTTPS 访问 API。API 检查身份与权限，读写数据库和对象存储。需要即时更新时，客户端还可建立实时连接。外部服务只通过受控后端取得秘密。

## 后端解决什么问题

第一个问题是共享数据。一个预约名额不能只存在访客手机里，所有用户需要看到同一份最新状态。第二个问题是可信规则。浏览器中的 JavaScript 由用户设备执行，用户可以修改请求。名额是否可约、金额如何计算、谁能退款，都要在可信服务端重新判断。

第三个问题是秘密。数据库密码、邮件密钥和支付私钥不能交给每个浏览器。后端在受控环境中使用它们。第四个问题是长期工作。发送邮件、处理文件、记录审计和运行后台任务，需要在用户关闭页面后继续。

MDN 对服务端的介绍也强调，服务端可以验证请求、使用数据库、发送通知并为不同用户返回不同内容。

前端负责用户看见和操作的界面；它收集输入、展示状态、发出请求并处理响应；后端负责决定请求是否允许，以及数据怎样变化；它不相信前端已经验证过的价格、用户 ID 和角色；假设预约页面让用户选择下午三点。前端可以先显示该时段可用，后端收到提交后仍要再次检查。两个人可能同时看见最后一个名额。

后端在数据库事务中确认名额并创建预约。一个成功，另一个得到已满响应。只靠前端按钮变灰无法解决并发。

## API 是一份约定

API 约定请求地址、方法、输入、身份、成功结果和错误。调用者不需要知道服务器内部用了哪种语言和数据库。例如创建留言可以约定向 `/api/messages` 发送 POST，请求体包含正文。成功返回留言 ID、创建时间和状态。

读取留言列表可以向同一路径发送 GET。方法不同，操作不同。服务器也可以用版本路径或请求头管理不兼容变化。约定应写成文档或可生成的接口描述。只靠前端代码猜字段，双方改动时很容易失配。

用户点击“提交留言”，前端先检查是否为空。这是界面反馈，不是最终安全验证。浏览器通过 HTTPS 向 API 发请求，带上内容与会话。入口把请求交给后端。后端识别用户，检查是否被禁言、正文长度和频率。通过后写入数据库，生成服务器时间与 ID。

数据库提交成功，后端返回 201 与新留言。前端把它加入页面并显示成功。任何一步失败都要有明确结果。网络断开时没有 HTTP 响应，未登录可以返回 401，无权操作返回 403，输入不合规则返回 400 或 422，服务器异常返回 500。

状态码语义要与 API 约定一致，不能所有错误都返回 200 再在正文写失败。

## 请求由哪些部分组成

URL 表示资源位置，HTTP 方法表达操作意图，Headers 携带内容类型、认证和追踪信息，Body 携带提交数据。查询参数适合筛选、分页和排序，例如 `?page=2&status=open`。敏感值不要放 URL，因为 URL 更容易进入历史、日志和分析系统。

JSON 是常见请求体格式。文件上传通常使用表单或直传对象存储。服务器按 `Content-Type` 解析，但仍要验证实际内容。客户端还可以发送请求 ID，服务端在日志中沿用。一次操作跨多个服务时，它帮助串起证据。

状态码给出结果类别，Headers 说明内容类型、缓存和其他元数据，Body 提供数据或错误详情。成功响应只返回客户端需要的数据。不要把数据库内部字段、密码哈希和管理员备注一起序列化。

错误响应使用稳定结构，例如错误代码、用户可读提示和请求 ID。详细堆栈进入受限日志，不直接给浏览器。用户提示可以本地化，机器错误代码保持稳定。前端根据代码决定显示登录、重试还是修改输入。

## 浏览器怎样调用 API

浏览器可用 Fetch API 发出请求。MDN 把它描述为通过 Request 与 Response 对象处理网络请求。下面代码只演示结构，运行在自己的练习网页中。地址使用保留域名，不会产生真实业务。

```
const response = await fetch("https://api.example.test/messages", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ text: "这是一条练习留言" })
});

if (!response.ok) {
  throw new Error(`请求失败 ${response.status}`);
}

const message = await response.json();
```

`fetch` 的 Promise 在服务器返回 404 或 500 时通常仍会完成，所以代码要检查 `response.ok` 或状态码。真实项目还要处理超时、取消、认证、重复提交和错误展示。不要把服务端秘密写进浏览器代码。

## 后端要再次验证输入

前端限制字数有助于用户操作，攻击者可以绕过界面直接发请求。后端必须验证类型、长度、范围和业务关系。用户提交 `user_id` 时，后端不能据此决定身份。身份来自已验证会话，资源归属由服务器查询。价格也不能由前端最终决定。客户端提交商品与数量，后端从可信数据计算金额。

文件名、MIME 类型和扩展名都可伪造。上传安全在第 33 章与第 66 章专门处理。

数据库保存和查询数据，API 暴露受控业务能力。让浏览器直接使用管理员数据库连接，会绕过业务与权限边界。有些 BaaS 允许客户端通过 SDK 或自动 API 访问数据库。它们仍通过认证、行级权限和服务网关控制，不等于把数据库密码放进前端。

Supabase 的架构把 API 网关、PostgreSQL、Auth、Storage、Realtime 与 Functions 分成组件。客户端 Key 是否可公开，要根据角色与权限规则判断，服务角色秘密不能进入客户端。

后端也不应拥有无限权限。不同服务账号按所需表和操作分配权限，降低泄露影响。

## 业务规则放在哪里

必须保持一致的规则应在服务端或数据库中执行。前端可以复制部分逻辑提供即时提示，但服务器结论为准。预约开始时间不能早于当前时间，服务端使用统一时区和可信时间。前端本地时间可能被修改。

库存扣减需要原子操作或事务，防止并发超卖。单纯先查询再更新，中间可能被另一请求改变。权限规则应靠资源归属和角色计算，不能只隐藏按钮。管理员接口即使前端没有链接，也必须验证角色。

快速操作可以在一个请求内完成，例如读取个人资料。视频处理、群发邮件和生成大报告不应让浏览器长时间等待。后端可创建任务并立即返回任务 ID。工作进程异步处理，客户端轮询或通过实时通道获得状态。

任务要记录待处理、进行中、成功和失败。重试要避免重复扣款与重复邮件。API 返回“已接收”不代表任务完成。前端文案要把两种状态分开。

## 分页、筛选和限制

留言很多时，API 不应一次返回全部。客户端请求一页，响应带下一页指针或页码信息。排序必须稳定。只按创建时间排序时，同一时间多条记录可能在翻页中重复或漏掉，可加入唯一 ID 作为第二排序键。

服务端限制最大页大小，防止客户端用超大参数消耗资源。筛选字段也使用允许列表，不把任意 SQL 片段交给客户端。响应可以包含总数，但大数据量下计算总数有成本。产品需求决定是否必需。

用户双击按钮、手机网络重试和代理超时都可能重复请求。创建支付和预约时要考虑幂等。客户端生成一次操作 Key，后端在一定范围内识别相同 Key，重复请求返回原结果。具体设计取决于业务和供应商。

前端禁用按钮只能减少误触，不能处理网络层重复。后端的唯一约束与事务才是最后防线。GET 应当只读取，不用它执行删除。爬虫和预加载可能自动访问链接。

## 超时与重试

客户端不能无限等待。设置合理超时，并允许用户看见仍在处理、可重试或已失败。重试适合暂时网络错误和部分服务不可用。输入错误、权限错误和确定的资源不存在不应自动重试。指数退避能避免所有客户端同时猛烈重试。服务器还要限流和保护下游。

有副作用的请求重试前确认幂等。第一次实际成功但响应丢失，第二次可能重复执行。

增加可选响应字段通常较容易兼容，删除或改名会破坏旧客户端。手机 App 用户不会同时升级，后端要承担一段兼容期。在发布前列出旧 Web、旧 App 和外部调用者。重大变化可使用版本路径、协商或过渡字段。

记录弃用时间与替代方式，监控旧版本调用量。确认没有使用者后再下线。API 文档也要随部署更新。代码已经变，文档仍写旧字段，会制造人工故障。

## 一个最小预约 API

练习系统有时段列表、创建预约、查看我的预约和取消预约四项能力。未登录用户可以读取公开时段。创建、查看和取消需要会话。创建时后端确认时段存在、未过期、仍有容量，并检查用户是否重复预约。

数据库写入成功后返回预约 ID。发送确认邮件放入后台任务，邮件失败不撤销已经成功的预约，但系统应显示邮件状态并允许重发。取消接口检查预约属于当前用户和取消期限。成功后释放名额，记录审计时间。

这四项已经覆盖公开读取、认证、授权、事务、后台任务和幂等。界面只是它们的一个客户端。

按钮没有发请求，检查前端 Console 与事件。请求发出但被浏览器拦截，检查 CORS、Mixed Content 和证书。收到 401，检查会话是否存在与过期。403 检查资源和角色。400 或 422 查看输入错误详情。

500 查看服务端请求 ID 与运行日志。请求很慢，分解入口、后端、数据库和外部 API 耗时。数据库已写入而前端提示失败，检查响应丢失与重复提交。不要让用户反复点击制造更多数据。

## 后端内部常见的四层

路由层接收 HTTP 请求，解析参数并选择处理程序。它不应塞入全部业务。业务层执行预约、退款和权限等规则。数据访问层负责与数据库交谈，外部服务层封装邮件、支付和对象存储。分层目的是让规则有明确位置，便于测试和替换。小项目只需几个函数，不必为了名称建立庞大目录。

一个取消预约处理程序可以先识别用户，调用业务函数检查期限，再由数据函数在事务中更新，最后创建邮件任务。

每个端点记录方法、路径、认证、请求字段、成功响应、错误代码和示例。字段说明类型、是否必需、范围和时区。错误示例与成功示例同样重要。前端需要知道配额用尽、资源冲突和会话过期怎样表现。

分页说明游标或页码，排序说明默认顺序。时间字段统一格式，金额说明单位和币种。文档中不放真实 Token 与用户数据。使用保留域名、虚构 ID 和测试账号。

## OpenAPI 与代码生成的边界

OpenAPI 可用机器可读方式描述 HTTP API，工具能生成文档、客户端和部分验证。生成代码减少手写字段错误，却不能表达所有业务权限和并发规则。说明文字仍要写“为什么会失败”。规范与实现要在持续集成中检查。规范停留在旧版本，比没有文档更容易误导。

小型内部 API 可以先写清楚 Markdown 表，稳定后再引入规范工具。

语法层检查 JSON 能否解析、字段类型和长度。业务层检查预约时间、库存和状态变化。权限层检查当前用户能否操作资源。三层错误给出不同代码和提示。把所有失败变成 500 会让前端无法帮助用户修正。

验证还要处理未知字段。忽略未知字段便于兼容，严格拒绝更容易发现拼写错误，按端点风险选择并记录。服务端使用允许字段列表更新，避免用户提交 `role` 或 `is_admin` 等不应修改属性。

## 输出也需要验证

数据库对象可能包含密码哈希、内部备注和软删除标记。不要直接返回整行。为响应定义明确 DTO，也就是数据传输对象，只选择公开字段。管理员响应和普通用户响应分开。序列化时间、数字和空值要稳定。大整数在 JavaScript 中可能失去精度，可用字符串表达公开 ID。

部署前用测试断言响应不包含秘密字段。新增数据库列后也不会自动暴露。

登录、验证码、搜索和 AI 调用都需要限制频率。限制可以按账号、IP、设备和 API Key 组合。只按 IP 会误伤共享网络，只按账号无法限制未登录攻击。策略要适合入口。达到限制时返回明确状态和等待信息。客户端按提示停止重试，不不断刷新。

限流状态需要共享存储时，多个实例不能各自在内存计算。平台网关也可能提供基础限制。

## 缓存放在哪里

浏览器缓存静态和可公开响应，CDN 在边缘缓存，后端缓存数据库查询，数据库自身也有缓存。个人资料和订单响应不能被公共缓存。设置正确 Cache-Control，并让缓存 Key 包含必要身份与查询条件。

缓存失效比写入缓存更难。数据改变后，删除或更新对应 Key。暂时旧数据是否可接受要由业务决定。缓存是副本，权威数据仍在数据库。清空缓存不应丢失业务事实。

支付、邮件和存储服务会向你的后端发送事件，这类回调常叫 Webhook。端点公开可达，不代表任意请求可信。验证供应商签名、时间戳和请求体，并使用当前官方算法。供应商可能重复发送或乱序。保存事件 ID 去重，按业务状态判断是否仍适用。

先快速返回接收结果，再交给后台任务处理。长时间阻塞会触发供应商重试。

## API 网关与反向代理

公开入口可以统一处理 TLS、域名、请求大小、限流和路由，把 `/api` 请求转给后端。网关不理解全部业务权限，后端仍要认证和授权。代理传来的用户 IP 与协议 Header 只信任已知代理。配置错误会让后端认为所有请求来自同一地址，或生成 HTTP 回调 URL。记录实际转发头并按框架当前说明信任代理。

第六卷讲 Caddy 与 Nginx 时会回到这一位置。

GraphQL 允许客户端声明需要的字段，通过一套 Schema 查询。它能减少固定响应不合适的问题。它仍需要身份、字段权限、查询复杂度限制、分页和错误处理。一个端点不代表安全更简单。个人项目已有清楚 REST 端点时，不必为了流行改用 GraphQL。多个客户端字段需求复杂时再评估。

本书不展开 Schema 与 Resolver 编写，读者只需知道它是另一种 API 约定。

## API 测试分几类

单元测试检查业务函数，集成测试连接测试数据库，契约测试确认请求响应格式，端到端测试从客户端走完整路径。权限测试必须覆盖未登录、资源所有者、其他普通用户和管理员。输入测试覆盖边界、缺失和超长。

并发测试同时创建最后一个预约，确认只成功一次。重试测试重复发送相同幂等 Key。测试数据库使用虚构数据，结束后可安全清理。生产数据不复制到开发日志。

入口为每个请求生成 ID，响应 Header 返回给客户端。后端、数据库查询和外部服务日志使用同一关联值。错误报告给用户时展示短请求 ID，客服能在受限日志查找。不要把完整堆栈给用户。指标记录请求数、状态、延迟和关键业务结果。日志解释单次事件，指标发现整体趋势。

追踪工具可展示跨服务耗时，个人项目先有结构化日志和请求 ID 已经很有价值。

## API 关闭与维护模式

计划维护时，读取可以继续，危险写入暂时拒绝。返回清楚状态与重试时间。维护页面不能只遮住前端，API 写入也要限制。移动 App 和脚本仍可能调用。数据库迁移前等待进行中请求结束，并处理后台任务。恢复后先内部验收，再开放写入。

意外故障时使用功能开关关闭单项能力，避免整个应用全部下线。

用户在网络较差的手机上点击预约，第一次请求已写入数据库，响应在途中丢失。界面显示失败，用户再次点击；没有幂等设计时出现两条预约；前端禁用按钮也无法处理响应丢失；修复后，客户端为一次预约意图生成 Key；数据库对用户、时段和 Key 建唯一约束；重复请求返回原预约。

日志通过请求 ID 与幂等 Key 区分网络重试。前端收到原结果后显示成功。这个案例同时用到数据库约束、API 响应和用户体验。任何一层单独处理都不完整。

## 文件上传 API 的边界

客户端先请求上传授权，API 只接收文件用途、大小和类型等元数据。服务器生成随机对象 Key 与短时权限。上传字节直接到对象存储后，客户端把完成信息交给 API。服务器核实对象并创建业务记录。

这样 API 不长期转发大文件，秘密仍在后端。客户端不能自行指定任意 Bucket 和他人目录。上传成功、业务记录失败时会留下孤立对象，后台清理按到期状态删除。第 33 章会展开安全扫描。

搜索端点接收关键词、筛选和分页。服务端限制长度、允许字段与最大结果。不要把用户关键词直接拼进 SQL。使用参数化查询或搜索服务 SDK，防止注入。搜索结果只含用户有权查看的资源。先搜全库再在前端隐藏会泄露标题和计数。

关键词可能含个人信息，日志按隐私策略处理，不默认永久保存完整查询。

## 管理 API

管理界面也是 API 客户端。端点要求管理员身份、细分权限和审计。批量删除、退款和导出需要二次确认、范围预览和幂等。高风险操作可要求重新认证。审计记录操作者、时间、目标、理由与结果，不记录秘密。管理员不能删除自己的审计线索。

管理 API 与普通 API 可共用业务层，权限入口保持独立清楚。

用户需要知道下一步，例如重新登录、修改字段或稍后重试。开发者需要请求 ID、内部错误与堆栈。生产响应不返回 SQL、文件路径和供应商密钥。调试模式只在受控环境启用。相同内部原因可能转为不同用户提示。数据库唯一约束可转成“该时段已预约”。

本地化文案与机器代码分开，避免前端解析中文句子决定逻辑。

## API 发布检查单

确认认证与每个资源授权，输入和输出 Schema，分页与上限，超时和幂等，日志与请求 ID。用未登录、本人、他人和管理员四种身份测试。用重复请求和两个并发请求测试写入。检查错误响应不含堆栈，浏览器端不含服务密钥。关闭测试后门和宽松 CORS。

部署后从真实域名走核心路径，监控状态码、延迟与业务结果。

用户请求导出账号资料。API 验证最近登录，创建导出任务并立即返回任务 ID。Worker 从数据库和对象记录收集用户有权取得的数据，生成加密或受控 ZIP，放进私有存储。完成后发送应用内通知，用户重新认证后取得短时下载 URL。文件到期自动删除。

任务失败可安全重试，日志不打印导出内容。管理员能看到状态，不能无理由下载用户文件。这条流程把长任务、隐私、对象存储、通知和过期清理连接起来，单一同步 API 无法可靠完成。

## API 草案先接受权限和失败路径审查

AI 可以根据业务故事草拟 API 端点、请求响应示例和错误表，也能从脱敏日志串联一次请求。让它明确权限来源、并发和重复提交。只生成成功 JSON，未覆盖错误与资源归属的设计不能直接上线。

亲自确认后端不信任客户端身份、价格和权限。使用两个测试账号验证彼此不能读取或修改资源。检查生产秘密只在服务端，错误响应不泄露堆栈，重复提交不会重复扣费或占用名额。下一章会比较 REST、WebSocket、身份认证和授权，把“谁在请求”和“能做什么”拆开。
