# 每周、每月和每季度维护清单

系统维护不能只靠出事时想起来。也不能把所有事情都塞进一张巨大清单，最后谁也不看。好清单要少、准、有人负责，并且能留下证据。它的目标是让小问题在平时被发现，不等事故来提醒。

## 先建立资产、负责人和证据位置

清单从资产开始。你维护哪些仓库、部署平台、服务器、数据库、对象存储、域名、证书、商店应用、小程序、第三方 API、监控、账单和账号。每项写负责人、登录入口、证据位置和应急联系方式。

没有负责人，清单就是装饰。负责人不一定亲手处理所有事项，但要确保有人看、有人记录、有人升级。个人项目也要写清楚。否则几个月后自己也会忘记域名在哪续费，数据库备份放在哪里。

证据位置要固定。维护记录可以放在仓库文档、内部 Wiki 或工单系统。不要散在聊天里。每次检查写日期、检查人、异常、处理动作和未完成事项。

## 每周看变化和告警

每周清单适合处理正在变化的东西。

- 查看最近部署、失败构建、回滚和临时开关。
- 查看错误日志、崩溃、登录失败、支付或同步异常。
- 查看监控告警是否有人处理，是否有重复噪声。
- 查看磁盘、数据库连接、队列积压和对象存储增长。
- 查看账单是否有突增。
- 查看证书、域名和关键密钥是否接近到期。

每周不追求深度审计。它像巡视。发现异常后开单处理，不在清单里写长篇调查。临时 Debug 日志、防火墙规则、测试账号和功能开关若已超过期限，也要在这一轮收回。

App 和小程序还要看线上版本与后端兼容。商店评论、崩溃率、审核反馈、体验版测试问题和微信公众平台通知，都可能提示新风险。

每周检查最好控制在半小时内。超过这个长度，人会拖延。清单只负责发现异常和创建后续任务，不负责现场解决所有问题。看到数据库增长异常，就记录并安排分析。看到证书还有十天到期，就创建续期任务并指定负责人。

检查结果要能被后来的人读懂。写“正常”可以，但异常要写证据。比如“对象存储本周增长 18GB，高于平时 3GB，来源集中在头像上传，已开任务排查”。这样的记录能让下周接着看。

## 每月处理增长、更新和账号变化

每月清单适合处理慢慢堆起来的东西。

- 检查依赖更新、运行时版本、基础镜像和平台弃用通知。
- 检查数据库大小、慢查询、索引、备份体积和恢复记录。
- 检查对象存储、日志保留、缓存和临时文件。
- 检查成员权限、离职人员、外包账号、API Key 和 SSH key。
- 检查预算、固定费用、闲置资源和第三方配额。
- 检查隐私政策、商店资料和小程序隐私保护指引是否仍对应实际功能。

更新不要全自动冲进生产。先看 changelog、风险、测试和回退。小版本安全修复可以快，大版本升级要单独计划。依赖升级、数据库迁移和平台要求变化，最好不要和业务大功能混在同一天。

账号变化尤其容易漏。人离开项目后，他的 GitHub、部署平台、云平台、商店、SSH 和客服系统权限都要撤销。共享账号要逐步替换成独立账号。

每月还适合整理文档。README、部署步骤、恢复手册、商店发布记录、隐私政策链接和客服模板，都会随着项目变化变旧。文档过期比没有文档更危险，因为它会让新人按旧步骤做错。

如果项目使用 AI 生成功能，每月看配额、失败率、平均费用、敏感数据过滤和模型版本变化。模型供应商、价格、上下文限制和安全策略都可能调整。记录当前使用的模型和关键参数，避免一次升级改变生产行为却无人知道。

## 每季度验证系统性假设

每季度清单不看小修小补，专门验证平时没人愿意碰的大问题。

- 从备份恢复一次到隔离环境。
- 演练一次后端故障、App 旧版本兼容或小程序线上版回退。
- 检查最小权限、密钥轮换和应急联系人。
- 审查公开入口、数据库暴露、文件上传和错误页面。
- 检查域名、证书、商店账号、公司主体和付款资料。
- 审查监控覆盖的用户路径和告警值班。
- 删除过期测试数据、临时资源和废弃项目。

季度检查要记录实际结果。恢复花了多久，失败在哪一步，谁能批准，哪份文档过期。只勾选“已检查”没有意义。演练发现问题，是好事。它说明事故前还有时间改。

季度检查也适合做一次权限瘦身。很多权限是在赶项目时临时给出的。三个月后，上传权限、管理员权限、生产数据库访问、商店发布角色、服务器 sudo 和第三方 API 管理权，可能已经超过实际需要。收回权限比等事故后追责有效。

对外部依赖也要问一次替代方案。域名服务、部署平台、数据库、支付、短信、邮件、地图、AI API 和商店账号，任何一个长时间不可用时怎么办。答案不一定是马上做多活架构，至少要知道影响、沟通方式和短期手工方案。

## 触发事件不用等日历

某些变化发生时，不要等到下周或下季度。发布重大版本、数据库迁移、接入支付、开放文件上传、上线 AI 功能、换云平台、改域名、升级目标 API、提交 App 或小程序审核，都应临时执行相关检查。

安全事件、费用异常、用户投诉集中、依赖曝出漏洞、成员离职、密钥疑似泄露，也要立刻触发清单。日历是最低频率，不是最高频率。

触发事件后，把新项目加入长期清单。新增小程序，就增加 AppID、成员、合法域名、隐私指引、体验版、审核版和线上版检查。新增移动 App，就增加签名、商店账号、崩溃、版本兼容和隐私表单检查。

触发事件要有负责人。数据库迁移由后端负责人牵头，支付由业务和技术一起确认，商店审核由账号持有人确认，安全事件由能撤销权限的人处理。只在群里说“大家注意一下”，通常没有人真正负责。

触发检查还要有结束条件。比如目标 API 升级后，Android 内部测试通过、权限拒绝路径通过、崩溃率观察一段时间、商店资料更新完成，才算结束。没有结束条件，任务会变成“大家都觉得应该差不多了”。

## 自动化保留人工确认边界

自动化适合提醒、采集和生成报告。它可以检查证书剩余天数、备份是否生成、构建是否失败、预算是否超限、依赖是否过期。它不应在没有授权的情况下删除数据库、开放防火墙、轮换生产密钥或公开发布 App。

每个自动化动作写清触发条件、权限、通知对象和失败处理。提醒没人看，就等于没有提醒。自动修复也要有日志。错误的自动化比没有自动化更危险，因为它会稳定地做错事。

AI 可以把日志、账单、依赖和权限整理成周报。输出应标明数据来源和不确定项。涉及生产变更时，让它提出建议，由人确认执行。

自动化提醒要避免制造噪声。证书还有 60 天、30 天、7 天可以分级提醒。每天重复发送同一条无人处理的消息，只会让人屏蔽。提醒里要有链接、负责人和具体动作。没有动作的提醒，应该删掉或改写。

自动化报告也要保护数据。周报里不要包含完整用户邮箱、订单、令牌、日志正文和付款信息。给 AI 生成摘要时，先用聚合数据和脱敏样本。维护报告会被转发，里面的权限要比原始日志更收敛。

## 小项目的轻量版本

个人项目或早期产品不需要一开始就上复杂流程。可以先保留四张小表。资产表，写域名、部署平台、数据库、存储和账号。发布表，写提交、版本、时间和验证。秘密表，只写名称、保存位置和撤销办法。维护表，写每周、每月、每季度要看的几件事。

轻量不等于随意。至少要知道谁拥有账号、钱从哪里扣、数据在哪里、怎样备份、怎样关闭。项目越小，越容易把所有事放在一个人脑子里。那个人一忙，维护就断了。

等项目变复杂，再把清单拆细。新增用户账号，就增加隐私和删除路径。新增移动 App，就增加签名和商店发布。新增小程序，就增加 AppID、成员、合法域名和审核材料。清单跟着责任长大。

## 定期删除无效项目

清单会膨胀。项目已经下线，告警已经废弃，负责人已经变化，某个检查从来没有发现过问题，就要调整。保留无效项目会让真正重要的项被淹没。

删除清单项前确认风险是否已经消失。例如旧服务器已销毁，域名已释放，密钥已撤销，备份保留期已过。若只是暂时没人看，不能靠删除让问题消失。把原因写进维护记录。

事故也要反哺清单。一次 502 来自代理端口不一致，就把发布前代理健康检查加入清单。一次商店审核因测试账号失效被拒，就把审核账号检查加入发布前步骤。清单从事故里长出来，才会越来越贴合项目。

清单也要有版本。每次增加、删除或修改项目，写清原因和日期。这样半年后能看见维护重点怎样变化。项目从静态网站变成带账号的应用，清单会增加数据库、备份、隐私和权限。项目停止商业使用，清单会转向数据导出、下线和账号撤销。

不要追求一份永远完整的清单。维护对象会变，平台规则会变，团队成员也会变。清单最重要的能力，是能跟着真实项目继续改。

## 值班交接卡

维护清单还需要交接。很多项目平时有人照看，信息却停在某个人脑子里。那个人休假、离职、换岗位，后来的人只能从群消息和旧邮件里猜。值班交接卡可以很短，但要固定。

一张交接卡至少写清本周发布了什么，哪些告警反复出现，哪些临时权限还没收回。证书、域名、套餐或商店材料快到期，也要单独写。备份是否成功生成，最近一次恢复测试有没有通过，同样要留下记录。还要写未完成事项和下一位负责人。不要只写“已同步”，要写下一步谁做、什么时候看、到哪里找证据。

交接也要覆盖小程序和移动端。体验版给了谁，审核版是否还在等待，线上版是否依赖某个后端兼容开关，测试账号是否有效，隐私设置是否和实际功能一致。这些信息看起来琐碎，出问题时却最难临时补。

值班交接卡不必正式到像制度文件。它可以是一页 Markdown、一张表、一个工单模板。关键是每次交接都能让后来的人接着跑，不需要重新追问背景。项目越依赖少数熟人，越需要这张小卡片。交接卡也能暴露维护债。如果每周都要解释同一个临时开关、同一个手工发布步骤、同一个审核账号异常，就说明它不该继续靠口头提醒存在，应当进入文档、脚本或发布前检查。

交接结束前，接手人要能独立找到后台入口、最近一次发布记录、备份位置和告警页面。找不到，就把缺口当场补进清单。下次检查时，也要确认这条补充是否真的帮后来的人少问一次。

## 本章最终检查

- 是否列出所有资产、负责人和证据位置。
- 每周是否看部署、告警、费用、容量和临时变更。
- 每月是否看依赖、账号、存储、备份和隐私资料。
- 每季度是否真实演练恢复、安全和旧版本兼容。
- 触发事件是否能临时启动相关检查。
- 自动化是否只做被授权的动作。
- 无效清单项是否定期删除。

维护清单的价值不在于显得专业。它让普通项目在几个月后仍有人知道入口、证据和责任在哪里。
