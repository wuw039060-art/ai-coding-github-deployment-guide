# 包管理器、锁文件、版本号和环境差异

同一个项目在作者电脑上能运行，换一台电脑却失败，常被含糊地归为“环境问题”。这个说法太宽，里面可能藏着一组差异。包管理器、锁文件、运行时版本、操作系统、环境变量、工作目录和全局工具都可能参与。

本章目标，是把“环境不同”变成一张可以逐项比较的表。读者无需学会维护包管理器内部机制，只需要知道哪些文件不能随意删，哪些版本需要记录，哪些值不能放进仓库。

## 包管理器按项目约定工作

包管理器负责读取项目清单，从软件仓库取得依赖，放入约定位置，并执行项目脚本。JavaScript 项目常见 npm、pnpm 和 Yarn。一个项目通常会表明自己使用哪一个。仓库存在 `pnpm-lock.yaml`，README 又要求 pnpm 时，应遵循项目约定。混用工具可能生成第二份锁文件，得到不同依赖树。

可以把包管理器想成按采购单配货的仓库。`package.json` 写需要哪些物品和可接受范围，锁文件记录上次实际配到的品牌与批次，`node_modules` 是送到现场的箱子。包管理器不会判断软件是否适合你的业务，也不能保证所有依赖安全。处理风险仍是维护者责任。

项目构建工具通常应写进开发依赖，通过包管理器脚本调用。不要依靠本机全局安装的 `vite`、`typescript` 或某个 CLI。平台和新电脑没有这些全局工具，就会失败。全局工具适合系统级管理或官方明确要求的 CLI，也要记录版本。

## 清单写范围，锁文件写结果

`package.json` 中的 `dependencies` 通常列出程序运行需要的包，`devDependencies` 常列出构建、测试和开发工具。构建平台若在云端执行构建，就要安装构建所需开发依赖。把 Vite 只装在某个人电脑的全局环境中，平台便找不到它。

锁文件描述更完整的依赖树，帮助后续安装固定依赖解析结果，但不能单独保证不同操作系统、运行时和安装脚本生成完全相同的文件。它通常由工具维护。更新依赖应通过包管理器命令完成，让工具同步修改清单与锁文件。遇到锁文件冲突时，不要随意保留两边文本；确认最终清单需要哪些依赖，在受控环境重新安装并测试，再提交工具生成的锁文件。

自动构建应采用项目约定的严格安装方式。例如 npm 项目使用 `npm ci` 时，清单与锁文件不一致会报错，不会顺手改写锁文件。它也会移除已有 `node_modules` 后重新安装，适合全新副本或构建环境；不要在唯一工作副本中把它当作没有影响的检查命令。其他包管理器的冻结锁文件选项需按对应版本确认。

常见语义化版本写成 `3.7.2`。三个数字通常依次代表主版本、次版本和修订版本。兼容性承诺由维护者给出，不能只凭数字保证。项目清单还会使用范围符号。`1.2.3` 倾向锁定一个版本，`^1.2.3` 通常允许同一主版本内更新，`~1.2.3` 通常允许同一次版本内修订更新。实际规则以当前包管理器文档为准。

上面的范围示例不能直接套到所有 `0.x` 版本。按 npm 使用的 semver 规则，`^0.2.3` 允许兼容的 `0.2.x` 更新，不包括 `0.3.0`；`^0.0.3` 则不会接受 `0.0.4`。预发布版本还有额外匹配规则。

范围不等于实际安装版本。锁文件才记录一次解析后的具体结果。删除锁文件再安装，虽然清单没有变化，也可能拿到更晚的依赖。若一个小改动突然引发大量构建错误，先看锁文件是否消失或被意外重写。

## 更新依赖要分批验证

项目直接使用的包叫直接依赖，直接依赖又会引用传递依赖。你只在清单中增加一个界面库，实际可能安装数百个包。升级直接依赖可能改变传递依赖；构建工具升级又可能要求更高运行时版本。只看自己改动的一行版本号，会低估影响范围。

更新时保存三类证据。清单与锁文件的差异，安装和构建日志，关键页面或测试结果。安全警告也要具体判断。漏洞是否影响本项目使用路径，修复是否带来主版本升级，生产是否实际包含该依赖，都需要核实。不要看到审计数字就盲目执行强制自动修复。

一次同时升级框架、运行时和几十个插件，会让错误难以定位。按依赖关系分批更新，每批都有可返回提交。主版本变化更要单独处理，先读迁移说明，再用预览环境验证。

## 运行时版本要有证据

项目可以在 README、`package.json` 的 `engines`、`.nvmrc`、平台设置或容器配置中声明 Node.js 版本。多个位置同时存在时要保持一致。部署日志通常会写实际使用版本。不要只看控制台中选择的值，因为平台可能有默认升级、格式解析失败或项目配置覆盖。

本机记录版本时保留完整输出。`v20` 太宽泛，`v20.19.4` 才能用于复现。npm、pnpm 或 Yarn 也各自有版本。不要把 npm 版本号误填到 Node.js Runtime 选项，也不要因为 npm 有新版本就立即全局升级正式构建机。先看项目支持范围，在练习分支验证，再统一团队和平台设置。

操作系统也会暴露差异。Windows 和常见 macOS 默认文件系统经常不严格区分大小写，Linux 云构建环境通常区分。导入路径的每个字母应与真实文件名一致。脚本还可能依赖 Bash 命令，在 Windows PowerShell 中不可用。若项目只支持某个 Shell，应写在 README 和发布记录中。

## 环境变量不是自动安全

环境变量由运行环境向程序提供名称和值。常见用途包括 API 地址、功能开关和服务凭据。开发、预览和生产可以使用同名变量、不同值，减少代码分支。代码读取变量，部署平台在指定环境中提供值。

前端构建需要的变量可能被写进浏览器可下载的 JavaScript。只要值送到浏览器，就不能当作秘密。框架常用特定前缀区分可暴露变量，前缀只是明确暴露意图，不会加密值。数据库管理员密码、支付私钥、服务端密钥和小程序 AppSecret 应只在可信服务端使用。

真实 `.env` 通常加入 `.gitignore`，仓库可以提供不含秘密的 `.env.example`，只列变量名、用途和示例格式。不要先提交真实密钥，再用一个新提交删除。历史中仍可能存在旧内容。变量缺失时，程序应尽早给出清楚错误；空字符串可能让请求悄悄发往错误地址。

平台控制台添加变量后，要确认作用环境并触发新部署。若预览正常、生产失败，第一项比较就是两边的变量名、作用环境和部署时间。检查时不把真实值复制进公开 Issue、截图或 AI 对话。

## 工作目录决定工具看到什么

终端命令总在某个当前目录执行。包管理器从这里或上级寻找清单，构建工具据此解析相对路径。一个仓库可能同时有 `web/` 和 `api/` 两个项目。部署网页时如果平台以仓库根为根，就可能报告找不到 `package.json`；Root Directory 用来告诉构建系统先进入哪个子目录。

Root Directory 指原材料所在位置，Output Directory 指构建后成品所在位置。它们不是同一个字段。填入本机绝对路径没有意义，云端没有你的电脑目录。Monorepo 项目还可能需要从仓库根安装，再构建子项目。先读工作区配置和 README，不要把共享源码复制进站点目录。

全新 Clone 是检验环境的好办法。不要在唯一工作副本上随意删除依赖或锁文件。创建新目录，Clone 指定提交，按照项目声明安装、构建和预览。若新目录失败而旧目录成功，旧环境可能藏有未提交文件、缓存或全局工具。

## 环境差异表

遇到本地与云端不同，可以填写下表。未知项保留未知，随后从日志或配置取得证据。

| 项目 | 本地 | 预览 | 生产 |
| --- | --- | --- | --- |
| 源提交 | 完整编号 | 完整编号 | 完整编号 |
| 项目根目录 | 实际路径 | 平台设置 | 平台设置 |
| 运行时 | 名称与完整版本 | 日志版本 | 日志版本 |
| 包管理器 | 名称与版本 | 日志版本 | 日志版本 |
| 锁文件 | 文件名与提交状态 | 是否使用 | 是否使用 |
| 构建命令 | 实际命令 | 平台命令 | 平台命令 |
| 环境变量 | 名称清单 | 名称清单 | 名称清单 |
| 操作系统 | Windows 或 macOS 等 | 构建镜像 | 构建镜像 |

表中不写秘密值。比较结果用“相同”“不同”“未知”标记。先处理与错误最相关的差异。日志说找不到 `src/logo.svg`，操作系统大小写和源提交比数据库变量更相关；登录回调指向测试域名，环境变量与部署环境更相关。

## 锁文件消失以后的例子

假设一个维护多年的小站只改了页脚文字，部署却突然报出许多 TypeScript 错误。Git Diff 显示前一个提交删除了 `package-lock.json`，理由是“它会自动生成”。平台重新解析依赖范围，安装了后来发布的多个版本。本机旧目录仍保留以前的 `node_modules`，所以作者没有复现。

维护者先从上一个成功提交恢复锁文件，在全新 Clone 中运行严格安装与构建。错误消失，证明问题与依赖树变化相关。随后把真正需要的依赖升级拆成单独分支，查看变更说明并逐项测试。锁文件随清单一起提交，部署日志记录实际 Node.js 和 npm 版本。

这次修复没有删除缓存碰运气，也没有把平台命令改宽松。它恢复了可重现输入，再把升级变成一项可审查工作。若上一个锁文件本身已经不可用，仍可从成功构建记录、包仓库版本和备份中重建。重建结果要经过完整测试，不能冒充原来的精确环境。

依赖安装期间还可能执行安装脚本。它们可编译组件，也具备读取当前环境和发起网络请求的能力。陌生项目先查看清单与锁文件，避免在含生产密钥的终端环境安装。需要更严格审计时，在隔离环境评估哪些包确实需要脚本。
