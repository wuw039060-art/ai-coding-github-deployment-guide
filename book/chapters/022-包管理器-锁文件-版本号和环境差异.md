# 包管理器、锁文件、版本号和环境差异

同一个项目在作者电脑上能运行，换一台电脑却失败，常被含糊地归为“环境问题”。环境问题不是一个原因，它是一组差异。包管理器、锁文件、运行时版本、操作系统、环境变量和工作目录都可能参与。

这一章的目标，是让“环境不同”变成一张可以逐项比较的表。读者无需学会维护包管理器，只需要知道哪些文件不能随意删，哪些版本需要记录，哪些值不能放进仓库。

## 包管理器管理什么

包管理器负责读取项目清单，从软件仓库取得依赖，放入约定位置，并执行项目脚本。JavaScript 项目常见 npm、pnpm 和 Yarn。一个项目通常会表明自己使用哪一个。不要因为电脑里恰好装了 npm，就把任何项目的安装命令改成 `npm install`。仓库存在 `pnpm-lock.yaml`，README 又要求 pnpm 时，应遵循项目约定。混用工具可能生成第二份锁文件，得到不同依赖树。

可以把包管理器想成按采购单配货的仓库。`package.json` 写需要哪些物品和可接受范围，锁文件记录上次实际配到的品牌与批次，`node_modules` 是送到现场的箱子。包管理器不会判断软件是否适合你的业务，也不能保证所有依赖安全。它负责取得与组织文件，选择依赖和处理风险仍是项目维护者的责任。

## 清单写范围，锁文件写结果

`package.json` 中的 `dependencies` 通常列出程序运行需要的包，`devDependencies` 常列出构建、测试和开发工具。具体部署是否需要安装开发依赖，取决于平台在哪一步执行构建。若平台先安装依赖再构建，构建工具即使不进入最终网页，也必须在构建阶段可用。把 Vite 只装在某个人电脑的全局环境中，平台便找不到它。

`package-lock.json` 会描述更完整的依赖树，使后续安装可以重现相同结果。npm 官方说明锁文件应提交到源代码仓库，让团队、部署和持续集成获得同一依赖树。锁文件不是手写配置。日常更新依赖应通过包管理器命令完成，让工具同步修改清单与锁文件。手工删除其中几行可能破坏完整性校验。

遇到锁文件冲突时也不要随意保留两边文本。确认最终清单需要哪些依赖，在受控环境重新安装并测试，再提交工具生成的锁文件。

常见语义化版本写成 `3.7.2`。三个数字通常依次代表主版本、次版本和修订版本。兼容性承诺由软件维护者给出，不能只凭数字保证。修订版本常用于兼容的错误修复，次版本常增加兼容功能，主版本常包含不兼容变化。npm 的初学者说明也采用这一模型。

项目清单还会使用范围符号。`1.2.3` 倾向于锁定一个版本，`^1.2.3` 通常允许安装同一主版本内的更新，`~1.2.3` 通常允许同一次版本内的修订更新。零开头版本有额外规则，最终以包管理器的版本范围规则为准。范围不等于实际安装版本。锁文件才记录一次解析后的具体结果。删除锁文件再安装，虽然清单没有变化，也可能拿到更晚的依赖。

## 更新依赖为什么会连锁

项目直接使用的包叫直接依赖，直接依赖又会引用其他包，那些是传递依赖。你只在清单中增加一个界面库，实际可能安装数百个包。升级直接依赖可能改变传递依赖。构建工具升级又可能要求更高 Node.js 版本。只看自己改动的一行版本号，会低估影响范围。

因此更新时保存三个证据。清单与锁文件的差异，安装和构建日志，关键页面或测试结果。生产部署还应有可恢复的上一个版本。安全警告也要具体判断。漏洞是否影响本项目使用路径，修复是否带来主版本升级，生产是否实际包含该依赖，都需要核实。不要看到审计数字就盲目执行带强制参数的自动修复。

项目可以在 README、`package.json` 的 `engines`、`.nvmrc`、平台设置或容器配置中声明 Node.js 版本。多个位置同时存在时要保持一致。部署日志通常会写实际使用版本。不要只看控制台中选择的值，因为平台可能有默认升级、格式解析失败或项目配置覆盖。

本机查看 Node.js 与 npm 版本可以运行以下命令。

```
node --version
npm --version
```

这两条命令只读取版本，不修改项目。可以在 Windows PowerShell、Windows Terminal、macOS Terminal 或 Linux Shell 运行。正常结果是分别显示版本号。

若显示找不到命令，说明当前终端无法定位程序。先核对安装与 PATH，关闭并重新打开终端。不要从陌生网站下载所谓修复工具。记录版本时把前缀和完整数字都保留。`v20` 太宽泛，`v20.19.4` 才能用于复现。

## 开发、预览和生产环境

开发环境强调快速修改和详细错误，预览环境用于检查候选版本，生产环境面对真实用户。三者可能使用不同域名、数据库、密钥和优化设置。环境变量是由运行环境向程序提供的名称和值。常见用途包括 API 地址、功能开关和服务凭据。代码读取变量，部署平台在指定环境中提供值。

环境变量不等于自动安全。前端构建需要的变量可能被写进浏览器可下载的 JavaScript。只要值送到浏览器，就不能当作秘密。框架通常用特定前缀区分可暴露变量，但前缀只是明确暴露意图，不会加密值。

数据库管理员密码、支付私钥和服务端密钥应只在可信服务端使用。公开站点所需的 API 基础地址通常可以公开。判断关键是浏览器用户是否本来就需要知道这个值。Vercel 当前文档把变量按 Development、Preview 和 Production 等环境管理。变量改动只用于后续部署，旧部署不会自动重建。平台规则会变化，封版时还要复核。

许多本地项目用 `.env` 保存环境变量。真实 `.env` 通常加入 `.gitignore`，仓库可以提供不含秘密的 `.env.example`，只列变量名与示例格式。一个合适的示例可能这样写。

```
PUBLIC_API_URL=https://api.example.test
SERVER_API_KEY=replace-me-locally
```

示例中的域名与值必须是虚构或专用测试值。不要先提交真实密钥，再用一个新提交删除。历史中仍可能存在旧内容。本机缺少变量时，程序应尽早给出清楚错误。空字符串可能让请求悄悄发往错误地址，更难排查。

平台控制台添加变量后，要确认作用环境并触发新部署。若预览正常、生产失败，第一项比较就是两边的变量名和是否存在。检查时不要把值复制进公开 Issue 或聊天记录。

## 工作目录决定工具看到什么

终端命令总在某个当前目录执行。包管理器从这里或上级寻找清单，构建工具据此解析相对路径。一个仓库可能这样组织。

```
my-project/
  README.md
  web/
    package.json
    src/
  api/
    package.json
    src/
```

网页项目根目录是 `web`，后端根目录是 `api`。部署网页时如果平台以 `my-project` 为根，便可能报告找不到 `package.json`。平台中的 Root Directory 用来告诉构建系统先进入哪个子目录。它不是发布目录。Root Directory 指向原材料所在位置，Output Directory 指向构建后成品所在位置。

相对输出目录通常相对于项目根目录解释。填入绝对的本机路径没有意义，云端没有你的 `C:\Users\...`。

## 操作系统差异

Windows 和常见 macOS 默认文件系统经常不严格区分大小写，Linux 云构建环境通常区分。导入路径的每个字母应与真实文件名一致。路径分隔符也不同。代码和构建配置应使用工具提供的跨平台路径能力，不要把 Windows 反斜杠硬编码进网页 URL。

脚本还可能依赖 Bash 命令，在 Windows PowerShell 中不可用。若项目只支持某个 Shell，应在 README 写明。部署平台执行的 Shell 也要核对。换行符通常由 Git 和编辑器处理，但某些脚本的解释器行会受影响。看到脚本存在却报告无法执行时，检查权限、换行与解释器路径。

选择一个没有秘密的练习项目。记录当前提交编号、操作系统、Node.js 版本和包管理器版本。确保清单与锁文件均已提交。把现有 `node_modules` 当作可重建缓存，不把它复制到另一台电脑。在一个新目录 Clone 项目，使用项目约定的包管理器安装，然后执行构建与预览。

成功结果应包括依赖安装无错误、构建命令退出成功、输出目录出现、浏览器可打开关键页面。把四项结果写入验证记录。若新目录失败而旧目录成功，旧环境可能藏有未声明依赖、未提交文件或全局工具。比较文件清单和命令路径，比反复删除缓存更有价值。

不要在唯一工作副本上随意删除依赖或锁文件。练习使用新 Clone，问题解决后再决定是否调整正式项目。

## 四类常见失败

第一类是锁文件与清单不一致。持续集成常使用严格安装命令，发现两者不同会直接失败。用正确包管理器更新并提交两者。第二类是平台选错运行时。日志中语法错误或引擎不兼容时，对照项目声明与实际版本。

第三类是环境变量缺失。构建阶段缺失会让构建失败，运行阶段缺失可能直到访问某项功能才出现。区分错误发生阶段。第四类是根目录错误。日志连清单都找不到时，先看工作目录，不要开始升级依赖。

先看锁文件。`package-lock.json` 通常对应 npm，`pnpm-lock.yaml` 对应 pnpm，`yarn.lock` 对应 Yarn。再看 `package.json` 是否有 `packageManager` 字段，README 是否写了准备步骤。持续集成工作流也是证据。GitHub Actions 中启用了 pnpm，缓存键也引用 `pnpm-lock.yaml`，说明维护者期待使用 pnpm。

仓库同时出现多种锁文件要谨慎。可能正在迁移，也可能有人误用工具。查看最近提交和项目说明，不要自行删除其中任何一份。确认后把包管理器名称与版本写进验证记录。Corepack 等工具可能帮助固定版本，是否启用按项目当前文档处理。

## 版本范围的一个实际后果

假设清单允许 `^2.4.0`，锁文件记录 `2.4.3`。电脑甲按锁文件安装 2.4.3。有人删除锁文件后，电脑乙可能解析到后来发布的 2.9.0。两个版本理论上位于兼容范围，维护者仍可能在边缘行为上出现差异。若乙的构建失败，只比较 `package.json` 会认为环境相同，实际依赖已经不同。

恢复锁文件并严格安装，可以验证差异是否来自依赖解析。若需要升级到 2.9.0，应把它作为一次明确更新，审查变更、运行测试并提交新锁文件。主版本变化更要单独处理。一次同时升级框架、运行时和几十个插件，会让错误难以定位。按依赖关系分批更新，每批都有可返回的提交。

安装 Node.js 通常会带一个 npm 版本，二者各自有版本号。平台选择 Node.js 后，实际 npm 版本也可能受平台镜像或项目设置影响。日志同时记录 `node --version` 和 `npm --version`。锁文件由较新 npm 生成，较旧 npm 可能给出格式警告或不同结果。

不要把 npm 版本号误当成 Node.js 版本填写到平台 Runtime 选项。也不要因为 npm 有新版本就立即全局升级正式构建机。先看项目支持范围，在练习分支验证，再统一团队与平台设置。

## 建一张环境差异表

遇到本地与云端不同，可以填写下表。未知项保留未知，随后从日志或配置取得证据。

| 项目 | 本地 | 预览 | 生产 |
| --- | --- | --- | --- |
| 源提交 | 完整编号 | 完整编号 | 完整编号 |
| 项目根目录 | 实际路径 | 平台设置 | 平台设置 |
| Node.js | 完整版本 | 日志版本 | 日志版本 |
| 包管理器 | 名称与版本 | 日志版本 | 日志版本 |
| 锁文件 | 文件名与提交状态 | 是否使用 | 是否使用 |
| 构建命令 | 实际命令 | 平台命令 | 平台命令 |
| 环境变量 | 名称清单 | 名称清单 | 名称清单 |
| 操作系统 | Windows 或 macOS 等 | 构建镜像 | 构建镜像 |

表中不写秘密值。比较结果用“相同”“不同”“未知”标记。先处理与错误最相关的差异。例如日志说找不到 `src/logo.svg`，操作系统大小写和源提交比数据库变量更相关。登录回调指向测试域名，环境变量与部署环境更相关。

平台表单有时把输入当纯文本，有时支持引用其他秘密。不要把外层引号误当成值的一部分。多行私钥、JSON 和换行符尤其容易出错。使用供应商支持的秘密格式，验证程序能解析。不要通过在日志打印完整值来检查。

末尾空格也可能造成签名或 URL 异常。确认输入方式与官方示例，必要时在本地用虚构值复现格式。布尔值环境变量仍是字符串；代码把字符串 `false` 当成真值，会错误开启功能；程序要明确解析允许的值；空值与不存在也可能含义不同；部署前定义校验，在启动或构建早期列出缺少的变量名。

## 全局工具造成的隐形依赖

本机曾经全局安装 `vite`、`typescript` 或某个 CLI，项目脚本即使未声明依赖也可能碰巧运行。新电脑与平台没有该工具，立即失败。检查命令实际来自哪里。在 Windows PowerShell 可使用 `Get-Command 工具名`，macOS 或 Linux 可使用 `command -v 工具名`。这里只在自己的开发环境读取路径。

项目构建工具通常应写进开发依赖，通过包管理器脚本调用。这样版本进入清单与锁文件。全局工具适合系统级管理或官方明确要求的 CLI，也要记录版本。不要用全局安装掩盖项目清单缺漏。

部分包包含针对操作系统和处理器编译的本机代码。复制另一台电脑的 `node_modules`，可能携带不兼容文件。常见表现是安装成功记录来自旧环境，运行时却报告无法加载二进制模块。处理方向是保留清单与锁文件，在目标环境重新安装。

Windows、Intel Mac、Apple 芯片 Mac 和 Linux 的产物可能不同。部署包不要简单打包本机整个依赖目录，除非项目工具明确支持目标平台交叉构建。Docker 能固定更多环境，仍不能自动解决处理器、内核与外部服务差异。第七卷会展开这一边界。

## 一个最小复现环境

当旧工作目录状态复杂时，创建全新临时目录 Clone 指定提交。不要复制 `.env`，先用示例值启动纯构建。按照项目声明安装并构建。成功说明仓库至少包含基本材料，旧目录问题可能来自未提交修改或缓存。失败说明问题更容易复现和共享。

随后只加入当前功能需要的测试变量。每次增加一组并记录结果。这样能发现哪个环境输入引发变化。临时目录验证完可清理，但先确认没有唯一修改或日志。正式修复回到工作分支，通过可审查提交完成。

先读框架和关键依赖的支持范围，选择仍受维护的目标版本。在分支中更新版本声明，让本机、持续集成和平台一致。从全新依赖安装开始，运行测试、构建与预览。检查原生依赖、图片处理、服务端启动和部署。

生产更新前准备旧版本回退，并确认数据库没有不兼容变化。发布后记录实际运行版本，不以设置页面的期望值代替日志证据。完成后更新 README 和验证记录。下一位维护者不应再从聊天记录猜版本。

## 安装脚本带来的安全风险

依赖安装期间可能执行 `preinstall`、`install` 或 `postinstall` 脚本。它们可编译组件，也具备读取当前环境和发起网络请求的能力。陌生项目先查看清单与锁文件，避免在含生产密钥的终端环境安装。需要更严格审计时，在隔离环境阻止安装脚本，再评估哪些包确实需要。

关闭脚本可能让合法原生依赖无法工作，所以它是调查手段，不是对所有项目的永久设置。发现可疑行为时停止运行，保存包名、版本和日志，通过包仓库与项目安全渠道核实。

组织项目可能从私有 npm 注册表取得依赖。部署平台需要只读令牌与正确注册表配置。令牌放入秘密管理，不写进 `.npmrc` 后提交。仓库可保留引用环境变量的配置模板。安装返回 401 或 403 时，检查注册表地址、令牌作用范围和过期时间。返回 404 也可能是无权限时隐藏包存在。

令牌应只允许读取所需包，预览分支不自动继承生产发布令牌。撤销成员时同步撤销包仓库凭据。

## Windows 与 macOS 的记录方式

Windows 记录 PowerShell 版本、Node.js 架构和项目路径。路径位于 OneDrive 或含特殊字符时，也应写入复现信息。macOS 记录 Intel 或 Apple 芯片。Rosetta 下安装的原生依赖与原生 ARM 环境可能不同。

两边都不要复制 `node_modules` 给另一台机器。提交清单与锁文件，在目标环境安装。团队确需统一系统时，可在后续使用容器或持续集成作为共同基准，仍保留本机差异说明。

在新分支只更新一个目标依赖及必要配套包。保存清单和锁文件 Diff。从干净环境安装，运行测试、构建和预览。对受影响功能做具体操作，例如路由库更新就检查深层链接与刷新。查看产物大小、浏览器 Console 和平台预览。确认后再合并，发布记录写明旧版、新版和回退提交。

如果更新引发大范围锁文件变化，先确认是否误换包管理器或版本。无法解释的变化不要直接合并。

## 综合例子　锁文件消失以后

一个维护多年的小站只改了页脚文字，部署却突然报出许多 TypeScript 错误。Git Diff 显示有人在前一个提交删除了 `package-lock.json`，理由是“它会自动生成”。平台重新解析依赖范围，安装了后来发布的多个版本。本机旧目录仍保留以前的 `node_modules`，所以作者没有复现。

维护者先从上一个成功提交恢复锁文件，在全新 Clone 中运行严格安装与构建。错误消失，证明问题与依赖树变化相关。随后把真正需要的依赖升级拆成单独分支，查看变更说明并逐项测试。锁文件随清单一起提交，部署日志记录实际 Node.js 和 npm 版本。

这次修复没有删除缓存碰运气，也没有把平台命令改宽松。它恢复了可重现输入，再把升级变成一项可审查工作。若上一个锁文件本身已经不可用，仍可从成功构建记录、包仓库版本和备份中重建。重建结果要经过完整测试，不能冒充原来的精确环境。

不要背所有版本范围符号。先能认出清单、锁文件、依赖目录和运行时声明。复制部署配置前，确认使用的包管理器、项目根目录、构建命令与产物目录。暂时不用在 npm、pnpm 和 Yarn 之间做性能比较。已有项目使用哪个，就先按它的文档复现。新项目也应选一个并保持一致。

## 依赖升级不能只看安装成功

AI 可以根据仓库文件判断项目使用的包管理器，比较多个版本声明，列出环境差异检查表，并从脱敏日志中定位安装阶段或构建阶段。要求 AI 引用文件名和字段。若它建议删除锁文件、强制升级或执行自动修复，先让它说明影响与恢复办法。

环境变量的真实值、生产与预览的作用范围、密钥是否暴露、依赖升级后的关键流程都要亲自确认。提交前查看 Git Diff，避免把 `.env` 和大批依赖文件带入仓库。下一章会用这些准备在本机预览一个静态站点，并分清直接发布文件和先构建再发布的两条路线。
