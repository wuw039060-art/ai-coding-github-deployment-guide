# 备份、恢复测试、监控、费用和安全下线

一个项目上线后，需要回答三个容易被推迟的问题。数据丢失时能恢复到哪里，服务变坏时谁会先知道，项目停止时怎样关闭而不留下费用、域名、密钥和用户数据。备份、监控、费用与下线分别处理数据、运行、支出和终止，最终都在管理长期责任。

备份文件存在不等于能够恢复，监控页面绿色不等于用户核心路径正常，删除服务器也不等于项目已经下线。每项工作都需要明确对象、负责人、触发条件、验证证据和保留期限。本章使用一个小型笔记服务说明完整维护过程，具体命令仍要按真实数据库版本、平台和数据政策核对。

## 先确定能承受丢多少和停多久

恢复点目标 RPO 表示最多能接受丢失多长时间的数据。例如每晚备份一次，最坏可能丢近二十四小时；若用户每分钟创建订单，这个目标通常不可接受。恢复时间目标 RTO 表示发生故障后，希望多长时间恢复到可用状态。两者是业务选择，决定备份频率、技术方案、成本和演练难度。

个人笔记站可以选择 RPO 为一小时、RTO 为四小时；静态作品集的源文件已经在 Git，RPO 可能按每次提交计算；支付与健康数据需要更严格设计和法规评估。不要复制大型公司的数字，也不要把“实时同步”当备份。错误删除、勒索软件和程序 Bug 可能立即同步到所有副本。

先写数据分类。通常包括数据库、用户上传、对象存储、配置、秘密的恢复方式、域名与 DNS、部署版本、商店材料和文档。缓存、构建产物与可从代码重新生成的内容可以不备份，但要验证生成过程仍可用。秘密往往不适合直接塞进普通备份，应通过秘密管理系统的恢复机制与受控应急材料处理。

只在同一服务器复制数据库文件，无法应对磁盘损坏、账号被攻破或供应商删除。实用原则是保留多个副本、使用不同介质或故障域，并至少有一份与生产权限隔离。具体数量与位置由风险、成本和隐私决定，重要的是一次生产账号失陷不能同时删除全部恢复点。

备份存储要加密、限制访问、记录保留与删除策略。加密密钥若与备份放在同一公开目录，保护形同虚设；唯一密钥若无人能恢复，备份也会失去价值。建立恢复负责人、应急访问和轮换流程，定期确认账号、多因素认证与付款状态。

对象存储提供对象与元数据的持久保存能力，是否有版本控制、生命周期、跨区域复制和不可变保护取决于具体服务配置。不要因为平台宣传“高耐久”就省略版本与删除保护。应用错误地覆盖对象、拥有删除权限的凭据泄露、生命周期设置错误，都可能损坏数据。

## PostgreSQL 逻辑备份与恢复测试

`pg_dump` 可以导出一个 PostgreSQL 数据库的逻辑内容，适合迁移与常见恢复场景。它不是所有规模和时间目标的唯一方案，大型数据库还可能需要物理备份、连续归档和托管平台快照。PostgreSQL 官方备份文档区分不同方法，应根据版本、规模与恢复目标选择。

运行位置为能安全连接数据库的受控主机，前提是使用专用备份账号、目标目录有足够空间、密码通过受控机制提供。下面示例使用自定义格式，实际数据库名、主机和文件路径应替换，命令历史中不写密码。

```
pg_dump \
  --format=custom \
  --file=notes-20260806.dump \
  --dbname=notes
```

预期生成非空 dump 文件，命令退出码为零。随后计算校验值、加密并传到隔离存储，同时记录 PostgreSQL 客户端版本、数据库版本、开始结束时间、文件大小与备份对象。只有文件大小增加不能证明内容完整，脚本必须检查退出码并在失败时告警。

恢复测试在隔离环境进行，不能覆盖生产数据库。先创建空测试数据库，再使用与备份格式匹配的工具恢复。下面命令会写入目标数据库，运行前必须确认 `notes_restore_test` 是可丢弃的隔离目标。

```
createdb notes_restore_test
pg_restore \
  --dbname=notes_restore_test \
  notes-20260806.dump
```

预期恢复过程无未处理错误，应用使用测试配置连接后能读取关键表、登录测试账号并完成受控读写。还要检查行数、约束、扩展、权限、时区和用户上传引用。测试结束后删除隔离数据库属于破坏性操作，应再次确认准确名称并按团队流程执行，本书不提供可直接复制的删除命令。

恢复可能因角色不存在、扩展缺失或版本差异出现警告。不要看到几张表就宣告成功，应记录每条警告是否影响功能。恢复演练还要测量实际耗时，与 RTO 比较；若恢复用八小时而目标是四小时，就需要优化流程、并行传输或调整承诺。

## 时间点恢复解决持续写入后的故障

周期性 dump 只能恢复到最近导出时刻。若数据库持续写入且 RPO 更短，PostgreSQL 可以结合基础备份与预写日志归档设计时间点恢复。它能把数据库恢复到某个时间或事务附近，配置、存储与演练也更复杂，必须按当前 PostgreSQL 版本的官方备份文档实施。

时间点恢复仍要在隔离目标验证。维护者先确定误操作发生时间和时区，选择之前的恢复点，再检查恢复后的订单、文件引用与外部副作用。邮件已经发送、第三方支付已经完成或对象已经删除时，数据库回到过去不会自动撤销外部世界，需要单独对账与补偿。

备份策略应说明采用逻辑导出、托管快照、连续归档还是组合，以及每种方法覆盖哪些故障。快照创建成功后也要测试能否在另一个实例挂载或恢复，连续归档要监控日志缺口。工具越复杂，文档、权限和演练要求越高，不能只因为名称听起来“实时”就采用。

把备份文件导入工具，只能证明格式在当时可读。完整恢复还要回答应用能否连接、用户能否登录、关键记录是否存在、上传文件是否与数据库引用对应，以及权限和时间信息是否正确。若恢复出来的数据只能由管理员在数据库控制台看见，普通用户仍无法完成任务，这次测试还没有到达业务层。

恢复演练应使用隔离位置和明确时间点，防止覆盖生产。先记录备份标识、校验和、软件版本和恢复目标，再按手册执行。恢复后抽查数量、边界时间、代表性记录和关联文件，最后从应用入口完成关键路径。发现手册缺少账号、密钥、插件或版本条件时，当场补齐并重新演练。

同一份备份至少需要一次由非编写者完成的演练。作者常会凭记忆跳过文档缺口，换一个执行者才能发现“进入哪个目录”“从哪里取得解密密钥”“怎样判断导入结束”等信息没有写清。备份的价值由可恢复的结果决定，文件存在、任务绿灯和云端显示占用空间都只是中间证据。

## 恢复手册要在生产不可用时仍能取得

恢复说明若只放在已经故障的服务器或私有仓库，而应急人员又需要该服务器登录才能读取，就形成循环依赖。保留一份加密、受控且离线可取的应急手册，写账号入口、资源定位、备份位置、解密责任、恢复顺序和验证。手册不包含无需出现的秘密明文。

每次平台、域名、数据库版本和负责人变化后更新手册。季度演练由另一位人员按文档执行，记录哪些步骤依赖作者记忆。演练结束修正文档并撤销临时权限，使“能恢复”属于团队能力，而不是某个人刚好记得命令。

SQLite 数据库常是单个文件，但事务期间还可能涉及 journal 或 WAL。直接复制正在使用的主文件可能得到不一致快照。SQLite 官方 Online Backup API 能在数据库保持可访问时制作一致备份，具体库和工具可能封装这一能力。

备份前记录应用版本、SQLite 版本、journal mode 与文件位置，使用官方或框架支持的备份接口输出到另一个路径。完成后在独立副本上执行完整性检查并启动测试应用。不要用恢复测试直接打开唯一生产文件，也不要把同步盘中的冲突副本当作最新备份。

移动 App 还要区分服务器数据与设备本地数据。用户未同步的草稿可能只在设备上，服务器备份无法恢复；iCloud、Google 备份或应用导出也各有范围。产品应明确哪些数据会同步、哪些依赖设备备份、用户怎样导出，以及卸载会造成什么后果。

## 用户上传要与数据库引用一起恢复

数据库可能只保存对象键，真实图片与附件位于对象存储。只备份数据库会留下无法访问的引用，只复制对象又不知道属于哪个用户和版本。备份计划要覆盖二者，并记录一致性策略，例如在同一恢复点保留数据库快照与对象版本，或通过清单校验引用。

恢复测试随机抽取不同类型与时期的文件，验证权限、内容类型、大小和校验值。缩略图等可生成资源可以重建，但源文件必须可恢复。删除策略也要同步处理原对象、派生资源、缓存和备份到期，不能承诺用户立即删除却在无限期备份中永久保存。

上传文件可能包含个人与敏感内容，备份访问应比普通应用读取更严格。恢复人员只在演练窗口获得权限，操作留审计，测试环境使用脱敏样本或受控数据。OWASP 的授权、上传和秘密指南适用于备份通道，不应把备份当作安全规则之外的特殊区域。

一项可靠备份至少产生开始时间、结束时间、对象、字节数、退出状态、校验值、上传位置和保留结果。监控要发现未运行、运行失败、异常变小、异常变大、超时、目标空间不足和恢复测试过期。只在失败时发邮件仍可能因邮件本身失效而沉默，因此还要监控“最后一次成功距今多久”。

告警应指向动作。例如“生产 PostgreSQL 最后成功备份已超过两小时，目标为一小时，请检查任务 `[JOB_ID]` 与存储权限”，比“backup error”更可执行。通知中不附数据库密码、完整文件名或用户数据。修复后补跑备份并验证，不能只关闭告警。

restic 等备份工具提供加密、快照、校验与恢复能力，具体仓库、密码和保留命令必须按官方文档配置。工具能自动化重复动作，仍要保护仓库凭据、测试恢复和监控退出码。备份密码丢失可能让所有快照无法读取，应使用受控恢复机制，不能只存在某台服务器的环境变量里。

## 监控要覆盖用户看得见的结果

主机 CPU、内存和磁盘属于资源指标，HTTP 错误率、延迟与流量属于服务指标，登录、保存、上传与同步属于用户路径。只看主机在线，无法发现所有请求都返回错误；只看首页 200，也无法发现数据库写入失败。Google SRE 的监控资料强调围绕延迟、流量、错误和饱和度等信号建立可行动观察。

一个小项目可以从少量高价值检查开始。公网健康检查确认 DNS、TLS 和入口，应用健康检查确认进程与关键依赖，合成测试使用专用账号完成无破坏的登录与读取，指标观察错误率、P95 延迟、磁盘和备份年龄。每个告警写负责人、严重度、操作说明和静默条件。

阈值要来自基线与影响。磁盘 80% 可能在增长缓慢的静态站点仍有时间，在日志每小时增加 10% 的服务器则很紧急。告警同时考虑绝对值与增长率，避免一到夜间低流量就误报。监控系统自身也要有外部检查，否则服务器与监控一起断电时可能无人知道。

日志解释具体事件，指标展示随时间变化，追踪连接分布式调用，状态页面向用户沟通已知影响。小项目不必一次引入所有平台，但要确保核心故障有证据、告警能到达负责人、用户能知道重要中断。Prometheus 入门资料展示指标采集与查询，实际部署仍需考虑存储、权限和告警通道。

状态页不要暴露内部地址、攻击细节和用户信息。更新包含影响范围、已采取措施、下一次更新时间和恢复状态，根因未确认时直接写“调查中”。事故结束后发布简洁复盘与预防行动，内部保留更详细证据。Google SRE 的事故与复盘资料强调角色、时间线和可执行跟进。

日志保留要设置总量与期限。systemd、Docker、代理和数据库各自会增长，任何一层无限保留都可能占满磁盘。事故日志可转存到受控位置，普通调试日志按政策到期删除。

## 费用监控从资源清单开始

费用不仅来自主服务器，还可能来自对象存储容量与请求、数据库、出站流量、日志、备份、域名、证书服务、CI 分钟、邮件、推送和商店账号。免费额度与价格会变化，所有数字应使用官方资料并注明检索日期。本书不把任何免费方案写成永久承诺。

建立资源清单，记录供应商、项目、区域、计费单位、负责人、付款方式、预算、续费时间和删除条件。设置平台预算告警只是提醒，通常不会自动阻止消费。异常费用出现时先找增长资源和时间，再判断流量、循环任务、日志爆炸、攻击或遗留测试环境，不能直接删除未知卷与数据库。

域名到期会让网站和邮件失效，自动续费依赖付款方式与账号可用。MDN 对域名的说明帮助理解注册与 DNS 的位置。维护者应记录注册商、到期日、自动续费状态、恢复邮箱和多因素认证，避免域名绑定到离职人员或无人访问的邮箱。

下线前列出用户、数据、域名、API、客户端、商店应用、服务器、数据库、对象存储、CI、监控、备份、密钥和账单。确定停止新注册、停止写入、只读期、最终导出、用户通知和正式关闭日期。涉及合同、隐私与法规时，由有资格人员确认保存与删除责任。

给用户合理导出期，并用可读格式说明内容、校验与导入限制。最终备份完成后进行恢复抽查，记录快照与保留到期。若承诺删除，应覆盖生产、缓存、搜索索引、派生图片和备份生命周期。无法立即从不可变备份删除时，要在政策中真实说明隔离与到期时间。

移动 App 下线还要考虑已安装客户端。后端突然消失会让用户无法导出，旧客户端也可能不断重试。可以先发布包含下线说明、导出与只读模式的最终版本，再按商店规则停止新下载。商店账号和应用记录是否保留取决于更新、法律与品牌需要，不能只删除本地工程。

## 按依赖顺序关闭入口与资源

先阻止新写入并完成最终数据核对，再停止应用流量。随后删除或收窄 DNS、代理和 API 入口，撤销 CI、云平台、数据库、邮件、对象存储与第三方令牌，移除 SSH 公钥和成员权限。秘密撤销要记录结果，不能只删除 `.env` 文件。

确认不再需要回滚后，再按供应商流程删除计算实例、数据库、卷、快照、对象、日志与测试环境。每个删除目标先核对准确账号、项目、区域、名称和数据保留；关键数据有可恢复副本并完成验证。Docker `prune` 只处理特定未使用对象，不能代替云资源清单，也不应用作生产下线总开关。

域名可以保留用于跳转、品牌保护和最终通知，也可以在风险评估后到期。若不续费，确认邮件、登录回调和证书不再依赖它。DNS 缓存需要时间，删除记录后仍可能有残留访问；保留一个安全的终止响应比让旧域名指向被他人接管的资源更稳妥。

从外部网络确认域名与 API 按预期关闭或显示终止页面，从云平台确认计算、数据库、卷和对象状态，从账单页面确认不再产生新的可变费用，从身份系统确认成员、密钥和令牌已撤销。保留最终资源清单、导出校验、删除回执、账单截图的脱敏版本和仍需等待到期的项目。

下线后的一个或两个账单周期继续检查费用，防止快照、静态 IP、日志或域名遗留。监控与通知最后关闭，因为它们要覆盖下线过程。恢复材料按政策保留到期后，由授权人员删除并记录；如果项目可能重启，仍要明确哪些凭据必须重新生成，不能复用已经撤销的旧秘密。

高风险操作

> 删除数据库、对象存储、卷、快照、域名和商店应用可能不可恢复。执行前逐项核对账号、区域、资源 ID、最终备份、恢复测试和批准。不要用模糊名称或通配符批量删除。

## 一个“有备份却恢复不了”的例子

假设笔记服务每天生成 PostgreSQL dump，并显示任务成功。服务器故障后，团队才发现备份都保存在同一磁盘，最近一份上传到外部存储的文件为零字节，告警只检查任务是否启动。所谓“每天备份”没有提供独立副本，也没有验证文件和恢复。

改进后，任务检查 `pg_dump` 退出码与文件大小，计算校验并上传隔离存储，监控最后成功时间。每月在隔离数据库恢复，执行行数、登录、读取、写入和对象引用测试，记录耗时。季度再模拟主服务器不可用，由另一位维护者只用文档和应急凭据完成恢复。

这个案例表明，备份成功是可验证的恢复能力。文件、任务和绿色图标都只是中间证据。只有在独立环境中按目标时间恢复出可用业务，才能证明计划与人员准备有效。

## AI 可以生成清单，删除和恢复必须人工确认

AI 可以根据资源清单生成备份矩阵、恢复演练步骤、监控项、费用分类和下线顺序，也能检查日志是否缺少退出码与时间。输入使用占位符和资源类别，不提供真实凭据与用户数据。让 AI 对每个动作标明读取、写入、停止服务或永久删除。

AI 不能根据一个相似名称决定删除哪个数据库，也不能替用户确认保留期限、商店状态和法律责任。恢复测试由人核对目标环境与数据隔离，下线删除由账号持有人确认资源 ID，账单与域名在外部平台亲自复查。

- 已定义各类数据的 RPO 与 RTO
- 备份覆盖数据库、用户上传、配置和恢复材料
- 至少一个副本与生产故障和权限隔离
- 备份作业检查退出码、大小、校验和最后成功时间
- PostgreSQL 或 SQLite 恢复在隔离环境真实执行
- 恢复验证包含核心读写、权限与对象引用
- 监控覆盖入口、应用、数据、资源和备份
- 告警写影响、负责人、操作说明和下一步
- 费用清单包含资源、续费、预算与删除条件
- 下线给用户导出与通知窗口
- 密钥、成员、DNS、商店、资源和账单逐项关闭
- 删除后继续检查外部访问和后续账单

备份解决可恢复性，监控缩短未知故障时间，费用清单防止资源失控，下线流程结束长期责任。它们共同要求同一种纪律，用真实恢复、外部检查和平台回执证明结果，而不是把“已经设置”写成“已经可靠”。
