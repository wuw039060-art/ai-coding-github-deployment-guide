# 备份、恢复测试、监控、费用和安全下线

项目能上线，只说明它现在能工作。能不能承受误删、数据库坏掉、费用暴涨、服务商故障和安全下线，要看另一套维护能力。很多团队直到出事才发现，备份从没恢复过，监控只看 CPU，云账单没人管，旧服务器还在扣费。

## 先确定能承受丢多少和停多久

备份策略从两个问题开始。最多能丢多少数据，最长能停多久。前者常叫 RPO，后者常叫 RTO。个人作品集可能丢一天内容也能接受。付费订单系统丢一分钟都可能严重。目标不同，备份频率、恢复方案和成本就不同。

不要只说“每天备份”。要写备份对象、频率、保存位置、保留时间、加密、访问人和恢复步骤。数据库、对象存储、配置、环境变量、上传文件、商店资料、域名 DNS 和代码仓库都可能需要备份或导出。

备份也有权限风险。备份文件通常包含全部数据，不能放在公开桶、个人网盘或无密码压缩包里。测试恢复时使用脱敏数据或受控环境。

## 备份必须恢复过

没有恢复测试的备份，只能算一种愿望。PostgreSQL 逻辑备份可以导出结构和数据，适合迁移和小型项目。物理备份或托管平台时间点恢复适合更大系统。选择哪一种，要看数据量、恢复速度、停机窗口和平台能力。

恢复测试不应在生产库上随手做。准备隔离环境，使用最近备份恢复，运行基本查询，验证用户、订单、文件引用和权限。记录开始时间、结束时间、遇到的问题和实际耗时。恢复成功后清理测试环境，避免副本长期暴露。

时间点恢复能处理持续写入后的故障，例如下午两点误删数据，希望恢复到一点五十九分。它依赖日志和备份连续性。真正需要时，还要决定事故后产生的新写入怎样处理。不能简单把全库倒回去，覆盖用户在事故期间的真实操作。

恢复手册要在生产不可用时仍能取得。若手册只放在故障系统自己的数据库里，事故时没人能打开。至少保存一份离线或跨平台副本，并限制访问。手册里写清账号入口、备份位置、恢复命令、验证步骤、联系人和停止条件。

恢复测试也要验证权限。能下载备份的人，是否有权解密。能解密的人，是否能创建临时数据库。恢复后谁能访问副本，副本何时删除。备份副本若长期留在测试环境，可能变成第二个生产数据泄露点。

## 用户上传要和数据库一起恢复

很多应用把文件放对象存储，数据库只保存引用。只恢复数据库，文件可能不存在。只恢复文件，数据库可能不知道它。头像、照片、报告、发票和音频都要检查引用关系。

对象存储也要有版本、生命周期和删除保护。用户删除文件后，是否立即永久删除，还是进入延迟清理，要与隐私政策一致。恢复时要避免把用户已删除的数据重新公开。

备份清单要包含外部服务。邮件队列、支付订单、推送记录、搜索索引、分析数据和 AI 任务不一定能随数据库恢复。对于不可逆外部事件，要记录补偿办法，而不是假装回滚能解决所有事。

## 监控看用户结果

监控不要只看 CPU、内存和磁盘。用户关心的是能否打开页面、登录、保存、付款、同步、收到邮件或上传文件。基础资源监控必要，但它不能证明业务路径正常。

至少建立三类信号。可用性，服务是否能访问。正确性，关键操作是否成功。容量，资源是否接近限制。Web 项目可以定时请求关键页面和 API。App 项目看启动崩溃、登录成功率、同步失败率和后端错误。商店发布后还要看新 build 的稳定性。

告警要有人接。凌晨三点发到没人看的邮箱，等于没有告警。每个告警写清影响、判断办法、第一步动作和升级对象。告警太多会让人麻木，定期删掉无意义项。

监控还要有基线。今天的 500 错误数是 20，听起来不高，但如果平时只有 1，就值得看。登录成功率从 99% 降到 93%，比 CPU 从 40% 到 60% 更接近用户感受。发布前记录稳定版本的基线，发布后按同一口径比较。

合成监控可以定时访问关键路径，例如首页、登录、保存测试记录和上传小文件。它能早于用户发现问题。合成账号只使用测试数据和最小权限，产生的数据要定期清理。不要让监控本身制造订单、付款和邮件骚扰。

## 费用监控从资源清单开始

云费用失控常来自忘记关的测试服务器、日志暴涨、对象存储外发、数据库规格过高、AI API 调用和备份保留太久。先列资源，再设预算和告警。资源清单包括云账号、项目、服务器、数据库、存储桶、CDN、队列、域名、监控、第三方 API 和商店账号费用。

账单要有负责人。个人项目也要知道每月固定成本和可能暴涨的项目。AI 功能尤其要有限额、超时、重试控制和按用户或任务的费用记录。不要让一个错误循环不断调用付费 API。

费用优化不能破坏恢复能力。删除备份、关监控、缩小数据库前，先确认影响。省下一点钱，换来无法恢复，通常不划算。

费用异常也可能是安全信号。对象存储外发突然变高，可能是公开文件被爬取。AI API 调用暴涨，可能是循环重试或密钥泄露。数据库读写量异常，可能是坏查询或恶意访问。账单告警同时服务财务、稳定性和安全。

给每个高费用资源写停止办法。队列可以暂停到什么程度，API key 怎样限额，哪些任务可以降频，哪些存储桶不能删除。事故时先限流和止血，再做长期优化。

费用预算也要分环境。测试环境不应无限调用付费 AI、短信、地图和邮件。预发布压测要设置上限和结束时间。生产环境要有每日和每月告警。免费额度用完后的价格、限速和停服方式，要在上线前知道。

如果费用突然归零，也值得看。监控、备份或支付服务可能已经停了。账单正常不是越低越好，关键是符合预期。

## 按依赖顺序下线

项目不用了，也要安全下线。先通知用户和团队，提供数据导出，停止新写入，备份必要资料，再关闭入口。随后按依赖顺序处理前端、后端、数据库、对象存储、队列、域名、证书、CI、监控、商店应用和第三方 API。

不要先删数据库，再发现用户还要导出。不要先关域名，再发现 OAuth 回调、邮件链接和小程序合法域名还依赖它。不要留下旧服务器、旧密钥和公开存储桶长期无人管。

下线后撤销密钥、删除测试账号、关闭预算项和归档文档。保留必要的审计、账务和法律材料。不同业务有不同保留要求，高风险项目按专业意见执行。

下线也要处理搜索引擎、移动商店和小程序入口。网站关闭后，旧搜索结果和分享链接仍会带来访问。App 下架后，已安装用户可能还在使用旧后端。小程序暂停服务后，用户可能从聊天记录再次打开。给用户一个说明页和数据出口，比直接断开更稳。

域名和证书不要随意丢弃。域名过期后可能被别人注册，旧邮件、OAuth 回调和用户书签都会指向新持有人。高风险域名至少保留一段时间，或确保所有入口已经迁移。

## 一个有备份却恢复不了的假设情境

设想一个团队每天导出数据库，事故时才发现备份文件保存在同一台服务器。磁盘损坏后，生产库和备份一起没了。另一组备份虽在对象存储，但没人知道解密密码。最后只能从用户上传记录和日志里手工补数据。

问题出在恢复路径从未验证。改进也很具体。备份离开生产机器，保存加密密钥，定期恢复到隔离环境，记录实际耗时，确认对象存储和数据库引用一致。

AI 可以生成备份清单、恢复演练脚本和监控项。真正删除资源、恢复生产数据、切换数据库和下线服务，必须由授权人员确认。维护工作的底线，是灾难发生时还有路可走。

## 恢复后的验证

恢复完成后，不要只看数据库能连接。用真实用户路径验证。登录、查看列表、新增记录、上传文件、下载旧附件、发送邮件或推送、支付沙箱回调，都要按业务选择。若恢复的是 App 后端，还要用旧客户端和新客户端各走一次。

恢复后还要检查权限和外部副作用。测试环境恢复出的用户不能收到真实邮件，支付沙箱不能触发正式扣款，推送也不能发给真实设备。隔离环境应使用替代密钥和阻断外部发送。恢复测试的目的，是确认数据能回来，不是制造第二场事故。

最后记录实际耗时和卡点。RTO 写两小时，演练花了六小时，就按六小时改计划或补工具。纸面目标不能替代真实演练。

## 恢复优先级

事故中不一定所有功能同时恢复。先恢复用户查看重要数据，再恢复新写入。先恢复登录和支付状态查询，再恢复营销活动。先恢复导出和客服入口，再恢复不影响核心流程的报表。优先级应在平时写好，事故时再讨论会浪费时间。

只读模式是一种有用的中间状态。数据库写入不安全时，可以暂时允许用户查看已有数据，暂停下单、删除和上传。只读模式要在产品上有清楚提示，后端也要真的拒绝写操作，不能只把按钮变灰。

恢复顺序还要考虑外部依赖。支付、邮件、短信、对象存储和 AI API 若不可用，核心系统可以先降级。降级方案要提前设计。否则第三方服务一次故障，就会把整个应用拖下水。
