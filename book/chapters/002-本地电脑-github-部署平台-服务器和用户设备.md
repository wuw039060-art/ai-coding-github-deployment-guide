# 本地电脑、GitHub、部署平台、服务器和用户设备

同一个项目会同时存在于几个位置：电脑里是正在修改的文件，GitHub 上是已经推送的版本，部署平台保存构建与发布记录，服务器运行程序，用户设备又保留浏览器缓存、登录状态或 App 数据。它们来自同一条工作链，却不会自动保持完全相同。

所以，“我明明改了，线上为什么没变”首先不是代码问题，而是位置问题。改动可能停在保存、提交、推送、构建、生产切换或用户缓存中的任何一道边界。先问它走到哪里，再决定看什么证据。

## 五个位置各自保存什么

**本地电脑**是编辑和第一次验证的起点。保存文件只写入本机磁盘；Git Commit 把选择的变化记为本地历史；Push 才把提交发往远程。开发服务器、模拟器和本地数据库往往比生产环境宽松，因此“本地能运行”是必要证据，不是上线证明。

本地还可能有多个同名副本。下载 ZIP 得到一个快照，Clone 得到带远程关系的 Git 仓库，复制目录又产生另一个独立位置。命令在 `site-copy` 运行、编辑器却打开 `site` 时，你会在正确文件中修改、在错误副本中看结果。运行前确认项目绝对路径和当前分支，比反复重启有效。

**GitHub**保存远程提交和协作记录。部署平台通常只监听特定仓库、分支，有时还限定子目录。它看不见电脑里未推送的变化。Issue、Pull Request、Actions 和 Release 也不是生产系统：自动测试通过不等于部署成功，Release 存在不等于服务器已切换。

仓库可见性与网站可见性同样不同。公开仓库让人读代码；网站是否公开由托管、域名和应用权限决定。私有仓库可以部署公开网站，公开仓库也可能从未部署。Git 与 GitHub 的具体命令、Desktop 操作、权限和秘密事故处理统一见[《Git 与 GitHub 操作参考》](../../references/git-github.md)。

**部署平台**取得远程提交，选择运行环境，安装依赖，执行构建，再把产物交给静态托管或运行服务。平台能按配置做事，却不知道错误命令原本想表达什么；它能注入已经保存的变量，不能恢复从未配置的秘密；构建成功也不能保证数据库与第三方服务可用。

一次部署至少记录仓库与分支、提交编号、构建时间、部署 ID，以及生产域名当前指向哪个部署。控制台地址用于管理，平台默认域名和自定义域名用于访问。默认域名正常而自定义域名失败，应先查 DNS、绑定和证书；两个地址都失败，再查构建与运行状态。Web 发布与浏览器验证清单见[《Web 部署与浏览器排错参考》](../../references/web-deployment.md)。

**服务器**既可以指网络角色，也可以指 VPS 等远程计算机。只要程序持续响应客户端，它就在承担服务端角色。托管平台也使用服务器，只是隐藏了许多系统管理。程序真正部署到远程环境后，关闭个人电脑通常不影响它；只在本地终端启动的后端则会随电脑休眠或进程退出而消失。

服务器内部仍有多层：应用进程、反向代理、容器、数据库和持久数据可能位于不同目录或服务。GitHub 上的 Dockerfile 只是构建说明，只有镜像被构建并运行成容器，应用才存在于运行环境。服务器与容器的操作分别见[《Linux 与服务器运行手册》](../../references/linux-server.md)和[《Docker 与 Compose 操作参考》](../../references/docker.md)。

**用户设备**保存最后一段状态。浏览器会分别请求页面、脚本、图片与接口，还可能保存 HTTP 缓存、Cookie、本地存储和 Service Worker。首页返回成功不代表所有资源和 API 成功。若只有一台设备显示旧页面，用无痕窗口或另一设备做对照，通常比重新部署更有信息量。

已安装的 App 也不会因 GitHub 代码变化自动更新。维护者要生成新构建、测试和分发，用户再取得新版本。删除 App 可能清掉本地数据，却不必然删除后端账号；服务器恢复备份也不会恢复从未同步的本地草稿。微信小程序又有开发、体验、审核和线上版本。产品名称不同，判断仍回到代码与数据实际位于哪里。

## 一次修改怎样走到用户

假设把首页按钮从“开始”改为“立即开始”，完整路径是：

1. 在正确本地项目中修改并保存。
2. 用本地预览验证文字与布局。
3. 检查 Diff，排除意外文件和秘密。
4. Commit，得到本地提交编号。
5. Push 到平台监听的远程分支。
6. 平台为该提交完成构建。
7. 生产入口切换到新部署。
8. 从公开地址和独立浏览器状态验证。

每一步都产生不同证据：文件内容、Diff、提交 SHA、远程分支、构建日志、部署 ID、页面响应。某一步的绿色图标不能替后续步骤作证。

线上仍显示旧文字时，先比较生产部署的提交与 GitHub 目标提交。不同，问题在触发、分支或生产切换；相同，再比较构建产物、响应内容和缓存来源。生产部署尚未包含提交时，清浏览器缓存没有意义；无痕窗口已经正常时，重复构建也没有意义。

## 相同现象，可能是三种问题

阿青电脑里同时有 `site` 和 `site-copy`。编辑器改前者，终端在后者启动开发服务。检查绝对路径后，她停止旧进程，在正确目录启动。这里不需要改部署配置。

小周把首页变化提交到 `feature-home`，部署平台却监听 `main`。GitHub 能看到新提交，生产部署仍指向 `main` 的旧提交。正确处理是按团队流程合并，或确认用途后调整监听分支，不是把未完成代码直接塞进生产。

另一项目的生产提交和响应都正确，同事的无痕窗口能看到新图标，只有维护者常用浏览器仍旧。Network 显示图片来自内存缓存，此时才有理由检查缓存规则。

三种问题都表现为“没有更新”，解决方法却分别是纠正运行目录、纠正版本流向和纠正客户端状态。对照证据比猜测根因可靠。

## 版本差异有时是设计

预览环境运行新提交、生产环境继续服务稳定提交，是正常发布安排。移动端差异更长：开发设备可能是今天的 build，内部测试是上周版本，商店用户仍在更早版本。后端不能假设客户端会同时更新，API 和数据格式要保留兼容窗口。

数据库也有版本。新代码读取新字段前要安排迁移；先删除旧字段会破坏尚未更新的客户端。代码部署、数据库迁移和客户端发布应分别记录顺序、停止条件与回退边界。版本差异是否合理，取决于它是否可识别：预览部署有提交 SHA，App 显示 version/build，数据库保存迁移版本。

环境也会分叉。同一个人可能登录个人与组织 GitHub、两个部署团队和多个云项目。变量写在预览环境，生产不会自动获得；平台只授权个人仓库，也找不到组织仓库。排错时记录账户或团队、项目、环境和分支，不记录密码或令牌。

> **必须由人确认**
>
> AI 可以比较你提供的配置和页面文字，却不知道另一个浏览器标签是否登录了不同账户。涉及生产发布、删除、付费和权限授予时，亲自读出账户、项目、环境与目标版本，再确认动作。

## 文件与秘密不要一路复制

不是本地所有文件都应进入 GitHub，也不是仓库所有内容都应进入浏览器或容器。依赖缓存、构建缓存、本地数据库、日志和真实测试数据通常只留在受控位置。`.env` 可能含秘密，不能靠“仓库是私有的”获得安全保证。

前端产物最终会下载到用户设备。写进 JavaScript、App 包或小程序包的值可能被提取；把它放在部署控制台变量里，也不能改变产物公开这一事实。数据库管理员口令、服务端 API 密钥和签名私钥应由后端或秘密系统持有，客户端通过受控接口取得结果。

生产数据同样不应为了排错随意复制到个人电脑或 AI 会话。先缩小时间和字段，使用脱敏样本或专用测试数据。每个位置只保留完成任务所需的内容和权限，是比“所有地方都同步一份”更可靠的原则。

## 用位置表形成故障树

为自己的项目写一张表；不存在写“无”，不知道写“待确认”。

| 位置 | 记录 | 证据 |
|---|---|---|
| 本地 | 绝对路径、当前分支 | 文件、Git 状态、本地预览 |
| GitHub | 所有者、仓库、目标分支 | 提交 SHA、文件差异 |
| 部署平台 | 项目、环境、生产部署 | 构建日志、部署 ID、制品 |
| 服务器 | 服务、数据位置、运行方式 | 状态、日志、备份与版本 |
| 用户设备 | 浏览器或 App 版本 | 实际响应、Network、设备状态 |

这不是密码表。未知项也不要猜：数据库由谁托管、域名属于哪个账户、生产用哪个分支，都可以成为待确认问题，并写明要由配置、控制台还是账号持有人回答。

常见对照可以快速定位边界：

| 对照 | 先查 |
|---|---|
| 本地正常，远程构建失败 | 依赖、构建命令、环境变量 |
| 默认域名正常，自定义域名失败 | DNS、域名绑定、证书 |
| 预览正常，生产仍旧 | 生产部署与提交 SHA |
| 无痕正常，常用窗口陈旧 | 缓存、Service Worker、扩展 |
| 页面正常，登录接口 500 | API 日志、数据库与依赖 |
| 只有一个用户失败 | 账号权限、输入、设备版本 |
| 所有用户同时失败 | 公共入口、服务、共同依赖 |

对照要控制变量：换设备时访问同一 URL，比较部署时确认环境与数据库相同。一次同时更换域名、平台和代码，只会让结果难以解释。

## 把判断写成六行

一次真实故障中，本地 Windows 预览正常，GitHub 与生产部署 SHA 一致，无痕窗口里的图片仍返回 404。构建产物显示代码引用 `Logo.png`，实际文件是 `logo.png`；Linux 环境区分大小写，本地环境没有暴露问题。

可复用记录只需写清：现象、影响范围、正常对照、异常开始的边界、由证据支持的原因、修复与验证。再附日期、环境、提交和验证人。它保留判断过程，却不会把未来所有 404 都武断归为大小写问题。

用户点击登录时，浏览器 Network、反向代理、后端和数据库可能分别留下证据。请求 ID 和准确时间及时区能把它们串起来。日志可能含邮箱、IP、参数和内部错误，分享前删除秘密与不必要的个人信息；不要向用户索要密码或完整令牌。

## 本章掌握边界

出错先从改动最近的位置向用户移动：保存、Commit、Push、目标分支、构建、生产切换、用户缓存。每层只在证据支持时进入下一层。

AI 适合只读扫描本地结构、识别构建配置、整理提交与日志，或把五个位置画成候选地图。它无法只凭本地文件确认生产控制台账户、DNS 实时状态和真实用户版本。执行推送、生产切换、服务重启、数据库恢复或 App 发布前，目标位置与影响仍由人确认。
