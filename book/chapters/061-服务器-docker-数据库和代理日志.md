# 服务器、Docker、数据库和代理日志

一个网页请求进入自建服务器后，往往先经过 Caddy 或 NGINX，再到 systemd 管理的程序或 Docker 容器，最后访问 PostgreSQL。每层都可能写日志，却不会自动把同一次请求排成一行。真正有效的排错工作，是先画出请求经过的组件，再用时间、请求路径、状态码和关联编号把散落证据接起来。

日志也不是数据库的完整复制。它只记录程序开发者与运维配置允许记录的事件，空白可能表示请求没有到达，也可能表示日志级别、权限、输出位置或采集链路有问题。因此本章先讲每层能回答什么，再讲怎样串联，最后处理日志保留、隐私和磁盘风险。

## 先知道四层日志各自能证明什么

代理日志位于公网入口，通常最先记录方法、路径、状态码、响应大小、处理时间和客户端地址。它能证明请求是否到达服务器入口，以及代理最终向客户端返回了什么，却未必知道应用为什么失败。代理返回 502 时，常见含义是它无法从上游获得有效响应；这把范围缩到代理配置、上游地址、应用进程或主机资源，不能直接证明数据库损坏。

应用日志解释业务代码正在做什么，例如用户认证失败、参数验证不通过、外部 API 超时或数据库查询抛出异常。systemd Journal 还会记录服务启动、退出、重启和标准输出；Docker 日志则通常展示容器主进程写到标准输出与标准错误的内容。二者都能看到应用文字，但观察边界不同，一个围绕主机服务单元，另一个围绕容器。

数据库日志关注连接、认证、慢语句、锁、检查点、恢复和服务器错误。它可以说明数据库为什么拒绝连接或某次语句为何等待，却不能替应用判断业务权限。PostgreSQL 的 `pg_hba.conf` 控制客户端连接匹配与认证方式，应用收到“没有匹配规则”时应检查具体来源地址、数据库和用户，不能为了快速恢复把所有来源都放开。

主机与监控数据提供共同环境。磁盘已满时，代理、应用和数据库可能同时异常；内存压力可能让内核终止进程；时间漂移会使证书验证和日志对齐变得困难。监控指标适合回答“何时开始”“影响多大”“是否恢复”，日志适合回答“发生了哪类事件”，两者结合比只翻文字更可靠。

## 从用户请求建立一条时间线

先固定一个不会破坏数据的测试请求，例如打开公开健康页或读取测试记录。记录本地时间与时区、完整 URL、预期状态码、实际状态码和响应中的请求编号，然后在代理日志中找到同一条记录。若代理完全没有记录，应先回到 DNS、网络、TLS、负载均衡或日志配置，不要越过入口直接查数据库。

代理记录请求后，继续找应用是否收到它。最可靠的方式是由入口生成或保留一个请求编号，并把它传给应用；应用随后把同一编号写入数据库调用和错误日志。没有编号时，可以暂时用时间、方法、路径、用户的匿名内部编号和耗时组合，但并发高时容易把两个人的请求混在一起。关联编号应是随机且不含个人信息的标识，不能把访问令牌或邮箱当编号。

数据库通常不会自动知道 HTTP 请求编号。应用可以在安全的结构化日志中记录查询类别、耗时和请求编号，必要时使用数据库提供的会话标识或应用名协助定位。不要把完整 SQL 参数、密码、令牌和用户正文全部写进日志。OWASP 建议记录足以支持安全分析的事件，同时对敏感数据、日志完整性、访问控制与保留期限作出限制。

运行位置为已通过 SSH 登录的 Linux 服务器，前提是目标程序由 systemd 管理，并且当前账号有读取相应 Journal 的权限。先查看服务当前状态，再查询本次启动以来的日志。下面的 `notes.service` 只是示例，应替换为真实 unit 名称。

```
systemctl status notes.service
journalctl -u notes.service -b
```

第一行查看是否处于 `active`、最近退出码和末尾日志，第二行按服务单元筛选当前这次系统启动后的记录。预期结果是看到明确时间、主机、进程与消息；若提示找不到 unit，应先用 `systemctl list-units --type=service` 核对名称。若权限不足，使用具备日志读取权限的维护账号，是否需要 `sudo` 由服务器权限策略决定，不要为了方便长期使用 root 登录。

事故时间已知时，应限制区间，避免在几万行旧日志里搜索。持续观察只适合短时间复现，结束后按 `Ctrl+C` 停止，不会停止服务本身。

```
journalctl -u notes.service \
  --since "2026-08-06 14:00:00" \
  --until "2026-08-06 14:20:00"

journalctl -u notes.service -f
```

命令中的时间按服务器本地时区解释，跨时区协作前应先确认 `timedatectl` 输出。`-f` 表示跟随新日志，适合执行一次测试请求后立即观察。找不到预期记录时，先确认服务是否把输出交给 Journal、时间区间是否正确、日志是否已轮转，以及程序实际是不是运行在容器中。systemd 官方 `journalctl` 文档还支持按 boot、优先级与字段过滤。

## 用 docker logs 看容器主进程

运行位置仍是安装 Docker 的服务器，前提是已经知道容器名，并且账号有权访问 Docker daemon。访问 Docker 通常等同于获得很高的主机控制能力，不应随便把普通用户加入 Docker 组。先用只读命令确认容器，再限制时间和行数查看日志。

```
docker ps --all
docker logs \
  --since 20m \
  --tail 200 \
  notes-app
```

预期能看到容器主进程写到标准输出与标准错误的内容。容器处于 `Exited` 时，先记录退出码和末尾日志，再决定是否重启；反复执行 `docker restart` 会覆盖故障节奏，也可能让有问题的写入继续。若 `docker logs` 为空，应检查应用是否把日志写入容器内部文件、是否使用了不支持读取的 logging driver，以及容器名是否正确。Docker 官方文档说明日志可用性取决于 logging driver，`local`、`json-file` 与远端驱动的保留和读取方式并不相同。

Compose 项目可在含有 Compose 文件的项目目录执行下列命令，服务名使用 Compose 中的名称。`--no-log-prefix` 会减少前缀，不适合多服务混合排错，因此这里保留默认服务前缀。

```
docker compose ps
docker compose logs \
  --since 20m \
  --tail 200 \
  --follow app
```

预期先看到服务与容器状态，再看到带服务前缀的新日志。若 Compose 找不到配置，应确认当前目录和 `-f` 指定文件；若旧容器已被重新创建，当前容器日志不一定包含事故现场。重要事故要在重建或清理之前导出相关日志，并记录镜像摘要、配置版本和容器创建时间。

## 检查 Caddy 与 NGINX 入口日志

Caddy 的 `log` 指令用于配置 HTTP 访问日志，默认输出位置与格式取决于运行方式和配置。由 systemd 启动的 Caddy 常可通过 `journalctl -u caddy` 查看服务消息，但访问日志是否也在 Journal 中必须以 Caddyfile 为准。检查时关注请求时间、主机、方法、URI、状态、响应大小、持续时间和上游错误，不要把“服务正在运行”误当作“入口确实收到请求”。

NGINX 使用 `access_log` 记录请求，使用 `error_log` 记录运行错误，路径与日志格式由配置决定。维护者应先检查生效配置，而不是只猜 `/var/log/nginx/access.log`。在 Ubuntu 常见安装中可以先查看 `nginx -T` 的输出确认配置来源，该命令可能显示包含内部地址的完整配置，分享前要脱敏。

```
sudo nginx -T
sudo tail -n 200 /var/log/nginx/access.log
sudo tail -n 200 /var/log/nginx/error.log
```

运行位置为 NGINX 主机，前提是维护者有读取配置和日志的授权。`tail` 只读取文件末尾，不会修改日志；预期在访问日志找到测试请求，并在错误日志看到同一时间附近的上游、TLS 或文件错误。路径不存在时，应以 `nginx -T` 中的 `access_log` 与 `error_log` 为准。NGINX 官方模块文档说明日志格式和条件记录均可配置，因此不同服务器的字段可能完全不同。

## 检查 PostgreSQL 日志与连接边界

先从应用错误中提取数据库主机、数据库名、应用用户、错误类别和时间，真实密码不进入排错记录。连接被拒绝时要区分网络不可达、端口未监听、TLS 失败、认证失败、没有 `pg_hba.conf` 匹配项和用户无权访问数据库。把这些错误都写成“数据库连不上”，会把网络、身份与授权混为一谈。

PostgreSQL 的日志去向可能是标准错误、日志采集器、syslog 或其他配置目标，不能假设固定文件。具备数据库管理授权时，可以在 `psql` 中查看当前设置。以下命令只读，但结果可能暴露内部路径，分享前要删去不必要信息。

```
SHOW log_destination;
SHOW logging_collector;
SHOW log_directory;
SHOW log_filename;
```

预期得到当前实例配置。若使用 systemd 且标准错误进入 Journal，可结合服务 unit 查看；若 `logging_collector` 开启，则按 `log_directory` 和 `log_filename` 找文件。不要为了一次排错盲目开启所有语句日志，完整参数可能包含个人数据，额外写入也可能迅速占满磁盘。需要观察慢查询或锁时，应先选取最低必要范围，并在验证结束后恢复配置。

数据库出现锁等待时，要把应用请求时间、事务开始和数据库事件对齐。一次超时不代表数据库性能整体不足，也可能是某事务长时间持锁、连接池耗尽或外部调用占住事务。先在测试条件下复现并确认阻塞关系，再修改事务、索引或容量；直接重启数据库会中断所有连接，还可能抹去最有价值的现场。

## 日志级别、结构化字段与请求编号

常见级别包括 Debug、Info、Warning 和 Error，但每个项目的定义可能不同。生产环境不应把正常 404 全部记录为最高级错误，也不应把数据库不可连接藏在 Debug。级别应对应可行动影响，字段则保持稳定，例如时间、服务、环境、版本、事件名、请求编号、结果、耗时和错误类别。

结构化日志常用 JSON，优势是采集系统可以按字段筛选，代价是直接阅读不如短文本自然。无论格式如何，同一事件只记录一次关键事实，避免代理、应用和中间件各自输出十行重复文字。错误应保留稳定类别与调用位置，用户输入只记录必要的脱敏摘要。应用启动时记录版本和配置来源名称，不能打印配置秘密本身。

请求编号需要从入口传到应用，再随响应返回给客户端。发生错误时，用户可提供编号，维护者据此定位服务器记录。编号不能保证所有日志一定完整，但能显著减少按时间猜测。后台任务没有 HTTP 请求时，应生成任务编号，并记录它由哪个请求、定时任务或消息触发。

日志会持续增长，保留策略至少要回答单文件大小、轮转频率、总量上限、保留天数和异常增长告警。Docker 默认或自定义 logging driver、systemd Journal、代理与数据库各有自己的限制，不能只配置其中一层。磁盘达到危险水位时，数据库可能无法写入，容器也可能无法启动，日志系统本身就会成为故障来源。

不要在事故中直接运行 `docker system prune` 或删除 `/var/log`。Docker prune 会删除未使用对象，不等同于只清日志，若理解错误可能影响回滚所需镜像；删除数据库或代理日志则会破坏证据。更安全的顺序是先确认哪个目录增长、保存事故区间、按组件文档执行轮转或压缩，再验证磁盘与服务。数据库数据目录尤其不能当作普通日志目录清理。

高风险操作

> 不要用 `chmod 777` 解决日志权限，也不要把数据库端口向全网开放来“验证连接”。前者扩大读取与篡改范围，后者把内部服务暴露给互联网。应修正日志所有者、用户组或服务策略，并从受控主机测试数据库连接。

## 一个跨四层的保存失败案例

用户报告保存笔记时页面等待十秒后失败，并提供时间戳 `2026-08-06T15:12:00+08:00` 和响应请求编号。NGINX 访问日志显示 `POST /api/notes` 返回 504，耗时约十秒。应用日志中同一编号显示数据库操作超过超时，PostgreSQL 日志附近出现锁等待。四层证据把问题缩到写入事务，无需修改 DNS 或 TLS。

维护者用两个测试账号同时编辑同一条测试记录，复现了等待。进一步发现应用在事务中调用外部图片服务，网络变慢时数据库锁一直不释放。开发者把外部调用移到事务之后，并让任务按业务操作编号保持幂等。复测相同并发后，代理耗时恢复到基线，应用没有超时，数据库也不再出现相同锁等待。

验证不能止于“一次保存成功”。还要测试外部图片服务失败、重复提交、两个用户编辑不同记录，以及旧版本客户端。观察窗口覆盖原故障常见频率后，才能把状态从“已缓解”改为“已解决”。记录中应保留修复 Diff、部署版本、验证编号和回滚方式，用户正文与数据库凭据继续脱敏。

负载均衡后面可能有多个应用实例，Compose 也可能把同一服务扩展成多个容器。若只有一个实例配置错误，用户会偶尔成功、偶尔失败。每条应用日志应包含实例、版本、区域和请求编号，入口日志最好也能记录选择的上游。维护者按请求编号定位具体实例，再比较同版本其他实例，避免把正常机器的日志当作故障现场。

滚动发布期间，新旧版本会在一段时间内同时接收请求。数据库结构与 API 必须在兼容窗口内支持两者，日志则要按版本分别统计错误率。部署平台显示成功，只能证明编排流程结束，不能证明每个实例都处理过真实请求。用健康检查、核心合成请求、版本响应头和一段观察窗口确认切换。

实例被自动重启后，原容器日志可能仍在，也可能随平台回收而消失。发现崩溃循环时先记录容器 ID、创建时间、退出码、重启次数、镜像摘要和末尾日志，再暂停可能扩大数据损坏的自动重试。不要通过持续扩容掩盖每个新实例都会退出的配置错误。

## 应用写文件时要知道文件在哪里

`docker logs` 主要读取容器主进程的标准输出与标准错误。应用若只写 `/app/logs/app.log`，这些内容可能留在容器可写层，重建后丢失，也不会自动出现在集中日志。更适合容器的做法通常是把事件写到标准流，由 logging driver 或平台收集；确需日志文件时，应明确挂载、轮转、权限与备份责任。

systemd 服务也可能同时写 Journal 和独立文件。重复采集会让同一错误出现两遍，完全不采集则留下空白。资产表应写每个服务的权威日志来源、保留时间和查询方法。调整输出位置后制造一个安全测试事件，从服务本地、采集系统和告警三处验证，不能只看配置文件语法通过。

集中平台方便跨主机搜索和保留，但网络中断、采集代理故障、字段解析错误与配额都可能让日志缺失。应用与代理仍应保留短期本地缓冲，并监控采集延迟、丢弃量和最后成功时间。平台搜索不到事件时，回到源主机和请求路径验证，不能立刻断言应用没有执行。

集中查询的访问权限往往覆盖多个服务与用户数据，应按环境和职责分开。导出、共享链接和 AI 集成都要经过脱敏与审批。索引保留过长会增加费用与隐私风险，过短又影响事故调查，期限应依据日志类型和真实调查需要，而不是所有内容使用一个永久保留策略。

## 数据库日志需要和应用连接池一起看

应用报告数据库超时时，数据库日志可能没有慢查询，因为请求还在等待连接池空位。记录连接池活动数、等待数、获取连接耗时与数据库实际连接数，才能区分“查询很慢”和“根本没有取得连接”。连接池上限也要与数据库容量、应用实例数相乘后核对，单实例配置合理不代表扩容十台后仍合理。

认证失败同样要区分旧实例与新秘密。轮换数据库密码后若少数请求继续失败，可能是滚动发布中的旧容器仍使用旧值。按实例与版本统计失败，确认所有使用者完成轮换后再撤销过渡凭据。不要通过让数据库同时永久接受多个密码来掩盖配置分发问题。

数据库日志中的 SQL、参数和错误可能包含个人数据。优先记录查询指纹、耗时、行数与错误类别，只有在受控调查中才查看必要参数。临时开启详细语句日志要设到期、磁盘告警和访问限制，结束后确认配置恢复。

AI 适合把多层脱敏日志按时间和请求编号排序，提取重复错误，并生成待验证假设。输入前先删去 Cookie、令牌、数据库连接串、邮箱、正文和内部敏感地址，只提供与故障窗口相关的最小片段。要求 AI 标明每个结论来自哪一层日志，并把事实、推断与缺失证据分开。

AI 建议运行命令时，人必须确认运行位置、权限、影响和回退。`journalctl`、`docker logs` 与读取代理日志通常是只读检查，重启服务、改变日志级别、修改 `pg_hba.conf`、清理 Docker 对象和删除日志会改变系统状态。没有审批与备份时，AI 不应自动执行后面这些动作。

## 本章最终检查

- 已画出请求经过的代理、应用、容器和数据库
- 所有系统使用可对齐的时间与时区
- 入口能生成或保留安全的请求编号
- journalctl 与 Docker 查询限制了服务、时间和行数
- 代理访问日志和错误日志分开理解
- 数据库连接、认证、授权和查询错误没有混为一谈
- 日志没有记录密码、令牌或完整用户正文
- 每层都有轮转、总量限制与磁盘告警
- 清理、重启与提高日志级别都有授权和回退
- 修复使用原请求、相邻功能与观察窗口验证

日志的核心价值是重建事实顺序。入口记录请求到达，应用解释业务动作，数据库说明数据边界，主机与监控补充共同环境。只有把这些证据放回同一时间线，日志才会从大量文字变成可验证的故障判断。
