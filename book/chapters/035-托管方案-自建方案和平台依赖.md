# 托管方案、自建方案和平台依赖

托管服务让供应商运行基础设施，自建让项目团队直接运行服务器和软件。两者都不是免责任方案，只是责任分配不同。个人项目常从托管开始，因为上线快、维护入口清楚。自建适合需要特定运行环境、成本模型、网络控制或团队已有运维能力的情况。为了“完全掌控”购买 VPS，却没有备份、补丁和监控，实际控制力很弱。

## 先拆责任项

应用至少包含计算、数据库、文件存储、域名、TLS、身份、日志、备份、监控和费用。托管平台可能处理服务器硬件、操作系统、数据库进程和自动备份。你仍处理数据模型、权限、密钥、业务监控和恢复验证。

自建时还要负责系统更新、防火墙、进程、磁盘、证书、容量和安全事件。选择之前给每项写负责人。空白项不会因项目很小而消失。没人负责的备份、账单和域名，迟早会在事故里冒出来。

供应商安装数据库、管理高可用基础设施、提供监控和备份入口。团队能把时间放在数据模型与产品。可连接地址、账号和资源上限仍需配置。错误的公网暴露和宽权限不会被托管自动修正。备份功能也要查频率、保留和恢复方式。

## 自建增加什么

自建数据库或服务器意味着你要安装受支持版本、配置存储与内存、限制网络、创建受限用户、监控连接与查询、安排备份和升级。磁盘满会让写入失败，证书过期会断开连接，系统补丁需要维护窗口。单台服务器故障时，应用和数据库可能一起离线。

复制、高可用和时间点恢复是独立工程。个人项目若无法演练，使用成熟托管服务通常更稳妥。自建也提供更大配置自由和固定资源成本，前提是团队愿意承担持续值守。

自建的常见误区是只比较月费。托管数据库看起来更贵，自建 VPS 看起来便宜。把备份、监控、升级、故障处理、值班时间和恢复演练算进去，结果可能相反。对学习项目来说，自建很有价值。对真实业务来说，学习成本不能转嫁给用户数据。

## 平台依赖有层级

平台依赖不只来自数据库。代码托管、构建、域名、DNS、身份服务、支付、邮件、对象存储、AI API 和监控都可能形成依赖。依赖本身不是坏事。坏的是不知道依赖在哪里，也没有替代方案。

可以把依赖分成三层。第一层是可替换服务，例如邮件供应商。换起来需要改配置和模板。第二层是深度集成，例如 BaaS 的客户端 SDK、权限规则和实时监听。迁移会影响代码结构。第三层是数据和身份锁定，例如用户账号、文件对象和审计记录。迁移需要计划和验证。

退出计划的最低内容很简单。数据怎样导出，文件怎样复制，域名和 DNS 是否掌握在自己账号里，用户身份怎样延续，Webhook 和第三方回调怎样改，旧平台下线前保留多久。计划不要求明天迁移，只要求今天知道出口。

## 免费额度和服务等级怎样看

免费额度适合试验和早期验证。正式项目要看当前官方价格、超额处理、休眠规则、限制项、团队席位、日志保留、备份保留和支持方式。价格会变，本书不写永久数字。创建项目时记录查询日期、预计用量和告警入口。

服务等级也要读清。供应商承诺的是平台可用性，通常不包括你的代码错误、错误配置、账单失败、被删除资源和超额限流。支持渠道也分等级。社区问答、邮件工单、企业支持和紧急电话的响应速度不同。

告警要覆盖业务，不只覆盖平台状态。平台绿色，支付仍可能失败。数据库健康，邮件可能全部退信。首页正常，后台任务可能积压。托管减少基础设施工作，不会替你定义用户成功。

## 决策表

| 情况 | 倾向选择 |
| --- | --- |
| 公开内容站 | 静态托管 |
| 登录、数据库、文件上传的早期产品 | BaaS 或托管后端 |
| 需要标准关系数据库和可控 SQL | 托管 PostgreSQL |
| 特殊系统软件、长进程或私有网络 | VPS 或容器平台 |
| 团队没有运维能力但有真实用户数据 | 优先托管 |
| 学习 Linux 和部署原理 | 可用测试 VPS |

这张表只做第一轮筛选。真实选择还要看地区网络、合规、预算、团队熟练度、数据恢复目标和退出计划。不要为一个展示页自建复杂后端，也不要把支付和用户数据放在没有备份演练的练习服务器上。

## 迁移和下线

迁移可以采用逐步替换。先把新功能放到新服务，旧系统继续承担原功能。这种思路常被称为绞杀者模式，核心是分阶段控制风险，不一次推倒重来。若还要迁移已有数据，应先回填并同步变化，验证新服务读到的数据完整、及时，再逐步切换读流量。切换写入前明确哪个系统是权威写入端，安排短暂停写或可靠的同步方案，并准备失败回退，避免两个系统各自接受写入却无法合并。

下线同样要有清单。删除平台项目前，确认域名、Webhook、后台任务、存储文件、数据库备份、日志、账单和密钥都已处理。旧资源保留一段观察期。确认没有请求和回调后，再删除或归档。直接点 Delete，往往会把排错证据和回退入口一起删掉。

供应商停服、账号被锁、价格大涨、地区不可用和产品能力改变，都属于平台风险。预案可以很朴素。谁接收通知，数据如何导出，临时公告放哪里，关键服务能否降级，费用上限到哪里必须人工确认。

## 一个独立开发者的选择

假设一位独立开发者做预约小程序，第一版有登录、预约、商家图片、邮件通知和后台管理。直接买 VPS 自建全部组件，需要系统更新、数据库备份、对象存储、邮件信誉和监控，而开发者没有时间值守。

可以考虑托管后端或 BaaS。小程序客户端通过微信平台审核发布；如果另有纯前端的 Web 管理界面，可以使用静态托管，它的后端接口仍要验证管理员权限。数据库用托管服务，图片进对象存储，邮件用成熟供应商，后台任务由平台函数或队列处理。README 写清每个组件、负责人和账单入口。等业务稳定后，再评估哪些部分值得迁移或自建。

这个选择不酷，但能把风险放在可见位置。小团队最宝贵的是出事时知道该找谁、看哪份日志、从哪里恢复。拥有每一层机器并不会自动带来这种能力。

## 共同责任和变更日历

许多供应商会提到共同责任。平台负责物理设施、基础服务和部分默认安全；项目负责账号、配置、数据、权限、代码和业务流程。读条款时不要只找可用性承诺，还要看排除项。错误配置、弱密码、泄露密钥、用户误删和账单失败，通常仍由项目自己处理。

托管服务也会变化。数据库版本升级、运行时弃用、免费额度调整、证书策略变化和区域维护都可能影响项目。把这些变化放进日历。收到供应商邮件后，记录影响组件、截止日期、测试环境和负责人。不要等到旧运行时停止支持当天再改。

托管方案的最低演练包括几件事。恢复一份备份，轮换一个低风险密钥，触发一次告警，导出一份数据，关闭一个测试项目。演练用来确认控制台入口、权限和文档还有效。

## 共同故障清单

个人作品页可以接受几个小时不可用，预约、支付和企业协作系统要求更高。先定义用户能接受的中断时间和数据损失，再谈架构。目标越高，成本和复杂度越高。不能只说“最好别挂”。

共同故障清单要写出哪些故障会同时影响多个能力。同一个平台承担登录、数据库、文件和函数时，平台事故可能让整套应用受影响。同一个账号掌握域名、账单和数据库时，账号丢失也会变成系统事故。故障来源不一定马上消除，但要知道它存在。

成本也是一种停机来源。信用卡过期、预算上限触发、团队席位失效，都可能让服务停摆。账单联系人至少两个，预算告警要发到有人看的地方。删除资源前先确认备份和依赖，别把省钱动作变成下线事故。

## 退出服务的清单

决定离开一个托管平台时，先列资产。数据库、文件、域名、证书、环境变量、队列、函数、用户账号、日志和账单记录都可能在平台里。很多迁移失败，问题不在导出数据，常常在忘了某个边角功能还挂在旧服务上。

退出清单至少包含三类验收：新服务能读旧数据，用户能继续登录，旧平台的收费资源和订阅已逐项处理。停止应用不一定停止计费，保留的磁盘、快照、存储和套餐仍可能产生费用；应核对最终账单，并确认没有非预期的新费用。若登录供应商改变，还要处理用户标识映射和会话失效。若文件域名改变，还要处理旧链接、缓存和搜索引擎引用。

不要把供应商后台当作唯一文档。服务名、区域、套餐、负责人、恢复办法和替代方案都要进项目文档。这个文档平时看着笨，事故发生时会让团队少翻很多聊天记录。

## 账号交接

平台依赖常常藏在个人账号里。域名在谁名下，云服务绑定哪张卡，短信签名由谁审核，邮件域名的 DNS 谁能改，应用商店和小程序后台谁是管理员，这些问题平时不显眼，离职、换岗或账号丢失时会立刻变成故障。

团队项目至少准备两个管理员。账单联系人、域名联系人和安全通知联系人都要能收到邮件。重要操作使用团队账号或组织空间，不把生产资源放在个人练习账号里。必须使用个人实名账号的平台，也要在文档里写清授权关系和交接办法。

交接不是共享密码。密码管理器、组织权限、紧急联系人和操作记录更可靠。交接时确认登录入口、二次验证设备、备用邮箱、账单状态和资源列表。确认完再移除旧负责人权限。这样做有点麻烦，但比事故当天找不到验证码轻松得多。交接清单至少每季度看一次。

## 本章验收清单

能列出计算、数据库、文件、域名、身份、日志、备份、监控和费用的负责人。知道托管减少操作量，不取消数据模型、权限和恢复责任。自建前能说明补丁、备份、监控和故障处理怎样做。平台依赖有分层和出口。删除或迁移前有清单。

AI 可以帮你把方案拆成责任表、费用表和退出清单。不要把生产账号、账单权限、密钥和客户数据交给它。真正选择平台前，由负责人确认价格、地区、备份、支持、合规和下线办法。下一章进入 VPS 和云服务器购买参数。
