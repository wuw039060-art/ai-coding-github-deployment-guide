# 托管方案、自建方案和平台依赖

托管服务让供应商运行基础设施，自建让项目团队直接运行服务器和软件。两者没有免责任方案，只是责任分配不同。个人项目常从托管开始，因为上线快、维护入口清楚。自建适合需要特定运行环境、成本模型、网络控制或团队已有运维能力的情况。为了“完全掌控”购买 VPS，却没有备份、补丁和监控，实际控制力很弱。

## 把系统拆成责任项

应用至少包含计算、数据库、文件存储、域名、TLS、身份、日志、备份、监控和费用。托管平台可能处理服务器硬件、操作系统、数据库进程和自动备份。你仍处理数据模型、权限、密钥、业务监控和恢复验证。

自建时还要负责系统更新、防火墙、进程、磁盘、证书、容量和安全事件。第六卷会逐项展开。选择之前给每项写负责人。空白项不会因项目很小而消失。

供应商安装数据库、管理高可用基础设施、提供监控和备份入口。团队能把时间放在数据模型与产品；连接地址、账号和资源上限仍需配置；错误的公网暴露和宽权限不会被托管自动修正；备份功能要查频率、保留和恢复方式。PostgreSQL 官方列出多类备份方法，供应商计划只覆盖其中部分。

升级窗口、扩容和故障转移行为也要测试。托管减少操作量，不代表零停机承诺。

## 自建数据库增加什么

你要安装受支持版本、配置存储与内存、限制网络、创建受限用户、监控连接与查询、安排备份和升级。磁盘满会让写入失败，证书过期会断开连接，系统补丁需要维护窗口。单台服务器故障时，应用和数据库可能一起离线。

复制、高可用和时间点恢复是独立工程。个人项目若无法演练，使用成熟托管服务通常更稳妥。自建也提供更大配置自由和固定资源成本，前提是团队愿意承担持续值守。

托管 PostgreSQL 主要提供数据库。BaaS 还组合 Auth、Storage、Realtime 和 Function。组合减少集成工作，也让账号、区域和权限集中。一个平台事故可能同时影响登录、数据和文件。

采用 BaaS 时仍可把核心业务封装在自己的 API 后面，或直接使用客户端 SDK。前者迁移边界更清楚，后者开发更快。小项目可以直接用 SDK，但把权限规则、数据模型和导出脚本留在版本控制。

## 平台依赖有哪些层

第一层是数据格式。标准 SQL 与普通对象文件相对容易导出，专有文档结构需要转换。第二层是 API 和 SDK。大量客户端代码使用供应商查询与实时监听，迁移要重写。第三层是身份。密码哈希、联合身份、MFA 和会话无法只靠用户表迁移。

第四层是运维。日志、告警、函数触发、计划任务和秘密都需要重建。第五层是组织。团队已经熟悉控制台、权限和账单，迁移也有学习成本。

完全没有供应商依赖很难。自建仍依赖 Linux、云主机、域名、开源数据库和备份存储。关键是依赖是否可见、价值是否值得、退出是否可承受。记录替代方案和最大迁移时间。使用标准 PostgreSQL 能降低数据层迁移难度，仍需处理 Auth、Storage 和边缘函数。Supabase 的架构就清楚展示这些附加组件。

Firestore 的文档查询、离线和实时 SDK 带来产品能力，也增加客户端与规则迁移工作。

## 退出计划的最低内容

列出能否导出数据库、用户、文件、日志和配置。记录导出格式、频率和最近一次测试。列出域名怎样切换，旧 API 怎样兼容，移动 App 是否需要发布新版。用户不会同时升级。准备一个供应商自带地址或维护页，用于迁移窗口。重要回调与 Webhook 更新清单不能漏。

退出计划不要求现在搭第二套生产系统。先保证数据可取、配置可重建、责任人清楚。

托管账单看起来高，自建云主机月费看起来低。比较时还要计入更新、监控、备份、事故和学习时间。自建数据库每月节省一些费用，却需要一次深夜恢复，成本可能远高于差价。反过来，稳定高用量在按请求计费平台上可能昂贵，固定资源自建或专用托管更合适。

用真实用量估算存储、带宽、读写、计算、备份和支持。价格统一标注查询日期。

## 免费额度怎样看

免费层适合练习和早期验证，常有休眠、资源、带宽、构建、地区和商业使用限制。产品进入真实用户阶段前，按预期增长模拟超额费用。设置硬限制或预算告警。免费政策随时可能调整。本书截至 2026 年 8 月 5 日只记录方法，不承诺任何平台永久免费。

账号升级还涉及支付方式、税费和币种。中国大陆用户要核对可用性和付款渠道。

数据库和对象存储通常在创建时选择地区，后续迁移可能复杂。先考虑主要用户、应用服务距离和数据驻留要求。备份和日志可能位于另一区域。供应商的“项目区域”不一定覆盖所有子服务。处理个人信息、健康、金融或儿童数据时，根据适用法律、合同和行业规则获得专业意见。

自建服务器也不自动合规。控制权增加，审计和保护责任也增加。

## 服务等级与支持

查看状态页、历史事故、支持渠道和服务等级。免费社区支持与付费响应不同。供应商 SLA 常有适用条件和赔偿上限，不等于业务一定可用。自己的应用、DNS 和数据库错误不属于供应商故障。关键项目需要联系人、升级渠道和事故通知。个人项目至少订阅状态更新。

选择小众服务时评估维护活跃度、数据导出和公司持续性。不要只看首页功能数量。

第一阶段用托管 PostgreSQL、对象存储和平台函数完成预约 MVP。数据关系明确，团队不用维护服务器。第二阶段用户增长，后端迁到长期 Web Service，数据库继续托管。应用层变化，数据层不同时迁移。

第三阶段文件处理量增加，加入独立 Worker 和队列。对象存储继续作为权威文件位置。只有当数据库成本、配置或合规出现明确需求时，团队才评估迁移或自建。每次只改变一个主要边界。

## 一个错误的自建理由

开发者担心平台锁定，把数据库、文件和邮件全部放进一台廉价 VPS。没有异地备份，上传文件和数据库同盘。磁盘故障后，代码仍在 GitHub，用户数据和文件一起丢失。所谓自建控制没有转化为恢复能力。

更可靠方案可以是托管数据库加对象存储，或自建后配置独立备份与恢复演练。供应商数量不是可靠性的唯一指标。控制意味着能观察、更新、备份、恢复和退出。只有 root 密码不够。

另一个团队认为 BaaS 会自动保护数据，把所有表规则设为公开方便开发。上线后用户可读取他人资料。平台正常运行，事故来自项目权限。修复需要立即收紧规则、检查访问日志、通知受影响用户并轮换可能暴露凭据。

托管只接管约定基础设施，业务授权仍属于开发团队。选择任何平台都要用未登录和两个账号测试权限。

## 决策表

| 条件 | 倾向托管 | 倾向自建 |
| --- | --- | --- |
| 团队没有运维经验 | 是 | 风险高 |
| 需要快速验证 | 是 | 准备较慢 |
| 需要特殊系统配置 | 可能受限 | 可评估 |
| 有稳定高用量 | 比较计划 | 比较固定资源 |
| 有数据驻留要求 | 查供应商区域 | 自担合规与审计 |
| 要求深度可控恢复 | 查托管能力 | 需自建完整机制 |

决策表给出调查方向，不直接输出供应商答案。每项都要用当前合同、文档和测试验证。

选一个虚构留言板，只实现注册、私人留言和图片上传。分别记录托管方案与自建方案的设置步骤。托管方案测试账号、权限、备份导出、费用告警和删除项目影响。自建方案只在隔离服务器测试安装、更新、备份和恢复时间。

比较总工时、可恢复性、权限和月度成本。不要把一次安装成功当成三年维护成本。试验结束清理测试数据和密钥，保留决策记录。

## Shared Responsibility

共享责任模型说明供应商与客户各自负责哪些层。云厂商保护数据中心，不会替你决定谁能看订单。托管数据库可能负责补丁，客户负责账户、网络允许列表、Schema 和数据。BaaS 可能负责认证协议实现，客户负责启用哪些登录、规则和账号恢复。

每项能力在合同与官方文档中确认，不从“托管”两个字推断。

| 项目 | 托管常见责任 | 项目团队责任 |
| --- | --- | --- |
| 基础硬件 | 供应商 | 选择区域与计划 |
| 数据库进程 | 供应商或共同 | Schema、查询、账号 |
| 应用代码 | 团队 | 全部业务验证 |
| 数据权限 | 提供机制 | 设计、测试与审计 |
| 备份 | 可能提供 | 配置、监控、恢复演练 |
| 域名 | 提供绑定 | 注册、DNS、续费 |
| 费用 | 计量与账单 | 预算与异常处理 |

实际平台可能不同。把矩阵作为提问表，再填当前答案。

## 构建与购买的边界

自建身份系统涉及密码、MFA、恢复、攻击防护和合规，个人团队通常优先托管。简单业务 API 反而适合自己写，因为规则独特且代码不多。数据库基础设施成熟度要求高，托管常有价值。特定扩展或隔离要求可能推动自建。

选择每一组件，不必整个系统全部托管或全部自建。

前端在静态平台，API 在托管 Web Service，数据库为托管 PostgreSQL，文件在对象存储。这已经是常见混合。自建 API 也可调用托管 Auth。此时验证 Token 的密钥和可用性成为依赖。

组件之间跨区域会增加延迟和费用。日志与请求 ID 要跨平台传递。混合减少单一锁定，也增加多供应商账号和故障。按具体收益采用。

## 迁移的 Strangler Pattern

迁移可先让新系统接管一小类请求，旧系统继续服务其他路径，逐步扩大。入口按路由切分，数据同步需明确单一写入来源。两个系统同时改同一订单会冲突。每阶段有回退和验收，旧能力确认无人使用后下线。

这种方法降低一次性切换风险，也延长双系统维护期，个人小项目未必需要。

业务代码通过小型存储接口调用对象服务，可以减少供应商 SDK 散落。接口只包含项目真正用到的上传、读取和删除。为了假想迁移复制整个供应商 API，会过度复杂。先隔离最关键边界。数据库使用标准迁移与 SQL，供应商特性集中在明确模块。函数触发写成可测试业务函数。

可移植性靠实际导出和替换试验验证，不能只看抽象类存在。

## 供应商停服预案

订阅状态页，保存支持联系人和项目编号。故障时确认范围，不连续改配置。非关键服务降级。邮件队列等待，AI 功能暂时关闭，核心订单继续。数据库不可用时通常停止写入，不能把请求写到单机内存假装成功。

恢复后控制积压重放，并核对幂等与数据一致性。

平台管理员开启 MFA，使用密码管理器和最小成员权限。恢复码离线保存。GitHub、云平台、域名和邮件账号不要全部依赖一个不可恢复邮箱。定期审查 OAuth App、API Token 和服务账号。离职与设备丢失触发撤销。

账单联系人与技术管理员至少有明确备份责任人。

## 删除项目的退出清单

导出数据库和文件，验证恢复。导出 Auth 与抑制名单等附加数据。移除自定义域名、Webhook、移动 App 配置和第三方回调。撤销 API Key 与服务账号。取消计划前查询最终账单与备份保留。删除后项目 ID 可能无法恢复。

操作由项目所有者确认，记录完成时间和不可恢复内容。

操作系统、数据库、反向代理和应用运行时都有安全支持周期。列出版本和维护窗口。订阅安全公告，先在测试服务器更新，验证启动、备份和回滚。长期忽略升级会跨多个大版本，迁移风险积累。自动安全更新也要知道重启行为。

第六卷会建立每周、每月和季度维护清单。

## 托管的变更日历

供应商也会升级运行时、弃用 API 和调整计划。订阅 Changelog 与邮件。弃用通知记录负责人、截止日期和测试计划。不要等服务关闭才处理。平台自动升级数据库前，阅读兼容说明并在副本验证。

账单和免费额度变化纳入季度复查。

商业项目查看数据处理协议、子处理商、删除、导出、事故通知和支持条款。营销页面不能代替合同。需要认证或合规证明时从供应商官方信任中心取得当前文件。自建也需要云主机和备份供应商合同，并自行完成更多控制。

本书提供技术通识，不替代法律和采购审查。

## 一个费用迁移案例

图片应用在 BaaS 上增长，下载带宽成为主要费用。团队先优化缩略图、缓存和重复请求，账单明显下降。随后评估把公开图片迁到更合适对象存储，数据库和 Auth 保持不变。通过新 URL 逐步切流量。

没有因为一项费用立刻重写整个后端。优化和局部迁移的工时低于全面替换。决策记录使用三个月真实用量，不基于单日峰值。

团队自建 PostgreSQL 后发现无人能在故障时恢复，补丁长期拖延。他们决定迁回托管。先在托管服务创建测试实例，从备份恢复并运行应用。设置网络、用户和监控。安排短暂停写，完成最终增量与校验，切换连接。旧实例保留只读观察期。

迁回托管不是失败。它让责任与团队能力重新匹配。

## 可用性目标

定义核心能力允许中断多久，哪些功能可以降级。展示页、登录、支付和后台报表等级不同。目标越高，冗余、监控和值守成本越高。个人项目可以诚实选择较低目标，并提供状态说明。供应商 SLA 只是一个输入，系统可用性还受代码、域名和数据影响。

每季度用真实事故和维护时间比较目标，不用首页宣传语代替。

## 单点清单

列出唯一管理员、唯一邮箱、唯一数据库、同盘备份、单一 DNS、唯一支付方式和无人维护脚本。单点不一定立即消除。先标出影响和恢复方式，优先处理不可恢复数据与账号。添加第二管理员要遵循最小权限，不能为冗余给所有人最高权力。

备份账号与恢复联系人定期验证可用。

在测试 VPS 从空系统部署应用，配置防火墙、HTTPS、服务、日志和备份。记录总时间。重启服务器，确认应用和数据库自动恢复。模拟磁盘接近上限与服务崩溃。从异地备份恢复到另一台测试服务器，切换测试域名并验收。

没有完成这些演练时，不把单机自建用于唯一生产数据。

## 托管前的最低演练

创建测试项目，限制成员和预算。部署后导出数据与文件，恢复到第二测试项目。撤销一个客户端会话和服务密钥，确认轮换流程。模拟规则错误并恢复版本。查看状态页、支持和账单导出。删除测试项目以前验证域名与 Webhook 已解除。

托管的核心验收是权限、恢复和退出，不只是创建速度。

写业务目标、预计用户与数据、团队能力、候选方案、当前价格查询日期和主要风险。对每个候选填写数据模型、地区、权限、备份、恢复、费用、支持和退出。未知项不能当作零风险。记录选择理由、未选择理由和重新评估触发条件，例如月账单、连接数或合规变化。

批准人和复查日期明确，半年后不用从聊天记录重建决策。

## 综合例子　独立开发者的选择

一名独立开发者制作小型课程预约，预计数百用户，没有服务器值守经验。需求包括登录、关系数据、邮件和少量图片。他选择托管 PostgreSQL、Auth 和对象存储，应用部署在自动平台。邮件使用外部服务，失败进入队列。

选择理由是数据关系清楚、恢复入口可测试、个人能维护。没有因为未来可能扩张自建集群。每月导出数据库和对象清单，季度恢复。账单或平台限制超过记录阈值时，再评估迁移。这项选择有平台依赖，也有明确退出路径。可见、可测试的依赖比口头追求“零锁定”更实用。

每个组件都有供应商与团队责任、负责人、备份、费用和退出。选择基于真实需求与能力。托管方案完成权限和恢复演练，自建方案完成重启、更新和异地恢复演练。未验证项清楚标记。决策记录包含查询日期和复查条件，用户能判断何时需要改变，而非被某个平台永久绑定。

AI 可以生成责任矩阵、平台退出清单、费用模型和迁移风险表，也能根据官方文档找出未回答条件。它不能保证供应商长期价格和政策，也不能替团队承担夜间运维。最终选择由预算、数据和人员责任共同决定。

亲自测试数据导出与隔离恢复，核对账号权限、地区、计划和账单。为每个组件写负责人和故障入口。若选择自建，确认有人持续处理更新、监控和备份。若选择托管，确认业务权限和退出不被忽略。第五卷到这里结束。下一卷进入 Linux 与 VPS，展示自建服务器具体增加了哪些日常操作与长期责任。
