# 移动应用签名、测试与发布参考

这份参考用于 Android / Google Play 和 iOS / App Store 的操作准备。控制台页面、账号资格、测试人数、持续时间、构建工具、审核问卷和地区规则都会变化；每次真实发布都应在当天打开平台控制台与官方帮助重新核对。下面出现的日期或数字只代表 v2.2 原稿冻结时的政策样例，不是当前承诺。微信小程序不走这两家应用商店，单独见[《微信小程序开发、体验、审核与发布参考》](wechat-miniprogram.md)。

## 先区分共同模型与平台身份

两条发布线都包含应用身份、签名身份、递增构建、测试人群、商店资料、审核和上线观察，但凭据不能混用。

| 关系 | Android | iOS |
|---|---|---|
| 应用身份 | package name / applicationId | Bundle ID |
| 用户版本 | versionName | Version |
| 每次上传身份 | versionCode | Build number |
| 交付产物 | 签名 AAB | Archive / 上传的 build |
| 测试入口 | Play 测试轨道 | TestFlight 组 |
| 发布控制台 | Play Console | App Store Connect |

上传成功只是平台收到构建，不代表完成处理、通过测试、进入审核或已经对用户可用。每一步保存构建身份和平台状态。

Apple Account、开发者会员、Team、证书、Bundle ID、Capabilities 与 Provisioning Profile 是相互关联但不同的对象。第一次发布优先让 Xcode 自动管理签名；出现问题时按 Team、Bundle ID、证书私钥、设备/分发用途和权限能力逐项核对，不随机重建所有凭据。

## iOS 从 Archive 到发布

1. App Store Connect 先创建与 Bundle ID 对应的应用记录。
2. 在真机验证 Release 配置、版本、Build、权限说明和生产后端。
3. 用 Xcode Archive；在 Organizer 中核对 Team、Bundle ID、Version 和 Build。
4. 选择符合目的的分发方式并上传，保存 Organizer 或交付日志。
5. 等待 App Store Connect Processing；处理失败与“仍在等待”分开排查。
6. 回答 Export Compliance 等实际适用问题，把 build 加入内部 TestFlight 组。
7. 测试首次安装、旧版升级、登录、核心读写、权限拒绝、弱网与崩溃反馈。
8. 需要外部测试时提供 What to Test、测试账号与环境条件，并完成 Beta Review。
9. 选择验证过的 build，补齐版本资料与审核说明，确认真正提交 App Review。
10. 按批准的自动、手动或分阶段方式发布，观察客户端与后端。

Archive succeeded、upload succeeded、Processing 完成、Ready to Test、进入审核和商店可用是不同状态。构建没有出现时先确认正确 Team 和应用，再比对 Bundle ID、Version、Build 与交付历史。相同 Build 不能靠改文件名重新上传。

## TestFlight 与审核清单

- 内部测试者属于 App Store Connect 团队；只为测试加入的人使用最低角色并在结束后移除。
- 外部测试者、公开链接、测试期限和人数属于易变规则，以当前账号页面为准。
- What to Test 写具体任务、已知限制和反馈入口，不写“请测试”。
- 测试反馈关联 Version、Build、设备、系统、时间和步骤；崩溃符号化要匹配正确 Archive 与 dSYM。
- 审核账号在审核地区、时区和网络中可用，不依赖办公室 IP 或夜间关闭的测试环境。
- Resolution Center 回复原始问题、修复位置和复现步骤，不生成未经确认的政策承诺。
- App Store 没有把已安装坏 build 直接降回旧二进制的传统回滚；分阶段发布、后端兼容、功能开关与更高 Build 修复共同构成恢复能力。

包名必须和 AAB 一致，并承担长期更新身份。商店展示名可以变化，包名、签名链和版本代码不能当普通文案处理。上传证书用于证明提交者，Play 应用签名证书用于最终分发；第三方登录、地图、推送等服务要求指纹时，要确认它需要哪一张证书。

## 内部测试最小流程

1. 打开正确的 Play 应用记录，确认开发者主体与包名。
2. 进入 Internal testing，创建或选择测试轨道。
3. 用邮箱列表或群组配置测试者，记录他们实际使用的 Google 账号。
4. 创建 Release，上传已签名 AAB；保存包名、版本代码、签名、目标 API 的处理结果。
5. 写有任务的 Release name / notes，不写“测试一下”。
6. 复核轨道、制品和测试者范围，由授权人员发布到内部测试。
7. 测试者用名单中的账号接受邀请，从 Google Play 安装。
8. 在真机记录 versionName/versionCode，完成首次启动、登录、核心读写、关闭重开和退出。
9. 至少用一个旧 build 验证升级与旧数据兼容。

Release notes 可以这样写。

```text
版本 1.2.0 (17)

请重点检查
1. 首次登录后创建一条购物记录
2. 关闭网络后新增记录，再恢复网络
3. 从 1.1.0 升级，确认旧记录仍在

已知限制
平板横屏页面仍在调整
```

## 测试者找不到应用

按顺序核对这些事项。

- 浏览器和 Play 商店 App 是否登录同一个、且已加入名单的 Google 账号。
- Release 是否真正发布到目标轨道，而不是草稿、处理中或等待补充任务。
- 邀请链接是否属于正确应用和正确测试方式；Internal app sharing 与 Internal testing 不是同一通道。
- 账号国家/地区、设备、最低系统、ABI、屏幕和硬件能力是否在支持范围。
- 设备是否装有同包名但不同签名来源的版本。
- Play 处理是否仍在进行；不要用相同 versionCode 反复上传。

记录失败账号、设备、Android 版本、时间、页面状态与实际 build，避免只说“链接打不开”。

## 上传错误对照

| 提示 | 正确处理 |
|---|---|
| versionCode 已使用 | 提高项目内的 versionCode，重新构建；改文件名无效 |
| 包名不匹配 | 核对当前 Play 应用和构建配置；不改已发布应用身份来迁就上传 |
| 签名证书不匹配 | 核对上传密钥与控制台记录；遗失时走官方重置流程 |
| target API 不足 | 升级项目设置并重新测试权限、后台、存储等行为 |
| 权限/政策警告 | 回到真实应用行为、SDK 和披露；不删文字掩盖收集 |
| 设备不支持 | 查设备目录中的系统、ABI、功能和排除原因 |

AAB 被接收只是静态与轨道门槛的一部分，不证明应用在目标设备、正式签名和真实后端上可用。

## 轨道与生产访问

内部、封闭、开放、生产的区别是影响范围和准入责任，不是一条每个项目都必须完整走过的直线。封闭测试适合受控扩大设备与场景；开放测试适合公开招募，随之增加支持和商店资料责任；生产是面向公众的外部状态变化。

v2.2 原稿在 2026-08-05 记录过“部分新个人账号需要至少 12 名测试者连续选择加入 14 天”的封闭测试样例。执行时不要引用这个数字安排发布日期，应以账号自己的 Dashboard 和当日官方政策为准。生产访问申请应使用真实测试记录回答招募、参与、反馈、修复和准备情况，不生成夸张故事或购买虚假测试者。

## Data safety 与 App content

先建立产品事实表，再填控制台。

- 哪些数据离开设备，由应用还是第三方 SDK 接收。
- 数据用于核心功能、分析、广告、账号还是其他目的。
- 是否关联身份、是否加密传输、能否请求删除。
- 应用是否包含广告、购买、儿童/健康/金融内容或用户生成内容。
- 登录审核账号能访问什么，如何避免使用生产管理员权限。

SDK 版本和远端开关会改变实际行为。开发、产品、运营与法务分别确认自己的事实，由有权限的人提交。Dashboard 的绿色勾选表示任务已提交或条件满足，不证明回答准确。新增功能或 SDK 后重新审查相关表单。

## 商店资料、市场与定价

应用名、说明、图标、Feature graphic、截图、分类、联系信息和隐私政策应与当前 Release 一致，不含真实用户数据。多语言资料要逐一核对，默认语言完成不代表其他语言没有旧截图。

国家/地区会改变内容、支付、税务、退款和支持责任。不要默认首日全球开放。免费、付费、订阅和应用内购买使用 Play 当前提供的测试机制；不要向测试者收真实费用后人工退款。本手册不保存固定费率。

## 发布前最终复核

- 轨道是内部、封闭、开放还是生产，影响范围是否符合批准。
- 制品要核对包名、versionCode、versionName、目标 API、支持设备、签名与校验和。
- 人群要看测试者或国家/地区是否意外扩大。
- 内容要看 Data safety、权限、广告、分级、隐私政策、支持入口和审核账号。
- 时间要看审核通过后是否自动公开，managed publishing 或分阶段策略如何设置。
- 后端要确认容量、备份、监控、兼容旧客户端和支持渠道是否已运行。
- 责任人要明确。AI 可以准备草稿，最终 rollout 由账号授权人员检查并确认。

保存最终摘要时脱敏。审核耗时不能写进硬性承诺；提交成功只说明进入平台流程。
