# 测试、监控与事故参考

这份参考把 AI 变更证据、CI 细项、证据保留和 SLO 计算集中在一起。主书负责解释选择，本文负责留下可复查格式。

## 变更前记录

```text

失败行为：
必须保持不变：
风险等级与理由：
允许读取：
允许写入：
允许执行：
允许联网或外部状态变化：
当前分支 / 提交：
已有未提交修改：
基线测试与可见行为：

```

读取、写文件、执行代码、联网和改变外部系统是不同权限。凭据只授予任务所需资源、环境、动作和有效期；不要把生产令牌写入对话、Diff、日志或快照。现有未提交文件默认属于用户，不能覆盖或回退。

## Diff 审查

先看文件列表与增删规模，再逐块问：

1. 这段变化对应哪条验收标准？
2. 正常路径和失败路径分别怎样？
3. 权限、数据、费用和外部状态有何变化？
4. 哪个测试或人工步骤覆盖它？
5. 如何恢复？

发现任务外文件、秘密、二进制、生成噪声、锁文件大改或全仓格式化时暂停。删除验证、错误处理、兼容层、日志和回退代码时，必须说明替代机制。新增依赖、迁移、权限或公共接口应触发重新计划。

## 测试分层与记录

静态检查、单元、集成、端到端、平台分发和真实设备回答不同问题。先运行与改动最相关的快速检查，再扩大到相邻模块与完整套件。修 Bug 时先让复现测试在修复前失败；无法自动化的流程记录环境、步骤、预期、实际和不能自动化的原因。

```text
提交或工作区状态：
操作系统与运行时：
命令：
开始与结束时间：
退出码：
通过：
失败：
跳过：
警告：
报告或截图：
测试数据与环境：
仍未验证：
```

退出码 0 只表示工具认为成功。确认测试数量、目标文件、跳过项和警告；错误筛选匹配到零个用例也可能绿色。移动应用还要注明模拟器、真机、内部测试或商店构建，不能用 Android 结果代替未验证的 iOS 发布。

## CI 与当前版本对应

CI 结果必须绑定当前提交 SHA、触发事件、矩阵任务和构建产物。绿色可能来自 skipped、neutral、缓存产物或旧提交，不能只看颜色。关键发布记录提交 SHA、构建号、镜像摘要、部署 ID 或应用 versionCode；可变的 `latest` 标签不足以证明测试过哪一份产物。

本地通过而 CI 失败时比较操作系统、大小写路径、运行时、依赖锁、环境变量、时区和外部服务。CI 通过而生产失败时比较真实构建、部署配置、数据库版本、网络与数据规模。预览环境只有在资源和数据真的隔离时才是安全试验场。

## 不稳定测试、覆盖率与缓存

同一提交在相同环境时过时不过，应保存每次结果、随机种子、并发、机器和发生频率。不要重跑到绿后删除首次失败。当前改动造成的不稳定不能以一次通过放行；既有问题也要说明是否覆盖当前风险。

覆盖率说明代码被执行，不说明断言正确、越权被阻止或需求完整。测试必须有会因错误行为失败的断言，Mock 不能代替真实文件、数据库和 HTTP 边界。修改覆盖率阈值或排除目录属于需评审的行为变化。

缓存清理会改变状态。先保存原始错误、确认目录可重建且不含用户数据、签名或唯一产物，再做精确清理。关键发布至少有一次从锁文件干净构建，并确认缓存键包含会影响产物的配置。

## 证据隐私与中断恢复

CI 日志、截图、HAR、崩溃报告和数据库样本可能含秘密或个人数据。证据索引记录文件、版本、环境、生成时间、用途、访问范围和删除日期。哈希只证明文件未变，不证明内容正确。

命令超时或平台返回失败，不等于没有副作用。重试前检查工作区、进程、临时文件和外部平台实际状态：邮件是否发出、迁移是否执行、资源是否创建、DNS 是否更新。可用事务、原子替换、不可变产物和幂等键降低未知状态；不支持时写清查询与补偿动作。

并行检查必须绑定同一基线。任何检查修改文件后，旧报告可能过期；最终由一个集成人把静态检查、测试、界面 QA、安全评审和人工结论汇合到同一提交与产物。

## 风险强度

- **低风险**：文案、无行为说明、隔离测试数据。常用 Diff、构建和页面检查。
- **中风险**：业务逻辑、依赖、缓存、普通 API。增加相关测试、预览与代码评审。
- **高风险**：认证、权限、生产数据、支付、秘密、网络入口、迁移和不可逆删除。需要独立评审、恢复证据、受保护部署、人工批准和发布观察。

等级取决于最坏后果、影响范围、可恢复性和不确定性，不取决于行数。一行防火墙规则可以是高风险，一百行隔离测试可能较低。

## 回滚与发布观察

```text

代码或制品回退步骤：
配置回退步骤：
数据库兼容或补偿：

```

共享历史通常用新提交撤销比强制改写更安全，但应服从项目规则。回滚后仍要测试和观察；“命令执行成功”不等于流量、数据和用户版本已经恢复。

## SLI / SLO / Error Budget 计算卡

可用性 SLI 的基本形式：

```text
SLI = good events / valid events
```

先定义 valid：是否排除内部探针、明显无效请求、用户主动取消和计划维护。分母改变会直接改变结果，必须版本化定义。

SLO 必须同时写指标、目标、窗口和适用范围，例如“28 天滚动窗口内，有效视频播放启动请求中 99.5% 在 2 秒内成功”。请求型与时间型目标不能混写；低流量服务只按整分钟可用可能掩盖关键用户失败。

错误预算：

```text
allowed bad events = valid events × (1 - SLO target)
remaining budget = allowed bad events - observed bad events
```

示例：28 天有 200,000 个有效请求，SLO 为 99.5%，允许坏请求 `200000 × 0.005 = 1000`。已发生 650 个坏请求，剩余 350 个。若 1 小时内发生 100 个坏请求，它消耗了整个窗口预算的 10%；是否停止发布由预先约定的预算政策决定。

预算消耗速率用于发现“短时间烧得过快”。简化表达为观察窗口中的实际坏比例除以 SLO 允许坏比例。它不是单独的服务质量目标，应与短、长窗口和最小事件量结合，避免低流量下一个失败产生噪声。

SLA 是面向客户的合同或服务约定，可能包含计算口径、排除条件、赔付和申报流程。SLO 是团队内部目标；两者数值可以不同，不能把内部仪表盘直接当合同结论。

## SLO 最小落地清单

1. 选一个真实用户动作，例如“登录成功”或“视频在 2 秒内开始播放”。
2. 写出 good/valid 定义与数据来源。
3. 用一小组手工标注的成功、业务失败、超时、取消和无效样本核对查询。
4. 选择目标与滚动窗口，计算一组手工可复核的数字。
5. 写预算消耗后的动作：继续发布、加强评审、暂停高风险变更或优先可靠性工作。
6. 记录指标局限、低流量处理、数据延迟和谁有权修改定义。

小型低风险项目可以先只记录一个诚实 SLI 和样本，不必立刻建立完整 SLO/SLA 体系。涉及付费承诺、多人值班或显著用户影响时，再补充预算政策、告警与正式责任。
