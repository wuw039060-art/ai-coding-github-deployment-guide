# Git 与 GitHub 操作参考

这份参考承接 Git、GitHub 网页与 GitHub Desktop 的具体操作。主章负责解释版本、边界与协作模型；按钮名称、认证方式和平台规则可能变化，实际操作时以当前客户端和官方文档为准。

## 先做仓库身份卡

```text
项目用途：
本地目录：
远程仓库 URL：
仓库所有者：个人 / 组织
可见性：公开 / 私有
默认分支：
当前分支：
部署是否跟随某个分支：
秘密与本地数据位置：
备份或归档方式：
```

文件夹、Git 仓库和 GitHub 仓库不是同一个对象。本地保存只改变磁盘；提交把一组变化写入本地历史；推送才把提交发送到远程。部署平台还可能在收到提交以后单独构建。排错时先说明停在哪一层。

## 命令行最小工作流

在项目根目录先观察，不要把互联网上的命令整段粘贴执行。

```bash
git status --short
git branch --show-current
git remote -v
git diff
git diff --staged
```

准备提交时只添加本次有关的路径：

```bash
git add path/to/file
git diff --staged
git commit -m "describe the change"
git log -1 --oneline
```

推送前确认远程、分支和权限：

```bash
git remote -v
git branch -vv
git push
```

`git add .`、强制推送、重写历史和递归删除会扩大影响范围。看不懂 `status` 或 `diff` 时先停下。恢复动作要根据“未跟踪、未提交、已提交、已推送”选择，不能用同一条命令处理所有情况。

## 新仓库与已有项目

空练习目录可以初始化后提交：

```bash
git init
git add README.md
git commit -m "initial commit"
```

已有远程项目优先使用 Clone，让远程地址和历史一并建立。下载 ZIP 只得到某个时刻的文件，不带完整 Git 历史。把已有本地项目连接到新远程前，比较双方是否都有提交；两边都有独立历史时，不要靠反复覆盖合并。

GitHub 网页上传适合少量非敏感练习文件。上传后检查目录层级、提交者、目标分支和实际文件内容。依赖目录、构建产物、日志、数据库、密钥和真实用户文件通常不应直接上传。

## 分支与同步

分支是一条提交工作线，不是项目的第二份自动备份。开始工作前确认基线，完成后保留可审查差异。

```bash
git fetch
git status --short
git log --oneline --decorate -5
```

拉取、合并或变基前先保存当前工作。出现冲突时，标记只说明 Git 无法自动选择；维护者必须理解两边意图、编辑最终内容、运行测试并再提交。不要为了让冲突消失而整文件选择一侧。

## `.gitignore` 最小模板

规则按项目实际生成，不盲抄。一个跨平台起点如下：

```gitignore
# 本地秘密
.env
.env.*
!.env.example

# 依赖与生成物
node_modules/
dist/
build/

# 日志与本地数据
*.log
*.sqlite
uploads/

# 编辑器与系统文件
.DS_Store
```

`.gitignore` 只影响尚未跟踪的路径。文件一旦进入历史，新增规则不会把旧内容擦掉。若提交过密钥，第一步是撤销或轮换密钥，再调查传播范围；删除最新文件不能使历史中的值失效。

## GitHub 账号、仓库与权限

- 账号代表操作身份，组织代表共同所有权；离职或交接时不能依赖某个个人账号永久在线。
- 公开仓库意味着任何人都能读取当前内容和可达历史，不等于任何人都能写入。
- 私有仓库降低公开暴露，不替代秘密管理、最小权限和备份。
- 协作者只获得完成任务所需的最低角色；管理员权限、部署密钥和自动化令牌分别管理。
- 更改可见性、转移、归档或删除前，核对 Pages、Actions、部署平台、Webhook、包和分支保护的影响。

启用双重验证并保存恢复方式。令牌和 SSH 私钥不截图、不写进仓库；授权失败时辨认自己正在用哪个账号、哪种凭据和哪个远程 URL。

## GitHub Desktop 快速路径

1. 打开正确仓库，确认 Current repository 与 Current branch。
2. 在 Changes 中逐文件看差异，取消与本次无关的勾选。
3. 写能说明原因的 Summary，提交到当前分支。
4. 观察顶部动作是 Fetch、Pull 还是 Push；先读文字再点击。
5. 推送后在 GitHub 网页核对提交 SHA 和文件，而不是只看客户端“成功”。

客户端界面简化了命令，没有改变仓库状态。Publish repository 会创建远程；Push origin 发送本地提交；Fetch 只获取远程信息；Pull 会把远程变化带入当前工作线。

## 提交与发布证据

```text
仓库 / 分支：
基线提交：
变更文件：
本地验证：
提交 SHA：
远程提交 SHA：
部署产物或页面：
仍未验证：
回退入口：
```

GitHub 显示提交不代表部署完成。部署平台、服务器和用户设备各自还可能保留旧构建或缓存；沿提交 SHA、构建 ID、制品摘要和页面版本逐层核对。

## 高风险动作前停下

以下动作必须先列出目标、影响、恢复点和批准人：强制推送、重写共享历史、删除分支或仓库、公开私有仓库、转移所有权、清理大文件历史、撤销组织访问。AI 可以解释和生成候选命令，不能替代仓库所有者确认。
